Предыдущий раздел собрал части агента на языковой модели: цикл, который читает наблюдения и выдаёт действия, инструменты со схемами, память для длинных задач, планы, рефлексию и выбор между фиксированным рабочим процессом и агентом, который сам выбирает шаги. Этот раздел пускает эти части в дело в четырёх средах задач и начинает с той, где агенты продвинулись дальше всего: с программного репозитория. Агент для программирования (coding agent) получает описание ошибки или новой возможности, читает и правит файлы, выполняет команды и останавливается, когда считает, что изменение готово. Программы — хорошая среда для агентов по причине, к которой заметка будет постоянно возвращаться: в ней есть собственный судья. Тесты можно запустить, а прошедший тест — свидетельство, которое словами модели не подделать.

**Обозначения.** Задача — это репозиторий в состоянии $R$ и описание проблемы (issue) $q$, текст, написанный человеком. Агент выдаёт патч $\delta$, а $R \oplus \delta$ — репозиторий с применённым патчем. Тест $\tau$ на репозитории либо проходит, либо падает. $T_{\text{F2P}}$ и $T_{\text{P2P}}$ — два набора оценочных тестов, определённых ниже. $B$ — бюджет шагов (step budget): число действий, которые агенту разрешено сделать. В анализе проверки предложенное исправление верно с вероятностью $c$, неверно, но проходит видимые агенту тесты, с вероятностью $h$, а в остальных случаях неверно так, что эти тесты его ловят.

## Отправная точка: найти файлы и написать патч за один раз \{#baseline-retrieve-the-files-write-the-patch-in-one-shot\}

Первый подход решает задачу как [генерацию с извлечением](/ru/notes/nlp/rag): найти лексическим поиском (BM25) файлы, больше всего похожие на описание проблемы, положить их в контекст вместе с описанием и попросить модель написать патч в формате unified diff. Цикла нет: модель ничего не запускает и не видит, применяется ли её патч.

На бенчмарке, о котором речь пойдёт ниже, этот подход проваливается почти всегда. В исходной статье о SWE-bench (октябрь 2023) лучшая модель, Claude 2 с поиском BM25, решила 1.96% из 2294 задач ([Jimenez et al., 2024](#references)). С тем же поиском GPT-4 Turbo в статье о SWE-agent (май 2024) решила 1.31%. У неудач три причины. Найденные файлы часто не те, которые нужно менять. Патч, написанный вслепую, содержит мелкие ошибки (неверный номер строки в diff, неверный отступ), из-за которых он не применяется. И ничто не сообщает модели, что её исправление неверно, потому что она никогда не выполняет код. Каждая причина указывает на то, что может сделать агент в цикле: искать и читать, пока не найдёт нужное место, править через интерфейс, который проверяет правку, и запускать код.

## Среда агента для программирования \{#the-environment-of-a-coding-agent\}

В терминах заметки [Что такое агент](/ru/notes/agents/what-an-agent-is#the-properties-of-task-environments) репозиторий частично наблюдаем (агент видит один файл или вывод одной команды за раз), в основном детерминирован (исключения — нестабильные тесты, или flaky tests, и сетевые вызовы), последователен, статичен, пока агент работает, и дискретен с огромным пространством действий. Его составляют три вещи.

- **Репозиторий**: файлы, их история в системе контроля версий и установленные для них зависимости. Восприятия агента — виды репозитория: строки файла, список результатов поиска, содержимое каталога.
- **Оболочка** (shell): любая команда, которую мог бы набрать разработчик, от `grep` до запуска скрипта. Каждая команда — действие, а её вывод — следующее наблюдение.
- **Тесты**: программы, которые проверяют код. Именно из-за них эта среда подходит агентам. Запуск тестов — действие, наблюдение которого выносит вердикт работе самого агента; в большинстве других сред такой вердикт может дать только человек.

Действия — это вызовы инструментов в смысле заметки [Использование инструментов и вызов функций](/ru/notes/agents/tool-use-and-function-calling), а цикл — тот же, что в заметке [ReAct и цикл агента](/ru/notes/agents/react-and-the-agent-loop). Специфична для кода форма успешного эпизода; ниже она показана на маленькой задаче из раздела «Код».

1. **Локализация.** Найти код, о котором говорит описание: искать имена, которые в нём встречаются, открывать подходящие файлы и читать, пока не найдётся определение.
2. **Воспроизведение.** Превратить пример из описания в тест или скрипт и убедиться, что на текущем коде он падает. Воспроизведение превращает описание проблемы в то, что можно выполнить.
3. **Правка.** Изменить код. Хорошо спроектированный инструмент правки проверяет результат, здесь — линтером, который отклоняет правку с синтаксической ошибкой.
4. **Тесты.** Запустить тест воспроизведения и существующие тесты. Если что-то падает, вернуться к шагу 3.
5. **Отправка.** Патч $\delta$ — разница между репозиторием и его исходным состоянием.
6. **Оценивание.** Тесты, которых агент никогда не видел, решают, решена ли задача.

Не каждый агент проходит эти шаги в таком порядке, а некоторые пропускают воспроизведение. Но именно эти шаги уточняет остальная часть заметки: локализацию, правку и проверку.

## SWE-bench: что такое задача и как её оценивают \{#swe-bench-what-a-task-is-and-how-it-is-graded\}

**SWE-bench** ([Jimenez et al., 2024](#references)) превратил сопровождение программ с открытым кодом в бенчмарк. Его 2294 задачи взяты из 12 популярных репозиториев на Python, среди них Django, scikit-learn, SymPy и Matplotlib. Каждая задача построена из настоящего issue на GitHub и пул-реквеста (pull request), который его закрыл:

- **вход** — текст issue и репозиторий на коммите перед пул-реквестом;
- **эталонный патч** — изменение кода из пул-реквеста;
- **тесты** — те, что пул-реквест добавил или изменил; агент их не видит.

Оценочные тесты делят по тому, как они ведут себя до и после эталонного патча $\delta^\star$:

$$
\begin{aligned}
T_{\text{F2P}} &= \{\tau : \tau \text{ падает на } R \text{ и проходит на } R \oplus \delta^\star\} && \text{(FAIL\_TO\_PASS)} \\
T_{\text{P2P}} &= \{\tau : \tau \text{ проходит на } R \text{ и на } R \oplus \delta^\star\} && \text{(PASS\_TO\_PASS)}.
\end{aligned}
$$

Тесты FAIL_TO_PASS проверяют, что проблема исправлена; тесты PASS_TO_PASS — что не сломалось ничего, что работало раньше. Патч-кандидат $\delta$ **решает** (resolves) задачу, если на исправленном репозитории проходит каждый оценочный тест:

$$
\boxed{\;\operatorname{resolved}(\delta) = \prod_{\tau \,\in\, T_{\text{F2P}} \cup T_{\text{P2P}}} \mathbb 1\big[\tau \text{ проходит на } R \oplus \delta\big]\;}
$$

а результат системы — процент решённых задач. Произведение делает критерий строгим: патч, который исправляет ошибку и ломает один посторонний тест, не решает ничего.

**Разобранный пример.** В задаче из раздела «Код» есть функция `median`, которая возвращает `s[n // 2]` от отсортированного списка, что неверно для списков чётной длины. Её оценочные тесты:

| тест | на $R$ | на $R \oplus \delta^\star$ | набор |
| --- | --- | --- | --- |
| `test_median_even`: `median([4, 1, 3, 10]) == 3.5` и `median([1.0, 2.0]) == 1.5` | падает | проходит | $T_{\text{F2P}}$ |
| `test_median_odd`: `median([3, 1, 2]) == 2` | проходит | проходит | $T_{\text{P2P}}$ |
| `test_mean`: `mean([1, 2, 3]) == 2` | проходит | проходит | $T_{\text{P2P}}$ |

Патч `return (s[n // 2 - 1] + s[n // 2]) / 2` исправляет чётный случай и ломает нечётный, так что `test_median_odd` падает, и произведение равно 0. Патч `return sum(s) / n`, который вычисляет среднее, проходит собственный пример из описания, $(1+2+3+4)/4 = 2.5$, и нечётный тест, $(1+2+3)/3 = 2$; он падает на `median([4, 1, 3, 10])`, у которого среднее равно $4.5$, а не $3.5$. По одному описанию агент не может отличить эти патчи от правильного. Различить их могут только тесты, которых он не видит.

**Verified, Lite, Pro.** Некоторые задачи исходного набора нельзя решить по их описанию: issue неоднозначен, или скрытые тесты проверяют детали, о которых описание не упоминает (точный текст сообщения об ошибке, имя новой функции). В августе 2024 OpenAI выпустила **SWE-bench Verified** — 500 задач, отобранных 93 профессиональными разработчиками на Python: они разметили 1699 случайных задач и оставили только те, у которых описание проблемы чётко сформулировано, а тесты справедливы ([OpenAI, 2024](#references)). SWE-bench Lite (300 задач) — более раннее подмножество, отобранное простыми правилами, чтобы его было дешевле запускать. Verified стал стандартной мерой агентов для программирования примерно на полтора года, а затем насытился: в феврале 2026 OpenAI объявила, что перестаёт его публиковать. Аудит задач, на которых ошибались передовые модели, показал, что у большинства проверенных задач тесты отвергают правильные исправления или описания не задают исправление, а некоторые модели могли воспроизвести эталонные патчи по памяти — признак того, что публичные задачи попали в обучающие данные ([OpenAI, 2026](#references)). Вместо него OpenAI рекомендовала **SWE-bench Pro** ([Deng et al., 2025](#references)): 1865 задач из 41 активно поддерживаемого репозитория, большая часть которых входит в отложенные и коммерческие наборы, не опубликованные открыто. Урок относится к каждому бенчмарку курса: публичный тестовый набор — мишень, к которой дрейфуют обучающие данные, а его ошибки становятся потолком, как только модели становятся достаточно хорошими. К этому вернётся заметка [Оценка агентов](/ru/notes/agents/evaluating-agents).

## Интерфейс агент–компьютер \{#the-agentcomputer-interface\}

**SWE-agent** ([Yang et al., 2024](#references)) задался вопросом, что нужно языковой модели от компьютера, на котором она работает. Его ответ: интерфейс, спроектированный для модели, как IDE спроектирована для человека; авторы назвали его **интерфейсом агент–компьютер** (agent–computer interface, ACI). Обычная оболочка — интерфейс для людей: `cat` на файле в 2000 строк заливает контекст, правки через `sed` легко сделать неправильно и при этом не получить никакого сообщения, а `grep -r` может вернуть тысячи строк. SWE-agent заменил их небольшим набором команд:

- **просмотрщик файлов**, который показывает окно из 100 строк с номерами строк и команды прокрутки и перехода к строке;
- **команды поиска**, которые перечисляют файлы и строки, где встречается термин, а при слишком большом числе совпадений выдают сводку вместо каждого совпадения;
- **команда правки**, которая заменяет диапазон строк и запускает линтер на результате; правка, вносящая синтаксическую ошибку, отклоняется, и агент видит ошибку при неизменённом файле;
- **управление контекстом**: старые наблюдения сворачиваются в однострочную заглушку, полностью сохраняются последние пять.

Абляции на SWE-bench Lite с GPT-4 Turbo (май 2024) измеряют, сколько стоит каждое проектное решение. Полный интерфейс решил 18.0% из 300 задач; таблица даёт долю решённых задач при одном изменённом решении.

| изменение интерфейса | решено (Lite) |
| --- | --- |
| нет (полный SWE-agent) | 18.0% |
| правка без защиты линтером | 15.0% |
| нет команды правки (только инструменты оболочки) | 10.3% |
| поиск, который печатает каждое совпадение | 12.0% |
| нет команды поиска | 15.7% |
| просмотрщик на 30 строк | 14.3% |
| просмотрщик, показывающий весь файл | 12.7% |
| вся история вместо последних пяти наблюдений | 15.0% |

Выделяются два вывода. Показывать больше — не лучше: весь файл и поиск без сводки стоят дороже, чем помогают, потому что модели приходится искать нужные строки в длинном наблюдении, а длинные контексты ухудшают её внимание. Защитный механизм (guardrail) ценнее новой возможности: линтер превращает молчаливую ошибку в немедленное наблюдение. Агент только с оболочкой и той же моделью решил 11.0% задач Lite; SWE-agent решил 12.47% полного набора из 2294 задач против 1.31% у поиска с той же моделью.

<aside class="callout"><strong>Ключевая идея.</strong> Агента для программирования ограничивает не столько то, что знает модель, сколько то, что она видит, и то, как ломаются её действия. Проектируйте интерфейс для модели: короткие структурированные наблюдения; действия, которые проверяют себя и громко сообщают о неудаче; и тест, который агент может запустить, — он превращает «кажется, исправлено» в наблюдение.</aside>

Тот же урок определил устройство более поздних агентов. Для обновлённой Claude 3.5 Sonnet (октябрь 2024) Anthropic сообщила о 49% на SWE-bench Verified с ещё более простым интерфейсом, описанным в более позднем разборе: один инструмент для команд оболочки и один для просмотра и правки файлов точной заменой строки, редактор `str_replace`, которому подражает раздел «Код» ([Anthropic, 2025](#references)). Замена строки громко сообщает о неудаче, когда старый текст найден не ровно один раз, — тот же принцип, что у линтера: правка либо делает ровно то, что имела в виду модель, либо не делает ничего и объясняет почему. Некоторые прогоны занимали больше сотни шагов.

## Agentless: фиксированный конвейер как отправная точка \{#agentless-a-fixed-pipeline-as-a-baseline\}

Если агент тратит большую часть шагов на предсказуемую последовательность (найти файл, найти функцию, править, тестировать), зачем позволять модели выбирать последовательность? **Agentless** ([Xia et al., 2024](#references)) закрепил её в коде — это [рабочий процесс](/ru/notes/agents/workflows-and-protocols) в терминах предыдущего раздела — и поручил модели заполнять каждый этап:

1. **Иерархическая локализация.** Показать модели дерево файлов репозитория и спросить, какие файлы менять; затем показать скелеты этих файлов (сигнатуры классов и функций) и спросить, какие классы и функции; затем показать их код и спросить точные строки.
2. **Исправление.** Сэмплировать несколько патчей-кандидатов для выбранных мест, каждый в виде правки поиском и заменой: точные старые строки и новые, которые применяются чисто или не применяются вовсе.
3. **Проверка патчей.** Сгенерировать по описанию тесты воспроизведения, запустить их и существующие тесты репозитория на каждом кандидате, отбросить те, что падают, и выбрать среди оставшихся большинством голосов по нормализованным патчам.

С GPT-4o (июль 2024) Agentless решил 32.00% задач SWE-bench Lite, 96 из 300, в среднем за 0.70 доллара США на задачу — больше, чем любой агент с открытым кодом на тот момент. На SWE-bench Verified тот же конвейер решил 33.2% (август 2024). Сравнение с SWE-agent — не состязание двух результатов, полученных с разными моделями и в разное время; это урок о том, где должны приниматься решения. Когда шаги задачи известны заранее, записать их конвейером ничего не стоит в той гибкости, которая задаче нужна, а взамен даёт предсказуемость и меньшую стоимость. Агент со свободным выбором шагов окупается, когда задача не укладывается в конвейер: проблема, причина которой лежит не там, где её симптом; исправление, которому нужен новый файл; сбой, объяснение которого появляется только после запуска команды.

## Локализация, правка и проверка \{#localization-editing-and-verification\}

Три этапа — отдельные задачи с отдельными способами сломаться.

**Локализация** (localization) — это поиск. В репозитории из тысяч файлов агент должен найти несколько строк, которые нужно изменить. Сигналы — имена в описании (функции, классы, сообщения об ошибках), трассировка стека, если она есть, структура кода (кто вызывает функцию) и запуск воспроизведения под отладчиком или с отладочной печатью. Ошибки локализации — самая частая причина неудач: агент, который правит не ту функцию, может пройти свои тесты и всё равно ничего не решить.

**Правка** — это создание изменения, которое применяется. Распространены три формата: переписать файл целиком (просто, дорого и легко потерять посторонний код), unified diff (компактно, но номера строк и контекстные строки легко указать неправильно) и поиск с заменой точного текста (надёжно и громко сообщает о неудаче). Правка через интерфейс, проверяющий синтаксис и применимость, убирает целый класс неудач, не имеющих отношения к ошибке.

**Проверка** (verification) — это контроль изменения до отправки с единственным судьёй, доступным во время решения: тестами, которые агент может запустить. Она тоже стоит шагов, а каждый цикл работает в рамках [бюджета шагов](/ru/notes/agents/react-and-the-agent-loop#stopping-budgets-and-loops). Возьмём заскриптованного агента из раздела «Код» с бюджетом шагов $B$. Каждое предложенное им исправление верно с вероятностью $c$, неверно, но проходит его видимые тесты, с вероятностью $h$ (среднее в разобранном примере выше), а в остальных случаях неверно так, что его ловят тесты или линтер. Агент, который отправляет первую же правку, добивается успеха с вероятностью $c$. Агент, который тестирует и повторяет, останавливается на первом исправлении, прошедшем его тесты, и оно верно с вероятностью $p$, удовлетворяющей

$$
\begin{aligned}
p &= c + (1 - c - h)\, p && \text{первое исправление верно, или его поймали, и агент начинает заново} \\
\Rightarrow\quad p\,(c + h) &= c && \text{собираем члены с } p \\
\Rightarrow\quad &\boxed{\,p = \frac{c}{c + h}\,} && \text{при неограниченном бюджете.}
\end{aligned}
$$

Проверка убирает пойманные неудачи и оставляет только те, которых тесты не видят. При $c = 3/8$ и $h = 1/8$ она вдвое повышает долю успехов, с $0.375$ до $0.75$. При конечном бюджете проявляется цена:

<StepBudget />

При бюджете меньше 8 шагов агент, который тестирует, решает меньше задач, чем агент, который не тестирует, потому что тест воспроизведения и каждый запуск тестов — это шаги. При $B = 10$ он решает $0.612$, а к $B = 20$ — почти всё, что может решить, $0.747$. Два следствия верны и за пределами этой игрушечной задачи. Результат бессмыслен без своего бюджета, поскольку один и тот же агент с ростом бюджета переходит от $0.125$ к $0.75$. А потолок $c/(c+h)$ задаётся $h$ — неверными исправлениями, которые проходят собственные тесты агента: лучшая проверка означает лучшие тесты, и поэтому сильные агенты сначала пишут тест воспроизведения, а затем ищут граничные случаи.

То же рассуждение переносится с повторов на сэмплирование. Сгенерируем $N$ патчей-кандидатов параллельно, как делает Agentless, и выберем один тестами или обученным верификатором. Выбор удаётся, когда какой-то кандидат верен и верификатор его распознаёт; идеальный верификатор превратил бы вероятность того, что хотя бы один из $N$ сэмплов верен, pass@$N$, в долю успехов. Рассуждающие модели и [вычисления при выводе](/ru/notes/agents/reasoning-models) делают этот обмен вычислений на долю правильных ответов систематическим, а заметка [Обучение агентов с подкреплением](/ru/notes/agents/agentic-rl) использует те же тесты как награды.

## Песочницы \{#sandboxing\}

Агент для программирования выполняет код, который написал сам, внутри репозитория, написанного кем-то другим, командами, которые выбрала модель: это [код как действие](/ru/notes/agents/tool-use-and-function-calling#code-as-the-action) в самой открытой форме. Любая из трёх сторон может навредить: удалить файлы за пределами репозитория, прочитать учётные данные, отправить данные по сети или работать бесконечно. Поэтому агент должен работать в **песочнице** (sandbox): среде, чьи эффекты остаются внутри неё и которую можно выбросить.

Стандартный инструмент — контейнер, как в [курсе по архитектуре компьютеров и операционным системам](/ru/notes/acos/virtual-machines-and-containers#containers-one-kernel-many-views). Пространства имён (namespaces) дают агенту собственный взгляд на файловую систему, процессы и сеть, так что он видит только репозиторий и его зависимости; контрольные группы (cgroups) ограничивают его память, процессорное время и число процессов; многослойный образ позволяет каждой задаче начинаться из одного и того же чистого состояния и затем выбрасываться. Собственная программа оценки SWE-bench (evaluation harness) запускает каждую задачу в Docker-контейнере, собранном для её репозитория. Внутри контейнера агент должен работать от имени непривилегированного пользователя ([Пользователи, группы и права доступа](/ru/notes/acos/users-and-permissions)), с выключенной сетью, если задаче она не нужна, и с ограничением времени на каждую команду. Контейнер разделяет ядро с хостом, поэтому уязвимость ядра позволяет из него выбраться; для недоверенного кода в больших масштабах виртуальная машина добавляет более прочную границу, как показывает [сравнение того, что изолирует каждый из них](/ru/notes/acos/virtual-machines-and-containers#what-each-one-isolates). Запуск тестов из раздела «Код» выполняет код в том же процессе Python и песочницей не является; для игрушечной задачи, код которой мы написали сами, этого достаточно.

Песочница защищает хост от агента. Она не защищает задачу от ошибок агента внутри песочницы и не защищает агента от инструкций, спрятанных в читаемых им файлах, например от комментария в зависимости, который велит ему выгрузить переменные окружения. Эту угрозу разбирает заметка [Безопасность агентов и инъекции в промпт](/ru/notes/agents/agent-security).

## Ограничения \{#limitations\}

- **Тесты — несовершенный судья.** Тесты агента пропускают то, чего не проверяют, а оценочные тесты могут отвергнуть правильное исправление или принять неправильное. Доля решённых задач измеряет согласие с набором тестов, а не правильность.
- **Бенчмарки утекают и насыщаются.** Публичные задачи из публичных репозиториев попадают в обучающие данные; ответ на это — отложенные и закрытые наборы ценой результатов, которые другие не могут проверить.
- **SWE-bench узок.** Его задачи — на Python, из популярных библиотек, и в основном это небольшие исправления хорошо описанных проблем. Построить новую возможность по расплывчатому запросу, работать с несколькими сервисами или понять, что имел в виду пользователь, — другие задачи.
- **Стоимость и задержка.** Сотни шагов на задачу, каждый из которых перечитывает длинный контекст, стоят больше, чем стоят многие исправления; результат при неуказанном бюджете это скрывает.
- **Прошедшие тесты — не хороший код.** Патч может пройти тесты и всё же быть нечитаемым, медленным или небезопасным; ревью кода людьми остаётся частью цикла.

## Что нужно запомнить \{#what-you-should-remember\}

- Среда агента для программирования — репозиторий, оболочка и тесты; тесты делают её одной из немногих сред, где судья доступен во время решения.
- Задачи SWE-bench взяты из настоящих issue и пул-реквестов; патч решает задачу, когда проходит каждый тест FAIL_TO_PASS и PASS_TO_PASS. Verified — подмножество из 500 задач, отобранных людьми; в начале 2026 года его перестали использовать как главную метрику из-за ошибочных тестов и загрязнения обучающих данных.
- Интерфейс агент–компьютер важен не меньше модели: просмотр файлов окнами, поиск со сводкой, правки, которые сами проверяют себя линтером и громко сообщают о неудаче, и компактная история.
- Agentless показывает, что фиксированный конвейер (локализовать, исправить, проверить) — сильная отправная точка, когда шаги предсказуемы.
- Проверка поднимает потолок с $c$ до $c/(c+h)$ и стоит шагов; результат ничего не значит без бюджета, модели, обвязки, части бенчмарка и даты.
- Запускайте агента в одноразовой песочнице: контейнер на задачу, непривилегированный пользователь, сеть по умолчанию выключена, ограничения по времени и памяти.

## Код \{#code\}

Репозиторий в памяти с ошибочной `median`, критерий оценки SWE-bench, маленький интерфейс агент–компьютер (поиск, открытие, правка заменой строки с проверкой линтером, запуск тестов, отправка), заскриптованная замена модели, один эпизод с трассой и доля успехов в зависимости от бюджета шагов, смоделированная и точная. Только NumPy и стандартная библиотека; начальные значения генератора фиксированы, а точные числа могут немного различаться на разных платформах и версиях библиотек. Скрипт работает около десяти секунд.

Замена модели — фиксированная стратегия: она ищет имя из описания, открывает упоминающие его файлы в случайном порядке, пишет тест воспроизведения и сэмплирует исправления из списка восьми правдоподобных строк. Настоящая модель выбирала бы каждое действие по записи предыдущих шагов, и её исправления были бы лучше случайных; интерфейс, запуск тестов, оценка и арифметика бюджета остаются теми же.

```python
import builtins, re, types
import numpy as np

# 1. репозиторий в памяти (путь -> текст), описание проблемы и скрытые тесты, которые оценивают исправление
REPO = {
    'stats/core.py': (
        'def mean(xs):\n'
        '    return sum(xs) / len(xs)\n'
        '\n'
        'def median(xs):\n'
        '    s = sorted(xs)\n'
        '    n = len(s)\n'
        '    return s[n // 2]\n'),
    'stats/report.py': (
        'from stats.core import mean, median\n'
        '\n'
        'def summary(xs):\n'
        '    return f"mean={mean(xs):.2f} median={median(xs):.2f}"\n'),
    'docs/usage.md': 'Call median(xs) to get the middle value of a list.\n',
    'tests/test_core.py': (
        'from stats.core import mean, median\n'
        '\n'
        'def test_mean():\n'
        '    assert mean([1, 2, 3]) == 2\n'
        '\n'
        'def test_median_odd():\n'
        '    assert median([3, 1, 2]) == 2\n'),
}
ISSUE = 'median([1, 2, 3, 4]) returns 3, but the median of an even-length list is 2.5.'
FAIL_TO_PASS = ('def test_median_even():\n'                     # агент их не видит
                '    assert median([4, 1, 3, 10]) == 3.5\n'
                '    assert median([1.0, 2.0]) == 1.5\n')
PASS_TO_PASS = ['test_mean', 'test_median_odd']

# 2. запуск тестов: модули репозитория из памяти выполняются через перехват импорта (это НЕ песочница, см. заметку)
def run_tests(repo, extra=''):
    mods = {}
    def imp(name, globals=None, locals=None, fromlist=(), level=0):
        path = name.replace('.', '/') + '.py'
        if path not in repo: return builtins.__import__(name, globals, locals, fromlist, level)
        if name not in mods:
            m = types.ModuleType(name); m.__dict__['__builtins__'] = env
            mods[name] = m
            exec(compile(repo[path], path, 'exec'), m.__dict__)
        return mods[name]
    env = dict(vars(builtins), __import__=imp)
    results = {}
    files = {p: s for p, s in repo.items() if p.startswith('tests/')}
    if extra: files['hidden'] = 'from stats.core import median\n' + extra
    for path, src in sorted(files.items()):
        ns = {'__builtins__': env}
        try:
            exec(compile(src, path, 'exec'), ns)
        except Exception as e:
            results[path] = f'ERROR {type(e).__name__}'; continue
        for name, fn in ns.items():
            if name.startswith('test_') and callable(fn):
                try: fn(); results[name] = 'PASS'
                except AssertionError: results[name] = 'FAIL'
                except Exception as e: results[name] = f'ERROR {type(e).__name__}'
    return results

def resolved(repo):                     # критерий SWE-bench: проходят все тесты F2P и все тесты P2P
    r = run_tests(repo, FAIL_TO_PASS)
    return all(r.get(t) == 'PASS' for t in ['test_median_even'] + PASS_TO_PASS)

print(run_tests(REPO, FAIL_TO_PASS))
# {'test_median_even': 'FAIL', 'test_mean': 'PASS', 'test_median_odd': 'PASS'}

# 3. интерфейс агент–компьютер: поиск, открытие, правка с проверкой линтером, запуск тестов, отправка
class Computer:
    def __init__(self, repo, lint=True):
        self.repo, self.lint = dict(repo), lint
    def search(self, term):
        hits = [f'{p}:{i + 1}' for p, s in sorted(self.repo.items()) for i, l in enumerate(s.splitlines()) if term in l]
        return ' '.join(hits)
    def open(self, path):
        return '\n'.join(f'{i + 1:3d}| {l}' for i, l in enumerate(self.repo[path].splitlines()))
    def edit(self, path, old, new):
        src = self.repo.get(path, '')
        if src.count(old) != 1: return f'error: old text found {src.count(old)} times'
        text = src.replace(old, new) if old else new
        if self.lint and path.endswith('.py'):
            try: compile(text, path, 'exec')
            except SyntaxError as e: return f'error: edit rejected, SyntaxError line {e.lineno}'
        self.repo[path] = text
        return 'ok'
    def run_tests(self):
        r = run_tests(self.repo)
        bad = [k for k, v in r.items() if v != 'PASS']
        return 'all passed' if not bad else 'failed: ' + ', '.join(bad)
    def submit(self):
        return 'submitted'

# 4. заскриптованная замена языковой модели: исследует репозиторий, пишет тест воспроизведения и сэмплирует исправления
CANDIDATES = [
    'return s[n // 2] if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2',   # верно
    'return (s[(n - 1) // 2] + s[n // 2]) / 2',                         # верно
    'return (s[n // 2] + s[~(n // 2)]) / 2',                            # верно
    'return sum(s) / n',                                                # неверно, но проходит видимые тесты
    'return (s[n // 2 - 1] + s[n // 2]) / 2',                           # неверно, падает test_median_odd
    'return s[n // 2 - 1]',                                             # неверно, падает тест воспроизведения
    'return s[(n - 1) // 2]',                                           # неверно, падает тест воспроизведения
    'return s[n // 2] if n % 2 else (s[n // 2 - 1] + s[n // 2] / 2',   # синтаксическая ошибка
]
class ScriptedCoder:
    def __init__(self, rng, verify=True):
        self.rng, self.verify = rng, verify
    def run(self, issue, budget, log=None):
        pc, steps = Computer(REPO, lint=self.verify), 0
        def act(name, *args):
            nonlocal steps
            steps += 1
            obs = getattr(pc, name)(*args)
            if log is not None:
                shown = args[-1] if name == 'edit' and args[1] else args[0] if args else ''
                log.append(f'{steps:2d} {name:9s} {shown.splitlines()[0] if shown else "":40.40s} -> {obs.splitlines()[0][:38]}')
            return obs
        func = re.search(r'(\w+)\(', issue).group(1)                    # 'median'
        hits = act('search', func).split()
        files = sorted({h.split(':')[0] for h in hits if not h.startswith('tests/')})
        target = None
        for f in self.rng.permutation(files):                           # открывает найденные файлы в случайном порядке
            if steps >= budget: return False, steps
            if f'def {func}(' in act('open', str(f)): target = str(f); break
        current = 'return s[n // 2]'
        if self.verify:
            if steps >= budget: return False, steps
            act('edit', 'tests/test_repro.py', '', 'from stats.core import median\n\n'
                'def test_issue():\n    assert median([1, 2, 3, 4]) == 2.5\n')
        while steps < budget:
            new = CANDIDATES[self.rng.integers(len(CANDIDATES))]
            if act('edit', target, current, new) != 'ok': continue       # линтер отклонил правку
            current = new
            if self.verify:
                if steps >= budget: break
                if act('run_tests') != 'all passed': continue
            if steps >= budget: break
            act('submit')
            return resolved(pc.repo), steps
        return False, steps

log = []
ok, n = ScriptedCoder(np.random.default_rng(33)).run(ISSUE, budget=30, log=log)
print('\n'.join(log))
print('resolved:', ok, 'steps:', n)

# 5. успех в зависимости от бюджета шагов: моделирование и точное распределение
def exact(budgets, verify):
    pre = {1 + k + verify: 1 / 3 for k in (1, 2, 3)}                    # поиск, k открытий, (тест воспроизведения)
    if not verify:
        return [3 / 8 * sum(p for s, p in pre.items() if s + 2 <= B) for B in budgets]
    succ = np.zeros(200)
    frontier = dict(pre)                                                # число шагов -> вероятность, агент ещё работает
    while frontier:
        nxt = {}
        for s, p in frontier.items():
            succ[s + 3] += p * 3 / 8                                    # верно: правка, тесты, отправка
            for cost, q in ((2, 3 / 8), (1, 1 / 8)):                    # поймано тестами или линтером
                if s + cost < 150: nxt[s + cost] = nxt.get(s + cost, 0) + p * q
        frontier = nxt
    return [succ[:B + 1].sum() for B in budgets]

budgets = [6, 8, 10, 15, 20, 30]
for verify in (True, False):
    rng = np.random.default_rng(0)
    runs = [ScriptedCoder(rng, verify).run(ISSUE, budget=60) for _ in range(20000)]
    sim = [np.mean([ok and n <= B for ok, n in runs]) for B in budgets]
    print('verify' if verify else 'no tests', np.round(sim, 3), np.round(exact(budgets, verify), 3))
# verify [0.127 0.457 0.612 0.73  0.748 0.75 ] [0.125 0.455 0.612 0.729 0.747 0.75 ]
```
