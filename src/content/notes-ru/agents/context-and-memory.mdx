[Предыдущая заметка](/ru/notes/agents/react-and-the-agent-loop) замкнула цикл агента: модель пишет мысль и действие, среда выполнения исполняет действие, наблюдение дописывается в контекст, и модель снова принимает решение, пока не сработает правило остановки. Каждый оборот этого цикла удлиняет контекст, а модель на каждом шаге читает его целиком. Задача из нескольких шагов помещается легко. Задача из нескольких сотен шагов — исправить ошибку, затрагивающую весь репозиторий, или ответить на вопрос, для которого нужно сорок поисковых запросов, — уже нет: контекст заполняется, каждый шаг обходится дороже предыдущего, а то, как модель пользуется прочитанным, ухудшается задолго до того, как окно заполнится. Курс NLP показал, [где живёт память диалога](/ru/notes/nlp/tools-and-agents#where-the-memory-of-a-conversation-lives) и как среда выполнения обрезает диалог под бюджет токенов. Эта заметка рассматривает ту же задачу для агентов, где она острее: что содержит контекстное окно и сколько это стоит, что в него класть и в каком порядке, как сжимать старую часть, как держать вне окна память, которую агент сам пишет и читает, и как кэширование промпта меняет арифметику.

**Обозначения.** Контекстное окно вмещает $W$ токенов. **Префикс** (prefix) из $s$ токенов (системные инструкции и схемы инструментов) одинаков на каждом шаге. Каждый шаг добавляет $d = u + o$ токенов, как в предыдущей заметке: $u$ пишет модель (мысль и действие), $o$ приходится на наблюдение. $L_t$ — число токенов, которое модель читает на шаге $t$; запуск состоит из $T$ шагов. Цены указаны относительно базовой цены одного входного токена: токен, прочитанный из кэша промпта, стоит $\rho$, токен, записанный в кэш, — $\omega$. У записи $m$ в долговременном хранилище есть важность $\iota(m)$, время $\tau(m)$ последнего обращения и эмбеддинг $e(m)$; у запроса — эмбеддинг $e(q)$.

## Отправная точка: дописывать всё \{#baseline-append-everything\}

Цикл предыдущей заметки хранит каждый шаг. На шаге $t$ модель читает префикс и $t - 1$ предыдущих шагов, $L_t = s + (t - 1)\, d$, так что контекст растёт линейно, а входные токены всего запуска, как показал [разбор стоимости цикла](/ru/notes/agents/react-and-the-agent-loop#the-cost-and-latency-of-a-loop), растут квадратично:

$$
\sum_{t=1}^{T} L_t = T s + d\, \frac{T (T - 1)}{2} .
$$

**Разобранный пример.** Префикс $s = 3\,000$ токенов (инструкции и двадцать схем инструментов), $d = 1\,500$ токенов на шаг, окно $W = 128\,000$, из которых $4\,000$ оставлены свободными для ответа. Последний шаг, который помещается, — наибольшее $t$, при котором $3\,000 + 1\,500\,(t-1) \le 124\,000$, то есть $t = 81$. Восемьдесят шагов читают

$$
80 \cdot 3\,000 + 1\,500 \cdot \frac{80 \cdot 79}{2} = 240\,000 + 4\,740\,000 = 4\,980\,000
$$

входных токенов, из которых на префикс приходится меньше 5%. Один только последний шаг читает 121 500. Сразу три вещи идут не так: запуск останавливается на шаге 82, что бы ни требовала задача, стоимость шага растёт с его номером, и, как покажет следующий раздел, длинным контекстом модель пользуется хуже, чем коротким. Контекстное окно — это **рабочая память** (working memory) агента в смысле когнитивно-архитектурного взгляда на языковых агентов ([Sumers et al., 2024](#references)): всё, чем модель может воспользоваться на текущем шаге, находится в нём, и больше ничего.

<aside class="callout"><strong>Ключевая идея.</strong> Контекст — это бюджет, который среда выполнения тратит намеренно. В него кладут только то, что нужно следующему шагу, в порядке, который модель хорошо читает и который кэш может переиспользовать. Старое заменяют резюме, а то, что должно сохраниться, выносят в хранилище вне окна, откуда агент извлекает это по оценке, когда оно снова становится нужным.</aside>

## Что класть в контекст и в каком порядке \{#what-goes-in-and-in-what-order\}

Практику выбора токенов для каждого вызова стали называть **инженерией контекста** (context engineering): это поиск наименьшего набора информативных токенов, при котором желаемое поведение становится вероятным ([Anthropic, 2025](#references)). Контекст шага собирается из частей с разным временем жизни:

<ContextAssembly />

1. **Стабильный префикс** идёт первым: системные инструкции, схемы инструментов, фиксированные примеры. Он одинаков на каждом шаге, и именно поэтому его можно кэшировать (последний раздел).
2. **Найденные записи памяти** идут следом: несколько элементов из долговременного хранилища, выбранных для этого шага по оценке.
3. **Модель читает контекст и пишет действие.**
4. **Наблюдение**, возвращённое инструментом, дописывается к последним шагам.
5. **Сжатие** (compaction): когда контекст переходит верхний порог, самые старые шаги заменяются резюме.
6. **Запись в память**: то, что должно пережить окно (исход, факт о пользователе, сработавший навык), отправляется в хранилище.

Ограничение бюджета — одно неравенство: префикс, найденные записи, резюме, последние шаги и ответ должны поместиться, $s + |\text{записи}| + |\text{резюме}| + |\text{последние шаги}| + |\text{ответ}| \le W$. Каждая часть конкурирует со всеми остальными.

### Почему важен порядок: потеря в середине \{#why-order-matters-lost-in-the-middle\}

Модель читает длинный контекст неравномерно. [Liu et al. (2024)](#references) давали моделям вопрос из NaturalQuestions-Open вместе с $k$ найденными отрывками из Википедии, ровно в одном из которых был ответ, и перемещали этот отрывок с первой позиции на последнюю. [Заметка о RAG](/ru/notes/nlp/rag#building-the-context) вывела из этого исследования практическое правило; здесь — сами измерения:

<LostInTheMiddle />

С 20 отрывками (около 4000 токенов) `gpt-3.5-turbo-0613` правильно ответила на 75.8% вопросов, когда отрывок с ответом стоял первым, на 53.8%, когда он был десятым, и на 63.2%, когда последним. Совсем без отрывков, только по своим параметрам, она отвечала верно на 56.1%; с одним лишь отрывком с ответом — на 88.3%. В середине контекста отрывок был хуже чем бесполезен: без него модель справлялась лучше. Для агентов важны ещё два результата. Версии тех же моделей с более длинными окнами (16K у GPT-3.5-Turbo, 100K у Claude-1.3) давали те же кривые, так что большее окно не означает, что им лучше пользуются; и провал проявлялся у всех моделей, проверенных в 2023 году (MPT-30B-Instruct, LongChat-13B, GPT-3.5-Turbo, Claude-1.3). Исследование 2025 года, охватившее 18 более новых моделей, включая GPT-4.1, Claude 4, Gemini 2.5 и Qwen3, обнаружило, что доля правильных ответов (accuracy) падает с длиной входа даже на простых задачах, например при поиске одного предложения в длинном тексте, и падает сильнее при семантически похожих отвлекающих фрагментах ([Hong, Troynikov and Huber, 2025](#references)). Этот эффект авторы назвали **деградацией контекста** (context rot). Точные кривые зависят от модели и меняются с каждым поколением; направление сохраняется.

Отсюда четыре правила, и каждое дёшево применить:

- **Важное — по краям.** Инструкции в начале, текущая задача и самый релевантный материал в конце, рядом с местом, где модель пишет.
- **Повторять цель.** В длинном запуске исходный запрос остаётся далеко позади; агенты, которые держат в конце контекста короткий переписанный план или список дел, держат цель рядом с читателем.
- **Убирать отработанное.** Список файлов, прочитанный сорок шагов назад, редко нужен дословно; замена старых выходов инструментов однострочной заметкой («просмотрен `src/`, 212 файлов») — самая лёгкая форма сжатия ([Anthropic, 2025](#references)).
- **Меньше, но точнее.** В этих исследованиях отвлекающие фрагменты обходятся дороже, чем недостающий контекст: пять хорошо выбранных записей лучше тридцати правдоподобных.

## Сжатие: резюме старых шагов \{#compaction-summarizing-the-old-steps\}

**Сжатие** (compaction) заменяет часть истории резюме, которое пишет модель. Политике сжатия нужны четыре числа: верхний порог (high-water mark) $H \le W$, который запускает сжатие, число $k$ последних шагов, сохраняемых дословно, размер резюме $\sigma$ и то, что читает суммаризатор (старое резюме и заменяемые шаги, так что резюме рекурсивны). С порогом $H$ контекст колеблется между нижним уровнем и порогом: сразу после сжатия в нём $s + \sigma + k d$ токенов, и он растёт на $d$ за шаг, пока снова не перейдёт $H$.

**Разобранный пример.** Запуск из примера выше с $H = W/2 = 64\,000$, $k = 8$ и $\sigma = 2\,000$. На шаге 41 контекст перешёл бы порог, поэтому суммаризатор читает префикс и 33 самых старых шага, $3\,000 + 33 \cdot 1\,500 = 52\,500$ токенов, а контекст падает до $3\,000 + 2\,000 + 8 \cdot 1\,500 = 17\,000$. Затем требуется 32 шага, чтобы снова достичь порога:

За 80 шагов запуск со сжатием читает 2 791 500 токенов, и его два вызова суммаризатора — ещё 105 500, вместе 58.2% от 4 980 000 у запуска, который всё дописывает; и он не останавливается на шаге 82. За 1000 шагов контекст ни разу не превышает 63 500 токенов и в среднем составляет 39 930, так что сумма растёт по $T$ линейно, а не квадратично. Держать контекст на половине окна — выбор не только ради стоимости, но и ради качества: так модель не попадает в режим, в котором приведённые выше измерения ухудшаются.

Сжатие происходит с потерями, и то, что резюме отбросило, пропало. Ущерб уменьшают три приёма. Писать резюме по явному списку того, что сохранить (принятые решения, открытые проблемы, пути к файлам, ограничения пользователя), и того, что отбросить (сырые выходы, по которым уже приняты действия). Сохранять последние шаги дословно, потому что от них сильнее всего зависит следующее действие. И записывать всё, что может снова понадобиться целиком, во внешнее хранилище до того, как оно исчезнет в резюме, — об этом следующий раздел.

## Долговременная память как извлечение \{#long-term-memory-as-retrieval\}

Память, которая переживает окно, — это генерация с извлечением (RAG), в которой корпус пишет сам агент. Агент сохраняет записи по ходу работы и извлекает несколько из них в контекст, когда они становятся релевантными, с помощью [поисковой модели из курса NLP](/ru/notes/nlp/semantic-search#the-index) или более простого индекса. Привычное деление по тому, что хранится, даёт когнитивная психология, и [Sumers et al. (2024)](#references) перенесли его на языковых агентов:

| память | что хранит | когда пишется | как читается | пример |
| --- | --- | --- | --- | --- |
| рабочая | текущий контекст | на каждом шаге | моделью, напрямую | последние восемь шагов |
| эпизодическая | что произошло | по окончании эпизода или шага | по сходству с ситуацией | «деплой упал, потому что не было файла конфигурации» |
| семантическая | факты о мире или о пользователе | когда факт узнан | по сходству или по точным ключам | «пользователь хочет ответы на испанском» |
| процедурная | как что-то сделать | когда процедура удалась | по сходству с задачей | проверенная функция, которая крафтит кирку |

К процедурной памяти относятся также промпт и веса модели, которые меняются только редактированием или обучением. Пространство решений показывают три системы.

### MemGPT: подкачка страниц между основным контекстом и внешним хранилищем \{#memgpt-paging-between-a-main-context-and-external-storage\}

MemGPT ([Packer et al., 2023](#references)) заимствует у операционных систем виртуальную память, при которой программа видит больше памяти, чем есть у машины, потому что страницы перемещаются между оперативной памятью и диском. Его **основной контекст** (main context), то есть промпт, играет роль оперативной памяти и состоит из трёх частей: системных инструкций только для чтения; **рабочего контекста** (working context), блока текста, который модель может редактировать через вызовы функций (факты о пользователе, её персона); и очереди последних сообщений по принципу FIFO (first in, first out), первая запись которой — рекурсивное резюме всего вытесненного. Его **внешний контекст** (external context) играет роль диска: **хранилище истории** (recall storage) — база данных всех сообщений, и **архивное хранилище** (archival storage) — хранилище произвольного текста с векторным поиском. Модель сама перемещает данные между двумя уровнями, вызывая функции, например поиск по хранилищу истории (аналог страничного отказа, page fault) или вставку в архивное хранилище. Бюджет соблюдает менеджер очереди: когда промпт переходит порог предупреждения (в статье — 70% окна), он вставляет сообщение о «нехватке памяти» (memory pressure), чтобы модель могла сохранить важное, а когда промпт переходит порог сброса, менеджер вытесняет часть очереди (в статье — 50%) в новое рекурсивное резюме.

На задаче, построенной на наборе данных Multi-Session Chat, — вопрос в шестой сессии о детали из первых пяти — GPT-4 с фиксированным контекстом, содержащим резюме предыдущих сессий, ответила правильно в 32.1% случаев; GPT-4 внутри MemGPT, которая могла искать по всей истории, — в 92.5% (правильность оценивала языковая модель по эталонному ответу; 2023). Сравниваются резюме с потерями и резюме вместе с поиском, и это довод в пользу того, чтобы держать и то и другое.

### Generative Agents: поток памяти, оцениваемый по давности, важности и релевантности \{#generative-agents-a-memory-stream-scored-by-recency-importance-and-relevance\}

Generative Agents ([Park et al., 2023](#references)) моделировали 25 персонажей в небольшом городке, каждым из которых управляла языковая модель с **потоком памяти** (memory stream): списком наблюдений на естественном языке, у каждого из которых есть время создания, время последнего обращения и важность. Извлечение оценивает каждую запись относительно текущей ситуации $q$ формулой

$$
\boxed{\; \text{score}(m) = \alpha_{\text{rec}}\, \widehat{\text{rec}}(m) + \alpha_{\text{imp}}\, \widehat{\iota}(m) + \alpha_{\text{rel}}\, \widehat{\text{rel}}(m, q) \;}
$$

из трёх составляющих:

- **давность** (recency) $\text{rec}(m) = 0.995^{\,h}$, где $h$ — число игровых часов с последнего извлечения записи, так что извлечение освежает запись;
- **важность** (importance) $\iota(m) \in \{1, \dots, 10\}$ — целое число, которое модель назначает при создании записи в ответ на промпт, где чистка зубов названа единицей, а расставание — десяткой;
- **релевантность** (relevance) $\text{rel}(m, q) = \cos\big(e(m), e(q)\big)$ — косинусное сходство эмбеддингов.

Шляпки обозначают **min–max-нормировку** (min–max scaling) по кандидатам, $\hat x = (x - \min x)/(\max x - \min x)$, которая приводит все три к $[0, 1]$; все три веса были равны 1. В контекст вставляются записи с наибольшей оценкой, которые в него помещаются. Агенты также писали **рефлексии** (reflections) — заключения более высокого уровня, сделанные по недавним записям и сохранённые в тот же поток, — всякий раз, когда сумма важностей недавних событий превышала 150, примерно два-три раза за моделируемый день.

**Разобранный пример.** На 100-м часу запрос — «почему в прошлый раз упал деплой?». Три записи:

| запись | часов с обращения | важность | релевантность |
| --- | --- | --- | --- |
| A: деплой упал, потому что не было файла конфигурации | 95 | 7 | 0.62 |
| B: дедлайн проекта перенесли на пятницу | 30 | 8 | 0.10 |
| C: пил кофе, пока шли тесты | 2 | 2 | 0.05 |

Давности равны $0.995^{95} = 0.6211$, $0.995^{30} = 0.8604$ и $0.995^{2} = 0.9900$; после нормировки — $0$, $(0.8604 - 0.6211)/(0.9900 - 0.6211) = 0.6487$ и $1$. Важности после нормировки равны $5/6 = 0.8333$, $1$ и $0$; релевантности — $1$, $0.05/0.57 = 0.0877$ и $0$. Оценки: $0 + 0.8333 + 1 = 1.833$ у A, $0.6487 + 1 + 0.0877 = 1.736$ у B и $1 + 0 + 0 = 1$ у C. A побеждает за счёт релевантности, хотя она самая старая. Min–max-нормировка делает каждую оценку относительной к другим кандидатам: B, которая не имеет никакого отношения к деплою, приближается к A только потому, что C настолько слаба по важности и релевантности, что B оказывается лучшей из оставшихся по обоим признакам. С большим числом кандидатов составляющие расходятся, и веса становятся настоящим проектным решением.

### Voyager: библиотека навыков как процедурная память \{#voyager-a-skill-library-as-procedural-memory\}

Voyager ([Wang et al., 2023](#references)) играл в Minecraft через код: GPT-4 писала программы на JavaScript для игрового API, запускала их и исправляла по обратной связи от игры и по собственной проверке того, выполнена ли задача. Программа, которая справилась со своей задачей, добавлялась в **библиотеку навыков** (skill library) с ключом — эмбеддингом описания того, что она делает. Для новой задачи пять навыков с ключами, ближайшими к задаче, помещались в промпт, и модель могла вызывать их как функции. Навыки компонуются: «скрафтить железную кирку» вызывает навыки, которые добывают железо и крафтят палки. Эта память процедурная и исполняемая, и пишется она только после проверки, поэтому в ней не накапливаются сломанные программы.

В эксперименте статьи с деревом технологий (`gpt-4-0314`, три запуска не более чем по 160 итераций промптинга, 2023) Voyager получил алмазный инструмент в одном из трёх запусков, а та же система без библиотеки навыков — ни в одном; обе получили железные инструменты во всех трёх запусках, в среднем за 21 и 29 итераций. В новом мире, на задачах, которых он не видел, выученная библиотека помогла и агенту другой архитектуры (AutoGPT) решить задачи, с которыми тот без неё не справлялся.

### Что трудно в записи \{#what-is-hard-about-writing\}

По сравнению с решением о том, что записывать, извлечение — решённая задача. Хранилище, которое получает каждое наблюдение, заполняется почти дубликатами, и при извлечении они вытесняют полезные записи. Факты меняются («дедлайн перенесли на пятницу», затем на понедельник), и хранилищу нужно правило, какая версия побеждает: обычно самая новая с отметкой времени, иногда явное обновление. Неверная запись хуже отсутствующей, потому что извлекается с той же уверенностью, что и верная. И всё, что попадает в хранилище со страницы в интернете или из выхода инструмента, может оказаться инструкцией, подброшенной кем-то другим, а это делает память каналом для [инъекции в промпт](/ru/notes/agents/agent-security) (prompt injection), который сохраняется между сессиями. Поэтому практические системы пишут меньше, чем могли бы: исходы целых эпизодов, факты, подтверждённые пользователем, и процедуры, прошедшие проверку.

## Кэширование промпта как экономика \{#prompt-caching-as-economics\}

Сервер модели хранит ключи и значения внимания для промпта, который он только что обработал, — [KV-кэш](/ru/notes/nlp/gpt#making-generation-faster) из курса NLP. Если следующий запрос начинается с точно тех же токенов, эти ключи и значения можно переиспользовать, а не вычислять заново. Провайдеры предоставляют это как **кэширование промпта** (prompt caching) и назначают цену: на октябрь 2026 года документация Anthropic указывает для большинства моделей запись в кэш по цене 1.25 базовой цены входа при времени жизни пять минут (2 — при одном часе) и чтение из кэша по 0.1, а документация OpenAI — чтение по 0.1 цены входа и запись по 1.25 для её новых моделей ([Anthropic, 2026](#references); [OpenAI, 2026](#references)). Главное правило везде одно: для переиспользования нужно **точное совпадение префикса** (exact prefix match), так что изменение в позиции $i$ делает недействительным всё, что идёт после неё.

Цикл агента, который только дописывает, — лучший случай. На шаге $t$ первые $L_{t-1}$ токенов уже были отправлены на шаге $t - 1$, поэтому они читаются из кэша по цене $\rho$, и только $L_t - L_{t-1}$ новых токенов записываются по цене $\omega$ (при $L_0 = 0$):

$$
\begin{aligned}
C_{\text{cache}} &= \sum_{t=1}^{T} \Big( \rho\, L_{t-1} + \omega\, (L_t - L_{t-1}) \Big) && \text{кэшированная часть плюс новая, по шагам} \\
&= \rho \sum_{t=1}^{T} L_{t-1} + \omega\, L_T && \text{разности телескопически дают } L_T - L_0 = L_T \\
&= \boxed{\, \rho \Big( \sum_{t=1}^{T} L_t - L_T \Big) + \omega\, L_T \,} && \textstyle \sum_{t=1}^{T} L_{t-1} = \sum_{t=1}^{T} L_t - L_T \text{, так как } L_0 = 0 .
\end{aligned}
$$

Без кэширования запуск стоит $\sum_t L_t$. Поскольку $\sum_t L_t$ растёт как $T^2$, а $L_T$ — как $T$, их отношение стремится к $\rho$: длинный запуск, который только дописывает, стоит примерно десятую часть цены без кэша. Для запуска из 80 шагов это $0.1 \cdot (4\,980\,000 - 121\,500) + 1.25 \cdot 121\,500 = 637\,725$ токенов по базовой цене вместо 4 980 000, в 7.8 раза меньше. Кэширование также сокращает время до первого выходного токена, поскольку кэшированный префикс не вычисляется заново.

Сжатие и кэширование тянут в разные стороны. Сжатие переписывает контекст начиная с резюме, так что следующий за ним шаг платит $\omega$ за весь новый контекст; собственный вызов суммаризатора, который читает ещё кэшированный префикс, дёшев. Для запуска из 80 шагов вариант со сжатием и кэшированием стоит 465 075 токенов по базовой цене против 637 725 у варианта, который всё дописывает, с кэшированием: сжатие всё равно выигрывает, потому что переписывает контекст редко и оставляет каждый следующий шаг коротким. Не окупается правка ранней части контекста на каждом шаге, например вставка найденных записей или отметки времени перед историей: каждая такая правка выбрасывает кэш для всего, что идёт за ней. Отсюда практические правила:

- сначала стабильный префикс, изменчивые части в конце, а найденные записи — после истории или в блоке, который меняется редко;
- история между сжатиями только дописывается, а сжатия редки;
- списки инструментов в детерминированном порядке (ревизия Model Context Protocol 2026 года требует от серверов именно этого, чтобы кэши оставались тёплыми; см. [Рабочие процессы, фреймворки и протоколы](/ru/notes/agents/workflows-and-protocols)).

## Что изменилось \{#what-changed\}

| | цикл, который всё дописывает | управляемые контекст и память |
| --- | --- | --- |
| что читает модель | всё, что было до сих пор | префикс, несколько найденных записей, резюме, последние шаги |
| размер контекста за запуск | растёт на $d$ за шаг, пока не переполнится | ограничен порогом $H$ |
| входные токены запуска | квадратичны по $T$ | линейны по $T$ |
| что переживает окно | ничего | эпизоды, факты и навыки в хранилище, извлекаемые по оценке |
| стоимость входного токена | базовая цена | около $\rho$ для кэшированного префикса |
| как отказывает | останавливается на границе окна; хуже работает в середине | резюме с потерями, неверные или устаревшие записи |

## Ограничения \{#limitations\}

- **Резюме теряют информацию незаметно.** Ничто не отмечает, что резюме отбросило, и модель считает резюме полным. Деталь, которая окажется важной через сорок шагов, пропала, если её не записали ещё и в хранилище.
- **Извлечению нужен правильный запрос.** Агент извлекает то, что похоже на текущую ситуацию; запись, релевантная по причине, которую запрос не выражает, не находится. Оценки с вручную заданными весами, как приведённая выше, — эвристики, настроенные на одном приложении.
- **Память может быть неверной, устаревшей или подброшенной.** У хранилища нет встроенного понятия истины, а содержимое, записанное из недоверенных источников, — поверхность атаки, которая переживает сессию.
- **Свидетельства неравномерны.** Эффекты позиции и деградацию контекста тщательно измеряли на задачах извлечения; польза конкретного устройства памяти для длинных задач агента показана в основном на одном бенчмарке на статью, и результаты из разных постановок нельзя ранжировать.
- **Цены и ограничения меняются.** Размеры окон, цены кэша, время его жизни и минимальная кэшируемая длина различаются между провайдерами и моделями и меняются за месяцы; арифметика переносится, константы — нет.

## Что нужно запомнить \{#what-you-should-remember\}

- Контекстное окно — это рабочая память. Цикл, который всё дописывает, читает $T s + d\,T(T-1)/2$ входных токенов за $T$ шагов и останавливается, когда окно заполнено.
- Модели пользуются длинным контекстом неравномерно: информация в середине используется хуже всего, более длинные окна это не исправляют, а доля правильных ответов падает с длиной и с отвлекающими фрагментами. Инструкции стоит ставить первыми, задачу и ключевой материал — последними, а отработанные выходы инструментов — убирать.
- Сжатие заменяет старые шаги резюме, когда контекст переходит верхний порог, удерживая контекст ограниченным, а суммарную стоимость линейной; оно происходит с потерями, поэтому его нужно дополнять внешним хранилищем.
- Долговременная память — это извлечение из того, что агент записал сам: эпизодическая, семантическая и процедурная. MemGPT подкачивает страницы между основным контекстом и внешним хранилищем; Generative Agents оценивают записи по нормированным min–max давности, важности и релевантности; Voyager хранит проверенные навыки в виде кода.
- Кэширование промпта переиспользует точно совпадающий префикс: чтение стоит около десятой части базовой цены, так что длинный запуск, который только дописывает, стоит примерно в $\rho$ раз меньше, чем без кэша. Префикс нужно держать стабильным, контекст — дописывать, а не править, и сжимать его редко.

## Код \{#code\}

Арифметика токенов цикла, который всё дописывает, политика сжатия с верхним порогом, стоимость с кэшированием промпта, оценка извлечения из разобранного примера и небольшой поток памяти с заскриптованным оценщиком важности и игрушечным эмбеддингом (хэшированный мешок слов). С настоящей моделью важность берётся из промпта, а эмбеддинг — из модели эмбеддингов; оценка, учёт давности и политика сжатия остаются прежними. Только NumPy и стандартная библиотека; скрипт работает намного меньше секунды, не использует случайности, и его числа на разных платформах могут отличаться в последнем знаке.

```python
import re
import numpy as np

# 1. цикл, который всё дописывает: на шаге t модель читает префикс и t - 1 предыдущих шагов
s, d, W, reserve = 3_000, 1_500, 128_000, 4_000                 # префикс, токенов на шаг, окно, запас на ответ
context = lambda t: s + (t - 1) * d
last = max(t for t in range(1, 1000) if context(t) <= W - reserve)
print(last, sum(context(t) for t in range(1, 81)), 80 * s + d * 80 * 79 // 2)
# 81 4980000 4980000            (последний шаг, который помещается; входные токены за 80 шагов — циклом и по формуле)

# 2. сжатие: когда контекст переходит верхний порог H, префикс остаётся, последние `keep` шагов остаются,
#    а всё прочее становится одним резюме из sigma токенов; суммаризатор читает то, что заменяет
def run(T, H=None, keep=8, sigma=2_000):
    history, summary, reads, summarizer = [], 0, [], []
    for t in range(1, T + 1):
        reads.append(s + summary + sum(history))                 # что читает шаг t
        history.append(d)                                        # что добавляет шаг t
        if H is not None and s + summary + sum(history) > H:
            summarizer.append(s + summary + sum(history[:-keep]))
            summary, history = sigma, history[-keep:]
    return np.array(reads), np.array(summarizer)

H = W // 2
full, _ = run(80)
comp, summ = run(80, H)
print(full.max(), comp.max(), comp.min(), len(summ), summ.tolist())
# 121500 63500 3000 2 [52500, 53000]   (наибольший контекст без сжатия и со сжатием; наименьший; что читает суммаризатор)
print(full.sum(), comp.sum(), summ.sum(), round((comp.sum() + summ.sum()) / full.sum(), 3))
# 4980000 2791500 105500 0.582     (входные токены: всё дописывается, со сжатием, вызовы суммаризатора; их отношение)
long, long_summ = run(1000, H)
print(len(long_summ), long.max(), round(long.mean()))            # 30 63500 39930: за 1000 шагов контекст остаётся ограниченным

# 3. кэширование промпта: чтение кэшированного префикса стоит rho, запись токенов в кэш — omega (базовая цена = 1)
rho, omega = 0.1, 1.25
def cached_cost(reads, rewrites=()):
    new = np.diff(np.r_[0, reads])                               # токены, дописанные с предыдущего шага
    c = rho * (reads - new) + omega * new
    for i in rewrites: c[i] = omega * reads[i]                   # после сжатия префикс изменился: записать его заново
    return c.sum()
rew = [i for i in range(1, len(comp)) if comp[i] < comp[i - 1]]
print(round(full.sum() / 1e6, 3), round(cached_cost(full) / 1e6, 3),
      round((comp.sum() + summ.sum()) / 1e6, 3), round((cached_cost(comp, rew) + rho * summ.sum()) / 1e6, 3), rew)
# 4.98 0.638 2.897 0.465 [41, 73]   (миллионы токенов по базовой цене: без кэша, с кэшем; со сжатием, со сжатием и кэшем)

# 4. оценка извлечения в Generative Agents: нормированные min-max давность + важность + релевантность, все веса 1
def score(hours_since_access, importance, relevance, decay=0.995):
    mm = lambda x: (x - x.min()) / (x.max() - x.min() + 1e-12)
    rec = decay ** np.asarray(hours_since_access, float)
    return mm(rec) + mm(np.asarray(importance, float)) + mm(np.asarray(relevance, float)), rec
total, rec = score([95, 30, 2], [7, 8, 2], [0.62, 0.10, 0.05])   # разобранный пример: записи A, B, C
print(rec.round(4), total.round(3))                               # [0.6211 0.8604 0.99  ] [1.833 1.736 1.   ]

# 5. поток памяти: запись с оценкой важности, чтение по оценке, обновление давности при каждом чтении
def embed(text, dim=64):                                         # игрушечный эмбеддинг: хэшированный мешок слов единичной длины
    v = np.zeros(dim)
    for w in re.findall(r'[a-z]+', text.lower()):
        v[sum(map(ord, w)) % dim] += 1.0
    return v / np.linalg.norm(v)
def rate_importance(text):                                       # заскриптованная замена модели, «оценивающей от 1 до 10»
    table = {'password': 9, 'deadline': 8, 'failed': 7, 'prefers': 6, 'coffee': 2, 'weather': 1}
    return max((v for k, v in table.items() if k in text), default=3)

class MemoryStream:
    def __init__(self):
        self.items = []
    def write(self, text, hour):
        self.items.append(dict(text=text, vec=embed(text), imp=rate_importance(text), last=hour))
    def read(self, query, hour, k=3):
        q = embed(query)
        sc, _ = score([hour - m['last'] for m in self.items], [m['imp'] for m in self.items],
                      [m['vec'] @ q for m in self.items])
        top = np.argsort(-sc)[:k]
        for i in top: self.items[i]['last'] = hour
        return [(self.items[i]['text'], round(float(sc[i]), 3)) for i in top]

mem = MemoryStream()
for hour, text in [(0, 'user prefers answers in Spanish'), (2, 'had coffee while the tests ran'),
                   (5, 'the deploy failed because the config file was missing'), (30, 'weather was sunny today'),
                   (70, 'project deadline moved to Friday'), (95, 'ran the tests again, all passed')]:
    mem.write(text, hour)
for row in mem.read('why did the deploy fail last time', hour=100): print(row)
# ('the deploy failed because the config file was missing', 1.899)
# ('ran the tests again, all passed', 1.81)
# ('project deadline moved to Friday', 1.689)
print(sum(m['imp'] for m in mem.items))                          # 27: ниже порога рефлексии в 150
```
