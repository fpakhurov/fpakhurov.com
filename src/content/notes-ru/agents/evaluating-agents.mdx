Предыдущий раздел обучал агентов на задачах, у которых есть проверка: тест, который проходит, ответ, который совпадает, база данных в нужном состоянии. Каждый результат, приведённый в этом курсе, сопровождался моделью, обвязкой (scaffold), версией бенчмарка и датой, а также предупреждением, что результаты разных постановок — не рейтинг. Этот раздел задаёт вопросы, стоящие за этими предупреждениями: как получается число, описывающее агента, насколько ему можно доверять и чего оно не говорит. [Заметка об оценке из курса NLP](/ru/notes/nlp/llm-evaluation) измеряла отдельные выходы: бенчмарки с фиксированными промптами, модели-судьи, предпочтения людей. Агент добавляет три сложности. Его выход — траектория в среде, а не строка. Два запуска одного и того же агента на одной задаче могут закончиться по-разному. И каждый запуск стоит минут и долларов. Эта заметка строит статистику для такой постановки, а затем обозревает бенчмарки, которые её используют.

**Обозначения.** В бенчмарке есть задачи $i = 1, \dots, N$. Одна **попытка** (trial) — один запуск агента на одной задаче, от среды, сброшенной в начальное состояние, до оценённого конца. На задаче $i$ одна попытка успешна с неизвестной вероятностью $p_i$; мы делаем $n$ попыток и наблюдаем $c_i$ успехов. $k \le n$ — число попыток, к которому относится метрика. $\bar p$ — среднее $p_i$ по генеральной совокупности задач, из которой бенчмарк делает выборку. Для горизонтов задач $t$ — время, которое нужно на задачу квалифицированному человеку, $h$ — горизонт агента, а $\beta$ — наклон его кривой успеха; $\sigma(z) = 1/(1 + e^{-z})$.

## Отправная точка: один запуск на задачу, одно число \{#baseline-one-run-per-task-one-number\}

Простейшая оценка запускает агента по одному разу на каждой задаче и сообщает долю решённых задач. Именно это сообщает большинство таблиц лидеров (leaderboard), и это число скрывает четыре вещи.

- **Случайность.** Модель сэмплирует, смоделированный пользователь сэмплирует, веб-страницы меняются, тесты нестабильны (flaky). Запустим оценку ещё раз — и число сдвинется. При 50 задачах и одной попытке на каждой 95-процентный интервал вокруг доли успехов 0.6 имеет ширину около $\pm 0.14$.
- **Надёжность.** Если задача решена один раз, это ничего не говорит о том, решается ли она каждый раз. В τ-bench (июнь 2024 года) агент с вызовом функций на GPT-4o решил 61.2% задач розничной торговли за одну попытку и меньше 25% из них во всех восьми попытках ([Yao et al., 2024](#references)).
- **Стоимость.** Агент, который решает на 2% больше задач по десятикратной цене, не очевидно лучше, а отправная точка цену не записывает.
- **Что оценивали.** Доля «решённых» задач хороша ровно настолько, насколько хороша проверка, которая решила судьбу каждой из них.

У каждой из этих проблем есть средство, и разделы ниже разбирают их по очереди.

## Чем отличается оценка агента \{#what-makes-an-agent-evaluation-different\}

Агента оценивают в **среде**, а не на наборе данных. У среды есть состояние (файлы, база данных, браузер, смоделированный клиент), агент его меняет, а оценщик (grader) смотрит, что осталось в конце. Прогон оценки — цикл из попыток:

<EvalHarness />

1. **Сброс.** Каждая попытка начинается с одного и того же состояния, обычно со свежего контейнера, собранного из одного образа, чтобы одна попытка не могла протечь в следующую. Это [песочница из заметки об агентах для программирования](/ru/notes/agents/coding-agents#sandboxing), используемая для измерения.
2. **Цикл.** Агент действует, среда отвечает, как в [ReAct и цикле агента](/ru/notes/agents/react-and-the-agent-loop), пока агент не остановится или не кончится [бюджет](/ru/notes/agents/react-and-the-agent-loop#stopping-budgets-and-loops). В некоторых бенчмарках часть среды — другая модель, которая играет пользователя.
3. **Итоговое состояние.** То, что оставляет попытка: репозиторий, база данных, ответ.
4. **Оценка.** Программа или судья решает, был ли успех, по итоговому состоянию, а не по пути к нему.
5. **Запись.** Успех, а также токены, доллары, время по часам и число шагов.
6. **Повтор и оценивание.** $n$ попыток на каждой из $N$ задач, затем статистика, описанная ниже.

Из этой постановки следуют три свойства, которые определяют всё остальное. Исход попытки — случайная величина даже при фиксированных задаче и агенте, поэтому у задачи есть *вероятность* успеха $p_i$, а не метка. Задачи сильно различаются по трудности, поэтому $p_i$ разбросаны по $[0, 1]$, и разброс важен не меньше их среднего. И попытки дороги: задача SWE-bench может занять сотню шагов, поэтому $n$ и $N$ малы, и любая статистика должна работать при малых значениях обоих.

## pass@k: успех хотя бы в одной из k попыток \{#passk-success-in-at-least-one-of-k-trials\}

Если на задаче $i$ сделано $k$ независимых попыток, вероятность того, что хотя бы одна из них успешна, равна $1 - (1 - p_i)^k$. Её среднее по задачам — это **pass@k**:

$$
\text{pass@}k = \frac1N \sum_{i=1}^N \big(1 - (1 - p_i)^k\big).
$$

Эта метрика измеряет, что агент может сделать, когда ему разрешено попробовать $k$ раз и что-то распознаёт успех: тесты, которые можно запустить, как в [проверке у агентов для программирования](/ru/notes/agents/coding-agents#localization-editing-and-verification), или человек, который выбирает работающий ответ. Её ввели для генерации кода, где отбор делает модульный тест ([Kulal et al., 2019](#references); [Chen et al., 2021](#references)).

### Несмещённая оценка \{#an-unbiased-estimator\}

$p_i$ неизвестны; у нас есть $c_i$ успехов в $n \ge k$ попытках. Очевидная оценка подставляет $\hat p_i = c_i / n$ и сообщает $1 - (1 - \hat p_i)^k$. Она смещена, и Chen et al. вывели оценку, которая смещения не имеет. Опустим индекс задачи.

**Идея.** $(1 - p)^k$ — вероятность того, что $k$ заданных независимых попыток все неудачны. Из $n$ сделанных попыток выберем $k$ случайно, без возвращения. Вероятность того, что все $k$ выбранных неудачны, — число, которое можно вычислить по $c$, и его математическое ожидание равно $(1 - p)^k$.

$$
\boxed{
\begin{aligned}
\widehat{\text{pass@}k} &= 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}}, \\
\widehat{\text{pass}^k} &= \frac{\binom{c}{k}}{\binom{n}{k}}
\end{aligned}
}
$$

**Почему она несмещённая.** Пусть $S$ — множество из $k$ попыток, выбранное из $n$ равновероятно и независимо от их исходов, а $F$ — событие «все попытки из $S$ неудачны».

$$
\begin{aligned}
\mathbb E\!\left[\frac{\binom{n-c}{k}}{\binom{n}{k}}\right]
&= \mathbb E\big[P(F \mid c)\big] && \text{(i)} \\
&= P(F) && \text{(ii) формула полной вероятности} \\
&= (1 - p)^k && \text{(iii)}
\end{aligned}
$$

Шаг (i): при данном $c$ все $\binom{n}{k}$ возможных множеств $S$ равновероятны, и $\binom{n-c}{k}$ из них не содержат ни одного из $c$ успехов. Шаг (iii): $S$ выбирается, не глядя на исходы, поэтому его $k$ попыток — независимые одинаково распределённые попытки с вероятностью неудачи $1 - p$, и все они неудачны с вероятностью $(1 - p)^k$.

Вычитание из 1 даёт несмещённую оценку $1 - (1 - p)^k$, а усреднение по задачам — несмещённую оценку pass@k. То же рассуждение с событием «все $k$ выбранных попыток успешны» даёт вторую оценку, $\binom{c}{k}/\binom{n}{k}$ для $p^k$, которая используется в следующем разделе. Когда $n - c < k$, каждое $k$-элементное множество содержит успех, и оценка равна 1. Биномиальные коэффициенты при $n = 200$ переполняются, поэтому реализации используют равное им произведение $\binom{n-c}{k}/\binom{n}{k} = \prod_{j = n - c + 1}^{n} (1 - k/j)$, как и раздел «Код».

**Почему подстановочная оценка смещена.** При $k \ge 2$ функция $x \mapsto 1 - (1 - x)^k$ вогнута, а $\hat p$ — несмещённая оценка $p$, поэтому по неравенству Йенсена $\mathbb E[1 - (1 - \hat p)^k] \le 1 - (1 - p)^k$: подстановочная (plug-in) оценка занижает результат. На 50 синтетических задачах из раздела «Код» при $n = 20$ и 500 повторах истинное значение pass@4 равно 0.917, несмещённая оценка в среднем даёт 0.917, а подстановочная — 0.904.

**Разобранный пример.** Одна задача, $n = 10$ попыток, $c = 3$ успеха. При $k = 2$: $\binom{7}{2}/\binom{10}{2} = 21/45$, поэтому $\widehat{\text{pass@}2} = 1 - 21/45 = 0.533$, тогда как подстановочная оценка даёт $1 - 0.7^2 = 0.51$. При $k = 8$: $n - c = 7 < 8$, поэтому любые 8 из 10 попыток содержат успех, и оценка равна 1. А $\widehat{\text{pass}^2} = \binom{3}{2}/\binom{10}{2} = 3/45 = 0.067$ против подстановочной $0.3^2 = 0.09$.

На HumanEval, 164 написанных вручную задачах на Python, Chen et al. (июль 2021 года) брали $n = 200$ сэмплов на задачу и сообщили для Codex с 12 миллиардами параметров и температурой сэмплирования, подобранной для каждого $k$: pass@1 = 28.81%, pass@10 = 46.81% и pass@100 = 72.31%.

## pass^k: успех во всех k попытках \{#passk-success-in-all-of-k-trials\}

Агент службы поддержки, который обрабатывает один и тот же запрос от тысячи клиентов, должен справиться с ним тысячу раз; успех в одной попытке из восьми здесь бесполезен. τ-bench ([Yao et al., 2024](#references)) ввёл дополняющую метрику **pass^k** (читается «pass hat k») — вероятность того, что все $k$ независимых попыток успешны:

$$
\begin{gathered}
\text{pass}^k = \frac1N \sum_{i=1}^N p_i^k, \\
\widehat{\text{pass}^k} = \frac1N \sum_{i=1}^N \frac{\binom{c_i}{k}}{\binom{n}{k}} .
\end{gathered}
$$

При $k = 1$ обе метрики равны средней доле успехов. С ростом $k$ pass@k поднимается к доле задач, которые агент вообще способен решить, а pass^k падает к доле задач, которые он решает всегда. Куда они идут, зависит от того, как разбросаны $p_i$, а не только от их среднего:

Рисунок показывает практически важную вещь. При одном и том же pass@1 = 0.6 набор одинаковых задач дал бы pass^8 = 0.017, а реалистичный разброс трудности даёт 0.186. Одна попытка на задачу не может различить эти случаи, поэтому надёжность нужно измерять повторными попытками на каждой задаче, а не выводить из pass@1.

**τ-bench**, выпущенный в июне 2024 года, помещает агента в разговор с пользователем, которого моделирует языковая модель (в исходных прогонах GPT-4), с инструментами, которые читают и пишут базу данных, и с письменными правилами, которым агент должен следовать: розничная торговля со 115 задачами и авиакомпания с 50. Попытка успешна, если база данных в конце совпадает с размеченным целевым состоянием, а сообщения агента содержат нужную информацию. С агентом на GPT-4o с вызовом функций pass^1 составил 61.2% в рознице и 35.2% в авиакомпании, а pass^8 в рознице был ниже 25%. Авторы отмечают, что их оценщик необходим, но не достаточен для хорошего эпизода: агент, который пропускает подтверждение, требуемое правилами, но приходит к нужному состоянию, всё равно проходит. **τ²-bench** (июнь 2025 года) добавил телекоммуникационную область, в которой смоделированный пользователь тоже действует на общее состояние своими инструментами, как это делает клиент, выполняющий указания агента поддержки ([Barres et al., 2025](#references)).

## Сколько нужно задач? Интервалы для доли успехов \{#how-many-tasks-intervals-for-a-success-rate\}

Доля успехов $\hat R = \frac{1}{Nn}\sum_i c_i$ оценивает $\bar p$. У её ошибки два источника: какие задачи случайно попали в бенчмарк и как случайно легли попытки на них. Закон полной дисперсии разделяет эти источники. Будем считать задачи случайной выборкой из генеральной совокупности, а $c_i \mid p_i \sim \mathrm{Binomial}(n, p_i)$:

$$
\begin{aligned}
\operatorname{Var}(c_i) &= \mathbb E\big[\operatorname{Var}(c_i \mid p_i)\big] + \operatorname{Var}\big(\mathbb E[c_i \mid p_i]\big) && \text{закон полной дисперсии} \\
&= n\, \mathbb E\big[p(1 - p)\big] + n^2 \operatorname{Var}(p) && \text{биномиальные среднее } n p_i \text{ и дисперсия } n p_i (1 - p_i) \\
\Rightarrow\quad \operatorname{Var}(\hat R) &= \frac{1}{N^2 n^2} \cdot N \operatorname{Var}(c_i) && \text{задачи независимы} \\
&= \boxed{\;\frac{1}{N}\left(\operatorname{Var}(p) + \frac{\mathbb E[p(1 - p)]}{n}\right)\;}
\end{aligned}
$$

Первое слагаемое — разброс трудности по задачам; уменьшить его можно только числом задач. Второе — шум попыток; его уменьшают дополнительные попытки на задачу, но только до первого слагаемого и не дальше. При одной попытке на задачу скобка равна $\operatorname{Var}(p) + \mathbb E[p(1-p)] = \bar p(1 - \bar p)$ — биномиальной дисперсии одной монеты с вероятностью $\bar p$, как и должно быть.

**Разобранный пример.** В разделе «Код» у задач $p \sim \mathrm{Beta}(1.2, 0.8)$: $\bar p = 0.6$, $\operatorname{Var}(p) = \frac{1.2 \cdot 0.8}{2^2 \cdot 3} = 0.08$, $\mathbb E[p(1-p)] = 0.6 \cdot 0.4 - 0.08 = 0.16$. Полуширина нормального 95-процентного интервала, $1.96\sqrt{\operatorname{Var}(\hat R)}$, тогда такова:

| задачи $N$ | попыток на задачу $n$ | полуширина |
| --- | --- | --- |
| 50 | 1 | 0.136 |
| 50 | 20 | 0.082 |
| 50 | 1000 | 0.078 |
| 200 | 20 | 0.041 |
| 800 | 1 | 0.034 |

Двадцать попыток на каждой из 50 задач стоят столько же, сколько одна попытка на каждой из 1000 задач, и дают интервал больше чем вдвое шире, чем 800 одиночных попыток. Повторные попытки нужны для pass^k и для того, чтобы знать $p_i$ отдельной задачи; для доли успехов важны задачи. Чтобы оценить долю успехов около 0.5 с точностью $\pm 0.05$ при одной попытке на задачу, нужно $N \ge (1.96 \cdot 0.5 / 0.05)^2 \approx 385$ задач — больше, чем есть в большинстве бенчмарков для агентов. [Miller (2024)](#references) рекомендует для новой оценки не меньше примерно 1000 вопросов, стандартные ошибки при каждом результате и анализ мощности до запуска.

**Перевыбирать нужно задачи, а не попытки.** [Бутстрэп](/ru/notes/probability/confidence-intervals-and-bootstrap#the-bootstrap) даёт интервалы для любой статистики, включая pass^k, но только если повторная выборка делается по независимым единицам. Здесь это задачи: попытки на одной задаче разделяют её трудность, и это случай [сгруппированных данных](/ru/notes/probability/confidence-intervals-and-bootstrap#when-the-bootstrap-fails). На одном синтетическом бенчмарке из раздела «Код» (50 задач по 20 попыток, доля успехов 0.613) повторная выборка задач даёт 95-процентный интервал $[0.538, 0.682]$, а повторная выборка 1000 попыток так, будто они независимы, — $[0.582, 0.643]$. На 300 смоделированных бенчмарках интервал по задачам содержал истинную долю в 95% случаев, а интервал по попыткам — в 55%. Двух агентов, запущенных на одних и тех же задачах, нужно сравнивать [парным](/ru/notes/probability/confidence-intervals-and-bootstrap#comparing-two-models-on-one-test-set) анализом: перевыбирать задачи и вычислять разность на каждой повторной выборке, поскольку трудные задачи трудны для обоих.

<aside class="callout"><strong>Ключевая идея.</strong> Результат агента — оценка вероятности по генеральной совокупности задач и по случайности попыток, полученная конкретным оценщиком при конкретном бюджете. Измерением он становится, только когда указаны единица повторной выборки (задачи), $k$, к которому он относится, оценщик и стоимость попытки.</aside>

Бенчмарки для репозиториев, веба, рабочего стола и исследований описаны с датированными результатами в заметках [Агенты для программирования](/ru/notes/agents/coding-agents#swe-bench-what-a-task-is-and-how-it-is-graded), [Агенты для веба и управления компьютером](/ru/notes/agents/computer-use-agents#benchmarks-webarena-mind2web-osworld) и [Исследовательские агенты](/ru/notes/agents/research-agents#evaluations-gaia-and-browsecomp); AgentDojo — предмет [следующей заметки](/ru/notes/agents/agent-security). Три других кратко.

**Terminal-Bench** ([Merrill et al., 2026](#references)) даёт агенту терминал в контейнере и задачу вроде сборки проекта, настройки сервера или обучения небольшой модели; успех решают тесты в контейнере, и у каждой задачи есть эталонное решение, написанное человеком. Версия 2.0 оставила 89 из 229 предложенных задач после проверки тремя людьми, а её обвязка для оценки запускает одни и те же задачи под несколькими обвязками агентов. В статье января 2026 года передовые модели со своими агентами решили меньше 65% задач, и выбор модели значил больше, чем выбор обвязки.

**MLE-bench** ([Chan et al., 2024](#references)) берёт 75 соревнований Kaggle, даёт агенту данные и задачу и оценивает его решение по настоящей таблице лидеров соревнования: получило бы оно бронзовую, серебряную или золотую медаль? В октябре 2024 года лучшая конфигурация, o1-preview в обвязке AIDE, получила как минимум бронзовую медаль в 16.9% соревнований.

**В бенчмарках бывают ошибки.** Аудит бенчмарков для агентов в июле 2025 года нашёл оценщики, которые принимают неверные ответы, среди них оценщик τ-bench, засчитывавший пустые ответы как успешные, и оценил, что такие недостатки могут сдвинуть результат до 100% в относительном выражении в любую сторону ([Zhu et al., 2025](#references)). Его контрольный список Agentic Benchmark Checklist проверяет, корректны ли задачи и означает ли вердикт оценщика то, что он заявляет; применённый к CVE-Bench, он сократил завышение качества на 33%. Дешёвая проверка любого оценщика — нулевой агент, который ничего не делает: он должен получить ноль.

## Загрязнение и насыщение \{#contamination-and-saturation\}

Публичный бенчмарк — мишень. Его задачи лежат в вебе, а веб — это обучающие данные; если модель видела задачу и её решение, успех измеряет память. Когда модели становятся достаточно сильными, потолком становятся собственные ошибки бенчмарка: задачу, тесты которой отвергают правильные исправления, лучший агент решить не может.

**SWE-bench Verified** прошёл через оба явления — загрязнение (contamination) и насыщение (saturation). Он был выпущен в августе 2024 года как 500 задач, отобранных профессиональными разработчиками, и около полутора лет оставался стандартной мерой агентов для программирования. 23 февраля 2026 года OpenAI объявила, что перестаёт его публиковать. Аудит задач, на которых передовые модели ошибались, нашёл ошибочные тесты или недоопределённые описания как минимум в 59.4% проверенного подмножества, а модели могли воспроизвести эталонные патчи по одной лишь задаче — признак того, что публичные задачи просочились в обучающие данные. OpenAI рекомендовала SWE-bench Pro, большинство задач которого отложены или закрыты ([OpenAI, 2026](#references)).

Средства защиты известны, и каждое чего-то стоит:

- **Отложенные и закрытые наборы**, как в SWE-bench Pro и в закрытых ответах GAIA: их труднее загрязнить, но и другим труднее их проверить.
- **Строки-канарейки** (canary strings) — уникальная метка в каждом файле бенчмарка, по которой разработчики моделей могут отфильтровать его из обучающих данных; в Terminal-Bench такая есть. Они работают, только если разработчики фильтруют.
- **Свежие задачи**, собранные после даты отсечения обучающих данных модели, и проверки того, что модель не может выполнить задачу по одному её описанию.
- **Вывод бенчмарка из употребления**, когда его оставшиеся неудачи — в основном его собственные ошибки.

Агенты добавляют третий сбой, который не является ни загрязнением, ни насыщением: агент может **обмануть оценщика** во время оценки — отредактировать тесты, обработать проверяющую программу особым случаем или прочитать эталонный ответ. METR сообщила, что в феврале и марте 2026 года на задачах её набора, которые занимают у людей больше восьми часов, не меньше 16% успешных запусков при проверке оказались нечестными ([METR, 2026b](#references)). Оценщик, которого агент может изменить, или эталон, который он может прочитать, — не оценщик. Заметка [Выравнивание агентов и надзор за ними](/ru/notes/agents/alignment-and-oversight) рассматривает такое поведение как проблему обучения.

## Горизонт задачи METR \{#the-metr-time-horizon\}

Бенчмарки насыщаются один за другим, и их результаты нельзя сравнивать между бенчмарками и годами. METR предложила меру на шкале, которая не насыщается: длину задач, измеренную тем, сколько времени на них тратит квалифицированный человек, которые агент выполняет с заданной вероятностью, — горизонт задачи (time horizon) ([Kwa et al., 2025](#references)).

**Задачи.** 170 программистских и исследовательских задач в трёх наборах: HCAST (97 задач в 46 семействах, от минут до часов), RE-Bench (7 открытых исследовательских сред по машинному обучению примерно на восемь часов) и SWAA (66 коротких задач от секунд до минут). Задачи пробовали решить люди с подходящей квалификацией, и время задачи $t$ — среднее геометрическое успешных попыток.

**Подгонка.** Каждого агента запускают около 8 раз на каждой задаче. Для одного агента вероятность успеха на задаче с человеческим временем $t$ моделируется логистической функцией от $\log_2 t$:

$$
\boxed{\;P(\text{success} \mid t) = \sigma\big(\beta\,(\log_2 h - \log_2 t)\big)\;}
$$

Это [логистическая регрессия](/ru/notes/ml/logistic-regression) с одним признаком. Если записать её логит как $w_0 + w_1 \log_2 t$ и сопоставить коэффициенты, получим $\beta = -w_1$ и $\log_2 h = w_0 / \beta$. При $t = h$ логит равен 0, а вероятность — $1/2$, поэтому $h$ — **50-процентный горизонт**. 80-процентный горизонт находится там, где $\sigma(z) = 0.8$, то есть $z = \ln 4$:

$$
\begin{aligned}
\beta\,(\log_2 h - \log_2 t_{80}) &= \ln 4 && \sigma(z) = 0.8 \iff e^{-z} = 1/4 \\
\Rightarrow\quad t_{80} &= h \cdot 2^{-\ln 4 / \beta} && \text{выражаем } \log_2 t_{80} .
\end{aligned}
$$

Пологая кривая (малое $\beta$) ставит 80-процентный горизонт далеко ниже 50-процентного; METR нашла, что 80-процентные горизонты в 4–6 раз короче. В статье задачи взвешиваются обратно пропорционально квадратному корню из размера их семейства, чтобы семейство из многих похожих задач не доминировало, а подгонка слегка регуляризуется.

**Разобранный пример.** На синтетических данных из раздела «Код», 40 задач от 1 минуты до 8 часов, по 8 запусков на каждой, сгенерированных с $h = 60$ минут и $\beta = 0.6$:

Подгонка даёт $\beta = 0.57$ и $h = 67.4$ минуты. Повторная выборка 40 задач даёт 95-процентный интервал $[49.8, 93.9]$ минуты; он широк, потому что 40 задач несут мало информации о том, где кривая пересекает половину. 80-процентный горизонт равен $67.4 \cdot 2^{-\ln 4 / 0.57} = 12.6$ минуты.

**Тренд.** Затем METR построила регрессию $\log h$ передовых моделей по датам их выпуска. В статье марта 2025 года 50-процентный горизонт вырос примерно с 2 секунд у GPT-2 (2019) примерно до 50 минут у Claude 3.7 Sonnet (февраль 2025 года), удваиваясь каждые 207 дней, около семи месяцев, с 95-процентным бутстрэп-интервалом от 166 до 240 дней; модели 2024–2025 годов сами по себе указывали на более быстрый темп, но их было всего семь. Более поздние измерения датированы и широки. В январе 2026 года METR дала около 4 часов 49 минут для Claude Opus 4.5 (ноябрь 2025 года) с 95-процентным интервалом от 1 часа 49 минут до 20 часов 25 минут ([METR, 2026a](#references)). На обновлённом наборе Time Horizon 1.1 она оценила самые сильные публичные модели февраля и марта 2026 года примерно в 12 часов с разбросом от 5 до 61 часа, а их 80-процентный горизонт — примерно в 1.5 часа, и заявила, что набор больше не может надёжно измерять горизонты свыше 16 часов ([METR, 2026b](#references)).

**Чего горизонт не говорит.** Собственный список оговорок METR длинный, и каждая из них важна для чтения тренда:

- Горизонт — *человеческое* время задач, а не то, сколько работает агент; обычно агент работает гораздо меньше.
- Он зависит от области. По сравнениям METR визуальное управление компьютером даёт горизонты в 40–100 раз ниже, чем программистские и исследовательские задачи.
- Задачи самодостаточны, хорошо специфицированы и оцениваются автоматически; реальная работа запутаннее, и на задачах, признанных более запутанными, модели справлялись хуже.
- Погрешности — примерно в 2 раза в каждую сторону, шире у недавних моделей; 20- и 80-процентные горизонты подгоняются не независимо от 50-процентного, а горизонты для надёжности 99% по набору такого размера подогнать нельзя.
- 50-процентный горизонт — не порог для делегирования: работе, которая должна удаваться в 98% случаев, нужна гораздо более короткая задача.
- Набор тоже насыщается, и успехи на его самых длинных задачах нужно проверять на нечестность.

## Оценка с учётом стоимости и фронты Парето \{#cost-aware-evaluation-and-pareto-fronts\}

Доля правильных ответов (accuracy) сама по себе поощряет траты. Любого агента можно сделать точнее за счёт большего числа попыток, сэмплов и проверок, поэтому таблица лидеров, отсортированная по доле решённых задач, благоволит тому, кто потратил больше всех. [Kapoor et al. (2024)](#references) утверждали, что оценки агентов должны сообщать стоимость и оптимизировать долю решённых задач и стоимость совместно, и нашли, что лучшие агенты того времени были без нужды сложными и дорогими.

**Повтор с верификатором.** Пусть агенту разрешено повторять попытку, пока не пройдёт тест, но не больше $k$ раз, и тест безошибочен. Агент успешен, если успешна хоть одна попытка, поэтому его доля успехов равна pass@k. Попытку $j + 1$ он делает, только если первые $j$ были неудачны, а это происходит с вероятностью $(1 - p)^j$, поэтому

$$
\boxed{\;\mathbb E[\text{attempts}] = \sum_{j=0}^{k-1} \mathbb E\big[(1 - p)^j\big]\;}
$$

а ожидаемая стоимость — это число, умноженное на цену попытки. Возьмём две модели: малую с $p \sim \mathrm{Beta}(0.6, 0.9)$ и средним 0.4 по \$0.01 за попытку и большую с $p \sim \mathrm{Beta}(1.2, 0.6)$ и средним 0.667 по \$0.10:

<CostFront />

Конфигурация лежит на **фронте Парето** (Pareto front), если нет другой, которая не менее точна и не более дорога. Большая модель с одной попыткой, 0.667 за \$0.100, доминируется малой с четырьмя, 0.673 за \$0.024; с двумя попытками, 0.810 за \$0.133, — малой с шестнадцатью, 0.847 за \$0.051. Выше 0.85 добирается только большая модель. Сравнение, которое отвечает на практический вопрос, — сравнение фронтов, а не точек. Пример держится на двух допущениях: попытки на задаче независимы, а верификатор безошибочен. С ошибающимся верификатором доля успехов насыщается на уровне его точности, как выведено в заметке [Рефлексия и самокоррекция](/ru/notes/agents/reflection-and-self-correction#generate-and-verify), и фронт опускается.

У стоимости есть и составляющие, которые цена попытки скрывает: токены растут с каждым шагом цикла ([Стоимость и задержка цикла](/ru/notes/agents/react-and-the-agent-loop#the-cost-and-latency-of-a-loop)), кэширование промптов меняет цену длинного контекста, а время по часам важно для человека, который ждёт. Полезная оценка сообщает вместе с результатом как минимум доллары и время на попытку.

## Оценщики \{#graders\}

Каждое число выше наследует ошибки оценщика. Их четыре вида, в порядке убывания механичности.

- **Исполнение: модульные тесты и скрипты.** Точны в том, что проверяют, и молчат обо всём остальном; они бывают нестабильными, могут отвергать правильные решения (аудит SWE-bench Verified) и могут быть изменены агентом, у которого есть к ним доступ на запись. Их нужно держать скрытыми и вне песочницы агента.
- **Проверки состояния.** Сравнивают итоговое состояние среды с целью: базу данных τ-bench, магазин и репозитории WebArena, файлы и настройки OSWorld. Они принимают любой путь к цели, что для агентов правильно, и должны перечислить все допустимые конечные состояния и проверить побочные эффекты, что трудно: лишний возврат денег, оформленный по пути, — это другая база данных, а письмо, отправленное не тому человеку, может быть не видно проверке входящих.
- **Модели-судьи.** Для длинных ответов и траекторий без механической проверки. Судья — верификатор с частотами ошибок, которые нужно измерить относительно людей на той же задаче, прежде чем использовать его оценки, как в заметке [Оценка LLM](/ru/notes/nlp/llm-evaluation#a-model-as-judge); и он — цель оптимизации, поэтому агенты, обученные на нём, найдут его ошибки ([Модель в роли судьи](/ru/notes/agents/reflection-and-self-correction#a-model-as-judge)).
- **Люди.** Эталон для остальных, дорогой и достаточно шумный, чтобы их согласованность тоже нужно было сообщать.

Практичная оценка использует несколько оценщиков: решает механическая проверка, судья или человек просматривает выборку успехов в поисках нечестных и выборку неудач в поисках ошибок оценщика, и частоты того и другого сообщаются.

## Что изменилось \{#what-changed\}

| | один запуск на задачу | тщательная оценка агента |
| --- | --- | --- |
| что оценивается | доля задач | вероятность для каждой задачи, усреднённая по генеральной совокупности задач |
| повторные попытки | нет | $n$ на задачу, для pass@k, pass^k и трудности каждой задачи |
| погрешности | нет или по попыткам | по задачам, по формуле дисперсии или бутстрэпом по задачам |
| надёжность | не видна | pass^k, который падает к доле задач, решаемых всегда |
| стоимость | не записывается | доллары и время на попытку; фронты Парето |
| оценщик | принимается на веру | проверяется: нулевые агенты, просмотр успехов и неудач |
| между бенчмарками | несравнимо | горизонт задачи, с его оговорками |

## Ограничения \{#limitations\}

- **Независимость — допущение.** pass@k, pass^k и формула повторов предполагают, что попытки на задаче независимы при данном $p_i$. Детерминированный агент с температурой 0 или среда, которая помнит прежние попытки, это нарушают.
- **Генеральная совокупность не определена.** Интервал по задачам обобщается на задачи, подобные этим; бенчмарки редко бывают случайными выборками из того, что важно пользователям.
- **Смоделированные пользователи — это модели.** Пользователь τ-bench — языковая модель со своими ошибками и своей дисперсией, которые становятся частью результата агента.
- **Горизонты задач опираются на замеры людей.** Кто проходил замеры, как учитываются неудачные попытки и как агрегируется время — всё это сдвигает горизонт больше чем на 25%, а тренд на своём переднем крае опирается на немногие модели.
- **Стоимость — меняющаяся цена.** Цены токенов падают и различаются у разных поставщиков, поэтому фронт в долларах на одну дату не выполняется на следующую.
- **Статические бенчмарки стареют.** Загрязнение и насыщение для любого публичного набора — вопрос времени.

## Что нужно запомнить \{#what-you-should-remember\}

- Агента оценивают попытками в среде, сброшенной в одно и то же состояние, и судят по итоговому состоянию; у задачи есть вероятность успеха $p_i$, а не метка.
- pass@k $= \frac1N \sum (1 - (1 - p_i)^k)$ измеряет возможности при $k$ попытках и механизме отбора; pass^k $= \frac1N \sum p_i^k$ измеряет надёжность. Несмещённо их оценивают через $1 - \binom{n-c}{k}/\binom{n}{k}$ и $\binom{c}{k}/\binom{n}{k}$; подстановка $c/n$ занижает pass@k.
- $\operatorname{Var}(\hat R) = \frac1N(\operatorname{Var}(p) + \mathbb E[p(1-p)]/n)$: попытки уменьшают только второе слагаемое, поэтому точность требует задач. Бутстрэп делается по задачам, а агентов сравнивают парно на одних и тех же задачах.
- Бенчмарки различаются средой, тем, кто ещё в ней есть, и оценщиком; каждый результат нужно читать с его версией и датой. Публичные наборы утекают и насыщаются, как SWE-bench Verified к февралю 2026 года, а оценщиков можно обмануть.
- Горизонт задачи METR подгоняет $\sigma(\beta(\log_2 h - \log_2 t))$ к успеху в зависимости от человеческого времени задачи; горизонты передовых моделей удваивались примерно каждые семь месяцев с 2019 по начало 2025 года, с широкими погрешностями, зависимостью от области и набором, который в 2026 году насытился.
- Стоимость нужно сообщать вместе с долей решённых задач и сравнивать фронты Парето: с верификатором дешёвая модель с повторами может доминировать дорогую.

## Код \{#code\}

Оценки pass@k и pass^k с проверкой по биномиальной формуле, синтетический бенчмарк из 50 задач по 20 попыток, смещение подстановочной оценки, бутстрэп-интервалы по задачам и по попыткам с их покрытием, формула дисперсии, подгонка горизонта задачи методом Ньютона с бутстрэпом по задачам, время удвоения методом наименьших квадратов и стоимость повторов с верификатором. Только NumPy и стандартная библиотека; начальные значения генератора фиксированы, а точные числа могут немного различаться на разных платформах и версиях библиотек. Скрипт работает несколько секунд.

Агент здесь — набор вероятностей успеха: каждая попытка на задаче $i$ успешна с вероятностью $p_i$. Настоящая оценка заменяет каждое подбрасывание монеты запуском агента в песочнице и оценщиком; оценки, интервалы и подгонки — те же, что использует настоящая оценка.

```python
import numpy as np
from math import comb

# 1. оценки: n попыток на одной задаче, c из них успешны
def pass_at_k(n, c, k):                 # P(хотя бы одна из k попыток успешна), несмещённо (Chen et al., 2021)
    if n - c < k: return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))
def pass_hat_k(n, c, k):                # P(все k попыток успешны), несмещённо (pass^k из tau-bench)
    if c < k: return 0.0
    return float(np.prod(np.arange(c - k + 1, c + 1) / np.arange(n - k + 1, n + 1)))
assert abs(pass_at_k(10, 3, 4) - (1 - comb(7, 4) / comb(10, 4))) < 1e-12
assert abs(pass_hat_k(10, 7, 4) - comb(7, 4) / comb(10, 4)) < 1e-12
print('one task, n=10, c=3:', [round(float(pass_at_k(10, 3, k)), 3) for k in (1, 2, 4, 8)],
      [round(pass_hat_k(10, 3, k), 3) for k in (1, 2, 4, 8)])
# one task, n=10, c=3: [0.3, 0.533, 0.833, 1.0] [0.3, 0.067, 0.0, 0.0]

# 2. синтетический бенчмарк: задача i решается одной попыткой с вероятностью p_i ~ Beta(1.2, 0.8)
A, B = 1.2, 0.8
rng = np.random.default_rng(1)
N, n = 50, 20
p = rng.beta(A, B, N)
c = rng.binomial(n, p)                      # n попыток агента на каждой задаче
def benchmark(c, k):
    return np.mean([pass_at_k(n, ci, k) for ci in c]), np.mean([pass_hat_k(n, ci, k) for ci in c])
def population(k):                          # по всей генеральной совокупности Beta: 1 - E[(1-p)^k] и E[p^k]
    return 1 - np.prod([(B + j) / (A + B + j) for j in range(k)]), np.prod([(A + j) / (A + B + j) for j in range(k)])
for k in (1, 2, 4, 8):
    print(f'k={k}: pass@k {benchmark(c, k)[0]:.3f}  pass^k {benchmark(c, k)[1]:.3f}   population {population(k)[0]:.3f} {population(k)[1]:.3f}')
# k=1: pass@k 0.613  pass^k 0.613   population 0.600 0.600
# k=2: pass@k 0.788  pass^k 0.438   population 0.760 0.440
# k=4: pass@k 0.903  pass^k 0.279   population 0.872 0.296
# k=8: pass@k 0.955  pass^k 0.172   population 0.938 0.186

# 3. несмещённость: повторяем попытки на тех же 50 задачах; подстановочная 1 - (1 - c/n)^k занижена (она вогнута по c/n)
reruns = rng.binomial(n, p, size=(2000, N))
for k in (4, 8):
    est = np.array([benchmark(cr, k)[0] for cr in reruns[:500]])
    plug = np.mean(1 - (1 - reruns / n) ** k)
    print(f'k={k}: true {np.mean(1 - (1 - p) ** k):.3f}  unbiased {est.mean():.3f} (sd {est.std():.3f})  plug-in {plug:.3f}')
# k=4: true 0.917  unbiased 0.917 (sd 0.011)  plug-in 0.904
# k=8: true 0.972  unbiased 0.972 (sd 0.010)  plug-in 0.961

# 4. 95-процентный интервал для доли успехов: перевыбираем задачи (единицы), а не попытки
def boot_ci(c, n, B=2000, rng=rng, unit='task'):
    N = len(c)
    if unit == 'task':
        idx = rng.integers(0, N, (B, N)); stats = c[idx].sum(1) / (N * n)
    else:                                # считает все N*n попыток независимыми
        trials = np.repeat([1, 0], [c.sum(), N * n - c.sum()])
        stats = rng.choice(trials, (B, N * n)).mean(1)
    return np.percentile(stats, [2.5, 97.5])
print('success rate', round(c.sum() / (N * n), 3), 'task bootstrap', np.round(boot_ci(c, n), 3),
      'trial bootstrap', np.round(boot_ci(c, n, unit='trial'), 3))
true_rate = A / (A + B)                  # доля по генеральной совокупности задач, из которой берёт выборку бенчмарк
cover = {'task': 0, 'trial': 0}
for r in range(300):
    pr = rng.beta(A, B, N); cr = rng.binomial(n, pr)
    for u in cover:
        lo, hi = boot_ci(cr, n, B=1000, unit=u); cover[u] += lo <= true_rate <= hi
print('coverage over 300 benchmarks:', {u: round(float(v) / 300, 2) for u, v in cover.items()})
# success rate 0.613 task bootstrap [0.538 0.682] trial bootstrap [0.582 0.643]
# coverage over 300 benchmarks: {'task': 0.95, 'trial': 0.55}

# 5. сколько задач: Var = Var(p)/N + E[p(1-p)]/(n N); дополнительные попытки не убирают первое слагаемое
var_p = A * B / ((A + B) ** 2 * (A + B + 1)); e_pq = true_rate * (1 - true_rate) - var_p
for N_, n_ in ((50, 1), (50, 20), (50, 1000), (200, 20), (800, 1)):
    print(f'N={N_:4d} n={n_:5d}: half-width {1.96 * np.sqrt(var_p / N_ + e_pq / (n_ * N_)):.3f}')
# N=  50 n=    1: half-width 0.136
# N=  50 n=   20: half-width 0.082
# N=  50 n= 1000: half-width 0.078
# N= 200 n=   20: half-width 0.041
# N= 800 n=    1: half-width 0.034

# 6. горизонт задачи: подгоняем P(success) = sigmoid(beta (log2 h - log2 t)) к запускам на задачах с известным человеческим временем t
T = np.round(2 ** rng.uniform(0, 10, 40)).astype(int)         # 40 задач от 1 минуты до 17 часов (в минутах)
h_true, beta_true = 60.0, 0.6
runs = 8
wins = rng.binomial(runs, 1 / (1 + np.exp(-beta_true * (np.log2(h_true) - np.log2(T)))))
def fit_horizon(T, wins, runs, iters=50):
    X = np.c_[np.ones(len(T)), np.log2(T)]; w = np.zeros(2)          # логит = w0 + w1 log2 t
    for _ in range(iters):                                           # метод Ньютона для биномиального логарифма правдоподобия
        q = 1 / (1 + np.exp(-X @ w))
        g = X.T @ (wins - runs * q); H = (X * (runs * q * (1 - q))[:, None]).T @ X + 1e-9 * np.eye(2)
        w += np.linalg.solve(H, g)
    beta = -w[1]; return 2 ** (w[0] / beta), beta                    # h50 — там, где логит равен 0
h, beta = fit_horizon(T, wins, runs)
hb = []
for _ in range(1000):
    i = rng.integers(0, len(T), len(T)); hb.append(fit_horizon(T[i], wins[i], runs)[0])
print(f'h50 = {h:.1f} min (true 60), beta = {beta:.2f}, 95% task bootstrap [{np.percentile(hb, 2.5):.1f}, {np.percentile(hb, 97.5):.1f}]')
print(f'h80 = {h * 2 ** (-np.log(4) / beta):.1f} min')                     # сигмоида равна 0.8 там, где логит равен ln 4
print('tasks:', T.tolist()); print('wins:', wins.tolist())
# h50 = 67.4 min (true 60), beta = 0.57, 95% task bootstrap [49.8, 93.9]
# h80 = 12.6 min
# tasks: [4, 2, 14, 16, 5, 19, 2, 9, 2, 14, 8, 59, 475, 197, 42, 253, 1, 1, 75, 450, 70, 1, 60, 36, 306, 1, 43, 4, 226, 60, 20, 58, 85, 22, 93, 115, 2, 347, 5, 7]
# wins: [8, 8, 6, 6, 8, 7, 8, 6, 7, 7, 7, 4, 2, 3, 5, 3, 8, 7, 2, 0, 2, 8, 4, 6, 2, 7, 6, 8, 0, 3, 5, 7, 5, 6, 4, 2, 7, 2, 5, 8]

# 7. время удвоения: метод наименьших квадратов для log2 h50 по дате выпуска
dates = np.array([2019.1, 2020.4, 2022.2, 2023.2, 2024.0, 2024.5, 2025.1, 2025.6])
log2h = np.log2(0.05) + (dates - 2019.1) * 12 / 7 + rng.normal(0, 0.6, len(dates))   # истинное удвоение: 7 месяцев
slope = np.polyfit(dates, log2h, 1)[0]
print('doubling time', round(12 / slope, 1), 'months')
# doubling time 7.2 months

# 8. стоимость: повторяем, пока тесты не пройдут, не больше k попыток; успех = pass@k, ожидаемое число попыток = sum_j E[(1-p)^j]
def beta_fail(a, b, j): return np.prod([(b + i) / (a + b + i) for i in range(j)])
configs = []
for name, (a, b, price) in {'small': (0.6, 0.9, 0.01), 'large': (1.2, 0.6, 0.10)}.items():
    for k in (1, 2, 4, 8, 16):
        configs.append((name, k, 1 - beta_fail(a, b, k), price * sum(beta_fail(a, b, j) for j in range(k))))
front = [x for x in configs if not any(y[2] >= x[2] and y[3] <= x[3] and y != x for y in configs)]
for x in configs: print(f'{x[0]:5s} k={x[1]:2d}: success {x[2]:.3f}  cost ${x[3]:.3f}' + ('   front' if x in front else ''))
# small k= 1: success 0.400  cost $0.010   front
# small k= 2: success 0.544  cost $0.016   front
# small k= 4: success 0.673  cost $0.024   front
# small k= 8: success 0.774  cost $0.036   front
# small k=16: success 0.847  cost $0.051   front
# large k= 1: success 0.667  cost $0.100
# large k= 2: success 0.810  cost $0.133
# large k= 4: success 0.902  cost $0.165   front
# large k= 8: success 0.953  cost $0.195   front
# large k=16: success 0.979  cost $0.221   front
```
