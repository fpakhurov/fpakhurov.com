[Предыдущая заметка](/ru/notes/agents/context-and-memory) дала агенту память, так что длинная задача больше не ломается на границе контекстного окна. Память не решает, что делать дальше. Цикл из заметки [ReAct и цикл агента](/ru/notes/agents/react-and-the-agent-loop) выбирает по одному действию за раз, исходя из того, что модели кажется правильным сейчас, а на задачах, где ранний ход может сделать более позднюю цель недостижимой, этого мало. Первый раздел курса решал такие задачи поиском: заметка [Поиск и планирование](/ru/notes/agents/search-and-planning) формулировала их как пространства состояний и находила планы с помощью A\* и PDDL-планировщиков, а заметка [Игры и поиск по дереву методом Монте-Карло](/ru/notes/agents/games-and-tree-search) искала с помощью сэмплирования. Эта заметка спрашивает, насколько хорошо планируют языковые модели и как они начинают планировать лучше, когда вокруг них возвращают старые механизмы: разбиение на шаги, классический планировщик, получающий формулировку от модели, поиск по дереву предложений модели и модель мира, в которой можно искать.

**Обозначения.** Состояние $s$, действие $a$, цель $G$ и план $(a_1, \dots, a_n)$. Языковая модель — это **распределение предложений** (proposal distribution) $p_\theta(a \mid s, G)$ над следующими действиями; **оценка ценности** (value estimate) $V(s)$ говорит, насколько многообещающе состояние; **модель переходов** (transition model) $s' = f(s, a)$ даёт следующее состояние, а **верификатор** (verifier) проверяет, что действие применимо и что состояние удовлетворяет $G$. При поиске на каждое состояние берётся $k$ предложений, а на каждой глубине сохраняется $b$ состояний.

## Отправная точка: решать по одному шагу \{#baseline-decide-one-step-at-a-time\}

Агент, который ничего не планирует, следует своему распределению предложений: в каждом состоянии он выбирает самое вероятное действие, $a_t = \arg\max_a p_\theta(a \mid s_t, G)$. В терминах заметки о поиске это жадный поиск по первому наилучшему (greedy best-first search), где эвристикой служит модель, граница состоит из одного узла, а возвратов нет. Он работает, когда локально привлекательный ход оказывается и глобально верным, и отказывает ровно там, где нужно планирование.

**Разобранный пример: снова аномалия Зуссмана.** Задача о блоках из заметки о поиске: C стоит на A, B — на столе, цель — A на B на C. Заскриптованная замена модели (в разделе «Код») предлагает ходы, которые делают целевой факт истинным, и избегает ходов, которые его отменяют, с некоторым шумом:

<GreedyVsSearch />

Из начального состояния ход «поставить B на C» делает целевой факт on(B, C) истинным, поэтому модель его предлагает. Это ловушка: A теперь погребён под C и B, и единственный допустимый ход — снова снять B, что отменяет целевой факт. В начальном состоянии «B на C» выглядит так же хорошо, как и раньше. В одном из десяти запусков раздела «Код» этот цикл повторяется шесть раз, прежде чем шум разрывает ничью, и запуску нужно 15 ходов для плана из 3 ходов; по десяти запускам планы занимают от 3 до 15 ходов, в среднем 6.8. A\* с допустимой эвристикой (числом блоков, ещё не стоящих на своём окончательном месте) раскрывает 4 состояния и возвращает оптимальный план. Жадный агент не глуп; у него просто нет способа заметить, что целевой факт, достигнутый сейчас, позже придётся отменить, — именно в этом и состоит взаимодействие целей в аномалии Зуссмана.

<aside class="callout"><strong>Ключевая идея.</strong> Языковая модель — хороший источник шагов-кандидатов и плохой гарант планов. Планировать с ней нужно так, как первый раздел планировал с эвристиками: модель предлагает, что-то надёжное проверяет, а поиск идёт по предложениям с проверкой цели, возвратами и бюджетом. Если задачу можно записать на языке планирования, пусть модель её запишет, а решит классический планировщик.</aside>

## Декомпозиция: сначала план или план по ходу \{#decomposition-plan-first-or-plan-as-you-go\}

Простейшая форма планирования — **декомпозиция задачи** (task decomposition): разбить цель на подцели на естественном языке, прежде чем действовать. «Исправить падающий тест» превращается в «воспроизвести сбой, найти функцию, которая выдаёт неверное значение, изменить её, перезапустить набор тестов». Две архитектуры различаются тем, когда это происходит.

- **Сначала план, потом выполнение** (plan-and-execute). Модель один раз пишет весь план, а исполнитель выполняет шаги; модель вызывается снова только для того, чтобы составить ответ, или когда шаг не удался. ReWOO с его заполнителями для свидетельств и вызовами инструментов, которые делаются без модели, — пример из заметки [ReAct и цикл агента](/ru/notes/agents/react-and-the-agent-loop#plan-first-then-execute) вместе с измеренной экономией токенов.
- **Чередующееся планирование** (interleaved planning). ReAct выбирает каждый шаг, увидев предыдущее наблюдение. Он приспосабливается к неожиданностям ценой вызова модели на каждом шаге по растущему контексту.

Арифметика токенов из [предыдущей заметки](/ru/notes/agents/context-and-memory#baseline-append-everything) делает разницу для планирования конкретной. При префиксе из $s$ токенов, $T$ шагах с инструментами и $d$ токенах на шаг чередующийся агент делает $T + 1$ вызовов модели, которые читают $\sum_{t=1}^{T+1} \big(s + (t - 1)d\big)$ токенов, — квадратично по $T$. Агент «сначала план» делает два вызова: планировщик читает $s$, а решатель — около $s + T d$; это линейно по $T$. При $s = 2\,000$, $d = 500$ и $T = 5$ получается $6 \cdot 2\,000 + 500 \cdot 15 = 19\,500$ токенов против $2\,000 + 4\,500 = 6\,500$. Вызовы инструментов фиксированного плана к тому же можно выполнять параллельно.

| | сначала план, потом выполнение | чередующееся (ReAct) |
| --- | --- | --- |
| вызовы модели | около двух плюс перепланирование | по одному на шаг |
| входные токены | линейны по числу шагов | квадратичны без сжатия |
| реагирует на наблюдение | только перепланированием | на каждом шаге |
| отказывает, когда | план неверен, и никто этого не замечает | агент уходит в сторону, зацикливается или забывает цель |
| подходит для | шагов, известных заранее | исследования, отладки |

Практические агенты сочетают оба подхода: короткий план пишется в начале и хранится в конце контекста (список дел из предыдущей заметки), выполняется шаг за шагом и пересматривается, когда наблюдение ему противоречит. У плана в прозе нет проверки цели и нет предусловий, так что его ничто не проверяет, пока этого не сделает мир.

## Насколько хорошо языковые модели планируют сами? \{#how-well-do-language-models-plan-on-their-own\}

PlanBench ([Valmeekam et al., 2023](#references)) проверяет порождение планов на доменах International Planning Competition; задачи генерируются из PDDL и проверяются валидатором планов VAL. На 600 задачах Blocksworld с тремя–пятью блоками, когда домен описан на естественном языке и дан один пример, GPT-4 в 2023 году выдала допустимый план для 206 задач, или 34.3% ([Valmeekam et al., 2023b](#references)). Из 50 человек, получивших то же описание, допустимый план написали 39 (78%). Показательный вариант — **Mystery Blocksworld**: те же задачи, в которых действия и предикаты переименованы в посторонние слова («attack», «feast»), что для планировщика ничего не меняет. Успех GPT-4 упал до 26 из 600, 4.3%, а со случайными строками в качестве имён — до 12 из 600, 2%. Модели, которая действительно планирует, было бы всё равно, как называются действия; модели, которая вспоминает планы для знакомо звучащих задач, — нет.

Рассуждающие модели 2024 года сильно сдвинули эти числа ([Valmeekam, Stechly and Kambhampati, 2024](#references)). OpenAI o1-preview в режиме zero-shot решила 587 из 600 задач Blocksworld (97.8%) и 317 из 600 задач Mystery Blocksworld (52.8%), где прежние модели были близки к нулю. На 110 более крупных задачах, от 6 до 20 блоков с оптимальными планами от 20 до 40 шагов, она решила 23.6%. Классический планировщик Fast Downward решил их все, в среднем за 0.265 секунды против 40–111 секунд на задачу у o1-preview, и с гарантией, что каждый возвращённый им план допустим. На 2026 год рассуждающие модели снова стали лучше, и приведённые числа лучше читать как датированный снимок одного бенчмарка. Два заключения сохранились через поколения моделей: успех падает с ростом длины планов, и план от модели нужно проверить, прежде чем кто-то начнёт по нему действовать. Если надёжный верификатор существует, им нужно пользоваться. Когда планы GPT-4 проверял VAL и ошибки возвращались модели («предусловие clear(C) шага 3 не выполнено»), она нашла допустимый план для 41 из 50 задач Blocksworld, которые до этого провалила, не более чем за 15 раундов; почему внешние проверки работают там, где самопроверка не работает, разбирает заметка [Рефлексия и самокоррекция](/ru/notes/agents/reflection-and-self-correction).

## LLM+P: модель ставит задачу, планировщик ищет \{#llmp-the-model-formulates-a-planner-searches\}

LLM+P ([Liu et al., 2023](#references)) делит работу по линии, проведённой в [заметке о поиске](/ru/notes/agents/search-and-planning#why-this-matters-for-language-model-planners). Протокол состоит из четырёх шагов:

1. Человек один раз задаёт **домен** (domain) на PDDL: предикаты и схемы действий с их предусловиями и эффектами, как в [разделе о STRIPS заметки о поиске](/ru/notes/agents/search-and-planning#classical-planning-strips-and-pddl).
2. Получив задачу на естественном языке («красный блок стоит на синем; поставьте их в порядке…») и одну пару из описания задачи и её файла задачи PDDL в качестве примера, модель пишет **файл задачи** (problem file) PDDL: объекты, начальное состояние и цель.
3. Классический планировщик (в статье — Fast Downward) ищет план, оптимальный, если его оптимальная конфигурация успевает завершиться.
4. Модель переводит план обратно на естественный язык.

С GPT-4 на семи доменах планирования, по 20 задач в каждом (2023), модель, планирующая напрямую, выдала оптимальный план для 15% задач Blocksworld и допустимый — для 30%; LLM+P выдала оптимальные планы для 90%. По доменам она достигла 95% на Grippers и 85% на Storage, где модель в одиночку выдала оптимальные планы для 35% и 0%. Два результата очерчивают границы метода. Без примера файла задачи в промпте LLM+P не решила ничего ни в одном домене: слабое звено — перевод, который делает модель, а не планировщик, и модели нужно увидеть целевой формат. А на Floortile не справились оба подхода, потому что модель не смогла правильно перевести задачи.

Там, где такое разделение применимо, оно надёжно. Всё, что возвращает планировщик, — допустимый план для полученного им файла задачи, так что все оставшиеся ошибки — ошибки постановки, и их можно проверять отдельно: файл должен разбираться, упоминать только объявленные объекты и иметь начальное состояние, совпадающее с описанием. Цена — файл домена, который пишет человек, и предположение, что мир укладывается в STRIPS: детерминирован, полностью наблюдаем, с дискретными действиями. Более поздние работы просят модель набросать и файл домена, а человек или валидатор его исправляет, — это переносит трудную часть, а не убирает её.

## Поиск по предложениям модели \{#search-over-model-proposals\}

Там, где никакой язык планирования не подходит, поиск из первого раздела может идти по собственным предложениям модели:

<ProposeVerifySearch />

1. **Выбор** состояний с границы: $b$ сохранённых на текущей глубине или лист, выбранный стратегией спуска по дереву.
2. **Предложение**: модель сэмплирует $k$ действий-кандидатов или частичных решений из $p_\theta(\cdot \mid s, G)$.
3. **Проверка**: всё, что можно проверить механически, проверяется, а неприменимые или некорректные предложения отбрасываются.
4. **Переход**: каждое оставшееся действие даёт следующее состояние — из настоящей среды, из симулятора или из модели мира.
5. **Оценка и отбор**: оценка ценности $V(s')$ оценивает новые состояния, и поиск сохраняет лучшие; состояние, удовлетворяющее проверке цели, завершает поиск планом.

Жадное следование предложениям — частный случай $k = b = 1$ без верификатора. Методы ниже различаются алгоритмом поиска и тем, откуда берутся $V$ и $f$.

**Tree of Thoughts** ([Yao et al., 2023](#references)) запускает поиск в ширину с лучом или поиск в глубину с возвратами по «мыслям» — частичным решениям в виде текста; модель их предлагает и сама же оценивает, играя роль и $p_\theta$, и $V$. Его результат на «Игре 24» приведён в [заметке о поиске](/ru/notes/agents/search-and-planning#why-this-matters-for-language-model-planners).

**RAP**, Reasoning via Planning ([Hao et al., 2023](#references)), добавляет модель переходов. Одну и ту же модель промптят дважды для разных ролей: как агент она предлагает действие, а как **модель мира** (world model) предсказывает получающееся состояние в виде текста («оранжевый блок в руке, на красном блоке ничего нет…»). Награда сочетает уверенность модели в действии с сигналами, специфичными для задачи, а поиск по дереву методом Монте-Карло с правилом UCT из [заметки об играх](/ru/notes/agents/games-and-tree-search#selection-as-a-bandit-problem-ucb1-and-uct) выбирает, где расширять дерево. На задачах Blocksworld, требующих 2, 4 и 6 шагов, LLaMA-33B с RAP и 20 итерациями решила 100%, 88% и 42% против 17%, 2% и 0% у той же модели с цепочкой рассуждений (chain of thought) и 50%, 63% и 40% у GPT-4 с цепочкой рассуждений (2023).

**LATS**, Language Agent Tree Search ([Zhou et al., 2024](#references)), запускает MCTS по целым траекториям ReAct в настоящей среде. Её оценка ценности смешивает собственную оценку модели с согласием между сэмплами,

$$
V(s) = \lambda\, \text{LM}(s) + (1 - \lambda)\, \text{SC}(s),
$$

где $\text{LM}(s)$ — оценка, которую модель даёт траектории на данный момент, $\text{SC}(s)$ — оценка самосогласованности (self-consistency; как часто одно и то же действие предлагается среди сэмплов), а $\lambda$ — вес. Когда траектория проваливается, модель пишет рефлексию о том, почему, и она добавляется в контекст следующих попыток, — механизм следующей заметки. На HumanEval, где GPT-4 генерировала 5 кандидатов на каждое расширение в течение не более 8 итераций и проверяла их модульными тестами, которые написала сама, LATS достигла pass@1 92.7% против 80.1% у одной GPT-4 (2024).

**Разобранный пример: что даёт поиск.** Раздел «Код» запускает три планировщика на 200 случайных задачах о блоках каждого размера с заскриптованным генератором предложений, $k = 3$ предложениями и $b = 3$ состояниями, сохраняемыми на каждой глубине при поиске по предложениям, и бюджетом в 20 ходов для жадного агента:

| блоков | жадно, без верификатора | жадно, с верификатором | поиск по предложениям | A\* |
| --- | --- | --- | --- | --- |
| 3 | 41.0% | 95.0% | 100% | 100% |
| 4 | 16.5% | 77.0% | 95.5% | 100% |
| 5 | 3.5% | 65.0% | 94.5% | 100% |
| 6 | 2.0% | 60.5% | 84.5% | 100% |

Без верификатора одного недопустимого хода на десять предложений достаточно, чтобы погубить большинство эпизодов; с верификатором жадное следование всё равно проваливает 40% задач с шестью блоками, а его успешные планы на 2.7 хода длиннее оптимальных. Поиск по тем же предложениям, с оценкой ценности, верной лишь в среднем, решает 84.5% с планами, длиннее оптимальных на 0.7 хода, ценой 13.6 вызова модели на задачу. A\* с эвристикой, допустимой по построению, всегда находит оптимальный план, раскрывая в среднем 8.3 состояния, тогда как поиск в ширину достигает 2179. Разрыв между двумя последними столбцами — это разрыв между эвристикой, которая угадывает, и эвристикой, которая гарантированно никогда не завышает, а такой гарантии не даёт ни одна языковая модель.

Сторона затрат вполне реальна. Каждое расширение — это вызов модели, и каждая оценка может оказаться ещё одним; поиск, дешёвый с точным симулятором, дорог, когда моделью переходов служит сама языковая модель. И поиску нужна возможность откатиться: возврат из состояния бесплатен в симуляторе и невозможен на живом сайте после покупки или отправленного сообщения.

## Модели мира для планирования \{#world-models-for-planning\}

Поиск в настоящей среде требует среды, которую можно сбросить. Когда этого сделать нельзя, агенту нужна **модель мира** (world model): функция, которая предсказывает исход действия, не выполняя его, — идея, которую заметка [Обучение с подкреплением на основе модели](/ru/notes/agents/model-based-rl) развивает с выученной динамикой. Языковая модель может служить такой моделью в текстовом виде, как в RAP. WebDreamer ([Gu et al., 2024](#references)) применяет это к веб-агентам: для каждого действия-кандидата на странице модель описывает, как страница будет выглядеть после него, оценка ценности оценивает воображаемые исходы, и по-настоящему выполняется только лучшее действие. На VisualWebArena он был сопоставим с поиском по дереву в настоящей среде, будучи в четыре-пять раз эффективнее, и работал на живых сайтах, где поиск по дереву недоступен, потому что действия нельзя отменить; модель с 7 миллиардами параметров, обученная в роли модели мира, справлялась с этой ролью сравнимо с GPT-4o (2024–2025).

Воображаемые исходы наследуют ошибки модели, и ошибки накапливаются с глубиной: прогон (rollout) из десяти воображаемых шагов — это десять предсказаний, каждое из которых зависит от предыдущих. Поэтому модели мира используют для короткого просмотра вперёд, на один-два шага, чтобы ранжировать действия перед необратимым; окончательным верификатором остаётся настоящая среда.

<aside class="callout"><strong>Проверьте себя.</strong> (1) Чередующийся агент с $s = 3\,000$ и $d = 1\,000$ использует $T = 8$ шагов с инструментами. Сколько входных токенов читают его вызовы модели и сколько читает агент «сначала план», если решатель читает $s + T d$? (2) Почему падение с 34.3% до 4.3% на Mystery Blocksworld говорит о планировании больше, чем сами 34.3%? (3) В LLM+P планировщик сообщает, что у файла задачи нет решения. Кто виноват и что должен сделать агент?<details><summary>Ответы</summary>(1) Девять вызовов читают $9 \cdot 3\,000 + 1\,000 \cdot (0 + 1 + \dots + 8) = 27\,000 + 36\,000 = 63\,000$ токенов; агент «сначала план» читает $3\,000 + 11\,000 = 14\,000$. (2) Переименование оставляет задачу планирования той же самой, так что успех планировщика измениться не может; большое падение показывает, что успех зависел от узнавания знакомого домена, а не от поиска. (3) Надёжный планировщик не ошибается насчёт полученного файла (если он завершил поиск), значит, виновата постановка: модель неверно перевела начальное состояние или цель, либо задача действительно невыполнима. Агенту следует сверить файл с описанием, сгенерировать его заново, передав отчёт планировщика как обратную связь, и, если у задачи по-прежнему нет решения, спросить пользователя.</details></aside>

## Что изменилось \{#what-changed\}

| | по одному шагу | план с поиском и проверками |
| --- | --- | --- |
| кто выбирает действие | первое предложение модели | поиск по предложениям модели или планировщик |
| возвраты | нет: циклы и тупики остаются | встроены в поиск |
| что проверяет шаг | мир, после действия | верификатор и проверка цели, до действия |
| в чём модель сильна | везде, где её используют | предлагать, ставить задачу, описывать исходы |
| гарантии | нет | допустимые планы от надёжного планировщика или верификатора |
| стоимость | один вызов на шаг | много вызовов на шаг или запуск планировщика |

## Ограничения \{#limitations\}

- **Постановка остаётся узким местом.** LLM+P хороша ровно настолько, насколько хорош файл задачи, а домен кто-то должен написать. Задачи со временем, ресурсами, неопределённостью или частичной наблюдаемостью не укладываются в классический STRIPS.
- **Оценки ценности от модели не допустимы.** Поиск по предложениям исправляет многие ошибки, но наследует смещение оценщика: если модель высоко оценивает тупик, поиск его исследует.
- **Поиск умножает стоимость и задержку.** Каждое расширение — вызов модели; поиск по дереву траекторий может стоить в десятки раз больше одной попытки, и это оправдано, только когда попытку дёшево проверить, а ошибиться дорого.
- **Настоящие среды редко можно отмотать назад.** Для возвратов нужны симулятор, песочница или модель мира, а воображаемые исходы за несколько шагов уходят от реальности.
- **Бенчмарки быстро устаревают.** Результаты на PlanBench, HumanEval и похожих наборах — снимки конкретных моделей и промптов; рассуждающие модели изменили их в течение года, и результаты из разных постановок нельзя ранжировать.

## Что нужно запомнить \{#what-you-should-remember\}

- Следовать первому предложению модели — это жадный поиск без возвратов; он отказывает там, где цели взаимодействуют, как в аномалии Зуссмана, и зацикливается там, где привлекательный ход приходится отменять.
- «Сначала план, потом выполнение» пишет план один раз (два вызова модели, линейное число токенов); чередующееся планирование выбирает каждый шаг после наблюдения (один вызов на шаг, квадратичное число токенов). Гибриды держат короткий план и пересматривают его.
- На PlanBench GPT-4 в 2023 году решила 34.3% задач Blocksworld и 4.3% после запутывания имён; o1-preview в 2024 году решила 97.8% и 52.8%, а также 23.6% более крупных задач, тогда как классический планировщик решил их все с гарантиями.
- LLM+P даёт модели написать файл задачи PDDL, а планировщику — найти план; перевод — слабое звено, и пример целевого формата необходим.
- Поиск по предложениям модели (Tree of Thoughts, RAP с моделью мира и MCTS, LATS по траекториям ReAct) использует модель как распределение предложений и оценку ценности, а верификатор и проверка цели дают то, чего модель дать не может. Модели мира позволяют смотреть вперёд там, где действия нельзя отменить.

## Код \{#code\}

Мир блоков как среда в стиле STRIPS с проверкой предусловий (верификатор), заскриптованная замена модели, которая ранжирует следующие ходы по тому, делают ли они целевой факт истинным или отменяют его (с шумом и изредка недопустимыми предложениями), и три планировщика: жадное следование предложениям, лучевой поиск (beam search) по предложениям модели с зашумлённой оценкой ценности и A\* с допустимой эвристикой. С настоящей моделью `propose` разбирала бы ходы из текста модели, а `value` просила бы её оценить состояние; верификатор, поиск и сравнение остаются прежними. Только NumPy и стандартная библиотека; начальные значения генератора (seed) зафиксированы, скрипт работает около восьми секунд, а точные числа могут отличаться на разных платформах и версиях библиотек.

```python
import heapq, itertools
from collections import deque
import numpy as np

# 1. мир блоков: состояние — множество стопок, каждая — кортеж снизу вверх
def canon(stacks): return tuple(sorted(tuple(s) for s in stacks if s))
def on_map(state):                                               # блок -> на чём он стоит ('T' — стол)
    return {b: (s[i - 1] if i else 'T') for s in state for i, b in enumerate(s)}
def valid(state, move):                                          # верификатор: предусловия STRIPS
    x, dest = move
    tops = {s[-1] for s in state}
    return x in tops and x != dest and (dest == 'T' or dest in tops) and not (dest == 'T' and on_map(state)[x] == 'T')
def apply(state, move):                                          # модель переходов
    x, dest = move
    stacks = [list(s) for s in state]
    src = next(s for s in stacks if s and s[-1] == x); src.pop()
    if dest == 'T': stacks.append([x])
    else: next(s for s in stacks if s and s[-1] == dest).append(x)
    return canon(stacks)
def moves(state):
    blocks = [b for s in state for b in s]
    return [(x, d) for x in blocks for d in blocks + ['T'] if valid(state, (x, d))]

# 2. заскриптованная замена языковой модели, предлагающей следующий ход: она любит ходы, которые делают целевой
#    факт истинным, не любит ходы, которые его отменяют, иногда называет погребённый блок и зашумлена
class ScriptedProposer:
    def __init__(self, goal, rng, noise=0.6, slip=0.1):
        self.g, self.rng, self.noise, self.slip = on_map(goal), rng, noise, slip
    def propose(self, state):                                    # ранжированный список ходов, лучший первым
        on = on_map(state)
        cands = [(x, d) for x in on for d in list(on) + ['T'] if d != x]
        def score(m):
            x, d = m
            s = 2.0 * (self.g[x] == d) - 1.5 * (self.g[x] == on[x]) + self.noise * self.rng.normal()
            if not valid(state, m): s = s + 3.0 if self.rng.random() < self.slip else s - 10.0   # изредка ошибается
            return s
        return sorted(cands, key=score, reverse=True)

def greedy(start, goal, rng, verifier=True, budget=20):          # следовать первому (допустимому) предложению модели
    model, state, plan = ScriptedProposer(goal, rng), start, []
    for _ in range(budget):
        if state == goal: return plan
        props = model.propose(state)
        m = next(m for m in props if valid(state, m)) if verifier else props[0]
        if not valid(state, m): return None                      # без верификатора недопустимый ход завершает эпизод
        state = apply(state, m); plan.append(m)
    return plan if state == goal else None

# 3. поиск по предложениям модели: на каждой глубине сохранять b лучших состояний по зашумлённой оценке ценности (в духе Tree of Thoughts)
def value(state, goal, rng, noise=0.6):                          # модель оценивает состояние: сколько целевых фактов уже истинны
    g, on = on_map(goal), on_map(state)
    return sum(on[x] == g[x] for x in on) + noise * rng.normal()
def beam(start, goal, rng, k=3, b=3, depth=20):
    model, level, seen, calls = ScriptedProposer(goal, rng), [start], {start}, 0
    for dpt in range(depth):
        children = []
        for s in level:
            if s == goal: return dpt, calls
            calls += 1                                           # один вызов для предложений на каждое раскрытое состояние
            for m in [m for m in model.propose(s) if valid(s, m)][:k]:
                t = apply(s, m)
                if t not in seen: seen.add(t); children.append(t)
        if not children: return None, calls
        level = sorted(children, key=lambda t: value(t, goal, rng), reverse=True)[:b]
    return None, calls

# 4. поиск с гарантиями: A* с h = числом блоков, ещё не стоящих на своём окончательном месте (каждому нужен хотя бы один ход)
def h_misplaced(state, goal):
    good = {b for s in goal for i, b in enumerate(s) for t in state if t[:i + 1] == s[:i + 1]}
    return sum(len(s) for s in state) - len(good)
def astar(start, goal, h=h_misplaced):
    tie, frontier, g, parent, closed = itertools.count(), [(h(start, goal), 0, 0, start)], {start: 0}, {start: None}, set()
    while frontier:
        _, _, _, s = heapq.heappop(frontier)
        if s in closed: continue
        closed.add(s)
        if s == goal:
            plan = []
            while parent[s]: s, m = parent[s]; plan.append(m)
            return plan[::-1], len(closed)
        for m in moves(s):
            t = apply(s, m)
            if g[s] + 1 < g.get(t, 1e9):
                g[t], parent[t] = g[s] + 1, (s, m)
                heapq.heappush(frontier, (g[t] + h(t, goal), -g[t], next(tie), t))
    return None, len(closed)

# 5. аномалия Зуссмана: C на A, A и B на столе; цель — A на B на C
start, goal = canon([['A', 'C'], ['B']]), canon([['C', 'B', 'A']])
print(astar(start, goal))                                        # ([('C', 'T'), ('B', 'C'), ('A', 'B')], 4)
rng = np.random.default_rng(0)
runs = [greedy(start, goal, rng) for _ in range(10)]
print([len(p) for p in runs])                                    # [3, 3, 15, 5, 15, 3, 5, 3, 7, 9]
print(runs[2][:4])                                               # [('B', 'C'), ('B', 'T'), ('B', 'C'), ('B', 'T')]

# 6. случайные задачи с n блоками: жадное следование предложениям, поиск по предложениям и A*
def random_state(blocks, rng):
    order, stacks = list(rng.permutation(blocks)), []
    for x in order:
        if stacks and rng.random() < 0.6: stacks[rng.integers(len(stacks))].append(x)
        else: stacks.append([x])
    return canon(stacks)
def bfs_count(start, goal):                                      # неинформированный поиск, для подсчёта узлов
    seen, q = {start}, deque([start])
    while q:
        s = q.popleft()
        if s == goal: return len(seen)
        for m in moves(s):
            t = apply(s, m)
            if t not in seen: seen.add(t); q.append(t)

rng = np.random.default_rng(1)
for n in (3, 4, 5, 6):
    ok = dict(free=0, greedy=0, beam=0, astar=0); extra = dict(greedy=[], beam=[]); calls, exp_a, exp_b = [], [], []
    for _ in range(200):
        s0, g0 = random_state(list('ABCDEF'[:n]), rng), random_state(list('ABCDEF'[:n]), rng)
        p, e = astar(s0, g0); ok['astar'] += 1; exp_a.append(e); exp_b.append(bfs_count(s0, g0))
        ok['free'] += greedy(s0, g0, rng, verifier=False) is not None
        q = greedy(s0, g0, rng)
        if q is not None: ok['greedy'] += 1; extra['greedy'].append(len(q) - len(p))
        dpt, c = beam(s0, g0, rng)
        if dpt is not None: ok['beam'] += 1; extra['beam'].append(dpt - len(p)); calls.append(c)
    print(n, {k: v / 2 for k, v in ok.items()}, round(np.mean(extra['greedy']), 2), round(np.mean(extra['beam']), 2),
          round(np.mean(calls), 1), round(np.mean(exp_a), 1), round(np.mean(exp_b), 1))
# 3 {'free': 41.0, 'greedy': 95.0, 'beam': 100.0, 'astar': 100.0} 1.09 0.0 3.3 3.1 8.5
# 4 {'free': 16.5, 'greedy': 77.0, 'beam': 95.5, 'astar': 100.0} 1.79 0.16 7.2 4.5 49.1
# 5 {'free': 3.5, 'greedy': 65.0, 'beam': 94.5, 'astar': 100.0} 1.87 0.7 11.9 6.4 301.8
# 6 {'free': 2.0, 'greedy': 60.5, 'beam': 84.5, 'astar': 100.0} 2.72 0.7 13.6 8.3 2179.4
#   (блоков; % решённых: жадно без верификатора и с ним, лучевой поиск по предложениям, A*; лишние ходы сверх оптимума
#    у жадного и лучевого; вызовы модели у лучевого; состояний, раскрытых A* и достигнутых поиском в ширину)
```
