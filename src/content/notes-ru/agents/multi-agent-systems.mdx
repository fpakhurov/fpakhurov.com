Каждый агент этого раздела до сих пор был одной моделью в одном цикле с одним контекстом. [Исследовательский агент](/ru/notes/agents/research-agents) уже испытывает эту архитектуру на прочность: вопрос, который ветвится на десять подвопросов, заполняет единственный контекст страницами, прочитанными для первого подвопроса, пока агент работает над десятым, а подвопросы ждут друг друга, хотя друг от друга не зависят. Очевидное средство — разделить работу между несколькими агентами, у каждого из которых свой контекст, и это поднимает старый вопрос искусственного интеллекта: что происходит, когда в одной среде действуют несколько агентов? Заметка отвечает на него в две части. Сначала, кратко, классический взгляд: агенты со своими целями и то, как они приходят к сотрудничеству. Затем системы на языковых моделях последних трёх лет: что они выигрывают от нескольких агентов, чем за это платят, и расчёт, который ограничивает то, чего может добиться голосование любого числа агентов.

**Обозначения.** Агентов $n$. В игре агент $i$ выбирает действие $a_i$ и получает выигрыш (payoff) $u_i(a_1, \dots, a_n)$. В анализе голосования агенты отвечают на вопрос «да или нет»; $X_i \in \{0, 1\}$ показывает, что агент $i$ прав, причём $P(X_i = 1) = p$ для каждого агента, а $\rho$ — корреляция между правильностью любых двух агентов. $A_n$ — вероятность того, что большинство из $n$ агентов (при нечётном $n$) право, а $B_n(p)$ — та же вероятность для независимых агентов.

## Отправная точка: один агент делает всё \{#baseline-one-agent-does-everything\}

Один агент справляется с задачей из многих частей, выполняя их одну за другой в одном контексте. У этого есть настоящие преимущества: каждое решение принимается с учётом всего, что агент видел, ничего не теряется при передаче работы между агентами, а стоимость — вызовы одного контекста. Его пределы — пределы контекстного окна и времени. Каждая страница, прочитанная для любой части, остаётся в контексте, или сжимается и пропадает, для всех следующих частей; шаги идут последовательно, даже когда они независимы; а слепые пятна одной модели присутствуют на каждом шаге, и ловить их некому.

## Классические мультиагентные идеи вкратце \{#classical-multi-agent-ideas-in-brief\}

В терминах заметки [Что такое агент](/ru/notes/agents/what-an-agent-is#the-properties-of-task-environments) среда мультиагентная, когда в ней действуют и другие агенты. Классическая теория, построенная задолго до языковых моделей, различает их по целям ([Russell and Norvig, 2021](#references), глава 18; [Shoham and Leyton-Brown, 2009](#references)).

**Соревнование** — случай из заметки [Игры и поиск по дереву методом Монте-Карло](/ru/notes/agents/games-and-tree-search#minimax): два игрока, выигрыш одного — проигрыш другого, решается минимаксом. **Игры с ненулевой суммой** (general-sum games) тоньше, потому что интересы агентов частично совпадают. Теория игр описывает выигрыш каждого агента при каждом сочетании действий и спрашивает, какие сочетания устойчивы. **Равновесие Нэша** (Nash equilibrium) — такой выбор действий, при котором ни один агент не может выиграть, изменив в одиночку только своё действие:

$$
u_i(a_i^\star, a_{-i}^\star) \ge u_i(a_i, a_{-i}^\star) \quad \text{для каждого агента } i \text{ и каждого действия } a_i,
$$

где $a_{-i}$ обозначает действия всех агентов, кроме $i$. **Разобранный пример.** В дилемме заключённого (prisoner's dilemma) два агента каждый либо сотрудничают (C), либо предают (D), с выигрышами $(3, 3)$ при (C, C), $(0, 5)$ при (C, D), $(5, 0)$ при (D, C) и $(1, 1)$ при (D, D). Что бы ни сделал другой, предательство выгоднее: $5 > 3$ против C, $1 > 0$ против D. Поэтому (D, D) — единственное равновесие, и оба агента получают 1 там, где сотрудничество дало бы каждому 3. Рациональные агенты, действующие порознь, могут вместе получить меньше, чем могли бы: это проблема координации в самой острой форме, и она возникает снова всякий раз, когда агенты оптимизируют каждый свою часть задачи.

**Сотрудничество** — случай агентов, у которых общая цель и которым нужно разделить работу. **Протокол контрактной сети** (contract net protocol; [Smith, 1980](#references)) дал рецепт, узнаваемый и в сегодняшних системах: менеджер объявляет задачу, подрядчики делают ставки в соответствии со своими возможностями, менеджер присуждает задачу, а подрядчики сообщают результаты и при этом могут сами выступать менеджерами для своих подзадач. Эта область определила и языки, на которых агенты разговаривают друг с другом, построенные из речевых актов (speech acts), таких как *inform* (сообщить), *request* (попросить) и *propose* (предложить), чтобы цель сообщения была явной. Их современный потомок — протокол вроде Agent2Agent, через который агенты, созданные разными организациями, передают друг другу задачи ([Рабочие процессы, фреймворки и протоколы](/ru/notes/agents/workflows-and-protocols#agent2agent)). Многоагентное обучение с подкреплением добавляет трудность, которой нет при обучении одного агента: пока один агент учится, другие меняются, так что его среда больше не стационарна.

Системы на языковых моделях унаследовали почти исключительно случай сотрудничества. Их агенты обычно разделяют одну цель — цель пользователя, — а вопросы те же, что в контрактной сети: как разделить задачу, что сказать каждому агенту и как объединить то, что вернулось.

## Мультиагентные системы на языковых моделях \{#language-model-multi-agent-systems\}

Повторяются четыре архитектуры.

**Ролевая игра** (role-play). CAMEL ([Li et al., 2023](#references)) заставил два экземпляра модели разговаривать — один в роли пользователя, который даёт инструкции, другой в роли ассистента, который их выполняет, каждый со своей ролью из начального промпта, — чтобы выполнить задачу без человека в цикле. Авторы описали неудачи, с которыми потом сталкивалась каждая система: агенты меняются ролями, повторяют друг друга, отвечают без содержания или зацикливаются в разговоре, не заканчивая его.

**Фреймворки для диалога агентов.** AutoGen ([Wu et al., 2023](#references)) сделал мультиагентный разговор моделью программирования: агенты, которые отправляют и получают сообщения, человек или исполнитель кода в качестве одного из участников и групповые чаты, в которых менеджер выбирает, кто говорит следующим. Такие фреймворки позволяют легко строить множество топологий, а значит, легко строить и такие, которые хуже одного агента; заметка [Рабочие процессы, фреймворки и протоколы](/ru/notes/agents/workflows-and-protocols) обсуждает, что фреймворк решает за проектировщика, а что нет.

**Дебаты** (debate). Несколько экземпляров отвечают на один и тот же вопрос, читают ответы друг друга и пересматривают свои за несколько раундов ([Du et al., 2023](#references)). С тремя агентами и двумя раундами `gpt-3.5-turbo` (2023) дебаты подняли долю правильных ответов (accuracy) в арифметике с 67.0% у одного агента до 81.8% против 69.0% у голосования большинством по первым ответам агентов, а в школьных математических задачах (GSM8K) — с 77.0% до 85.0% против 81.0% у голосования.

**Оркестратор и субагенты.** Ведущий агент планирует, пишет поручение (brief) каждому субагенту, запускает их параллельно и сводит то, что они вернули: это контрактная сеть с языковыми моделями в роли менеджера и подрядчиков и [рабочий процесс «оркестратор — исполнители»](/ru/notes/agents/workflows-and-protocols#the-building-block-and-five-workflows), в котором исполнители сами являются агентами:

<OrchestratorWorkers />

1. **Деление.** Оркестратор делит задачу на части, которые не зависят друг от друга.
2. **Поручение.** Каждый исполнитель получает краткое описание своей части: цель, ожидаемую форму результата, инструменты, которыми пользоваться, и момент, когда остановиться.
3. **Работа.** Исполнители параллельно выполняют свои циклы, каждый в своём контексте, вызывая инструменты.
4. **Возврат.** Каждый исполнитель возвращает короткий структурированный результат, а не всё, что прочитал.
5. **Сведение.** Оркестратор проверяет результаты, запрашивает повторно там, где результат не прошёл проверку, и пишет ответ.

В июне 2025 года Anthropic описала такую систему для исследований: ведущий агент на Claude Opus 4 с субагентами на Claude Sonnet 4 показал результат на 90.2% выше, чем один агент на Claude Opus 4, на внутренней исследовательской оценке компании ([Anthropic, 2025](#references)). Ведущий агент обычно запускал параллельно от трёх до пяти субагентов, а для сложных вопросов — больше десяти, и параллельные вызовы инструментов сократили время исследования на сложных запросах до 90%. Ссылки на источники расставлял отдельный агент. Системы для программирования применяют ту же схему осторожнее: по сообщению Cognition на апрель 2026 года, работают те конфигурации, в которых писать код поручено одному агенту, а другие агенты читают, ищут или проводят ревью в чистых контекстах, тогда как рои агентов, параллельно правящих код, по-прежнему проваливаются, потому что их неявные решения противоречат друг другу ([Yan, 2026](#references)).

<aside class="callout"><strong>Ключевая идея.</strong> Несколько агентов помогают, когда они выполняют разную работу в раздельных контекстах, параллельно, и возвращают компактные проверяемые результаты; или когда их ошибки независимы, так что сравнение ответов гасит ошибки. Общую ошибку они перевесить голосованием не могут, а каждая передача между ними может потерять то, что было нужно другому.</aside>

## Когда несколько агентов помогают \{#when-several-agents-help\}

**Параллельное исследование.** Задачи, которые скорее широки, чем глубоки, — охватить много источников, попробовать несколько подходов, проверить много кандидатов, — распадаются на независимые части. Цепочка последовательных вызовов тогда равна по длине одной части, а не всем им.

**Раздельные контексты.** Исполнитель читает двадцать страниц и возвращает два абзаца. Контекст оркестратора содержит абзацы, а не страницы: исполнители работают как шаг сжатия, и каждый контекст остаётся достаточно коротким, чтобы модель хорошо им пользовалась. Рецензент в чистом контексте, который не видел рассуждений, породивших работу, тоже судит о ней независимее, чем агент, который её написал.

**Разнообразие.** Агенты с разными промптами, инструментами или моделями делают разные ошибки. Когда ошибки независимы, сравнение или голосование их гасит, что количественно описывает последний раздел.

Арифметика стоимости из раздела «Код» делает этот обмен конкретным. Каждый вызов модели читает весь свой контекст, инструкции и определения инструментов занимают 3000 токенов, а каждый документ — 600:

| документов | один агент: прочитано токенов | самый длинный контекст | вызовов подряд | несколько агентов: прочитано токенов | самый длинный контекст | вызовов подряд |
| --- | --- | --- | --- | --- | --- | --- |
| 6 | 34 790 | 6890 | 7 | 47 260 | 3700 | 4 |
| 30 | 392 150 | 22 250 | 31 | 211 900 | 6050 | 4 |

Для маленькой задачи мультиагентная архитектура читает больше токенов, потому что каждый исполнитель повторяет инструкции. Для большой — меньше, потому что один агент на каждом шаге перечитывает свой растущий контекст, и эта стоимость растёт как квадрат числа шагов ([арифметика цикла ReAct](/ru/notes/agents/react-and-the-agent-loop#the-cost-and-latency-of-a-loop)). В обоих случаях её контексты короче, а длина последовательной цепочки фиксирована. Настоящие системы тратят больше, чем предполагает эта игрушка, потому что их исполнители исследуют: Anthropic измерила, что агенты используют примерно в 4 раза больше токенов, чем чат, а её мультиагентная система — примерно в 15 раз больше, и что число использованных токенов объясняло 80% дисперсии качества на BrowseComp. Многое из того, что дают несколько агентов, — это возможность с пользой потратить больше вычислений.

## Когда несколько агентов вредят \{#when-several-agents-hurt\}

**Стоимость в токенах.** Пятнадцатикратный по сравнению с чатом расход токенов стоит заплатить за трудный исследовательский вопрос и расточителен для лёгкого. Мультиагентная архитектура должна окупать свою стоимость на тех задачах, для которых её используют.

**Ошибки при передаче.** Каждая передача (handoff) передаёт сводку, а сводка может потерять то, что было нужно получателю. В разделе «Код» небрежный исполнитель возвращает население города как *2*, потому что потерял слово *million*; если свести результаты без проверки, эта ошибка изменила бы ответ на другой город, и оркестратор уверенно сообщил бы его. Один агент, который сам прочитал документ, такой ошибки не сделал бы. Защита — та же, что в коде: результаты в структуре, которую можно проверить (число, единица измерения, источник), и проверка перед сведением.

**Сбои координации.** Анализ более 1600 размеченных трасс семи мультиагентных фреймворков на задачах по программированию, математике и общих задачах разделил неудачи на 14 видов в трёх категориях ([Cemri et al., 2025](#references)) с высоким согласием разметчиков (κ = 0.88):

- **проектирование системы и спецификация:** агенты игнорируют свою роль или ограничения задачи, повторяют шаги, теряют историю разговора или не знают, когда задача выполнена;
- **рассогласование между агентами:** агенты не просят уточнений, скрывают информацию, нужную другому агенту, игнорируют вклад друг друга или уходят от задачи, а то, что они говорят, не совпадает с тем, что они делают;
- **проверка задачи:** система останавливается слишком рано или проверяет неполно или неправильно.

Многие из этих сбоев не исправить лучшей моделью, потому что они происходят от структуры: поручений, в которых сказано недостаточно, результатов, в которых сказано слишком мало, и отсутствия того, кто отвечает за проверку. Довод Cognition против параллельных авторов кода говорит о том же из практики: каждое действие несёт решения, которые никто не высказал (имя, стиль, понимание задачи), и агенты, параллельно работающие над частями одного артефакта, принимают несовместимые решения ([Yan, 2025](#references)).

## Голосование, дебаты и коррелированные ошибки \{#voting-debate-and-correlated-errors\}

Голосование большинством (majority vote) — простейший способ объединить агентов, и у него есть классическое обоснование: если каждый из $n$ независимых голосующих прав с вероятностью $p > 1/2$, то большинство право с вероятностью, которая стремится к 1 с ростом $n$, — теорема Кондорсе о присяжных (Condorcet's jury theorem). Агенты на языковых моделях не независимы. Несколько экземпляров одной модели разделяют её обучающие данные и её слепые пятна, и даже разные модели разделяют бо́льшую часть своих данных. Насколько это важно?

**Модель общих ошибок.** Пусть общий переключатель решает для каждого вопроса, ошибаются агенты или правы вместе: с вероятностью $\rho$ все агенты дают один и тот же ответ, верный с вероятностью $p$; с вероятностью $1 - \rho$ они отвечают независимо, каждый прав с вероятностью $p$. Каждый агент по-прежнему прав с вероятностью $p$. Для двух агентов $i \ne j$

$$
\begin{aligned}
E[X_i X_j] &= \rho\, p + (1 - \rho)\, p^2 && \text{общий исход: оба правы с вероятностью } p\text{; независимо: } p \cdot p \\
\operatorname{Cov}(X_i, X_j) &= E[X_i X_j] - p^2 = \rho\,(p - p^2) = \rho\, p(1 - p) && \text{вычитаем } E[X_i]\,E[X_j] = p^2 \\
\operatorname{Corr}(X_i, X_j) &= \frac{\rho\, p(1 - p)}{p(1 - p)} = \rho && \text{каждая дисперсия равна } p(1 - p),
\end{aligned}
$$

так что $\rho$ — в точности корреляция правильности агентов. Когда агенты согласны из-за общего переключателя, большинство право с вероятностью $p$; когда они независимы — с вероятностью, равной хвосту биномиального распределения $B_n(p)$. По формуле полной вероятности

$$
\boxed{
\begin{aligned}
A_n &= \rho\, p + (1 - \rho)\, B_n(p), \\
B_n(p) &= \sum_{k > n/2} \binom{n}{k} p^k (1 - p)^{n - k}
\end{aligned}
}
$$

и поскольку $B_n(p) \to 1$ при $p > 1/2$, доля правильных ответов голосования никогда не превысит

$$
A_\infty = \rho\, p + 1 - \rho = 1 - \rho\,(1 - p).
$$

**Разобранный пример.** При $p = 0.7$ и $n = 5$ получаем $B_5 = 10 \cdot 0.7^3 \cdot 0.3^2 + 5 \cdot 0.7^4 \cdot 0.3 + 0.7^5 = 0.3087 + 0.3602 + 0.1681 = 0.837$. Независимые агенты ($\rho = 0$) поднимают долю правильных ответов с $0.70$ до $0.837$. При $\rho = 0.5$ имеем $A_5 = 0.5 \cdot 0.7 + 0.5 \cdot 0.837 = 0.768$, и никакое число агентов не позволит превзойти $1 - 0.5 \cdot 0.3 = 0.85$. Выигрыш по сравнению с одним агентом не больше $(1 - \rho)(1 - p)$: голосование может исправить только независимую часть ошибок.

<VoteAccuracy />

*Необязательное углубление: почему корреляция задаёт нижнюю границу в любой модели, а не только в этой. Остальная часть заметки от него не зависит.*

Для любых агентов с одинаковой вероятностью быть правым $p$ и попарной корреляцией $\rho$ доля правых агентов $\bar X = \frac1n \sum_i X_i$ имеет дисперсию

$$
\operatorname{Var}(\bar X) = \frac{1}{n^2}\Big(\sum_i \operatorname{Var}(X_i) + \sum_{i \ne j} \operatorname{Cov}(X_i, X_j)\Big) = \frac{n\, p(1-p) + n(n-1)\, \rho\, p(1-p)}{n^2} = p(1-p)\Big(\rho + \frac{1 - \rho}{n}\Big).
$$

С ростом $n$ дисперсия падает до $\rho\, p(1 - p)$, а не до 0. У независимых агентов доля правых концентрируется около $p$, и порог большинства $1/2$, лежащий ниже, почти никогда не пересекается. У коррелированных агентов доля сохраняет разброс, который не уменьшается, так что на некоторых вопросах большинство агентов ошибается вместе, сколько бы их ни было.

**Дебаты.** Помогает ли агентам разговор больше, чем голосование? В игрушечной модели из раздела «Код» пять агентов с $\rho = 0.2$, увидев ответы остальных, каждый с вероятностью одна вторая принимают ответ большинства. Доля правильных ответов отдельного агента растёт с $0.70$ до $0.75$, а доля правильных ответов большинства остаётся равной $0.81$: агенты чаще соглашаются, но не чаще правы. Свидетельства с настоящими моделями указывают в ту же сторону. Du et al. в 2023 году получили для дебатов результат выше, чем для голосования. Контролируемое исследование 2025 года разделило два компонента дебатов — ансамбль ответов и обмен сообщениями — на семи бенчмарках: одно лишь голосование большинством объяснило бо́льшую часть выигрыша, приписываемого дебатам ([Choi, Zhu and Li, 2025](#references)). Его анализ моделирует дебаты как процесс, ожидаемая правильность которого не меняется от раунда к раунду, если что-то не смещает обновления к правильному ответу: верификатор, инструмент или агент, который знает больше. Обмен мнениями их распространяет; точнее их делают только новая информация или проверка.

## Что изменилось \{#what-changed\}

| | один агент | несколько агентов |
| --- | --- | --- |
| контексты | один, со всем сразу | по одному на агента, у каждого своя часть |
| последовательность | все шаги по порядку | независимые части параллельно |
| токены | растут как квадрат числа шагов | инструкции повторяются для каждого агента; на настоящих задачах в сумме обычно больше |
| точки отказа | собственные ошибки модели | плюс передачи, поручения и координация |
| объединение ошибок | нет | голосование и ревью гасят независимые ошибки, но не общие |
| кто решает | агент | оркестратор, протокол или разговор |

## Ограничения \{#limitations\}

- **Выигрыш измеряют на выбранных задачах.** Сообщаемые улучшения получены на задачах, которые подходят для параллельной работы, например на широких исследованиях; задачи с тесно связанными частями, в том числе большинство изменений кода, выигрывают меньше или проигрывают.
- **Корреляция — норма.** Копии одной модели разделяют её слепые пятна, а разные модели — бо́льшую часть обучающих данных; независимая часть ошибок, которую может исправить голосование, часто мала.
- **Дебаты не только исправляют, но и убеждают.** Уверенный, но неправый агент может привести остальных к своему ответу; согласие после дебатов не свидетельствует о правильности.
- **Неудачи трудно приписать.** Найти в трассе многих агентов шаг и агента, на которых прогон пошёл не так, — само по себе открытая задача.
- **Пространство архитектур велико и мало изучено.** Топологии, поручения и правила сведения выбирают методом проб; таксономия сбоев есть, теории хороших архитектур нет.

## Что нужно запомнить \{#what-you-should-remember\}

- Классическая мультиагентная теория разделяет соревнование (минимакс), взаимодействие с ненулевой суммой (равновесия Нэша, при которых своекорыстные агенты могут вместе получить меньше, как в дилемме заключённого) и сотрудничество (распределение задач, как в протоколе контрактной сети).
- Мультиагентные системы на языковых моделях используют ролевую игру (CAMEL), фреймворки для диалога агентов (AutoGen), дебаты (Du et al.) и оркестраторы с субагентами; последние на практике используются чаще всего.
- Несколько агентов помогают за счёт параллельного исследования, раздельных контекстов, сжимающих прочитанное, и независимых ошибок. Вредят они стоимостью в токенах, ошибками при передаче и сбоями координации (MAST: 14 видов в трёх категориях).
- Голосование большинством при корреляции $\rho$: $A_n = \rho p + (1 - \rho) B_n(p)$ с потолком $1 - \rho(1 - p)$; дисперсия доли правых никогда не опускается ниже $\rho p(1 - p)$.
- Дебаты заставляют агентов соглашаться; точнее они их делают, только если что-то приносит новую информацию или проверку. Голосование большинством объясняет бо́льшую часть сообщаемого выигрыша от дебатов.
- Возвращайте результаты в проверяемых структурах и проверяйте их перед сведением; если части артефакта зависят друг от друга, поручайте запись одному агенту.

## Код \{#code\}

Оркестратор, который делит вопрос о шести городах между заскриптованными исполнителями, проверяет их структурированные результаты и запрашивает повторно, когда результат не проходит проверку; арифметика токенов одного агента против нескольких; голосование большинством с коррелированными ошибками, смоделированное и точное; и один раунд дебатов. Только NumPy и стандартная библиотека; начальные значения генератора фиксированы, а точные числа могут немного различаться на разных платформах и версиях библиотек. Скрипт работает меньше секунды.

Исполнители — регулярные выражения, а голосующие агенты — монеты с общим переключателем. Настоящие исполнители — агенты на языковых моделях, выполняющие циклы предыдущих заметок, а ошибки настоящих агентов коррелированы так, как не описывает ни одно значение $\rho$; структура «свести и проверить», арифметика токенов и граница того, что может исправить голосование, остаются теми же.

```python
import re
from math import comb
import numpy as np

# 1. задача, которая делится на части: в каком из шести (вымышленных) городов больше всего жителей? По документу на город.
DOCS = {
    'Arvel': 'Arvel, a river port, had 412,000 inhabitants in the last census.',
    'Brisk': 'The census counted 1.3 million people in Brisk and its suburbs.',
    'Corran': 'Corran is home to 2.1 million residents, the census reports.',
    'Dunmoor': 'Dunmoor has a population of 870,000 according to the census.',
    'Elsby': 'With 1,950,000 inhabitants, Elsby is the largest city of its province.',
    'Fenwick': 'Fenwick, a university town, has 95,000 inhabitants.',
}
def read(city): return DOCS[city]                  # инструмент, которым пользуется каждый агент: один документ, около 15 слов

def worker(city, careless=False):                 # заскриптованный исполнитель: читает свой документ, возвращает короткий структурированный результат
    text = read(city)
    m = re.search(r'(\d[\d,]*(?:\.\d+)?)( million)?', text)
    value = float(m.group(1).replace(',', '')) * (1e6 if m.group(2) and not careless else 1)
    return {'city': city, 'population': int(value), 'source': city}

def check(result):                                # оркестратор проверяет каждый результат перед сведением
    return result['population'] >= 1000 and result['source'] in DOCS

def orchestrator(cities, careless=()):
    results, log = [], []
    for c in cities:                               # исполнители независимы: они могли бы работать параллельно
        r = worker(c, careless=c in careless)
        if not check(r):
            log.append(f'rejected {r}; asked again')
            r = worker(c)
        results.append(r)
    best = max(results, key=lambda r: r['population'])
    return best, results, log

best, results, log = orchestrator(list(DOCS), careless={'Corran'})
print(*log, sep='\n')
print([(r['city'], r['population']) for r in results])
print('answer:', best['city'], best['population'], 'source:', best['source'])
# rejected {'city': 'Corran', 'population': 2, 'source': 'Corran'}; asked again
# [('Arvel', 412000), ('Brisk', 1300000), ('Corran', 2100000), ('Dunmoor', 870000), ('Elsby', 1950000), ('Fenwick', 95000)]
# answer: Corran 2100000 source: Corran
# (без проверки небрежный результат 2 попал бы в сводку, и ответом был бы Elsby: ошибка, возникшая при передаче)

# 2. во что это обходится: токены, прочитанные каждым вызовом модели (каждый вызов перечитывает весь свой контекст), и самая длинная цепочка вызовов
SYSTEM, TASK, DOC, NOTE, BRIEF = 3000, 50, 600, 40, 60  # размеры в токенах: инструкции и инструменты, задача, документ, заметка, поручение
def single_agent(n):                               # один контекст: читает все n документов, по вызову на документ
    ctx, total = SYSTEM + TASK, 0
    for _ in range(n):
        total += ctx; ctx += NOTE + DOC            # вызов пишет запрос к инструменту; документ добавляется в контекст
    total += ctx                                   # последний вызов, который отвечает
    return total, ctx, n + 1
def multi_agent(n):                                # оркестратор и n исполнителей со своими короткими контекстами
    plan = SYSTEM + TASK                           # оркестратор планирует и пишет n поручений
    w_ctx = SYSTEM + BRIEF                         # каждый исполнитель: один вызов, чтобы прочитать, и один, чтобы подытожить
    worker_total = w_ctx + (w_ctx + NOTE + DOC)
    merge = SYSTEM + TASK + n * BRIEF + n * NOTE   # оркестратор читает n компактных результатов
    return plan + n * worker_total + merge, max(w_ctx + NOTE + DOC, merge), 1 + 2 + 1
for n in (6, 30):
    print(n, 'single: total %d, longest context %d, calls in sequence %d' % single_agent(n),
          '| multi: total %d, longest context %d, calls in sequence %d' % multi_agent(n))
# 6 single: total 34790, longest context 6890, calls in sequence 7 | multi: total 47260, longest context 3700, calls in sequence 4
# 30 single: total 392150, longest context 22250, calls in sequence 31 | multi: total 211900, longest context 6050, calls in sequence 4

# 3. голосование большинством с коррелированными агентами: с вероятностью rho у всех агентов один общий исход (одно и то же слепое пятно)
def vote_exact(n, p, rho):
    independent = sum(comb(n, k) * p ** k * (1 - p) ** (n - k) for k in range(n // 2 + 1, n + 1))
    return rho * p + (1 - rho) * independent
def simulate(n, p, rho, trials, rng):
    shared = rng.random(trials) < rho             # вопросы, на которых агенты ошибаются (или правы) вместе
    common = rng.random(trials) < p
    own = rng.random((trials, n)) < p
    correct = np.where(shared[:, None], common[:, None], own)
    return correct
rng = np.random.default_rng(0)
p = 0.7
for rho in (0.0, 0.2, 0.5, 0.8):
    row = []
    for n in (1, 3, 5, 9, 25):
        c = simulate(n, p, rho, 200_000, rng)
        row.append(f'{(c.sum(1) > n / 2).mean():.3f}/{vote_exact(n, p, rho):.3f}')
    print(f'rho={rho}: ' + '  '.join(row) + f'   limit {1 - rho * (1 - p):.3f}')
# rho=0.0: 0.699/0.700  0.784/0.784  0.838/0.837  0.902/0.901  0.983/0.983   limit 1.000
# rho=0.2: 0.700/0.700  0.767/0.767  0.811/0.810  0.860/0.861  0.926/0.926   limit 0.940
# rho=0.5: 0.703/0.700  0.743/0.742  0.769/0.768  0.800/0.801  0.842/0.841   limit 0.850
# rho=0.8: 0.700/0.700  0.717/0.717  0.730/0.727  0.741/0.740  0.758/0.757   limit 0.760
print('pairwise correlation at rho=0.5:', round(np.corrcoef(simulate(2, p, 0.5, 200_000, rng).T)[0, 1], 3))
# pairwise correlation at rho=0.5: 0.497

# 4. раунд «дебатов»: каждый агент видит ответы остальных и с вероятностью 0.5 принимает ответ большинства
c = simulate(5, p, 0.2, 200_000, rng)
majority = c.sum(1, keepdims=True) > 2.5
switch = rng.random(c.shape) < 0.5
after = np.where(switch, majority, c)
print('individual accuracy %.3f -> %.3f; majority accuracy %.3f -> %.3f' %
      (c.mean(), after.mean(), majority.mean(), (after.sum(1) > 2.5).mean()))
# individual accuracy 0.699 -> 0.754; majority accuracy 0.808 -> 0.808
```
