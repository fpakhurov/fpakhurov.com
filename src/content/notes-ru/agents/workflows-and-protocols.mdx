Заметки этого раздела добавили к циклу агента память, планирование и самокоррекцию. Каждое из этого можно построить двумя способами. Свободный агент во время работы сам решает, когда извлекать, когда планировать и когда проверять; фиксированный **рабочий процесс** (workflow) делает то же самое в точках, выбранных программистом. [Предыдущая заметка](/ru/notes/agents/reflection-and-self-correction) закончилась как раз таким фиксированным устройством — генератором и верификатором в цикле. Эта заметка собирает повторяющиеся устройства, говорит, когда фиксированный рабочий процесс — лучшее решение, в общих чертах описывает, что дают фреймворки для агентов, а затем переходит к технической обвязке, которая лежит под всеми ними: как модель добирается до своих инструментов. [Заметка об использовании инструментов](/ru/notes/agents/tool-use-and-function-calling) описала отдельный вызов функции; Model Context Protocol стандартизирует то, как приложение обнаруживает и вызывает инструменты, которые живут в других программах, и в 2026 году этот протокол существенно изменился.

**Обозначения.** Шаг успешен с вероятностью $s$; в цепочке $k$ шагов. Маршрутизатор отправляет запрос нужному обработчику с вероятностью $\rho$. Обработчики успешны с вероятностью $h$ на предназначенных им запросах и $h'$ на прочих. Голосование проводится среди $m$ независимых сэмплов по ответам, каждый из которых верен с вероятностью $p$.

## Отправная точка: один агент со всеми инструментами \{#baseline-one-agent-with-every-tool\}

Самое общее устройство даёт одной модели все инструменты и все инструкции и позволяет ей работать в цикле, пока она не остановится. В принципе оно справляется с чем угодно. На практике за свою общность оно платит четырьмя способами, и все они встречались в предыдущих заметках: каждый шаг заново читает контекст, включающий схему каждого инструмента; ошибки накапливаются на шагах, которые ничто не проверяет; поведение меняется от запуска к запуску, так что сбои трудно воспроизвести; а стоимость задачи без бюджетов ничем не ограничена. [Курс NLP](/ru/notes/nlp/tools-and-agents#when-an-agent-is-unnecessary) дал соответствующее эмпирическое правило: начинать с конвейера и переносить решение в модель, только когда фиксированная логика измеримо становится узким местом. Эта заметка уточняет это правило.

<aside class="callout"><strong>Ключевая идея.</strong> Большинство систем на языковых моделях — это небольшое число вызовов модели, которые расставлены обычным кодом: соединены в цепочку с проверками между ними, распределены классификатором, запущены параллельно с агрегацией, делегированы оркестратором или замкнуты в цикл с оценщиком. Использовать стоит простейшее устройство, которое измеримо работает, а выбор шагов оставлять модели, только когда шаги нельзя знать заранее. Модели следует подключать к инструментам через протокол, чтобы инструмент писался один раз и им могло пользоваться любое приложение.</aside>

## Строительный блок и пять рабочих процессов \{#the-building-block-and-five-workflows\}

Таксономия [Anthropic (2024)](#references) начинается с одного строительного блока — **дополненной LLM** (augmented LLM): модели с извлечением, инструментами и памятью, которая может сама писать запросы, выбирать инструменты и решать, что сохранить. Рабочие процессы расставляют несколько таких вызовов по путям, записанным в коде; **агент** позволяет модели самой направлять свой процесс.

<WorkflowPatterns />

**Цепочка промптов** (prompt chaining). Задача делится на фиксированную последовательность вызовов, каждый из которых потребляет выход предыдущего: набросать план документа, сверить его с требованиями, написать документ по плану. Между шагами стоят **фильтры** (gates) — программные проверки, которые останавливают или повторяют плохой промежуточный результат. Без фильтров цепочка из $k$ шагов успешна с вероятностью $s^k$; с фильтром, который ловит долю $g$ сбоев и допускает один повтор, шаг успешен с вероятностью $s + (1 - s) g s$. При $s = 0.9$, $k = 4$ и $g = 0.8$ это $0.9^4 = 0.656$ без фильтров против $0.972^4 = 0.893$ с ними. Цепочка меняет задержку на точность: каждый вызов выполняет более лёгкую работу.

**Маршрутизация** (routing). Классификатор, часто небольшая модель, отправляет каждый вход специализированному обработчику: возвраты денег — одному промпту с набором инструментов, технические вопросы — другому, всё остальное — человеку. Маршрутизация окупается, когда классам нужна разная обработка, а классификатор надёжен. Общий успех равен $\rho h + (1 - \rho) h'$. Если специалисты успешны с $h = 0.9$ на своих запросах и с $h' = 0.3$ на неверно направленных, маршрутизация лучше одного универсального промпта, успешного с вероятностью 0.8, только если $0.9\rho + 0.3(1 - \rho) > 0.8$, то есть $\rho > 5/6 \approx 0.83$: точность маршрутизатора — первое, что нужно измерить.

**Параллелизация** (parallelization). Независимые вызовы выполняются одновременно. При **разбиении на части** (sectioning) задача делится на независимые части (проверить пункты договора по отдельности или проверить ответ на безопасность, пока другой вызов отвечает), и задержка равна задержке самой медленной части, а не сумме. При **голосовании** (voting) одна и та же задача выполняется несколько раз, и ответы агрегируются, — это самосогласованность из заметки [Цепочка рассуждений](/ru/notes/agents/chain-of-thought#self-consistency-vote-over-reasoning-paths): при трёх независимых голосах, каждый из которых верен с вероятностью $p = 0.7$, большинство верно с вероятностью $p^3 + 3p^2(1 - p) = 0.784$. Голоса одной модели коррелированы, так что реальный выигрыш меньше.

**Оркестратор и исполнители** (orchestrator-workers). Центральная модель разбивает задачу на подзадачи, которые нельзя было перечислить заранее, передаёт каждую вызову-исполнителю и объединяет результаты: изменение кода, затрагивающее неизвестное число файлов, поиск по источникам, которые зависят от вопроса. Это похоже на параллелизацию, но подзадачи определяются во время работы. Этот шаблон — мост к заметке [Мультиагентные системы](/ru/notes/agents/multi-agent-systems).

**Оценщик–оптимизатор** (evaluator-optimizer). Один вызов порождает, другой оценивает и возвращает замечания, и цикл повторяется, пока оценщик не примет результат. Предыдущая заметка вычислила его потолок: цикл хорош настолько, насколько низка доля ложноположительных у оценщика. Он подходит, когда критерии ясны, а критика измеримо улучшает следующий черновик, как при переводе с рецензентом или при написании кода с тестами.

**Автономные агенты.** Модель выбирает шаги, вызывает инструменты в цикле, читает обратную связь от среды и останавливается сама или по исчерпании бюджета — цикл из заметки [ReAct и цикл агента](/ru/notes/agents/react-and-the-agent-loop). Он подходит для открытых задач, где число и порядок шагов нельзя предсказать, и ему нужны меры защиты из предыдущих заметок: песочницы, бюджеты, подтверждение перед побочными эффектами и тесты на многих запусках.

### Когда фиксированный рабочий процесс лучше \{#when-a-fixed-workflow-is-the-better-design\}

Список решений, от самого дешёвого устройства к самому дорогому:

1. Если задачу решает один вызов с хорошим извлечением и примерами, на этом и остановиться.
2. Если шаги известны заранее, записать их как цепочку, с фильтрами там, где возможна проверка.
3. Если входы делятся на классы, которым нужна разная обработка, и маршрутизатор можно сделать точным, маршрутизировать.
4. Если части независимы, запускать их параллельно; если один ответ ненадёжен, а ответы можно сравнить, голосовать.
5. Если результат можно проверить и улучшить критикой, добавить цикл с оценщиком.
6. Только если шаги зависят от того, что выяснили предыдущие шаги, а неверный шаг можно обнаружить или отменить, давать модели их выбирать: оркестратор — для декомпозиции, агент — для открытой работы.

Каждый шаг вниз по списку покупает гибкость ценой токенов, задержки и предсказуемости. Заметка [Оценка агентов](/ru/notes/agents/evaluating-agents) даёт измерения, которые оправдывают такой шаг. Устройство, сочетающее шаблоны, — норма: маршрутизатор перед несколькими цепочками, одна из которых — агент с оценщиком.

## Фреймворки \{#frameworks\}

Фреймворки для агентов упаковывают общую для этих шаблонов техническую обвязку. Важны два семейства, и оба быстро меняются; даты здесь — даты первых публичных выпусков.

- **Библиотеки оркестрации на графах**, например LangGraph (первый выпуск в январе 2024 года), описывают приложение как **граф состояний** (state graph): типизированное состояние (сообщения плюс поля приложения), узлы — функции из состояния в обновление, рёбра, которые могут зависеть от состояния, и **механизм контрольных точек** (checkpointer), который сохраняет состояние после каждого шага под идентификатором потока (thread). [Курс NLP](/ru/notes/nlp/tools-and-agents#where-the-memory-of-a-conversation-lives) так строил память диалога. Цепочки, маршрутизаторы и циклы с оценщиком прямо ложатся на узлы и рёбра; агент — это узел, вызывающий модель, и ребро, которое возвращается назад, пока остаются вызовы инструментов.
- **SDK для агентов от провайдеров моделей** упаковывают сам цикл агента: модель с инструкциями и инструментами, исполнитель (runner), который выполняет вызовы инструментов и возвращает результаты, передачу управления между агентами (hand-offs), ограничители (guardrails), проверяющие входы и выходы, и трассировку (tracing). Agents SDK от OpenAI появился в марте 2025 года, Agent Development Kit от Google — в апреле 2025 года, а Claude Agent SDK от Anthropic под этим названием — в сентябре 2025 года, как переименование Claude Code SDK.

Вопросы к любому фреймворку одни и те же: можно ли увидеть и записать в журнал каждый промпт и каждый ответ модели; сохраняется ли состояние так, чтобы запуск можно было возобновить или воспроизвести; может ли человек прервать цикл и одобрить действие; и уходит ли фреймворк с дороги, когда шаг лучше написать обычным кодом. Anthropic советует начинать с прямых вызовов API модели и переходить на фреймворк, только понимая код под ним ([Anthropic, 2024](#references)), потому что абстракция, которая прячет промпт, прячет и ошибку.

## Model Context Protocol \{#the-model-context-protocol\}

Каждое приложение, которое хочет, чтобы модель пользовалась инструментом, должно описать инструмент, вызвать его и вернуть результат. Без стандарта $M$ приложениям и $N$ инструментам нужно до $M \times N$ интеграций; со стандартом — $M + N$. **Model Context Protocol** (MCP), выпущенный Anthropic в ноябре 2024 года и переданный в декабре 2025 года фонду Agentic AI Foundation при Linux Foundation, и есть такой стандарт. Его устройство заимствовано у Language Server Protocol, который сделал то же самое для языков программирования и редакторов. Описание ниже следует ревизии спецификации `2026-07-28`, актуальной в октябре 2026 года ([MCP specification](#references)).

**Роли.** **Хост** (host) — приложение, которое запускает пользователь (чат-приложение, IDE, агент для программирования); ему принадлежат модель, диалог и согласие пользователя. Хост создаёт по одному **клиенту** (client) на каждый подключённый сервер, и каждый клиент говорит ровно с одним **сервером** (server) — программой, которая предоставляет возможности и работает локально как подпроцесс или удалённо по URL. Один из принципов устройства спецификации: серверы не видят ни всего диалога, ни друг друга; хост решает, что получает каждый сервер.

**Возможности сервера.** Серверы предлагают три вида вещей:

- **инструменты** (tools) — функции, которые вызывает модель, у каждой из которых есть имя, описание и JSON Schema для входа (и, необязательно, для выхода); они обнаруживаются через `tools/list` и вызываются через `tools/call`;
- **ресурсы** (resources) — данные, адресуемые URI (файл, строка базы данных, ответ API), которые читает приложение или модель; их перечисляют через `resources/list` и получают через `resources/read`;
- **промпты** (prompts) — шаблонные сообщения и рабочие процессы, предлагаемые пользователю, например команда «проверить этот pull request».

С другой стороны, серверы могут попросить клиента получить ввод от пользователя (**elicitation**). Две старые возможности клиента — позволить серверу запросить генерацию у модели хоста (sampling) и сообщить серверу, какими каталогами он может пользоваться (roots), — в ревизии 2026 года объявлены устаревшими.

**Сообщения.** Все сообщения — JSON-RPC 2.0: **запросы** (requests) с методом, параметрами и `id`, который не может быть null; **ответы** (responses) с тем же `id` и либо `result`, либо `error`; и **уведомления** (notifications), у которых нет `id` и на которые не отвечают. Вызов инструмента и его результат в сокращённом виде из того, что печатает раздел «Код»:

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "get_order", "arguments": {"order_id": "A-1001"},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
{"jsonrpc": "2.0", "id": 3,
 "result": {"resultType": "complete", "isError": false,
            "content": [{"type": "text", "text": "{\"total\": 40.0, \"status\": \"delivered\"}"}],
            "structuredContent": {"total": 40.0, "status": "delivered"}}}
```

Ошибки бывают двух видов, и для агентов это различие важно. **Ошибка протокола** (protocol error), например неизвестный инструмент или некорректный запрос, — это JSON-RPC `error` для клиента. **Ошибка выполнения инструмента** (tool execution error), например аргумент вне допустимого диапазона или неудачный вызов API, — это обычный результат с `isError: true` и сообщением в `content`, предназначенный модели, которая может прочитать его и повторить вызов с исправленными аргументами, как в заметке [Использование инструментов и вызов функций](/ru/notes/agents/tool-use-and-function-calling#errors-and-retries): это внешняя обратная связь из предыдущей заметки.

**Один обмен, шаг за шагом:**

<McpExchange />

1. **Обнаружение.** Клиент может вызвать `server/discover`, чтобы узнать версии протокола, возможности и инструкции сервера.
2. **Список.** `tools/list` возвращает инструменты с их схемами в детерминированном порядке, чтобы хост мог их кэшировать и кэш промпта модели оставался тёплым ([Контекст и память](/ru/notes/agents/context-and-memory#prompt-caching-as-economics)).
3. **Показ.** Хост помещает описания инструментов в контекст модели.
4. **Решение.** Модель выдаёт вызов инструмента. Хост сверяет его с согласием пользователя: спецификация требует явного согласия перед вызовом любого инструмента и говорит, что человек должен иметь возможность отклонить каждый вызов.
5. **Вызов.** Клиент отправляет `tools/call` с аргументами и метаданными запроса; сервер проверяет аргументы по схеме, запускает инструмент и возвращает `content`, необязательно `structuredContent`, и `isError`.
6. **Наблюдение.** Хост добавляет результат в контекст модели как наблюдение, и цикл продолжается.

**Транспорты.** Стандартных два. При **stdio** клиент запускает сервер как подпроцесс, и они обмениваются сообщениями JSON-RPC по одному на строку через стандартные ввод и вывод; сервер может писать журнал в стандартный поток ошибок. При **Streamable HTTP** сервер — веб-сервис, и каждый запрос — это HTTP POST, ответом на который служит либо тело JSON, либо поток событий, отправляемых сервером (server-sent events, SSE); HTTP-серверы используют авторизацию протокола на основе OAuth. Прежний транспорт HTTP с SSE объявлен устаревшим.

**Ревизии.** Протокол датируется по ревизиям, и агенты одновременно встречают серверы нескольких ревизий:

| ревизия | основные изменения |
| --- | --- |
| `2024-11-05` | первая публичная версия: рукопожатие `initialize`, согласующее версию и возможности, затем сессия с состоянием; инструменты, ресурсы, промпты, sampling; stdio и HTTP с событиями, отправляемыми сервером |
| `2025-03-26` | авторизация OAuth 2.1; Streamable HTTP заменяет HTTP с SSE; аннотации инструментов, например «только чтение» или «разрушающий» |
| `2025-06-18` | структурированный выход инструментов; elicitation; ссылки на ресурсы в результатах инструментов; пакетная обработка JSON-RPC удалена |
| `2025-11-25` | экспериментальные задачи (tasks) для долгих запросов; elicitation в режиме URL; вызов инструментов внутри sampling |
| `2026-07-28` | без состояния: нет рукопожатия и нет сессий протокола; каждый запрос несёт свою версию и возможности клиента в `_meta`; `server/discover`; у каждого результата есть `resultType`; sampling, roots и журналирование объявлены устаревшими; задачи перенесены в расширение |

Изменение 2026 года — то, которое нужно понять. Прежние ревизии начинали каждое соединение с `initialize`, после чего сервер мог хранить состояние сессии. В ревизии без состояния (stateless) каждый запрос самодостаточен, что позволяет удалённому серверу работать за обычными балансировщиками нагрузки, а состояние, которое должно охватывать несколько вызовов (корзина покупок, открытый браузер), хранит сервер под явным дескриптором (handle), который модель передаёт обратно как обычный аргумент инструмента. Клиенты, которым нужно говорить с серверами обоих видов, пробуют `server/discover` и возвращаются к `initialize`, если сервер его не понимает.

**Безопасность.** Протокол, который позволяет любой программе предлагать модели инструменты, расширяет поверхность атаки. Описания и аннотации инструментов приходят от сервера, и считать их доверенными можно, только если доверенным является сервер: описание может содержать инструкции, нацеленные на модель. Результаты инструментов — данные, а не инструкции. Спецификация возлагает согласие и авторизацию на хост, а не на протокол, который не может их обеспечить. Эти атаки и защиту от них разбирает заметка [Безопасность агентов и инъекции в промпт](/ru/notes/agents/agent-security).

### Agent2Agent \{#agent2agent\}

MCP связывает агента с инструментами. **Agent2Agent** (A2A), анонсированный Google в апреле 2025 года и переданный Linux Foundation в июне 2025 года, связывает агентов друг с другом, когда ни один из них не является инструментом другого, например агентов, созданных разными организациями. Агент публикует **Agent Card** — документ JSON по известному URL, который описывает его навыки, конечную точку и аутентификацию; другой агент отправляет ему **задачу** (task) и следит за её состояниями до получения результата. Он тоже использует JSON-RPC поверх HTTP. На октябрь 2026 года MCP развёрнут гораздо шире; к агентам, которые разговаривают с агентами, возвращается заметка [Мультиагентные системы](/ru/notes/agents/multi-agent-systems).

## Что изменилось \{#what-changed\}

| | один агент со всеми инструментами | составленные рабочие процессы поверх протокола |
| --- | --- | --- |
| кто выбирает следующий шаг | всегда модель | код, кроме мест, где шаги нельзя знать заранее |
| проверки между шагами | нет, если модель о них не попросит | фильтры, маршрутизаторы, оценщики |
| стоимость и задержка | без бюджетов не ограничены | заданы устройством, параллельно, где возможно |
| воспроизводимость | низкая | высокая для фиксированных частей |
| как подключаются инструменты | свой код в каждом приложении | один сервер на инструмент, им может пользоваться любой хост |
| вызовы инструментов на линии | частный формат приложения | JSON-RPC: `tools/list`, `tools/call`, результаты с `isError` |

## Ограничения \{#limitations\}

- **Таксономия — словарь, а не теория.** Шаблоны пришли из практики; реальные системы их смешивают, и выбор между ними — эмпирический вопрос, на который отвечает оценка на собственной задаче.
- **Рабочие процессы хрупки на краях.** У маршрутизатора нет маршрута для входа, которого никто не предвидел, а цепочка не может оправиться от сбоя, который её фильтры не обнаруживают.
- **Фреймворки и протоколы быстро меняются.** Перечисленные SDK меняли интерфейсы в течение месяцев после выпуска, а у MCP было пять ревизий меньше чем за два года, последняя из которых убрала рукопожатие; код, написанный под одну ревизию, может не договориться с сервером другой.
- **Протокол не делает инструмент безопасным.** MCP стандартизирует то, как инструменты описываются и вызываются, но не то, честно ли описание и разумен ли вызов; согласие, песочница и минимальные привилегии остаются заботой хоста.
- **Взаимодействие между агентами только складывается.** За A2A и похожими протоколами на 2026 год стоит мало свидетельств реального развёртывания.

## Что нужно запомнить \{#what-you-should-remember\}

- Дополненная LLM (модель с извлечением, инструментами и памятью) — строительный блок; рабочие процессы расставляют вызовы в коде, агенты дают модели выбирать.
- Пять рабочих процессов: цепочка промптов с фильтрами, маршрутизация, параллелизация разбиением на части или голосованием, оркестратор и исполнители и оценщик–оптимизатор. Их арифметика проста: цепочки перемножают успехи шагов, фильтры их повышают, маршрутизация окупается, только когда маршрутизатор достаточно точен, голосование выигрывает меньше, чем обещает независимость.
- Использовать простейшее устройство, которое измеримо работает; переносить решение в модель, только когда оно зависит от того, что выяснили предыдущие шаги.
- Фреймворки дают графы состояний с контрольными точками или упакованный цикл агента с инструментами, передачей управления, ограничителями и трассировкой; выбирать стоит тот, чьи промпты и состояние видны.
- MCP связывает хосты с серверами инструментов: один клиент на сервер, инструменты, ресурсы и промпты, запросы и результаты JSON-RPC, ошибки протокола для клиента и ошибки выполнения инструмента для модели, stdio и Streamable HTTP. Начиная с ревизии `2026-07-28` он не хранит состояния, с метаданными в каждом запросе и `server/discover`. A2A связывает агентов с агентами.

## Код \{#code\}

Сервер инструментов и клиент в одном процессе, которые говорят на JSON-RPC 2.0 с именами методов, метаданными и формой результатов ревизии MCP `2026-07-28`, минимальная проверка аргументов инструмента по JSON Schema, два вида ошибок и рабочий процесс маршрутизации, в котором маршрут возврата денег — короткая цепочка с фильтром и шагом подтверждения. Классификатор и шаг извлечения — заскриптованные замены (правила по ключевым словам и регулярное выражение); с настоящей моделью каждый из них был бы одним вызовом со структурированным выходом, а сервер, клиент, формат на линии и рабочий процесс остались бы прежними. Настоящий хост к тому же запускал бы сервер как подпроцесс через stdio или обращался бы к нему по HTTP, а не вызывал бы его в том же процессе. Только стандартная библиотека; скрипт работает мгновенно и не использует случайности.

```python
import json, re

VERSION = '2026-07-28'

# 1. минимальная проверка по JSON Schema: подмножество, которое обычно нужно схемам инструментов
def validate(value, schema, path='arguments'):
    t = schema.get('type')
    kinds = {'object': dict, 'string': str, 'number': (int, float), 'integer': int, 'boolean': bool}
    if t and not isinstance(value, kinds[t]) or (t in ('number', 'integer') and isinstance(value, bool)):
        return f'{path}: expected {t}'
    if t == 'object':
        for k in schema.get('required', []):
            if k not in value: return f'{path}: missing required property "{k}"'
        props = schema.get('properties', {})
        if schema.get('additionalProperties') is False:
            extra = sorted(set(value) - set(props))
            if extra: return f'{path}: unexpected property "{extra[0]}"'
        for k, sub in props.items():
            if k in value:
                err = validate(value[k], sub, f'{path}.{k}')
                if err: return err
    if 'minimum' in schema and value < schema['minimum']: return f'{path}: must be at least {schema["minimum"]}'
    if 'pattern' in schema and not re.fullmatch(schema['pattern'], value): return f'{path}: does not match {schema["pattern"]}'
    return None

# 2. сервер инструментов: JSON-RPC 2.0 поверх JSON с разделением по строкам, без состояния, с именами методов 2026-07-28
ORDERS = {'A-1001': {'total': 40.0, 'status': 'delivered'}, 'A-1002': {'total': 15.5, 'status': 'in transit'}}
DOCS = {'returns': 'Items can be returned within 30 days of delivery.', 'shipping': 'Standard shipping takes 3 to 5 days.'}
TOOLS = [
    {'name': 'get_order', 'description': 'Look up an order by its id.',
     'inputSchema': {'type': 'object', 'properties': {'order_id': {'type': 'string', 'pattern': r'A-\d{4}'}},
                     'required': ['order_id'], 'additionalProperties': False}},
    {'name': 'refund', 'description': 'Refund part or all of an order. Side effect: moves money.',
     'inputSchema': {'type': 'object', 'properties': {'order_id': {'type': 'string', 'pattern': r'A-\d{4}'},
                                                      'amount': {'type': 'number', 'minimum': 0}},
                     'required': ['order_id', 'amount'], 'additionalProperties': False},
     'annotations': {'destructiveHint': True}},
    {'name': 'search_docs', 'description': 'Search the help pages.',
     'inputSchema': {'type': 'object', 'properties': {'query': {'type': 'string'}}, 'required': ['query']}},
]

class ToolServer:
    def handle_line(self, line):                                 # один запрос на входе, один ответ на выходе
        req = json.loads(line)
        rid, method, params = req.get('id'), req.get('method'), req.get('params', {})
        def error(code, message, data=None):
            e = {'code': code, 'message': message} | ({'data': data} if data else {})
            return json.dumps({'jsonrpc': '2.0', 'id': rid, 'error': e})
        def result(body):
            body = {'resultType': 'complete'} | body | {'_meta': {'io.modelcontextprotocol/serverInfo': {'name': 'shop', 'version': '0.1'}}}
            return json.dumps({'jsonrpc': '2.0', 'id': rid, 'result': body})
        meta = params.get('_meta', {})
        if 'io.modelcontextprotocol/protocolVersion' not in meta or 'io.modelcontextprotocol/clientCapabilities' not in meta:
            return error(-32602, 'Invalid params: missing required _meta fields')
        if meta['io.modelcontextprotocol/protocolVersion'] != VERSION:
            return error(-32022, 'Unsupported protocol version',
                         {'supported': [VERSION], 'requested': meta['io.modelcontextprotocol/protocolVersion']})
        if method == 'server/discover':
            return result({'supportedVersions': [VERSION], 'capabilities': {'tools': {}}})
        if method == 'tools/list':
            return result({'tools': TOOLS})
        if method == 'tools/call':
            tool = next((t for t in TOOLS if t['name'] == params.get('name')), None)
            if tool is None: return error(-32602, f'Unknown tool: {params.get("name")}')
            args = params.get('arguments', {})
            err = validate(args, tool['inputSchema'])
            if err:                                              # ошибка выполнения инструмента: модель может исправить аргументы
                return result({'content': [{'type': 'text', 'text': err}], 'isError': True})
            out = self.run(tool['name'], args)
            return result({'content': [{'type': 'text', 'text': json.dumps(out)}], 'structuredContent': out, 'isError': 'error' in out})
        return error(-32601, f'Method not found: {method}')
    def run(self, name, args):
        if name == 'get_order': return ORDERS.get(args['order_id'], {'error': 'no such order'})
        if name == 'refund':
            o = ORDERS.get(args['order_id'])
            if o is None or args['amount'] > o['total']: return {'error': 'refund exceeds the order total'}
            return {'refunded': args['amount'], 'order_id': args['order_id']}
        if name == 'search_docs':
            hits = [v for k, v in DOCS.items() if k[:5] in args['query'].lower()]
            return {'results': hits}

# 3. клиент: по одному на сервер; к каждому запросу он прикладывает версию протокола и свои возможности
class Client:
    def __init__(self, server, version=VERSION):
        self.server, self.version, self.next_id, self.wire = server, version, 0, []
    def request(self, method, **params):
        self.next_id += 1
        params['_meta'] = {'io.modelcontextprotocol/protocolVersion': self.version,
                           'io.modelcontextprotocol/clientCapabilities': {},
                           'io.modelcontextprotocol/clientInfo': {'name': 'demo-host', 'version': '0.1'}}
        line = json.dumps({'jsonrpc': '2.0', 'id': self.next_id, 'method': method, 'params': params})
        assert '\n' not in line                                  # кадрирование stdio: одно сообщение на строку
        reply = self.server.handle_line(line)
        self.wire += [line, reply]
        return json.loads(reply)
    def call(self, name, **arguments):
        return self.request('tools/call', name=name, arguments=arguments)['result']

server = ToolServer()
client = Client(server)
print(client.request('server/discover')['result']['supportedVersions'])        # ['2026-07-28']
print([t['name'] for t in client.request('tools/list')['result']['tools']])      # ['get_order', 'refund', 'search_docs']
r = client.call('get_order', order_id='A-1001')
print(client.wire[-2]); print(client.wire[-1])                 # две строки на линии
# {"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "get_order", "arguments": {"order_id": "A-1001"}, "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}, "io.modelcontextprotocol/clientInfo": {"name": "demo-host", "version": "0.1"}}}}
# {"jsonrpc": "2.0", "id": 3, "result": {"resultType": "complete", "content": [{"type": "text", "text": "{\"total\": 40.0, \"status\": \"delivered\"}"}], "structuredContent": {"total": 40.0, "status": "delivered"}, "isError": false, "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "shop", "version": "0.1"}}}}
print(client.call('refund', order_id='A-1001', amount=-5)['content'])          # ошибка выполнения инструмента — для модели
# [{'type': 'text', 'text': 'arguments.amount: must be at least 0'}]
print(Client(server, version='2025-11-25').request('tools/list')['error'])     # ошибки протокола — для клиента
# {'code': -32022, 'message': 'Unsupported protocol version', 'data': {'supported': ['2026-07-28'], 'requested': '2025-11-25'}}
print(client.request('tools/call', name='delete_everything', arguments={})['error'])
# {'code': -32602, 'message': 'Unknown tool: delete_everything'}

# 4. рабочий процесс маршрутизации: заскриптованный классификатор выбирает маршрут; каждый маршрут — фиксированная цепочка шагов с фильтром
def classify(message):                                           # замена одного вызова небольшой модели
    m = message.lower()
    if 'refund' in m or 'money back' in m: return 'refund'
    if '?' in m: return 'question'
    return 'other'

def refund_route(message, approve):
    calls = 1                                                    # классификатор
    oid = re.search(r'A-\d{4}', message)
    amount = re.search(r'(\d+(?:\.\d+)?) ?(?:dollars|usd|\$)', message.lower())
    calls += 1                                                   # извлечение: один вызов модели со схемой
    if not oid: return 'ask the user for the order id', calls
    order = client.call('get_order', order_id=oid.group())['structuredContent']
    amt = float(amount.group(1)) if amount else order.get('total', 0.0)
    if 'error' in order or amt > order['total']:                 # фильтр: программная проверка между шагами
        return 'escalate to a person: the request does not match the order', calls
    if not approve(oid.group(), amt):                            # человек подтверждает каждый побочный эффект
        return 'refund declined by the reviewer', calls
    out = client.call('refund', order_id=oid.group(), amount=amt)['structuredContent']
    return f'refunded {out["refunded"]} on {out["order_id"]}', calls

def question_route(message):
    hits = client.call('search_docs', query=message)['structuredContent']['results']
    return (hits[0] if hits else 'no answer in the help pages; escalate'), 2   # классификатор + ответ

def workflow(message, approve=lambda oid, amt: amt <= 50):
    route = classify(message)
    if route == 'refund': return route, *refund_route(message, approve)
    if route == 'question': return route, *question_route(message)
    return route, 'hand over to a person', 1

for msg in ['I want a refund of 12 dollars for A-1001', 'Please refund A-1002, 99 dollars',
            'How long does shipping take?', 'What is your returns policy?', 'You are great']:
    print(workflow(msg))
# ('refund', 'refunded 12.0 on A-1001', 2)
# ('refund', 'escalate to a person: the request does not match the order', 2)
# ('question', 'Standard shipping takes 3 to 5 days.', 2)
# ('question', 'Items can be returned within 30 days of delivery.', 2)
# ('other', 'hand over to a person', 1)
print(len(client.wire) // 2, 'requests on the wire')               # 10 requests on the wire
```

Каждый маршрут использует не больше двух вызовов модели и двух вызовов инструментов, а возврат, превышающий сумму заказа, никогда не доходит до инструмента возврата: фильтр останавливает его в коде. Агент с теми же инструментами смог бы обработать запросы, которых не предвидел ни один маршрут, но ценой неограниченного числа вызовов и решения о возврате, которое сделать безопасным могла бы только проверка вроде этого фильтра.
