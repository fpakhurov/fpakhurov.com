[Предыдущая заметка](/ru/notes/acos/processes-and-threads) дала программе несколько потоков в одном адресном пространстве, и её пример был правильным только потому, что потоки выполнялись один за другим. Потоки существуют, чтобы выполняться одновременно, на разных ядрах или вперемешку на одном, и тогда порядок их обращений к памяти определяют планировщик, кэши и компилятор. Эта заметка показывает, как ломается даже такое простое обновление, как `counter++`, когда его одновременно выполняют два потока, объясняет сбой на уровне команд и строит инструменты, которые его предотвращают: атомарные команды, блокировки, условные переменные и семафоры. Она заканчивается взаимной блокировкой — сбоем, который блокировки приносят с собой, — и коротким взглядом на упорядочение обращений к памяти.

## Отправная точка: общий счётчик без защиты \{#baseline-a-shared-counter-with-no-protection\}

Два потока выполняют каждый по миллиону раз `counter++` над общей переменной `long counter = 0`. Программа должна напечатать 2 000 000. При компиляции `clang -O0` на Apple M1 (macOS 26) шесть запусков напечатали от 1 002 319 до 1 008 633, каждый раз другое число (раздел «Код»). Около половины приращений исчезло.

Причина в том, что `counter++` — не одна операция. В RISC-V она компилируется в три команды, и то же верно для любой архитектуры с раздельными загрузками и сохранениями (load–store):

```asm
        lw   t0, 0(a0)        # загрузка: t0 = counter
        addi t0, t0, 1        # сложение: t0 = t0 + 1
        sw   t0, 0(a0)        # сохранение: counter = t0
```

У каждого потока свои регистры, но слово памяти общее. Если оба потока загружают значение раньше, чем кто-то из них сохраняет, оба вычисляют одно и то же новое значение, и второе сохранение затирает первое:

<LostUpdate />

1. Поток A загружает 5 в свой регистр `t0`.
2. Поток B загружает 5 в свой регистр `t1`: A ещё не сохранил значение.
3. A прибавляет 1: `t0 = 6`.
4. B прибавляет 1: `t1 = 6`.
5. A сохраняет 6.
6. B сохраняет 6. Два приращения увеличили счётчик на единицу: обновление A потеряно.

Это **гонка** (race condition): результат зависит от того, как во времени выполняются потоки. Из 20 возможных чередований одного приращения в каждом потоке (выбираем, какие 3 из 6 шагов принадлежат A) только 2, в которых три шага одного потока целиком выполняются раньше шагов другого, дают 7; остальные 18 теряют обновление (раздел «Код» перебирает их все). На двух ядрах потоки действительно выполняются параллельно, каждая итерация занимает несколько наносекунд, и опасные окна постоянно перекрываются; поэтому из двух миллионов приращений потерялось так много.

Правильный на вид результат ничего не доказывает. Скомпилированная с `-O2`, та же программа с гонкой напечатала 2 000 000 в трёх запусках из трёх: оптимизатор превратил цикл каждого потока в одно прибавление 1 000 000, так что теперь потоки перекрываются редко, но ничто не мешает им это сделать. В C11 обращение двух потоков к одной неатомарной переменной без синхронизации, если хотя бы один из них пишет, — это **гонка данных** (data race), и поведение программы не определено ([ISO/IEC 9899:2018](#references), §5.1.2.4).

## Критические секции \{#critical-sections\}

**Критическая секция** (critical section) — участок кода, который обращается к общим данным и не должен выполняться в двух потоках одновременно; здесь это три команды `counter++`. Решение задачи критической секции должно гарантировать **взаимное исключение** (mutual exclusion: внутри одновременно не больше одного потока), **продвижение** (progress: если секция свободна и какие-то потоки хотят войти, один из них входит) и **ограниченное ожидание** (bounded waiting: поток, попросившийся войти, не обгоняют бесконечно) ([Arpaci-Dusseau, 2018](#references), глава 28).

На машине с одним ядром ядро операционной системы может сделать секцию атомарной, запретив прерывания: без прерывания таймера нет вытеснения, поэтому ничто другое не выполняется, пока прерывания снова не разрешат. Это привилегированная операция, бесполезная для пользовательских программ, а на многоядерной машине она ничего не останавливает: остальные ядра продолжают работать. Решения на одних обычных загрузках и сохранениях существуют (алгоритм Петерсона для двух потоков, алгоритм пекарни Лэмпорта для многих), но им нужно несколько обращений к памяти на каждый вход, а на процессорах с ослабленным упорядочением памяти — ещё и барьеры. Вместо этого каждая практическая блокировка построена на одной аппаратной возможности: команде, которая читает и записывает слово памяти как один неделимый шаг.

## Атомарные команды \{#atomic-instructions\}

<aside class="callout"><strong>Ключевая идея.</strong> Последовательность команд атомарна, только если что-то делает её такой. Либо аппаратура выполняет всё чтение-модификацию-запись как одну неделимую команду, и никакое другое ядро не может обратиться к слову посередине, либо блокировка, сама построенная на такой команде, позволяет выполнять всю последовательность только одному потоку за раз.</aside>

Расширение RISC-V A даёт два вида атомарных команд ([RISC-V Unprivileged ISA](#references), «Zaamo» и «Zalrsc»).

**Атомарные операции с памятью** (atomic memory operations, AMO) загружают слово, объединяют его с регистром и сохраняют результат обратно, неделимо: `amoadd.w rd, rs2, (rs1)` помещает старое значение слова по адресу `rs1` в `rd` и сохраняет старое значение плюс `rs2`. Есть AMO для обмена, сложения, «и», «или», исключающего «или», минимума и максимума. Одна команда делает счётчик правильным:

```asm
# фрагмент (расширение A; здесь не запускался: в интерпретаторе курса нет атомарных команд; работает на машине RISC-V)
        li      t0, 1
        amoadd.w zero, t0, (a0)       # counter += 1 одним неделимым шагом; старое значение отбрасывается
```

**Загрузка с резервированием / условное сохранение** (load-reserved / store-conditional, LR/SC) делит операцию на две. `lr.w rd, (rs1)` загружает слово и регистрирует на нём *резервирование* (reservation). `sc.w rd, rs2, (rs1)` сохраняет `rs2`, только если резервирование ещё действительно, то есть если никакое другое ядро не записывало слово после `lr.w`, и записывает в `rd` 0 при успехе и ненулевое значение при неудаче. Неудачная попытка просто повторяется:

```asm
# фрагмент (расширение A; здесь не запускался)
again:  lr.w    t0, (a0)              # загрузить counter и зарезервировать его
        addi    t0, t0, 1
        sc.w    t1, t0, (a0)          # сохранить, только если никто не писал counter после lr.w
        bnez    t1, again             # t1 != 0: сохранение не удалось, повторить
```

Через LR/SC можно построить любое чтение-модификацию-запись, в том числе сравнение с обменом (compare-and-swap). Спецификация гарантирует, что такой цикл в конце концов завершится успешно, если он *ограниченный* (constrained): не больше 16 команд, между `lr` и `sc` только простые целочисленные команды и никаких других загрузок и сохранений.

Отсюда прямо следует **спин-блокировка** (spinlock). Блокировка — это слово: 0, когда она свободна, и 1, когда захвачена. Чтобы захватить её, атомарно записываем 1 обменом: если старое значение было 0, блокировка была свободна и теперь наша; если 1, её кто-то держит, и мы пробуем снова.

```asm
# фрагмент (расширение A; здесь не запускался). a0 = адрес слова блокировки
acquire: li     t0, 1
retry:   amoswap.w.aq t1, t0, (a0)    # t1 = старое значение, слово становится 1
         bnez   t1, retry             # уже было 1: блокировку держит кто-то другой
         ret
release: amoswap.w.rl zero, zero, (a0)  # сохранить 0: блокировка свободна
         ret
```

Суффиксы `.aq` (acquire, захват) и `.rl` (release, освобождение) относятся к упорядочению — последнему разделу этой заметки: ни одно обращение к памяти из критической секции не может быть выполнено раньше захватывающего обмена или позже освобождающего.

**Атомарные типы C11** дают переносимый доступ к этим командам через `<stdatomic.h>` ([ISO/IEC 9899:2018](#references), §7.17). Переменная, объявленная как `atomic_long counter`, обновляется вызовом `atomic_fetch_add(&counter, 1)`; `atomic_compare_exchange_strong(&x, &expected, desired)` сохраняет `desired`, только если `x` всё ещё равно `expected`. При упорядочении по умолчанию, последовательно согласованном, спецификация RISC-V отображает атомарное чтение-модификацию-запись, такое как `atomic_fetch_add`, в AMO с обоими установленными битами, `amoadd.w.aqrl` ([RISC-V Unprivileged ISA](#references), «Code porting and mapping guidelines»). В разделе «Код» атомарный счётчик в каждом запуске доходит ровно до 2 000 000.

## Мьютексы \{#mutexes\}

Спин-блокировка, пока ждёт, впустую занимает ядро: поток, нашедший блокировку захваченной, продолжает выполнять обмены, пока владелец её не отпустит, а это может занять целый квант, если владельца вытеснили. **Мьютекс** (mutex, mutual-exclusion lock) ждёт иначе: поток, который не может получить блокировку, просит ядро усыпить его, а поток, освобождающий блокировку, будит его. Linux реализует это через **фьютекс** (futex): слово блокировки лежит в пользовательской памяти, захват или освобождение без соперничества — одна атомарная команда без системного вызова, а ядро участвует, только когда поток должен заснуть или быть разбуженным ([Drepper, 2011](#references)).

Интерфейс POSIX — `pthread_mutex_lock(&m)` и `pthread_mutex_unlock(&m)`, с `PTHREAD_MUTEX_INITIALIZER` для статически выделенного мьютекса ([Kerrisk, 2010](#references), глава 30). Счётчик принимает вид

```c
pthread_mutex_lock(&m);
counter++;                            /* the critical section: at most one thread here */
pthread_mutex_unlock(&m);
```

и оба потока вместе доходят до 2 000 000 в каждом запуске. У правильности есть цена: на используемом здесь M1 два миллиона приращений заняли около 2.2 мс без защиты, от 30 до 39 мс с мьютексом и от 34 до 51 мс с атомарным сложением (шесть запусков, `-O0`, время измеряла программа из раздела «Код»). Атомарная версия здесь не быстрее, потому что каждое приращение перемещает кэш-строку со счётчиком с одного ядра на другое — это трафик когерентности из [заметки о многоядерных процессорах](/ru/notes/acos/thread-level-parallelism#false-sharing); владелец мьютекса часто успевает сделать несколько приращений, прежде чем строка переместится. Времена зависят от машины и от соперничества, и блокировка, которую держат лишь несколько команд, должна защищать больше работы, чтобы её стоило захватывать.

Правила использования мьютекса: каждое обращение к общим данным, включая чтения, происходит с захваченным мьютексом; критическая секция коротка; и, держа мьютекс, код никогда не возвращается из функции, не выходит из цикла и не вызывает ничего, что может заблокироваться навсегда.

## Условные переменные: ожидание состояния \{#condition-variables-waiting-for-a-state\}

Мьютекс заставляет потоки действовать по очереди. Часто поток должен ещё и ждать, пока общее состояние не позволит ему продолжить: потребитель — пока очередь не перестанет быть пустой, производитель — пока она не перестанет быть полной. Проверка в цикле с освобождением мьютекса между проверками (*активное ожидание*, busy waiting) впустую тратит ядро. **Условная переменная** (condition variable) позволяет потоку спать, пока другой поток не просигналит, что состояние могло измениться.

`pthread_cond_wait(&cv, &m)` нужно вызывать с захваченным мьютексом `m`. Она освобождает мьютекс и усыпляет поток одним атомарным шагом, так что сигнал не может проскочить между ними; проснувшись, она снова захватывает мьютекс и только потом возвращается. `pthread_cond_signal(&cv)` будит один ожидающий поток, `pthread_cond_broadcast(&cv)` — все.

Классическое применение — **ограниченный буфер** (bounded buffer) из задачи производителя и потребителя (producer–consumer): кольцо из `CAP` ячеек, производитель, который кладёт элементы, и потребитель, который их забирает, один мьютекс и две условные переменные, `not_full` и `not_empty`:

```c
void put(int v) {
    pthread_mutex_lock(&m);
    while (count == CAP)                      /* full: sleep until a consumer makes room */
        pthread_cond_wait(&not_full, &m);
    buf[tail] = v; tail = (tail + 1) % CAP; count++;
    pthread_cond_signal(&not_empty);          /* a consumer may be waiting for this item */
    pthread_mutex_unlock(&m);
}
```

`get` — зеркальное отражение. Условие проверяется в цикле `while`, никогда не в `if`. Разбуженному потоку не гарантировано, что условие истинно: другой потребитель мог забрать элемент между сигналом и моментом, когда этот поток снова захватил мьютекс, а POSIX допускает *ложные пробуждения* (spurious wakeups) вообще без сигнала. Повторная проверка после каждого пробуждения всегда правильна. В разделе «Код» производитель передаёт квадраты 1, 4, …, 100 через буфер из четырёх ячеек, и потребитель получает все десять по порядку, а в буфере никогда не бывает больше четырёх элементов.

## Семафоры \{#semaphores\}

**Семафор** (semaphore) Дейкстры — целое число с двумя атомарными операциями ([Dijkstra, 1965](#references)): *P*, или `sem_wait`, ждёт, пока значение не станет положительным, и затем уменьшает его; *V*, или `sem_post`, увеличивает его и будит ожидающего, если такой есть. Семафор, инициализированный 1, — это блокировка: `sem_wait` входит, `sem_post` выходит. Семафор, инициализированный $n$, пропускает одновременно до $n$ потоков, например чтобы ограничить число открытых соединений. Семафор, инициализированный 0, — это сигнал: один поток ждёт на нём, пока другой не выполнит `sem_post`.

Ограниченному буферу нужны два считающих семафора и блокировка: `empty` начинается с `CAP` и считает свободные ячейки, `full` начинается с 0 и считает элементы. Производитель выполняет `sem_wait(&empty)`, вставляет элемент под блокировкой, затем `sem_post(&full)`; потребитель — наоборот. Счётчики заменяют циклы `while` версии с условными переменными, потому что семафор помнит, сколько было вызовов `sem_post`, а сигнал условной переменной, которую никто не ждёт, теряется.

POSIX даёт безымянные семафоры (`sem_init`), которые живут в памяти, общей для потоков, и именованные (`sem_open`), которые процессы могут открыть по имени. macOS реализует только именованные: `sem_init` там возвращает $-1$ и устанавливает `errno` в «Function not implemented». [Следующая заметка](/ru/notes/acos/inter-process-communication) использует именованные семафоры между процессами.

| Инструмент | Что гарантирует | Ожидание | Типичное применение |
| --- | --- | --- | --- |
| Атомарная команда | одно чтение-модификация-запись одного слова неделимо | нет | счётчики, флаги, построение блокировок |
| Спин-блокировка | взаимное исключение | активное: занимает ядро | очень короткие секции, внутри ядер ОС |
| Мьютекс | взаимное исключение, с владельцем | спит в ядре при соперничестве | защита общих структур данных |
| Условная переменная | сон до сигнала с освобождённым мьютексом | спит | ожидание состояния: очередь не пуста |
| Семафор | счётчик доступных единиц | спит, когда счётчик равен 0 | ограничение параллельности, сигналы между процессами |

## Взаимная блокировка \{#deadlock\}

Блокировки приносят собственный вид сбоя. Поток 1 переводит деньги со счёта X на счёт Y: он захватывает X, затем Y. Поток 2 переводит с Y на X: он захватывает Y, затем X. Если каждый захватит свою первую блокировку раньше, чем другой захватит вторую, поток 1 держит X и ждёт Y, поток 2 держит Y и ждёт X, и ни один никогда не продолжит работу. Это **взаимная блокировка** (deadlock).

Взаимная блокировка возможна, только если одновременно выполнены четыре условия ([Coffman, Elphick and Shoshani, 1971](#references)):

1. **Взаимное исключение** (mutual exclusion): ресурс одновременно может держать только один поток.
2. **Удержание и ожидание** (hold and wait): поток держит один ресурс, ожидая другой.
3. **Отсутствие вытеснения** (no preemption): ресурс нельзя отобрать у потока, который его держит.
4. **Циклическое ожидание** (circular wait): есть цикл потоков, каждый из которых ждёт ресурс, который держит следующий.

Устранение любого одного условия предотвращает взаимную блокировку. Обычно устраняют циклическое ожидание с помощью **упорядочения блокировок** (lock ordering): фиксируют глобальный порядок блокировок (для счетов — по номеру счёта, в общем случае — по адресу блокировки) и всегда захватывают их в этом порядке. Тогда оба перевода сначала захватывают счёт с меньшим номером; поток, который его получил, получит и вторую блокировку, а другой ждёт на первой.

<LockOrder />

Рисунок изображает каждую ситуацию графом: стрелка от блокировки к потоку, который её держит, и пунктирная стрелка от потока к блокировке, которую он ждёт. Взаимная блокировка — это цикл в таком графе. При глобальном порядке каждый поток захватывает блокировки в порядке возрастания, поэтому каждая стрелка вдоль пути ведёт к более старшей блокировке, и путь никогда не вернётся туда, откуда начался.

Можно атаковать и другие условия: захватывать сразу все блокировки или ни одной (`pthread_mutex_trylock` и освобождение всего при неудаче), что устраняет удержание и ожидание ценой риска *активной блокировки* (livelock) — потоков, которые синхронно повторяют попытки снова и снова; или находить циклы во время выполнения и разрывать их, как делают системы баз данных, прерывая одну транзакцию.

## Коротко об упорядочении обращений к памяти \{#memory-ordering-briefly\}

*Дополнительный материал: почему блокировки ещё и упорядочивают обращения к памяти. Остальная часть заметки на него не опирается.*

Блокировка делает больше, чем исключение. Процессоры и компиляторы переставляют обращения к памяти по разным адресам, когда один поток не может заметить разницы, а [заметка о многоядерных процессорах](/ru/notes/acos/thread-level-parallelism#memory-consistency-in-what-order-do-writes-become-visible) показывает, что модель памяти RISC-V, как и модель ARM, позволяет другим ядрам видеть сохранения одного ядра в другом порядке. Ломается шаблон передачи сообщения:

```c
/* thread 1 */                    /* thread 2 */
data = 42;                        while (!ready) { }
ready = 1;                        printf("%d\n", data);   /* may print 0 */
```

Ничто не мешает сохранению в `ready` стать видимым раньше сохранения в `data` или загрузке `data` выполниться раньше загрузки `ready`; компилятор может даже вынести загрузку `ready` из цикла. Исправление — сделать `ready` атомарной и сказать, какой порядок нужен: `atomic_store_explicit(&ready, 1, memory_order_release)` оставляет каждое более раннее обращение до сохранения, а `atomic_load_explicit(&ready, memory_order_acquire)` оставляет каждое более позднее обращение после загрузки. В RISC-V спецификация отображает освобождающее сохранение в `fence rw,w` с последующим `sw`, а захватывающую загрузку — в `lw` с последующим `fence r,rw` ([RISC-V Unprivileged ISA](#references), «Code porting and mapping guidelines»). Мьютекс делает ровно это: у `lock` семантика захвата (acquire), у `unlock` — семантика освобождения (release), и именно это дают биты `.aq` и `.rl` спин-блокировки выше. В программе, общие данные которой всегда используются под блокировками или через атомарные переменные, гонок данных нет; если её атомарные операции к тому же сохраняют упорядочение по умолчанию, последовательно согласованное, C11 гарантирует, что она ведёт себя так, будто обращения потоков чередуются в одном глобальном порядке, — это **последовательная согласованность** (sequential consistency) [Лэмпорта (1979)](#references).

## Что изменилось \{#what-changed\}

| | Общий счётчик без защиты | С синхронизацией |
| --- | --- | --- |
| `counter++` | загрузка, сложение, сохранение; другой поток может вклиниться | одна AMO, цикл LR/SC или три команды под мьютексом |
| Результат 2 × 1 000 000 приращений | около 1.0 миллиона, каждый раз разный (здесь) | ровно 2 000 000 |
| Время (M1, `-O0`, шесть запусков) | около 2.2 мс | 30–39 мс (мьютекс), 34–51 мс (атомарная операция) |
| Ожидание состояния | активный цикл по флагу | условная переменная или семафор |
| Новые виды сбоев | потерянные обновления, неопределённое поведение | взаимная блокировка, активная блокировка, соперничество |

## Ограничения \{#limitations\}

- **Блокировки не компонуются.** Две правильные функции, каждая из которых захватывает блокировку, могут взаимно заблокироваться, когда одна вызывает другую; порядок блокировок — свойство всей программы.
- **Соперничество упорядочивает в очередь.** Под одной блокировкой потоки выполняются по одному; популярная блокировка ограничивает ускорение по закону Амдала.
- **Инверсия приоритетов** (priority inversion). Поток с низким приоритетом, держащий блокировку, нужную потоку с высоким приоритетом, могут не допускать к процессору потоки со средним приоритетом; системам реального времени нужно наследование приоритетов.
- **Гонки прячутся.** Гонка может оставаться невидимой при тестировании, как при `-O2` выше. Инструменты вроде ThreadSanitizer (`clang -fsanitize=thread`) обнаруживают гонки данных во время выполнения на тех путях, которые выполняют тесты.

## Что нужно запомнить \{#what-you-should-remember\}

- `counter++` — три команды: загрузка, сложение, сохранение. Два потока, чередующие их, теряют обновления; так происходит в 18 из 20 чередований двух приращений.
- Критической секции нужны взаимное исключение, продвижение и ограниченное ожидание. Запрет прерываний работает только в ядре одноядерной машины.
- Атомарные команды RISC-V: AMO (`amoadd.w`, `amoswap.w`) выполняют чтение-модификацию-запись одной командой; LR/SC (`lr.w`, `sc.w`) повторяет попытку, пока никакое другое ядро не запишет слово в промежутке. `atomic_fetch_add` из C11 отображается в `amoadd.w.aqrl`.
- Спин-блокировка ждёт активно; мьютекс при соперничестве спит в ядре, а без соперничества стоит одну атомарную команду.
- Условная переменная ждёт состояния с освобождённым мьютексом; условие всегда перепроверяется в цикле `while`.
- Семафор считает: инициализированный 1, он блокировка, $n$ — пропускает $n$, 0 — сигнализирует.
- Взаимной блокировке нужны взаимное исключение, удержание и ожидание, отсутствие вытеснения и циклическое ожидание; захват блокировок в одном глобальном порядке устраняет цикл.
- Блокировки и атомарные операции с семантикой захвата и освобождения ещё и упорядочивают обращения к памяти; программа без гонок, которая использует только блокировки и атомарные операции с упорядочением по умолчанию, ведёт себя так, будто память последовательно согласована.

## Код \{#code\}

Счётчик без защиты, с мьютексом и с атомарной переменной C11. Скомпилировать и запустить: `clang -std=c17 -Wall -Wextra -O0 race.c -o race && ./race`. Значение счётчика с гонкой меняется от запуска к запуску и от машины к машине; два других всегда равны 2 000 000:

```c
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <time.h>

#define N 1000000                                    /* increments per thread */
static long counter;
static atomic_long acounter;
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

static void *racy(void *arg)   { (void)arg; for (int i = 0; i < N; i++) counter++; return NULL; }
static void *locked(void *arg) {
    (void)arg;
    for (int i = 0; i < N; i++) {
        pthread_mutex_lock(&m);
        counter++;                                   /* the critical section */
        pthread_mutex_unlock(&m);
    }
    return NULL;
}
static void *atomic(void *arg) { (void)arg; for (int i = 0; i < N; i++) atomic_fetch_add(&acounter, 1); return NULL; }

static double now(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec * 1e-9; }

static void run(const char *name, void *(*f)(void *)) {
    pthread_t a, b;
    counter = 0;
    double t0 = now();
    pthread_create(&a, NULL, f, NULL);
    pthread_create(&b, NULL, f, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("%-7s %ld  (%.1f ms)\n", name, f == atomic ? (long)atomic_load(&acounter) : counter, (now() - t0) * 1e3);
}

int main(void) {
    printf("expect  %d\n", 2 * N);
    run("racy", racy);
    run("mutex", locked);
    run("atomic", atomic);
    return 0;
}
/* One run on an Apple M1, macOS 26, clang -O0. In six runs the racy count was 1,002,319 to 1,008,633,
   and the times were 2.2-2.3 ms, 29.6-39.0 ms and 34.4-51.1 ms:
expect  2000000
racy    1008633  (2.2 ms)
mutex   2000000  (30.5 ms)
atomic  2000000  (34.5 ms)
*/
```

Потерянное обновление с рисунка в синтаксисе RARS: одна программа играет роль обоих потоков, A с регистром `t0` и B с `t1`, в том чередовании, что на рисунке (проверено интерпретатором RV32IM курса):

```asm
# Два «потока» увеличивают один счётчик; их шаги загрузки, сложения и сохранения чередуются вручную.
        .data
counter: .word 5
nl:     .asciz "\n"
        .text
main:
        la   a1, counter
        lw   t0, 0(a1)        # A: загрузка   -> t0 = 5
        lw   t1, 0(a1)        # B: загрузка   -> t1 = 5 (A ещё не сохранил)
        addi t0, t0, 1        # A: сложение   -> t0 = 6
        addi t1, t1, 1        # B: сложение   -> t1 = 6
        sw   t0, 0(a1)        # A: сохранение -> counter = 6
        sw   t1, 0(a1)        # B: сохранение -> counter = 6: обновление A потеряно
        lw   a0, 0(a1)
        li   a7, 1            # печать целого: печатает 6
        ecall
        la   a0, nl
        li   a7, 4            # печать строки
        ecall
        li   a7, 10           # выход
        ecall
```

Все чередования одного приращения в каждом потоке на Python:

```python
from itertools import combinations

results = {}
for slots in combinations(range(6), 3):         # какие 3 из 6 шагов принадлежат потоку A
    mem, reg, step = 5, {'A': 0, 'B': 0}, {'A': 0, 'B': 0}
    for k in range(6):
        t = 'A' if k in slots else 'B'
        op = step[t]; step[t] += 1
        if op == 0: reg[t] = mem                 # загрузка
        elif op == 1: reg[t] += 1                # сложение
        else: mem = reg[t]                       # сохранение
    results[mem] = results.get(mem, 0) + 1
print(results)                                   # {7: 2, 6: 18}: 18 of 20 interleavings lose an update
```

Ограниченный буфер с мьютексом и двумя условными переменными. Поток-производитель посылает квадраты чисел от 1 до 10, а затем $-1$ как маркер конца:

```c
#include <pthread.h>
#include <stdio.h>

#define CAP 4                                        /* a bounded buffer of 4 slots */
static int buf[CAP], head, tail, count, max_seen;
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER, not_empty = PTHREAD_COND_INITIALIZER;

static void put(int v) {
    pthread_mutex_lock(&m);
    while (count == CAP) pthread_cond_wait(&not_full, &m);    /* while, not if: recheck after waking */
    buf[tail] = v; tail = (tail + 1) % CAP; count++;
    if (count > max_seen) max_seen = count;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&m);
}

static int get(void) {
    pthread_mutex_lock(&m);
    while (count == 0) pthread_cond_wait(&not_empty, &m);
    int v = buf[head]; head = (head + 1) % CAP; count--;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&m);
    return v;
}

static void *producer(void *arg) {
    (void)arg;
    for (int i = 1; i <= 10; i++) put(i * i);
    put(-1);                                         /* end marker: no more items */
    return NULL;
}

int main(void) {
    pthread_t p;
    pthread_create(&p, NULL, producer, NULL);
    long sum = 0;
    for (int v; (v = get()) != -1; ) { printf("%d ", v); sum += v; }
    pthread_join(p, NULL);
    printf("\nsum=%ld, buffer within %d slots: %s\n", sum, CAP, max_seen <= CAP ? "yes" : "no");
    return 0;
}
/* Output:
1 4 9 16 25 36 49 64 81 100
sum=385, buffer within 4 slots: yes
*/
```
