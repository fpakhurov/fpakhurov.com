[Предыдущая заметка](/ru/notes/acos/control-flow-and-memory) дала программам на ассемблере циклы, ветвления и память, и в её примерах уже была небольшая подпрограмма `show`, в которую попадали командой `jal ra, show` и из которой выходили командой `ret`. Это работало, потому что `show` больше ничего не вызывала и трогала только три регистра, не нужные вызывающему коду. Эта заметка превращает такое везение в правила. **Процедура** (procedure; в C — функция) — это код, который существует в одном экземпляре и выполняется по просьбе многих вызывающих: она должна найти свои аргументы, вернуться к тому, кто её вызвал, отдать результат и не испортить значения вызывающего. Для переходов RISC-V предоставляет две команды, **соглашение о вызовах** (calling convention), которое делит регистры между вызывающей и вызываемой стороной, и **стек** (stack) в памяти, где каждый активный вызов держит то, что не помещается в регистры. С ними процедуры могут вызывать процедуры, в том числе самих себя.

**Обозначения.** `ra` — регистр адреса возврата (return address) `x1`, `sp` — указатель стека (stack pointer) `x2`. **Вызывающий** (caller) — код, который делает вызов, **вызываемая процедура** (callee) — та, которую вызывают. **Кадр** (frame) — участок памяти стека, принадлежащий одному активному вызову; его размер кратен 16 байтам.

## Отправная точка: переход в общий код и обратно \{#baseline-jump-to-shared-code-and-jump-back\}

Даже без команды вызова код можно сделать общим: поставить его по метке, переходить туда командой `j` и заканчивать командой `j` обратно, на место после перехода. С одним вызывающим это работает. С двумя — нет, потому что общий код должен заканчиваться одной фиксированной командой `j`, а она может вернуть только к одному из них.

Исправление напрашивается само: вызывающий кладёт в регистр адрес, куда хочет вернуться, а общий код переходит по адресу, который лежит в этом регистре. Ровно это и предоставляет RISC-V. Но исправление сразу порождает следующую проблему. Если общий код сам вызовет другую процедуру тем же способом, второй вызов перезапишет регистр с первым адресом возврата, и первого вызывающего уже не найти. А каждый регистр, который общий код использует для своей работы, может хранить то, что ещё нужно вызывающему. Процедурам нужно место, где адреса возврата и значения хранятся *для каждого активного вызова отдельно*, и правило о том, кто что сохраняет.

## jal и jalr: вызов и возврат \{#jal-and-jalr-calling-and-returning\}

Вызовы и возвраты делают две команды:

| Команда | Действие |
| --- | --- |
| `jal rd, label` | $x[rd] = pc + 4$; $pc = $ метка (смещение в пределах ±1 МиБ, формат J) |
| `jalr rd, rs1, imm` | $t = (x[rs1] + \operatorname{sext}(imm))$ с обнулённым битом 0; $x[rd] = pc + 4$; $pc = t$ (формат I) |

Обе **сохраняют адрес возврата** (link): записывают в `rd` адрес команды, следующей за ними, и по соглашению это `ra`. `jalr` переходит по адресу из регистра, поэтому может вернуться к любому вызывающему, а также вызвать процедуру, адрес которой вычисляется во время выполнения. Типичные применения названы псевдокомандами (pseudo-instructions) ассемблера:

| Псевдокоманда | Раскрывается в | Применение |
| --- | --- | --- |
| `jal label` | `jal ra, label` | вызвать процедуру в пределах ±1 МиБ |
| `call label` | `auipc ra, hi` + `jalr ra, ra, lo` | вызвать процедуру по любому адресу |
| `ret` | `jalr zero, ra, 0` | возврат: перейти по `ra`, ничего не сохраняя |
| `jr rs` | `jalr zero, rs, 0` | перейти по адресу из регистра |

**Разобранный пример.** В программе вычисления факториала из раздела «Код» `main` начинается по адресу `0x00400000`, а её `jal ra, fact` стоит по адресу `0x00400004`; `fact` начинается с `0x00400050`. Выполнение `jal` устанавливает `ra` = `0x00400008` и `pc` = `0x00400050`. Когда `fact` заканчивается командой `ret`, процессор переходит по `ra`, и `main` продолжается с `0x00400008`. Внутри `fact` рекурсивный `jal ra, fact` стоит по адресу `0x0040006c`, поэтому каждый рекурсивный вызов возвращается на `0x00400070`, к следующей за ним команде.

## Соглашение о вызовах \{#the-calling-convention\}

<aside class="callout"><strong>Ключевая идея.</strong> Процедуру можно безопасно вызывать откуда угодно, если обе стороны соблюдают один договор. Аргументы передаются в `a0`–`a7`, а результат возвращается в `a0` (и `a1`). Вызываемая процедура может свободно менять `t0`–`t6`, `a0`–`a7` и `ra`, поэтому вызывающий сам сохраняет те из них, которые ему ещё нужны; вызываемая процедура обязана оставить `s0`–`s11` и `sp` такими, какими их получила, поэтому она сохраняет те из них, которые меняет, и восстанавливает их перед возвратом. Всё, что должно пережить вызов и не помещается в регистры, кладётся в кадр вызываемой процедуры на стеке.</aside>

Соглашение — часть ABI, а не ISA ([RISC-V psABI](#references), целочисленное соглашение о вызовах):

| Регистры | Роль | Кто сохраняет их при вызове |
| --- | --- | --- |
| `a0`–`a7` | первые восемь целочисленных аргументов; `a0`–`a1` — ещё и возвращаемое значение | вызывающий, если они ему нужны |
| `t0`–`t6` | временные | вызывающий, если они ему нужны |
| `ra` | адрес возврата | вызывающий (каждый вызов его перезаписывает) |
| `s0`–`s11` | сохраняемые регистры; `s0` может служить указателем кадра `fp` | вызываемая процедура, если она их использует |
| `sp` | указатель стека | вызываемая процедура: при возврате он должен быть прежним |
| `zero`, `gp`, `tp` | константа, глобальный указатель и указатель потока | процедуры их никогда не меняют |

Аргументы после восьмого передаются через стек: в момент вызова они лежат по адресам `0(sp)`, `4(sp)` и так далее.

Зачем делить регистры, а не поручить одной стороне сохранять всё? Если бы вызывающие сохраняли каждый используемый регистр, вызов крошечной процедуры стоил бы множества сохранений и загрузок, которые ей вовсе не были нужны. Если бы вызываемые процедуры сохраняли каждый используемый регистр, вызывающий, которому нечего беречь, всё равно платил бы за сохранения. При разделении значения, которые должны жить через вызовы, попадают в регистры `s`, и за них один раз платит каждая использующая их вызываемая процедура, а короткоживущие значения попадают в регистры `t` и `a`, которые ничего не стоят, если посреди их жизни не случился вызов.

**Разобранный пример.** Процедура `sum_f` из раздела «Код» вычисляет $f(1) + \dots + f(5)$ для процедуры $f$, адрес которой получает в `a0`. Её счётчик цикла `i`, текущая сумма, граница 5 и адрес $f$ должны пережить пять вызовов $f$. Она держит их в `s0`–`s3`, которые `f` обязана сохранить, и поэтому сама сохраняет значения `s0`–`s3` своего вызывающего, а вместе с ними свой `ra`, который перезаписывает каждый `jalr` в `f`: пять слов в кадре из 32 байтов. Альтернатива — держать `i` в `t0` — вынудила бы `sum_f` сохранять и заново загружать `t0` вокруг каждого из пяти вызовов.

## Стек и кадры стека \{#the-stack-and-stack-frames\}

**Стек** — область памяти, растущая в сторону меньших адресов. `sp` указывает на её младший занятый байт; в RARS он начинается с `0x7fffeffc`. Процедура, которой на время вызова нужна память, берёт её, уменьшая `sp`, и отдаёт, увеличивая `sp` на ту же величину перед возвратом. Каждый вызов отдаёт ровно то, что взял, поэтому память активных сейчас вызовов всегда образует непрерывный участок, и последний вызов лежит ниже всех: последним пришёл, первым ушёл, в том порядке, в каком вызовы завершаются.

Процедура, которой нужен кадр, следует фиксированному шаблону:

```riscv
proc:   addi sp, sp, -16            # пролог: выделить кадр из 16 байтов
        sw   ra, 12(sp)             # сохранить адрес возврата (если proc что-то вызывает)
        sw   s0, 8(sp)              # сохранить каждый регистр s, который proc будет использовать
        ...                         # тело: может вызывать другие процедуры
        lw   s0, 8(sp)              # эпилог: восстановить в обратном порядке
        lw   ra, 12(sp)
        addi sp, sp, 16             # освободить кадр
        ret
```

psABI требует, чтобы при каждом вызове `sp` был кратен 16, поэтому размеры кадров кратны 16 байтам, даже если используется меньше; кроме того, кадр хранит локальные переменные и массивы, которые не помещаются в регистры, и исходящие аргументы после восьмого. Данные ниже `sp` никому не принадлежат и могут быть перезаписаны в любой момент. (RARS начинает `sp` с `0x7fffeffc`, а это не кратно 16; наши кадры, как и предписывает соглашение, имеют размеры, кратные 16, так что `sp` всё время остаётся сравним с 12 по модулю 16.)

## Рекурсия: факториал \{#recursion-factorial\}

Рекурсивная процедура — обычная процедура, которая вызывает саму себя, и стек обеспечивает её работу без всякого особого механизма: у каждого активного вызова свой кадр, а значит, свой сохранённый `ra` и свои сохранённые значения.

```riscv
fact:   addi sp, sp, -16            # пролог: кадр из 16 байтов
        sw   ra, 12(sp)             # сохранить адрес возврата: fact вызывает fact
        sw   s0, 8(sp)              # сохранить s0 вызывающего: мы сейчас его займём
        mv   s0, a0                 # s0 = n, сохраняется через рекурсивный вызов
        li   t0, 1
        ble  a0, t0, base           # n <= 1: база рекурсии
        addi a0, a0, -1
        jal  ra, fact               # a0 = fact(n - 1)
        mul  a0, s0, a0             # a0 = n * fact(n - 1)
        j    out
base:   li   a0, 1
out:    lw   s0, 8(sp)              # эпилог: восстановить в обратном порядке
        lw   ra, 12(sp)
        addi sp, sp, 16             # освободить кадр
        ret
```

`n` нужно после рекурсивного вызова, чтобы умножить на его результат, поэтому оно живёт в `s0`, и `fact` сохраняет `s0` своего вызывающего, прежде чем его перезаписать. `ra` сохраняется, потому что рекурсивный `jal` его перезаписывает.

<FactorialFrames />

**Разобранный пример.** `main` вызывает `fact(3)` при `sp` = `0x7fffeffc`:

1. `jal ra, fact` в `main` устанавливает `ra` = `0x00400008`.
2. `fact(3)` уменьшает `sp` до `0x7fffefec` и сохраняет `ra` = `0x00400008` по адресу `0x7fffeff8`, а `s0` из `main` (0) — по адресу `0x7fffeff4`; затем устанавливает `s0` = 3.
3. Она вызывает `fact(2)`, которая уменьшает `sp` до `0x7fffefdc` и сохраняет `ra` = `0x00400070` (команда `mul` в `fact`) и `s0` = 3; затем устанавливает `s0` = 2.
4. `fact(2)` вызывает `fact(1)`: `sp` = `0x7fffefcc`, сохранены `ra` = `0x00400070` и `s0` = 2. Поскольку $n \le 1$, она возвращает 1, предварительно восстановив из своего кадра `s0` = 2 и `ra` = `0x00400070`.
5. Снова в `fact(2)` по адресу `0x00400070`: `mul` даёт $2 \cdot 1 = 2$; эпилог восстанавливает `s0` = 3 и `ra` = `0x00400070` и освобождает кадр.
6. Снова в `fact(3)`: $3 \cdot 2 = 6$; эпилог восстанавливает `s0` = 0 и `ra` = `0x00400008`, `sp` возвращается к `0x7fffeffc`, и `ret` попадает в `main` с `a0` = 6.

`fact(n)` делает $n$ вызовов, и в самой глубокой точке ей нужно $16n$ байтов стека. Результаты переполняются задолго до стека: $12! = 479\,001\,600$ помещается в 32 бита, а $13! = 6\,227\,020\,800$ — нет, и `mul` молча возвращает его по модулю $2^{32}$, то есть 1 932 053 504.

**Цена рекурсии.** Рекурсивная функция Фибоначчи, $\mathrm{fib}(n) = \mathrm{fib}(n-1) + \mathrm{fib}(n-2)$, делает два вызова на каждый вызов, и число вызовов растёт как сами числа Фибоначчи: $\mathrm{fib}(n)$ делает $2F_{n+1} - 1$ вызовов, где $F_k$ — $k$-е число Фибоначчи. Для $n = 20$ это $2 \cdot 10\,946 - 1 = 21\,891$ вызов ради числа 6765. Версия из раздела «Код» тратит 8 команд на вызов, попавший в базу рекурсии, и 23 — на вызов, который рекурсивно вызывает себя дальше, что в сумме даёт $31 F_{n+1} - 23$ команды, 339 303 при $n = 20$; циклу, который несёт два соседних числа Фибоначчи, нужно $5n + 5$, то есть 105.

Рекурсия — естественная запись многих алгоритмов, и стек делает её корректной; будет ли она дешёвой, зависит от того, сколько вызовов она делает.

## Листовые и нелистовые процедуры \{#leaf-and-non-leaf-procedures\}

**Листовая** процедура (leaf procedure) ничего не вызывает. Её `ra` остаётся нетронутым, и если она использует только регистры `t` и `a`, то ничего не сохраняет и кадр ей не нужен: `show` из предыдущих заметок, итеративный цикл Фибоначчи и `square_leaf` ниже — листовые. **Нелистовая** процедура (non-leaf) обязана сохранить `ra` до первого вызова и держать каждое значение, нужное ей после вызова, либо в регистре `s` (сохранив значение этого регистра у вызывающего), либо в своём кадре.

**Разобранный пример.** Два правильных способа вычислить $i^2$ для цикла `sum_f`:

```riscv
square_leaf:                        # листовая: только временный регистр, без кадра
        mul  t0, a0, a0
        mv   a0, t0
        ret

square_frame:                       # использует s0, поэтому должна сохранить и восстановить его
        addi sp, sp, -16
        sw   s0, 12(sp)
        mul  s0, a0, a0
        mv   a0, s0
        lw   s0, 12(sp)
        addi sp, sp, 16
        ret
```

Обе возвращают одно и то же значение; листовая версия выполняет 3 команды на вызов против 7 у другой и не обращается к памяти. Компиляторы делают тот же выбор: листовая функция, которой хватает временных регистров, вовсе не получает пролога, а рекурсивная `fib`, о которой шла речь выше, проверяет базу рекурсии *до* построения кадра, поэтому половина её вызовов, заканчивающихся сразу, стоит 8 команд вместо 23.

<aside class="callout"><strong>Проверьте себя.</strong> (1) Процедура вызывает две другие, и после обоих вызовов ей нужно одно значение. Какие регистры она должна сохранить в своём кадре? (2) `jalr` обнуляет бит 0 адреса перехода. Почему это безвредно и для чего это полезно? (3) `fact(1000)` в RARS: что ограничивает её раньше, стек или арифметика?<details><summary>Ответы</summary>(1) `ra`, потому что её собственные вызовы его перезаписывают, и один регистр `s` для хранения значения (сохранив значение этого регистра `s` у вызывающего) или же само значение в ячейке кадра: два слова, значит, кадр из 16 байтов. (2) Адреса команд всегда чётные, поэтому бит 0 адреса перехода не несёт информации. Его обнуление немного упрощает аппаратуру и позволяет программам хранить метку в младшем бите указателя на функцию и всё равно переходить по нему ([RISC-V Unprivileged ISA](#references), обоснование `jalr`). (3) Арифметика: начиная с 13 результат неверен (берётся по модулю $2^{32}$), а 1000 кадров занимают всего 16 000 байтов стека, в котором места гораздо больше.</details></aside>

## Ошибка в кадре стека и что она ломает \{#a-stack-frame-bug-and-what-it-breaks\}

Соглашение — договор, соблюдение которого ничто не проверяет: ассемблер принимает процедуру, которая его нарушает, а программа ломается в другом месте и позже.

**Вызываемая процедура, портящая регистр `s`.** `square_bad` вычисляет $i^2$ в `s0`, не сохранив его:

```riscv
square_bad:                         # ОШИБКА: пишет в s0, не сохранив его
        mul  s0, a0, a0
        mv   a0, s0
        ret
```

`sum_f` держит счётчик цикла $i$ в `s0`, полагаясь на соглашение. После `square_bad(1)` `s0` = 1, и сумма равна 1; `i++` даёт 2. После `square_bad(2)` `s0` = 4: счётчик перескочил, и `i++` даёт 5. После `square_bad(5)` `s0` = 25, сумма равна $1 + 4 + 25 = 30$, а `i++` даёт 26, и цикл заканчивается. Программа печатает 30 вместо 55 и завершается как обычно. Ошибка — в `square_bad`, а неверное число появляется в `sum_f`. Раздел «Код» запускает эту версию и обе правильные.

**Нелистовая процедура, которая не сохраняет `ra`.**

```riscv
f:      addi sp, sp, -16            # ОШИБКА: кадр не сохраняет ra
        sw   s0, 12(sp)
        mv   s0, a0
        jal  ra, g                  # перезаписывает ra адресом команды add ниже
        add  a0, a0, s0
        lw   s0, 12(sp)
        addi sp, sp, 16
        ret                         # переходит на add, а не обратно к вызывающему
```

`jal ra, g` заменяет адрес возврата вызывающего адресом команды `add`. Дойдя до `ret`, `f` переходит на этот `add`, снова выполняет эпилог, освобождает ещё 16 байтов, которых никогда не выделяла, и опять возвращается на `add`: до вызывающего дело так и не доходит. Каждый круг увеличивает `sp` на 16 и загружает `s0` из памяти выше кадра, так что через несколько сотен кругов `sp` целиком выходит за пределы стека. Чем программа в итоге закончится, зависит от среды: бесконечным циклом или ошибкой, когда загрузка дойдёт до памяти, к которой программе нельзя обращаться; в любом случае то, что собирался напечатать вызывающий, так и не появится. В запуске, где `f` находится по адресу `0x00400018`, трасса после возврата из `g` бесконечно повторяет четыре адреса: `add` по адресу `0x00400028`, `lw` по адресу `0x0040002c`, `addi` по адресу `0x00400030`, `ret` по адресу `0x00400034` и снова `0x00400028`.

У обеих ошибок одна форма: значение, на которое полагалась одна сторона вызова, уничтожила другая сторона, и симптом проявляется далеко от причины. Обычные средства защиты механические: писать пролог и эпилог вместе, сохранять каждый регистр `s` и `ra`, в который пишет тело, и каждой команде `addi sp, sp, -N` ставить в пару `addi sp, sp, N`.

## Что изменилось \{#what-changed\}

| | Отправная точка: `j` в общий код и обратно | Процедуры с соглашением и стеком |
| --- | --- | --- |
| Адрес возврата | одна фиксированная метка | `ra`, который `jal`/`jalr` записывает при каждом вызове |
| Вложенные вызовы | невозможны: адрес возврата перезаписывается | `ra` сохраняется в собственном кадре вызывающего |
| Рекурсия | невозможна | у каждого активного вызова свой кадр |
| Аргументы и результаты | как придётся | на входе `a0`–`a7`, на выходе `a0`–`a1` |
| Регистры при вызове | может измениться что угодно | `s0`–`s11`, `sp` сохраняются; `t`, `a`, `ra` — нет |
| Цена вызова | по одному переходу в каждую сторону | по переходу в каждую сторону плюс сохранения и восстановления, которые нужны процедуре; у листовой их нет |

## Ограничения \{#limitations\}

- **Соблюдение соглашения ничто не проверяет.** Процедура, которая его нарушает, ассемблируется и выполняется, а сбой проявляется в другом месте, как показывают обе ошибки. Компиляторы соблюдают его надёжно; написанный вручную ассемблер приходится проверять вручную или тестами.
- **Вызовы стоят команд и обмена с памятью.** Сохранения и восстановления — это загрузки и сохранения в память; глубокая рекурсия превращает их во множество обращений к памяти, цену которых считает [заметка о кэшах](/ru/notes/acos/caches). Компиляторы убирают вызовы, встраивая (inlining) небольшие процедуры.
- **Стек конечен.** Глубокая рекурсия его исчерпывает: в Linux стек потока по умолчанию обычно занимает 8 МиБ (настройка `ulimit -s`), так что рекурсия с кадрами по 64 байта переполняет его примерно на 130 000 уровней. Что происходит дальше, разбирает [заметка о виртуальной памяти](/ru/notes/acos/virtual-memory).
- **Кадр доступен по адресу.** Процедура, которая пишет за конец локального массива, перезаписывает сохранённый `ra` над ним, и `ret` переходит туда, куда указывают записанные данные. Это переполнение буфера на стеке (stack buffer overflow), основа длинного ряда атак на безопасность.
- **Рекурсия может умножать работу.** Наивная функция Фибоначчи делает экспоненциальное число вызовов; стек делает рекурсию корректной, а не эффективной.

## Что нужно запомнить \{#what-you-should-remember\}

- `jal rd, label` и `jalr rd, rs1, imm` выполняют переход и записывают адрес возврата $pc + 4$ в `rd`; `call`, `jal label` и `ret` — их обычные формы с `rd` = `ra` или `zero`.
- Аргументы передаются в `a0`–`a7`, результаты возвращаются в `a0`–`a1`. Вызывающий сохраняет регистры `t`, `a` и `ra`, которые ему ещё нужны; вызываемая процедура сохраняет регистры `s`, которые меняет, и возвращает `sp` неизменным.
- Стек растёт вниз от `sp`; кадр процедуры берётся командой `addi sp, sp, -N` и отдаётся командой `addi sp, sp, N`, где $N$ кратно 16. В нём лежат сохранённый `ra`, сохранённые регистры `s`, локальные переменные и дополнительные аргументы.
- Рекурсии больше ничего не нужно: у каждого вызова свой кадр. `fact(3)` строит три кадра по 16 байтов, вплоть до `sp` = `0x7fffefcc` в RARS.
- Листовой процедуре, которая использует только временные регистры, кадр не нужен. Нелистовая процедура обязана сохранять `ra`.
- Нарушение соглашения проявляется далеко от причины: испорченный `s0` превратил сумму 55 в 30; забытый `ra` заставляет процедуру возвращаться в саму себя.

## Код \{#code\}

Рекурсивный факториал, включая первый переполняющийся результат:

```riscv
        .text
        .globl main
main:
        li   a0, 3
        jal  ra, fact               # a0 = fact(3)
        li   a7, 1
        ecall                       # prints 6
        li   a0, ' '
        li   a7, 11
        ecall
        li   a0, 12
        jal  ra, fact
        li   a7, 1
        ecall                       # prints 479001600
        li   a0, ' '
        li   a7, 11
        ecall
        li   a0, 13
        jal  ra, fact               # 13! = 6227020800 не помещается в 32 бита
        li   a7, 1
        ecall                       # prints 1932053504, the product modulo 2^32
        li   a7, 10
        ecall

fact:   addi sp, sp, -16            # пролог: кадр из 16 байтов
        sw   ra, 12(sp)             # сохранить адрес возврата: fact вызывает fact
        sw   s0, 8(sp)              # сохранить s0 вызывающего: мы сейчас его займём
        mv   s0, a0                 # s0 = n, сохраняется через рекурсивный вызов
        li   t0, 1
        ble  a0, t0, base           # n <= 1: база рекурсии
        addi a0, a0, -1
        jal  ra, fact               # a0 = fact(n - 1)
        mul  a0, s0, a0             # a0 = n * fact(n - 1)
        j    out
base:   li   a0, 1
out:    lw   s0, 8(sp)              # эпилог: восстановить в обратном порядке
        lw   ra, 12(sp)
        addi sp, sp, 16             # освободить кадр
        ret
# Output: 6 479001600 1932053504
```

Рекурсивная функция Фибоначчи со счётчиком своих вызовов (всего выполняется 339 316 команд, 13 из них в `main`):

```riscv
        .data
calls:  .word 0                     # увеличивается при каждом вызове fib

        .text
        .globl main
main:
        li   a0, 20
        jal  ra, fib                # a0 = fib(20)
        li   a7, 1
        ecall                       # prints 6765
        li   a0, ' '
        li   a7, 11
        ecall
        lw   a0, calls
        li   a7, 1
        ecall                       # prints 21891, the number of calls
        li   a7, 10
        ecall

fib:    la   t0, calls              # calls++ (t0, t1 временные: сохранять их не нужно)
        lw   t1, 0(t0)
        addi t1, t1, 1
        sw   t1, 0(t0)
        li   t0, 2
        blt  a0, t0, done           # n < 2: вернуть n, ещё до построения кадра
        addi sp, sp, -16            # рекурсивному пути нужен кадр
        sw   ra, 12(sp)
        sw   s0, 8(sp)
        sw   s1, 4(sp)
        mv   s0, a0                 # s0 = n
        addi a0, a0, -1
        jal  ra, fib
        mv   s1, a0                 # s1 = fib(n - 1), должно пережить следующий вызов
        addi a0, s0, -2
        jal  ra, fib                # a0 = fib(n - 2)
        add  a0, s1, a0
        lw   s1, 4(sp)
        lw   s0, 8(sp)
        lw   ra, 12(sp)
        addi sp, sp, 16
done:   ret
# Output: 6765 21891
```

Итеративная версия, листовая (всего выполняется 111 команд, 105 из них в `fib_iter`):

```riscv
        .text
        .globl main
main:
        li   a0, 20
        jal  ra, fib_iter
        li   a7, 1
        ecall                       # prints 6765
        li   a7, 10
        ecall

fib_iter:                           # листовая: a0 = fib(a0) только на временных регистрах, без кадра
        li   t0, 0                  # t0 = fib(i)
        li   t1, 1                  # t1 = fib(i + 1)
        beqz a0, fdone
floop:  add  t2, t0, t1
        mv   t0, t1
        mv   t1, t2
        addi a0, a0, -1
        bnez a0, floop
fdone:  mv   a0, t0
        ret
# Output: 6765
```

Ошибка в соблюдении соглашения и две правильные вызываемые процедуры, вызываемые через `jalr` с адресом процедуры в регистре:

```riscv
        .text
        .globl main
main:
        la   a0, square_bad
        jal  ra, sum_f
        jal  ra, print              # 30: счётчик цикла испорчен
        la   a0, square_leaf
        jal  ra, sum_f
        jal  ra, print              # 55
        la   a0, square_frame
        jal  ra, sum_f
        jal  ra, print              # 55
        li   a7, 10
        ecall

sum_f:                              # a0 = f(1) + ... + f(5), где f — процедура, адрес которой лежит в a0
        addi sp, sp, -32            # кадр: ra и четыре регистра s, которые использует процедура
        sw   ra, 28(sp)
        sw   s0, 24(sp)
        sw   s1, 20(sp)
        sw   s2, 16(sp)
        sw   s3, 12(sp)
        mv   s3, a0                 # s3 = f, сохраняется через вызовы
        li   s0, 1                  # s0 = i: регистр, сохраняемый вызываемой процедурой, поэтому переживёт каждый вызов f
        li   s1, 0                  # s1 = сумма
        li   s2, 5
loop:   mv   a0, s0
        jalr ra, s3, 0              # вызов f(i): переход по адресу из s3, адрес возврата в ra
        add  s1, s1, a0
        addi s0, s0, 1
        ble  s0, s2, loop
        mv   a0, s1
        lw   s3, 12(sp)
        lw   s2, 16(sp)
        lw   s1, 20(sp)
        lw   s0, 24(sp)
        lw   ra, 28(sp)
        addi sp, sp, 32
        ret

square_bad:                         # ОШИБКА: пишет в s0, не сохранив его
        mul  s0, a0, a0
        mv   a0, s0
        ret

square_leaf:                        # правильная листовая: только временный регистр, без кадра
        mul  t0, a0, a0
        mv   a0, t0
        ret

square_frame:                       # тоже правильная: использует s0, поэтому сохраняет и восстанавливает его
        addi sp, sp, -16
        sw   s0, 12(sp)
        mul  s0, a0, a0
        mv   a0, s0
        lw   s0, 12(sp)
        addi sp, sp, 16
        ret

print:                              # напечатать a0 и перевод строки
        li   a7, 1
        ecall
        li   a0, 10
        li   a7, 11
        ecall
        ret
# Output:
# 30
# 55
# 55
```

Число вызовов и команд рекурсивной функции Фибоначчи по двум её путям:

```python
F = [0, 1]
for k in range(2, 32):
    F.append(F[-1] + F[-2])

def calls(n):        # fib(n) при n >= 2 вызывает fib(n-1) и fib(n-2); fib(0) и fib(1) ничего не вызывают
    return 1 if n < 2 else 1 + calls(n - 1) + calls(n - 2)

print([calls(n) for n in range(8)], [2 * F[n + 1] - 1 for n in range(8)])
# [1, 1, 3, 5, 9, 15, 25, 41] [1, 1, 3, 5, 9, 15, 25, 41]

n = 20
base, recursive = F[n + 1], F[n + 1] - 1      # вызовы, которые сразу заканчиваются, и вызовы, которые рекурсивно вызывают fib
print(F[n], base + recursive, 8 * base + 23 * recursive, 5 * n + 5)
# 6765 21891 339303 105
```

## Дальше \{#next\}

С процедурами картина программы на RISC-V завершена: используемые значения лежат в 32 регистрах, а всё остальное — массивы, строки и кадры активных вызовов — живёт в памяти, и до него добираются загрузками и сохранениями. До сих пор заметки считали все загрузки одинаково дешёвыми. [Следующая заметка](/ru/notes/acos/caches) показывает, почему это не так: основная память отвечает намного дольше, чем выполняется команда, и небольшие быстрые кэши, которые скрывают эту задержку, определяют, насколько быстро работают реальные программы.
