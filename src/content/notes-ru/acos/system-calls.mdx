[Заметка об операционных системах](/ru/notes/acos/operating-systems) поместила ядро в привилегированный режим, в который пользовательские программы войти не могут, а [предыдущая заметка](/ru/notes/acos/c-for-systems-programming) писала эти программы на C. Между ними — узкая дверь. Программа, которая хочет что-то напечатать, прочитать файл, запустить процесс или получить память, должна попросить ядро, и единственный способ попросить — **системный вызов** (system call): ловушка, которая переносит в ядро номер запроса и его аргументы и возвращает результат. [Заметка об исключениях](/ru/notes/acos/exceptions-and-interrupts#how-ecall-becomes-a-system-call) проследила эту ловушку через аппаратуру. Эта заметка прослеживает запрос: от вызова функции C через библиотеку C к команде `ecall`, через таблицу услуг ядра и обратно; как сообщается об ошибках; сколько стоит путь туда и обратно; как наблюдать за вызовами, которые делает программа; и чем `printf` отличается от `write`, на котором он построен.

**Обозначения.** В RISC-V `a0`–`a7` — регистры аргументов из [соглашения о вызовах](/ru/notes/acos/procedures-and-the-stack). Раздел руководства (manual) для функции пишется после её имени: `write(2)` — системный вызов из раздела 2 руководства, `printf(3)` — библиотечная функция из раздела 3. *errno* — переменная библиотеки C с номером последней ошибки.

## Отправная точка: вызывать ядро как функцию \{#baseline-calling-the-kernel-like-a-function\}

Почему бы не вызвать функцию ядра `sys_write` напрямую, командой `jal`, как любую другую функцию? По трём причинам.

1. **Код недоступен.** Страницы ядра отображены в каждом процессе, но со сброшенным битом U. Переход на `sys_write` в режиме U выбирает команду с такой страницы и вызывает страничный отказ при выборке команды (причина 12); ядро отвечает сигналом `SIGSEGV`.
2. **Режим не сменился бы.** Даже если бы код удалось выбрать, он выполнялся бы в режиме U, где каждая привилегированная команда, которую он использует, вызвала бы исключение.
3. **Подошла бы любая точка входа.** `jal` может перейти по любому адресу, в том числе в середину функции, мимо кода, который проверяет аргументы.

Поэтому для запроса к ядру нужна команда, которая меняет режим и переходит по адресу, который программа не выбирает: ловушка. В RISC-V это `ecall`, в x86-64 — `syscall`, в Arm — `svc`. Сама ловушка не может передать, *какую* услугу хочет программа и с какими аргументами; об этом договариваются ядро и библиотека C, и эта договорённость — **ABI системных вызовов** (system-call ABI).

## Путь одного системного вызова \{#the-path-of-one-system-call\}

Программа hello-world из [первой заметки](/ru/notes/acos/computer-systems) заканчивается вызовом `write(1, buf, 13)`: записать 13 байт из `buf` в файловый дескриптор 1, стандартный вывод. В Linux на RISC-V вызов проходит так.

<SyscallPath />

1. **Вызов.** `main` вызывает `write`, как любую функцию C. По соглашению о вызовах три её аргумента уже лежат в `a0`, `a1` и `a2`. `write` — короткая функция в библиотеке C, **обёртка** (wrapper).
2. **Ловушка.** Обёртка кладёт номер системного вызова `write`, 64, в `a7` и выполняет `ecall`. Процессор записывает адрес `ecall` в `sepc` и причину 8 (вызов окружения из режима U, environment call from U-mode) в `scause`, переключается в режим S и переходит по адресу из `stvec`.
3. **Вход.** Код входа в ядро сохраняет все 31 пользовательский регистр на стеке ядра этого процесса и прибавляет 4 к сохранённому `sepc`, чтобы возврат пришёлся на команду после `ecall`, а не на неё саму.
4. **Диспетчеризация.** Номер из `a7` служит индексом в **таблице системных вызовов** (system-call table) ядра. Если он вне диапазона, результат — `-ENOSYS`; элемент 64 — это `sys_write` ([Linux, `arch/riscv/kernel/traps.c`](#references)).
5. **Услуга.** `sys_write(1, buf, 13)` проверяет, что дескриптор 1 открыт на запись и что 13 байт по адресу `buf` лежат в пользовательской памяти процесса, копирует их в ядро и передаёт драйверу терминала. Он возвращает 13. Путь выхода записывает 13 в сохранённый `a0`, восстанавливает регистры и выполняет `sret`, который возвращает в режим U по адресу из `sepc`.
6. **Результат.** Снова в обёртке: `a0` содержит 13, неотрицательное число, поэтому `write` возвращает его в `main`.

**Разобранный пример: тот же вызов без библиотеки.** Обёртка не делает ничего, чего программа не могла бы сделать сама. В Linux на RISC-V следующая программа печатает приветствие и завершается двумя «голыми» `ecall` и вообще без библиотеки C. Она работает только в Linux (номера и `ecall` ничего не значат для macOS). Собранная `clang` из LLVM командой из её второй строки и запущенная под `qemu-riscv64`, эмулятором RISC-V в пользовательском режиме, в контейнере Debian 13, она печатает `hello, world` и завершается с кодом 0; и её `_start` дизассемблируется в команды шагов 1 и 2: `auipc` и `addi` кладут адрес `msg` в `a1`, затем идут `li a2, 13`, `li a7, 64`, `li a0, 1` и `ecall`; ещё две команды превращают результат в код завершения, и `li a7, 93` предшествует второму `ecall`.

```c
// raw.c: Linux on RISC-V only, no C library; run under qemu-riscv64 in a Debian 13 container: prints hello, world, exit status 0.
// clang --target=riscv64-linux-gnu -O1 -ffreestanding -nostdlib -static -fuse-ld=lld raw.c -o raw
static long syscall3(long number, long arg0, long arg1, long arg2) {
    register long a0 __asm__("a0") = arg0;
    register long a1 __asm__("a1") = arg1;
    register long a2 __asm__("a2") = arg2;
    register long a7 __asm__("a7") = number;
    __asm__ volatile("ecall" : "+r"(a0) : "r"(a1), "r"(a2), "r"(a7) : "memory");
    return a0;                                    /* the result, or -errno */
}

void _start(void) {
    static const char msg[] = "hello, world\n";
    long n = syscall3(64, 1, (long)msg, 13);      /* write(1, msg, 13) */
    syscall3(93, n == 13 ? 0 : 1, 0, 0);          /* exit(0) if all 13 bytes were written */
}
```

<aside class="callout"><strong>Ключевая идея.</strong> Системный вызов — это вызов функции, разрезанный ловушкой на две половины. Половина программы (обёртка) кладёт в регистры номер и до шести аргументов и выполняет одну команду, вызывающую ловушку; половина ядра сохраняет регистры, ищет номер в таблице, проверяет каждый аргумент, выполняет работу и возвращает одно значение в регистре. Всё, о чём программа может попросить ядро, — это строка этой таблицы.</aside>

## Аргументы, номера и ошибки \{#arguments-numbers-and-errors\}

**Регистры.** Каждая архитектура фиксирует, где лежат номер, аргументы и результат ([Linux man-pages, syscall(2)](#references)):

| Архитектура | Команда | Номер в | Аргументы 1–6 в | Результат в |
| --- | --- | --- | --- | --- |
| RISC-V | `ecall` | `a7` | `a0`–`a5` | `a0` |
| arm64 | `svc #0` | `x8` | `x0`–`x5` | `x0` |
| x86-64 | `syscall` | `rax` | `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` | `rax` |

В RISC-V и arm64 аргументы системного вызова лежат ровно там же, где аргументы функции C, поэтому обёртке остаётся только задать номер. В x86-64 четвёртый аргумент переезжает из `rcx`, куда его кладёт вызов функции, в `r10`, потому что сама команда `syscall` записывает в `rcx` адрес возврата (а в `r11` — флаги). Ни один системный вызов не принимает больше шести аргументов; тем, которым нужно больше, передают указатель на структуру.

**Номера.** Номер вызова — часть ABI одного ядра на одной архитектуре. `write` имеет номер 64 на RISC-V и arm64, которые пользуются общей (generic) таблицей Linux, 1 на x86-64 и 4 в macOS, ядро которой нумерует вызовы в традиции BSD ([Linux `asm-generic/unistd.h`](#references); [XNU `syscalls.master`](#references)). Программа, скомпилированная для одной из этих систем, не может делать свои вызовы в другой, даже если набор команд тот же; это одна из причин, по которым исполняемые файлы привязаны к операционной системе, а не только к процессору. Библиотека C скрывает номера: программы вызывают `write`, а библиотека для каждой платформы знает номер.

**Ошибки.** Ядро никогда не устанавливает `errno`. При неудаче оно возвращает в регистре результата номер ошибки со знаком минус: −9 (`-EBADF`) для дескриптора, который не открыт, −14 (`-EFAULT`) для буфера вне памяти процесса. Допустимые результаты никогда не попадают в диапазон от −4095 до −1, поэтому обёртка может их различить: для значения из этого диапазона она записывает его модуль в `errno` и возвращает −1 ([Linux man-pages, intro(2)](#references)). Для вызывающего кода из этого следуют три правила:

- сначала проверять возвращаемое значение; `errno` что-то значит, только если вызов вернул −1;
- читать `errno` сразу, потому что следующий библиотечный вызов может его изменить;
- у каждого потока свой `errno` ([C17](#references), §7.5), так что потоки не видят ошибок друг друга.

**Разобранный пример.** `write(42, "x", 1)` в процессе, где нет дескриптора 42: ядро возвращает −9, обёртка устанавливает `errno = 9` и возвращает −1, а `strerror(9)` — это "Bad file descriptor". `write(1, (char *)1, 5)` указывает на буфер по адресу 1, который не отображён: проверка ядра не проходит ещё до того, как оно что-либо скопирует, оно возвращает −14, и программа видит −1 с `errno = 14`, "Bad address". Ядро не падает и не посылает сигнал: о недопустимом указателе, переданном в системный вызов, сообщается кодом ошибки, ловушки не происходит. Оба случая есть в разделе «Код», с одними и теми же номерами в macOS и в Linux.

<aside class="callout"><strong>Проверьте себя.</strong> (1) Программа на RISC-V выполняет <code>ecall</code> с <code>a7 = 999</code>. Что она получит? (2) Почему ядро не может просто доверять указателю <code>buf</code>, который получает от <code>write</code>?<details><summary>Ответы</summary>(1) В Linux нет вызова 999, поэтому диспетчеризация не находит элемента таблицы, и вызов возвращает <code>-ENOSYS</code> в <code>a0</code>; через универсальную функцию <code>syscall()</code> библиотеки C программа видит −1 и <code>errno</code>, равный <code>ENOSYS</code>, "Function not implemented". (2) Ядро работает с доступом ко всей памяти. Если бы оно копировало с любого переданного адреса, программа могла бы передать адрес данных ядра и записать их в файл; поэтому каждый указатель перед использованием проверяется на то, что он лежит в пользовательской части адресного пространства, а копирование идёт через функции, которые превращают отказ в <code>-EFAULT</code>.</details></aside>

## Сколько стоит системный вызов \{#what-a-system-call-costs\}

Вызов функции — это переход и возврат. Системный вызов добавляет ловушку, сохранение и восстановление регистров, проверку аргументов и диспетчеризацию, а на процессорах, уязвимых к Meltdown, ещё и переключение таблиц страниц при каждом входе и выходе, о котором [заметка об операционных системах](/ru/notes/acos/operating-systems) упоминала среди ограничений. Косвенную цену заметить труднее: код и данные ядра вытесняют строки программы из кэшей и её записи из TLB, поэтому после каждого вызова программа какое-то время работает медленнее.

Измерено на Apple M1 с macOS 26.5 и `clang -O2` (первая программа из раздела «Код», один запуск; числа меняются от запуска к запуску и от машины к машине):

| Операция | Время |
| --- | --- |
| пустой вызов функции (не встроенный) | 3.4 нс |
| `getppid()`, самый дешёвый системный вызов: он возвращает одно число | 149 нс |
| `write` 1 байта в `/dev/null`, который его отбрасывает | 516 нс |
| `pwrite` 1 байта в файл в страничном кэше (page cache) | 736 нс |

Самый дешёвый системный вызов стоит около 40 вызовов функций, а вызов, выполняющий реальную работу, — сотни. Постоянная часть не зависит от размера запроса, поэтому программа, которая передаёт много байтов за вызов, платит её редко.

<SyscallCost />

**Разобранный пример.** Запись 1 МиБ, 1 048 576 байт, в файл по одному байту за вызов требует 1 048 576 вызовов примерно по 736 нс: около 0.77 с. Запись кусками по 4 КиБ требует 256 вызовов по 824 нс: около 0.21 мс, примерно в 3700 раз быстрее, для тех же байтов. В расчёте на байт цена падает с 736 нс до 0.20 нс. После примерно 16 КиБ более крупные вызовы мало что дают: постоянная цена вызова размазана так тонко, что преобладает копирование байтов, около 0.026 нс на байт. [Заметка о файлах](/ru/notes/acos/files-and-io#buffering-fewer-and-larger-calls) строит то же рассуждение для чтения и показывает буферизацию, которую делает за нас библиотека C.

Некоторые услуги нужны так часто, что даже такую цену платить за них слишком дорого. Linux отображает в каждый процесс небольшую разделяемую библиотеку, **vDSO**, с функциями вроде `clock_gettime` и `gettimeofday`, которые читают данные, поддерживаемые ядром в актуальном состоянии на странице, доступной процессу для чтения; они возвращают время, вообще не входя в ядро ([Linux man-pages, vdso(7)](#references)).

## Наблюдение за системными вызовами: strace \{#watching-system-calls-strace\}

`strace` запускает программу и печатает каждый системный вызов, который она делает, с аргументами и результатом; `strace -c` вместо этого печатает сводную таблицу, `-e trace=write,read` ограничивает вывод некоторыми вызовами, а `-o file` отправляет его в файл вместо терминала ([strace(1)](#references)). Она пользуется отладочным интерфейсом ядра, `ptrace`, поэтому программу менять не нужно. Даже программа hello-world делает много вызовов до запуска `main`: `execve`, чтобы её запустить, затем `openat`, `mmap` и `mprotect` динамического компоновщика, чтобы загрузить библиотеку C, — это объясняет [следующая заметка](/ru/notes/acos/linking-and-loading).

Программа `order.c` из раздела «Код» вызывает `printf("A\n")`, затем `write(1, "B\n", 2)`, затем `printf("C\n")`. Трассировка в Linux, если оставить только `write`:

```text
# Только Linux: запущено в контейнере Debian 13 (glibc 2.41, strace, arm64).
$ strace -e trace=write -o trace.txt ./order          # стандартный вывод — терминал
$ cat trace.txt
write(1, "A\n", 2)                      = 2
write(1, "B\n", 2)                      = 2
write(1, "C\n", 2)                      = 2
+++ exited with 0 +++
$ strace -e trace=write -o trace.txt ./order > out.txt   # стандартный вывод — файл
$ cat trace.txt
write(1, "B\n", 2)                      = 2
write(1, "A\nC\n", 4)                   = 4
+++ exited with 0 +++
```

С терминалом каждый `printf` заканчивается собственным `write`. С файлом два `printf` дают один общий `write`, при выходе, и он идёт *после* прямого `write` строки B: файл содержит B, A, C. Почему — объясняет следующий раздел.

В macOS нет `strace`. Её аналог, `dtruss`, построен на DTrace, требует прав root и при включённой защите целостности системы (System Integrity Protection) не может трассировать большинство программ; поэтому опыты раздела «Код» с временем и порядком вывода запускаются там.

## write(2) напрямую против printf \{#write2-directly-versus-printf\}

`write` — это системный вызов: он принимает готовые байты и делает одну ловушку на вызов. `printf` — библиотечная функция, которая выполняет две работы в пространстве пользователя до всякого системного вызова. Она **форматирует**: `printf("%d", 13)` превращает целое число в символы `1` и `3`. И она **буферизует**: символы попадают в буфер в собственной памяти процесса, привязанный к `FILE` по имени `stdout`, а `write` вызывается, только когда буфер сбрасывается. Когда это происходит, зависит от того, к чему подключён стандартный вывод ([C17](#references), §7.21.3):

- терминал: **построчная буферизация** (line-buffered), сброс при каждом переводе строки, так что пользователь сразу видит каждую строку;
- файл или канал: **полная буферизация** (fully buffered), сброс при заполнении буфера (обычно 4 КиБ) или при `exit`, что даёт меньше всего вызовов;
- `stderr`: **без буферизации** (unbuffered), так что сообщения об ошибках появляются, даже если программа падает сразу после них.

`fflush(stdout)` принудительно сбрасывает буфер. Смешивая `printf` и `write` на одном дескрипторе, мы смешиваем буферизованный и небуферизованный пути, поэтому трассированная программа напечатала B первой, когда её вывод шёл в файл: A и C ещё ждали в буфере, когда B ушла прямо в ядро.

| | `write(fd, buf, n)` | `printf(fmt, ...)` |
| --- | --- | --- |
| Раздел руководства | 2: системный вызов | 3: библиотечная функция |
| Форматирование | нет: байты на входе, байты на выходе | превращает числа и строки в текст |
| Системные вызовы | ровно один на вызов | один на сброс: на строку, на буфер или при выходе |
| Ошибки | возвращает −1 и устанавливает `errno` | возвращает отрицательное число; ошибка может проявиться только при сбросе |
| Переносимость | POSIX | ISO C: любая размещённая (hosted) реализация C |

## Что изменилось \{#what-changed\}

| | Вызов функции | Системный вызов |
| --- | --- | --- |
| Команда | `jal` по любому адресу | `ecall`; цель выбрало ядро в `stvec` |
| Режим | остаётся режим U | U → S, и обратно через `sret` |
| Какой код выполняется | по адресу из команды | по номеру из `a7`, найденному в таблице ядра |
| Аргументы | принимаются на веру | проверяются: каждый дескриптор и каждый указатель |
| Ошибки | как решит функция | `-errno` от ядра, −1 и `errno` от обёртки |
| Цена на M1 | около 3 нс | около 150 нс для самого дешёвого, сотни для реальной работы |

## Ограничения \{#limitations\}

- **Каждый вызов — путь туда и обратно.** Программы, которые делают много мелких вызовов, тратят время на вход в ядро и выход из него; пакетная обработка (буферы, `readv`/`writev`, асинхронные интерфейсы вроде `io_uring` в Linux) существует, чтобы распределить эту цену.
- **Интерфейс свой у каждого ядра и каждой архитектуры.** Номера, структуры и отчасти семантика различаются в Linux, macOS и Windows; переносимые программы работают через библиотеку C и POSIX, которые скрывают часть различий, но не все.
- **Вызовы могут блокироваться.** `read` из канала или сокета ждёт, пока придут данные; процесс спит, и программе, которая должна оставаться отзывчивой, нужны потоки или неблокирующие дескрипторы.
- **Проверки хороши лишь настолько, насколько удачен момент.** Если ядро проверяет значение в пользовательской памяти и позже читает его снова, другой поток может изменить его в промежутке (ошибка *time-of-check to time-of-use*, между моментом проверки и моментом использования); ядра копируют аргументы в память ядра один раз и работают только с копией.
- **Трассировка стоит времени и требует прав.** `strace` останавливает программу на каждом вызове и поэтому заметно её замедляет; в macOS аналогу нужны права root, и его ограничивает System Integrity Protection.

## Что нужно запомнить \{#what-you-should-remember\}

- Системный вызов — это ловушка с номером и аргументами в регистрах: в Linux на RISC-V номер в `a7`, аргументы в `a0`–`a5`, `ecall`, результат в `a0`. `write` — это 64 (RISC-V, arm64), 1 (x86-64), 4 (macOS).
- Обёртка библиотеки C задаёт номер и выполняет ловушку; ядро сохраняет регистры, сдвигает `sepc` за `ecall`, обращается по индексу к таблице системных вызовов, проверяет аргументы, выполняет работу и возвращается через `sret`.
- При неудаче ядро возвращает `-errno`; обёртка превращает результат из диапазона −4095…−1 в −1 и устанавливает `errno`. Сначала проверяется возвращаемое значение, потом `errno`.
- На M1: вызов функции около 3 нс, `getppid` около 150 нс, запись 1 байта 0.5–0.7 мкс. Передавать нужно много байтов за вызов: 1 МиБ записями по 4 КиБ примерно в 3700 раз быстрее, чем побайтно.
- `strace` показывает каждый системный вызов; `printf` буферизует в пространстве пользователя (построчно на терминале, полностью в остальных случаях), `write` идёт прямо в ядро.

## Код \{#code\}

Цена вызова функции, самого дешёвого системного вызова и записей растущего размера; числа в комментариях — один запуск на Apple M1 (macOS 26.5, Apple clang 21), между запусками они меняются на десятки процентов:

```c
// cost.c: clang -std=c17 -Wall -Wextra -O2 cost.c -o cost && ./cost
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}
static int cmp(const void *a, const void *b) {
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}
__attribute__((noinline)) static int empty(int x) { __asm__ volatile(""); return x + 1; }

int main(void) {
    enum { N = 1000000 };
    volatile long sink = 0;
    int null = open("/dev/null", O_WRONLY);
    static char buf[1 << 16];

    double t0 = now();
    for (int i = 0; i < N; i++) sink += empty(i);           /* an ordinary function call */
    double t1 = now();
    for (int i = 0; i < N; i++) sink += getppid();          /* the cheapest system call */
    double t2 = now();
    for (int i = 0; i < N; i++) sink += write(null, buf, 1); /* write 1 byte, discarded */
    double t3 = now();
    printf("call %.1f ns, getppid %.0f ns, write to /dev/null %.0f ns\n",
           (t1 - t0) / N * 1e9, (t2 - t1) / N * 1e9, (t3 - t2) / N * 1e9);

    /* rewrite the same 1 MiB of a file in chunks of B bytes; median of 9 repetitions */
    const long total = 1 << 20;
    int fd = open("cost.tmp", O_RDWR | O_CREAT | O_TRUNC, 0600);
    for (long off = 0; off < total; off += sizeof buf) pwrite(fd, buf, sizeof buf, off);
    for (long b = 1; b <= 65536; b *= 4) {
        double t[9];
        for (int r = 0; r < 9; r++) {
            double s = now();
            for (long off = 0; off < total; off += b) pwrite(fd, buf, b, off);
            t[r] = now() - s;
        }
        qsort(t, 9, sizeof t[0], cmp);
        printf("B = %5ld: %6.0f ns per call, %8.3f ns per byte\n", b, t[4] / (total / b) * 1e9, t[4] / total * 1e9);
    }
    close(fd);
    unlink("cost.tmp");
    return 0;
}
// call 3.4 ns, getppid 149 ns, write to /dev/null 516 ns
// B =     1:    736 ns per call,  735.963 ns per byte
// B =     4:    736 ns per call,  184.042 ns per byte
// B =    16:    745 ns per call,   46.540 ns per byte
// B =    64:    745 ns per call,   11.648 ns per byte
// B =   256:    747 ns per call,    2.916 ns per byte
// B =  1024:    757 ns per call,    0.739 ns per byte
// B =  4096:    824 ns per call,    0.201 ns per byte
// B = 16384:   1078 ns per call,    0.066 ns per byte
// B = 65536:   2437 ns per call,    0.037 ns per byte
```

`write`, `read` и `getpid`, а также две ошибки из разобранного примера:

```c
// calls.c: clang -std=c17 -Wall -Wextra -O0 calls.c -o calls && echo "abc" | ./calls
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void) {
    /* write(2): file descriptor 1 is standard output; the result is the number of bytes written */
    const char msg[] = "hello, world\n";
    ssize_t n = write(1, msg, strlen(msg));

    /* read(2): up to 64 bytes from standard input; 0 would mean end of input */
    char line[64];
    ssize_t got = read(0, line, sizeof line);

    /* getpid(2): no arguments, cannot fail */
    pid_t pid = getpid();

    /* errors: the wrapper returns -1 and leaves the error number in errno */
    ssize_t bad_fd = write(42, "x", 1);              /* descriptor 42 is not open */
    int e1 = errno;
    ssize_t bad_buf = write(1, (const char *)1, 5);  /* address 1 is not mapped */
    int e2 = errno;

    printf("write -> %zd, read -> %zd, getpid > 1: %d\n", n, got, pid > 1);
    printf("write(42, ...) -> %zd, errno %d (%s)\n", bad_fd, e1, strerror(e1));
    printf("write(1, (char *)1, 5) -> %zd, errno %d (%s)\n", bad_buf, e2, strerror(e2));
    return 0;
}
// hello, world
// write -> 13, read -> 4, getpid > 1: 1                     ("abc" and the newline: 4 bytes)
// write(42, ...) -> -1, errno 9 (Bad file descriptor)
// write(1, (char *)1, 5) -> -1, errno 14 (Bad address)
```

Буферизованный и небуферизованный вывод на одном дескрипторе:

```c
// order.c: clang -std=c17 -Wall -Wextra -O0 order.c -o order && ./order && ./order | cat
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("A\n");          /* into the stdio buffer */
    write(1, "B\n", 2);     /* straight to the kernel */
    printf("C\n");          /* into the stdio buffer */
    return 0;               /* exit flushes the buffer */
}
// ./order on a terminal prints A, B, C on three lines (line-buffered: each printf flushes at its newline)
// ./order | cat prints B, A, C (fully buffered: A and C leave the buffer together at exit)
```

В RARS `ecall` попадает в симулятор, который играет роль ядра: номер в `a7` выбирает услугу так же, как в Linux, но из собственной таблицы RARS. Проверено интерпретатором RV32 курса:

```asm
# ecall в RARS: симулятор играет роль ядра. a7 выбирает услугу, a0 передаёт аргумент.
    .data
msg:    .asciz "hello, world\n"
    .text
main:
    la   a0, msg
    li   a7, 4          # PrintString: напечатать строку с нулём в конце по адресу a0
    ecall
    li   a0, 13
    li   a7, 1          # PrintInt: напечатать a0 в десятичной записи
    ecall
    li   a0, '\n'
    li   a7, 11         # PrintChar
    ecall
    li   a0, 0
    li   a7, 93         # Exit2: завершить программу с кодом a0 (93 — это и exit в Linux)
    ecall
# hello, world
# 13
```

## Дальше \{#next\}

[Следующая заметка](/ru/notes/acos/linking-and-loading) прослеживает это имя: как компоновщик соединяет объектные файлы и библиотеки и вписывает адреса в код, как разделяемая библиотека C находится и связывается во время выполнения через PLT и GOT и как ядро и динамический компоновщик загружают результат в новый процесс.
