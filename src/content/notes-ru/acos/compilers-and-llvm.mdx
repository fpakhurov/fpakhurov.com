[Предыдущая заметка](/ru/notes/acos/language-runtimes) закончилась циклом на C, который компилятор удалил: при `-O2` обратный отсчёт на 20 миллионов итераций не занял никакого времени, потому что компилятор заранее вычислил его результат. Эта последняя заметка открывает компилятор. Она прослеживает одну маленькую функцию на C через LLVM — инфраструктуру компиляции, на которой построены Clang, Rust, Swift и многие другие языки: от текста к токенам и синтаксическому дереву, в промежуточное представление в форме статического единственного присваивания, через оптимизирующие проходы, которые его переписывают, и на выходе — к командам RISC-V того рода, что [ассемблерный раздел](/ru/notes/acos/processor-and-isa) курса писал вручную. Заметка заканчивается объяснением, почему LLVM устроен именно так, и курсом в одном абзаце.

**Обозначения.** IR — **промежуточное представление** (intermediate representation) компилятора: программа в том виде, в каком компилятор держит её между исходным кодом и машинным кодом. SSA — форма **статического единственного присваивания** (static single assignment). **Проход** (pass) — один шаг компилятора, который читает IR и пишет IR. LLVM IR показан так, как его печатает LLVM: `%name` — значение, `i32` — 32-битное целое, `ptr` — указатель, а метка с двоеточием начинает базовый блок.

Сквозной пример — сумма $1 + 2 + \dots + n$:

```c
int sum_to(int n) {
    int s = 0;
    for (int i = 1; i <= n; i++)
        s += i;
    return s;
}
```

## Отправная точка: свой компилятор для каждого языка и процессора \{#baseline-one-compiler-for-each-language-and-processor\}

Простейший компилятор переводит один язык прямо в ассемблер одного процессора: он читает функцию на C выше и печатает команды RISC-V, так же как ассемблерные заметки переводили C вручную. Такой компилятор — одна программа без видимых этапов, и для одной пары он работает. Он ломается двумя способами.

1. **Пары размножаются.** При $M$ языках и $N$ процессорах нужно написать $M \times N$ компиляторов, и каждый повторяет одну и ту же работу: синтаксический анализатор C пишется заново для каждого процессора, таблицы команд RISC-V — для каждого языка. Трём языкам и трём процессорам уже нужно девять компиляторов, десяти и десяти — сто.
2. **Оптимизации негде жить.** Улучшения вроде хранения переменных в регистрах, заблаговременного вычисления констант или выноса работы из циклов одинаковы для всех языков и почти одинаковы для всех процессоров. В компиляторе, построенном для одной пары, их пишут заново в каждом — или не пишут вовсе.

## Конвейер \{#the-pipeline\}

<aside class="callout"><strong>Ключевая идея.</strong> Поставить в середину одно представление. **Фронтенд** (front end) для каждого языка переводит исходный код в общее IR; **оптимизатор** (optimizer) переписывает IR в лучшее IR последовательностью независимых проходов, которые ничего не знают ни об исходном языке, ни о целевой платформе; **бэкенд** (back end) для каждого процессора переводит IR в машинный код. Тогда $M$ языкам и $N$ процессорам нужно $M + N$ частей вместо $M \times N$ компиляторов, и каждая оптимизация пишется один раз и служит всем.</aside>

<CompilerPipeline />

1. **Фронтенды.** Clang для C, C++ и Objective-C, rustc для Rust, swiftc для Swift: каждый разбирает свой язык, проверяет его и выдаёт LLVM IR.
2. **Одно IR.** LLVM IR — типизированный низкоуровневый язык команд над значениями в форме SSA. Оно существует как структуры данных в памяти, как читаемый текст (файлы `.ll`) и как компактный двоичный *биткод* (bitcode, `.bc`).
3. **Оптимизатор.** Конвейер проходов, каждый — функция из IR в IR. Конвейер `-O2` запускает десятки проходов, некоторые по несколько раз.
4. **Бэкенды.** По одному на семейство процессоров: x86-64, AArch64, RISC-V, GPU и другие. Каждый выбирает машинные команды, назначает регистры, упорядочивает команды и выдаёт ассемблерный код или объектный файл.
5. **Подсчёт.** 3 языкам и 3 целевым платформам нужно $3 + 3 = 6$ частей вместо $3 \times 3 = 9$ компиляторов; 10 и 10 — 20 вместо 100.

Команда `clang` — **драйвер** (driver), который запускает эти этапы, а затем ассемблер и компоновщик из [заметки о компоновке](/ru/notes/acos/linking-and-loading). Он печатает свой план с `-ccc-print-phases` (LLVM 17, вывод сокращён до этапов):

```text
$ clang -ccc-print-phases -c sum.c
            +- 0: input, "sum.c", c
         +- 1: preprocessor, {0}, cpp-output
      +- 2: compiler, {1}, ir
   +- 3: backend, {2}, assembler
+- 4: assembler, {3}, object
```

## Фронтенд: от текста к IR \{#the-front-end-from-text-to-ir\}

Фронтенд работает в четыре шага, все внутри Clang.

1. **Препроцессирование** вставляет файлы из `#include` и раскрывает макросы, как в [заметке о C](/ru/notes/acos/c-for-systems-programming).
2. **Лексический анализ** (lexical analysis) разрезает текст на **токены** (tokens). Оператор `s += i;` превращается в четыре: `identifier 's'`, `plusequal '+='`, `identifier 'i'`, `semi ';'` (вывод `clang -fsyntax-only -Xclang -dump-tokens`).
3. **Синтаксический анализ** (parsing) строит из токенов по грамматике C **абстрактное синтаксическое дерево** (abstract syntax tree, AST): функцию `sum_to`, тело которой содержит объявление, оператор `for`, телом которого служит составное присваивание, и `return`.
4. **Семантический анализ** (semantic analysis) проверяет дерево по правилам, которые грамматика выразить не может: каждое имя объявлено, `s += i` складывает два `int`, возвращаемое значение имеет объявленный тип. Ошибки и предупреждения появляются здесь, со строкой и столбцом проблемного токена.

Затем **генерация кода** (code generation) обходит AST и выдаёт IR. При `-O0` Clang идёт самым простым корректным путём: каждая локальная переменная получает ячейку на стеке (`alloca`), каждое использование читает её, а каждое присваивание записывает. Чтобы увидеть это IR, его нужно выдать без оптимизации и без атрибута `optnone`, который не дал бы последующим проходам его трогать (всё IR в этой заметке получено в LLVM 17 для цели `riscv32` с сохранением имён значений):

```llvm
define dso_local i32 @sum_to(i32 noundef %n) #0 {
entry:
  %n.addr = alloca i32, align 4
  %s = alloca i32, align 4
  %i = alloca i32, align 4
  store i32 %n, ptr %n.addr, align 4
  store i32 0, ptr %s, align 4
  store i32 1, ptr %i, align 4
  br label %for.cond

for.cond:                                         ; preds = %for.inc, %entry
  %0 = load i32, ptr %i, align 4
  %1 = load i32, ptr %n.addr, align 4
  %cmp = icmp sle i32 %0, %1
  br i1 %cmp, label %for.body, label %for.end

for.body:                                         ; preds = %for.cond
  %2 = load i32, ptr %i, align 4
  %3 = load i32, ptr %s, align 4
  %add = add nsw i32 %3, %2
  store i32 %add, ptr %s, align 4
  br label %for.inc

for.inc:                                          ; preds = %for.body
  %4 = load i32, ptr %i, align 4
  %inc = add nsw i32 %4, 1
  store i32 %inc, ptr %i, align 4
  br label %for.cond, !llvm.loop !4

for.end:                                          ; preds = %for.cond
  %5 = load i32, ptr %s, align 4
  ret i32 %5
}
```

Функция разбита на **базовые блоки** (basic blocks): линейные последовательности команд, в которые входят только сверху и из которых выходят только через последнюю команду — переход (`br`) или возврат (`ret`). Цикл `for` стал четырьмя блоками: заголовком с проверкой (`for.cond`), телом, приращением и выходом — та же форма, что у циклов из [заметки об управлении потоком](/ru/notes/acos/control-flow-and-memory). `icmp sle` — знаковое сравнение «меньше или равно»; `nsw` («no signed wrap», без знакового переполнения) фиксирует, что в C знаковое переполнение — неопределённое поведение, так что оптимизатор может считать, что его никогда не бывает. Clang служит основой и для других инструментов, которым нужен корректный синтаксический анализатор C: статического анализатора Clang (Clang Static Analyzer), который исследует пути выполнения функции в поисках ошибок вроде разыменования нулевого указателя, и `clang-tidy`, который проверяет стиль и типичные ошибки.

## LLVM IR и SSA \{#llvm-ir-and-ssa\}

В IR выше `%s` обозначает ячейку памяти, в которую записывают дважды, и чтобы узнать, какую запись видит чтение, нужно следить за потоком управления. Форма **статического единственного присваивания** снимает этот вопрос: каждое значение присваивается ровно один раз, в одном месте текста программы, так что каждое использование называет ровно одно определение ([Cytron et al., 1991](#references)). Изменяющаяся переменная превращается в несколько значений. Там, где потоки управления сходятся и переменная может иметь одно из нескольких значений, SSA ставит в начало блока **φ-узел** (phi node, записывается `phi`), который выбирает значение в зависимости от блока, из которого пришло управление.

Проход **mem2reg** превращает ячейки на стеке из IR при `-O0` в значения SSA. Он применим к ячейке, адрес которой никуда не утекает, — здесь это верно для всех трёх, — и ставит φ-узлы там, где встречаются определения с разных путей. После `opt -passes=mem2reg`:

```llvm
define dso_local i32 @sum_to(i32 noundef %n) #0 {
entry:
  br label %for.cond

for.cond:                                         ; preds = %for.inc, %entry
  %s.0 = phi i32 [ 0, %entry ], [ %add, %for.inc ]
  %i.0 = phi i32 [ 1, %entry ], [ %inc, %for.inc ]
  %cmp = icmp sle i32 %i.0, %n
  br i1 %cmp, label %for.body, label %for.end

for.body:                                         ; preds = %for.cond
  %add = add nsw i32 %s.0, %i.0
  br label %for.inc

for.inc:                                          ; preds = %for.body
  %inc = add nsw i32 %i.0, 1
  br label %for.cond, !llvm.loop !4

for.end:                                          ; preds = %for.cond
  ret i32 %s.0
}
```

Все `alloca`, `load` и `store` исчезли: кроме четырёх переходов и возврата, в функции теперь 5 команд вместо 17. Метка `!llvm.loop` прикрепляет к циклу метаданные и не влияет на его смысл.

<SsaLoop />

1. `entry` переходит к заголовку цикла.
2. В `for.cond` φ-узел `%s.0` равен 0, когда управление приходит из `entry`, и `%add`, когда оно возвращается из `for.inc`; `%i.0` аналогично равен 1 или `%inc`. Затем идут сравнение и переход.
3. `for.body` вычисляет новую сумму и даёт ей новое имя, `%add`.
4. `for.inc` вычисляет новый счётчик, `%inc`, и возвращается по обратной дуге (back edge).
5. `for.end` возвращает `%s.0` — значение, которое заголовок выбрал последним.

**Разобранный пример.** При $n = 3$ управление входит в `for.cond` четыре раза. Пары $(\%i.0, \%s.0)$ равны $(1, 0)$ из `entry`, затем $(2, 1)$, $(3, 3)$ и $(4, 6)$ из `for.inc`. Сравнения $1 \le 3$, $2 \le 3$, $3 \le 3$ выполняются, а $4 \le 3$ — нет, так что функция возвращает 6.

SSA делает многие вопросы дешёвыми. У каждого значения одно определение, поэтому оптимизатор может пройти от значения к его использованиям и обратно, не анализируя поток управления; значение без использований мертво и может быть удалено; значение, вычисленное из констант, — константа. Большинство оптимизаций LLVM написаны над SSA.

## Оптимизатор: проходы \{#the-optimizer-passes\}

Проход читает IR и либо вычисляет факты о нём (**анализ**, analysis: доминаторы, циклы, псевдонимы указателей), либо переписывает его (**преобразование**, transformation: mem2reg, свёртка констант, встраивание функций, развёртывание циклов). Уровни `-O1`, `-O2`, `-O3` и `-Os` — фиксированные последовательности проходов. Если запустить конвейер `-O2` на IR, полученном при `-O0`, командой `opt -passes='default<O2>' -print-changed=quiet`, она перечислит по порядку проходы, изменившие эту функцию: SimplifyCFG, SROA, GlobalOpt, InstCombine, Reassociate, LCSSA, LoopRotate, SimplifyCFG, InstCombine, LoopSimplify, LCSSA, IndVarSimplify, GVN, CorrelatedValuePropagation и PostOrderFunctionAttrs. Внутри конвейера `-O2` работу mem2reg выполняет **SROA** (scalar replacement of aggregates, скалярная замена агрегатов), и не только её: он ещё и разбивает структуры на отдельные скаляры.

Решающий проход — **IndVarSimplify**. Он использует **скалярную эволюцию** (scalar evolution) — анализ, который описывает, как значение меняется от одной итерации цикла к следующей. Здесь `%i.0` начинается с 1 и растёт на 1, а `%s.0` начинается с 0 и растёт на `%i.0` — это сумма арифметической прогрессии, значение которой после цикла выражается в замкнутой форме. Проход вычисляет конечное значение `s` без цикла; после этого цикл больше ни на что не влияет, и **LoopDeletion** его удаляет. Результат после оставшихся проходов:

```llvm
define dso_local i32 @sum_to(i32 noundef %n) local_unnamed_addr #0 {
entry:
  %cmp.not4 = icmp slt i32 %n, 1
  br i1 %cmp.not4, label %for.end, label %for.body.preheader

for.body.preheader:                               ; preds = %entry
  %0 = shl nuw i32 %n, 1
  %1 = add nsw i32 %n, -1
  %2 = zext i32 %1 to i33
  %3 = add nsw i32 %n, -2
  %4 = zext i32 %3 to i33
  %5 = mul i33 %2, %4
  %6 = lshr i33 %5, 1
  %7 = trunc i33 %6 to i32
  %8 = add i32 %0, %7
  %9 = add i32 %8, -1
  br label %for.end

for.end:                                          ; preds = %for.body.preheader, %entry
  %s.0.lcssa = phi i32 [ 0, %entry ], [ %9, %for.body.preheader ]
  ret i32 %s.0.lcssa
}
```

При $n \ge 1$ функция теперь возвращает $2n + (n-1)(n-2)/2 - 1$ (`shl` на 1 удваивает, `lshr` на 1 делит пополам). Это знакомая формула:

$$
\begin{aligned}
2n + \frac{(n-1)(n-2)}{2} - 1 &= \frac{4n - 2 + n^2 - 3n + 2}{2} && \text{общий знаменатель, раскрываем } (n-1)(n-2) \\
&= \frac{n(n+1)}{2} && \text{приводим подобные.}
\end{aligned}
$$

**Разобранный пример.** При $n = 3$: $2 \cdot 3 + (2 \cdot 1)/2 - 1 = 6 + 1 - 1 = 6$ — значение из трассы выше. Почему именно такая форма, с 33-битным типом (`i33`)? Скалярная эволюция вычисляет замкнутую форму так, чтобы она совпадала с 32-битной арифметикой цикла при любом $n$, включая значения, при которых сумма переполняется и оборачивается. Произведение, поделённое пополам после усечения до 32 бит, потеряло бы свой старший бит, поэтому $(n-1)(n-2)$ вычисляется по модулю $2^{33}$, делится пополам и только потом усекается обратно до 32 бит. При $n \le 65\,535$, когда сумма $n(n+1)/2$ помещается в знаковый 32-битный `int`, произведение тоже случайно помещается в 32 бита, но проход на это не полагается. При $n = 70\,000$ произведение $69\,999 \times 69\,998 = 4\,899\,790\,002$ больше $2^{32}$, и только 33-битная версия совпадает с обёрнутой суммой цикла. Раздел «Код» проверяет оба утверждения.

## Бэкенд: команды и регистры \{#the-back-end-instructions-and-registers\}

Бэкенд превращает IR в команды одного процессора за три основных шага ([Aho et al.](#references), глава 8).

1. **Выбор команд** (instruction selection) отображает операции IR на команды целевой платформы, сопоставляя шаблоны: `add` регистра и константы становится `addi`, `icmp`, питающий `br`, становится одним условным переходом, например `bge`. LLVM делает это в основном на графе для каждого базового блока (SelectionDAG); некоторые платформы используют более новую систему, GlobalISel.
2. **Распределение регистров** (register allocation) отображает неограниченное число значений SSA на 31 доступный регистр RISC-V. Двум значениям, живым одновременно, нужны разные регистры; если одновременно живо больше значений, чем есть регистров, некоторые **вытесняются** (spill) в ячейки на стеке и загружаются обратно. Классическая постановка раскрашивает граф, вершины которого — значения, а рёбра соединяют значения, живые одновременно ([Chaitin, 1982](#references)); распределитель LLVM по умолчанию при `-O1` и выше, жадный (greedy), разбивает интервалы жизни значений и назначает их в порядке приоритета. Здесь исчезают φ-узлы: φ означает «один и тот же регистр на каждом входящем ребре» плюс пересылку там, где это невозможно.
3. **Планирование команд** (instruction scheduling) упорядочивает команды так, чтобы избежать простоев конвейера из [заметки о конвейере](/ru/notes/acos/pipelining), например отодвигая загрузку от команды, которая использует её результат. Затем ассемблер кодирует каждую команду, как в [заметке о кодировании](/ru/notes/acos/risc-v-instructions).

**Разобранный пример.** Одна и та же функция на трёх этапах, скомпилированная для RV32IM (LLVM 17; директивы ассемблера опущены). Если компилировать прямо из IR при `-O0`, каждая переменная живёт в своей ячейке на стеке, каждое использование — это `lw`, а каждое присваивание — `sw`; один только блок тела цикла выглядит так (комментарии добавлены):

```text
.LBB0_2:
	lw	a1, -20(s0)          # i
	lw	a0, -16(s0)          # s
	add	a0, a0, a1
	sw	a0, -16(s0)          # s = s + i
	j	.LBB0_3
```

Из формы SSA без оптимизации IR (`llc -O2` на выходе mem2reg, комментарии опущены) распределитель регистров помещает `%s.0` в `a1`, а `%i.0` в `a2`, и цикл занимает три команды без обращений к памяти:

```text
	li	a1, 0
	li	a2, 1
	blt	a0, a2, .LBB0_2
.LBB0_1:
	add	a1, a1, a2
	addi	a2, a2, 1
	bge	a0, a2, .LBB0_1
.LBB0_2:
	mv	a0, a1
	ret
```

Бэкенд к тому же перевернул цикл: проверка переехала вниз, так что каждая итерация выполняет один переход вместо двух. С полным конвейером `-O2` цикла нет вовсе, а 33-битное произведение собирается из младшей (`mul`) и старшей (`mulhu`) половин 64-битного произведения:

```text
	blez	a0, .LBB0_2
	slli	a1, a0, 1            # 2n
	addi	a2, a0, -1           # n - 1
	addi	a0, a0, -2           # n - 2
	mul	a3, a2, a0           # младшие 32 бита (n-1)(n-2)
	mulhu	a0, a2, a0           # старшие 32 бита
	slli	a0, a0, 31
	srli	a3, a3, 1
	or	a0, a0, a3           # биты с 1 по 32 произведения: (n-1)(n-2)/2
	add	a0, a0, a1
	addi	a0, a0, -1
	ret
.LBB0_2:
	li	a0, 0
	ret
```

Во всех трёх версиях аргумент приходит в `a0`, и результат уходит в `a0`, как требует [соглашение о вызовах](/ru/notes/acos/procedures-and-the-stack); это соглашение — договор, который позволяет коду из разных компиляторов вызывать друг друга.

## Почему важна модульная архитектура \{#why-the-modular-design-matters\}

[Lattner and Adve (2004)](#references) построили LLVM вокруг одной идеи: единое низкоуровневое типизированное представление в форме SSA, не зависящее от языка и сохраняемое на протяжении всей жизни программы, чтобы её можно было анализировать и оптимизировать во время компиляции, во время компоновки по всем файлам сразу, между запусками по профилям и во время работы программы. Каждая из этих возможностей стала обычной практикой:

- **Оптимизация во время компоновки** (link-time optimization). С `-flto` объектные файлы содержат биткод LLVM вместо машинного кода, и компоновщик запускает оптимизатор над всей программой сразу, так что функцию из одного файла можно встроить в другой.
- **Новые языки получают полный компилятор.** Автор языка пишет фронтенд, выдающий LLVM IR, и наследует оптимизатор и все бэкенды. Так построены Rust, Swift, Julia и Zig.
- **Новые процессоры получают все языки.** Бэкенд для RISC-V сразу делает C, C++, Rust и остальные языки доступными на RISC-V, с тем же оптимизатором за ними.
- **То же IR питает другие машины.** Бэкенды для GPU NVIDIA и AMD компилируют ядра, написанные на CUDA, OpenCL или Triton — языке для написания слитых GPU-ядер, на которых держатся методы вроде поблочного внимания из [заметки об эффективных трансформерах](/ru/notes/nlp/efficient-transformers); Triton понижает свои программы через MLIR до LLVM IR, а оттуда — до кода GPU ([Tillet et al., 2019](#references)).
- **JIT-компиляторы используют его повторно.** JIT-компиляторы из предыдущей заметки могут строиться на библиотеках LLVM: Julia компилирует каждую функцию с помощью LLVM при первом вызове с данными типами аргументов.

У этой архитектуры есть цена. IR не полностью независимо от целевой платформы: фронтенд уже должен знать размеры типов и соглашение о вызовах цели, поэтому IR, которое Clang выдаёт для RISC-V, нельзя скомпилировать для x86-64. А большой общий оптимизатор медленно работает и медленно меняется, поэтому быстрые JIT часто пишут собственные, более простые бэкенды.

## Что изменилось \{#what-changed\}

| | Свой компилятор для каждого языка и процессора (отправная точка) | LLVM |
| --- | --- | --- |
| Компоненты для $M$ языков и $N$ процессоров | $M \times N$ компиляторов | $M$ фронтендов + 1 оптимизатор + $N$ бэкендов |
| Где живут оптимизации | в каждом компиляторе, если вообще есть | один раз, как проходы над общим IR |
| Представление программы | на входе текст, на выходе ассемблер | AST, затем LLVM IR в форме SSA, затем машинные команды |
| `sum_to` при `-O0` и `-O2` | цикл, который на каждом шаге читает и пишет память | цикл в регистрах или вовсе без цикла |
| Анализ по всем файлам | нет | оптимизация во время компоновки над биткодом |

## Ограничения \{#limitations\}

- Заметка показывает LLVM. GCC следует тому же плану со своими IR (GIMPLE в форме SSA и RTL), и идеи там те же.
- IR несёт размеры типов и соглашение о вызовах целевой платформы, поэтому оно переносимо между компиляторами, но не между процессорами.
- Оптимизации опираются на правила языка. Флаг `nsw` выше безопасен только потому, что знаковое переполнение в C не определено; программу на C, которая всё же переполняется, компилятор может «неправильно скомпилировать» так, что это удивит её автора.
- Конвейер проходов — эвристика: проход, который помогает одной программе, может замедлить другую, а конвейер `-O2` меняется от версии к версии LLVM, так что напечатанное здесь IR в другой версии будет отличаться в деталях.
- Теория синтаксического анализа, AST языка C++, анализ псевдонимов, векторизация циклов и остальная часть оптимизатора выходят за рамки этой заметки.

## Что нужно запомнить \{#what-you-should-remember\}

- Компилятор — это конвейер: фронтенд (препроцессирование, токены, AST, семантические проверки, генерация IR), оптимизатор (проходы из IR в IR), бэкенд (выбор команд, распределение регистров, планирование, выдача кода). Одно общее IR превращает $M \times N$ компиляторов в $M + N$ частей.
- LLVM IR — типизированный низкоуровневый язык, разбитый на базовые блоки. Clang при `-O0` держит каждую переменную в ячейке на стеке (`alloca`, `load`, `store`).
- В форме SSA каждое значение определяется один раз; φ-узлы сливают значения в точках, где сходятся потоки управления. mem2reg строит SSA из ячеек на стеке.
- Оптимизация — это последовательность проходов. На `sum_to` проход IndVarSimplify со скалярной эволюцией заменил цикл замкнутой формой $n(n+1)/2$, вычисленной в 33 битах, чтобы совпасть с 32-битным результатом цикла.
- Распределение регистров отображает неограниченное число значений на регистры процессора и вытесняет остальное в память; соглашение о вызовах закрепляет, куда попадают аргументы и результаты.

## Курс в одном абзаце \{#the-course-in-one-paragraph\}

Курс проследил одну программу от битов её данных до процесса, общающегося по сети, и обратно — до компилятора, который её создал. Числа — это [биты](/ru/notes/acos/data-representation): целые в дополнительном коде и в определённом порядке байтов, вещественные — в формате [с плавающей точкой](/ru/notes/acos/floating-point) с его округлением. [Процессор](/ru/notes/acos/processor-and-isa) исполняет набор команд — договор между аппаратурой и программами, — чьи [кодировки](/ru/notes/acos/risc-v-instructions), [ветвления и обращения к памяти](/ru/notes/acos/control-flow-and-memory) и [процедуры и стек](/ru/notes/acos/procedures-and-the-stack) в RISC-V мы писали и запускали вручную. Память медленнее процессора, поэтому [кэши](/ru/notes/acos/caches) держат используемые данные рядом с ним, а [виртуальная память](/ru/notes/acos/virtual-memory) даёт каждой программе собственное частное адресное пространство. Внутри процессора [конвейер](/ru/notes/acos/pipelining) совмещает выполнение команд, [исключения и прерывания](/ru/notes/acos/exceptions-and-interrupts) прерывают последовательность, чтобы передать управление ядру, а [устройства ввода-вывода](/ru/notes/acos/input-and-output) переносят данные внутрь и наружу. Производительность даёт параллелизм на всех уровнях — [на уровне команд](/ru/notes/acos/instruction-level-parallelism), [на уровне потоков](/ru/notes/acos/thread-level-parallelism) и [на уровне данных](/ru/notes/acos/data-level-parallelism), — [код, считающийся с иерархией памяти](/ru/notes/acos/performance-optimization), и в конце концов [аппаратура, специализированная под одну предметную область](/ru/notes/acos/domain-specific-architectures). [Операционная система](/ru/notes/acos/operating-systems) превращает эту машину в безопасную и разделяемую: программы, написанные на [C](/ru/notes/acos/c-for-systems-programming), просят у неё услуг через [системные вызовы](/ru/notes/acos/system-calls), [компонуются и загружаются](/ru/notes/acos/linking-and-loading) в процессы и [выделяют у неё память](/ru/notes/acos/memory-allocation). [Процессы и потоки](/ru/notes/acos/processes-and-threads) работают одновременно, [синхронизируются](/ru/notes/acos/synchronization), чтобы оставаться корректными, и [обмениваются данными](/ru/notes/acos/inter-process-communication) через каналы и разделяемую память; [файлы](/ru/notes/acos/files-and-io) дают им постоянные данные, [пользователи и права доступа](/ru/notes/acos/users-and-permissions) решают, кто может к ним прикасаться, а [виртуальные машины и контейнеры](/ru/notes/acos/virtual-machines-and-containers) изолируют целые системы. [Сети](/ru/notes/acos/networking) переносят байты между машинами через уровни, каждый из которых решает одну задачу, а [сокеты](/ru/notes/acos/sockets) дают программе оба конца соединения. Наконец, [среды выполнения языков](/ru/notes/acos/language-runtimes) строят объекты, сборку мусора и потоки поверх тех же системных вызовов, а компиляторы вроде LLVM превращают исходный код в команды, с которых курс начался. `printf("hello, world\n")` из [первой заметки](/ru/notes/acos/computer-systems) затрагивает каждый из этих уровней: компилятор выбрал его команды, процессор выполнил их через свои кэши и свой конвейер, а системный вызов перенёс тринадцать байт из процесса через ядро на экран.

## Код \{#code\}

Команды, которые дают каждый листинг заметки. Им нужны `clang`, `opt` и `llc` из одной установки LLVM; показанные выводы получены в LLVM 17.0.4 (Homebrew на macOS; в Debian или Ubuntu эти инструменты называются `clang-17`, `opt-17` и `llc-17`). Другие версии печатают ту же структуру с небольшими отличиями.

```sh
# sum.c содержит функцию sum_to из начала заметки.
T="--target=riscv32-unknown-elf -march=rv32im"

clang -ccc-print-phases -c sum.c                      # этапы драйвера (первый листинг)
clang -fsyntax-only -Xclang -dump-tokens sum.c        # токены, в том числе четыре токена `s += i;`

# IR при -O0 с ячейками на стеке, с сохранением имён значений и разрешением последующих проходов
clang $T -S -emit-llvm -O0 -Xclang -disable-O0-optnone -fno-discard-value-names -fomit-frame-pointer sum.c -o sum.ll
opt -S -passes=mem2reg sum.ll -o sum.m2r.ll           # форма SSA с phi-узлами
opt -S -passes='default<O2>' -print-changed=quiet sum.ll -o sum.o2.ll   # замкнутая форма и проходы, которые её получили

clang $T -S -O0 sum.c -o -                            # код RISC-V, в котором каждая переменная на стеке
llc -O2 sum.m2r.ll -o -                               # код RISC-V из формы SSA: цикл в a1 и a2
clang $T -S -O2 sum.c -o -                            # код RISC-V из полного конвейера -O2: цикла нет
```

Цикл и замкнутая форма в том виде, в каком их скомпилировал LLVM, в программе для RARS, которая вызывает обе; проверить её можно командой `python3 -I rv32.py sum.s` или запустить в RARS:

```asm
# sum_to(n) = 1 + 2 + ... + n в том виде, в каком LLVM скомпилировал её для RV32IM: цикл (mem2reg, без оптимизации IR)
# и замкнутая форма (-O2). main вызывает обе для n = 100 и n = 70000 и печатает четыре результата.
# При n = 70000 сумма переполняется в 32 битах (в C такое переполнение не определено; здесь обе версии совпадают).
        .data
space:  .asciz " "
newline: .asciz "\n"
        .text
main:
        li      s0, 100
        jal     try
        li      s0, 70000
        jal     try
        li      a7, 10                  # выход
        ecall

try:                                    # напечатать sum_loop(s0), sum_closed(s0) и перевод строки
        addi    sp, sp, -16
        sw      ra, 12(sp)
        mv      a0, s0
        jal     sum_loop
        li      a7, 1                   # напечатать целое число из a0
        ecall
        la      a0, space
        li      a7, 4
        ecall
        mv      a0, s0
        jal     sum_closed
        li      a7, 1
        ecall
        la      a0, newline
        li      a7, 4
        ecall
        lw      ra, 12(sp)
        addi    sp, sp, 16
        ret

sum_loop:                               # llc -O2 на IR после mem2reg: s в a1, i в a2
        li      a1, 0
        li      a2, 1
        blt     a0, a2, loop_end
loop:
        add     a1, a1, a2
        addi    a2, a2, 1
        bge     a0, a2, loop
loop_end:
        mv      a0, a1
        ret

sum_closed:                             # clang -O2: 2n + (n-1)(n-2)/2 - 1 с 64-битным произведением
        blez    a0, closed_zero
        slli    a1, a0, 1
        addi    a2, a0, -1
        addi    a0, a0, -2
        mul     a3, a2, a0              # младшие 32 бита (n-1)(n-2)
        mulhu   a0, a2, a0              # старшие 32 бита
        slli    a0, a0, 31
        srli    a3, a3, 1
        or      a0, a0, a3              # биты 1..32 произведения: (n-1)(n-2)/2
        add     a0, a0, a1
        addi    a0, a0, -1
        ret
closed_zero:
        li      a0, 0
        ret
# 5050 5050
# -1844932296 -1844932296
```

Замкнутая форма из IR при `-O2`, проверенная на Python против цикла, с 33-битным произведением и 32-битным оборачиванием, как в IR:

```python
def loop(n):                          # цикл на C в 32-битной арифметике
    s = 0
    for i in range(1, n + 1):
        s = (s + i) % 2**32
    return s

def closed(n, bits=33):               # что вычисляет IR при -O2: произведение по модулю 2**bits
    if n < 1:
        return 0
    p = ((n - 1) * (n - 2)) % 2**bits # zext до i33, затем mul i33
    return (2 * n + p // 2 - 1) % 2**32   # lshr, trunc до i32, два add

ns = list(range(3000)) + [65535, 70000, 100000]
print(all(loop(n) == closed(n) for n in ns))              # True
print(closed(3), closed(100), closed(65535))              # 6 5050 2147450880
print((65535 - 1) * (65535 - 2) < 2**32)                  # True: до n = 65535 произведение помещается в 32 бита
print(loop(70000), closed(70000), closed(70000, bits=32)) # 2450035000 2450035000 302551352: 32 бит недостаточно
```
