[Предыдущая заметка](/ru/notes/acos/system-calls) проследила вызов `write` до ядра. Один вопрос остался открытым: как вызов в нашей программе достигает кода `write`, который живёт в библиотеке C — в файле, которого компилятор никогда не видел. [Заметка о C](/ru/notes/acos/c-for-systems-programming) показала последнюю стадию драйвера компилятора только снаружи: ассемблер оставляет объектный файл, в котором некоторые адреса ещё нулевые, а компоновщик выдаёт исполняемый файл, в котором они заполнены. Эта заметка раскрывает эту стадию. Она показывает, что содержит объектный файл, как компоновщик сопоставляет имена с определениями и вписывает адреса в команды, как разделяемые библиотеки находятся и связываются во время работы программы, как ядро и динамический компоновщик загружают результат в процесс и что этот механизм делает возможным: случайные адреса и замену библиотечной функции без перекомпиляции.

**Обозначения.** В перемещении $S$ — адрес символа, к которому относится перемещение, $A$ — хранящееся вместе с ним слагаемое (addend; во всех наших примерах 0), а $P$ — адрес исправляемого места. *hi* и *lo* — старшие 20 бит и младшие 12 бит 32-битного значения, как их разделяла для `lui` и `addi` [заметка о кодировании](/ru/notes/acos/risc-v-instructions). Шестнадцатеричные числа записываются как `0x…`; в выводе инструментов они появляются без префикса.

Все примеры собраны для 64-битного RISC-V Linux с помощью LLVM (`clang`, `ld.lld`, `llvm-objdump`, `llvm-readelf`): инструменты работают на любой машине, даже там, где результат запустить нельзя. macOS использует другой формат объектных файлов, Mach-O, с которым его сравнивает раздел о macOS; объяснение ведётся в терминах ELF, формата Linux и большинства других Unix-систем.

## Отправная точка: один исходный файл \{#baseline-one-source-file\}

Простейшей сборке компоновщик почти не нужен: вся программа и все библиотечные функции, которые она вызывает, помещаются в один исходный файл, и он компилируется. Это ломается в трёх местах.

- **Каждое изменение перекомпилирует всё.** Исправление одной строки в одной функции обходится пересборкой всей программы; в больших проектах миллионы строк.
- **Библиотеки компилируются снова и снова.** Библиотека C должна была бы лежать исходным текстом внутри каждой программы.
- **Каждый процесс носит собственную копию.** Библиотека C системы Debian 13 для arm64, `libc.so.6` (glibc 2.41), занимает 1 716 616 байт. Двести процессов, у каждого из которых своя копия её кода, хранили бы 343 МБ одинаковых байтов; одна копия, общая для всех, занимает 1.7 МБ.

Раздельная компиляция решает первые две проблемы, а разделяемые библиотеки — третью. Обоим нужна программа, которая соединяет отдельно скомпилированные части: **компоновщик** (linker). Разделяемым библиотекам нужна ещё и программа, которая делает часть этой работы во время выполнения: **динамический компоновщик** (dynamic linker).

## Объектные файлы и секции ELF \{#object-files-and-elf-sections\}

В программе-примере три исходных файла. `counter.c` определяет глобальный счётчик и функцию, которая его увеличивает:

```c
int counter = 5;                 /* initialized global: .data */
static int calls;                /* zero-initialized, file-local: .bss */

int bump(int by) {
    calls++;
    counter += by;
    return counter;
}
```

`main.c` пользуется ими, зная только их объявления:

```c
extern int counter;              /* defined in counter.c */
int bump(int by);                /* defined in counter.c */

int main(void) {
    bump(2);
    return bump(3) + counter;    /* 10 + 10 = 20 */
}
```

а `start.s` — точка входа, играющая роль стартового файла библиотеки C `crt1.o`: он вызывает `main` и передаёт её результат системному вызову `exit`.

```asm
    .globl _start
_start:                          # то, что делает crt1.o, без библиотеки C
    call main                    # a0 = main()
    li   a7, 93                  # 93 = exit в Linux на RISC-V
    ecall                        # exit(a0)
```

`clang -c` превращает каждый файл в **перемещаемый объектный файл** (relocatable object file) в формате **ELF** (Executable and Linkable Format, [System V ABI](#references)). Файл ELF начинается с заголовка, первые четыре байта которого — `7f 45 4c 46` (`\x7f` и `ELF`), и записывает машину (RISC-V), размер слова (64 бита), порядок байтов (little-endian) и тип файла. Тот же формат с другими типами хранит ещё три вида файлов: **исполняемый файл** (executable, тип `EXEC` или `DYN` для позиционно-независимого), **разделяемый объект** (shared object, `DYN`, библиотека `.so`) и дамп памяти (core dump). Перемещаемый файл разделён на **секции** (sections):

| Секция | Содержит | В `counter.o` |
| --- | --- | --- |
| `.text` | машинный код | `bump`, 36 байт |
| `.rodata` | константы, строковые литералы | (нет) |
| `.data` | инициализированные глобальные переменные | `counter`, 4 байта |
| `.bss` | глобальные переменные, инициализированные нулём; тип `NOBITS`, места в файле не занимает | `calls`, 4 байта |
| `.symtab`, `.strtab` | таблица символов и имена, которые она использует | `bump`, `counter`, `calls` |
| `.rela.text` | записи перемещения для `.text` | 6 записей |
| `.debug_*` | отладочная информация, с `-g` | (нет) |

Каждый адрес внутри перемещаемого файла начинается с 0 в своей секции: ассемблер не может знать, где окажется секция.

## Символы и таблица символов \{#symbols-and-the-symbol-table\}

**Символ** (symbol) — это имя со значением: функция или переменная, которую файл определяет или использует. `llvm-nm` печатает таблицы символов двух объектных файлов:

```text
main.o:                                 counter.o:
                 U bump                 0000000000000000 T bump
                 U counter              0000000000000000 b calls
0000000000000000 T main                 0000000000000000 D counter
```

Буква обозначает вид: `T` — определён в `.text`, `D` — в `.data`, `b` — в `.bss`, `U` — не определён: используется здесь, определён в другом месте. Заглавные буквы — **глобальные** символы, видимые другим файлам; строчные — **локальные**: `calls` объявлен `static`, поэтому никогда не участвует в компоновке, и в другом файле может быть свой `calls`.

**Разрешение символов** (symbol resolution) сопоставляет каждому неопределённому символу ровно одно глобальное определение среди всех входных файлов и библиотек. Возможны две ошибки, и `ld.lld` сообщает о них так:

```text
ld.lld: error: undefined symbol: bump        # main.o скомпонован без counter.o
>>> referenced by main.c
ld.lld: error: duplicate symbol: counter     # второй файл тоже определяет int counter = 7;
>>> defined at counter.c
>>> defined at other.c
```

Функция или переменная, определённая в заголовке, который включают два файла `.c`, вызывает вторую ошибку; поэтому заголовки содержат только объявления. В GCC и Clang есть также **слабые** (weak) символы, помеченные `__attribute__((weak))`: слабое определение используется, только если нет обычного (сильного, strong), что позволяет библиотеке дать определение по умолчанию, которое программа может заменить ([Bryant and O'Hallaron, 2016](#references), §7.6.1).

## Перемещение: исправление адресов \{#relocation-patching-the-addresses\}

После разрешения компоновщик знает, к какому определению относится каждое имя, но ещё не знает, где что будет лежать. Дальше он делает ещё два шага.

<LinkerFlow />

1. **Разрешение**, как описано выше: `bump` и `counter`, не определённые в `main.o`, определены в `counter.o`.
2. **Размещение** (layout). Компоновщик сцепляет одноимённые секции всех входных файлов (все `.text` вместе, все `.data` вместе) и назначает каждой выходной секции адрес. `ld.lld` помещает `.text` по адресу `0x11190`: `_start` из `start.o` по адресу `0x11190`, `main` по `0x111a0`, `bump` по `0x111d8`. `.data` начинается с `0x121fc`, так что `counter` лежит по адресу `0x121fc`, а за ней следует `.bss`, где `calls` лежит по `0x12200`. Теперь у каждого символа есть окончательный адрес $S$.
3. **Перемещение** (relocation). Для каждой записи каждой секции `.rela` компоновщик вычисляет значение из $S$, $A$ и $P$ и вписывает его в команду по адресу $P$, в те битовые позиции, которые предписывает тип записи ([RISC-V ELF psABI](#references)).

В `main.o` ассемблер оставил записи трёх видов:

```text
   c: 97 00 00 00   auipc  ra, 0            R_RISCV_CALL_PLT  bump
  10: e7 80 00 00   jalr   ra
  20: b7 05 00 00   lui    a1, 0            R_RISCV_HI20      counter
  24: 83 a5 05 00   lw     a1, 0(a1)        R_RISCV_LO12_I    counter
```

**Вызов** — это пара `auipc ra, hi` и `jalr ra, lo(ra)`: цель равна $P + (\mathit{hi} \ll 12) + \mathit{lo}$, поэтому кодировать нужно расстояние $S - P$. **Глобальная переменная** в позиционно-зависимом коде этого примера достигается парой `lui a1, hi` и `lw a1, lo(a1)`, адрес которой равен $(\mathit{hi} \ll 12) + \mathit{lo}$, поэтому значение — само $S$. В обоих случаях *lo* — знаковое 12-битное поле, которое процессор расширяет знаком, поэтому при разбиении нужно округление:

$$
\begin{aligned}
\mathit{hi} &= \Big\lfloor \frac{v + \texttt{0x800}}{2^{12}} \Big\rfloor, \\
\mathit{lo} &= v - \mathit{hi} \cdot 2^{12} \in [-2048, 2047] .
\end{aligned}
$$

Прибавление `0x800` перед отбрасыванием младших 12 бит увеличивает *hi* на единицу ровно тогда, когда младшие 12 бит равны `0x800` или больше, то есть когда *lo* окажется отрицательным.

**Разобранный пример.** Первый вызов `bump` стоит по адресу $P = \texttt{0x111ac}$ (`main` по адресу `0x111a0` плюс смещение `0xc`), а $S = \texttt{0x111d8}$:

- $v = S - P = \texttt{0x2c} = 44$; $\mathit{hi} = \lfloor (44 + 2048)/4096 \rfloor = 0$, $\mathit{lo} = 44$. Пара становится `auipc ra, 0` и `jalr 44(ra)` — ровно то, что `llvm-objdump` показывает в `prog`. Второй вызов, по адресу `0x111b8`, получает `jalr 32(ra)`.
- `counter` лежит по адресу $S = \texttt{0x121fc}$. Его младшие 12 бит, `0x1fc` = 508, меньше `0x800`, поэтому $\mathit{hi} = \texttt{0x12} = 18$ и $\mathit{lo} = 508$: `lui a1, 18` и `lw a1, 508(a1)`, и $18 \cdot 4096 + 508 = 74\,236 = \texttt{0x121fc}$. В `bump` переменная `calls` по адресу `0x12200` превращается в `lw a2, 512(a1)` после того же `lui a1, 18`.
- Если бы `counter` лежал по адресу `0x12a44`, младшие биты которого `0xa44` больше `0x7ff`, разбиение было бы $\mathit{hi} = 19$, $\mathit{lo} = \texttt{0xa44} - 4096 = -1468$, и снова $19 \cdot 4096 - 1468 = \texttt{0x12a44}$.

Результат, `prog`, — полный исполняемый файл размером 1528 байт без неопределённых символов. Его точка входа — `0x11190`, адрес `_start`.

<aside class="callout"><strong>Ключевая идея.</strong> Компиляция оставляет дыры, компоновка их заполняет. Компилятор и ассемблер транслируют каждый файл, не зная, где что окажется, и записывают каждое место, которому нужен адрес, как запись перемещения: где оно находится, какой символ ему нужен и как его закодировать. Компоновщик сопоставляет каждому имени одно определение, решает, где будет лежать всё, и вычисляет содержимое каждой дыры из трёх чисел: адреса символа, слагаемого и собственного адреса места. Разделяемые библиотеки откладывают часть этой работы до запуска программы.</aside>

## Статические библиотеки \{#static-libraries\}

**Статическая библиотека** (static library) — это архив объектных файлов, созданный программой `ar`: `llvm-ar rcs libcounter.a counter.o`. Компоновка с `-lcounter` (и с `-L.`, чтобы искать в текущем каталоге) не копирует в программу весь архив; компоновщик берёт только те члены архива, которые определяют символ, ещё не определённый к этому моменту, плюс то, что нужно им самим. Программа, которая вызывает одну функцию большой статической библиотеки, получает объектный файл этой функции, а не всю библиотеку.

GNU `ld` просматривает входные файлы один раз, слева направо, и извлекает члены архива только для символов, не определённых *к этому моменту*: `ld main.o -lcounter` работает, а `ld -lcounter main.o` завершается ошибкой о неопределённой ссылке, потому что, когда просматривался архив, `bump` ещё никому не был нужен ([Bryant and O'Hallaron, 2016](#references), §7.6.3). `ld.lld` запоминает архивы и принимает любой порядок. Статическая компоновка даёт самодостаточный исполняемый файл, который работает на любой системе с тем же интерфейсом ядра, ценой копии каждой библиотечной функции в каждой программе и необходимости перекомпоновать каждую программу, чтобы исправить ошибку в библиотеке.

## Динамическая компоновка: разделяемые библиотеки, PLT и GOT \{#dynamic-linking-shared-libraries-the-plt-and-the-got\}

**Разделяемая библиотека** (shared library: `.so` в Linux, `.dylib` в macOS, `.dll` в Windows) компонуется с программой, когда та *загружается*, а не когда собирается. Файл `libc.so.6` отображается в каждый процесс, который им пользуется, и его страницы кода, которые никогда не меняются, — одни и те же физические страницы во всех процессах: одна копия в памяти, как и требовала отправная точка. Исправление ошибки в библиотеке исправляет каждую программу при её следующем запуске.

У разделения есть условие. Библиотека загружается в каждом процессе (а с ASLR — при каждом запуске) по своему адресу, и если бы её код содержал абсолютные адреса, динамическому компоновщику пришлось бы исправлять их в каждом процессе, создавая частные копии страниц. Поэтому разделяемый код компилируется как **позиционно-независимый код** (position-independent code, PIC, `-fPIC`): он никогда не содержит собственных абсолютных адресов. К своему коду и данным он обращается с адресацией относительно PC (`auipc` плюс смещение, которое не меняется, где бы ни загрузилась библиотека), а ко всему, что вне его, — через две таблицы, которые лежат в записываемых данных процесса:

- **GOT** (global offset table, таблица глобальных смещений) хранит адреса внешних переменных. Код читает из GOT адрес, а затем саму переменную. Динамический компоновщик заполняет GOT при загрузке; сам код никогда не меняется.
- **PLT** (procedure linkage table, таблица компоновки процедур) хранит небольшую *заглушку* (stub) для каждой внешней функции. Вызов идёт на заглушку, а заглушка переходит через слот в той части GOT, что отведена функциям, `.got.plt`.

Исполняемый файл `prog-dyn` собран из того же `main.c`, скомпилированного с `-fPIE` и скомпонованного с `libcounter.so` вместо `counter.o`. `llvm-readelf` показывает, что осталось на время выполнения: динамическая секция называет библиотеку (`NEEDED libcounter.so`), и остаются два перемещения: `R_RISCV_64 counter` для элемента GOT по адресу `0x2528` и `R_RISCV_JUMP_SLOT bump` для слота PLT по адресу `0x3540`. Обращение к `counter` в `main` превратилось в `auipc a1, 1; ld a1, 356(a1)`, что загружает адрес `counter` из `0x2528`, за которым следует `lw a1, 0(a1)`, загружающая значение.

<PltGot />

Вызовы `bump` идут на заглушку `bump@plt` по адресу `0x1400`, три команды которой — `auipc t3, 2`, `ld t3, 320(t3)` (то есть загрузить слот по адресу `0x3400 + 320 = 0x3540`) и `jalr t1, t3`. Поначалу слот содержит не адрес `bump`, а `0x13e0`, адрес общего заголовка PLT, PLT0. Это **ленивое связывание** (lazy binding):

1. `main` вызывает `bump@plt`.
2. Заглушка загружает слот и переходит по его содержимому.
3. При первом вызове это PLT0, который вычисляет номер слота по адресу заглушки и переходит на резолвер (resolver) динамического компоновщика, адрес которого динамический компоновщик записал в `.got.plt[0]`, когда загружал программу.
4. Резолвер ищет имя `bump` в таблицах символов загруженных библиотек и записывает найденный адрес в слот.
5. Он переходит на `bump`, которая возвращается прямо в `main`.
6. Каждый следующий вызов загружает новое значение слота и сразу переходит на `bump`: на одну загрузку и один косвенный переход больше, чем при прямом вызове.

Ленивое связывание тратит поиск только на те функции, которые действительно вызываются; программа, скомпонованная с библиотекой из тысяч функций и вызывающая десять из них, разрешает десять. Цена — записываемая таблица адресов кода, которую может перенаправить атакующий, способный писать в память. Поэтому защищённые сборки компонуются с `-z now` (и с полным RELRO, который после загрузки делает GOT доступной только для чтения): каждый символ разрешается при загрузке, а переменная окружения `LD_BIND_NOW=1` делает то же самое для любой программы.

**Разобранный пример: как происходит связывание.** Динамический компоновщик glibc сообщает о своей работе, если задана переменная окружения `LD_DEBUG`. Программа, которая дважды вызывает `puts`, скомпонованная для ленивого связывания и запущенная в контейнере Debian 13 (glibc 2.41, arm64), показывает связывание `puts` после того, как управление перешло к программе, один раз, прямо перед тем, как первый вызов что-то напечатает; с `LD_BIND_NOW=1` то же связывание появляется до запуска программы. Только Linux, в macOS не запускалось; в отрывке оставлены нужные строки и убран столбец с идентификатором процесса:

```text
$ LD_DEBUG=bindings ./hello
...
    transferring control: ./hello
    binding file ./hello [0] to /lib/aarch64-linux-gnu/libc.so.6 [0]: normal symbol `puts' [GLIBC_2.17]
first call
second call
$ LD_BIND_NOW=1 LD_DEBUG=bindings ./hello
...
    binding file ./hello [0] to /lib/aarch64-linux-gnu/libc.so.6 [0]: normal symbol `puts' [GLIBC_2.17]
...
    transferring control: ./hello
first call
second call
```

## Загрузчик и образ процесса \{#the-loader-and-the-process-image\}

`execve("./prog", argv, envp)` просит ядро заменить программу, работающую в вызывающем процессе ([Процессы и потоки](/ru/notes/acos/processes-and-threads)). Ядро не читает секции; оно читает **программные заголовки** (program headers) — вторую таблицу в файле ELF, которая группирует секции в **сегменты** (segments), отображаемые в память. Для `prog`:

```text
Entry point 0x11190
  Type   Offset   VirtAddr  FileSiz  MemSiz   Flg
  LOAD   0x000000 0x010000  0x000190 0x000190 R        headers
  LOAD   0x000190 0x011190  0x00006c 0x00006c R E      .text
  LOAD   0x0001fc 0x0121fc  0x000004 0x000008 RW       .data and .bss
```

<LoadSegments />

1. Ядро проверяет заголовок ELF и читает программные заголовки.
2. Оно отображает каждый сегмент `LOAD` по его адресу с правами из его флагов, тем же механизмом, что и `mmap` файла: страницы читаются не сейчас, а при первом обращении, через [страничные отказы](/ru/notes/acos/virtual-memory). Смещение каждого сегмента в файле и его адрес совпадают по модулю размера страницы (`0x1fc` и `0x121fc` оба заканчиваются на `1fc`), и именно это позволяет отображать страницы файла напрямую.
3. Там, где `MemSiz` больше `FileSiz`, остаток заполняется нулями: 4 байта сегмента данных за пределами файла — это `.bss`, где живёт `calls`.
4. Оно строит начальный стек: число аргументов, строки аргументов и окружения и указатели на них, а также *вспомогательный вектор* (auxiliary vector) — список сведений для программы и её динамического компоновщика (размер страницы, адрес программных заголовков, точка входа).
5. Оно устанавливает счётчик команд на точку входа, `0x11190`, и возвращается в режим U. Начинает работать `_start`.

Для динамически скомпонованной программы есть ещё один шаг. Программные заголовки содержат запись `INTERP`, называющую динамический компоновщик, здесь `/lib/ld-linux-riscv64-lp64.so.1` (на x86-64 — `/lib64/ld-linux-x86-64.so.2`). Ядро отображает и этот файл и запускает *его* вместо программы. Динамический компоновщик читает записи `NEEDED` программы, находит и отображает каждую библиотеку (и их собственные библиотеки из `NEEDED`), применяет перемещения, которые не могут ждать (элементы GOT, такие как `counter`, и все слоты, если связывание немедленное), заполняет `.got.plt[0]` и `[1]`, выполняет функции инициализации библиотек и переходит на точку входа программы. В программе на C эта точка входа — `_start` из `crt1.o`, который вызывает `__libc_start_main`, а та вызывает `main` и передаёт её возвращаемое значение в `exit`. Многочисленные вызовы `openat`, `mmap` и `mprotect`, которые `strace` показывает до `main` в [заметке о системных вызовах](/ru/notes/acos/system-calls#watching-system-calls-strace), — это и есть загрузка.

`/proc/self/maps` показывает получившийся образ процесса в Linux: по одной строке на отображённую область, с её адресами, правами и файлом. [Заметка о C](/ru/notes/acos/c-for-systems-programming#the-memory-layout-of-a-program) нарисовала, где лежат области.

## Рандомизация размещения адресного пространства \{#address-space-layout-randomization\}

Если код программы и её библиотек всегда находится по одним и тем же адресам, атакующий, который может перезаписать адрес возврата, точно знает, куда перейти: например, в `system` из библиотеки C. **Рандомизация размещения адресного пространства** (address space layout randomization, ASLR) переносит области по случайным адресам при каждом запуске, так что такой атаке сначала нужно выяснить, где они. Linux управляет ею через `/proc/sys/kernel/randomize_va_space`: 0 выключает её; 1 делает случайными стек, область, куда `mmap` помещает библиотеки, и vDSO; 2, обычное значение по умолчанию, делает случайным ещё и начало кучи ([Linux kernel documentation](#references)). Сам исполняемый файл сдвигается, только если он позиционно-независимый, поэтому дистрибутивы теперь по умолчанию собирают программы как PIE; адреса Linux, приведённые в [заметке о C](/ru/notes/acos/c-for-systems-programming#the-memory-layout-of-a-program), относятся к запуску с выключенной рандомизацией.

**Разобранный пример.** Программа `aslr.c` из раздела «Код» печатает адреса `main`, глобальной переменной, блока в куче и локальной переменной и запускается дважды на Apple M1 (macOS рандомизирует всегда):

- запуск 1: `main` по адресу `0x102ca44f8`, глобальная переменная по `0x102cac000`, стек по `0x16d15a668`;
- запуск 2: `main` по адресу `0x10434c4f8`, глобальная переменная по `0x104354000`, стек по `0x16bab2668`.

Каждая база сдвинулась, но внутри одного запуска расстояние от `main` до глобальной переменной оба раза равно `0x7b08`: его зафиксировал компоновщик, и весь образ сдвинулся как единый блок. Младшие 14 бит каждого адреса тоже одинаковы, `0x04f8` у `main`: страницы M1 занимают 16 КиБ, а рандомизация работает целыми страницами. Оба наблюдения объясняют, почему у ASLR есть пределы: один утёкший адрес функции раскрывает положение всего образа, которому она принадлежит.

## Подмена библиотечных функций \{#library-interposition\}

Поскольку символы разрешаются по имени, программу можно заставить вызывать другую функцию с тем же именем без перекомпиляции. Это **подмена библиотечных функций** (library interposition), и она возможна в три момента ([Bryant and O'Hallaron, 2016](#references), §7.13):

- **при компиляции** — макросом: `#define malloc(n) mymalloc(n)` в заголовке, включённом до вызовов;
- **при компоновке** — параметром компоновщика `--wrap=malloc`, который направляет неопределённые ссылки на `malloc` к `__wrap_malloc` и позволяет через `__real_malloc` добраться до оригинала;
- **при загрузке** — переменной окружения `LD_PRELOAD`, которая заставляет динамический компоновщик загрузить указанную библиотеку раньше всех остальных ([ld.so(8)](#references)). Её определения стоят в порядке поиска первыми и поэтому побеждают.

Вариант при загрузке не требует доступа к исходному тексту программы или к её сборке. Обёртка, которая находит оригинал через `dlsym(RTLD_NEXT, ...)`, «следующее после моего определение этого имени», и печатает строку перед каждым вызовом `puts`:

```c
// trace.c: Linux only; not run on macOS.
// gcc -O1 -shared -fPIC trace.c -o libtrace.so    then    LD_PRELOAD=./libtrace.so ./hello
#define _GNU_SOURCE
#include <dlfcn.h>
#include <stdio.h>

int puts(const char *s) {                    /* same name as the C library's puts */
    static int (*real_puts)(const char *);
    if (!real_puts)
        real_puts = (int (*)(const char *))dlsym(RTLD_NEXT, "puts");
    real_puts("[trace] puts is called");
    return real_puts(s);
}
// Output of LD_PRELOAD=./libtrace.so ./hello in a Debian 13 container (glibc 2.41, arm64; the programs built with LLVM):
// [trace] puts is called
// first call
// [trace] puts is called
// second call
```

Подмена — это способ, которым отладчики памяти, профилировщики и трассировщики подключаются к немодифицированным программам. Ради безопасности динамический компоновщик игнорирует элементы `LD_PRELOAD`, содержащие косую черту, в программах с битом set-user-ID, которые работают с правами другого пользователя ([Пользователи, группы и права доступа](/ru/notes/acos/users-and-permissions)). В macOS есть тот же механизм под именем `DYLD_INSERT_LIBRARIES`, ограниченный для системных программ защитой System Integrity Protection.

## Коротко о сборке с CMake \{#building-with-cmake-briefly\}

Команды вроде приведённых выше набирают один раз. В настоящем проекте сотни файлов, несколько библиотек и несколько платформ, и его собирают системой сборки (build system). `make` читает `Makefile` из правил (цель, файлы, от которых она зависит, и команда, которая её создаёт) и перезапускает команду, только когда зависимость новее своей цели. **CMake** стоит на уровень выше: он читает платформенно-независимое описание, `CMakeLists.txt`, и порождает `Makefile` (или проект Ninja либо IDE) для текущей платформы и компилятора.

```cmake
cmake_minimum_required(VERSION 3.16)
project(counter_demo LANGUAGES C)

set(CMAKE_C_STANDARD 17)
add_compile_options(-Wall -Wextra)

add_library(counter STATIC counter.c)     # SHARED собрал бы libcounter.so (.dylib в macOS)
add_executable(prog main.c)
target_link_libraries(prog PRIVATE counter)
```

`add_library` и `add_executable` объявляют цели; `target_link_libraries` говорит, что `prog` компонуется с `counter`, а CMake сам выводит порядок сборки и флаги компоновщика. Сборка идёт в отдельном каталоге, так что дерево исходников остаётся чистым: `cmake -S . -B build` настраивает, `cmake --build build` собирает.

## Несколько слов о macOS: Mach-O \{#a-note-on-macos-mach-o\}

macOS не использует ELF. Её формат — **Mach-O**: 64-битный файл Mach-O начинается с байтов `cf fa ed fe` (число `0xfeedfacf`, записанное в порядке little-endian), и вместо секций и сегментов ELF в нём есть *сегменты*, такие как `__TEXT` и `__DATA`, которые содержат *секции*, такие как `__text`, `__cstring` и `__data`. У всех частей этой заметки есть соответствия. `__stubs` играет роль PLT, а `__got` — роль GOT; динамический компоновщик — `dyld`; библиотеки — файлы `.dylib`, которые записываются вместе с путём установки, а символы ищутся в конкретной библиотеке, а не во всех сразу (*двухуровневые пространства имён*, two-level namespaces); новые двоичные файлы заменяют ленивое связывание *цепочками исправлений* (chained fixups), которые dyld применяет при загрузке. Инструменты называются иначе (`otool -l` вместо `readelf -l`, `otool -L` вместо `ldd`; `nm` и `size` есть в обеих системах), но вопросы, на которые они отвечают, — те же, что в этой заметке: какие секции, какие символы, какие библиотеки, какие адреса.

## Ограничения \{#limitations\}

- **Ошибки компоновки появляются поздно и скупо описаны.** Отсутствующее определение или расхождение между объявлением и определением в разных файлах обнаруживается только при компоновке, а несовпадение типов между файлами часто не обнаруживается вовсе.
- **Разделяемые библиотеки приносят проблемы версий.** Программа, собранная с одной версией библиотеки, может не работать с другой: функцию убрали, структура изменилась. Для этого существуют версии символов (`[GLIBC_2.17]` в трассировке) и суффикс `.so.6`.
- **Косвенность немного стоит.** Вызов через PLT — это лишняя загрузка и косвенный переход; позиционно-независимому коду нужна загрузка из GOT для каждой внешней переменной. Загрузка и перемещение удлиняют запуск программ с большим числом библиотек.
- **Ленивое связывание меняет безопасность на скорость.** Записываемая таблица адресов кода — мишень; полный RELRO и `-z now` убирают её ценой разрешения всего при запуске.
- **ASLR даёт утечки.** Один раскрытый указатель выдаёт базу всего образа, которому он принадлежит, а в 32-битных системах возможных положений так мало, что их можно перебрать все.

## Что нужно запомнить \{#what-you-should-remember\}

- Объектный файл (ELF) содержит секции (`.text`, `.data`, `.bss`, `.rodata`), таблицу символов (определённые `T`/`D`/`b`, неопределённые `U`) и записи перемещения для каждого адреса, который он не смог заполнить.
- Компоновщик сопоставляет каждому неопределённому символу ровно одно определение, размещает объединённые секции и исправляет каждое перемещение по $S$, $A$ и $P$. В RISC-V значение делится на *hi* = $\lfloor (v + \texttt{0x800}) / 4096 \rfloor$ и знаковое *lo*: вызов `bump` по адресу `0x111ac` получает `jalr 44(ra)`, `counter` по адресу `0x121fc` получает `lui 18` и `lw 508`.
- Статические библиотеки — это архивы объектных файлов; копируются только нужные члены. Разделяемые библиотеки отображаются при загрузке и разделяются между процессами.
- Разделяемый код позиционно-независим: внешние переменные — через GOT, внешние функции — через заглушки PLT, слоты GOT которых заполняются лениво, при первом вызове, динамическим компоновщиком (или при загрузке с `-z now`).
- `execve` отображает сегменты `LOAD` из программных заголовков, заполняет нулями `.bss`, строит стек и запускает динамический компоновщик, названный в `INTERP`, который загружает библиотеки и переходит на `_start`.
- ASLR сдвигает целые образы на целые страницы при каждом запуске; `LD_PRELOAD` ставит библиотеку первой в поиске символов и тем самым заменяет функции без перекомпиляции.

## Код \{#code\}

Арифметика перемещений из разобранного примера:

```python
# reloc.py: python3 reloc.py -- арифметика трёх перемещений RISC-V из разобранного примера
def hi_lo(value):
    """Split a 32-bit value into hi (for lui/auipc, upper 20 bits) and lo (for addi/lw/jalr, signed 12 bits)."""
    hi = (value + 0x800) >> 12          # округление, потому что lo расширяется знаком
    lo = value - (hi << 12)             # всегда в [-2048, 2047]
    return hi, lo

symbols = {"_start": 0x11190, "main": 0x111A0, "bump": 0x111D8, "counter": 0x121FC, "calls": 0x12200}

# R_RISCV_CALL_PLT по адресу P: auipc ra, hi; jalr ra, lo(ra)  со значением S - P
for place in (0x111AC, 0x111B8):
    print(f"call bump at {place:#x}: offset {symbols['bump'] - place}, hi/lo {hi_lo(symbols['bump'] - place)}")
# R_RISCV_HI20 / R_RISCV_LO12_I: lui a1, hi; lw a1, lo(a1)  со значением S
for name in ("counter", "calls"):
    print(f"{name} at {symbols[name]:#x}: hi/lo {hi_lo(symbols[name])}")
# когда младшие 12 бит равны 0x800 или больше, hi растёт на единицу, а lo отрицательно
print(f"0x12a44: hi/lo {hi_lo(0x12A44)}, check {(hi_lo(0x12A44)[0] << 12) + hi_lo(0x12A44)[1]:#x}")
# call bump at 0x111ac: offset 44, hi/lo (0, 44)
# call bump at 0x111b8: offset 32, hi/lo (0, 32)
# counter at 0x121fc: hi/lo (18, 508)
# calls at 0x12200: hi/lo (18, 512)
# 0x12a44: hi/lo (19, -1468), check 0x12a44
```

Сборка примера статически и с разделяемой библиотекой, с `counter.c`, `main.c` и `start.s` из раздела об объектных файлах. Для неё нужны собственные инструменты LLVM, потому что у `clang` от Apple нет бэкенда RISC-V (в macOS с Homebrew: `PATH="$(brew --prefix llvm)/bin:$PATH"`). Программы здесь только собираются; чтобы их запустить, нужен Linux на RISC-V.

```bash
CFLAGS="--target=riscv64-linux-gnu -march=rv64g -mabi=lp64 -mno-relax -O1"
clang $CFLAGS -msmall-data-limit=0 -fno-asynchronous-unwind-tables -fno-pic -c main.c counter.c
clang $CFLAGS -c start.s
llvm-nm main.o counter.o                       # main.o: U bump, U counter, T main; counter.o: T bump, b calls, D counter
llvm-objdump -dr main.o | grep -A1 -E "auipc|lui|lw"
#        c: 97 00 00 00  auipc ra, 0           R_RISCV_CALL_PLT bump   (и то же по адресу 0x18)
#       20: b7 05 00 00  lui   a1, 0           R_RISCV_HI20     counter
#       24: 83 a5 05 00  lw    a1, 0(a1)       R_RISCV_LO12_I   counter
ld.lld -o prog start.o main.o counter.o
```
