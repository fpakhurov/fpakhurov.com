[Предыдущая заметка](/ru/notes/acos/operating-systems) описала ядро и границу между ним и пользовательскими программами. Обе стороны этой границы написаны на C. Ядро Linux — это C с небольшой долей ассемблера, библиотека C, которая служит обёрткой над системными вызовами, написана на C, и страницы руководства определяют сам интерфейс как функции C: `ssize_t write(int fd, const void *buf, size_t count)`. C заслужил это место, потому что из всех языков он ближе всего к машинной модели первой половины курса: адрес — это число, память — массив байтов, структура — фиксированное расположение байтов, а функция — метка, на которую переходит код. Эта заметка разбирает те части C, которые системный программист должен знать точно: размеры типов, указатели и арифметику над ними, раскладку структур и всей программы в памяти, неопределённое поведение, которое приходит вместе с близостью к машине, и стадии, превращающие исходные файлы в исполняемый файл.

**Обозначения.** `sizeof(T)` — размер типа `T` в байтах, `_Alignof(T)` — его выравнивание: число, которому должен быть кратен его адрес. `offsetof(S, m)` — расстояние в байтах от начала структуры `S` до её члена `m`. Шестнадцатеричные числа записываются как `0x…`, как в [заметке о целых числах](/ru/notes/acos/data-representation).

## Почему C для системного программирования \{#why-c-for-systems\}

C создал Деннис Ритчи в Bell Labs в 1972–1973 годах, чтобы писать на нём утилиты Unix, а в 1973 году на него было переписано и само ядро Unix ([Ritchie, 1993](#references)). Пять свойств удерживают его там.

- **Типы — это размеры.** `int` — машинное слово известной ширины, а не абстрактное целое; арифметика компилируется в одиночные команды.
- **Указатели — это адреса.** Программа может вычислить адрес, сохранить его и прочитать или записать то, что по нему лежит, — именно это ядро делает с таблицами страниц и регистрами устройств.
- **Раскладка предсказуема.** Байты структуры лежат в документированном порядке, поэтому на C можно описать блок регистров устройства, сетевой заголовок или аргументы системного вызова.
- **Нет скрытой среды выполнения.** Нет сборщика мусора, проверок границ, исключений. Функция на C может выполняться ещё до того, как появилось управление памятью, поэтому первый код ядра после загрузки может быть написан на C.
- **Автономный режим (freestanding).** Стандарт определяет подмножество языка, которому вообще не нужна библиотека, — то подмножество, которым пользуется ядро.

Те же свойства делают C опасным: ничто не проверяет индекс или указатель, и ошибки молча портят память. Начиная с версии 6.1 (2022) ядро Linux может содержать и код на Rust, пока в основном драйверы: Rust даёт тот же контроль над раскладкой и памятью, но с проверками во время компиляции.

## Отправная точка: та же функция на ассемблере \{#baseline-the-same-function-in-assembly\}

Функция, суммирующая массив, на C:

```c
int sum(const int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; i++)
        s += a[i];
    return s;
}
```

и код RISC-V, который выдаёт для неё `clang --target=riscv32-unknown-elf -march=rv32im -O1 -S` из LLVM (директивы убраны):

```asm
sum:
    li   a2, 0              # s = 0
    blez a1, .LBB0_2        # если n <= 0, пропустить цикл
.LBB0_1:
    lw   a3, 0(a0)          # *a
    add  a2, a3, a2         # s += *a
    addi a1, a1, -1         # n--
    addi a0, a0, 4          # a++: следующий int на 4 байта дальше
    bnez a1, .LBB0_1
.LBB0_2:
    mv   a0, a2             # вернуть s
    ret
```

[Заметка о процедурах](/ru/notes/acos/procedures-and-the-stack) писала такой код вручную. Каждый регистр, каждое смещение и каждый размер программист отслеживал сам: что `a0` содержит адрес, что `int` занимает 4 байта и поэтому следующий лежит по адресу `a0 + 4`, какие регистры вызывающая функция ожидает сохранёнными. Это работает, но программа, написанная так, работает на одном наборе команд, и каждое изменение означает заново проделать весь этот учёт вручную. C сохраняет машинную модель и передаёт учёт компилятору: функция на C выше без изменений компилируется для RISC-V, x86-64 и arm64. Кроме того, компилятор сделал то, о чём мы не просили: превратил индекс `i` в указатель, который сдвигается на 4, и считает `n` вниз, вместо того чтобы считать `i` вверх. Эта свобода преобразований — причина неопределённого поведения, о котором речь пойдёт дальше в этой заметке.

<aside class="callout"><strong>Ключевая идея.</strong> C сохраняет машинную модель ассемблера и передаёт учёт компилятору: тип — это размер и выравнивание, указатель — адрес, который движется шагами в размер своего элемента, структура — фиксированное расположение байтов, и каждый объект живёт в области памяти, выбранной тем, как он объявлен. Компилятор проверяет типы и больше ничего, а оптимизирует в предположении, что программа следует правилам; у программы, которая их нарушает, неопределённое поведение, и никакой результат не гарантирован.</aside>

## Типы и их размеры \{#types-and-their-sizes\}

C фиксирует только минимальные диапазоны: в `char` не меньше 8 бит, в `short` и `int` не меньше 16, в `long` не меньше 32, в `long long` не меньше 64, а `sizeof(char)` по определению равен 1 ([C17](#references), §5.2.4.2.1). Остальное каждая платформа выбирает в своей *модели данных* (data model):

| Тип | ILP32 (RV32) | LP64 (Linux и macOS, 64 бита) | LLP64 (Windows, 64 бита) |
| --- | --- | --- | --- |
| `short` | 2 | 2 | 2 |
| `int` | 4 | 4 | 4 |
| `long` | 4 | 8 | 4 |
| `long long` | 8 | 8 | 8 |
| указатель, `size_t` | 4 | 8 | 8 |

(размеры, которые Clang сообщает для целевых платформ `riscv32-unknown-elf`, `riscv64-linux-gnu`, `x86_64-linux-gnu`, `arm64-apple-darwin` и `x86_64-pc-windows-msvc`.) Код, который хранит указатель в `int`, работает на RV32 и ломается на любой 64-битной системе. Когда ширина важна, как в формате файла или в регистре, нужны типы точной ширины из `<stdint.h>`: `int32_t`, `uint8_t`, `uint64_t` и `uintptr_t` для целого, в котором помещается указатель. `size_t` — беззнаковый тип размеров и индексов, тип, который возвращает `sizeof`.

Некоторые свойства оставлены на усмотрение реализации. Одно из них — знаковый ли простой `char`: он знаковый на x86-64 и на arm64 от Apple и беззнаковый на RISC-V и в Linux на arm64. Поэтому `char c = (char)200;` содержит −56 на Mac и 200 на машине RISC-V. Преобразования между знаковыми и беззнаковыми типами следуют правилам [заметки о целых числах](/ru/notes/acos/data-representation): в `-1 < 1u` значение `-1` преобразуется в `unsigned int`, становится `0xFFFFFFFF` = 4 294 967 295, и сравнение ложно. Преобразование 300 в `uint8_t` оставляет младшие 8 бит: 300 − 256 = 44.

## Указатели и массивы \{#pointers-and-arrays\}

Указатель (pointer) — это адрес вместе с типом того, на что он указывает. `&x` — адрес `x`; `*p` — объект по адресу `p`, который можно прочитать или которому можно присвоить значение. C передаёт аргументы по значению, поэтому функция, которая должна изменить переменную вызывающей стороны, получает адрес этой переменной: `scanf("%d", &n)` записывает в `n` через указатель.

Массив — это блок последовательных элементов. Почти в любом выражении имя массива преобразуется в указатель на его первый элемент, а индексирование определено через арифметику указателей (pointer arithmetic) ([C17](#references), §6.5.2.1, §6.5.6):

$$
\texttt{a[i]} \equiv \texttt{*(a + i)}, \qquad \text{адрес}(\texttt{p + i}) = \text{адрес}(\texttt{p}) + i \cdot \texttt{sizeof(*p)} .
$$

Прибавление $i$ к указателю сдвигает его на $i$ *элементов*, а не на $i$ байт. Разность двух указателей в один и тот же массив даёт число элементов между ними, типа `ptrdiff_t`.

**Разобранный пример.** `int a[4] = {10, 20, 30, 40};` начинается по адресу `0x1000`. Тогда `a + 2` — это `0x1000 + 2 · 4 = 0x1008`, и `*(a + 2)`, и `a[2]` читают 4 байта по адресу `0x1008`: 30. Если смотреть на байты, `(char *)(a + 2) - (char *)a` равно 8; если на `int`, `&a[3] - a` равно 3. Поскольку `a[i]` — это `*(a + i)`, а сложение коммутативно, `2[a]` тоже равно 30: курьёз, который показывает, что определение надо понимать буквально. На RISC-V `a[i]` — это три команды из [заметки об обращениях к памяти](/ru/notes/acos/control-flow-and-memory): `slli t0, i, 2` (умножить на 4), `add t0, a, t0`, `lw t1, 0(t0)`.

Ничто не проверяет, что `a + i` остаётся внутри массива. Чтение `a[4]` читает то, что лежит за массивом; что из этого может выйти, показывает раздел о неопределённом поведении. Строки — это массивы `char`, оканчивающиеся нулевым байтом; [заметка о выделении памяти](/ru/notes/acos/memory-allocation) разбирает их вместе с ошибками, которые они притягивают.

## Структуры и их раскладка \{#structures-and-their-layout\}

`struct` объединяет члены разных типов в один объект. Компилятор размещает их в порядке объявления, но не обязательно вплотную друг к другу, из-за **выравнивания** (alignment): большинство процессоров быстрее всего (или вообще только так) загружают `int` с адреса, кратного 4, а 8-байтовый `double` — с адреса, кратного 8. RISC-V допускает, что невыровненная загрузка обрабатывается ловушкой и эмулируется программно, — это правильно, но медленно; некоторые процессоры просто выдают исключение. Правило, которому следует компилятор во всех распространённых ABI ([Bryant and O'Hallaron, 2016](#references), §3.9.3):

1. каждый член начинается со следующего смещения, кратного его собственному выравниванию;
2. выравнивание структуры — наибольшее из выравниваний её членов;
3. её размер округляется вверх до кратного этому выравниванию, чтобы в массиве таких структур каждый элемент тоже был выровнен.

Байты, пропущенные по правилам 1 и 3, — это **заполнение** (padding).

<StructLayout />

**Разобранный пример.** `struct rec { char tag; int count; char flag; double value; short id; };` в модели LP64:

- `tag` по смещению 0 (1 байт). `count` нужно смещение, кратное 4: смещение 4, после 3 байт заполнения.
- `flag` по смещению 8. `value` нужно смещение, кратное 8: смещение 16, после 7 байт заполнения.
- `id` по смещению 24, заканчивается на 26. Наибольшее выравнивание равно 8, поэтому размер округляется с 26 до 32.

Структура хранит 1 + 4 + 1 + 8 + 2 = 16 байт данных в 32 байтах. Если упорядочить члены по убыванию выравнивания, `value, count, id, tag, flag`, получатся смещения 0, 8, 12, 14, 15 и размер 16: заполнения нет совсем. `offsetof` подтверждает каждое число (раздел «Код»). Если структура уменьшается вдвое, вдвое уменьшаются и память, и число строк кэша, которые занимает массив из миллиона таких структур, а это важно на уровне [кэша](/ru/notes/acos/caches). Компиляторы принимают и `__attribute__((packed))`, который убирает заполнение ценой невыровненных обращений; его используют для форматов передачи данных, таких как сетевые заголовки, и больше нигде.

**Объединение** (union) — противоположность структуры: все его члены начинаются со смещения 0 и делят одни и те же байты, поэтому если записать один член и прочитать другой, видно, как хранится значение, например байты `uint32_t` в порядке [little-endian](/ru/notes/acos/data-representation).

## Раскладка программы в памяти \{#the-memory-layout-of-a-program\}

Когда программа на C работает, каждый объявленный ею объект живёт в одной из немногих областей [виртуального адресного пространства](/ru/notes/acos/virtual-memory) процесса; область определяется тем, как объект объявлен:

- **`.text`**: машинный код функций. Только чтение и исполнение.
- **`.rodata`**: константы, например символы строковых литералов. Только чтение.
- **`.data`**: глобальные и `static` переменные с ненулевым начальным значением. Значения хранятся в исполняемом файле.
- **`.bss`**: глобальные и `static` переменные, которые начинаются с нуля. Файл записывает только их общий размер; загрузчик предоставляет обнулённую память. `static int values[1000];` стоит 4000 байт памяти и ничего не стоит в файле.
- **куча** (heap): память от `malloc`, которая растёт вверх сразу над `.bss` и которой управляет библиотека C ([Динамическое выделение памяти и строки](/ru/notes/acos/memory-allocation)).
- **стек** (stack): локальные переменные, аргументы, которые не поместились в регистры, и сохранённые регистры, по одному кадру на каждый активный вызов; растёт вниз от места рядом с верхом пользовательской половины ([заметка о процедурах](/ru/notes/acos/procedures-and-the-stack)).
- **разделяемые библиотеки** (shared libraries) и другие отображения — между кучей и стеком.

Имена `.text`, `.data` и `.bss` — это имена секций объектных файлов ELF, которые раскрывает [заметка о компоновке](/ru/notes/acos/linking-and-loading).

<ProgramLayout />

**Разобранный пример.** В программе на рисунке `initialized` (значение 42) лежит в `.data`; `zeroed` — в `.bss`; `greeting` — указатель в `.data`, значение которого — адрес шести байтов `h e l l o \0` в `.rodata`; `local` — в кадре стека `main`; а `dynamic` — указатель на стеке, в котором хранится адрес 4-байтового блока в куче. В Linux на x86-64 при выключенной рандомизации адресов (address randomization), как под отладчиком, ядро загружает такую программу по адресу `0x555555554000`, на двух третях высоты пользовательской половины размером $2^{47}$ байт, а стек начинает сразу под `0x7ffffffff000`; половина ядра начинается с `0xffff800000000000`. При включённой рандомизации, обычной настройке, эти базы сдвигаются при каждом запуске. Порядок областей не меняется: раздел «Код» сравнивает адреса объектов из каждой области и получает `text < rodata < data < bss < heap < stack` и в macOS, и в Linux. Сам C ничего не обещает об этом порядке; это соглашение операционной системы и компоновщика.

Указатель на локальную переменную действителен, только пока выполняется её функция. Вернуть `&local` из функции — значит вернуть адрес кадра стека, который следующий вызов займёт заново; `-Wall` об этом предупреждает.

## Неопределённое поведение \{#undefined-behaviour\}

Стандарт C определяет **неопределённое поведение** (undefined behaviour) как поведение, «к которому настоящий международный стандарт не предъявляет требований» ([C17](#references), §3.4.3). Оно отличается от двух более слабых категорий: поведение, *определяемое реализацией* (implementation-defined: знаковость `char`, размер `long`), каждый компилятор обязан документировать, а *неуточнённое* поведение (unspecified: порядок вычисления аргументов функции) должно быть одним из нескольких вариантов. На неопределённое поведение не наложено никаких ограничений. Типичные случаи в системном коде:

- переполнение знакового целого, например `INT_MAX + 1`;
- чтение или запись за пределами массива, в том числе на один элемент за его концом;
- разыменование нулевого или висячего (dangling) указателя (после `free` или на завершённый кадр стека);
- чтение неинициализированной локальной переменной;
- сдвиг на отрицательное число разрядов или не меньше ширины типа: `1 << 32` для 32-битного `int`;
- обращение к объекту через указатель несвязанного типа (правило *строгого алиасинга*, strict aliasing);
- обращение двух потоков к одной переменной без синхронизации, когда хотя бы один из них пишет (гонка данных, data race, начиная с C11).

Суть не в том, что такой код падает. Суть в том, что компилятор может **предполагать, что этого никогда не происходит**, и оптимизировать, исходя из этого предположения ([Lattner, 2011](#references)). Именно это предположение позволяет компилятору держать 32-битный счётчик цикла в 64-битном регистре или векторизовать цикл, не доказывая, что счётчик никогда не переполнится.

**Разобранный пример.** Функция `int next_is_bigger(int x) { return x + 1 > x; }` вызывается с `x = INT_MAX` = 2 147 483 647. При компиляции с `-O0` сложение переходит через границу и даёт −2 147 483 648, как это делает аппаратура с дополнительным кодом, сравнение ложно, и функция возвращает 0. При компиляции с `-O2` Clang рассуждает так: `x + 1 > x` выполняется для любого `x`, у которого `x + 1` не переполняется, а в корректной программе переполнения быть не может, — и компилирует функцию в `mov w0, #1; ret`: она возвращает 1, не глядя на `x`. Допустимы оба результата. Один исходный текст, два ответа, и ни один компилятор не ошибается.

Реальный код пострадал именно от таких рассуждений. В 2009 году драйвер Linux разыменовывал указатель и только потом проверял его на ноль; поскольку разыменование нулевого указателя было бы неопределённым поведением, GCC удалил проверку, и ошибка превратилась в уязвимость, которую можно было эксплуатировать. С тех пор ядро собирают с флагами `-fno-delete-null-pointer-checks`, `-fno-strict-aliasing` и `-fno-strict-overflow` (`Makefile` верхнего уровня ядра), которые превращают три вида неопределённого поведения в определённое ([Wang et al., 2012](#references)).

Три способа защиты, в порядке роста цены:

- **Предупреждения.** `-Wall -Wextra` ловят многие ошибки во время компиляции, например неинициализированную переменную или сравнение знакового с беззнаковым.
- **Санитайзеры** (sanitizers). `-fsanitize=undefined` добавляет проверку перед каждой операцией, которая может оказаться неопределённой, и печатает строку исходного текста, если проверка не прошла; `-fsanitize=address` окружает каждый объект «отравленной» памятью и ловит обращения за границы и использование после освобождения. Они замедляют программу (AddressSanitizer — в среднем на 73% на бенчмарках статьи, [Serebryany et al., 2012](#references)) и предназначены для тестирования.
- **Флаги, которые определяют поведение.** `-fwrapv` заставляет знаковое переполнение переходить через границу, ценой некоторой потери в оптимизации.

## От исходного файла к исполняемому: gcc и clang \{#from-source-file-to-executable-gcc-and-clang\}

`gcc` и `clang` — это *драйверы* (drivers): одна команда, которая по очереди запускает четыре стадии и удаляет промежуточные файлы, если её не попросить их сохранить.

<CompilePipeline />

1. **Препроцессор** (preprocessor). Обрабатывает строки, начинающиеся с `#`: `#include` вставляет текст другого файла, `#define` определяет макрос, который текстуально подставляется везде, где встречается, а `#if`/`#ifdef` оставляют или выбрасывают строки. `-E` останавливает сборку здесь и печатает результат.
2. **Компилятор** (compiler). Разбирает C после препроцессора, проверяет типы, оптимизирует и выдаёт ассемблер для целевой платформы. `-S` останавливает сборку здесь.
3. **Ассемблер** (assembler). Кодирует команды в машинный код в **объектном файле** (object file, `.o`), который содержит также таблицу символов и *записи перемещения* (relocation entries): пометки о том, куда позже нужно вписать адрес. `-c` останавливает сборку здесь.
4. **Компоновщик** (linker). Соединяет объектные файлы и библиотеки в исполняемый файл и вписывает эти адреса. Этой стадии посвящена [заметка о компоновке](/ru/notes/acos/linking-and-loading).

**Разобранный пример.** Программа hello-world из 6 строк из [первой заметки](/ru/notes/acos/computer-systems), собранная Apple clang 21 на macOS (arm64) с `-O0`: `clang -E` выдаёт 572 строки, почти все — объявления из `stdio.h`, и среди них та, что важна, `int printf(const char * restrict, ...)`; `clang -S` выдаёт 30 строк ассемблера arm64 с одной командой `bl _printf`; `clang -c` выдаёт объектный файл размером 744 байта, в таблице символов которого `_main` определён, а `_printf` не определён; компоновщик выдаёт исполняемый файл размером 33 432 байта. Те же шаги в Linux дают другие размеры, но те же четыре файла. GCC запускает стадии как отдельные программы (`cc1`, `as`, `ld`); Clang выполняет первые три внутри одного процесса. В обоих случаях стадии одни и те же.

Флаги, которые используются в курсе: `-std=c17` выбирает версию языка; `-Wall -Wextra` включают важные предупреждения (`-Wall` — это не «все»: `-Wextra` добавляет ещё, например `-Wsign-compare`); `-O0` компилирует буквально, так легче всего отлаживать, а `-O2` оптимизирует; `-g` сохраняет отладочную информацию для `gdb` и `lldb`; `-o name` задаёт имя выходного файла.

## Заголовочные файлы \{#header-files\}

Компилятор транслирует по одному файлу `.c` за раз — *единицу трансляции* (translation unit) — и ничего не знает об остальных. Чтобы вызвать функцию, определённую в другом месте, ему нужно её **объявление** (declaration): имя, типы параметров и тип возвращаемого значения. **Заголовочный файл** (header file, `.h`) собирает объявления, которые предлагает модуль: прототипы функций, определения `struct`, константы и макросы, а также `extern`-объявления глобальных переменных. Файл `.c` модуля содержит **определения** (definitions) — тела функций и сами переменные, — а каждый файл, который пользуется модулем, включает заголовок.

```c
/* stats.h */
#ifndef STATS_H                /* include guard: the second #include of this file is empty */
#define STATS_H

#include <stddef.h>            /* for size_t */

struct stats { long count; int min, max; double mean; };

int compute_stats(const int *values, size_t n, struct stats *out);

#endif
```

Из того, как работают стадии, следуют три правила. Определение помещается ровно в один файл `.c`: тело функции или инициализированная глобальная переменная в заголовке становятся повторным определением в каждом файле, который его включает, и компоновщик такое отвергает. Защита от повторного включения (include guard, или `#pragma once`) позволяет безопасно включить заголовок дважды в одну единицу трансляции, что случается, когда заголовки включают друг друга. А `static` у глобальной функции или переменной делает её локальной для файла: она никогда не видна компоновщику, так что в двух файлах может быть по `static`-функции с одним и тем же именем. `#include <...>` ищет в системных каталогах, `#include "..."` — сначала в каталоге того файла, в котором стоит `#include`.

## Небольшая программа, шаг за шагом \{#a-small-program-walked-through\}

Программа читает целые числа со стандартного ввода и печатает их количество, минимум, максимум и среднее. В ней три файла: `stats.h` выше, `stats.c` с вычислением и `main.c` с вводом и выводом (все три — в разделе «Код»).

1. **Препроцессор.** В обоих файлах `.c` строка `#include "stats.h"` вставляет объявления `struct stats` и `compute_stats`, так что оба файла согласны в раскладке структуры и сигнатуре функции. `main.c` включает также `stdio.h` ради `scanf` и `printf`, а `#define MAX_VALUES 1000` заменяет это имя на `1000` везде, где оно встречается.
2. **Где лежат данные.** `static int values[MAX_VALUES]` — инициализированный нулями массив, локальный для файла: 4000 байт в `.bss`. `struct stats s` — локальная переменная в кадре `main`. Строковые литералы формата `printf` лежат в `.rodata`.
3. **Указатели как аргументы.** `main` передаёт `values` (преобразованный в `&values[0]`), количество `n` и `&s`. `compute_stats` записывает результаты через `out->min`, то есть `(*out).min`: сохранение по смещению `offsetof(struct stats, min)` = 8 от адреса в `out`. Цикл ведёт указатель от `values` до `values + n` — то же преобразование, что компилятор сделал в отправной точке.
4. **Раскладка.** `struct stats` содержит `long` (8 байт), два `int` (4 + 4) и `double` (8): смещения 0, 8, 12 и 16, размер 24, без заполнения, потому что каждый член и так попадает на кратное своему выравниванию.
5. **Сборка.** `clang -std=c17 -Wall -Wextra main.c stats.c -o stats` компилирует два файла по отдельности и компонует их. В `main.o` символ `compute_stats` не определён; компоновщик находит его определение в `stats.o`.
6. **Запуск.** `printf '3 -1 4 1 5\n' | ./stats` печатает `count 5, min -1, max 5, mean 2.40`: среднее чисел 3, −1, 4, 1 и 5 равно 12 / 5 = 2.4. При пустом вводе `compute_stats` возвращает −1, и программа завершается с кодом 1.

## Что изменилось \{#what-changed\}

| | Ассемблер | C |
| --- | --- | --- |
| Регистры и смещения в стеке | выбираются вручную | выбирает компилятор |
| Размеры и шаги по элементам | запоминаются вручную (`addi a0, a0, 4`) | следуют из типов (`p + 1`, `sizeof`) |
| Раскладка данных | там, куда её поместил программист | задана правилами ABI: члены по порядку, с заполнением для выравнивания |
| Переносимость | один набор команд | любая платформа с компилятором C; размеры зависят от модели данных |
| Проверки | никаких | типы во время компиляции; никаких проверок границ и указателей во время выполнения |
| Ошибки | делают то, что сказано в командах | неопределённое поведение: оптимизатор может считать, что их никогда не бывает |

## Ограничения \{#limitations\}

- **Нет безопасности памяти.** Обращения за границы, использование после освобождения и разыменование нулевого указателя не обнаруживаются; в коде на C и C++ они дают большую долю уязвимостей.
- **Размеры различаются.** `long` занимает 4 или 8 байт, `char` знаковый или нет; переносимому коду нужны `<stdint.h>` и аккуратность с преобразованиями.
- **Неопределённое поведение коварно.** Код может работать при `-O0` и ломаться при `-O2` или работать с одной версией компилятора и ломаться со следующей.
- **Препроцессор работает с текстом.** Макросы не знают об областях видимости и типах: `#define SQUARE(x) x * x` делает `SQUARE(1 + 2)` равным 1 + 2 · 1 + 2 = 5.
- **Заголовки — это соглашение.** Ничто не заставляет заголовок и его файл `.c` согласовываться, кроме включения одного в другой; расхождение между объявлением и определением в разных файлах компилятор не диагностирует.

## Что нужно запомнить \{#what-you-should-remember\}

- Размеры типов C зависят от платформы: LP64 в 64-битных Linux и macOS (`int` 4, `long` и указатели 8), ILP32 на RV32. Когда ширина важна, нужен `<stdint.h>`.
- Указатель — это типизированный адрес; `a[i]` — это `*(a + i)`, а `p + i` прибавляет `i · sizeof(*p)` байт.
- Члены структуры размещаются по порядку, каждый по смещению, кратному его выравниванию; размер кратен наибольшему выравниванию. `struct rec` занимает 32 байта, её упорядоченная версия — 16. Это проверяется с помощью `offsetof` и `sizeof`.
- Код в `.text`, константы в `.rodata`, инициализированные глобальные переменные в `.data`, обнулённые глобальные в `.bss`, блоки `malloc` в куче, локальные переменные на стеке.
- Неопределённое поведение (знаковое переполнение, выход за границы, нулевые и висячие указатели, чтение неинициализированных переменных) позволяет компилятору считать, что его никогда не бывает: `x + 1 > x` превращается в 1 при `-O2`. Компилировать стоит с `-Wall -Wextra`, а тестировать — с `-fsanitize=address,undefined`.
- Драйвер запускает препроцессор (`-E`), компилятор (`-S`), ассемблер (`-c`) и компоновщик. Заголовки содержат объявления; каждое определение живёт в одном файле `.c`.

## Код \{#code\}

Все программы скомпилированы Apple clang 21 на macOS 26.5 (Apple M1) командой `clang -std=c17 -Wall -Wextra -O0 file.c -o prog`, если в комментарии не сказано иное.

Типы, преобразования, арифметика указателей, раскладка структур и порядок областей:

```c
// types.c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

struct rec { char tag; int count; char flag; double value; short id; };
struct rec_sorted { double value; int count; short id; char tag; char flag; };

int initialized = 42;                    /* .data */
int zeroed;                              /* .bss */
const char *greeting = "hello";          /* the pointer in .data, the characters in .rodata */

int main(void) {
    /* 1. sizes depend on the data model: LP64 here */
    printf("char %zu short %zu int %zu long %zu long long %zu pointer %zu\n",
           sizeof(char), sizeof(short), sizeof(int), sizeof(long), sizeof(long long), sizeof(void *));

    /* 2. implementation-defined and surprising conversions */
    char c = (char)200;
    printf("(char)200 = %d, -1 < 1u is %d, (uint8_t)300 = %d\n", c, -1 < 1u, (uint8_t)300);

    /* 3. pointer arithmetic is scaled by the size of the element */
    int a[4] = {10, 20, 30, 40};
    int *p = a;
    printf("*(p + 2) = %d, a[2] = %d, 2[a] = %d\n", *(p + 2), a[2], 2[a]);
    printf("bytes from a to p + 2: %td, elements from a to &a[3]: %td\n",
           (char *)(p + 2) - (char *)a, &a[3] - a);

    /* 4. struct layout: each member at a multiple of its alignment */
    printf("rec: tag %zu count %zu flag %zu value %zu id %zu, size %zu\n",
           offsetof(struct rec, tag), offsetof(struct rec, count), offsetof(struct rec, flag),
           offsetof(struct rec, value), offsetof(struct rec, id), sizeof(struct rec));
    printf("rec_sorted: value %zu count %zu id %zu tag %zu flag %zu, size %zu\n",
           offsetof(struct rec_sorted, value), offsetof(struct rec_sorted, count), offsetof(struct rec_sorted, id),
           offsetof(struct rec_sorted, tag), offsetof(struct rec_sorted, flag), sizeof(struct rec_sorted));

    /* 5. where things live: compare addresses of the regions */
    int local = 1;
    int *dynamic = malloc(sizeof *dynamic);
    uintptr_t text = (uintptr_t)main, rodata = (uintptr_t)greeting, data = (uintptr_t)&initialized,
              bss = (uintptr_t)&zeroed, heap = (uintptr_t)dynamic, stack = (uintptr_t)&local;
    printf("text < rodata < data < bss < heap < stack: %d\n",
           text < rodata && rodata < data && data < bss && bss < heap && heap < stack);
    free(dynamic);
    return 0;
}
// char 1 short 2 int 4 long 8 long long 8 pointer 8
// (char)200 = -56, -1 < 1u is 0, (uint8_t)300 = 44          (200 where char is unsigned, as on RISC-V)
// *(p + 2) = 30, a[2] = 30, 2[a] = 30
// bytes from a to p + 2: 8, elements from a to &a[3]: 3
// rec: tag 0 count 4 flag 8 value 16 id 24, size 32
// rec_sorted: value 0 count 8 id 12 tag 14 flag 15, size 16
// text < rodata < data < bss < heap < stack: 1
```

Неопределённое поведение на двух уровнях оптимизации и под двумя санитайзерами:

```c
// ub.c
#include <limits.h>
#include <stdio.h>

int next_is_bigger(int x) { return x + 1 > x; }   /* undefined when x == INT_MAX */

int sum4(const int *a) {
    int s = 0;
    for (int i = 0; i <= 4; i++)                  /* off by one: reads a[4] */
        s += a[i];
    return s;
}

int main(void) {
    int a[4] = {1, 2, 3, 4};
    printf("next_is_bigger(INT_MAX) = %d\n", next_is_bigger(INT_MAX));
    printf("sum4 = %d\n", sum4(a));
    return 0;
}
// -O0:  next_is_bigger(INT_MAX) = 0     sum4 = -137658102   (garbage: 10 plus whatever follows a[3]; changes between builds)
// -O2:  next_is_bigger(INT_MAX) = 1     sum4 = 1            (different garbage)
// -O0 -fsanitize=undefined:
//   ub.c:5:38: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
// -O0 -fsanitize=address:
//   ERROR: AddressSanitizer: stack-buffer-overflow on address ...
//   READ of size 4 ... in sum4
```

Что добавляют флаги предупреждений. Без флагов этот файл компилируется молча:

```c
// warn.c: clang -std=c17 -Wall -Wextra -O0 -c warn.c
#include <stddef.h>

long total(const int *values, size_t n) {
    long sum;                          /* never initialized */
    for (int i = 0; i < n; i++)        /* int compared with size_t */
        sum += values[i];
    return sum;
}
// -Wall adds:   warn.c:7:9: warning: variable 'sum' is uninitialized when used here [-Wuninitialized]
// -Wextra adds: warn.c:6:23: warning: comparison of integers of different signs: 'int' and 'size_t' (aka 'unsigned long') [-Wsign-compare]
```

Разобранная программа в трёх файлах (`stats.h` — как в разделе о заголовочных файлах):

```c
// stats.c
#include "stats.h"

int compute_stats(const int *values, size_t n, struct stats *out) {
    if (n == 0)
        return -1;
    long long total = 0;
    out->min = out->max = values[0];
    for (const int *p = values; p < values + n; p++) {   /* walk with a pointer */
        if (*p < out->min) out->min = *p;
        if (*p > out->max) out->max = *p;
        total += *p;
    }
    out->count = (long)n;
    out->mean = (double)total / n;
    return 0;
}
```

```c
// main.c: clang -std=c17 -Wall -Wextra -O0 main.c stats.c -o stats && printf '3 -1 4 1 5\n' | ./stats
#include <stdio.h>
#include "stats.h"

#define MAX_VALUES 1000

static int values[MAX_VALUES];            /* zero-initialized storage: .bss */

int main(void) {
    size_t n = 0;
    while (n < MAX_VALUES && scanf("%d", &values[n]) == 1)
        n++;
    struct stats s;                       /* automatic storage: the stack */
    if (compute_stats(values, n, &s) != 0) {
        fprintf(stderr, "no input\n");
        return 1;
    }
    printf("count %ld, min %d, max %d, mean %.2f, sizeof(struct stats) %zu\n",
           s.count, s.min, s.max, s.mean, sizeof s);
    return 0;
}
// count 5, min -1, max 5, mean 2.40, sizeof(struct stats) 24
// with empty input: "no input" on stderr, exit status 1
```
