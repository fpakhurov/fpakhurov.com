[Предыдущая заметка](/ru/notes/acos/memory-allocation) управляла кучей одной программы так, будто на машине больше ничего не работает. Реальная система одновременно выполняет оболочку, редактор, компилятор и десятки фоновых служб на нескольких ядрах. Каждая программа должна считать, что процессор и память принадлежат только ей, ни одна не должна читать или портить чужую кучу, и все должны продвигаться. Операционная система достигает этого одной абстракцией — **процессом** (process): работающей программой вместе со всем, что нужно, чтобы остановить её и позже продолжить. Эта заметка определяет процесс, прослеживает жизнь одного процесса от `fork` до `wait`, добавляет **потоки** (threads), которые позволяют одной программе выполняться на нескольких ядрах над одной общей кучей, а затем переходит к **планировщику** (scheduler) — части ядра, которая решает, кто будет выполняться следующим, — и к цене переключения между ними.

**Обозначения.** В разделах о планировании задание $i$ прибывает в момент $a_i$, нуждается в $b_i$ миллисекундах процессорного времени (его *длительность работы*, burst), впервые запускается в момент $s_i$ и завершается в момент $c_i$. Его **время оборота** (turnaround time) — $T_i = c_i - a_i$, **время ожидания** (waiting time) — $W_i = T_i - b_i$ (время, когда задание готово, но не выполняется), а **время отклика** (response time) — $R_i = s_i - a_i$.

## Отправная точка: одна программа за раз \{#baseline-one-program-at-a-time\}

Самые ранние системы выполняли одно задание от начала до конца, затем следующее. Но программа не вычисляет всё время: она читает файл, ждёт диска, ждёт нажатия клавиши. Пока она ждёт, процессору нечего делать. Задание, которое 10 мс вычисляет, а затем 40 мс ждёт диска, занимает процессор $10 / (10 + 40) = 20\,\%$ времени.

**Мультипрограммирование** (multiprogramming) держит в памяти несколько заданий и отдаёт процессор другому, как только текущее начинает ждать. С пятью такими заданиями, каждое из которых ждёт, пока вычисляют остальные, процессор в лучшем случае может быть занят всё время. **Разделение времени** (time sharing) добавляет таймер: даже задание, которое никогда не ждёт, прерывается через несколько миллисекунд, чтобы каждый пользователь за терминалом быстро видел ответ. Обоим нужно от аппаратуры и ядра одно и то же: способ остановить работающую программу на любой команде, сохранить её в целости, выполнить другую и позже продолжить первую так, будто ничего не произошло. И обоим нужна защита, поскольку задания, разделяющие одну память, не должны иметь возможности затирать друг друга.

## Процесс \{#the-process\}

<aside class="callout"><strong>Ключевая идея.</strong> Процесс — выполняющаяся программа вместе с состоянием, нужным, чтобы приостановить и продолжить её: частным адресным пространством, сохранёнными регистрами в блоке управления в ядре и открытыми файлами. <code>fork</code> копирует это состояние в новый процесс, <code>exec</code> заменяет программу внутри процесса, <code>exit</code> и <code>wait</code> завершают его и передают его статус родителю. Поток — это ещё один набор регистров и ещё один стек внутри того же адресного пространства.</aside>

### Адресное пространство \{#the-address-space\}

У каждого процесса своё виртуальное адресное пространство: внизу код, затем инициализированные и обнулённые данные, растущая вверх куча, разделяемые библиотеки и другие отображения посередине и растущий вниз от вершины стек. [Виртуальная память](/ru/notes/acos/virtual-memory) делает его частным: один и тот же виртуальный адрес в двух процессах переводится через две разные таблицы страниц в два разных физических кадра, и у процесса нет способа назвать память, которую ему не дали. Два запуска одной программы — это два процесса с одинаковым кодом и раздельными данными.

### Блок управления процессом \{#the-process-control-block\}

Всё, что ядро знает о процессе, хранится в структуре данных ядра — **блоке управления процессом** (process control block, PCB); в Linux это `struct task_struct`. В нём хранятся:

- **идентификатор процесса** (process identifier, PID) и PID родителя;
- **состояние** (ниже);
- **сохранённые регистры**, включая счётчик команд и указатель стека, действительные, пока процесс не выполняется;
- **карта памяти**: корень таблицы страниц и список отображённых областей;
- таблица **открытых файлов**, индексируемая файловым дескриптором;
- сведения для планирования (приоритет, использованное время), учётные данные (пользователь и группа), настройки сигналов, учёт ресурсов.

### Состояния \{#states\}

Процесс находится в одном из немногих состояний. Он **выполняется** (running), пока его исполняет ядро процессора, **готов** (ready), когда мог бы выполняться, но свободного ядра нет, и **заблокирован** (blocked; говорят также «ожидает» или «спит»), пока ждёт события: чтения с диска, нажатия клавиши, завершения потомка. Прерывание таймера возвращает выполняющийся процесс в готовые; системный вызов, которому нужно ждать, переводит его в заблокированные; событие, о котором сообщает прерывание, возвращает его в готовые. В начале создаваемый процесс находится в состоянии **новый** (new); в конце процесс, который завершился, но статус которого родитель ещё не забрал, — **зомби** (zombie): это состояние Unix называет завершённым.

<ProcessStates />

Переходы в состояние выполнения и из него — это те места, где ядро получает управление. Оно никогда не «наблюдает» за выполняющимся процессом: оно работает, только когда процесс делает системный вызов или когда приходит [прерывание или исключение](/ru/notes/acos/exceptions-and-interrupts). Именно прерывание таймера гарантирует, что ядро вернёт себе управление даже от программы, застрявшей в бесконечном цикле.

## Создание процесса: fork, exec и wait \{#creating-a-process-fork-exec-and-wait\}

Unix создаёт процессы в два шага, которые являются отдельными системными вызовами ([Ritchie and Thompson, 1974](#references); [Kerrisk, 2010](#references), главы 24–27).

- **`fork()`** создаёт дочерний процесс (child), который является копией вызывающего: та же программа, то же содержимое памяти, те же открытые файлы, те же регистры. Он возвращается дважды, по разу в каждом процессе: в родителе (parent) возвращает PID потомка, в потомке — 0. Это возвращаемое значение — единственное различие, и программа ветвится по нему.
- **`exec(path, argv, ...)`** (семейство: `execl`, `execvp`, `execve` и другие) заменяет программу внутри вызывающего процесса. Ядро отбрасывает старое адресное пространство, загружает новый исполняемый файл так же, как это делает [загрузчик](/ru/notes/acos/linking-and-loading), и запускает его с точки входа. PID остаётся прежним, как и открытые файловые дескрипторы, если они не помечены флагом close-on-exec. Успешный `exec` никогда не возвращается: кода, который его вызвал, больше не существует.
- **`exit(status)`** завершает процесс. Ядро закрывает его файлы и освобождает его память, но сохраняет его PCB со статусом завершения.
- **`wait(&status)`** или **`waitpid(pid, &status, 0)`** блокирует родителя, пока потомок не завершится, затем возвращает PID и статус потомка (`WEXITSTATUS(status)` при нормальном завершении, `WTERMSIG(status)` для потомка, убитого сигналом) и позволяет ядру освободить PCB потомка.

<ForkExecWait />

1. Родитель вызывает `fork`. Ядро выделяет потомку PCB и PID и копирует таблицу файлов и карту памяти родителя.
2. Оба процесса возвращаются из `fork`: родитель получает PID потомка, потомок — 0.
3. Потомок вызывает `exec`. Его адресное пространство заменяется новой программой; PID и открытые файлы сохраняются.
4. Потомок вызывает `exit` и становится зомби, который хранит только свой статус завершения.
5. Родитель, заблокированный в `waitpid`, просыпается со статусом, и ядро удаляет зомби.

**Копирования в основном удаётся избежать.** Копировать большое адресное пространство при каждом `fork`, только чтобы выбросить его при следующем `exec`, было бы расточительно. Вместо этого ядро копирует таблицы страниц и помечает каждую доступную для записи страницу как доступную только для чтения в обоих процессах: это **копирование при записи** (copy-on-write). Пока ни один процесс не пишет, они разделяют физические кадры. Первая запись в страницу вызывает страничный отказ, и тогда ядро копирует эту одну страницу и делает обе копии доступными для записи. `fork`, за которым следует `exec`, почти ничего не копирует.

**Почему два шага.** Между `fork` и `exec` потомок выполняет код родителя со своей копией таблицы файлов, поэтому он может перестроить свои файлы до запуска новой программы. Оболочка выполняет `ls > out.txt` так: делает `fork`, открывает `out.txt` в потомке, дублирует этот дескриптор на дескриптор 1 (стандартный вывод) вызовом `dup2` и затем вызывает `exec("ls")`. `ls` пишет в дескриптор 1, как всегда, и никогда не узнаёт, куда идёт его вывод. [Заметка о межпроцессном взаимодействии](/ru/notes/acos/inter-process-communication) так же соединяет две программы каналом.

**Разобранный пример.** В первой программе раздела «Код» есть глобальная переменная `counter = 100`. Потомок прибавляет 1 и печатает 101, затем выполняет `exec` для `echo`. Родитель после `waitpid` печатает 100: потомок изменил собственную копию страницы, которую копирование при записи отделило от родительской при первой записи. У процесса `echo` PID потомка, но ничего из его памяти.

### Зомби и сироты \{#zombies-and-orphans\}

Завершившийся процесс остаётся в таблице процессов как **зомби**, пока его родитель не вызовет `wait`, потому что статус завершения нужно где-то хранить, пока кто-нибудь о нём не спросит. В разделе «Код» потомок завершается сразу, пока его родитель спит секунду; `ps` показывает его состояние как `Z`, пока `waitpid` родителя не вернёт код завершения 7, после чего PID больше не существует. Один зомби стоит лишь записи в таблице, но сервер, который порождает потомков и никогда их не ждёт, накапливает зомби, пока у него не закончатся PID.

**Сирота** (orphan) — процесс, родитель которого завершился первым. Ядро даёт ему нового родителя: PID 1 (`init` или `systemd` в Linux, `launchd` в macOS) или в Linux ближайшего предка, объявившего себя *subreaper* (процессом, который забирает осиротевших потомков). Новый родитель вызывает `wait` для каждого унаследованного потомка, поэтому сироты не остаются зомби. В разделе «Код» внук переживает своего родителя и затем сообщает, что PID его нового родителя — 1. Поэтому все процессы образуют одно дерево с корнем в PID 1.

## Потоки \{#threads\}

Процесс выполняет одну последовательность команд за раз. Чтобы использовать несколько ядер или продолжать вычислять, пока одна задача ждёт сеть, программа может создать несколько **потоков**. Поток — независимый поток управления внутри процесса: у него свои счётчик команд, регистры и стек, а всё остальное он разделяет с другими потоками процесса: код, глобальные данные, кучу, открытые файлы ([Arpaci-Dusseau, 2018](#references), глава 26).

| | Отдельные процессы | Потоки одного процесса |
| --- | --- | --- |
| Адресное пространство | у каждого своё, частное | одно, общее |
| Создаются вызовом | `fork` (копирует таблицы страниц) | `pthread_create` (выделяет стек) |
| Взаимодействуют через | ядро: каналы, файлы, объекты разделяемой памяти | обычные переменные |
| Сбой или ошибочная запись | убивает один процесс | убивает или портит весь процесс |
| Переключение между ними | меняет таблицу страниц | сохраняет таблицу страниц |
| Своё у каждого потока | всё | регистры, стек, локальные переменные потока |

Интерфейс C — потоки POSIX (pthreads) ([Kerrisk, 2010](#references), глава 29). `pthread_create(&t, NULL, f, arg)` запускает поток, выполняющий `f(arg)`; `pthread_join(t, &result)` ждёт его возврата и забирает результат, как `wait` для процесса; `pthread_detach` позволяет освободить ресурсы потока при его завершении, даже если никто его не присоединяет. В Linux и macOS каждый pthread — это поток ядра, который планируется самостоятельно; в Linux и потоки, и процессы создаются одним системным вызовом, `clone`, с флагами, которые говорят, что новая задача разделяет со своим создателем.

**Разобранный пример.** Во второй программе раздела «Код» два потока прибавляют каждый свой номер (1 и 2) к глобальной переменной `counter = 100`, и каждый хранит локальную переменную на своём стеке. После присоединения обоих `main` печатает `counter=103`: в отличие от примера с `fork`, все потоки писали в одну и ту же переменную. Чтобы этот пример оставался правильным, второй поток запускается только после завершения первого. Два потока, одновременно обновляющие одну переменную, — тема [следующей заметки](/ru/notes/acos/synchronization) и причина, по которой программировать потоки труднее, чем процессы.

## Планирование: кто выполняется следующим \{#scheduling-who-runs-next\}

Ядро отделяет **механизм** (mechanism) от **политики** (policy). Механизм — описанное ниже переключение контекста — может остановить любой процесс и продолжить любой другой. **Планировщик** — это политика, которая выбирает, какой готовый процесс выполняется следующим и как долго. Его цели противоречат друг другу: короткое время оборота для пакетной работы, короткое время отклика для интерактивных программ, справедливость и малые потери времени на переключения.

Четыре задания делают различия наглядными:

| Задание | Прибывает (мс) | Длительность работы (мс) |
| --- | --- | --- |
| A | 0 | 6 |
| B | 1 | 3 |
| C | 2 | 7 |
| D | 4 | 2 |

- **«Первым пришёл — первым обслужен»** (first come, first served, FIFO) выполняет задания до конца в порядке прибытия: A 0–6, B 6–9, C 9–16, D 16–18. D, самое короткое задание, ждёт 12 мс за длинными. Это *эффект конвоя* (convoy effect): короткие задания стоят в очереди за длинными, как легковые машины за грузовиком.
- **«Сначала кратчайшее задание»** (shortest job first, SJF) тоже выполняет каждое задание до конца, но, когда процессор освобождается, выбирает готовое задание с наименьшей длительностью работы: A 0–6, затем D 6–8 (в момент 6 готовы B с 3, C с 7 и D с 2), B 8–11, C 11–18. Если все задания прибывают одновременно, запуск кратчайшего первым минимизирует среднее время ожидания: перестановка более короткого задания перед более длинным уменьшает ожидание короткого сильнее, чем увеличивает ожидание длинного.
- **«Сначала наименьшее оставшееся время»** (shortest time to completion first, STCF; SJF с вытеснением) принимает решение заново при каждом прибытии задания: A выполняется 0–1, прибывает B с 3 мс против оставшихся у A 5 и забирает процессор на 1–4, затем D 4–6, A 6–11, C 11–18.
- **Циклическое планирование** (round robin, RR) по очереди даёт каждому готовому заданию **квант** (quantum) в 2 мс и ставит его в конец очереди, если оно не закончено (здесь задание, прибывшее во время кванта, встаёт в очередь раньше вытесняемого): A 0–2, B 2–4, C 4–6, A 6–8, D 8–10, B 10–11, C 11–13, A 13–15, C 15–18.

<SchedulingGantt />

| Политика | Среднее время оборота (мс) | Среднее время ожидания (мс) | Среднее время отклика (мс) |
| --- | --- | --- | --- |
| FIFO | 10.5 | 6.0 | 6.0 |
| SJF | 9.0 | 4.5 | 4.5 |
| STCF | 8.0 | 3.5 | 2.25 |
| RR, квант 2 мс | 11.75 | 7.25 | 1.75 |

У циклического планирования худшее время оборота и лучшее время отклика: каждое задание начинает выполняться через несколько миллисекунд после прибытия, и именно это замечает пользователь за клавиатурой, но и завершается каждое задание поздно, потому что делит процессор до самого конца. Компромисс задаёт квант. Длинный квант делает RR похожим на FIFO; короткий улучшает отклик, но переключения происходят чаще, а каждое стоит времени (последний раздел). SJF и STCF нужно заранее знать длительности работы, а система общего назначения их не знает.

### Многоуровневая очередь с обратной связью \{#the-multi-level-feedback-queue\}

**Многоуровневая очередь с обратной связью** (multi-level feedback queue, MLFQ), впервые применённая в системе разделения времени CTSS в начале 1960-х годов, узнаёт длительности работы, наблюдая за заданиями ([Arpaci-Dusseau, 2018](#references), глава 8). Она хранит несколько очередей с убывающим приоритетом и следует нескольким правилам:

1. Готовое задание из очереди с более высоким приоритетом всегда выполняется раньше задания из более низкой очереди; задания одной очереди делят процессор циклически.
2. Новое задание попадает в самую высокую очередь, поэтому получает короткое время отклика и считается интерактивным, пока не докажет обратное.
3. Задание, израсходовавшее свою долю времени (allotment) на одном уровне, за один раз или за несколько, опускается на уровень ниже. Задания, которые долго вычисляют, опускаются; задания, которые работают недолго и затем ждут ввода, остаются наверху.
4. Периодически каждое задание возвращается наверх, чтобы длинные задания не голодали вечно и чтобы задание, ставшее интерактивным, снова было замечено.

MLFQ приближает STCF, не зная будущего: короткие и интерактивные задания остаются в быстрых очередях, а длинные вычисления выполняются, когда не готово ничего более срочного. Учёт доли времени по нескольким отрезкам (правило 3) закрывает лазейку: иначе программа могла бы оставаться наверху, отдавая процессор перед самым концом своего кванта.

### Справедливое разделение: CFS и EEVDF \{#fair-sharing-cfs-and-eevdf\}

В 2007 году Linux выбрал другой подход — **полностью справедливый планировщик** (Completely Fair Scheduler, CFS). У каждой задачи есть **виртуальное время выполнения** (virtual run time), которое растёт, пока она выполняется, со скоростью, обратно пропорциональной её весу; планировщик всегда выполняет задачу с наименьшим виртуальным временем выполнения, а задачи хранятся в красно-чёрном дереве, упорядоченном по нему ([Linux CFS documentation](#references)). Веса берутся из значения *nice* задачи: 1024 для nice 0, 820 для nice 1, 335 для nice 5, каждый шаг примерно в 1.25 раза больше следующего ([Linux `sched_prio_to_weight`](#references)). Две всегда готовые задачи с nice 0 и nice 5 делят ядро в отношении своих весов, $1024 / (1024 + 335) = 75.3\,\%$ против $24.7\,\%$, и за 100 мс оба виртуальных времени выполнения продвигаются на одни и те же 75.3 мс: у задачи, которая работала втрое дольше, втрое больший вес. Спящая задача не накапливает виртуального времени выполнения, поэтому, проснувшись, она имеет наименьшее значение и скоро запускается, что даёт преимущество интерактивным задачам без какой-либо явной классификации. Начиная с версии 6.6 ядро переходит на **EEVDF** (earliest eligible virtual deadline first, «сначала допустимая задача с самым ранним виртуальным сроком»), который сохраняет веса и виртуальное время выполнения и добавляет каждой задаче срок, чтобы задачи с короткими квантами могли получать процессор раньше ([Linux EEVDF documentation](#references)).

## Переключения контекста \{#context-switches\}

Переключение процессора с одного процесса на другой — это **переключение контекста** (context switch). Оно происходит внутри ядра, после того как прерывание таймера или блокирующий системный вызов передали туда управление:

1. ловушка уже сохранила пользовательские регистры старого процесса; ядро записывает их вместе с указателем стека ядра в PCB старого процесса;
2. планировщик выбирает следующий процесс;
3. ядро переключается на стек ядра нового процесса и загружает его сохранённые регистры;
4. оно переключает адресное пространство: в RISC-V записью корня новой таблицы страниц в регистр `satp`, поле идентификатора адресного пространства (address-space identifier, ASID) которого позволяет TLB различать записи нескольких процессов, а не сбрасывать их;
5. оно возвращается в пользовательский режим, и новый процесс продолжает с того места, где был остановлен.

Переключение между двумя потоками одного процесса пропускает шаг 4. Прямая цена — несколько микросекунд. На используемой здесь машине (Apple M1, macOS 26, clang `-O0`) два процесса, передающие один байт туда и обратно через два канала, тратили от 3.3 до 4.1 мкс на один круг в девяти запусках; каждый круг включает четыре системных вызова (пустой системный вызов, `getppid`, занимал на той же машине около 0.12 мкс) и два пробуждения заблокированного процесса, возможно на разных ядрах, так что измеряется вся передача управления, а не одно переключение. Косвенная цена часто больше: новый процесс находит кэши и TLB заполненными данными старого и работает медленно, пока не заполнит их заново. Поэтому квант измеряется миллисекундами, а не микросекундами.

## Ограничения \{#limitations\}

- **Планировщик знает мало.** Он видит только прошлое поведение; MLFQ и CFS — эвристики, и обе можно обмануть или сбить с толку (задача, которая часто и ненадолго засыпает, выглядит интерактивной).
- **Переключения контекста не бесплатны.** Мелкое квантование времени и много потоков на ядро тратят время в ядре и на повторное заполнение кэшей.
- **Разделение ломает изоляцию.** Потоки отказываются от защиты отдельных адресных пространств: ошибка в одном потоке портит данные всех.
- **Больше одного ядра.** Эта заметка планировала один процессор. Настоящие планировщики держат очередь готовых задач на каждое ядро, балансируют нагрузку между ними и стараются держать задачу на том ядре, кэш которого хранит её данные; у [многоядерных процессоров](/ru/notes/acos/thread-level-parallelism) свои издержки.

## Что нужно запомнить \{#what-you-should-remember\}

- Процесс — выполняющаяся программа: частное адресное пространство, PCB с сохранёнными регистрами и состоянием и таблица открытых файлов.
- Состояния: новый, готов, выполняется, заблокирован, зомби. Управление ядру дают только прерывание или системный вызов; прерывание таймера гарантирует, что оно его получит.
- `fork` возвращается дважды (PID потомка в родителе, 0 в потомке) и разделяет память с копированием при записи; `exec` заменяет программу и сохраняет PID и открытые файлы; `wait` забирает статус завершения и удаляет зомби.
- Завершившийся потомок остаётся зомби, пока родитель его не дождётся; сироту усыновляет PID 1 или subreaper, который его и дожидается.
- Потоки разделяют адресное пространство, кучу и файлы и владеют только регистрами и стеком. Их дешевле создавать и переключать, и между ними возможны гонки.
- FIFO страдает от конвоев, SJF и STCF нужны длительности работы, циклическое планирование меняет время оборота на время отклика; MLFQ узнаёт, какие задания интерактивны, CFS и EEVDF делят процессор пропорционально весам через виртуальное время выполнения.
- Переключение контекста сохраняет и загружает регистры и переключает таблицы страниц; его прямая цена — микросекунды, а холодные кэши добавляют ещё.

## Код \{#code\}

Жизнь процесса: `fork`, `exec` и `waitpid`, затем зомби, каким его видит `ps`, затем сирота, который сообщает о своём новом родителе. Скомпилировать и запустить: `clang -std=c17 -Wall -Wextra -O0 proc.c -o proc && ./proc`:

```c
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int counter = 100;                                   /* after fork, each process has its own copy */

static void show_state(pid_t pid, const char *when) {
    char cmd[64], st[16] = "";
    snprintf(cmd, sizeof cmd, "ps -o stat= -p %d", (int)pid);
    FILE *ps = popen(cmd, "r");
    if (ps && fgets(st, sizeof st, ps)) st[strcspn(st, " \n")] = '\0';
    if (ps) pclose(ps);
    printf("%s: state %s\n", when, st[0] ? st : "(gone)");
}

int main(void) {
    /* 1. fork, exec, wait */
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {                                  /* child: fork returned 0 */
        counter += 1;
        printf("child:  counter=%d\n", counter);
        fflush(stdout);                              /* exec discards unflushed stdio buffers */
        execlp("echo", "echo", "child:  now running echo in the same process", (char *)NULL);
        perror("execlp");                            /* reached only if exec failed */
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);                        /* parent: fork returned the child's pid */
    printf("parent: counter=%d, child exit code %d\n", counter, WEXITSTATUS(status));

    /* 2. a zombie: the child has exited, the parent has not waited yet */
    pid_t z = fork();
    if (z == 0) _exit(7);
    sleep(1);
    show_state(z, "zombie before wait");
    waitpid(z, &status, 0);
    show_state(z, "after wait");
    printf("exit code collected: %d\n", WEXITSTATUS(status));

    /* 3. an orphan: the middle process exits before its own child */
    int fd[2];
    pipe(fd);
    pid_t mid = fork();
    if (mid == 0) {
        pid_t me = getpid();
        if (fork() == 0) {
            int before = getppid() == me;
            sleep(1);                                /* the middle process exits meanwhile */
            dprintf(fd[1], "orphan: parent was the middle process: %s; new parent pid: %d\n", before ? "yes" : "no", (int)getppid());
            _exit(0);
        }
        _exit(0);
    }
    waitpid(mid, NULL, 0);
    close(fd[1]);
    char buf[96];
    ssize_t n = read(fd[0], buf, sizeof buf - 1);    /* blocks until the orphan writes */
    if (n > 0) { buf[n] = '\0'; fputs(buf, stdout); }
    return 0;
}
/* Output (macOS 26; on Linux the new parent can be a subreaper instead of 1):
child:  counter=101
child:  now running echo in the same process
parent: counter=100, child exit code 0
zombie before wait: state Z
after wait: state (gone)
exit code collected: 7
orphan: parent was the middle process: yes; new parent pid: 1
*/
```

Два потока разделяют одну глобальную переменную, и у каждого свой стек:

```c
#include <pthread.h>
#include <stdio.h>

int counter = 100;                                   /* one copy, shared by every thread of the process */

static void *worker(void *arg) {
    int id = *(int *)arg;
    int local = id * 10;                             /* on this thread's own stack */
    counter += id;                                   /* the threads run one after another below, so no race */
    printf("thread %d: local=%d\n", id, local);
    return NULL;
}

int main(void) {
    pthread_t t[2];
    int ids[2] = {1, 2};
    for (int i = 0; i < 2; i++) {
        pthread_create(&t[i], NULL, worker, &ids[i]);
        pthread_join(t[i], NULL);                    /* wait for each before starting the next */
    }
    printf("main: counter=%d\n", counter);           /* 100 + 1 + 2: both threads wrote the same variable */
    return 0;
}
/* Output:
thread 1: local=10
thread 2: local=20
main: counter=103
*/
```

Пример планирования и доли CFS (`python3 sched.py`):

```python
jobs = [('A', 0, 6), ('B', 1, 3), ('C', 2, 7), ('D', 4, 2)]   # имя, прибытие, длительность работы (мс)

def fifo(jobs):
    t, g = 0, []
    for n, a, b in sorted(jobs, key=lambda j: j[1]):
        t = max(t, a); g.append((n, t, t + b)); t += b
    return g

def sjf(jobs):                                   # без вытеснения: кратчайшее задание среди уже прибывших
    left, t, g = list(jobs), 0, []
    while left:
        ready = [j for j in left if j[1] <= t] or [min(left, key=lambda j: j[1])]
        n, a, b = min(ready, key=lambda j: (j[2], j[1]))
        t = max(t, a); g.append((n, t, t + b)); t += b; left.remove((n, a, b))
    return g

def stcf(jobs):                                  # с вытеснением: наименьшее оставшееся время, решение каждую 1 мс
    rem = {n: b for n, _, b in jobs}; arr = {n: a for n, a, _ in jobs}; t, g = 0, []
    while any(rem.values()):
        ready = [n for n in rem if rem[n] and arr[n] <= t]
        if not ready: t += 1; continue
        n = min(ready, key=lambda n: (rem[n], arr[n]))
        g[-1:] = [(n, g[-1][1], t + 1)] if g and g[-1][0] == n and g[-1][2] == t else g[-1:] + [(n, t, t + 1)]
        rem[n] -= 1; t += 1
    return g

def rr(jobs, q):                                 # задание, прибывшее во время кванта, встаёт в очередь раньше вытесненного
    rem = {n: b for n, _, b in jobs}; pending = sorted(jobs, key=lambda j: j[1]); queue, t, g = [], 0, []
    def admit():
        while pending and pending[0][1] <= t: queue.append(pending.pop(0)[0])
    admit()
    while queue or pending:
        if not queue: t = pending[0][1]; admit(); continue
        n = queue.pop(0); run = min(q, rem[n])
        g[-1:] = [(n, g[-1][1], t + run)] if g and g[-1][0] == n else g[-1:] + [(n, t, t + run)]
        t += run; rem[n] -= run; admit()
        if rem[n]: queue.append(n)
    return g

for name, g in (('FIFO', fifo(jobs)), ('SJF', sjf(jobs)), ('STCF', stcf(jobs)), ('RR q=2', rr(jobs, 2))):
    T = W = R = 0
    for n, a, b in jobs:
        segs = [s for s in g if s[0] == n]
        T += segs[-1][2] - a; W += segs[-1][2] - a - b; R += segs[0][1] - a
    print(f"{name:7}", ' '.join(f'{n}{s}-{e}' for n, s, e in g), '| turnaround', T / 4, 'waiting', W / 4, 'response', R / 4)
# FIFO    A0-6 B6-9 C9-16 D16-18 | turnaround 10.5 waiting 6.0 response 6.0
# SJF     A0-6 D6-8 B8-11 C11-18 | turnaround 9.0 waiting 4.5 response 4.5
# STCF    A0-1 B1-4 D4-6 A6-11 C11-18 | turnaround 8.0 waiting 3.5 response 2.25
# RR q=2  A0-2 B2-4 C4-6 A6-8 D8-10 B10-11 C11-13 A13-15 C15-18 | turnaround 11.75 waiting 7.25 response 1.75

w0, w5 = 1024, 335                               # веса Linux для nice 0 и nice 5
share = w0 / (w0 + w5)
ran0, ran5 = 100 * share, 100 * (1 - share)       # мс из интервала в 100 мс
print(round(share, 3), round(ran0, 1), round(ran5, 1), round(ran0 * 1024 / w0, 1), round(ran5 * 1024 / w5, 1))
# 0.753 75.3 24.7 75.3 75.3: unequal real time, equal virtual run time
```

Передача управления между двумя процессами через два канала. Время различается между машинами и запусками; комментарий приводит один запуск:

```c
#include <stdio.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define ROUNDS 100000

static double now(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec * 1e-9; }

int main(void) {
    int ab[2], ba[2];
    pipe(ab); pipe(ba);
    char c = 'x';
    if (fork() == 0) {                               /* child: echo every byte back */
        for (int i = 0; i < ROUNDS; i++) { read(ab[0], &c, 1); write(ba[1], &c, 1); }
        _exit(0);
    }
    double t0 = now();
    for (int i = 0; i < ROUNDS; i++) { write(ab[1], &c, 1); read(ba[0], &c, 1); }
    double t1 = now();
    wait(NULL);
    printf("round trip: %.1f us\n", (t1 - t0) / ROUNDS * 1e6);
    return 0;
}
/* One run on an Apple M1, macOS 26, clang -O0: round trip: 3.6 us (3.3 to 4.1 in nine runs) */
```

## Дальше \{#next\}

Пример с потоками выше был правильным только потому, что его два потока никогда не выполнялись одновременно. Когда они выполняются одновременно, даже такое простое обновление, как `counter++`, может терять приращения, и результат меняется от запуска к запуску. [Следующая заметка](/ru/notes/acos/synchronization) показывает почему — на уровне трёх команд, стоящих за `counter++`, — и строит инструменты, которые делают параллельные обновления безопасными: атомарные команды, мьютексы, условные переменные и семафоры.
