Программа — это текстовый файл. Когда мы её запускаем, через несколько миллисекунд на экране появляются символы, а между этими двумя событиями стоят компилятор, компоновщик, операционная система, процессор, выполняющий миллиарды команд в секунду, микросхемы памяти, драйвер дисплея и транзисторы, которые включаются и выключаются. Каждый из них — уровень, построенный так, чтобы уровню выше не нужно было о нём думать. Этот курс открывает эти уровни по одному, от битов одного числа до процесса, который общается с другим процессом по сети. Первая заметка рисует всю картину: что происходит при запуске программы, какая идея делает возможным универсальный компьютер, как процессоры стали быстрыми и почему они перестали ускоряться прежним способом и как рассуждать о времени работы с помощью одного уравнения.

**Обозначения.** В уравнении производительности $I$ — число команд, которые выполняет программа (её *динамическое* число команд), $\mathrm{CPI}$ — среднее число тактов на команду, $T_c$ — период тактового сигнала, а $f = 1/T_c$ — тактовая частота. Числа вида `0x…` записаны в шестнадцатеричной системе; [следующая заметка](/ru/notes/acos/data-representation) объясняет эту запись.

## Что происходит при запуске программы \{#what-happens-when-a-program-runs\}

Возьмём самую маленькую программу на C, которая делает что-то видимое:

```c
#include <stdio.h>
int main(void) { printf("hello, world\n"); return 0; }
```

<HelloPath />

1. **Исходный текст.** `hello.c` — файл байтов на диске, по одному байту на символ в кодировке ASCII. Одна только строка `"hello, world\n"` занимает 13 байтов: двенадцать печатных символов, включая пробел, и перевод строки.
2. **Сборка.** Драйвер компилятора по очереди запускает четыре программы. *Препроцессор* (preprocessor) вставляет текст `stdio.h`; *компилятор* (compiler) переводит C на язык ассемблера целевого процессора; *ассемблер* (assembler) превращает ассемблерный текст в машинный код — последовательность чисел — в *объектном файле* (object file); *компоновщик* (linker) соединяет его с кодом `printf` из библиотеки C в *исполняемый файл* (executable).
3. **Загрузка.** Мы набираем в оболочке `./hello`. Оболочка просит операционную систему создать новый процесс и запустить в нём этот файл. *Загрузчик* (loader) ядра отображает исполняемый файл в память процесса и запускает его с точки входа (entry point).
4. **Исполнение.** Процессор выбирает из памяти команды `main` одну за другой и выполняет их. `printf` форматирует строку в буфер и вызывает `write(1, buffer, 13)`: записать 13 байтов в файловый дескриптор (file descriptor) 1, стандартный вывод.
5. **Системный вызов.** `write` не может сам обратиться к терминалу. Он выполняет специальную команду, которая переключает процессор в ядро; ядро проверяет запрос и передаёт 13 байтов драйверу терминала.
6. **Вывод.** Программа-терминал превращает байты в глифы, графическое оборудование превращает глифы в пиксели, и дисплей показывает `hello, world`.

В программе один вызов функции. Её запуск затрагивает каждый раздел этого курса: представление символов байтами, набор команд, для которого компилирует компилятор, память, в которой живёт программа, процессор, который её выполняет, системный вызов (system call), переходящий в ядро, процесс, в котором она работает, файловый дескриптор, в который она пишет, и компилятор с компоновщиком, которые её собрали.

## Уровни абстракции \{#layers-of-abstraction\}

Компьютер можно понять потому, что он построен из уровней. Каждый уровень предоставляет уровню выше *интерфейс* и скрывает, как он реализован. Программист на C видит переменные и функции, а не регистры; компилятор видит команды, а не конвейер, который их выполняет; набор команд говорит, что делает `add`, но не сколько транзисторов это делают.

| Уровень | Что он даёт уровню выше | Что он скрывает | Где в курсе |
| --- | --- | --- | --- |
| Приложение и алгоритм | решение задачи | как оно вычисляется | примеры по всему курсу |
| Язык программирования и среда выполнения | переменные, функции, объекты | регистры, адреса | Языки и компиляторы |
| Компилятор, ассемблер, компоновщик | перевод в машинный код | выбор команд, распределение регистров | Языки и компиляторы; компоновка — в разделе «Операционная система» |
| Операционная система | процессы, файлы, сокеты | устройства, физическую память, другие программы | от «Операционной системы» до «Сетей» |
| Архитектура набора команд (ISA) | команды, регистры, адреса памяти | аппаратуру, которая их выполняет | Ассемблер RISC-V |
| Микроархитектура | реализацию ISA | конвейеры, кэши, параллельные блоки | от «Иерархии памяти» до «Параллелизма и производительности» |
| Логика и схемы | вентили, сумматоры, регистры | транзисторы | упоминаются там, где нужны |
| Устройства | переключающиеся транзисторы | физику | история ниже |

Самая важная строка — архитектура набора команд (instruction set architecture, ISA). Это договор между аппаратурой и программами: любая программа, написанная для RISC-V, работает на любом процессоре, реализующем RISC-V, от микроконтроллера до сервера, хотя у них нет ни одной общей схемы. С неё начинается [заметка о процессоре и наборе команд](/ru/notes/acos/processor-and-isa).

Абстракция не делает нижние уровни несущественными. Уровни *протекают* (leak). На Apple M1 программа на C, перемножающая две матрицы $1024 \times 1024$ учебным тройным циклом и скомпилированная с `clang -O0`, в одном запуске работала 5.4 секунды; та же программа с двумя переставленными циклами работала 1.5 секунды и вычисляет тот же результат: каждый элемент суммируется по $k$ в том же порядке (раздел «Код»). Ничто в C не различает эти два порядка. Разница живёт в иерархии памяти, на два уровня ниже, и её объясняет [заметка о кэшах](/ru/notes/acos/caches). Чтобы писать быстрые и правильные программы, нужно знать, что скрывает каждый уровень.

## Отправная точка: машина, собранная под одну задачу \{#baseline-a-machine-wired-for-one-problem\}

Первые электронные вычислительные машины строились под один вид расчётов за раз. ENIAC, построенный в Пенсильванском университете в 1945 году для расчёта артиллерийских таблиц, содержал около 18 000 электронных ламп, потреблял 150 кВт и выполнял около 5000 сложений в секунду. Его программа нигде не хранилась: программой была разводка проводов. Операторы соединяли блоки кабелями на коммутационных панелях и выставляли тысячи переключателей, и смена задачи занимала дни перекоммутации, прежде чем можно было начать проверку ([ENIAC, Wikipedia](#references)).

Это работает, пока задача не меняется. Это перестаёт работать, как только машина должна обслуживать много пользователей и много задач: пока её перекоммутируют, компьютер простаивает, каждое изменение программы — это изменение аппаратуры, а программа не может сделать того, что делает программы мощными, — создать или изменить другую программу.

## Компьютер с хранимой программой \{#the-stored-program-computer\}

<aside class="callout"><strong>Ключевая идея.</strong> Хранить программу в той же памяти, что и данные, в виде чисел. Тогда неизменная аппаратура может выполнять любую программу, раз за разом выбирая из памяти следующую команду и делая то, что она предписывает, а изменить программу — значит записать в память новые числа. Программы становятся данными, которые могут создавать другие программы, например компиляторы и загрузчики.</aside>

Эта идея изложена в «Первом проекте отчёта об EDVAC» (*First Draft of a Report on the EDVAC*) Джона фон Неймана, датированном 30 июня 1945 года и написанном вместе с командой ENIAC ([von Neumann, 1945](#references)). В нём описана машина с центральной арифметической частью, центральной управляющей частью, памятью, вводом и выводом, в которой команды закодированы числами и хранятся в памяти. Первой машиной, выполнившей программу, хранившуюся в её собственной электронной памяти, стала манчестерская Baby (Manchester Baby), 21 июня 1948 года: 17 команд в памяти из 32 слов по 32 бита ([Manchester Baby, Wikipedia](#references)). Такую организацию до сих пор называют **архитектурой фон Неймана** (von Neumann architecture):

- **память** — массив пронумерованных ячеек, в которых хранятся и команды, и данные;
- **процессор** с небольшим набором **регистров**, **арифметико-логическим устройством** (АЛУ, arithmetic logic unit), которое вычисляет, и **устройством управления** (control unit), которое решает, что происходит дальше;
- **счётчик команд** (program counter, PC) — регистр, в котором хранится адрес следующей команды;
- устройства **ввода и вывода**, подключённые к той же системе.

Машину с раздельными памятями для команд и данных называют *гарвардской архитектурой* (Harvard architecture). Современные процессоры — смесь: одна память и одно адресное пространство, как в схеме фон Неймана, но раздельные быстрые кэши команд и данных рядом с процессором.

## Цикл «выборка — декодирование — исполнение» \{#the-fetchdecodeexecute-cycle\}

Устройство управления бесконечно выполняет один цикл:

<FetchExecute />

1. **Выборка** (fetch). Прочитать из памяти команду по адресу из PC в регистр команды (instruction register, IR).
2. **Декодирование** (decode). Разбить команду на поля: какая операция, какие регистры читать, в какой регистр писать и какая константа.
3. **Исполнение** (execute). Прочитать регистры-источники и дать АЛУ вычислить результат (или вычислить адрес в памяти, или сравнить для ветвления).
4. **Запись результата** (write back). Записать результат в регистр назначения (или в память).
5. **Следующая команда.** Перевести PC на следующую команду, для 32-битных команд — на 4 байта дальше, если только команда не была переходом или выполненным ветвлением, которые сами устанавливают PC.

**Разобранный пример.** Программа на RISC-V из трёх команд, загруженная с адреса `0x00400000`, куда симулятор RARS помещает код:

| Адрес | Машинное слово | Ассемблер | Действие |
| --- | --- | --- | --- |
| `0x00400000` | `0x00500513` | `addi a0, zero, 5` | a0 ← 0 + 5 |
| `0x00400004` | `0x00700593` | `addi a1, zero, 7` | a1 ← 0 + 7 |
| `0x00400008` | `0x00B50633` | `add a2, a0, a1` | a2 ← a0 + a1 |

Рисунок показывает третий оборот цикла. PC содержит `0x00400008`; выборка копирует слово `0x00B50633` в IR. Декодер читает его поля: операция `add`, регистр назначения 12 (a2), источники 10 (a0) и 11 (a1). АЛУ получает 5 и 7 и выдаёт 12, которое записывается в a2, а PC становится равным `0x0040000C`. Память хранит только числа; является ли `0x00B50633` командой или целым числом, зависит от того, указывает ли на него PC. Как поля упакованы в 32 бита, рассказывает [заметка о кодировании команд](/ru/notes/acos/risc-v-instructions).

Каждый процессор в этом курсе, как бы сложно он ни был устроен, реализует этот цикл. Конвейерный (pipelined) процессор работает с несколькими командами сразу, каждая на своей стадии цикла; суперскалярный (superscalar) выбирает несколько команд за такт; процессор с внеочередным исполнением (out-of-order) выполняет их в другом порядке. Все они обязаны давать тот же результат, что и выполнение команд по одной в порядке программы, потому что именно это обещает ISA.

## Как процессоры стали быстрыми и что изменилось \{#how-processors-got-fast-and-why-that-changed\}

Идея хранимой программы закрепила организацию машины. В следующие десятилетия менялась технология под ней, а вместе с ней скорость и стоимость.

- **Электронные лампы (1940-е — 1950-е).** ENIAC, EDSAC, UNIVAC: размером с комнату, прожорливые и ненадёжные, потому что лампы часто перегорали.
- **Транзисторы (с конца 1950-х).** Транзистор изобрели в Bell Labs в 1947 году. Транзистор переключается как лампа, но он меньше, быстрее, меньше греется и служит гораздо дольше. Мейнфреймы вроде IBM 7090 строились из дискретных транзисторов.
- **Интегральные схемы (с 1960-х).** Джек Килби (1958) и Роберт Нойс (1959) разместили несколько транзисторов вместе с соединениями на одном куске кремния. В 1971 году Intel 4004 поместил целый процессор на один кристалл примерно из 2300 транзисторов.
- **Закон Мура** (Moore's law). В 1965 году Гордон Мур заметил, что число компонентов на кристалле минимальной стоимости удваивается каждый год, и предсказал, что так будет и дальше ([Moore, 1965](#references)); в 1975 году он уточнил темп до удвоения примерно раз в два года. Уточнённый темп держался десятилетиями: в Apple M1 2020 года около 16 миллиардов транзисторов, примерно в семь миллионов раз больше, чем в 4004.

Одно лишь увеличение числа транзисторов не сделало бы процессоры быстрее. Бесплатное ускорение давало второе правило.

**Масштабирование Деннарда** (Dennard scaling). [Dennard et al. (1974)](#references) показали, как уменьшать транзистор так, чтобы он становился лучше во всех отношениях. Умножим все линейные размеры и напряжение питания на $1/\kappa$ для некоторого $\kappa > 1$. Тогда:

$$
\begin{aligned}
C &\propto 1/\kappa && \text{ёмкость уменьшается вместе с размерами} \\
f &\propto \kappa && \text{меньший транзистор при меньшем напряжении переключается быстрее} \\
P_{\text{transistor}} &\propto C V^2 f = \tfrac1\kappa \cdot \tfrac1{\kappa^2} \cdot \kappa = \tfrac{1}{\kappa^2} && \text{динамическая мощность} \\
\text{транзисторов на единицу площади} &\propto \kappa^2 \\
\text{мощность на единицу площади} &\propto \kappa^2 \cdot \tfrac1{\kappa^2} = 1 . &&
\end{aligned}
$$

Каждое поколение, с $\kappa \approx \sqrt 2$, так что число транзисторов на единицу площади удваивается, давало вдвое больше транзисторов, каждый примерно в 1.4 раза быстрее, при той же мощности на квадратный миллиметр. Архитекторы тратили транзисторы на более глубокие конвейеры, большие кэши и больше команд за такт, и производительность одного процессора с 1986 по 2003 год росла примерно на 52% в год ([Hennessy and Patterson, 2019](#references), §1.1).

**Конец масштабирования Деннарда.** Напряжение питания не может падать бесконечно. Вместе с ним должно падать пороговое напряжение (threshold voltage) транзистора, а ниже нескольких сотен милливольт ток утечки (leakage) через «выключенный» транзистор быстро растёт. Как только $V$ перестаёт меняться, то же уменьшение даёт $P_{\text{transistor}} \propto \frac1\kappa \cdot 1 \cdot \kappa = 1$, и мощность на единицу площади растёт в $\kappa^2$ раз, удваиваясь с каждым поколением, если частота продолжает расти. Кристалл может рассеивать лишь около 100 Вт, дальше охлаждение становится непрактичным. Около 2005 года отрасль упёрлась в эту *стену энергопотребления* (power wall): тактовые частоты настольных процессоров остановились около 3–4 ГГц ([Patterson and Hennessy, 2020](#references), §1.7), а рост производительности одного процессора упал примерно до 23% в год до 2011 года и примерно до 3.5% в год после 2015-го ([Hennessy and Patterson, 2019](#references), §1.1).

**Многоядерность и ускорители.** Закон Мура продолжал поставлять транзисторы, и они пошли не на более быстрые процессоры, а на большее число процессоров на кристалле: двухъядерные настольные процессоры появились в 2005 году, а у сегодняшних кристаллов от нескольких до более сотни ядер. Второй ответ — специализация: графические процессоры и ускорители машинного обучения (accelerators), такие как TPU компании Google, выполняют один класс вычислений с гораздо большим числом операций на ватт, чем универсальное ядро ([Jouppi et al., 2017](#references)). Ни то ни другое само по себе не ускоряет существующую последовательную программу. Программу нужно переписать так, чтобы она использовала параллелизм, поэтому курс отводит этому целый раздел.

## Сколько времени работает программа? \{#how-long-does-a-program-take\}

Время работы — единственная мера производительности, которая не может ввести в заблуждение. Оно раскладывается на три множителя — это **уравнение производительности** (performance equation) ([Patterson and Hennessy, 2020](#references), §1.6):

$$
\boxed{\;\text{время} = I \times \mathrm{CPI} \times T_c = \frac{I \times \mathrm{CPI}}{f}\;}
$$

$$
\begin{aligned}
\frac{\text{секунды}}{\text{программа}} &= \frac{\text{команды}}{\text{программа}} \times \frac{\text{такты}}{\text{команда}} \times \frac{\text{секунды}}{\text{такт}} && \text{единицы сокращаются попарно} \\
I &\text{: зависит от алгоритма, языка, компилятора и ISA} \\
\mathrm{CPI} &\text{: зависит от микроархитектуры, системы памяти и состава команд} \\
T_c &\text{: зависит от технологии схем и микроархитектуры.}
\end{aligned}
$$

Когда команды делятся на классы с разной стоимостью, средний CPI — это среднее CPI классов, взвешенное по тому, как часто выполняется каждый класс: если класс $j$ составляет долю $p_j$ выполненных команд и занимает $\mathrm{CPI}_j$ тактов, то $\mathrm{CPI} = \sum_j p_j\, \mathrm{CPI}_j$.

**Разобранный пример.** Программа выполняет $I = 2 \times 10^9$ команд на процессоре с $f = 3$ ГГц, так что $T_c = 1/(3 \times 10^9\ \text{Гц}) = 0.333$ нс. Половина её команд — арифметические (CPI 1), 30% — загрузки и сохранения (в среднем CPI 2 с учётом редких медленных обращений к памяти) и 20% — ветвления (CPI 1.5):

$$
\begin{aligned}
\mathrm{CPI} &= 0.5 \cdot 1 + 0.3 \cdot 2 + 0.2 \cdot 1.5 = 1.4, \\
\text{время} &= \frac{2 \times 10^9 \cdot 1.4}{3 \times 10^9\ \text{Гц}} = 0.933\ \text{с}.
\end{aligned}
$$

Более удачный компилятор убирает $0.2 \times 10^9$ арифметических команд. В новом составе в трёх классах $0.8$, $0.6$ и $0.4$ миллиарда команд, так что программе нужно $0.8 \cdot 1 + 0.6 \cdot 2 + 0.4 \cdot 1.5 = 2.6$ миллиарда тактов: 0.867 с, на 7% быстрее. Но средний CPI *вырос*, с 1.4 до $2.6/1.8 = 1.444$, потому что убраны были именно дешёвые команды. Ни один множитель уравнения сам по себе не измеряет производительность; её измеряет только произведение. То же касается одной лишь тактовой частоты (процессор на 4 ГГц с CPI на 40% выше медленнее процессора на 3 ГГц: $1.4 \cdot 1.4/4 > 1.4/3$) и «миллионов команд в секунду», которые поощряют выполнение множества дешёвых команд.

**Разобранный пример (измерения).** Умножение матриц из предыдущего раздела, $n = 1024$: внутренний оператор `C[i][j] += A[i][k] * B[k][j]` выполняется $n^3 = 2^{30} \approx 1.07 \times 10^9$ раз при любом порядке циклов. При компиляции с `clang -O0` для набора команд ARM процессора M1 каждый проход внутреннего цикла — это 29 команд в ассемблерном коде, который печатает `clang -O0 -S`, одинаково для любого порядка циклов (меняется лишь то, какой индекс стоит в каком цикле), так что во всех трёх вариантах $I \approx 29 \cdot 2^{30} \approx 3.1 \times 10^{10}$, и $T_c$ тоже одинаков. Следовательно, отношение времён работы равно отношению CPI. В одном запуске порядки `i, j, k`, `i, k, j` и `j, k, i` заняли 5.4 с, 1.5 с и 6.4 с: самый медленный порядок тратит на команду примерно в 4.3 раза больше тактов, чем самый быстрый. Если ядро работало на своей максимальной частоте около 3.2 ГГц, CPI составляли около 0.55, 0.15 и 0.66; CPI меньше 1 означает, что процессор завершает несколько команд за такт, — это тема [заметки о параллелизме на уровне команд](/ru/notes/acos/instruction-level-parallelism). Алгоритм и число команд одинаковы; различается порядок обращений к памяти.

## Ограничения \{#limitations\}

- **Узкое место фон Неймана** (von Neumann bottleneck). Каждая команда и каждый операнд проходят между процессором и памятью по одному соединению, а память стала гораздо медленнее процессоров. [Backus (1978)](#references) дал этому узкому месту имя; главный ответ на него — кэши, тема [заметки о кэшах](/ru/notes/acos/caches).
- **Уравнение производительности точно, но само по себе ничего не предсказывает.** CPI — не свойство процессора: он зависит от программы, её данных и системы памяти, поэтому его приходится измерять. Кроме того, уравнение не учитывает время ожидания ввода-вывода и других программ.
- **Уровни протекают.** Производительность, уязвимости и некоторые сбои можно понять, только спустившись на один-два уровня ниже того, на котором написана программа.
- **История упрощена.** В каждый шаг внесли вклад многие машины и люди; эта заметка называет лишь несколько вех.

## Что нужно запомнить \{#what-you-should-remember\}

- Программа проходит через цепочку уровней: компилятор, ассемблер и компоновщик её собирают; операционная система её загружает; процессор её выполняет; системные вызовы достигают устройств через ядро.
- Архитектура набора команд — договор между аппаратурой и программами.
- Принцип хранимой программы: команды — это числа в памяти, а процессор повторяет выборку, декодирование, исполнение, запись результата и продвижение PC.
- Масштабирование Деннарда давало более быстрые транзисторы при постоянной плотности мощности примерно до 2005 года; с тех пор дополнительные транзисторы идут на большее число ядер и специализированные ускорители, и чтобы выиграть от них, программы должны быть параллельными.
- $\text{время} = I \times \mathrm{CPI} \times T_c$. Число команд, CPI и частота зависят от разных уровней; производительность измеряет только их произведение.

## Код \{#code\}

Программа из трёх команд в синтаксисе RARS; она запускается в симуляторе RARS, с которым знакомит [заметка о процессоре и наборе команд](/ru/notes/acos/processor-and-isa):

```asm
# a2 = 5 + 7, печатается системным вызовом вывода целого числа
        .text
main:
        addi a0, zero, 5        # 0x00500513
        addi a1, zero, 7        # 0x00700593
        add  a2, a0, a1         # 0x00B50633
        mv   a0, a2             # системный вызов печатает a0
        li   a7, 1              # 1 = вывод целого числа
        ecall                   # prints 12
        li   a7, 10             # 10 = выход
        ecall
```

Цикл «выборка — декодирование — исполнение» на Python для двух форматов команд, которые использует программа. Память — словарь из адресов в 32-битные слова; декодер выделяет поля, описанные в [заметке о кодировании](/ru/notes/acos/risc-v-instructions):

```python
mem = {0x00400000: 0x00500513, 0x00400004: 0x00700593, 0x00400008: 0x00B50633}
reg = [0] * 32
pc = 0x00400000
names = {0: 'zero', 10: 'a0', 11: 'a1', 12: 'a2'}
while pc in mem:
    ir = mem[pc]                                  # 1. выборка
    opcode, rd = ir & 0x7F, (ir >> 7) & 0x1F      # 2. декодирование
    rs1, rs2 = (ir >> 15) & 0x1F, (ir >> 20) & 0x1F
    if opcode == 0x13:                            # addi: rd = rs1 + 12-битная константа
        imm = (ir >> 20) - ((ir >> 31) << 12)      # константа — 12-битное число со знаком
        result, text = reg[rs1] + imm, f'addi {names[rd]}, {names[rs1]}, {imm}'
    elif opcode == 0x33:                          # add: rd = rs1 + rs2
        result, text = reg[rs1] + reg[rs2], f'add {names[rd]}, {names[rs1]}, {names[rs2]}'
    reg[rd] = result                              # 3. исполнение, 4. запись результата
    print(f'{pc:#010x} {ir:#010x} {text:18} {names[rd]} = {result}')
    pc += 4                                       # 5. следующая команда
# 0x00400000 0x00500513 addi a0, zero, 5   a0 = 5
# 0x00400004 0x00700593 addi a1, zero, 7   a1 = 7
# 0x00400008 0x00b50633 add a2, a0, a1     a2 = 12
```

Примеры к уравнению производительности:

```python
def time(I, cpi, f):
    return I * cpi / f

mix = {'arith': (0.5, 1.0), 'mem': (0.3, 2.0), 'branch': (0.2, 1.5)}   # доля, CPI
cpi = sum(p * c for p, c in mix.values())
print(round(cpi, 3), round(time(2e9, cpi, 3e9), 3))                    # 1.4 0.933
counts = {'arith': 0.8e9, 'mem': 0.6e9, 'branch': 0.4e9}               # после того как компилятор убрал 0.2e9 арифметических команд
cycles = sum(n * mix[k][1] for k, n in counts.items())
print(round(cycles / 3e9, 3), round(cycles / sum(counts.values()), 3)) # 0.867 1.444: быстрее, но CPI выше
print(round(time(2e9, 1.4 * 1.4, 4e9), 3))                             # 0.98: частота 4 ГГц при CPI на 40% выше медленнее
print(10 * 2e9 / 2, round(time(1e10, 2.5, 3e9), 2))                    # 10000000000.0 8.33: самопроверка
```

Умножение матриц на C в трёх порядках циклов. Компиляция: `clang -std=c17 -Wall -Wextra -O0 matmul.c -o matmul`. Время зависит от машины и на загруженной машине меняется от запуска к запуску на 10–30%; комментарий показывает один запуск на Apple M1 (8 ГБ, macOS 26, Apple clang 21):

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#define N 1024
static double A[N][N], B[N][N], C[N][N];

static double seconds(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + 1e-9 * t.tv_nsec;
}

static double multiply(const char *order) {        /* C = A B with the loops nested in the given order */
    memset(C, 0, sizeof C);
    double t0 = seconds();
    if (strcmp(order, "ijk") == 0)                  /* B is walked down a column */
        for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) for (int k = 0; k < N; k++) C[i][j] += A[i][k] * B[k][j];
    else if (strcmp(order, "ikj") == 0)             /* B and C are walked along rows */
        for (int i = 0; i < N; i++) for (int k = 0; k < N; k++) for (int j = 0; j < N; j++) C[i][j] += A[i][k] * B[k][j];
    else                                            /* jki: A and C are walked down columns */
        for (int j = 0; j < N; j++) for (int k = 0; k < N; k++) for (int i = 0; i < N; i++) C[i][j] += A[i][k] * B[k][j];
    return seconds() - t0;
}

int main(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) {
            A[i][j] = rand() / (double)RAND_MAX;
            B[i][j] = rand() / (double)RAND_MAX;
        }
    const char *orders[] = {"ijk", "ikj", "jki"};
    double check = 0;
    for (int r = 0; r < 3; r++) {
        double t = multiply(orders[r]);
        if (r == 0) check = C[N / 2][N / 3];
        printf("%s %.1f s, same result: %d\n", orders[r], t, check == C[N / 2][N / 3]);
    }
    return 0;
}
/* ijk 5.4 s, same result: 1
   ikj 1.5 s, same result: 1
   jki 6.4 s, same result: 1 */
```
