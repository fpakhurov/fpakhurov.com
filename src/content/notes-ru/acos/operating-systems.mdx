[Предыдущая заметка](/ru/notes/acos/domain-specific-architectures) закончила обзор аппаратуры процессорами, построенными для одного вида работы, которые универсальный процессор снабжает данными и контролирует. В первой половине курса каждая программа владела машиной одна. Программе в RARS принадлежали все 32 регистра и вся память, а когда она выполняла `ecall`, чтобы напечатать число, печатал симулятор. Настоящий компьютер выполняет одновременно много программ, написанных разными людьми; ни одна из них не доверяет другим, и ни одна не умеет управлять диском. Это возможно благодаря **операционной системе** (operating system). Эта заметка объясняет, что она делает, на какие возможности аппаратуры опирается, как устроена её центральная часть — **ядро** (kernel), из чего состоит Linux и как машина проходит путь от включения питания до приглашения оболочки. Следующие заметки пишут программы на C, которые с ней работают.

**Термины.** *Ядро* — часть операционной системы, которая работает с полными аппаратными привилегиями. Всё остальное, включая библиотеку C, оболочку и системные утилиты, — обычные программы. *Процесс* (process) — выполняющаяся программа вместе с ресурсами, которые ей выдало ядро. *Режим ядра* (kernel mode) и *пользовательский режим* (user mode) — уровни привилегий процессора; в RISC-V они называются S-режимом (supervisor, режим супервизора) и U-режимом (user), а ещё один, M-режим (machine, машинный), находится под ядром.

## Отправная точка: одна программа на голом железе \{#baseline-one-program-on-bare-hardware\}

В простейшем устройстве операционной системы нет вовсе. Программа скомпонована вместе с кодом, который управляет каждым используемым ею устройством, процессор начинает выполнять её после сброса, и она работает, пока не выключат питание. Так устроены термостаты, стиральные машины и многие платы с микроконтроллерами, и такова модель каждой программы для RARS до сих пор: RARS загружает код по адресу `0x00400000`, данные — по адресу `0x10010000`, и программа может пользоваться любым регистром и любым адресом.

Теперь поместим две такие программы на одну машину.

- **Память.** Обе собраны так, чтобы хранить данные по адресу `0x10010000`. Без трансляции адресов они не могут одновременно находиться в памяти: строка второй программы затирает счётчик первой, и ни одна этого не замечает.
- **Процессор.** Первая программа заканчивается циклом `loop: j loop`, ожидая нажатия кнопки. Она никогда не возвращает управление, поэтому вторая программа так и не запускается.
- **Устройства.** Каждая программа несёт свой драйвер дисплея. Если обе одновременно пишут в его регистры, на выходе получается мусор.
- **Защита.** Ничто не мешает любой из программ перепрограммировать таймер, отключить прерывания или прочитать данные другой.

Каждой из этих проблем нужен арбитр, который работает с большими полномочиями, чем программы, между которыми он рассудит, и нужно, чтобы аппаратура дала этому арбитру способ вернуть себе управление. Этот арбитр — ядро.

## Три задачи: абстракция, управление ресурсами, изоляция \{#three-jobs-abstraction-resource-management-isolation\}

Операционная система делает три вещи, и большая часть её кода служит сразу нескольким из них.

**Абстракция.** Аппаратура предлагает регистры, физическую память, блоки диска и сетевые кадры. Программам нужно что-то более удобное, и ядро это предоставляет:

| Аппаратура | Абстракция | Что видит программа | Где в курсе |
| --- | --- | --- | --- |
| ядра процессора, таймер | процесс, поток | собственный процессор, работающий непрерывно | [Процессы и потоки](/ru/notes/acos/processes-and-threads) |
| физическая память | виртуальное адресное пространство | собственная память от адреса 0 и выше, 256 ГБ в Linux на RISC-V с Sv39 | [Виртуальная память](/ru/notes/acos/virtual-memory) |
| блоки диска, страницы флеш-памяти | файл | именованная последовательность байтов, которая может расти | [Файлы и ввод-вывод](/ru/notes/acos/files-and-io) |
| сетевая карта, пакеты | сокет | надёжный поток байтов к процессу на другой машине | [Сокеты](/ru/notes/acos/sockets) |
| терминал, клавиатура, любое устройство | файловый дескриптор | небольшое целое число, из которого можно читать `read` и в которое писать `write` | [Файлы и ввод-вывод](/ru/notes/acos/files-and-io) |

Абстракция одна и та же на любой машине, какой бы диск или сетевая карта в ней ни стояли, поэтому одна программа работает на всех. Код, зависящий от устройства, существует в одном месте — в драйверах ядра.

**Управление ресурсами.** Процессов больше, чем ядер, а памяти меньше, чем хотелось бы всем программам вместе. Ядро решает, кто получает процессор и на сколько (*планировщик*, scheduler), какие физические страницы кому принадлежат (*менеджер памяти*, memory manager) и в каком порядке запросы доходят до устройства. Это решения политики: справедливость, приоритет, пропускная способность.

**Изоляция.** Ни один процесс не может читать или писать чужую память, напрямую обращаться к устройству или удерживать процессор вопреки воле ядра. Изоляция и делает две другие задачи выполнимыми: планировщик, которого программа могла бы отключить, ничего бы не планировал.

**Разобранный пример: одно ядро на троих.** На одном ядре готовы к выполнению три программы. Ядро программирует таймер на прерывание каждые 4 мс; Linux собирается с периодом тика 1, 3.3, 4 или 10 мс, так что 4 мс — один из его стандартных вариантов. На каждом прерывании ядро сохраняет регистры выполняющейся программы и восстанавливает регистры следующей. Каждая программа работает 4 мс из каждых 12 мс, то есть получает треть процессора, и между её очередями проходит пауза в 8 мс. Программа, застрявшая в `loop: j loop`, прерывается так же, как остальные, и две другие продолжают работать. Ни одна из трёх не может остановить эту ротацию: перепрограммировать таймер аппаратура разрешает только в режиме ядра.

<aside class="callout"><strong>Ключевая идея.</strong> Ядро — не библиотека, которую программы вызывают, когда захотят. Оно владеет аппаратурой и даёт её во временное пользование. Программы выполняются прямо на процессоре с полной скоростью, но в режиме, в котором они не могут трогать таймер, таблицы страниц и устройства, а каждая ловушка, прерывание и отказ возвращают управление ядру по адресу, который ядро выбрало заранее. Такое устройство называется <em>ограниченным прямым выполнением</em> (limited direct execution; <a href="#references">Arpaci-Dusseau и Arpaci-Dusseau, 2023</a>, гл. 6).</aside>

## Режим ядра и пользовательский режим \{#kernel-mode-and-user-mode\}

[Заметка об исключениях](/ru/notes/acos/exceptions-and-interrupts) ввела **ловушку** (trap): процессор прекращает то, что делал, записывает причину и переходит к обработчику. Режимы привилегий превращают ловушку в механизм защиты. У процессора RISC-V их три: **M-режим** (machine, код 3), самый привилегированный, в котором работает прошивка; **S-режим** (supervisor, 1), в котором работает ядро; и **U-режим** (user, 0), в котором работает каждый процесс ([RISC-V Privileged Architecture](#references), гл. 1). В x86-64 уровни называются кольцами 0–3, и используются 0 и 3; в Arm — EL0–EL3. Текущий режим не хранится ни в одном регистре, который может прочитать программа; его меняют только ловушки и команды возврата `sret` и `mret`.

<OsLayers />

1. **Системный вызов** (system call). Программа выполняет `ecall`. Процессор сохраняет адрес `ecall` в `sepc`, записывает причину 8 (вызов окружения из U-режима) в `scause`, переключается в S-режим и переходит по адресу из `stvec`.
2. **Исключение** (exception). Команда завершается неудачей, например загрузка из страницы, которая не отображена. Срабатывает тот же механизм, с причиной 13 (страничный отказ при загрузке, load page fault).
3. **Прерывание** (interrupt). Устройство или таймер вызывает прерывание. Выполняющаяся программа ничего не нарушила, но её всё равно останавливают.
4. **Возврат.** Ядро заканчивает работу и выполняет `sret`, которая переключает процессор обратно в U-режим и переходит по адресу из `sepc`.

Что запрещает U-режим? Три вида вещей.

- **Привилегированные команды и регистры.** `sret`, `wfi` и `sfence.vma` в U-режиме вызывают исключение «недопустимая команда» (illegal instruction), как и любое обращение к управляющему регистру состояния (control and status register, CSR) с более высоким уровнем привилегий, чем текущий. 12-битный адрес CSR несёт в битах 9–8 наименьший режим, которому этот регистр доступен ([RISC-V Privileged Architecture](#references), §2.1).
- **Память, помеченная для ядра.** В каждой записи таблицы страниц есть бит U. Код в U-режиме может пользоваться только страницами с U = 1; ядро отображено в таблицу страниц каждого процесса, но с U = 0.
- **Устройства.** Регистры устройств отображены только в части адресного пространства, принадлежащей ядру, поэтому программа вообще не может до них дотянуться.

**Разобранный пример.** Программа в U-режиме выполняет `csrw satp, a0`, пытаясь установить собственную таблицу страниц. Адрес `satp` — `0x180`; биты 9–8 числа `0x180` равны `01`, значит, наименьший допустимый режим — S. Процессор вызывает исключение «недопустимая команда» с причиной 2, и обработчик ядра посылает процессу сигнал `SIGILL`, который завершает процесс, если программа его не перехватывает. Загрузка с адреса ядра останавливается иначе: адрес отображён, но в его записи таблицы страниц U = 0, поэтому процессор вызывает **страничный отказ** (page fault) при загрузке с причиной 13, и ядро посылает `SIGSEGV`. В обоих случаях команда так и не вступает в силу. Раздел «Код» пробует оба случая на настоящей машине.

(2) Почему адрес, на который процессор переходит при ловушке, должно задавать ядро, а не программа как аргумент <code>ecall</code>?<details><summary>Ответы</summary>(1) После кванта времени таймер вызывает прерывание, и ловушка входит в ядро по адресу из <code>stvec</code>. Чтобы отключить прерывания или перепрограммировать таймер, нужны привилегированные CSR, обращение к которым в U-режиме вызывает исключение. (2) Если бы адрес входа выбирала программа, она могла бы перейти в середину кода ядра, в обход проверок своих аргументов, и выполнить его с привилегиями ядра. Единственная точка входа, заданная ядром, означает, что каждый запрос проходит одни и те же проверки.</details></aside>

## Как устроено ядро: монолитное, микроядро, гибридное \{#how-a-kernel-is-organized-monolithic-microkernel-hybrid\}

Всё, что работает в режиме ядра, может делать что угодно, поэтому ошибка в любом месте ядра может обрушить машину или раскрыть любые данные. Сколько кода помещать в режим ядра — центральный вопрос проектирования, и на него есть два ответа.

**Монолитное ядро** (monolithic kernel) помещает все службы в одну программу, работающую в S-режиме в одном адресном пространстве: планировщик, менеджер памяти, файловые системы, сетевой стек и драйверы устройств. Они вызывают друг друга обычными вызовами функций. Linux, системы BSD и классический Unix — монолитные. Такая структура быстрая и простая, но каждый драйвер работает с полными привилегиями: ошибка в драйвере малоизвестного устройства может обрушить всю систему.

**Микроядро** (microkernel) оставляет в S-режиме только то, что не может находиться больше нигде: адресные пространства, потоки и передачу сообщений между процессами (*межпроцессное взаимодействие*, inter-process communication, IPC). Файловые системы, драйверы и сетевой стек становятся обычными пользовательскими процессами, которые называются *серверами*, а запрос к одному из них — это сообщение, которое передаёт ядро. Mach, L4, QNX и MINIX 3 — микроядра. Упавший драйвер — это просто упавший процесс, который можно перезапустить, а привилегированная часть мала: в seL4 около 8700 строк на C и 600 строк на ассемблере, достаточно мало, чтобы доказать корректность кода на C относительно формальной спецификации ([Klein et al., 2009](#references)). Цена — число переходов.

<KernelCrossings />

**Разобранный пример: одно чтение с диска.** Программа читает блок, которого нет в памяти, поэтому запрос должен дойти до драйвера диска.

- **Монолитное ядро.** (1) Программа уходит в ловушку и попадает в ядро; файловая система — код ядра. (2) Она вызывает функцию драйвера, (3) драйвер возвращает управление, и (4) ядро возвращается в программу командой `sret`. Две смены режима, а адресное пространство программы всё время остаётся на месте, потому что ядро отображено в нём.
- **Микроядро.** (1) Программа посылает сообщение, что вызывает ловушку в микроядро; (2) микроядро доставляет его файловому серверу, переключаясь на адресное пространство сервера; (3) файловый сервер посылает сообщение драйверу, (4) который его получает; (5) драйвер отвечает, (6) файловому серверу; (7) файловый сервер отвечает, (8) программе. Восемь смен режима и четыре смены адресного пространства.

Каждая смена режима сохраняет и восстанавливает регистры, а каждая смена адресного пространства может стоить сброса TLB и последующих промахов кэша. Микроядра первого поколения, такие как Mach, были медленными именно поэтому; Лидтке, опираясь на L4 как на доказательство, утверждал, что медлительность объяснялась в основном реализацией их IPC, а не самой идеей ([Liedtke, 1995](#references)). И всё же монолитное ядро обходится без этих переходов совсем.

**Гибридные ядра** (hybrid kernels) берут структуру микроядра, но ради скорости всё равно выполняют серверы в режиме ядра. Стандартные примеры — Windows NT и XNU от Apple, которое объединяет микроядро Mach с ядром BSD в одном адресном пространстве. Linux, в свою очередь, монолитный, но модульный: *загружаемый модуль ядра* (loadable kernel module) — это объектный файл, который можно скомпоновать с работающим ядром командой `insmod` и удалить командой `rmmod`; так загружается большинство драйверов. Модуль работает в S-режиме с полными привилегиями, так что это способ организовать код, а не изолировать его.

## Linux: ядро, дистрибутив, оболочка \{#linux-kernel-distribution-shell\}

Linux, начатый Линусом Торвальдсом в 1991 году, — монолитное ядро, распространяемое по лицензии GPL. Его дерево исходников показывает службы с рисунка выше в виде каталогов: `kernel/` (процессы и планирование), `mm/` (управление памятью), `fs/` (виртуальная файловая система и файловые системы), `net/` (сетевой стек), `drivers/` (драйверы устройств) и `arch/` (код, специфичный для каждого набора команд, где `arch/riscv` и `arch/x86` лежат рядом). Всё, что находится над интерфейсом системных вызовов, берётся из других проектов.

**Дистрибутив** (distribution) собирает ядро вместе со всем, что нужно для пригодной к работе системы: библиотекой C (glibc или musl), основными утилитами (`ls`, `cp`, `cat`), оболочкой, системой инициализации, которая запускает службы (в большинстве дистрибутивов systemd), менеджером пакетов и тысячами собранных пакетов. Debian и Ubuntu используют `apt` и пакеты `.deb`, Fedora и Red Hat — `dnf` и `.rpm`, Alpine — `apk` с musl и BusyBox. Android запускает ядро Linux под совершенно другим пользовательским окружением со своей библиотекой C, Bionic. Все они работают с одним и тем же интерфейсом ядра; какой из них установлен, важно для программ в основном через версии библиотек и пути к файлам.

**Оболочка** (shell; `bash`, `zsh`) — обычная пользовательская программа. Она читает командную строку, находит программу, которую та называет, запускает её как новый процесс вызовами `fork` и `exec` ([Процессы и потоки](/ru/notes/acos/processes-and-threads)) и ждёт её завершения, если строка не оканчивается на `&`. Её операторы соединяют процессы: `>` направляет вывод программы в файл, `|` соединяет вывод одной программы со входом следующей. Инструменты, которые используются в этой части курса:

| Команда | Что делает |
| --- | --- |
| `ls`, `cd`, `cat`, `cp`, `mv`, `rm` | показывает содержимое, меняет, печатает, копирует, перемещает, удаляет файлы и каталоги |
| `grep`, `wc`, `sort`, `head` | ищет, считает, сортирует и обрезает текст; объединяются через `\|` |
| `ps`, `top`, `kill` | показывает процессы, следит за ними, посылает им сигналы |
| `man 2 write`, `man 3 printf` | открывает руководство: раздел 1 — команды, 2 — системные вызовы, 3 — библиотечные функции |
| `gcc`, `clang`, `make`, `cmake` | компилирует и собирает программы на C |
| `strace`, `ltrace`, `gdb` | трассирует системные вызовы, трассирует библиотечные вызовы, отлаживает |
| `nm`, `objdump`, `readelf`, `ldd` | исследует объектные и исполняемые файлы |

Linux также показывает состояние ядра в виде файлов. В `/proc` у каждого процесса есть каталог: `/proc/self/maps` перечисляет области памяти того процесса, который его читает, а `ps` строит свой список, читая `/proc/<pid>/stat`. В `/dev` устройства выглядят как файлы: `/dev/null` отбрасывает всё, что в него записано. Чтение и запись в них выполняются теми же системными вызовами, что и для файлов на диске, — эта идея ещё не раз встретится в курсе.

## Загрузка вкратце \{#booting-briefly\}

При включении питания в памяти нет ни ядра, ни таблицы страниц, ни файловой системы. **Загрузка** (booting) — это цепочка, в которой каждый этап загружает и запускает более развитый, а привилегии по ходу цепочки понижаются.

<BootChain />

**Разобранный пример: плата QEMU `virt`.** Эмулируемая QEMU плата RISC-V помещает небольшое загрузочное ПЗУ по адресу `0x1000`, а оперативную память — с адреса `0x80000000` ([документация QEMU](#references)). После сброса процессор выполняет в M-режиме несколько команд ПЗУ и переходит на `0x80000000`, куда загружена **прошивка** (firmware) OpenSBI. OpenSBI настраивает таймер и делегирование прерываний, остаётся в памяти, чтобы обслуживать запросы ядра (*Supervisor Binary Interface*, SBI: например, установку следующего прерывания таймера), и командой `mret` входит в следующий этап в S-режиме. Образ ядра лежит на 2 МиБ выше начала оперативной памяти, по адресу `0x80200000`, — именно там следующий этап ожидает универсальная 64-битная сборка OpenSBI `fw_jump`: её смещение равно `0x200000` ([OpenSBI](#references)). Там запускается ядро: оно строит свои таблицы страниц и включает трансляцию, записывает адрес своего обработчика ловушек в `stvec`, находит устройства по *дереву устройств* (device tree), описывающему плату, монтирует корневую файловую систему и наконец запускает в U-режиме первую пользовательскую программу, `/sbin/init`, с идентификатором процесса 1. Init запускает всё остальное, от сетевой службы до приглашения входа в систему и оболочки.

ПК следует тому же плану под другими именами: прошивка UEFI вместо OpenSBI, **начальный загрузчик** (bootloader), например GRUB, который читает ядро с диска, и таблицы ACPI вместо дерева устройств. Настоящие платы RISC-V тоже добавляют начальный загрузчик, обычно U-Boot. В любом случае ядро — последний этап, который работает с привилегиями S-режима, а init — первый пользовательский процесс.

## Что изменилось \{#what-changed\}

| | Одна программа на голом железе | Программы в операционной системе |
| --- | --- | --- |
| Кто управляет процессором | программа, пока не остановится | ядро, которое выдаёт его квантами времени |
| Память | физические адреса, общие для всех | собственное виртуальное адресное пространство у каждого процесса |
| Устройства | каждая программа управляет ими сама | драйверы ядра, скрытые за файлами и сокетами |
| Привилегии | разрешено всё | U-режим: ни привилегированных команд, ни страниц ядра, ни устройств |
| Ошибка в одной программе | может испортить всё | завершает этот процесс сигналом, например `SIGSEGV` |
| Вход в ядро | неприменимо | только через ловушку: системный вызов, исключение или прерывание |

## Ограничения \{#limitations\}

- **Переходы стоят времени.** Каждый системный вызов, прерывание и переключение контекста сохраняет и восстанавливает состояние и нарушает работу кэшей и TLB. [Заметка о системных вызовах](/ru/notes/acos/system-calls) измеряет, насколько.
- **Ошибка ядра — ошибка системы.** В монолитном ядре любой драйвер может испортить любую память. Микроядра сокращают этот код ценой большего числа переходов, а гибридные ядра ради скорости отдают часть выигрыша обратно.
- **Изоляция надёжна ровно настолько, насколько надёжна аппаратура.** Meltdown позволял пользовательскому коду на многих процессорах читать память ядра за счёт спекулятивного выполнения, хотя права доступа в таблицах страниц были заданы верно ([Lipp et al., 2018](#references)). Исправление — убрать из отображения большую часть ядра, пока работает пользовательский код, — делает каждый системный вызов на затронутых процессорах дороже.
- **Абстракции скрывают стоимость.** Чтение файла может занять наносекунды, если данные в кэше, и миллисекунды, если нет; один и тот же вызов может быть быстрым или медленным по причинам, которых программа не видит.
- **Политики универсальны.** Планировщик и менеджер памяти настроены на типичные нагрузки, и программе с необычными потребностями (базе данных, контроллеру реального времени) может понадобиться их обходить.

## Что нужно запомнить \{#what-you-should-remember\}

- Операционная система даёт абстракции (процессы, виртуальная память, файлы, сокеты), управляет ресурсами (процессорным временем, памятью, устройствами) и изолирует процессы друг от друга и от ядра.
- Ядро работает в привилегированном режиме (S-режим в RISC-V), процессы — в пользовательском (U-режим). Прошивка работает в M-режиме, под ядром.
- Управление попадает в ядро только через ловушку (системный вызов, исключение или прерывание) по адресу, который задало ядро; `sret` возвращает в пользовательский режим. Это ограниченное прямое выполнение.
- U-режим не может выполнять привилегированные команды (недопустимая команда, `SIGILL`), обращаться к страницам с U = 0 (страничный отказ, `SIGSEGV`) и добираться до устройств.
- Монолитные ядра (Linux) помещают все службы в режим ядра: быстро, но одна область отказа. Микроядра (seL4, QNX) выносят их в пользовательские процессы: изоляция, но больше переходов (8 против 2 на одно чтение с диска в примере). Гибридные ядра (Windows, macOS) сочетают оба подхода.
- Система Linux — это ядро плюс дистрибутив: библиотека C, утилиты, оболочка, init, пакеты. Оболочка — обычный процесс.
- Загрузка — цепочка этапов с убывающими привилегиями: ПЗУ, прошивка в M-режиме, ядро в S-режиме, init как процесс 1 в U-режиме.

## Код \{#code\}

Что пользовательский режим разрешает, а что нет. Программа спрашивает у ядра его имя системным вызовом `uname`, затем пробует три вещи: обычную арифметику, маскирование прерываний (привилегированная команда на любой архитектуре) и чтение адреса 0, который не отображён ни в одном процессе. Последние две ядро превращает в сигналы, и программа перехватывает их, вместо того чтобы завершиться.

```c
// modes.c: clang -std=c17 -Wall -Wextra -O0 modes.c -o modes && ./modes
#include <setjmp.h>
#include <signal.h>
#include <stdio.h>
#include <sys/utsname.h>

static sigjmp_buf back;
static void on_signal(int sig) { siglongjmp(back, sig); }

static const char *name(int sig) {
    return sig == SIGILL ? "SIGILL" : sig == SIGSEGV ? "SIGSEGV" : sig == SIGBUS ? "SIGBUS" : "other";
}

/* Run f; report the signal the kernel sent instead of letting it end the process. */
static void attempt(const char *what, void (*f)(void)) {
    int sig = sigsetjmp(back, 1);
    if (sig == 0) {
        f();
        printf("%-20s allowed\n", what);
    } else {
        printf("%-20s stopped by the kernel with %s\n", what, name(sig));
    }
}

static void privileged(void) {       /* mask interrupts: a kernel-only operation */
#if defined(__aarch64__)
    __asm__ volatile("msr daifset, #2");
#elif defined(__x86_64__)
    __asm__ volatile("cli");
#elif defined(__riscv)
    __asm__ volatile("csrci sstatus, 2");
#endif
}

static void read_null(void) {        /* the page at address 0 is never mapped */
    volatile int *p = NULL;
    (void)*p;
}

static void ordinary(void) {         /* plain arithmetic needs no permission */
    volatile int x = 6 * 7;
    (void)x;
}

int main(void) {
    struct utsname u;
    uname(&u);                       /* a system call: the kernel describes itself */
    printf("kernel: %s\n", u.sysname);
    signal(SIGILL, on_signal);
    signal(SIGSEGV, on_signal);
    signal(SIGBUS, on_signal);
    attempt("arithmetic", ordinary);
    attempt("masking interrupts", privileged);
    attempt("reading address 0", read_null);
    return 0;
}
// Output on macOS, Apple M1 (Linux prints "kernel: Linux"; on x86-64 the cli line reports SIGSEGV,
// because the processor signals a general-protection fault there):
// kernel: Darwin
// arithmetic           allowed
// masking interrupts   stopped by the kernel with SIGILL
// reading address 0    stopped by the kernel with SIGSEGV
```
