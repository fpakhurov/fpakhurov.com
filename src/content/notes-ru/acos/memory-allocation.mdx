[Предыдущая заметка](/ru/notes/acos/linking-and-loading) проследила программу до выполнения её первой команды: загрузчик отобразил код и инициализированные данные, зарезервировал обнулённые данные, подготовил стек и перешёл на точку входа. Всё в этом образе имеет размер, зафиксированный при компоновке, плюс стек, который растёт и сжимается вместе с вызовами. Большинству программ нужно больше: строка ввода неизвестной длины, список, который растёт во время работы программы, буфер, который должен пережить заполнившую его функцию. Эта заметка — о памяти, которая обслуживает такие нужды. Она начинается с контракта `malloc` и `free`, строит распределитель памяти (allocator), который хранит все свои служебные данные внутри управляемой им памяти, показывает, как эта память получается от ядра, и заканчивается ошибками, которые допускает контракт, и строками C — структурой данных, в которой происходит большинство этих ошибок.

**Обозначения.** *Блок* — непрерывный участок кучи, которым управляет распределитель; его *полезная часть* (payload) — то, чем может пользоваться программа. После $k$-го запроса $P_k$ — суммарный размер полезных частей занятых в этот момент блоков, а $H_k$ — размер кучи. **Пиковая степень использования** (peak utilization) после $k$ запросов равна

$$
U_k = \frac{\max_{i \le k} P_i}{H_k},
$$

то есть доле кучи, которая понадобилась данным программы в пике ([Bryant and O'Hallaron, 2016](#references), §9.9.3). У распределителя, который ничего не теряет, $U_k = 1$.

## Стек и куча \{#the-stack-and-the-heap\}

Программа на C хранит данные в трёх видах мест. **Статическая** память (глобальные и `static`-переменные) находится в сегментах данных и обнулённых данных всё время работы. **Автоматическая** память (локальные переменные) находится в кадре текущей функции на стеке: [соглашение о вызовах](/ru/notes/acos/procedures-and-the-stack) выделяет кадр, сдвигая указатель стека вниз при входе, и освобождает его, сдвигая обратно при возврате. **Выделенная** память находится в куче (heap) — области адресного пространства, которой управляет библиотечный распределитель, — и существует от вызова, который её выделил, до вызова, который её освободил.

| | Стек | Куча |
| --- | --- | --- |
| Выделяется | сдвигом указателя стека при входе в функцию | вызовом `malloc` |
| Освобождается | возвратом из функции | вызовом `free` |
| Время жизни | вызов функции | выбирает программа |
| Размер | фиксирован при компиляции функции, если она не использует `alloca` или массив переменной длины | любой, известен во время выполнения |
| Цена | одна команда | поиск в структурах данных распределителя |
| Предел | размер стека: 8176 КиБ для главного потока и 512 КиБ для остальных потоков на машине, используемой ниже (macOS 26, Apple M1) | адресное пространство и память, которую выделяет ядро |

Стек быстр, потому что работает строго по принципу «последним пришёл — первым ушёл»: освобождение кадра никогда не оставляет дыры. В этом же его ограничение. Функция не может вернуть указатель на свой локальный массив, потому что кадр, в котором лежит массив, займёт следующий вызов:

```c
char *greeting(void) {
    char buf[16] = "hello";
    return buf;           /* bug: buf dies when greeting returns */
}
```

Здесь clang предупреждает (`address of stack memory associated with local variable 'buf' returned`), но в общем случае компилятор такого не видит. Данные, которые должны пережить создавший их вызов или размер которых неизвестен до выполнения, кладут в кучу.

## Контракт malloc и free \{#the-contract-of-malloc-and-free\}

Стандартная библиотека C объявляет четыре функции в `<stdlib.h>` ([ISO/IEC 9899:2018](#references), §7.22.3):

- `void *malloc(size_t n)` возвращает указатель хотя бы на `n` байт, выровненный подходящим образом для объекта любого типа, или `NULL`, если выделить память не удаётся. Байты **не** инициализируются. В 64-битных Linux и macOS результат кратен 16.
- `void *calloc(size_t count, size_t size)` выделяет `count * size` байт, заполненных нулями, и возвращает `NULL`, если произведение переполняется.
- `void *realloc(void *p, size_t n)` меняет размер блока по адресу `p`, сохраняя его содержимое до меньшего из двух размеров. Она может переместить блок: тогда старый указатель становится недействительным и пользоваться нужно новым.
- `void free(void *p)` возвращает блок распределителю. `p` должен быть значением, которое вернула одна из трёх функций выше, и ещё не освобождённым; `free(NULL)` ничего не делает.

Обязательства разделены. Распределитель должен отвечать на каждый запрос сразу, в порядке поступления, памятью, которая не пересекается ни с одним блоком, ещё находящимся в использовании, и никогда не может переместить выданный блок, потому что программа хранит прямые адреса внутри него. Программа должна освобождать каждый блок ровно один раз, никогда не обращаться к блоку после освобождения и никогда не писать за пределы запрошенных `n` байт. Сторону программы в контракте никто не проверяет. Его нарушение — **неопределённое поведение** (undefined behaviour): программа может упасть, напечатать неверный результат или казаться работающей, пока не будут затёрты собственные данные распределителя.

Распределитель может выдать больше, чем просили. На машине, используемой в этой заметке, вызовы от `malloc(1)` до `malloc(16)` все возвращают блоки по 16 байт; `malloc_size`, запрос macOS о пригодном к использованию размере блока, сообщает 16 для каждого (раздел «Код» печатает эти значения).

## Отправная точка: распределитель со сдвигом указателя \{#baseline-a-bump-allocator\}

Простейший распределитель (bump allocator) хранит один указатель на первый неиспользованный байт большой области. `malloc(n)` округляет `n` вверх до выравнивания, возвращает указатель и сдвигает его на эту величину; `free` ничего не делает. Выделение — одно сложение, и никаких служебных данных не нужно вовсе.

Он перестаёт работать, как только программа освобождает память и рассчитывает получить её обратно. Цикл, который миллион раз выделяет буфер в 1 КиБ, пользуется им и освобождает его, требует от распределителя со сдвигом указателя 1 ГиБ, тогда как распределителю, повторно использующему освобождённые блоки, нужен один блок примерно в 1 КиБ. Распределитель со сдвигом указателя всё же остаётся правильным инструментом, когда все объекты умирают в один момент: компиляторы и обработчики запросов выделяют память из такой *арены* (arena) и освобождают всю область разом. Распределитель общего назначения должен повторно использовать освобождённые блоки по отдельности, и отсюда четыре вопроса: как `free` узнаёт размер переданного ей блока, где записаны свободные блоки, какой свободный блок обслуживает запрос и что происходит с оставшимся местом.

## Распределитель, который хранит служебные данные в куче \{#an-allocator-that-keeps-its-bookkeeping-in-the-heap\}

<aside class="callout"><strong>Ключевая идея.</strong> Хранить структуру данных распределителя внутри управляемой им кучи. Каждый блок начинается со слова-заголовка, в котором записаны его размер и бит занятости, поэтому блоки образуют список, который можно пройти от первого до последнего без какой-либо памяти вне кучи. Копия заголовка в конце блока, граничный тег, позволяет <code>free</code> найти и предыдущий блок и сливать соседние свободные блоки за постоянное время.</aside>

### Заголовки: как free узнаёт размер \{#headers-how-free-knows-the-size\}

`free(p)` получает только адрес. Поэтому распределитель хранит размер блока непосредственно перед полезной частью, в **заголовке** (header). Поскольку размер каждого блока кратен 8, три младших бита размера всегда равны нулю, и в самом младшем можно записать, занят ли блок: значение заголовка 25 означает занятый блок из 24 байт, 24 — свободный блок из 24 байт ([Bryant and O'Hallaron, 2016](#references), §9.9.6). В распределителе этой заметки заголовок занимает 4 байта, и размер блока учитывает и заголовок.

### Неявный список свободных блоков и стратегия размещения \{#the-implicit-free-list-and-the-placement-policy\}

Поскольку каждый заголовок даёт расстояние до следующего заголовка, блоки образуют список без всяких указателей: начинаем с первого заголовка, прибавляем его размер, чтобы попасть на следующий, и останавливаемся на заголовке размера 0, который отмечает конец. Такой список называется **неявным** (implicit free list), потому что он связывает все блоки, свободные и занятые, а свободные находятся пропуском остальных. Чтобы обслужить запрос, распределитель вычисляет нужный размер блока (полезная часть плюс теги, с округлением вверх до 8) и проходит список в поисках свободного блока не меньше этого размера. Какой блок он выберет, определяет **стратегия размещения** (placement policy):

- **Первый подходящий** (first fit) берёт первый свободный блок достаточного размера. Это просто, но мелкие остатки накапливаются у начала кучи, и каждому поиску приходится проходить мимо них.
- **Следующий подходящий** (next fit) начинает каждый поиск там, где остановился предыдущий. Поиски короче, а фрагментация часто хуже.
- **Наилучший подходящий** (best fit) просматривает все свободные блоки и берёт наименьший из достаточно больших. На каждый запрос он теряет меньше всего места и каждый раз стоит полного прохода по списку.

Например, если свободны блоки по 48, 16 и 32 байта в порядке адресов, а запросу нужен блок из 16 байт, первый подходящий делит блок из 48 байт на 16 и 32 и оставляет свободные блоки по 32, 16 и 32 байта; наилучший подходящий берёт ровно блок из 16 байт и не трогает блоки по 48 и 32, так что более поздний запрос блока из 40 байт ещё можно обслужить. Измерения на восьми реальных программах на C и C++ показали почти нулевую фрагментацию для нескольких обычных стратегий, в том числе наилучшего подходящего и первого подходящего в порядке адресов, если учесть заголовки и выравнивание ([Johnstone and Wilson, 1998](#references)): хорошую стратегию найти легко, а трудна её эффективная реализация.

### Разбиение и слияние \{#splitting-and-coalescing\}

Если выбранный блок больше запроса, распределитель **разбивает** его (splitting): передняя часть становится занятым блоком, а остаток — новым свободным блоком со своим заголовком. Если остаток меньше минимального блока (здесь 16 байт: два тега и наименьшая полезная часть, сохраняющая выравнивание), он остаётся внутри занятого блока как заполнение.

Когда блок освобождается, его соседи тоже могут быть свободны. Если оставить их отдельными блоками, возникает *ложная фрагментация* (false fragmentation): два соседних свободных блока по 16 байт не могут обслужить запрос на 24 байта, хотя вместе могли бы. Поэтому `free` **сливает** (coalescing) освобождённый блок со свободным соседом. Слить блок со следующим легко: заголовок следующего находится по адресу текущего заголовка плюс текущий размер. Для слияния с предыдущим нужен его размер, а в списке ничто не указывает назад.

### Граничные теги \{#boundary-tags\}

Ответ Кнута — повторить заголовок в конце каждого блока, в виде **концевой метки** (footer), или граничного тега (boundary tag) ([Knuth, 1997](#references), §2.5). Тогда слово непосредственно перед заголовком блока — концевая метка предыдущего блока, и она даёт размер и состояние предыдущего блока. Освобождение блока смотрит на два слова, концевую метку предыдущего блока и заголовок следующего, и попадает в один из четырёх случаев: оба соседа заняты (только сбросить бит), следующий свободен (слить с ним), предыдущий свободен (влить блок в него) или оба свободны (слить все три). В каждом случае переписываются один заголовок и одна концевая метка, поэтому `free` работает за постоянное время.

Цена — ещё одно слово на блок. Занятым блокам концевая метка не нужна, если заголовок следующего блока хранит бит, говорящий, свободен ли предыдущий блок; так промышленные распределители возвращают себе это слово.

Остаётся один свободный блок из 120 байт. Последовательность запросов и то, что распределитель печатает после каждого шага:

1. **Начало**: один свободный блок из 120 байт, полезная часть по смещению 8.
2. **`a = malloc(10)`** требует $10 + 8 = 18$ байт, с округлением вверх — блок из 24 байт. Первый подходящий делит свободный блок на 24 занятых и 96 свободных байт.
3. **`b = malloc(20)`** требует 28, то есть блок из 32 байт, отделённый от 96.
4. **`c = malloc(8)`** требует 16: блок из 16 байт, и в конце остаётся 48 свободных байт.
5. **`free(b)`**: оба соседа заняты, поэтому сбрасывается только бит. Теперь в куче 80 свободных байт, но в двух кусках по 32 и 48. Вызову `malloc(60)` нужен блок из 72 байт, и он завершается неудачей, хотя свободно больше 72 байт: это **внешняя фрагментация** (external fragmentation).
6. **`d = malloc(4)`** требует минимального блока из 16 байт. Первый подходящий первой находит дыру из 32 байт и делит её на 16 занятых и 16 свободных.
7. **`free(c)`**: концевая метка перед `c` принадлежит свободному блоку из 16 байт, а заголовок после `c` — свободному блоку из 48 байт, поэтому все три сливаются в один свободный блок из $16 + 16 + 48 = 80$ байт.
8. **`e = malloc(60)`** теперь находит блок из 80. Разбиение оставило бы 8 байт, меньше минимального блока, поэтому `e` получает все 80.

В конце программа хранит $10 + 4 + 60 = 74$ байта полезных данных в 120 байтах блоков. Остальные 46 байт — **внутренняя фрагментация** (internal fragmentation): 24 байта тегов (по 8 на блок) и 22 байта заполнения (6 в `a`, 4 в `d`, 12 в `e`). Пиковый объём полезных данных, 74 байта, достигнут на последнем шаге, поэтому пиковая степень использования $U = 74/128 \approx 0.58$ от всего массива.

### Явные и раздельные списки свободных блоков \{#explicit-and-segregated-free-lists\}

Неявный список просматривает и занятые блоки, поэтому `malloc` работает за время, линейное по числу всех блоков. Два усовершенствования это исправляют.

**Явный список свободных блоков** (explicit free list) связывает только свободные блоки — через указатели на предыдущий и следующий, хранящиеся в их полезных частях, которыми свободные блоки иначе не пользуются. Тогда поиск посещает только свободные блоки. Указатели задают минимальный размер блока: при 4-байтовых тегах и 8-байтовых указателях свободному блоку нужно не меньше $4 + 8 + 8 + 4 = 24$ байт.

**Раздельные списки свободных блоков** (segregated free lists) хранят по списку на каждый класс размеров (size class; например, 16, 32, 48 и 64 байта, затем степени двойки). Запрос идёт прямо в список своего класса, что приближает наилучший подходящий без поиска по всей куче. Промышленные распределители, такие как распределитель glibc, jemalloc и mimalloc, построены на классах размеров и добавляют к ним кэши каждого потока, чтобы потоки не соперничали за одну блокировку. Ядро операционной системы использует ту же идею в **слябовом распределителе** (slab allocator), который держит наготове кэши одинаковых объектов ядра, например дескрипторов процессов ([Bonwick, 1994](#references)).

Тот же компромисс встречается далеко от C. Сервер, генерирующий текст языковой моделью, должен хранить ключи и значения внимания каждого запроса, а память запроса растёт токен за токеном до длины, которую никто не знает заранее; если резервировать максимум на каждый запрос, бо́льшая часть памяти теряется на фрагментацию. vLLM выделяет эту память блоками фиксированного размера, как операционная система выделяет страницы ([Kwon et al., 2023](#references)); [заметка о квантизации](/ru/notes/nlp/quantization#memory-latency-and-throughput-of-generation) подсчитывает, сколько памяти занимает этот кэш.

### Фрагментация \{#fragmentation\}

Два вида потерь ведут себя по-разному. **Внутренняя фрагментация** — место внутри занятых блоков, не занятое полезными данными: теги, заполнение для выравнивания, остатки, слишком маленькие для разбиения. Она зависит только от уже сделанных запросов, поэтому её легко измерить. **Внешняя фрагментация** — свободная память, разбитая на куски, слишком маленькие для следующего запроса. Она зависит от будущих запросов, которых распределитель знать не может, а поскольку занятые блоки нельзя перемещать, ни один распределитель для C в общем случае не может её избежать: для любой стратегии размещения найдутся последовательности запросов, которые сильно фрагментируют кучу ([Wilson et al., 1995](#references)). Языки со сборкой мусора могут *уплотнять* (compact) кучу, перемещая объекты и обновляя все ссылки на них; к этому возвращается [заметка о средах выполнения языков](/ru/notes/acos/language-runtimes).

## Откуда берётся куча: brk, sbrk и mmap \{#where-the-heap-comes-from-brk-sbrk-and-mmap\}

Распределитель управляет памятью, но сначала он должен получить её от ядра. Unix даёт процессу два способа ([Kerrisk, 2010](#references), §7.1 и §49.7).

**Граница программы** (program break) — конец сегмента кучи, который начинается сразу над обнулёнными данными. Системный вызов `brk(addr)` переносит её в `addr`, а библиотечная функция `sbrk(incr)` сдвигает её на `incr` байт и возвращает прежний конец. Простой распределитель увеличивает кучу через `sbrk`, когда не подходит ни один свободный блок, и новая память становится ещё одним свободным блоком в конце его списка. Куча может уменьшаться только сверху, поэтому один живой блок у конца удерживает всё, что под ним.

**`mmap`** с `MAP_ANONYMOUS` запрашивает новую область страниц в любом месте адресного пространства, а `munmap` возвращает её. По умолчанию `malloc` в glibc так обслуживает запросы от 128 КиБ, чтобы большой блок можно было вернуть ядру при `free`, не дожидаясь блоков под ним; порог динамически растёт, когда освобождаются большие блоки ([mallopt(3)](#references)). Руководство macOS называет `brk` и `sbrk` «историческими курьёзами» (historical curiosities), и распределитель Apple границу программы не использует: он получает память в виде областей виртуальной памяти, как это делает `mmap`.

Оба вызова работают с целыми страницами: 16 КиБ на Apple M1, используемом ниже, 4 КиБ на большинстве машин x86-64 с Linux. Ни один из них не даёт физической памяти. Они резервируют виртуальные страницы; первое обращение к странице вызывает [страничный отказ](/ru/notes/acos/virtual-memory) (page fault), и только тогда ядро находит физический кадр, заполняет его нулями и отображает. Поэтому `calloc` большого блока из свежей памяти `mmap` дёшев: нули уже гарантированы, а страницы, к которым никто не обращается, никогда не получают физической памяти.

## Ошибки, которые допускает контракт \{#bugs-the-contract-allows\}

Сторону программы в контракте никто не проверяет, и на четыре ошибки приходится большинство ошибок работы с памятью:

- **Использование после освобождения** (use after free): чтение или запись блока после `free`. Распределитель уже мог отдать эту память кому-то другому или хранить там указатели своего списка свободных блоков.
- **Двойное освобождение** (double free): освобождение одного блока дважды. Блок может дважды попасть в список свободных, и два последующих вызова `malloc` могут вернуть один и тот же адрес.
- **Переполнение буфера** (buffer overflow): запись за конец блока или массива на стеке. В куче она затирает заголовок следующего блока; на стеке может затереть сохранённый адрес возврата — классический путь, которым атакующий захватывает управление программой.
- **Утечка** (leak): потеря последнего указателя на блок, который так и не освободили. Ничего не ломается, но долго работающая программа растёт без ограничений.

**AddressSanitizer** находит первые три ошибки в момент, когда они происходят ([Serebryany et al., 2012](#references)). Компилятор добавляет проверку перед каждой загрузкой и сохранением; *теневая память* (shadow memory) хранит по байту состояния на каждые 8 байт памяти программы, указывая, к скольким из них можно обращаться. Распределитель санитайзера окружает каждый блок отравленными *красными зонами* (redzones) и держит освобождённые блоки в карантине, а не использует их сразу повторно, поэтому обращение сразу за конец блока или в недавно освобождённый блок попадает в отравленную теневую память. Типичное замедление — примерно в 2 раза ([Clang AddressSanitizer documentation](#references)), что достаточно дёшево для тестирования. При компиляции командой `clang -g -fsanitize=address` (Apple clang 21, macOS 26) программа из раздела «Код», которая освобождает блок и затем читает его первый байт, останавливается с таким отчётом (выдержка: номер процесса и кадры стека внутри собственных `free` и `malloc` санитайзера опущены):

```text
ERROR: AddressSanitizer: heap-use-after-free on address 0x6020000000b0
READ of size 1 at 0x6020000000b0 thread T0
    #0 0x000102098910 in main bugs.c:9
0x6020000000b0 is located 0 bytes inside of 8-byte region [0x6020000000b0,0x6020000000b8)
freed by thread T0 here:
    #1 0x0001020988c8 in main bugs.c:9
previously allocated by thread T0 here:
    #1 0x00010209889c in main bugs.c:7
```

Отчёт называет неверное обращение, строку, которая его совершила, и строки, которые освободили и выделили блок. Двойное освобождение сообщается как `attempting double-free`, а запись `p[8]` в 8-байтовый блок — как `heap-buffer-overflow ... WRITE of size 1 ... located 0 bytes after 8-byte region`. Адреса меняются от запуска к запуску; виды ошибок, размеры и номера строк — нет.

Утечки находит при выходе LeakSanitizer, который в Linux входит в AddressSanitizer и печатает `Direct leak of 8 byte(s) in 1 object(s) allocated from:`, а за этим стек выделения ([Clang LeakSanitizer documentation](#references)). Apple clang на используемой здесь машине отвечает `detect_leaks is not supported on this platform`; вместо этого в macOS есть отдельный инструмент, и `leaks --atExit -- ./a.out` сообщает для той же программы `1 leak for 16 total leaked bytes` — 16, потому что таков размер блока за `malloc(8)`.

## Строки C \{#c-strings\}

В C нет строкового типа. Строка — массив `char`, который заканчивается на первом байте, равном нулю, — **завершающем нуле** (NUL terminator), и каждая строковая функция полагается на то, что найдёт его. Литерал `"hi!"` занимает четыре байта, `'h' 'i' '!' '\0'`: `sizeof` даёт 4, а `strlen` — 3. `strlen` приходится проходить байты, пока не встретится ноль, поэтому она работает за время, пропорциональное длине, и выходит за конец массива, если нуля нет.

У каждой стандартной функции копирования ([ISO/IEC 9899:2018](#references), §7.24.2) есть своя ловушка:

- `strcpy(dst, src)` копирует до завершающего нуля и никогда не спрашивает, каков размер `dst`. Копирование аргумента из 15 символов в `char name[8]` переполняет массив; AddressSanitizer сообщает `stack-buffer-overflow ... WRITE of size 16` и называет переменную: `[32, 40) 'name' <== Memory access at offset 40 overflows this variable`. Шестнадцать байт — потому что копируется и завершающий ноль.
- `strncpy(dst, src, n)` записывает ровно `n` байт: дополняет нулями, если `src` короче, и **не завершает** `dst` нулём, если длина `src` не меньше `n`. Копирование `"systems"` в `char d[6]` с `n = 6` оставляет шесть букв и ни одного нуля; программа должна сама записать `d[5] = '\0'`, и тогда остаётся `"syste"`.
- `strcat(dst, src)` дописывает в конец `dst`, поэтому сначала должна найти этот конец, и у неё та же непроверяемая граница, что у `strcpy`.

`snprintf(buf, size, format, ...)` — безопасный универсальный инструмент ([ISO/IEC 9899:2018](#references), §7.21.6.5): она записывает не больше `size` байт **включая** завершающий ноль, всегда завершает строку при `size > 0` и возвращает длину, которую имел бы полный вывод. `snprintf(buf, 8, "pid=%d", 123456)` сохраняет `"pid=123"` и возвращает 10, поэтому сравнение `returned >= size` обнаруживает усечение, а `returned + 1` — размер, который нужно выделить для второй попытки. BSD-функции `strlcpy` и `strlcat` принимают полный размер буфера и всегда завершают строку; они есть в macOS и в glibc начиная с версии 2.38 ([glibc 2.38 release notes](#references)).

Общее правило следует из представления: каждой функции, которая пишет строку, нужен размер приёмника, и каждая строка должна быть завершена нулём, прежде чем её передадут функции, которая строку читает.

## Ограничения \{#limitations\}

- **Блоки нельзя перемещать.** Программа хранит прямые указатели, поэтому распределитель никогда не может уплотнить кучу; некоторые последовательности запросов фрагментируют кучу при любой стратегии размещения.
- **Контракт не проверяется.** Использование после освобождения, двойное освобождение и переполнения незаметно портят память; санитайзеры находят их только на тех путях, которые выполняют тесты.
- **Потоки.** Один список свободных блоков под одной блокировкой упорядочивает все выделения в многопоточной программе в одну очередь; настоящие распределители добавляют кэши каждого потока и арены, которых у игрушечного распределителя этой заметки нет.
- **Строки не хранят длину.** Каждая операция платит поиском завершающего нуля, и каждая запись зависит от размера, переданного отдельно.

## Что нужно запомнить \{#what-you-should-remember\}

- Память на стеке живёт один вызов функции и освобождается возвратом; память в куче живёт от `malloc` до `free`, и её размер можно выбрать во время выполнения.
- `malloc` возвращает неинициализированную, подходящим образом выровненную память или `NULL`; `free` принимает ровно один указатель от `malloc`, один раз. Всё остальное — неопределённое поведение.
- Распределитель хранит перед каждым блоком заголовок с размером и битом занятости; заголовки образуют неявный список. Первый подходящий, следующий подходящий и наилучший подходящий выбирают свободный блок; разбиение возвращает остаток, слияние объединяет свободных соседей.
- Копия заголовка в конце блока, граничный тег, позволяет `free` слиться с предыдущим блоком за постоянное время.
- Внутренняя фрагментация — потери внутри блоков; внешняя фрагментация — свободная память в кусках, слишком маленьких, чтобы ими воспользоваться. В разобранном примере 80 свободных байт не смогли обслужить блок из 72 байт.
- Куча растёт через `brk`/`sbrk` или через `mmap`, целыми страницами, а физическая память назначается только при первом обращении.
- AddressSanitizer сообщает об использовании после освобождения, двойном освобождении и переполнениях в строке, где произошла ошибка; LeakSanitizer (Linux) или `leaks` (macOS) находят утечки при выходе.
- Строка C заканчивается своим нулевым байтом. `strcpy` и `strcat` игнорируют размер приёмника, `strncpy` может не завершить строку нулём, а `snprintf` безопасно усекает и возвращает длину, которая ей была нужна.

## Код \{#code\}

Распределитель из разобранного примера. Он печатает список блоков после каждого запроса, каждый блок — как состояние, размер и смещение полезной части; скомпилировать и запустить: `clang -std=c17 -Wall -Wextra -O0 alloc.c -o alloc && ./alloc`:

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

/* A first-fit allocator with boundary tags over a 128-byte static heap.
   Every block has a 4-byte header and a 4-byte footer holding (size | allocated bit);
   sizes include both tags and are multiples of 8, so every payload is 8-byte aligned. */
#define HEAP 128
static _Alignas(8) uint8_t heap[HEAP];

static uint32_t get(size_t off)             { uint32_t v; memcpy(&v, heap + off, 4); return v; }
static void     put(size_t off, uint32_t v) { memcpy(heap + off, &v, 4); }
static uint32_t size_at(size_t hdr)  { return get(hdr) & ~7u; }
static int      alloc_at(size_t hdr) { return get(hdr) & 1; }
static void     tag(size_t hdr, uint32_t size, int a) { put(hdr, size | a); put(hdr + size - 4, size | a); }

static void heap_init(void) {
    put(0, 0);                        /* padding word: the first payload lands at offset 8 */
    tag(4, HEAP - 8, 0);              /* one free block of 120 bytes */
    put(HEAP - 4, 0 | 1);             /* end marker: a size-0 "allocated" header ends the list */
}

static void *my_malloc(size_t n) {
    uint32_t need = (uint32_t)((n + 8 + 7) & ~(size_t)7);       /* payload + tags, rounded up to 8 */
    if (need < 16) need = 16;
    for (size_t h = 4; size_at(h) > 0; h += size_at(h)) {       /* first fit: walk the implicit list */
        uint32_t sz = size_at(h);
        if (alloc_at(h) || sz < need) continue;
        if (sz - need >= 16) { tag(h, need, 1); tag(h + need, sz - need, 0); }   /* split */
        else tag(h, sz, 1);                                      /* remainder too small: take it all */
        return heap + h + 4;
    }
    return NULL;
}

static void my_free(void *p) {
    size_t h = (size_t)((uint8_t *)p - heap) - 4;
    uint32_t sz = size_at(h);
    size_t next = h + sz;
    if (!alloc_at(next)) sz += size_at(next);                    /* coalesce with the next block */
    if (h > 4 && !(get(h - 4) & 1)) {                            /* the previous block's footer says it is free */
        h -= get(h - 4) & ~7u;
        sz += size_at(h);
    }
    tag(h, sz, 0);
}

static void show(const char *what) {
    printf("%-14s", what);
    for (size_t h = 4; size_at(h) > 0; h += size_at(h))
        printf(" [%s %u @%zu]", alloc_at(h) ? "A" : "f", size_at(h), h + 4);
    printf("\n");
}

int main(void) {
    heap_init();                     show("init");
    char *a = my_malloc(10);         show("a=malloc(10)");
    char *b = my_malloc(20);         show("b=malloc(20)");
    char *c = my_malloc(8);          show("c=malloc(8)");
    my_free(b);                      show("free(b)");
    printf("malloc(60) -> %s\n", my_malloc(60) ? "ok" : "NULL: 80 bytes free, no block of 72");
    char *d = my_malloc(4);          show("d=malloc(4)");
    my_free(c);                      show("free(c)");
    char *e = my_malloc(60);         show("e=malloc(60)");
    printf("payload offsets a=%td d=%td e=%td\n", a - (char *)heap, d - (char *)heap, e - (char *)heap);
    return 0;
}
/* Output:
init           [f 120 @8]
a=malloc(10)   [A 24 @8] [f 96 @32]
b=malloc(20)   [A 24 @8] [A 32 @32] [f 64 @64]
c=malloc(8)    [A 24 @8] [A 32 @32] [A 16 @64] [f 48 @80]
free(b)        [A 24 @8] [f 32 @32] [A 16 @64] [f 48 @80]
malloc(60) -> NULL: 80 bytes free, no block of 72
d=malloc(4)    [A 24 @8] [A 16 @32] [f 16 @48] [A 16 @64] [f 48 @80]
free(c)        [A 24 @8] [A 16 @32] [f 80 @48]
e=malloc(60)   [A 24 @8] [A 16 @32] [A 80 @48]
payload offsets a=8 d=32 e=48
*/
```

Четыре ошибки, по одной на аргумент командной строки. Соберите с AddressSanitizer, `clang -std=c17 -Wall -Wextra -O0 -g -fsanitize=address bugs.c -o bugs`, и запустите `./bugs 1`, `./bugs 2`, `./bugs 3`; первая строка каждого отчёта приведена в комментариях. Аргумент 4 теряет блок, о чём AddressSanitizer в Linux сообщает при выходе; в macOS запустите сборку без санитайзера под `leaks --atExit -- ./bugs 4`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(int argc, char **argv) {
    int which = argc > 1 ? atoi(argv[1]) : 0;
    char *p = malloc(8);
    strcpy(p, "hello");
    if (which == 1) { free(p); printf("%c\n", p[0]); }          /* use after free */
    if (which == 2) { free(p); free(p); }                        /* double free */
    if (which == 3) { p[8] = '!'; free(p); }                     /* one byte past the block: overflow */
    if (which == 4) { p = NULL; }                                /* the only pointer is lost: leak */
    if (which == 0) free(p);
    return 0;
}
/* ./bugs 1  ERROR: AddressSanitizer: heap-use-after-free ... READ of size 1 ... in main bugs.c:9
   ./bugs 2  ERROR: AddressSanitizer: attempting double-free ... in main bugs.c:10
   ./bugs 3  ERROR: AddressSanitizer: heap-buffer-overflow ... WRITE of size 1 ... in main bugs.c:11
   leaks --atExit -- ./bugs 4   (macOS, built without -fsanitize)   1 leak for 16 total leaked bytes. */
```

Строковые функции и размеры маленьких блоков `malloc`. Последний цикл использует `malloc_size` из `<malloc/malloc.h>`, который есть только в macOS (аналог в glibc — `malloc_usable_size` из `<malloc.h>`, и его размеры другие):

```c
#include <malloc/malloc.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char s[] = "hi!";                                  /* 4 bytes: 'h' 'i' '!' '\0' */
    printf("sizeof=%zu strlen=%zu last=%d\n", sizeof s, strlen(s), s[3]);

    char d[6];
    strncpy(d, "systems", sizeof d);                   /* copies 6 bytes, no terminator */
    printf("strncpy terminated? %s\n", memchr(d, '\0', sizeof d) ? "yes" : "no");
    d[sizeof d - 1] = '\0';                            /* terminate by hand */
    printf("after fix: \"%s\"\n", d);

    char buf[8];
    int need = snprintf(buf, sizeof buf, "pid=%d", 123456);
    printf("snprintf wrote \"%s\", wanted %d chars, truncated: %s\n", buf, need, need >= (int)sizeof buf ? "yes" : "no");

    char path[32];
    snprintf(path, sizeof path, "%s/%s", "/tmp", "notes.txt");   /* the safe way to join strings */
    printf("%s (%zu chars)\n", path, strlen(path));

    for (size_t n = 1; n <= 64; n *= 4) {              /* macOS only: the usable size of a block */
        void *p = malloc(n);
        printf("malloc(%zu): block of %zu\n", n, malloc_size(p));
        free(p);
    }
    return 0;
}
```

## Дальше \{#next\}

Каждый блок в этой заметке принадлежал одной программе, работающей в одиночку. [Следующая заметка](/ru/notes/acos/processes-and-threads) помещает на машину несколько программ сразу. Операционная система заключает каждую работающую программу в процесс со своим адресным пространством, так что куча одного процесса невидима для остальных; она создаёт процессы через `fork` и `exec`, добавляет потоки, разделяющие одну кучу, и решает, какой из них следующим получит процессор.
