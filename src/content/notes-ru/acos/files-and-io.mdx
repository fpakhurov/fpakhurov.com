[Предыдущая заметка](/ru/notes/acos/inter-process-communication) соединяла процессы неименованными каналами, разделяемой памятью и сигналами. Каждый из этих каналов исчезает, когда процессы завершаются. Но неименованный канал уже был похож на файл: программа получала небольшое целое число, *дескриптор*, и передавала его в `read` и `write`. Эта заметка — о настоящих файлах, данных, которые переживают записавший их процесс. Она по очереди отвечает на пять вопросов: на что указывает дескриптор внутри ядра и что разделяют `fork` и `dup`; почему чтение по одному байту за системный вызов медленно и как это исправляет буферизация; как файловая система находит байты файла по имени; как прочитать файл вообще без `read`; и когда записанные данные действительно в безопасности на диске.

**Обозначения.** $n$ — размер файла в байтах, $B$ — размер буфера, так что цикл, читающий по $B$ байт за вызов, делает $\lceil n/B \rceil + 1$ вызовов: последний возвращает 0 в конце файла. $P$ — размер страницы в системе виртуальной памяти. Размеры даны в двоичных единицах: 1 КиБ $= 2^{10}$ байт, 1 МиБ $= 2^{20}$, 1 ГиБ $= 2^{30}$, 1 ТиБ $= 2^{40}$.

## Что видит программа: дескрипторы и пять вызовов \{#what-a-program-sees-descriptors-and-five-calls\}

Для программы в Unix файл — это последовательность байтов с именем. Ядро не навязывает ни записей, ни строк, ни типов; текстовый файл — последовательность байтов, в которой просто встречаются символы перевода строки. Процесс не обращается к файлу по имени при каждом доступе. Он один раз *открывает* файл и получает **файловый дескриптор** (file descriptor) — небольшое неотрицательное целое число, — и передаёт это число во все последующие вызовы. Каждый процесс начинает работу с тремя дескрипторами, которые открыла для него оболочка: 0 — стандартный ввод, 1 — стандартный вывод, 2 — стандартный вывод ошибок. `open` всегда возвращает наименьший неиспользуемый номер, поэтому первый файл, который открывает программа, обычно получает дескриптор 3.

Почти всю работу выполняют пять системных вызовов:

```c
int     open(const char *path, int flags, ... /* mode_t mode, when creating */);
ssize_t read(int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);
off_t   lseek(int fd, off_t offset, int whence);
int     close(int fd);
```

- `flags` задаёт, как открывать: ровно один из `O_RDONLY`, `O_WRONLY` или `O_RDWR` плюс параметры вроде `O_CREAT` (создать файл, если его нет, с битами прав `mode`), `O_TRUNC` (обрезать до длины 0) и `O_APPEND` (каждая запись идёт в текущий конец файла).
- У каждого открытого файла есть текущее **смещение** (offset). `read` и `write` начинают со смещения и продвигают его на число переданных байтов. `lseek` устанавливает его: в само значение `offset` (`SEEK_SET`), относительно текущего смещения (`SEEK_CUR`) или относительно конца файла (`SEEK_END`), — и возвращает новое значение.
- `read` возвращает число действительно прочитанных байтов, которое может быть меньше `count`, и 0 в конце файла. И `read`, и `write` при ошибке возвращают $-1$ и устанавливают `errno`. Если программе нужно ровно `count` байт, она должна читать в цикле, потому что неименованные каналы, терминалы и сокеты обычно возвращают меньше.

**Разобранный пример.** Файл содержит 10 байт `hello, os\n` с номерами от 0 до 9. `open` возвращает 3. `read(3, buf, 4)` возвращает 4, помещает `hell` в `buf` и переводит смещение в 4. `lseek(3, -2, SEEK_END)` возвращает $10 - 2 = 8$. `read(3, buf, 4)` просит 4 байта, но остались только байты 8 и 9, поэтому он возвращает 2: `s` и перевод строки. Следующий `read` возвращает 0 — конец файла, — и `close(3)` освобождает дескриптор.

Те же пять вызовов работают с терминалом, неименованным каналом, сокетом или устройством. `write(1, buffer, 13)` программы hello world из [первой заметки](/ru/notes/acos/computer-systems) не знает, что такое дескриптор 1 — терминал, файл или канал к другой программе; это решила оболочка ещё до запуска программы.

## Три таблицы за дескриптором \{#three-tables-behind-a-descriptor\}

Дескриптор — это индекс, а то, что он индексирует, занимает три уровня таблиц ядра:

- **Таблица дескрипторов** (descriptor table), по одной на процесс, — часть состояния процесса в ядре. Элемент $i$ хранит указатель на описание открытого файла и один флаг, close-on-exec.
- **Таблица открытых файлов** (open file table), одна на всю систему. Каждый её элемент, **описание открытого файла** (open file description), фиксирует, как файл был открыт: текущее смещение, режим доступа, флаги состояния вроде `O_APPEND` и число указывающих на него дескрипторов.
- **Таблица inode** — копии **индексных дескрипторов** (inodes) в памяти ядра. Inode описывает сам файл: его тип, владельца, биты прав, размер, временные метки и расположение его блоков на диске. Он один на файл, сколько бы раз файл ни был открыт.

<aside class="callout"><strong>Ключевая идея.</strong> Смещение хранится в описании открытого файла, а не в дескрипторе и не в файле. Дескрипторы, разделяющие одно описание, разделяют одно смещение: такие дескрипторы создают <code>dup</code> и <code>fork</code>. Каждый вызов <code>open</code> создаёт новое описание со своим смещением, даже для того же файла.</aside>

Каждый вызов меняет таблицы по-своему. `open` занимает наименьшую свободную ячейку, создаёт новое описание со смещением 0 и направляет его на inode файла. `dup(fd)` занимает другую свободную ячейку и направляет её на *то же* описание. `fork` копирует всю таблицу дескрипторов родителя, поэтому каждый дескриптор потомка указывает на то же описание, что и дескриптор родителя с тем же номером. `close` освобождает ячейку и уменьшает счётчик описания; описание исчезает, только когда счётчик доходит до 0.

**Разобранный пример.** Процесс создаёт `log.txt` и получает дескриптор 3 (описание A), вызывает `dup(3)` и получает 4, открывает файл второй раз и получает 5 (описание B). Затем он вызывает `fork`. Потомок пишет 6 байт `child ` через дескриптор 3. Описание A разделяют дескрипторы 3 и 4 обоих процессов, всего четыре ссылки, поэтому его смещение становится равным 6 для всех них; `lseek(4, 0, SEEK_CUR)` у родителя возвращает 6. Через описание B ещё ничего не писали, и `lseek(5, 0, SEEK_CUR)` у родителя возвращает 0. Если теперь родитель запишет `XY` через дескриптор 5, байты лягут по смещению 0 и затрут `ch`; если затем он запишет `parent\n` через 4, байты лягут по смещению 6. В итоге файл содержит `XYild parent` — это и печатает вторая программа из раздела «Код».

<FileTables />

1. `open` возвращает дескриптор 3, который указывает на новое описание A, а оно — на inode.
2. `dup(3)` возвращает дескриптор 4 — вторую ячейку, указывающую на то же A.
3. Второй `open` того же пути возвращает дескриптор 5 и новое описание B со своим смещением и тем же inode.
4. `fork` копирует таблицу: дескрипторы 3, 4 и 5 потомка указывают на те же A и B.
5. Запись потомка через дескриптор 3 сдвигает смещение A с 0 на 6 — для всех дескрипторов, разделяющих A.

Оба поведения используются намеренно. Оболочка выполняет `cmd > out 2>&1`, открывая `out` как дескриптор 1 и затем вызывая `dup2(1, 2)`: стандартный вывод и стандартный вывод ошибок разделяют одно смещение, поэтому их строки идут в файле друг за другом, а не затирают друг друга. Две программы, дописывающие в один журнальный файл, открывают его по отдельности, поэтому их смещения независимы; они используют `O_APPEND`, и тогда ядро перед каждой записью одним шагом переносит смещение в конец файла.

## Отправная точка: один системный вызов на байт \{#baseline-one-system-call-per-byte\}

Простейший способ обработать файл — цикл, читающий по одному байту:

```c
char c;
while (read(fd, &c, 1) == 1)
    process(c);
```

Он работает с любым видом файлов и обрабатывает каждый байт сразу, как тот приходит. Цена — число вызовов: $n + 1$ для файла из $n$ байт. Каждый вызов входит в ядро и возвращается, как показала [заметка о системных вызовах](/ru/notes/acos/system-calls), и стоит гораздо больше, чем перемещаемый им один байт. На Apple M1 (macOS 26.5, `clang -O0`) чтение так файла размером 1 000 000 байт заняло около 450 мс, когда файл уже был в памяти, — около 450 нс на вызов; чтение по 4096 байт за вызов заняло около 1.3 мс (последняя программа в разделе «Код»; числа меняются от машины к машине и от запуска к запуску). Работа на байт в обоих циклах одинакова. Разница почти целиком — стоимость миллиона входов в ядро и выходов из него.

## Буферизация: меньше вызовов, но крупнее \{#buffering-fewer-and-larger-calls\}

Исправление — перемещать много байтов за вызов. Цикл, читающий в буфер из $B$ байт, делает

$$
\Big\lceil \frac{n}{B} \Big\rceil + 1
$$

вызовов: $\lceil n/B \rceil$ возвращают данные, и последний возвращает 0. Для файла из $n = 100\,000$ байт и $B = 4096$ это $\lceil 24.41 \rceil + 1 = 26$ вызовов вместо $100\,001$, примерно в 3800 раз меньше.

Стандартная библиотека C делает это за нас. `FILE *`, полученный от `fopen`, несёт буфер в собственной памяти процесса. `fgetc` берёт следующий байт из буфера и вызывает `read`, только когда буфер пуст, чтобы заполнить его заново до $B$ байт; `fputc` и `printf` заполняют выходной буфер и вызывают `write`, только когда он полон, на переводе строки в случае терминала или когда программа вызывает `fflush`, `fclose` или `exit`. Библиотека сама выбирает $B$, обычно равным предпочтительному размеру блока файловой системы; на тестовой машине она выбрала 4096 байт. Первая программа в разделе «Код» делает это видимым: она читает файл размером 100 000 байт с помощью `fgetc` и следит за смещением в ядре, которое прыгает на 4096, только когда библиотека заново заполняет свой буфер. Она видит 25 заполнений и 100 000 вызовов `fgetc` против 100 001 вызова `read` у побайтового цикла.

| Чтение 1 000 000 байт | Вызовов `read` | Время, один запуск (Apple M1, `-O0`) |
| --- | --- | --- |
| `read`, 1 байт за вызов | 1 000 001 | около 450 мс |
| `fgetc` с буфером stdio на 4096 байт | 246 | около 19 мс |
| `read`, 4096 байт за вызов | 246 | около 1.3 мс |

Цикл на stdio в 24 раза быстрее отправной точки, но всё ещё в 15 раз медленнее прямого чтения блоками при том же числе системных вызовов. Остаётся стоимость одного библиотечного вызова на байт: POSIX требует, чтобы каждая функция stdio блокировала свой `FILE` от других потоков, и `fgetc` платит за это на каждом байте. Чтение блоками с помощью `fread` или вызов `getc_unlocked` в однопоточном цикле убирает большую часть этой стоимости.

У буферизации вывода есть одна ловушка, которую стоит знать. `printf("before fork\n")`, за которым следует `fork()`, печатает строку один раз, когда вывод идёт на терминал (он буферизуется построчно), но дважды, когда вывод идёт в файл или канал: в момент `fork` строка ещё лежит в буфере родителя, потомок получает копию буфера, и обе копии сбрасываются при завершении двух процессов. Вызывайте `fflush(stdout)` перед `fork`.

Ниже этого буфера есть второй. Ядро держит недавно использованные блоки файлов в памяти, в **страничном кэше** (page cache), поэтому `read` уже закэшированных данных копирует их из памяти и вообще не обращается к диску; приведённые выше времена измерены, когда файл был в кэше. Записи тоже попадают в страничный кэш, и это важно для последнего раздела.

## Где живут байты: inode и каталоги \{#where-the-bytes-live-inodes-and-directories\}

Диск — массив блоков фиксированного размера, обычно 4 КиБ. Файловая система строит поверх него файлы и имена с помощью двух структур.

**Индексный дескриптор** (inode) описывает один файл: его тип (обычный файл, каталог, символьная ссылка, устройство), владельца и группу, биты прав, размер, три временные метки, **счётчик ссылок** (link count) и расположение блоков данных. Inode пронумерованы, и номер уникален в пределах одной файловой системы. Имени файла inode *не* содержит.

Классическая схема Unix, используемая в ext2, хранит в inode 15 указателей на блоки: 12 указывают прямо на блоки данных, 13-й — на блок, полный указателей (*одинарный косвенный*, single indirect), 14-й — на блок указателей на такие блоки (*двойной косвенный*, double indirect), а 15-й — ещё на уровень глубже (*тройной косвенный*, triple indirect). При блоках по 4 КиБ и 4-байтных указателях блок указателей вмещает 1024 из них, так что четыре части охватывают

$$
\begin{aligned}
12 \cdot 4\ \text{КиБ} &= 48\ \text{КиБ}, & 1024 \cdot 4\ \text{КиБ} &= 4\ \text{МиБ}, \\
1024^2 \cdot 4\ \text{КиБ} &= 4\ \text{ГиБ}, & 1024^3 \cdot 4\ \text{КиБ} &= 4\ \text{ТиБ}.
\end{aligned}
$$

Маленьким файлам, обычному случаю, не нужно ничего, кроме inode; большие файлы платят одним-двумя дополнительными чтениями блоков.

**Разобранный пример.** Байт 1 000 000 файла лежит в блоке $\lfloor 1\,000\,000/4096 \rfloor = 244$. Блоки с 0 по 11 прямые, поэтому блок 244 — элемент $244 - 12 = 232$ одинарного косвенного блока: чтобы найти его, нужны inode, косвенный блок и затем блок данных. Байт 5 000 000 лежит в блоке 1220, за пределами $12 + 1024 = 1036$ блоков первых двух частей, поэтому это элемент $1220 - 1036 = 184$ первого блока под двойным косвенным указателем: inode, двойной косвенный блок, косвенный блок, блок данных. ext4 заменяет большинство этих указателей **экстентами** (extents) — парами из начального блока и длины до 32 768 блоков (128 МиБ при блоках по 4 КиБ), — и inode хранит четыре экстента непосредственно. Непрерывный файл размером 100 МБ, 24 415 блоков, описывается тогда одним экстентом вместо 24 415 указателей.

**Каталог** (directory) — это файл, данные которого представляют собой список записей, каждая из которых — имя и номер inode. Открытие `/home/ann/notes.txt` — это обход: начать с inode корневого каталога (номер 2 в ext2, ext3 и ext4), прочитать его записи и найти `home` с номером inode, прочитать этот inode и его записи и найти `ann`, затем сделать то же для `notes.txt`. Это четыре inode и три каталога, читаемые с диска, если их нет в кэше; Linux хранит недавние поиски имён в своём *кэше записей каталога* (dentry cache), так что повторные открытия того же пути пропускают обход. Каждый каталог на пути также должен давать право поиска — тема [следующей заметки](/ru/notes/acos/users-and-permissions).

## Жёсткие и символьные ссылки \{#hard-links-and-symbolic-links\}

Поскольку имя хранится в каталоге, а файл — в inode, у одного файла может быть несколько имён. **Жёсткая ссылка** (hard link) — ещё одна запись в каталоге с тем же номером inode, созданная вызовом `link` (в оболочке — `ln`). Все имена равноправны: ни одно из них не является оригиналом. Сколько их, говорит счётчик ссылок inode. `unlink` (в оболочке — `rm`) удаляет одно имя и уменьшает счётчик, а ядро освобождает inode и его блоки, только когда счётчик равен 0 *и* ни одно описание открытого файла больше не указывает на этот inode. Поэтому программа может создать временный файл, открыть его и сразу удалить его имя: данные остаются доступными через дескриптор и исчезают сами, когда программа закроет его или умрёт. Жёсткие ссылки не могут пересекать границы файловых систем, потому что номера inode уникальны только внутри одной, и не могут указывать на каталоги, что допустило бы циклы в дереве; единственные исключения — записи `.` и `..`, которые есть в каждом каталоге.

**Символьная ссылка** (symbolic link) — отдельный файл со своим inode, содержимое которого — путь. Встретив её при поиске, ядро начинает поиск заново с этого пути. Символьная ссылка может указывать на каталог или на другую файловую систему, и она может стать **висячей** (dangling): если цель удалена, ссылка остаётся, а её открытие завершается ошибкой. `stat` следует по символьным ссылкам, а `lstat` описывает саму ссылку.

<LinksAndInodes />

1. Каталог — файл, который отображает имена в номера inode.
2. `a.txt` и `b.txt` хранят один и тот же номер: два имени одного файла, inode которого имеет 2 ссылки.
3. Inode хранит метаданные и указатели на блоки данных, но не имя.
4. `c.txt` — символьная ссылка: отдельный inode, содержимое которого — путь `a.txt`, заново разыскиваемый при каждом открытии `c.txt`.

**Разобранный пример.** Третья программа в разделе «Код» создаёт `a.txt` с 5 байтами — `data` и перевод строки, — добавляет жёсткую ссылку `b.txt` и символьную ссылку `c.txt`, указывающую на `a.txt`. `stat` сообщает один и тот же inode для `a.txt` и `b.txt` с 2 ссылками, а `lstat` сообщает, что `c.txt` — символьная ссылка длиной 5 байт, длиной строки `a.txt`. После `unlink("a.txt")` у `b.txt` 1 ссылка, и он по-прежнему хранит данные, а открытие `c.txt` завершается ошибкой «No such file or directory»: имени, которое в ней записано, больше нет. Наконец программа открывает `b.txt` и тоже удаляет его имя. Счётчик ссылок равен 0, но `read` через открытый дескриптор по-прежнему возвращает 5 байт.

## Один интерфейс для многих файловых систем: VFS \{#one-interface-for-many-file-systems-the-vfs\}

Машина с Linux монтирует в одно дерево много видов файловых систем: ext4 или XFS на диске, `tmpfs` в памяти, NFS по сети, `procfs` в `/proc`, файлы которой ядро порождает в момент чтения. Неименованные каналы и сокеты — тоже файлы, принадлежащие внутренним файловым системам без имён. Программа ничего этого не видит, потому что системные вызовы реализованы один раз, в **виртуальной файловой системе** (virtual file system, VFS), а VFS передаёт работу файловой системе, которой принадлежит файл.

VFS работает с четырьмя видами объектов: *суперблоком* (superblock) для каждой смонтированной файловой системы, *inode* для каждого файла, *dentry* для каждого закэшированного имени и *file* для каждого описания открытого файла. Каждая файловая система предоставляет таблицы функций, которые реализуют операции для её собственных объектов. Таблица для открытых файлов выглядит так (ядро Linux, `include/linux/fs.h`, с сокращениями; только Linux, здесь не запускалось):

```c
struct file_operations {
    loff_t  (*llseek)    (struct file *, loff_t, int);
    ssize_t (*read)      (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)     (struct file *, const char __user *, size_t, loff_t *);
    ssize_t (*read_iter) (struct kiocb *, struct iov_iter *);
    ssize_t (*write_iter)(struct kiocb *, struct iov_iter *);
    int     (*mmap)      (struct file *, struct vm_area_struct *);
    int     (*open)      (struct inode *, struct file *);
    int     (*fsync)     (struct file *, loff_t, loff_t, int datasync);
    /* ... and more operations ... */
};
```

**Разобранный пример.** Один и тот же `read(fd, buf, 4096)` делает четыре разные вещи в зависимости от того, на что указывает `fd`. Для файла на диске с ext4 VFS вызывает `read_iter` из ext4, которая копирует данные из страничного кэша и запрашивает у драйвера диска недостающие блоки. Для `/proc/self/status` procfs форматирует состояние вызывающего процесса в текст в этот самый момент. Для неименованного канала код каналов копирует байты из буфера канала в ядре или усыпляет процесс, пока писатель их не предоставит. Для `/dev/zero` драйвер символьного устройства заполняет буфер нулями. В BSD и macOS та же структура называется слоем *vnode* — по названию разработки Sun, в которой она появилась ([Kleiman, 1986](#references)).

## Отображение файла в память \{#mapping-a-file-into-memory\}

Файл можно прочитать и без `read`. Системный вызов `mmap` делает диапазон файла частью адресного пространства процесса:

```c
char *p = mmap(NULL, n, PROT_READ, MAP_PRIVATE, fd, 0);   /* p[i] is now byte i of the file */
```

Когда `mmap` возвращается, никакие данные не скопированы. Ядро лишь записывает, что этот диапазон виртуальных адресов отображён на этот файл. Первое обращение к каждой странице вызывает страничный отказ (page fault), как в [заметке о виртуальной памяти](/ru/notes/acos/virtual-memory); обработчик отказа находит страницу файла в страничном кэше, при необходимости читая её с диска, и отображает в процесс именно эту страницу. С этого момента `p[i]` — обычная загрузка. С `MAP_SHARED` сохранения тоже попадают в страничный кэш, их видят другие процессы, отобразившие файл, и ядро записывает их обратно в файл; с `MAP_PRIVATE` первое сохранение в страницу даёт процессу собственную копию (копирование при записи, copy-on-write), и файл не меняется. Точно так же ядро отображает в память исполняемые файлы и разделяемые библиотеки ([компоновка и загрузка](/ru/notes/acos/linking-and-loading)).

**Разобранный пример.** Чтение файла размером 100 000 байт через отображение не делает ни одного вызова `read`. При страницах в $P = 4096$ байт оно затрагивает $\lceil 100\,000/4096 \rceil = 25$ страниц, так что вызывает не более 25 страничных отказов; при страницах по 16 КиБ на тестовой машине Apple M1 — не более $\lceil 100\,000/16\,384 \rceil = 7$. Каждый отказ входит в ядро, как и системный вызов, поэтому для одного последовательного прохода отображение мало что выигрывает у `read` с большим буфером. Оно окупается при произвольном доступе к большому файлу, для данных, читаемых много раз, и для разделения одной копии между процессами. У него есть и свои издержки: страница — наименьшая единица, неименованные каналы и сокеты отобразить нельзя, а ошибка проявляется сигналом, а не возвращаемым значением: обращение к странице за концом файла, который обрезал другой процесс, вызывает `SIGBUS`.

## Когда данные в безопасности? Страничный кэш и fsync \{#when-is-the-data-safe-the-page-cache-and-fsync\}

`write` возвращается, как только байты попали в страничный кэш. Страница помечается как *грязная* (dirty), и ядро запишет её на диск позже, в фоне. В Linux по умолчанию поток сброса (flusher thread) просыпается каждые 5 секунд и записывает обратно страницы, которые остаются грязными дольше 30 секунд (параметры `vm.dirty_writeback_centisecs` и `vm.dirty_expire_centisecs`, 500 и 3000). Отключение питания теряет всё, что ещё не записано обратно, — примерно последние полминуты записей, — хотя каждая программа видела, что её `write` завершился успешно. `close` этого не меняет.

Программа, которая не должна терять данные, просит об этом явно. `fsync(fd)` возвращается, только когда данные и метаданные файла переданы устройству хранения; `fdatasync` пропускает метаданные, которые не нужны, чтобы прочитать данные обратно, например время изменения. Только что созданному файлу нужен ещё и `fsync` его каталога, потому что имя файла хранится в данных каталога. В macOS `fsync` передаёт данные накопителю, но не заставляет накопитель опустошить собственный кэш; справочная страница направляет программы, которым нужна такая гарантия, например базы данных, к `fcntl(fd, F_FULLFSYNC)`.

**Разобранный пример.** Редактор, сохраняющий документ, никогда не должен оставлять наполовину записанный файл, даже если питание пропадёт посередине. Он записывает новое содержимое во временный файл в том же каталоге, вызывает для него `fsync`, переименовывает его поверх старого имени с помощью `rename`, которая заменяет запись в каталоге за один шаг, и вызывает `fsync` для каталога. После сбоя имя указывает либо на полный старый файл, либо на полный новый. Файловые системы защищают собственные структуры — inode, каталоги и карты свободных блоков — журналом (journal) или копированием при записи; содержимое файла, который программа как раз записывала, они сами по себе не защищают.

## Ограничения \{#limitations\}

- **Неполные чтения и записи.** `read` и `write` могут передать меньше байтов, чем запрошено, особенно на неименованных каналах, терминалах и сокетах, а сигнал может их прервать. Правильный код работает в цикле.
- **Два буфера могут расходиться.** Смешивание `fgetc` и `read` на одном файле даёт неверные результаты, потому что stdio уже прочитал данные вперёд в свой буфер. Несброшенный вывод теряется при `_exit` и сбое и дублируется при `fork`.
- **Общие и раздельные смещения.** Дескрипторы от `dup` и `fork` сдвигают смещение друг друга; раздельные `open` затирают данные друг друга, если не используют `O_APPEND`.
- **У отображений острые края.** Гранулярность в страницу, никаких неименованных каналов и сокетов и `SIGBUS`, когда файл сжимается под отображением.
- **Надёжность стоит времени и доверия.** `fsync` ждёт устройство, и его гарантия хороша ровно настолько, насколько устройство правильно обращается с собственным кэшем.
- **У ссылок есть пределы.** Жёсткие ссылки остаются в пределах одной файловой системы и никогда не указывают на каталоги; символьные ссылки могут стать висячими.

## Что нужно запомнить \{#what-you-should-remember\}

- Дескриптор — индекс в таблице дескрипторов процесса; элемент указывает на описание открытого файла (смещение, режим, флаги), а оно — на inode (владелец, права, размер, блоки).
- `dup` и `fork` разделяют описание и его смещение; каждый `open` создаёт новое описание.
- Цикл с буфером из $B$ байт делает $\lceil n/B \rceil + 1$ вызовов `read` вместо $n + 1$; stdio делает это за нас, с буфером в несколько КиБ. На M1 каждый однобайтовый `read` стоит около 450 нс.
- Inode хранит всё о файле, кроме имени; каталог отображает имена в номера inode. Жёсткая ссылка — ещё одно имя того же inode; символьная ссылка — отдельный файл, содержащий путь.
- Данные файла освобождаются, когда его счётчик ссылок равен 0 и никто не держит его открытым.
- VFS даёт каждой файловой системе, неименованному каналу и устройству одни и те же системные вызовы через таблицы операций каждой файловой системы.
- `mmap` отображает страничный кэш в адресное пространство: никакого `read`, никакого копирования, один страничный отказ на страницу.
- `write` доходит до страничного кэша, а не до диска; используйте `fsync` (а в macOS `F_FULLFSYNC`), когда данные должны пережить сбой, и запись с последующим переименованием, чтобы атомарно заменить файл.

## Код \{#code\}

Файл из разделов об отправной точке и буферизации, прочитанный четырьмя способами: по одному байту за `read`, по 4096 байт за `read`, через `fgetc` с буфером stdio и через `mmap`. Программа считает свои системные вызовы и печатает прочитанное (macOS и Linux; компиляция: `clang -std=c17 -Wall -Wextra -O0`):

```c
// Read one file four ways and count the read() system calls each way makes.
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

#define N 100000                       // file size: "hello, os\n" written 10,000 times

int main(void) {
    char path[] = "/tmp/io-demo-XXXXXX";
    int fd = mkstemp(path);            // creates and opens a new file, returns its descriptor
    for (int i = 0; i < N / 10; i++)
        write(fd, "hello, os\n", 10);  // 10,000 write calls of 10 bytes
    close(fd);

    // 1. Unbuffered, one byte per call: N + 1 calls (the last one returns 0 at end of file).
    fd = open(path, O_RDONLY);
    char c, first[11] = {0};
    long calls = 0, bytes = 0;
    ssize_t r;
    while ((r = read(fd, &c, 1)) > 0) {
        if (bytes < 10) first[bytes] = c;
        bytes += r, calls++;
    }
    calls++;                           // the final call that returned 0
    printf("read, 1 byte:     %ld bytes, %ld calls, starts \"%.9s\"\n", bytes, calls, first);

    // 2. Unbuffered, a 4096-byte buffer: 25 calls that return data, then one that returns 0.
    lseek(fd, 0, SEEK_SET);
    char buf[4096];
    calls = bytes = 0;
    while ((r = read(fd, buf, sizeof buf)) > 0) bytes += r, calls++;
    calls++;
    printf("read, 4096 bytes: %ld bytes, %ld calls\n", bytes, calls);
    close(fd);

    // 3. Buffered stdio, one fgetc per byte. The library refills its buffer with read();
    //    each refill moves the kernel's file offset, which lseek(..., SEEK_CUR) reports.
    //    (The lseek calls are only here to watch; a real program would not make them.)
    FILE *fp = fopen(path, "r");
    setvbuf(fp, NULL, _IOFBF, 4096);   // a 4096-byte buffer, as stdio picks for this file by itself
    long refills = 0, offset = 0, lines = 0, fgetcs = 0;
    int ch;
    while ((ch = fgetc(fp)) != EOF) {
        fgetcs++;
        if (ch == '\n') lines++;
        long now = lseek(fileno(fp), 0, SEEK_CUR);
        if (now != offset) refills++, offset = now;
    }
    printf("stdio fgetc:      %ld fgetc calls, %ld lines, %ld refills + 1 read at end of file\n",
           fgetcs, lines, refills);
    fclose(fp);

    // 4. mmap: no read() at all; the bytes appear in the address space, page by page.
    fd = open(path, O_RDONLY);
    char *p = mmap(NULL, N, PROT_READ, MAP_PRIVATE, fd, 0);
    long hellos = 0;
    for (long i = 0; i + 5 <= N; i += 10) hellos += memcmp(p + i, "hello", 5) == 0;
    printf("mmap:             0 read calls, %ld \"hello\"s, last byte '\\n'? %s\n",
           hellos, p[N - 1] == '\n' ? "yes" : "no");
    munmap(p, N);
    close(fd);
    unlink(path);
    return 0;
}
// read, 1 byte:     100000 bytes, 100001 calls, starts "hello, os"
// read, 4096 bytes: 100000 bytes, 26 calls
// stdio fgetc:      100000 fgetc calls, 10000 lines, 25 refills + 1 read at end of file
// mmap:             0 read calls, 10000 "hello"s, last byte '\n'? yes
```

Какие дескрипторы разделяют смещение — разобранный пример с тремя таблицами:

```c
// Which descriptors share an offset: dup and fork share one open file description, a second open() does not.
#include <fcntl.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    char path[] = "/tmp/share-demo-XXXXXX";
    int a = mkstemp(path);                 // fd 3 -> open file description A, offset 0
    int b = dup(a);                        // fd 4 -> the same description A
    int c = open(path, O_RDWR);            // fd 5 -> a new description B, offset 0, same inode
    printf("fds %d %d %d\n", a, b, c);
    if (fork() == 0) {                     // the child gets copies of fds 3, 4, 5: same descriptions
        write(a, "child ", 6);             // moves the offset of A to 6
        _exit(0);
    }
    wait(NULL);
    printf("offset via fd 4: %lld, via fd 5: %lld\n",
           (long long)lseek(b, 0, SEEK_CUR), (long long)lseek(c, 0, SEEK_CUR));
    write(c, "XY", 2);                     // B is still at 0: overwrites "ch"
    write(b, "parent\n", 7);               // A is at 6: writes after "child "
    char buf[32];
    ssize_t n = pread(a, buf, sizeof buf, 0);
    printf("file: %.*s", (int)n, buf);
    unlink(path);
    return 0;
}
// fds 3 4 5
// offset via fd 4: 6, via fd 5: 0
// file: XYild parent
```

Жёсткие ссылки, символьная ссылка и файл, переживающий своё последнее имя:

```c
// Hard links, a symbolic link, and a file that outlives its last name while it is open.
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void) {
    char dir[] = "/tmp/links-demo-XXXXXX";
    mkdtemp(dir);
    chdir(dir);                                   // work inside a fresh directory
    int fd = open("a.txt", O_WRONLY | O_CREAT, 0644);
    write(fd, "data\n", 5);
    close(fd);
    link("a.txt", "b.txt");                       // a second name for the same inode
    symlink("a.txt", "c.txt");                    // a new inode whose content is the path "a.txt"
    struct stat sa, sb, sc, lc;
    stat("a.txt", &sa); stat("b.txt", &sb); stat("c.txt", &sc); lstat("c.txt", &lc);
    printf("a, b same inode: %s, links %d\n", sa.st_ino == sb.st_ino ? "yes" : "no", (int)sa.st_nlink);
    printf("c follows to a: %s; c itself is a symlink of %lld bytes\n",
           sc.st_ino == sa.st_ino ? "yes" : "no", (long long)lc.st_size);
    unlink("a.txt");                              // remove one name
    stat("b.txt", &sb);
    printf("after unlink a: b has %d link, open c: %s\n", (int)sb.st_nlink,
           open("c.txt", O_RDONLY) < 0 ? strerror(errno) : "ok");
    fd = open("b.txt", O_RDONLY);
    unlink("b.txt");                              // the last name is gone, the file is still open
    fstat(fd, &sb);
    char buf[8];
    ssize_t n = read(fd, buf, sizeof buf);
    printf("after unlink b: %d links, still reads %zd bytes: %.4s\n", (int)sb.st_nlink, n, buf);
    close(fd);                                    // now the inode and its blocks are freed
    unlink("c.txt");
    chdir("/");
    rmdir(dir);
    return 0;
}
// a, b same inode: yes, links 2
// c follows to a: yes; c itself is a symlink of 5 bytes
// after unlink a: b has 1 link, open c: No such file or directory
// after unlink b: 0 links, still reads 5 bytes: data
```

Замеры времени из раздела о буферизации. Время зависит от машины, операционной системы и от того, закэширован ли файл, поэтому вывод ниже — один запуск на Apple M1 с macOS 26.5 и `clang -O0`, когда файл находился в страничном кэше:

```c
// Time reading a 1,000,000-byte file: one read() per byte, one fgetc() per byte, one read() per 4096 bytes.
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

#define N 1000000
static double now(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec * 1e-9; }

int main(void) {
    char path[] = "/tmp/io-time-XXXXXX";
    int fd = mkstemp(path);
    static char block[N];
    for (int i = 0; i < N; i++) block[i] = "hello, os\n"[i % 10];
    write(fd, block, N);
    close(fd);
    long sum = 0;                       // a checksum, so that every byte is really used
    char c, buf[4096];
    ssize_t r;
    for (int rep = 0; rep < 3; rep++) {
        double t0 = now();
        fd = open(path, O_RDONLY);
        while (read(fd, &c, 1) == 1) sum += c;
        close(fd);
        double t1 = now();
        FILE *fp = fopen(path, "r");
        int ch;
        while ((ch = fgetc(fp)) != EOF) sum += ch;
        fclose(fp);
        double t2 = now();
        fd = open(path, O_RDONLY);
        while ((r = read(fd, buf, sizeof buf)) > 0) for (ssize_t i = 0; i < r; i++) sum += buf[i];
        close(fd);
        double t3 = now();
        printf("read 1 byte: %.1f ms  fgetc: %.2f ms  read 4096: %.2f ms\n", (t1 - t0) * 1e3, (t2 - t1) * 1e3, (t3 - t2) * 1e3);
    }
    printf("checksum %ld\n", sum);
    unlink(path);
}
// read 1 byte: 449.7 ms  fgetc: 18.86 ms  read 4096: 1.25 ms
// read 1 byte: 450.4 ms  fgetc: 18.58 ms  read 4096: 1.25 ms
// read 1 byte: 451.1 ms  fgetc: 18.73 ms  read 4096: 1.24 ms
// checksum 759600000
```

Каждый `open` в этой заметке был успешным, потому что программы открывали собственные файлы. Но inode хранит ещё и владельца, группу и набор битов прав, и ядро сверяется с ними при каждом `open`, при каждом `exec` и в каждом каталоге на пути.
