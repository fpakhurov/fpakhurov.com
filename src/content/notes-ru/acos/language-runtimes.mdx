Все программы курса начиная с [заметки о системных вызовах](/ru/notes/acos/system-calls) были написаны на C, а [предыдущая заметка](/ru/notes/acos/sockets) закончилась наблюдением, что большинство программ написаны не на нём. Программа на Python, Java или JavaScript никогда не вызывает `malloc` или `free`, создаёт объекты, размера которых не знает, и без изменений работает в любой операционной системе. Между такой программой и ядром что-то стоит: **среда выполнения** (runtime) языка — большая программа, обычно написанная на C или C++, которая выполняет обещания языка с помощью тех же системных вызовов, что и программа на C. Эта заметка спрашивает, что среде выполнения нужно от операционной системы, и подробно отвечает на этот вопрос для одной среды выполнения — CPython, стандартной реализации Python: как она исполняет код, как управляет памятью, почему её потоки не выполняют код на Python параллельно и как её библиотека добирается до ядра. Заметка заканчивается JIT-компиляцией — техникой, которая делает другие среды выполнения намного быстрее.

## Отправная точка: программа на C и ядро \{#baseline-a-c-program-and-the-kernel\}

Программа на C заранее компилируется в машинный код для одного процессора и одной операционной системы. Во время выполнения между ней и ядром почти ничего нет: библиотека C оборачивает системные вызовы, `malloc` управляет кучей, которую программа освобождает вручную, поток — это поток POSIX, а обработчик сигнала — функция на C, которую ядро вызывает напрямую. Это самое быстрое устройство, и оно оставляет всю трудную работу программисту. Память, освобождённая слишком рано или не освобождённая никогда, гонка данных между потоками, обработчик, трогающий структуру, которую прерванный код обновил лишь наполовину: каждое из этого — ошибка, от которой язык никак не защищает.

Язык высокого уровня берёт эту работу на себя. Он обещает, что объекты живут, пока используются, что одна и та же программа работает в Linux, macOS и Windows, что ошибка возбуждает исключение, а не портит память. Каждое обещание — это код в среде выполнения, и каждое стоит времени.

## Что среда выполнения требует от операционной системы \{#what-a-runtime-asks-of-the-operating-system\}

<aside class="callout"><strong>Ключевая идея.</strong> Среда выполнения — это программа между языком и ядром. Она реализует абстракции языка — объекты, автоматическую память, потоки, исключения — с помощью тех же немногих услуг, которыми пользуется любой процесс: память от `mmap` или `brk`, потоки от поддержки потоков в ядре, ввод-вывод от `read`, `write` и вызова уведомления о событиях, сигналы от `sigaction`, процессы от `fork`, `exec` и `wait`. Каждая абстракция языка заканчивается системным вызовом, а среда выполнения решает, когда, как часто и под какими блокировками он делается.</aside>

| Язык обещает | Среда выполнения реализует это с помощью | Ядро предоставляет |
| --- | --- | --- |
| объекты, которые освобождаются автоматически | распределителя для маленьких объектов и сборщика мусора | страницы памяти: `mmap`, `munmap`, `brk` |
| потоки | одного потока ядра на каждый поток языка плюс блокировки или потокобезопасной кучи | `clone` в Linux, потоки POSIX |
| файлы и сокеты как объекты | объектов-обёрток вокруг дескрипторов, буферизации | `open`, `read`, `write`, `close`, `socket` |
| асинхронный ввод-вывод | цикла событий | `epoll` в Linux, `kqueue` в macOS и BSD |
| обработчики сигналов и ошибок | низкоуровневого обработчика, который ставит флаг, исполняемый позже как код на языке | `sigaction` |
| запуск других программ | API процессов | `fork`, `exec` или `posix_spawn`, `waitpid` |
| скорость за счёт компиляции горячего кода во время выполнения | JIT-компилятора | памяти, которую можно сделать исполняемой: `mmap`, `mprotect` |

## CPython: от исходного кода до системного вызова \{#cpython-from-source-to-system-call\}

CPython компилирует каждый модуль при первом импорте в **байт-код** (bytecode): команды виртуальной стековой машины, которые хранятся в памяти и кэшируются на диске в файлах `.pyc`. Python никогда не компилируется в машинный код. Вместо этого цикл, написанный на C, читает байт-код по одной команде и выполняет её. Стандартный модуль `dis` печатает байт-код. Для одной строки в CPython 3.12:

```text
>>> import dis
>>> dis.dis('os.write(1, b"hello, world\\n")')
  0           0 RESUME                   0
  1           2 LOAD_NAME                0 (os)
              4 LOAD_ATTR                3 (NULL|self + write)
             24 LOAD_CONST               0 (1)
             26 LOAD_CONST               1 (b'hello, world\n')
             28 CALL                     2
             36 POP_TOP
             38 RETURN_CONST             2 (None)
```

`LOAD_NAME` кладёт модуль `os` на стек вычислений (evaluation stack), `LOAD_ATTR` заменяет его функцией `write` из этого модуля, две команды `LOAD_CONST` кладут аргументы, а `CALL 2` вызывает функцию с двумя аргументами и оставляет её результат на стеке. Пропуски в смещениях, от 4 до 24 и от 28 до 36, — встроенные кэши (inline caches): начиная с CPython 3.11 интерпретатор переписывает команды на месте в специализированные версии, когда увидит типы, с которыми они работают ([PEP 659](#references)), а кэши хранят то, что нужно специализированным версиям. Набор команд меняется от версии к версии; CPython 3.9 компилирует ту же строку в `LOAD_METHOD` и `CALL_METHOD`.

Строка записывает те же 13 байт, что и программа hello world из [первой заметки](/ru/notes/acos/computer-systems), и рисунок прослеживает её до ядра:

<PythonToKernel />

1. Компилятор превращает строку в байт-код один раз, при загрузке модуля.
2. Байт-код — это пять команд для самого вызова плюс две, которые отбрасывают результат и завершают модуль.
3. Цикл интерпретатора — функция на C `_PyEval_EvalFrameDefault` — выбирает каждую команду и переходит к коду на C для неё. `CALL` обнаруживает, что `os.write` — функция, реализованная на C, и вызывает её.
4. Эта функция, `os_write_impl` в `Modules/posixmodule.c`, переводит объекты Python `int` и `bytes` в `int` языка C и пару «указатель, длина», затем вызывает `_Py_write`, которая отпускает глобальную блокировку интерпретатора (о ней ниже) на время системного вызова.
5. Дальше путь тот же, что у программы на C: `write` из библиотеки C кладёт номер системного вызова и аргументы в регистры и выполняет команду ловушки (`svc` на arm64, `syscall` на x86-64, `ecall` на RISC-V).
6. Ядро копирует 13 байт в дескриптор 1 и возвращает 13. На обратном пути `_Py_write` снова захватывает блокировку, и 13 становится объектом Python `int` на стеке вычислений.

**Разобранный пример (измерение).** Цикл обратного отсчёта `while n: n -= 1` выполняет в CPython 3.12 семь команд байт-кода за итерацию. Два прогона по 20 миллионов итераций занимают 0.72 с на Apple M1 (CPython 3.12.7 для arm64, скрипт приведён в разделе «Код») — 18 нс на итерацию. Тот же цикл на C, скомпилированный Apple clang 21 с `-O0`, занимает 0.0262 с, 0.65 нс на итерацию: интерпретатор здесь примерно в 27 раз медленнее. Каждая команда байт-кода стоит косвенного перехода, обращений к стеку и проверок типов объектов; `n` — объект в куче, и `n - 1` создаёт новый. С `-O2` компилятор C вообще удаляет цикл, как покажет [следующая заметка](/ru/notes/acos/compilers-and-llvm), и таймер показывает ноль.

## Память: подсчёт ссылок и сборщик циклов \{#memory-reference-counting-and-a-cycle-collector\}

Каждый объект CPython начинается с заголовка, в котором хранятся **счётчик ссылок** (reference count) и указатель на тип объекта. Сохранение ссылки на объект увеличивает его счётчик (`Py_INCREF` в коде на C); удаление ссылки уменьшает его (`Py_DECREF`). Когда счётчик доходит до нуля, объект сразу освобождается, а его собственные ссылки по очереди удаляются. Память возвращается, как только перестаёт использоваться, и то же происходит с другими ресурсами: файловый объект закрывает свой дескриптор, когда исчезает последняя ссылка на него.

**Разобранный пример.** `sys.getrefcount(x)` возвращает счётчик, включающий одну лишнюю ссылку, которую держит аргумент самого вызова. После `x = object()` он возвращает 2. После `y = x` и `items = [x]` он возвращает 4: имена `x` и `y`, ячейка списка и аргумент. После `del y, items` он снова возвращает 2. Малые целые числа, `None`, `True` и `False` начиная с CPython 3.12 **бессмертны** (immortal, [PEP 683](#references)): их счётчик закреплён на большом значении и никогда не меняется, так что потоки и процессы, которые их разделяют, никогда в них не пишут.

У подсчёта ссылок одно слепое пятно: **цикл** (cycle). Объект, который ссылается сам на себя, или два объекта, ссылающиеся друг на друга, держат счётчики друг друга выше нуля и после того, как программа удалила все ссылки на них. CPython добавляет **сборщик циклов** (cycle collector), который время от времени проходит по объектам, способным хранить ссылки (контейнерам: спискам, словарям, экземплярам классов). Он находит объекты, на которые ссылаются только изнутри рассматриваемого множества ([документация Python, `gc`](#references)):

1. Скопировать счётчик ссылок каждого объекта во вспомогательное поле.
2. Для каждой ссылки от одного рассматриваемого объекта к другому уменьшить вспомогательный счётчик цели. Остаток считает ссылки извне.
3. Объекты с положительным остатком достижимы извне, как и всё, на что они ссылаются. Остальное — мусор, и сборщик его освобождает.

**Разобранный пример.** Объекты `a` и `b` ссылаются друг на друга, а имя `x` ссылается на `a`. Счётчики равны 2 для `a` (от `b` и `x`) и 1 для `b` (от `a`). Шаг 2 вычитает две внутренние ссылки: у `a` остаётся 1, у `b` — 0, но `b` достижим из `a`, так что оба живы. После `del x` шаг 2 оставляет у обоих 0, и оба освобождаются.

Чтобы снизить затраты, сборщик работает по поколениям (generational): новые контейнеры попадают в поколение 0, которое собирается, когда разность числа выделений и освобождений со времени последней сборки превышает порог; выжившие переходят в более старое поколение, которое собирается реже. `gc.get_threshold()` возвращает `(700, 10, 10)` в CPython 3.12: поколение 0 — после 700 новых контейнеров сверх освобождённых, поколение 1 — после каждых 10 сборок поколения 0, поколение 2 — после каждых 10 сборок поколения 1, с дополнительными условиями, которые не дают слишком часто проверять самое старое поколение. Подробности меняются от версии к версии.

Под объектами лежит распределитель памяти, построенный специально для них. Большинство объектов Python маленькие: `sys.getsizeof(1)` на 64-битной машине равен 28 байтам (8-байтный счётчик, 8-байтный указатель на тип, 8 байт размера и знака и одна 4-байтная цифра). CPython обслуживает запросы размером до 512 байт собственным распределителем **pymalloc**, который нарезает пулы блоков одинакового размера из **арен** (arenas) по 1 МиБ, полученных у ядра через `mmap` на 64-битных системах, а более крупные запросы передаёт `malloc` из библиотеки C ([документация Python, управление памятью](#references)). Это классы размеров и списки свободных блоков из [заметки о выделении памяти](/ru/notes/acos/memory-allocation), специализированные под одну нагрузку.

Другие среды выполнения выбирают иначе. JVM, Go и движки JavaScript используют **трассирующие** сборщики (tracing collectors): вместо подсчёта ссылок они периодически находят всё, что достижимо из корней (стеков и глобальных переменных), и забирают остальное. Они ничего не платят за каждое присваивание указателя и естественно справляются с циклами, но память возвращается позже и порциями, а сборка может приостановить программу ([Jones, Hosking and Moss](#references), главы 2 и 5).

## Потоки и глобальная блокировка интерпретатора \{#threads-and-the-global-interpreter-lock\}

Поток Python — настоящий поток ядра, созданный через `pthread_create`. И всё же два потока Python никогда не выполняют байт-код в один и тот же момент. В CPython есть одна **глобальная блокировка интерпретатора** (global interpreter lock, GIL), и поток должен держать её, чтобы выполнять байт-код или трогать любой объект Python.

**Зачем она нужна.** Каждая команда байт-кода меняет счётчики ссылок, а собственные структуры интерпретатора (списки свободных блоков распределителя, кэши типов, словари модулей) общие для всех потоков. Два потока, которые без синхронизации увеличивают один и тот же счётчик, теряют обновления — это гонка из [заметки о синхронизации](/ru/notes/acos/synchronization), — а объект с неверным счётчиком освобождается, пока ещё используется. Сделать атомарным каждое обновление счётчика или поставить блокировку вокруг каждой общей структуры — значит замедлить каждую программу, включая подавляющее большинство тех, что используют один поток. Одна блокировка вокруг всего интерпретатора — самый дешёвый корректный ответ для одного потока, и она упрощает написание расширений на C: их код выполняется с захваченной GIL и не нуждается в собственных блокировках.

**Как она делится.** Поток отпускает GIL на время любой операции, которая может заблокироваться: системного вызова, такого как `read`, `recv` или `sleep`, как в шаге 4 рисунка, и долгих вычислений в библиотеках на C, таких как сжатие или хеширование больших буферов. Поток, выполняющий чистый байт-код, держит GIL, пока её не попросит другой поток; ожидающий поток ждёт один **интервал переключения** (switch interval), по умолчанию 5 мс (`sys.getswitchinterval()`), а затем ставит флаг, который заставляет работающий поток отпустить блокировку на следующей границе команд.

<GilTimeline />

**Разобранный пример (измерения).** Цикл обратного отсчёта на 20 миллионов итераций, выполненный дважды, на Apple M1 с 4 производительными ядрами, CPython 3.12.7:

| Два обратных отсчёта | Время | Относительно последовательного выполнения |
| --- | --- | --- |
| один за другим, в одном потоке | 0.72 с | 1 |
| одновременно, в двух потоках | 0.71 с | 1.00 |
| одновременно, в двух процессах | 0.37 с | 0.52 |

Два потока работают столько же, сколько один поток, выполняющий оба отсчёта: GIL позволяет работать только одному из них, и [ускорение от параллельного выполнения](/ru/notes/acos/thread-level-parallelism) теряется. У двух процессов свои интерпретаторы и свои GIL, и они работают параллельно на двух ядрах; отношение равно 0.52, а не 0.50, из-за затрат на передачу работы рабочим процессам и сбор результатов. Для работы, ограниченной вводом-выводом (I/O-bound), картина другая: поток, ожидающий в `recv`, не держит GIL, как в нижней половине рисунка, и ожидания потоков хорошо перекрываются.

GIL постепенно убирают. [PEP 703](#references) добавил в версии 3.13 необязательную **сборку без GIL** (free-threaded build) CPython, в которой счётчики ссылок обновляются смещённым подсчётом ссылок (biased reference counting: дёшево для потока-владельца объекта, атомарно для остальных), объекты несут собственные мелкозернистые блокировки, а в бессмертные объекты никогда не пишут; [PEP 779](#references) сделал эту сборку официально поддерживаемой в 3.14. Сборка по умолчанию всё ещё содержит GIL, и расширения на C нужно адаптировать, прежде чем они станут безопасными без неё.

## Обращение к системе: os, subprocess и сигналы \{#calling-the-system-os-subprocess-and-signals\}

**`os`.** Большинство функций модуля `os` — тонкие обёртки вокруг одного системного вызова каждая: `os.getpid`, `os.fork`, `os.pipe`, `os.write`, реализованные в `Modules/posixmodule.c`. Ошибка возбуждает `OSError` с `errno` вызова. Системный вызов, прерванный сигналом, автоматически повторяется после того, как отработал обработчик сигнала на Python ([PEP 475](#references)), так что код на Python не видит `EINTR`.

**`subprocess`.** `subprocess.run(['echo', 'hello, world'], capture_output=True)` создаёт канал для вывода потомка, запускает потомка, читает канал и ждёт код завершения: это `pipe`, `fork`, `exec` и `waitpid` из [заметки о процессах](/ru/notes/acos/processes-and-threads). `fork` и `exec` выполняются во вспомогательном модуле на C, `_posixsubprocess`, который там, где это безопасно, использует `vfork` или `posix_spawn` вместо `fork`, потому что копировать таблицы страниц большого интерпретатора лишь затем, чтобы `exec` сразу их заменил, — напрасная работа. Модуль `multiprocessing`, использованный в измерении выше, запускает рабочие процессы одним из трёх способов: `fork`, `spawn` (новый интерпретатор, который заново импортирует главный модуль) или `forkserver`. `spawn` используется по умолчанию в macOS и Windows, а `forkserver` — в Linux начиная с Python 3.14; в обоих случаях главный модуль заново импортируется в каждом рабочем процессе, поэтому скрипт защищает свою работу условием `if __name__ == '__main__'`.

**Сигналы.** Обработчик сигнала на Python не вызывается ядром напрямую. CPython устанавливает через `sigaction` маленький обработчик на C, который лишь запоминает, какой сигнал пришёл; цикл интерпретатора проверяет эту запись между командами байт-кода и запускает обработчик на Python в главном потоке ([документация Python, `signal`](#references)). Обработчик на C может вызывать только асинхронно-безопасные (async-signal-safe) функции, а код на Python, который выделяет память и захватывает GIL, таковым никак не является, поэтому обработчик откладывается до момента, когда его запуск безопасен. **Разобранный пример.** С таймером, который посылает `SIGALRM` через 0.1 с, вызов `time.sleep(0.3)` прерывается в ядре; обработчик на Python выполняется в главном потоке, сон продолжается на оставшееся время, и вызов возвращается в общей сложности не раньше чем через 0.3 с. Цена откладывания — задержка: сигнал, пришедший, пока минуту выполняется один вызов на C, обрабатывается после этой минуты.

**Асинхронный ввод-вывод.** Цикл событий `asyncio` — это событийно-управляемый сервер из [заметки о сокетах](/ru/notes/acos/sockets#serving-many-clients) в виде библиотеки: его модуль `selectors` использует `epoll` в Linux и `kqueue` в macOS, а сопрограммы заменяют состояние каждого соединения.

## JIT-компиляция, кратко \{#just-in-time-compilation-briefly\}

Накладные расходы интерпретатора возникают из-за того, что одна и та же работа повторяется при каждом выполнении команды: её декодирование, проверка типов операндов, упаковка каждого результата в новый объект. **JIT-компилятор** (just-in-time compiler) наблюдает за работающей программой, выбирает часто выполняемый код и компилирует его в машинный код, специализированный под то, что он увидел.

- **HotSpot JVM** начинает с интерпретации байт-кода Java, подсчитывая, как часто выполняется каждый метод. Горячие методы компилируются быстрым компилятором C1 в код, который также собирает профили, а самые горячие перекомпилируются оптимизирующим компилятором C2 с использованием этих профилей; это **многоуровневая компиляция** (tiered compilation), появившаяся в Java 7 и включённая по умолчанию в серверной VM ([Oracle](#references)). Если предположение, на котором основан скомпилированный код, перестаёт выполняться — например, загружается класс, переопределяющий метод, который компилятор встроил, — код **деоптимизируется** (deoptimization), и выполнение продолжается в интерпретаторе.
- **PyPy**, альтернативная реализация Python, использует **трассирующий JIT** (tracing JIT): он записывает операции одной итерации горячего цикла со сторожевыми проверками (guards) увиденных типов и компилирует эту трассу ([Bolz et al., 2009](#references)). Для цикла обратного отсчёта трасса, которая видела только малые целые, сводится к уменьшению, проверке и переходу — близко к тому, что выдаёт компилятор C.
- В CPython 3.13 есть экспериментальный JIT, выключенный по умолчанию, который сшивает заранее скомпилированные шаблоны машинного кода для специализированных команд; эта техника называется **copy-and-patch** («копирование и заплатка», [Xu and Kjolstad, 2021](#references); [PEP 744](#references)).

JIT нужна от операционной системы ещё одна услуга: память, в которую можно сначала записать машинный код, а затем его выполнить. Системы, требующие **W^X** (страница либо доступна для записи, либо исполняема, но не то и другое сразу — защита от внедрённого кода), заставляют JIT переключать права через `mprotect` между записью и выполнением — это применение прав доступа к страницам из [заметки о виртуальной памяти](/ru/notes/acos/virtual-memory); macOS на Apple silicon даёт JIT особые отображения `MAP_JIT`, право записи в которые переключается для каждого потока отдельно.

## Что изменилось \{#what-changed\}

| | Программа на C (отправная точка) | Программа на CPython |
| --- | --- | --- |
| Выполнение | машинный код, скомпилированный заранее | байт-код, интерпретируемый циклом на C; примерно в 27 раз медленнее на цикле обратного отсчёта |
| Память | `malloc` и `free` вручную | счётчики ссылок, сборщик циклов, pymalloc на аренах из `mmap` |
| Потоки | параллельно на всех ядрах; гонки — проблема программиста | потоки ядра, но под GIL байт-код выполняет только один за раз |
| Системные вызовы | напрямую, через библиотеку C | через обёртки на C в `os`, которые отпускают GIL и повторяют вызов при `EINTR` |
| Сигналы | обработчик выполняется сразу, но может делать только асинхронно-безопасные вызовы | обработчик на C ставит флаг; обработчик на Python выполняется позже в главном потоке |
| Ускорение | лучший компилятор, заранее | JIT во время выполнения (PyPy, JVM, экспериментальный JIT CPython 3.13) |

## Ограничения \{#limitations\}

- Заметка следует CPython, в основном версии 3.12. Байт-код, специализация, пороги сборщика и способ запуска `multiprocessing` меняются от версии к версии; сборка без GIL полностью меняет картину с потоками.
- Одно измерение на одной машине — иллюстрация, а не бенчмарк: отношение времени интерпретатора ко времени C зависит от кода, и интерпретатор гораздо ближе к C, когда работа происходит внутри библиотек на C, таких как NumPy.
- Другие среды выполнения идут на другие компромиссы: трассирующие сборщики мусора, зелёные потоки, которые планирует сама среда выполнения (горутины Go, процессы Erlang), заблаговременная компиляция управляемых языков. Вопросы те же: память, потоки, ввод-вывод, сигналы и когда компилировать.
- Алгоритмы сборки мусора (пометка и очистка, копирующие, поколенческие и параллельные сборщики) — отдельная тема, и здесь они только названы.

## Что нужно запомнить \{#what-you-should-remember\}

- Среда выполнения реализует обещания языка обычными системными вызовами: память от `mmap`, потоки от ядра, ввод-вывод через дескрипторы и цикл событий, сигналы через `sigaction`, процессы через `fork`, `exec` или `posix_spawn`.
- CPython компилирует Python в байт-код стековой машины и выполняет его в цикле на C; `dis` показывает байт-код. На простых циклах интерпретация обходится на порядок или больше дороже скомпилированного C.
- Память: счётчик ссылок в каждом объекте, освобождение при нуле; сборщик циклов по поколениям для циклов; pymalloc для объектов до 512 байт.
- GIL позволяет выполнять байт-код только одному потоку за раз. Она существует потому, что счётчики ссылок и состояние интерпретатора общие и не синхронизированы; она отпускается на время блокирующих системных вызовов. Потоки помогают коду на Python, ограниченному вводом-выводом, процессы — коду, ограниченному процессором.
- Обработчики сигналов на Python выполняются позже, в главном потоке, между командами байт-кода; прерванные системные вызовы повторяются.
- JIT компилирует горячий код во время выполнения с учётом увиденных типов, и ему нужна от ядра память, которую можно сначала записать, а затем выполнить.

## Код \{#code\}

Скрипт печатает то, что утверждает каждый раздел заметки. Ему нужна только стандартная библиотека; запуск — `python3 -I runtime.py`. Времена зависят от машины и приведены как один прогон с описанием условий; все остальные выходные данные одинаковы в любом 64-битном CPython начиная с 3.9.

```python
import gc, os, signal, subprocess, sys, threading, time, weakref
from multiprocessing import Pool

class Node:
    pass

def count(n):                        # чистая работа байт-кода: ни ввода-вывода, ни вызовов C, отпускающих GIL
    while n:
        n -= 1

def timed(run, repeats=3):           # лучший из трёх, чтобы пропустить медленный первый прогон
    best = float('inf')
    for _ in range(repeats):
        t = time.perf_counter()
        run()
        best = min(best, time.perf_counter() - t)
    return best

def two_threads(n):
    ts = [threading.Thread(target=count, args=(n,)) for _ in range(2)]
    for t in ts: t.start()
    for t in ts: t.join()

if __name__ == '__main__':          # нужно: multiprocessing заново импортирует этот файл в рабочих процессах
    # 1. os.write — тонкая обёртка вокруг системного вызова write
    sys.stdout.flush()               # print() буферизует внутри среды выполнения; os.write идёт прямо в ядро
    n = os.write(1, b'hello, world\n')                          # hello, world
    print(n)                         # 13

    # 2. Счётчики ссылок: getrefcount видит одну лишнюю ссылку, свой собственный аргумент
    x = object()
    print(sys.getrefcount(x))        # 2: имя x и аргумент
    y = x
    items = [x]
    print(sys.getrefcount(x))        # 4: x, y, ячейка списка, аргумент
    del y, items
    print(sys.getrefcount(x))        # 2

    # 3. Цикл держит свой счётчик выше нуля; освободить его может только сборщик циклов
    gc.collect()
    a = Node()
    a.me = a                         # a ссылается сам на себя
    alive = weakref.ref(a)
    del a                            # на него больше не ссылается ни одно имя
    print(alive() is not None)       # True: ссылка на себя держит счётчик на 1
    gc.collect()
    print(alive() is None)           # True: сборщик нашёл недостижимый цикл

    # 4. Обработчик сигнала на Python выполняется позже, в главном потоке; прерванный сон продолжается (PEP 475)
    caught = []
    signal.signal(signal.SIGALRM, lambda signum, frame: caught.append(threading.current_thread() is threading.main_thread()))
    signal.setitimer(signal.ITIMER_REAL, 0.1)                   # SIGALRM через 0.1 с
    t = time.perf_counter(); time.sleep(0.3); slept = time.perf_counter() - t
    print(caught, slept >= 0.3)      # [True] True

    # 5. subprocess: новый процесс через fork и exec (или posix_spawn), канал для его вывода, ожидание завершения
    r = subprocess.run(['echo', 'hello, world'], capture_output=True)
    print(r.returncode, r.stdout)    # 0 b'hello, world\n'

    # 6. Работа, ограниченная процессором, дважды: подряд, в двух потоках, в двух процессах
    N = 20_000_000
    seq = timed(lambda: (count(N), count(N)))
    thr = timed(lambda: two_threads(N))
    with Pool(2) as pool:
        proc = timed(lambda: pool.map(count, [N, N]))
    print(f'in a row {seq:.2f} s, 2 threads {thr:.2f} s, 2 processes {proc:.2f} s')
    print(f'threads / in a row {thr / seq:.2f}, processes / in a row {proc / seq:.2f}')
    # один прогон, Apple M1 (4 производительных ядра), macOS, CPython 3.12.7 для arm64:
    # in a row 0.72 s, 2 threads 0.71 s, 2 processes 0.37 s
    # threads / in a row 1.00, processes / in a row 0.52
```

Тот же обратный отсчёт на C для сравнения в тексте; компиляция — `clang -std=c17 -Wall -Wextra -O0 count.c -o count && ./count`, затем ещё раз с `-O2`:

```c
// The countdown loop of the Python script in C: two runs of 20 million iterations.
#define _DEFAULT_SOURCE                   // glibc: declare clock_gettime under -std=c17
#include <stdio.h>
#include <time.h>

static long count(long n) {
    while (n) n -= 1;
    return n;
}

int main(void) {
    struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    long r = count(20000000) + count(20000000);
    clock_gettime(CLOCK_MONOTONIC, &b);
    printf("result %ld, %.4f s\n", r, (double)(b.tv_sec - a.tv_sec) + (double)(b.tv_nsec - a.tv_nsec) / 1e9);
    return 0;
}
// one run each, Apple M1, macOS, Apple clang 21:
// -O0: result 0, 0.0262 s
// -O2: result 0, 0.0000 s   (the compiler removed the loop)
```

## Дальше \{#next\}

CPython превращает исходный код в байт-код и интерпретирует его; JIT превращает горячий байт-код в машинный код, пока программа работает. Программы на C в этом курсе шли третьим путём: компилятор превращал их в машинный код до запуска, а с `-O2` он оказывался достаточно умным, чтобы удалить цикл, результат которого мог вычислить сам. [Последняя заметка](/ru/notes/acos/compilers-and-llvm) открывает этот компилятор: его фронтенд, промежуточное представление, оптимизатор и бэкенд, на примере LLVM.
