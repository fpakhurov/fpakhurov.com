[Предыдущая заметка](/ru/notes/acos/instruction-level-parallelism) довела один поток команд до предела: ядро, которое переименовывает регистры, исполняет команды вне порядка и спекулятивно проходит переходы, выполняло цикл из примера со скоростью две команды за такт — предел его ширины. Дальнейшее продвижение стоит площади и энергии, которые растут быстрее найденного параллелизма, а [первая заметка](/ru/notes/acos/computer-systems#how-processors-got-fast-and-why-that-changed) показала, что именно мощность около 2005 года перестала расти. С тех пор дополнительные транзисторы каждого поколения уходят на новые ядра на том же кристалле. Больше ядер ускоряют одну программу, только если она разделена на несколько потоков команд — **потоков** (threads), — которые выполняются одновременно и разделяют общую память. Эта заметка выясняет, сколько это даёт и что должна делать аппаратура, чтобы потоки, разделяющие память через частные кэши, всё равно видели одну согласованную память.

**Обозначения.** $n$ — число ядер. $T_1$ — время работы программы на одном ядре, $T_n$ — на $n$ ядрах; **ускорение** (speed-up) — $S(n) = T_1/T_n$, а **эффективность** (efficiency) — $S(n)/n$. В законе Амдала $p$ — доля $T_1$, которую можно распределить между ядрами; в законе Густафсона $s$ — последовательная доля $T_n$. **Поток** — поток команд со своими счётчиком команд, регистрами и стеком, который разделяет память с другими потоками той же программы; как их создаёт операционная система, показывает [заметка о процессах и потоках](/ru/notes/acos/processes-and-threads). Здесь они создаются вызовом POSIX `pthread_create(&id, NULL, f, arg)`, который запускает поток, выполняющий `f(arg)`, и ожидаются вызовом `pthread_join(id, NULL)`, который ждёт его завершения.

## Почему больше ядер, а не более быстрое ядро \{#why-more-cores-instead-of-a-faster-core\}

Динамическая мощность пропорциональна $C V^2 f$, а в том диапазоне, где ядро может работать, нужное ему напряжение растёт примерно пропорционально тактовой частоте. Поэтому мощность растёт примерно как $f^3$, и при фиксированном бюджете мощности выбор очевиден.

**Разобранный пример.** Одно ядро работает на частоте $f$ при напряжении $V$ и потребляет мощность $P$. Заменим его двумя ядрами той же конструкции, каждое на $0.8f$ и $0.8V$. Каждое потребляет $0.8 \cdot 0.8^2 \cdot P = 0.512\,P$, оба вместе — $1.02\,P$: тот же бюджет мощности. Если работа делится между ними поровну, они выполняют в $2 \cdot 0.8 = 1.6$ раза больше работы в секунду. Если не делится совсем, программа работает со скоростью $0.8$ от прежней. Многоядерность выгодна ровно для тех программ, которые можно разделить.

Данные о тенденциях, собранные [Rupp (2022)](#references), показывают этот перелом: самая высокая тактовая частота среди процессоров набора данных достигла 3.65 ГГц в 2004 году и с тех пор остаётся ниже 5 ГГц, а наибольшее число ядер выросло с 1 до 2004 года до более чем 200 к 2016 году. Каждое ядро выполняет свой поток команд и имеет свои частные кэши: такой кристалл — это **мультипроцессор с общей памятью** (shared-memory multiprocessor), одно физическое адресное пространство, из которого каждое ядро может загружать данные и в которое может их сохранять. У Apple M1, на котором сделаны измерения этой заметки, 8 ядер: 4 производительных и 4 энергоэффективных.

Параллелизм между потоками бывает двух видов. **Параллелизм на уровне задач** (task-level parallelism) одновременно выполняет независимые работы (компилятор собирает разные файлы, сервер отвечает разным клиентам), и от программиста он не требует ничего, кроме их запуска. **Параллельная программа** (parallel program) разбивает одну работу на взаимодействующие потоки, и её потоки должны делить работу, обмениваться результатами и ждать друг друга, а это стоит времени, которого один поток не тратит.

## Отправная точка: одно ядро, несколько потоков \{#baseline-one-core-several-threads\}

Простейший способ выполнять несколько потоков — выполнять их на одном ядре по очереди. Операционная система каждые несколько миллисекунд переключает ядро между потоками, сохраняя регистры одного потока и загружая регистры другого (**переключение контекста**, context switch, которое запускается прерыванием таймера, как в [заметке об исключениях](/ru/notes/acos/exceptions-and-interrupts)). Пользователю кажется, что потоки выполняются одновременно, и пока один ждёт диск или сеть, работает другой. Но в каждый момент исполняется только один поток команд: два потока, занятых вычислениями, вместе работают столько же, сколько один за другим, плюс цена переключений. Эта отправная точка даёт конкурентность (concurrency), а не скорость. Настоящая скорость требует нескольких ядер, и с ними возникают два вопроса: какая часть программы может их использовать и как они разделяют память.

## Насколько быстрее: закон Амдала \{#how-much-faster-amdahls-law\}

Разделим время на одном ядре $T_1$ на часть $pT_1$, которая поровну делится между ядрами, и последовательную часть $(1 - p)T_1$, которая не делится: чтение входных данных, объединение результатов, принципиально последовательные части алгоритма. На $n$ ядрах последовательная часть занимает столько же, сколько раньше, а параллельная — в $n$ раз меньше:

$$
T_n = (1 - p)\,T_1 + \frac{p\,T_1}{n} .
$$

Деление $T_1$ на $T_n$ сокращает $T_1$ и даёт **закон Амдала** (Amdahl's law) ([Amdahl, 1967](#references); Амдал изложил рассуждение словами, а формула — его обычная запись):

$$
\boxed{\;S(n) = \frac{1}{(1 - p) + p/n} \;\le\; \frac{1}{1 - p}\;}
$$

Оценка верна, потому что $p/n > 0$, и $S(n)$ приближается к ней при $n \to \infty$. Сколько бы ни было ядер, одна только последовательная часть занимает $(1 - p)T_1$, поэтому ускорение никогда не превысит $1/(1 - p)$.

**Разобранный пример.** Программа с $p = 0.95$ работает на 8 ядрах в $1/(0.05 + 0.95/8) = 5.93$ раза быстрее, с эффективностью 74%. На 1024 ядрах она работает в 19.64 раза быстрее, и никакое число ядер не поднимет ускорение выше 20: 5% времени, последовательные на одном ядре, на 1024 ядрах составляют 98% времени. Если читать закон в обратную сторону, он говорит, насколько параллельной должна быть программа. Решив $S = 1/((1 - p) + p/n)$ относительно $p$, получаем $p = (1 - 1/S)/(1 - 1/n)$: ускорение 6 на 8 ядрах требует $p = 0.952$, а ускорение 50 на 64 ядрах — $p = 0.9956$, то есть последовательной части меньше половины процента.

Закон оптимистичен в двух отношениях. Он предполагает, что параллельная часть делится на точно равные куски; при **дисбалансе нагрузки** (load imbalance) время задаёт самое медленное ядро, и параллельная часть занимает больше, чем $pT_1/n$. И он не учитывает цену координации: создания потоков, ожидания друг друга и перемещения общих данных между кэшами, которая растёт с $n$.

## Закон Густафсона: задача побольше на большем числе ядер \{#gustafsons-law-a-larger-problem-on-more-cores\}

Закон Амдала держит задачу фиксированной, пока добавляются ядра; это называется **сильным масштабированием** (strong scaling). Часто же больше ядер нужно для того, чтобы за то же время решить задачу побольше: более мелкая сетка моделирования, более крупная модель. [Gustafson (1988)](#references) измеряет последовательную долю $s$ на параллельной машине: на $n$ ядрах прогон занимает время 1, из которого $s$ — последовательная часть, а $1 - s$ распределено между ядрами. Одно ядро выполнило бы ту же работу за $s + (1 - s)\,n$, потому что доли параллельной части, приходящиеся на каждое ядро, пришлось бы выполнять одну за другой. Поэтому **масштабированное ускорение** (scaled speed-up) равно

$$
\boxed{\;S_{\text{scaled}}(n) = s + (1 - s)\,n = n - s\,(n - 1)\;}
$$

и растёт линейно по $n$. При $s = 0.05$ 8 ядер дают 7.65, а 1024 ядра — 972.85. Это **слабое масштабирование** (weak scaling): работа на ядро остаётся фиксированной, а задача растёт вместе с машиной. Два закона не противоречат друг другу: они отвечают на разные вопросы. У Амдала $p$ — доля времени на одном ядре для фиксированной задачи, у Густафсона $s$ — доля параллельного времени для растущей задачи, а в растущей задаче последовательная часть обычно составляет всё меньшую долю работы.

## Общая память и проблема когерентности \{#shared-memory-and-the-coherence-problem\}

На многоядерном кристалле у каждого ядра есть частные кэши (кэш данных L1, а часто и L2), а общими у ядер являются кэш последнего уровня и основная память. Именно частные кэши делают каждое ядро быстрым, но из-за них два ядра могут держать копии одного и того же блока памяти, а запись одного ядра меняет только его собственную копию.

**Разобранный пример.** Два ядра, A и B, с кэшами с обратной записью (write-back), как в [заметке о кэшах](/ru/notes/acos/caches), и переменная `X`, равная 0 в памяти.

| Шаг | Событие | Кэш A | Кэш B | Память |
| --- | --- | --- | --- | --- |
| 1 | A читает `X` | 0 | | 0 |
| 2 | B читает `X` | 0 | 0 | 0 |
| 3 | A записывает 1 в `X` | 1 | 0 | 0 |
| 4 | B читает `X` | 1 | 0 | 0 |

На шаге 4 B читает 0 — значение, перезаписанное шагом раньше, — и продолжал бы читать его, пока строка остаётся в его кэше. Система памяти **когерентна** (coherent), когда такое невозможно ([Patterson and Hennessy, 2020](#references), §5.10):

1. чтение ядром ячейки, в которую оно записывало, без записи другого ядра в промежутке возвращает записанное им значение;
2. чтение ячейки, в которую записывало другое ядро, возвращает записанное значение, если чтение происходит достаточно долго после записи и других записей между ними нет;
3. записи в одну ячейку **сериализуются** (serialized): все ядра видят их в одном и том же порядке.

Когерентность обеспечивают контроллеры кэшей, в единицах строк кэша, с помощью протоколов одного из двух видов. В протоколе с **отслеживанием** (snooping) каждый контроллер кэша следит за запросами, которые остальные рассылают по общей шине или сети соединений, и реагирует на те, что касаются строк, которые он держит. В протоколе на основе **каталога** (directory) каталог рядом с памятью записывает, какие кэши держат каждую строку, и посылает сообщения только им; такой протокол масштабируется на большее число ядер, потому что не использует широковещательную рассылку. Оба отслеживают состояние каждой строки в кэше, и самый распространённый набор состояний — MESI.

## Протокол MESI \{#the-mesi-protocol\}

<aside class="callout"><strong>Ключевая идея.</strong> На каждую строку кэша допускается много читателей или один писатель. Ядро, которое хочет записать строку, сначала делает недействительными все остальные копии, поэтому строка, в которую идёт запись, существует ровно в одном кэше; ядро, которое хочет прочитать строку, изменённую в другом кэше, получает новые данные из этого кэша. Каждая строка несёт одно из четырёх состояний, которое записывает, какая из двух ситуаций имеет место.</aside>

Протокол [Papamarcos and Patel (1984)](#references), который теперь называют **MESI** по первым буквам названий состояний, присваивает каждой строке в кэше одно из четырёх состояний:

| Состояние | Смысл | Другие кэши | Память |
| --- | --- | --- | --- |
| **M**odified (изменённая) | у этого кэша единственная копия, и в неё была запись | копий нет | устарела |
| **E**xclusive (эксклюзивная) | у этого кэша единственная копия, записи не было | копий нет | актуальна |
| **S**hared (разделяемая) | у этого кэша копия без записи | могут быть копии | актуальна |
| **I**nvalid (недействительная) | действительных данных нет | | |

Кэш меняет состояние строки, когда его собственное ядро читает или записывает строку и когда он отслеживает запрос другого кэша:

| Состояние | Своё чтение | Своя запись | Отслеженное чтение | Отслеженная запись или инвалидация |
| --- | --- | --- | --- | --- |
| M | попадание | попадание | отдать данные, записать их в память, перейти в S | отдать данные, перейти в I |
| E | попадание | попадание, перейти в M (без обмена по шине) | перейти в S | перейти в I |
| S | попадание | разослать инвалидацию, перейти в M | остаться в S | перейти в I |
| I | промах: прочитать строку; перейти в E, если её нет в других кэшах, иначе в S | промах: прочитать строку для владения (read for ownership), сделав недействительными другие копии; перейти в M | | |

<MesiSteps />

Пример с проблемой когерентности, выполненный под MESI, с номерами как на рисунке:

1. **A читает `X`.** A промахивается и выставляет на шину запрос чтения. Ни в одном другом кэше строки нет, поэтому её отдаёт память, и A держит её в состоянии E со значением 0.
2. **B читает `X`.** B промахивается и запрашивает строку. A отслеживает запрос и видит, что держит эту строку; обе копии переходят в S, а копию для B отдаёт память, в которой данные актуальны.
3. **A записывает 1 в `X`.** A держит строку в состоянии S, поэтому могут существовать другие копии. Перед записью A рассылает инвалидацию (invalidation); копия B переходит в I, а A записывает 1 в свою копию, которая переходит в M. Память всё ещё хранит 0, и никто не может прочитать значение оттуда: единственная действительная копия — у A.
4. **B читает `X`.** Копия B недействительна, поэтому B промахивается и запрашивает строку. A отслеживает запрос, отдаёт значение 1 и записывает его в память, и обе копии переходят в S. B читает 1: чтение, которое без когерентности вернуло бы устаревший 0, теперь возвращает последнее значение.
5. **B записывает 2 в `X`.** B держит строку в состоянии S, поэтому рассылает инвалидацию; копия A переходит в I, а копия B — в M со значением 2.

Состояние E окупается в частом сценарии, когда частную переменную сначала читают, а потом записывают: строка приходит в E, и запись переводит её в M молча, не спрашивая другие кэши. Без E (в более старом протоколе MSI) строка пришла бы в S, и записи понадобилась бы широковещательная инвалидация, которую никому не нужно было слышать.

У когерентности есть цена, которую одно ядро никогда не платит. Промах на шаге 4 — это **промах когерентности** (coherence miss): строка была в кэше B, но запись A сделала её недействительной; на шагах 3 и 5 перед записью пришлось рассылать инвалидацию. Строка, в которую два ядра пишут по очереди, при каждой записи переезжает между их кэшами, и каждый такой переезд стоит примерно столько же, сколько промах в общий кэш.

## Ложное разделение \{#false-sharing\}

Когерентность отслеживается по строкам кэша, а не по переменным. Два потока, которые пишут *разные* переменные, случайно лежащие в одной строке, по очереди делают недействительной копию друг друга — в точности так, как если бы они разделяли одну переменную, хотя никакие данные на самом деле не разделяются. Это **ложное разделение** (false sharing).

**Разобранный пример (измерение).** Два потока каждый по 100 миллионов раз прибавляют 1 к своему счётчику атомарным сложением (обычный способ поддерживать правильность общих счётчиков статистики; атомарные операции объясняет [заметка о синхронизации](/ru/notes/acos/synchronization)). В первом прогоне два счётчика отстоят друг от друга на 8 байтов и лежат в одной строке; во втором каждый начинает собственную 128-байтовую строку — такой размер строки macOS сообщает для M1. На M1 (macOS 26.5, Apple clang 21, `-O0`) один прогон занял 2.52 с со счётчиками в одной строке и 0.22 с в разных строках — в 11 раз дольше при той же работе, хотя потоки никогда не трогают счётчик друг друга. Время меняется от прогона к прогону и между машинами; три прогона дали 2.46–2.52 с и 0.21–0.22 с. С обычными счётчиками `volatile long` и `(*c)++` вместо атомарных операций разница на той же машине была намного меньше и нестабильна — от 1.0 до 1.7 раза в восьми прогонах: атомарное чтение-изменение-запись (read-modify-write) требует строку в состоянии M на каждом шаге, а обычные сохранения могут ждать в буфере записи ядра и попадать в кэш вместе.

Исправление — в размещении данных: класть данные, которые пишут разные потоки, в разные строки, дополняя или выравнивая данные каждого потока до размера строки (`alignas(128)` в C11), либо дать каждому потоку свою копию счётчика и сложить копии в конце.

## Согласованность памяти: в каком порядке становятся видны записи? \{#memory-consistency-in-what-order-do-writes-become-visible\}

Когерентность касается одной ячейки: все ядра согласны в порядке записей в `X`. Программа же обычно общается через несколько ячеек, например записывает данные, а потом выставляет флаг, и тогда важно, в каком порядке ядро видит записи другого ядра в *разные* ячейки. Правила для этого составляют **модель согласованности памяти** (memory consistency model).

Модель, которую ожидают программисты, — **последовательная согласованность** (sequential consistency), определённая [Lamport (1979)](#references): результат любого выполнения такой же, как если бы операции всех ядер выполнялись в некотором едином последовательном порядке, в котором операции каждого ядра идут в порядке его программы. Тогда каждое выполнение — это чередование команд потоков.

**Разобранный пример.** Два потока начинают с `x = y = 0` в памяти:

| Поток 1 | Поток 2 |
| --- | --- |
| `x = 1;` | `y = 1;` |
| `r1 = y;` | `r2 = x;` |

Четыре операции можно чередовать шестью способами, и они дают $(r_1, r_2) = (0, 1)$, $(1, 0)$ или $(1, 1)$, но никогда $(0, 0)$: какая бы загрузка ни шла в чередовании первой, сохранение другого потока стоит перед ней. Последовательная согласованность запрещает $r_1 = r_2 = 0$ (программа на Python из раздела «Код» перебирает чередования).

Реальные процессоры такой результат дают. Сохранение, промахнувшееся мимо кэша, остановило бы ядро на всё время промаха, поэтому ядра кладут сохранения в **буфер записи** (store buffer) и пропускают более поздние загрузки вперёд. Тогда загрузка `y` в потоке 1 читает память, пока его сохранение в `x` ещё лежит в буфере записи и невидимо для потока 2, и поток 2 делает то же самое. Оба читают 0. Программа на C из раздела «Код» прогоняет этот тест миллион раз на M1 с ослабленными (relaxed) атомарными операциями, скомпилированная с `-O0`, чтобы компилятор оставил каждое сохранение перед загрузкой: в одном прогоне $r_1 = r_2 = 0$ получилось в 882 022 испытаниях из 1 000 000 (от 83% до 94% в шести прогонах). С последовательно согласованными атомарными операциями, для которых компилятор выдаёт упорядоченные команды сохранения и загрузки ARM, этого не случилось ни разу.

Аппаратура ослабляет порядок, потому что последовательная согласованность дорога: каждой загрузке пришлось бы ждать, пока все предыдущие сохранения станут видны всем остальным ядрам. Процессоры x86 допускают ровно эту перестановку сохранения с более поздней загрузкой (модель полного порядка сохранений, total store order); ARM и слабая модель памяти RISC-V RVWMO допускают больше, например перестановку двух сохранений или двух загрузок по разным адресам ([Adve and Gharachorloo, 1996](#references), о классах ослабленных моделей). Программы, которым нужен порядок, требуют его явно: в RISC-V есть команда `fence`, которая ставит каждое обращение к памяти до неё впереди каждого обращения после неё, а атомарные операции C11 с `memory_order_seq_cst` компилируются в те команды или барьеры, которые нужны конкретному процессору. Программы, которые защищают все общие данные блокировками и атомарными операциями и поэтому не содержат гонок данных (data races), ведут себя так, как если бы машина была последовательно согласованной. Как писать такие программы, рассказывает [заметка о синхронизации](/ru/notes/acos/synchronization).

## Аппаратная многопоточность \{#hardware-multithreading\}

Ядро, ждущее память, оставляет свои функциональные блоки без дела, а [предыдущая заметка](/ru/notes/acos/instruction-level-parallelism) показала, что один поток и так редко заполняет широкое ядро. **Аппаратная многопоточность** (hardware multithreading) хранит в одном ядре архитектурное состояние нескольких потоков, у каждого — свой счётчик команд и свои регистры, и позволяет им разделять функциональные блоки и кэши. Переключение между аппаратными потоками не требует участия операционной системы и стоит не больше нескольких тактов. Есть три вида:

- **Крупнозернистая** (coarse-grained) многопоточность переключается на другой поток только при долгом простое, например при промахе в основную память. Она скрывает долгие простои, но не короткие, и при каждом переключении платит за повторное заполнение конвейера.
- **Мелкозернистая** (fine-grained) многопоточность переключает потоки каждый такт, по кругу (round robin), пропуская остановленные потоки. Она скрывает и короткие простои, но каждый поток работает медленнее, потому что при $k$ потоках он получает не больше каждого $k$-го такта.
- **Одновременная многопоточность** (simultaneous multithreading, SMT; [Tullsen, Eggers and Levy, 1995](#references)) использует суперскалярное ядро с внеочередным исполнением из предыдущей заметки: в одном и том же такте очередь выдачи может запускать команды разных потоков. Переименование разводит их регистры, поэтому логике выдачи не нужно знать, какому потоку принадлежит команда.

**Разобранный пример.** Ядро шириной 4 выполняет поток, который чередует 6 тактов, когда он начинает по 2 команды за такт, и 4 такта простоя из-за промаха кэша: 12 команд за 10 тактов, IPC 1.2, занято 30% из 40 позиций выдачи. С SMT и вторым таким же потоком ядро начинает до 4 команд за такт от двух потоков вместе — 24 команды за 10 тактов, IPC 2.4, если потоки не мешают друг другу в кэшах. Каждый поток не быстрее, чем в одиночку; больше успевает ядро. Первая реализация SMT у Intel, Hyper-Threading, выполняла два потока на ядро, увеличивала размер и мощность кристалла меньше чем на 5% и давала измеренный выигрыш до 30% на серверных бенчмарках ([Marr et al., 2002](#references)). У используемого здесь M1 SMT нет: macOS сообщает 8 ядер и 8 аппаратных потоков.

## Что изменилось \{#what-changed\}

| | Одно ядро | Многоядерный процессор с когерентными кэшами |
| --- | --- | --- |
| Потоков команд одновременно | один, потоки сменяют друг друга | по одному на ядро (больше с SMT) |
| Ускорение программы | только за счёт ILP | не больше $1/(1 - p)$ для фиксированной задачи (Амдал); около $n$ для задачи, растущей с $n$ (Густафсон) |
| Откуда берётся производительность | частота и IPC | число ядер, каждое на более низкой частоте |
| Кэши | частные, невидимые для программ | частные, но когерентные благодаря протоколу (MESI) |
| Новые издержки | переключения контекста | промахи когерентности, ложное разделение, синхронизация |
| Порядок обращений к памяти | порядок программы | модель согласованности; в аппаратуре ослаблена, барьеры восстанавливают порядок |

## Ограничения \{#limitations\}

- **Последовательная часть.** Закон Амдала ограничивает ускорение фиксированной задачи величиной $1/(1 - p)$, а дисбаланс нагрузки и координация делают его ещё меньше.
- **Параллельное программирование трудно.** Работу нужно разделить, потоки синхронизировать, гонок данных избежать; ошибки зависят от времени и плохо воспроизводятся.
- **Когерентность не масштабируется бесплатно.** Отслеживанию нужно, чтобы каждый кэш видел каждый запрос; каталоги стоят памяти и добавляют лишний переход к каждому промаху. Записи в общие строки гоняют их между кэшами.
- **Общие ресурсы.** Ядра разделяют кэш последнего уровня и пропускную способность памяти, поэтому программы, ограниченные памятью, выигрывают от дополнительных ядер меньше, чем подсказывает их число.
- **Ослабленная согласованность.** Без барьеров или атомарных операций поток может увидеть записи другого потока в порядке, который не объясняется никаким чередованием.

## Что нужно запомнить \{#what-you-should-remember\}

- После конца масштабирования Деннарда ограничением стала мощность, а не транзисторы, и на делимой работе два более медленных ядра выполняют больше работы на ватт, чем одно быстрое.
- Амдал: $S(n) = 1/((1 - p) + p/n) \le 1/(1 - p)$. При $p = 0.95$: 5.93 на 8 ядрах и никогда больше 20.
- Густафсон: для задачи, растущей вместе с машиной, $S = s + (1 - s)\,n$, где $s$ — последовательная доля параллельного прогона.
- Когерентность: чтения возвращают последнюю запись, а записи в одну ячейку видны в одном порядке. MESI реализует её через инвалидацию: много читателей или один писатель на строку.
- Ложное разделение: разные переменные в одной строке заставляют строку переезжать между ядрами при каждой записи; часто записываемые данные каждого потока нужно дополнять до размера строки. Измерено на M1: 2.52 с против 0.22 с.
- Последовательная согласованность (Лэмпорт) означает, что каждое выполнение объясняется некоторым чередованием. Буферы записи её нарушают; барьеры и последовательно согласованные атомарные операции её восстанавливают.
- Аппаратная многопоточность делит одно ядро между несколькими потоками; SMT запускает команды нескольких потоков в одном такте.

## Код \{#code\}

Законы Амдала и Густафсона, мощность двух более медленных ядер и чередования, которые допускает последовательная согласованность:

```python
from itertools import combinations

# закон Амдала: доля p времени на одном ядре выполняется в n раз быстрее
amdahl = lambda p, n: 1 / ((1 - p) + p / n)
print([round(amdahl(0.95, n), 2) for n in (2, 4, 8, 64, 1024)], round(1 / 0.05))
# [1.9, 3.48, 5.93, 15.42, 19.64] 20

# параллельная доля, нужная для ускорения S на n ядрах: p = (1 - 1/S) / (1 - 1/n)
need = lambda S, n: (1 - 1 / S) / (1 - 1 / n)
print(round(need(6, 8), 4), round(need(50, 64), 4))
# 0.9524 0.9956

# закон Густафсона: доля s времени на n ядрах последовательна, остальное масштабируется с n
gustafson = lambda s, n: s + (1 - s) * n
print(round(gustafson(0.05, 8), 2), round(gustafson(0.05, 1024), 2))
# 7.65 972.85

# динамическая мощность C V^2 f: два ядра на 0.8 f и 0.8 V против одного ядра на f и V
print(round(2 * 0.8 * 0.8 ** 2, 3), 2 * 0.8)
# 1.024 1.6: the same power, 1.6 times the throughput on a job that divides

# последовательная согласованность для теста с буфером записи: все чередования двух потоков
T1 = [('st', 'x'), ('ld', 'y', 'r1')]
T2 = [('st', 'y'), ('ld', 'x', 'r2')]
outcomes = set()
for pos in combinations(range(4), 2):                # позиции, занятые потоком 1, в порядке его программы
    order, i, j = [], 0, 0
    for s in range(4):
        if s in pos: order.append(T1[i]); i += 1
        else:        order.append(T2[j]); j += 1
    mem, reg = {'x': 0, 'y': 0}, {}
    for op in order:
        if op[0] == 'st': mem[op[1]] = 1
        else:             reg[op[2]] = mem[op[1]]
    outcomes.add((reg['r1'], reg['r2']))
print(sorted(outcomes))                              # (0, 0) среди них нет
# [(0, 1), (1, 0), (1, 1)]
```

Ложное разделение. Компиляция: `clang -std=c17 -Wall -Wextra -O0 false_sharing.c -o false_sharing`. Время зависит от машины и меняется между прогонами; показан вывод одного прогона на Apple M1 (macOS 26.5, Apple clang 21) при работающих других программах.

```c
// False sharing: two threads each add 1 to their own counter 100 million times.
// In `same` the two counters sit next to each other, on one cache line;
// in `padded` each counter starts its own 128-byte line (the line size macOS reports on the M1).
#include <pthread.h>
#include <stdalign.h>
#include <stdatomic.h>
#include <stddef.h>
#include <stdio.h>
#include <time.h>

#define N 100000000L

struct same   { _Atomic long a; _Atomic long b; };
struct padded { alignas(128) _Atomic long a; alignas(128) _Atomic long b; };
static struct same same;
static struct padded padded;

static void *count(void *arg) {                // the body of each thread
    _Atomic long *c = arg;
    for (long i = 0; i < N; i++)
        atomic_fetch_add_explicit(c, 1, memory_order_relaxed);   // one atomic read-modify-write
    return NULL;
}

static double run(_Atomic long *x, _Atomic long *y) {   // two threads, one per counter; seconds
    struct timespec t0, t1;
    pthread_t a, b;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    pthread_create(&a, NULL, count, (void *)x);
    pthread_create(&b, NULL, count, (void *)y);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    clock_gettime(CLOCK_MONOTONIC, &t1);
    return (t1.tv_sec - t0.tv_sec) + (t1.tv_nsec - t0.tv_nsec) / 1e9;
}

int main(void) {
    printf("distance between the counters: same %zu bytes, padded %zu bytes\n",
           offsetof(struct same, b), offsetof(struct padded, b));
    double ts = run(&same.a, &same.b);
    double tp = run(&padded.a, &padded.b);
    printf("counts: %ld %ld %ld %ld\n", (long)same.a, (long)same.b, (long)padded.a, (long)padded.b);
    printf("same line %.2f s, separate lines %.2f s\n", ts, tp);
    return 0;
}
// distance between the counters: same 8 bytes, padded 128 bytes
// counts: 100000000 100000000 100000000 100000000
// same line 2.52 s, separate lines 0.22 s        (one run; the times vary)
```

Тест с буфером записи для последовательной согласованности: миллион испытаний с ослабленными и с последовательно согласованными атомарными операциями. Число исходов $r_1 = r_2 = 0$ меняется между прогонами и машинами; на процессорах, допускающих перестановку, оно положительно с ослабленными атомарными операциями и всегда равно 0 с последовательно согласованными.

```c
// Store buffering: thread 1 runs x = 1; r1 = y;  thread 2 runs y = 1; r2 = x.
// Sequential consistency forbids r1 == 0 && r2 == 0. Count how often it happens anyway.
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

#define TRIALS 1000000

static _Atomic int x, y, r1, r2;
static _Atomic int go[2];                  // trials finished by each thread
static _Atomic int round_no;               // the trial now running
static memory_order mo;                    // relaxed, or seq_cst

static void *t1(void *arg) {
    (void)arg;
    for (int k = 1; k <= TRIALS; k++) {
        while (atomic_load(&round_no) != k) ;        // wait for the trial to start
        atomic_store_explicit(&x, 1, mo);
        atomic_store_explicit(&r1, atomic_load_explicit(&y, mo), memory_order_relaxed);
        atomic_fetch_add(&go[0], 1);
    }
    return NULL;
}
static void *t2(void *arg) {
    (void)arg;
    for (int k = 1; k <= TRIALS; k++) {
        while (atomic_load(&round_no) != k) ;
        atomic_store_explicit(&y, 1, mo);
        atomic_store_explicit(&r2, atomic_load_explicit(&x, mo), memory_order_relaxed);
        atomic_fetch_add(&go[1], 1);
    }
    return NULL;
}

static long run(memory_order order) {
    mo = order;
    atomic_store(&round_no, 0); atomic_store(&go[0], 0); atomic_store(&go[1], 0);
    pthread_t a, b;
    pthread_create(&a, NULL, t1, NULL);
    pthread_create(&b, NULL, t2, NULL);
    long both_zero = 0;
    for (int k = 1; k <= TRIALS; k++) {
        atomic_store(&x, 0); atomic_store(&y, 0);
        atomic_store(&round_no, k);                  // start trial k
        while (atomic_load(&go[0]) != k || atomic_load(&go[1]) != k) ;
        both_zero += atomic_load(&r1) == 0 && atomic_load(&r2) == 0;
    }
    pthread_join(a, NULL); pthread_join(b, NULL);
    return both_zero;
}

int main(void) {
    printf("relaxed: r1 = r2 = 0 in %ld of %d trials\n", run(memory_order_relaxed), TRIALS);
    printf("seq_cst: r1 = r2 = 0 in %ld of %d trials\n", run(memory_order_seq_cst), TRIALS);
    return 0;
}
// relaxed: r1 = r2 = 0 in 882022 of 1000000 trials    (one run on the M1; the count varies)
// seq_cst: r1 = r2 = 0 in 0 of 1000000 trials
```

## Дальше \{#next\}

Потоки дают программе несколько потоков команд, каждый из которых сам выбирает, декодирует и планирует свои команды, и им приходится координироваться через когерентную память. Большая часть работы в графике, обработке сигналов и машинном обучении устроена проще: одна и та же операция над каждым элементом большого массива.
