В [предыдущей заметке](/ru/notes/acos/files-and-io) каждый `open` был успешным, потому что каждая программа открывала файлы, созданные ею самой. На машине, которой пользуются несколько человек или несколько служб, не доверяющих друг другу, ядро должно при каждом `open`, при каждом `exec` и в каждом каталоге на пути решать, разрешён ли запрос. У безопасности две половины. *Аутентификация* (authentication) устанавливает, кто спрашивает, например с помощью пароля при входе в систему. *Управление доступом* (access control) решает, что этой личности разрешено делать. Эта заметка — о второй половине в том виде, в каком её реализует Unix: об идентичностях, которые несёт процесс, о битах прав, которые [inode](/ru/notes/acos/files-and-io#where-the-bytes-live-inodes-and-directories) хранит рядом с размером файла, о специальных битах, которые позволяют программе действовать с чужими правами, и о более тонких средствах, появившихся позже.

**Обозначения.** UID — идентификатор пользователя (user ID), GID — идентификатор группы (group ID); оба — небольшие целые числа. У процесса есть реальный, эффективный и сохранённый UID, обозначаемые ruid, euid и suid, и такие же три GID. Режимы прав — восьмеричные числа, записанные, как в C, с ведущим нулём: `0640` — это $6 \cdot 8^2 + 4 \cdot 8 = 416$ в десятичной записи.

## Кто спрашивает? Пользователи, группы и учётные данные \{#who-is-asking-users-groups-and-credentials\}

Для ядра пользователь — это число, **UID**. Имена существуют для людей и хранятся в обычных файлах. Каждая строка `/etc/passwd` состоит из семи полей, разделённых двоеточиями: имя, заполнитель на месте пароля, UID, основной GID, комментарий, домашний каталог и оболочка входа. Например, в системе Debian 13:

```
root:x:0:0:root:/root:/bin/bash
postgres:x:999:999::/var/lib/postgresql:/bin/bash
```

Хеши паролей лежат в `/etc/shadow`, который обычные пользователи читать не могут. **Группа** — тоже число, **GID**; имена групп и их члены перечислены в `/etc/group`. У пользователя одна основная группа, из `/etc/passwd`, и сколько угодно *дополнительных* (supplementary) групп — из списков членов в `/etc/group`. Команда `id` печатает их: `uid=999(postgres) gid=999(postgres) groups=999(postgres),101(ssl-cert)`. UID 0 особый. Обычно его имя — `root`, и ядро позволяет процессу с UID 0 обходить проверки прав, о которых идёт речь в этой заметке.

Права проверяются для процесса, а не для человека. Каждый процесс несёт **учётные данные** (credentials): реальные UID и GID (кто его запустил), эффективные UID и GID (чьими правами он пользуется), сохранённые UID и GID (объясняются ниже) и список дополнительных групп. `fork` копирует их, а `exec` сохраняет, поэтому каждая программа, которую пользователь запускает из оболочки, работает с идентификаторами этого пользователя. Они устанавливаются один раз, при входе: программа входа работает от root, проверяет пароль, устанавливает группы, GID и UID пользователя и затем запускает его оболочку.

Каждый inode хранит два из этих чисел: UID владельца и GID файла. Новый файл получает владельцем эффективный UID создавшего его процесса; группой становится эффективный GID создателя в Linux и группа содержащего каталога в BSD и macOS.

## Отправная точка: один владелец, всё или ничего \{#baseline-one-owner-all-or-nothing\}

Простейшая схема: файл принадлежит владельцу, трогать его может только владелец, а root может трогать всё. Она защищает личные файлы, и примерно это даёт домашний каталог с режимом `0700`. Она не справляется в трёх обычных ситуациях:

- Команда работает над общим проектом. Все в команде должны иметь возможность читать и менять файлы, а больше никто.
- Некоторыми файлами должны пользоваться все, но менять их не должен никто: каждый пользователь запускает `/bin/ls` и читает `/etc/passwd`, и никому из них нельзя изменять ни то, ни другое.
- Пользователь должен иметь возможность сменить собственный пароль, который хранится в `/etc/shadow` — файле, который пользователь не может ни читать, ни писать.

Первым двум нужны разные права для разных классов пользователей и разные права для разных операций. Третьему нужно контролируемое исключение: программа, которая действует с бо́льшими правами, чем запустивший её человек, но только ради одного дела.

## Девять битов: чтение, запись и выполнение для владельца, группы и остальных \{#nine-bits-read-write-and-execute-for-owner-group-and-others\}

Unix делит всех на три класса относительно файла: его **владелец** (u, от user), члены его **группы** (g) и **остальные** (o, others). Для каждого класса inode хранит три бита:

| Бит | Для обычного файла | Для каталога |
| --- | --- | --- |
| r, чтение | читать содержимое | получать список имён в нём |
| w, запись | менять содержимое | создавать, удалять и переименовывать записи (нужен ещё и x) |
| x, выполнение | запускать как программу | *поиск*: использовать в пути, добираться до файлов внутри по имени |

Каждый процесс попадает ровно в один класс. Ядро берёт первое подходящее правило ([`path_resolution(7)`](#references)):

1. Если эффективный UID равен 0, проверка пройдена. (В Linux это возможность (capability) `CAP_DAC_OVERRIDE`, которой обладает root; право на выполнение она даёт, только если установлен хотя бы один из трёх битов x файла.)
2. Иначе, если эффективный UID равен владельцу файла, решают биты владельца.
3. Иначе, если эффективный GID или один из дополнительных GID равен группе файла, решают биты группы.
4. Иначе решают биты остальных.

<aside class="callout"><strong>Ключевая идея.</strong> Ядро выбирает один класс и затем смотрит только на три бита этого класса. Права никогда не собираются из нескольких классов: владельцу, чьи биты равны <code>---</code>, будет отказано, даже если биты остальных равны <code>rw-</code>.</aside>

1. Слово режима `report.txt` — `0640`: четыре восьмеричные цифры, по одной на каждую группу из трёх битов.
2. Процесс с эффективным UID 0 не проверяется.
3. Если эффективный UID равен UID владельца, учитываются только биты владельца: `ann` может читать и писать.
4. Иначе, если процесс входит в группу файла, учитываются только биты группы: `bob`, член `staff`, может читать, но не писать.
5. Иначе учитываются биты остальных: `carol` не может ничего.

**Разобранный пример.** `report.txt` принадлежит `ann` и группе `staff`, режим `rw-r-----`. `ann` открывает его на запись: она владелец, биты владельца `rw-`, открытие успешно. `bob`, входящий в `staff`, открывает его на чтение: биты группы `r--` это разрешают; на запись — нет, и `open` завершается ошибкой `EACCES`, «Permission denied». `carol`, не входящая ни в то, ни в другое, получает биты остальных `---` и не может даже прочитать файл. Теперь переставим биты: режим `----rw-rw-`. Все пользователи, кроме владельца, могут читать и писать, а владелец вообще не может открыть файл; программа из раздела «Код» показывает именно это. Однако владелец всегда может вернуть режим обратно, потому что `chmod` разрешён владельцу, что бы ни говорили биты.

Каталоги добавляют второй уровень. Чтобы открыть `/home/ann/report.txt`, процессу нужен x на `/`, `/home` и `/home/ann`, а затем нужный бит на самом `report.txt`. Удаление или переименование файла — операция над его каталогом: для неё нужны w и x на каталоге и никаких прав на сам файл. Каталог с режимом `rwx--x--x` (`0711`) позволяет остальным добраться до файла внутри, имя которого они уже знают, но не получить список содержимого каталога: `ls /home/ann` завершается ошибкой, а `cat /home/ann/notes.txt` работает, если сам `notes.txt` доступен для чтения.

Проверка происходит при открытии файла, а не при каждом чтении. Процесс, открывший файл, сохраняет свой дескриптор, даже если владелец мгновение спустя снимет все биты прав; отказ получат только новые вызовы `open`.

## Восьмеричные режимы и umask \{#octal-modes-and-the-umask\}

Три бита составляют одну восьмеричную цифру, где r стоит 4, w — 2, а x — 1. Поэтому режим — это четыре восьмеричные цифры: специальные биты из следующего раздела, затем владелец, группа и остальные. Команда оболочки `chmod 750 file` и системный вызов `chmod(path, 0750)` оба устанавливают режим `rwxr-x---`; `chmod u+x`, `g-w`, `o=r` и `a+r` меняют отдельные биты по классам.

**Разобранный пример.** `rwxr-x---` — это $4+2+1 = 7$ для владельца, $4+0+1 = 5$ для группы и $0$ для остальных: `0750`. В обратную сторону: `0644` — это `rw-` ($6 = 4+2$), `r--` и `r--`, обычный режим документа. `0755` — обычный режим программы или каталога, а `0600` — личного файла, например ключа SSH.

У процесса есть также **umask** (маска режима создания файлов) — набор битов, которые удаляются из режима каждого создаваемого им файла или каталога. `open(path, O_CREAT | O_WRONLY, 0666)` запрашивает `rw-rw-rw-`, и файл получает

$$
\text{режим} = \text{запрошенный} \mathbin{\&} \lnot\,\text{umask}.
$$

**Разобранный пример.** При umask `022`:

$$
\begin{aligned}
0666 &= 110\ 110\ 110 \\
\lnot\, 0022 &= 111\ 101\ 101 \\
0666 \mathbin{\&} \lnot\, 0022 &= 110\ 100\ 100 = 0644 .
\end{aligned}
$$

`mkdir` запрашивает `0777` и получает `0755`. При umask `077` те же вызовы дают `0600` и `0700`: ничего для группы и остальных. Операция удаляет биты, а не вычитает. При umask `033` файл, запрошенный с `0666`, получает $0666 \mathbin{\&} \lnot\, 0033 = 0644$, а не $0666 - 0033 = 0633$. Umask наследуется через `fork` и `exec`, а устанавливает её команда оболочки `umask`. `022` — распространённое значение по умолчанию; дистрибутивы, которые дают каждому пользователю собственную личную группу, часто используют `002`, чтобы члены группы могли писать в файлы друг друга в общих каталогах.

## setuid, setgid и липкий бит \{#setuid-setgid-and-the-sticky-bit\}

Первая из четырёх восьмеричных цифр хранит ещё три бита: setuid (4), setgid (2) и липкий бит (sticky, 1). `ls` показывает их на позициях x: `s` на месте x владельца или группы для setuid и setgid (заглавная `S`, если бит x под ним сброшен) и `t` на месте x остальных для липкого бита (`T` без x).

**setuid** на исполняемом файле заставляет процесс, который его запускает, взять владельца файла в качестве эффективного UID. Это и есть контролируемое исключение, которого не хватало отправной точке. В Debian 13:

```
-rwsr-xr-x 1 root root   142424 Apr 19  2025 /usr/bin/passwd
-rw-r----- 1 root shadow    497 Oct  6 01:35 /etc/shadow
```

`passwd` имеет режим `4755` и принадлежит root. Запустить его может любой пользователь, и пока он работает, его эффективный UID равен 0, поэтому он может открыть `/etc/shadow` на запись. Его реальный UID по-прежнему принадлежит пользователю, и это говорит `passwd`, чей пароль менять; что обычный пользователь меняет только собственный пароль, обеспечивает сама программа.

**setgid** на исполняемом файле делает то же для группы. `chage`, которая читает данные о сроке действия паролей, имеет вид `-rwxr-sr-x root shadow` (`2755`): она работает с группой `shadow`, что позволяет ей читать `/etc/shadow` через биты группы `r--`, и никогда не становится root. На каталоге setgid в Linux означает другое: файлы, созданные внутри, получают группу каталога вместо группы создателя, а новые подкаталоги наследуют этот бит, что удерживает общий каталог проекта в одной группе.

**Липкий бит** на каталоге ограничивает удаление. В каталоге, куда могут писать все, например в `/tmp` с режимом `drwxrwxrwt` (`1777`), иначе любой мог бы удалить или переименовать чужие файлы, потому что это операции над каталогом. С липким битом файл в таком каталоге может удалить или переименовать только его владелец, владелец каталога или root.

**Разобранный пример.** В контейнере Linux каталог `/shared` имеет режим `1777`. `ann` создаёт `/shared/a.txt` с режимом `0666`. `bob` может дописывать в файл, поскольку биты остальных разрешают запись, но `rm /shared/a.txt` от имени `bob` завершается ошибкой «Operation not permitted». После `chmod 0777 /shared`, без липкого бита, тот же `rm` проходит успешно.

Программа с setuid работает с чужими правами на входных данных, которые выбирает вызывающий, поэтому ядро ограничивает вред, который она может причинить. Linux игнорирует setuid и setgid у интерпретируемых сценариев (файлов, начинающихся с `#!`); запись в файл без привилегий сбрасывает оба бита; а файловая система, смонтированная с параметром `nosuid`, игнорирует их полностью.

## Реальный и эффективный UID \{#real-and-effective-user-ids\}

Три UID существуют для того, чтобы программа с setuid могла переключаться между двумя своими личностями. Когда `exec` запускает файл с setuid, эффективный UID становится равным владельцу файла и копируется в сохранённый UID; реальный UID не меняется. После этого:

- `seteuid(id)` меняет только эффективный UID. Непривилегированный процесс может установить его равным своему реальному или сохранённому UID и ничему другому.
- `setuid(id)`, вызванный с эффективным UID 0, устанавливает все три, навсегда. Вызванный без привилегий, он меняет только эффективный UID, как `seteuid`.

**Разобранный пример.** `ann` (UID 1000) запускает программу с setuid root. Она начинает с реальным, эффективным и сохранённым UID $(1000, 0, 0)$. Она выполняет свой привилегированный шаг, затем вызывает `seteuid(1000)` и работает с $(1000, 1000, 0)$: файлы теперь проверяются как файлы `ann`. Поскольку сохранённый UID всё ещё 0, `seteuid(0)` может восстановить $(1000, 0, 0)$ для второго привилегированного шага. Когда root больше не нужен, программа вызывает `setuid(1000)`, пока её эффективный UID равен 0, что даёт $(1000, 1000, 1000)$; с этого момента `seteuid(0)` завершается ошибкой `EPERM`, и ошибка в остальной части программы уже не сможет вернуть права root.

Это **принцип наименьших привилегий** (principle of least privilege) в формулировке [Saltzer and Schroeder (1975)](#references): каждая программа должна работать с наименьшим набором прав, нужным для её работы, и не дольше, чем они нужны. `chage` следует ему, будучи setgid `shadow`, а не setuid root. Веб-сервер, который должен слушать порт 80, к которому обычные пользователи не могут привязаться, стартует от root, открывает порт и затем переключает свои рабочие процессы на непривилегированного пользователя. `sudo` выполняет отдельные команды от root после проверки конфигурационного файла и записывает каждую в журнал, вместо того чтобы выдавать оболочку root.

Один вызов в этой области — ловушка. `access(path, mode)` проверяет права по *реальному* UID, чтобы программа с setuid могла спросить, мог бы её вызывающий открыть файл. Между этой проверкой и последующим `open` другой процесс может подменить файл, например символьной ссылкой на `/etc/shadow`. Это гонка между проверкой и использованием (*time-of-check to time-of-use*, TOCTOU). Безопасный вариант понижает эффективный UID до реального и просто вызывает `open`, позволяя ядру проверить и открыть за один шаг.

## За пределами девяти битов: ACL и возможности \{#beyond-nine-bits-acls-and-capabilities\}

*Дополнительный материал: два расширения, которые современные системы добавляют к классической модели. Остальная часть заметки на него не опирается.*

**Списки управления доступом** (access control lists, ACL) добавляют к файлу записи для конкретных пользователей и групп. Чтобы позволить `carol` читать `report.txt`, не добавляя её в `staff`, в Linux (только Linux; проверено в контейнере с Linux 5.10):

```
$ setfacl -m u:carol:r report.txt
$ getfacl report.txt
# file: report.txt
# owner: ann
# group: staff
user::rw-
user:carol:r--
group::r--
mask::r--
other::---
```

Теперь `carol` может читать файл, а `bob` из предыдущего примера, который не входит ни в `staff`, ни в список, по-прежнему не может. Запись `mask` — верхний предел для именованных записей и записи группы; `chmod` и `stat` показывают её на позиции группы в режиме, а GNU `ls -l` помечает такой файл знаком `+` после режима. В macOS есть более богатые ACL, похожие на ACL Windows; они задаются командой `chmod +a "bob allow read" report.txt`.

**Возможности** (capabilities) разделяют власть root в Linux на 41 отдельную привилегию ([`capabilities(7)`](#references)), среди них `CAP_CHOWN` (сменить владельца любого файла), `CAP_DAC_OVERRIDE` (обходить проверки прав), `CAP_NET_BIND_SERVICE` (привязываться к портам ниже 1024) и очень широкая `CAP_SYS_ADMIN`. Процесс обладает их набором, а исполняемый файл может нести набор как атрибут файла, вместо того чтобы быть setuid root: `setcap cap_net_bind_service=+ep ./server` позволяет обычному пользователю запустить на порту 80 сервер, который не может читать чужие файлы или менять систему. Среды выполнения контейнеров запускают процессы от root, отбросив большинство возможностей, как покажет следующая заметка.

## Ограничения \{#limitations\}

- **Управление избирательное** (discretionary). Владелец файла сам решает, какой у него режим, и может отдать его другим. Программа, работающая от имени пользователя, в том числе вредоносная, может всё, что может этот пользователь, например прочитать все его файлы. Мандатное управление доступом (mandatory access control), такое как SELinux или AppArmor, и песочницы (sandboxes) добавляют правила, которые владельцы не могут отменить.
- **Root по-прежнему — один ключ ко всему.** Возможности его разделяют, но одна `CAP_SYS_ADMIN` охватывает так много, что почти равна полному root.
- **Группы грубы.** Одна группа на файл; изменение членства действует только для процессов, запущенных после следующего входа в систему.
- **Программы с setuid — классическая поверхность атаки.** Они работают с переменными окружения, открытыми дескрипторами и аргументами вызывающего, и каждая ошибка в них — ошибка с правами их владельца.
- **Проверки происходят при `open`.** Снятие права не отзывает уже открытые дескрипторы.
- **Все по-прежнему делят одну систему.** Пользователи с разными UID видят одно дерево файлов, одни и те же процессы и одну сеть, а ошибка в ядре ломает все границы разом.

## Что нужно запомнить \{#what-you-should-remember\}

- Ядро проверяет числа, а не имена: эффективный UID, эффективный GID и дополнительные GID процесса сравниваются с владельцем и группой файла.
- Применяется ровно один класс, выбираемый в порядке root, владелец, группа, остальные; значение имеют только три бита этого класса.
- На каталоге r даёт список, w меняет записи, x позволяет пройти через каталог по пути. Для удаления файла нужны w и x на его каталоге, а не права на файл.
- Режим — четыре восьмеричные цифры, где r = 4, w = 2, x = 1: `0640` — это `rw-r-----`. Новые файлы получают запрошенный режим со сброшенными битами umask: $0666 \mathbin{\&} \lnot\,0022 = 0644$.
- Исполняемые файлы с setuid и setgid работают с владельцем или группой файла в качестве эффективного идентификатора; липкий бит на каталоге защищает файлы других пользователей от удаления.
- Реальный UID: кто запустил программу. Эффективный UID: чьими правами она пользуется. Сохранённый UID: на что она может переключиться обратно. Отказывайтесь от привилегий как можно раньше и как можно окончательнее.
- ACL добавляют именованных пользователей и группы; возможности Linux делят root на 41 привилегию.

## Код \{#code\}

Биты режима временного файла и каталога, установленные через `chmod` и `umask` и напечатанные в восьмеричном виде и в формате `ls`. Программа также показывает, что владельцу отказывают, когда биты владельца говорят «нет», и что проверка прав происходит только при `open` (macOS и Linux; компиляция: `clang -std=c17 -Wall -Wextra -O0`, запускать от имени обычного пользователя):

```c
// Mode bits of a temporary file and directory: what mkstemp, chmod and umask set, printed in octal and as ls shows them.
// Run it as an ordinary user: root skips the permission checks.
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void show(const char *what, const char *path) {
    struct stat st;
    stat(path, &st);
    mode_t m = st.st_mode;
    char s[11] = "-rwxrwxrwx";
    if (S_ISDIR(m)) s[0] = 'd';
    for (int i = 0; i < 9; i++)                    // s[1] is bit 8 (owner r), ..., s[9] is bit 0 (others x)
        if (!(m & (1 << (8 - i)))) s[i + 1] = '-';
    if (m & S_ISUID) s[3] = (m & S_IXUSR) ? 's' : 'S';
    if (m & S_ISGID) s[6] = (m & S_IXGRP) ? 's' : 'S';
    if (m & S_ISVTX) s[9] = (m & S_IXOTH) ? 't' : 'T';
    printf("%-22s %04o  %s\n", what, (unsigned)(m & 07777), s);
}

int main(void) {
    char path[] = "/tmp/perm-demo-XXXXXX";
    int fd = mkstemp(path);                        // mkstemp creates the file with mode 0600
    write(fd, "secret\n", 7);
    close(fd);
    show("mkstemp", path);
    chmod(path, 0640);                             // rw- r-- ---
    show("chmod 0640", path);
    chmod(path, S_IRWXU | S_IRGRP | S_IXGRP);      // the same idea with named constants: 0750
    show("chmod u=rwx,g=rx", path);
    chmod(path, 04755);                            // setuid + rwx r-x r-x
    show("chmod 4755", path);

    chmod(path, 0066);                             // --- rw- rw-: everyone but the owner may read
    show("chmod 0066", path);
    fd = open(path, O_RDONLY);                     // we are the owner, so only the owner bits count
    printf("owner opens for reading: %s\n", fd < 0 ? strerror(errno) : "ok");
    if (fd >= 0) close(fd);

    chmod(path, 0600);
    fd = open(path, O_RDONLY);                     // the check happens here, at open
    chmod(path, 0000);                             // taking every bit away afterwards...
    char buf[16];
    ssize_t n = read(fd, buf, sizeof buf);
    printf("after chmod 0000: old fd reads %zd bytes, a new open: %s\n",
           n, open(path, O_RDONLY) < 0 ? strerror(errno) : "ok");
    close(fd);                                     // ...does not revoke the open descriptor
    unlink(path);

    char dir[] = "/tmp/perm-dir-XXXXXX";
    mkdtemp(dir);                                  // mkdtemp creates the directory with mode 0700
    show("mkdtemp", dir);
    chmod(dir, 01777);                             // what /tmp has: everyone may create, sticky bit set
    show("chmod 1777 (dir)", dir);
    rmdir(dir);

    mode_t old = umask(022);                       // the umask clears bits from every new file's mode
    fd = open(path, O_CREAT | O_WRONLY, 0666);     // asks for rw-rw-rw-, gets 0666 & ~022
    close(fd);
    show("open 0666, umask 022", path);
    unlink(path);
    umask(077);
    fd = open(path, O_CREAT | O_WRONLY, 0666);     // gets 0666 & ~077
    close(fd);
    show("open 0666, umask 077", path);
    unlink(path);
    umask(old);

    // The kernel compares numbers: here the real and the effective UID are the same.
    printf("real UID == effective UID: %s\n", getuid() == geteuid() ? "yes" : "no");
    return 0;
}
// mkstemp                0600  -rw-------
// chmod 0640             0640  -rw-r-----
// chmod u=rwx,g=rx       0750  -rwxr-x---
// chmod 4755             4755  -rwsr-xr-x
// chmod 0066             0066  ----rw-rw-
// owner opens for reading: Permission denied
// after chmod 0000: old fd reads 7 bytes, a new open: Permission denied
// mkdtemp                0700  drwx------
// chmod 1777 (dir)       1777  drwxrwxrwt
// open 0666, umask 022   0644  -rw-r--r--
// open 0666, umask 077   0600  -rw-------
// real UID == effective UID: yes
```
