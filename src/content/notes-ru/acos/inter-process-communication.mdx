[Предыдущая заметка](/ru/notes/acos/synchronization) заставила потоки, разделяющие одно адресное пространство, действовать по очереди с помощью блокировок. Процессы начинают с противоположного конца. У каждого своё частное адресное пространство, поэтому ни один процесс не может испортить данные другого, и по той же причине ни один процесс не может просто передать другому значение: нет переменной, которую видят оба. Поэтому любой канал между процессами проходит через ядро — владельца единственных ресурсов, которые могут назвать несколько процессов. Эта заметка разбирает классические средства межпроцессного взаимодействия (inter-process communication, IPC) в Unix: неименованные каналы (pipes) и FIFO для потоков байтов, сигналы для событий, разделяемую память для больших объёмов данных с семафором для согласования и очереди сообщений для отдельных сообщений, — и заканчивается тем, как выбрать среди них.

## Отправная точка: обмен через файл \{#baseline-communicating-through-a-file\}

Два процесса уже могут общаться через файловую систему. Производитель записывает результаты в `results.txt`, потребитель читает файл. Это работает, и так данные передают многие конвейеры пакетной обработки, но как канал между работающими процессами этот способ плох в четырёх отношениях:

- **Нет признака конца сообщения.** Потребитель не может узнать, закончил ли производитель запись или находится посреди строки; ему приходится опрашивать файл, и он может прочитать неполный результат.
- **Нет ожидания.** Потребитель, нашедший файл пустым, может только заснуть и попробовать снова, теряя время или добавляя задержку.
- **Имена и уборка.** Два запуска, выбравшие одно имя, перезаписывают друг друга, а аварийно завершившийся производитель оставляет файл после себя.
- **Стоимость.** Каждый байт проходит через файловую систему, а возможно, и через диск, хотя нужен лишь однажды, одному читателю, мгновение спустя.

Процессам нужен канал, который ядро держит в памяти, который блокирует читателя, пока данных нет, сообщает читателю, что писатель закончил, и исчезает вместе с процессами.

<aside class="callout"><strong>Ключевая идея.</strong> По умолчанию процессы ничего не разделяют, поэтому любой канал между ними — объект в ядре. Либо ядро копирует байты из памяти отправителя в свой буфер и оттуда в память получателя (неименованные каналы, очереди сообщений и сокеты) и тогда может заодно заставить получателя ждать; либо оно отображает одни и те же физические страницы в оба адресных пространства (разделяемая память), что ничего не копирует и оставляет всё согласование процессам.</aside>

## Неименованные каналы \{#pipes\}

`pipe(fd)` создаёт буфер в ядре и возвращает два файловых дескриптора (file descriptors): `fd[0]` читает из буфера, а `fd[1]` пишет в него ([Kerrisk, 2010](#references), глава 44). Данные выходят в том порядке, в каком вошли, как поток байтов. Ожиданием занимается ядро: `read` из пустого канала блокируется, пока не придут данные, а `write` в полный канал блокируется, пока читатель не освободит место. Когда закрыты все концы для записи, `read` возвращает 0 — конец файла. Когда закрыты все концы для чтения, `write` завершается ошибкой `EPIPE`, и ядро посылает писателю сигнал `SIGPIPE`, действие которого по умолчанию завершает процесс: поэтому `yes | head -1` завершается.

У канала нет имени, поэтому он соединяет только процессы, унаследовавшие его дескрипторы: процесс создаёт канал и затем вызывает `fork`, а [заметка о процессах](/ru/notes/acos/processes-and-threads) показала, что `fork` копирует таблицу файлов. Чтобы канал работал в одном направлении, каждый процесс закрывает конец, которым не пользуется.

<PipeFlow />

1. Родитель вызывает `pipe(fd)`. Ядро создаёт буфер; родитель получает дескрипторы 3 (конец для чтения) и 4 (конец для записи).
2. Родитель вызывает `fork`. Таблица файлов потомка — копия, поэтому теперь оба процесса держат оба конца.
3. Потомок закрывает конец для записи, с помощью `dup2(3, 0)` делает конец для чтения своим стандартным вводом, закрывает 3 и выполняет `tr a-z A-Z`. Родитель закрывает конец для чтения.
4. Родитель пишет `bytes through a pipe\n`. Ядро копирует 21 байт в свой буфер; `tr` читает их из дескриптора 0 так же, как читал бы с терминала, и печатает `BYTES THROUGH A PIPE`.
5. Родитель закрывает конец для записи. Он был последним открытым, поэтому следующий `read` в `tr` возвращает 0, и `tr` завершается.

Закрытие ненужных концов — не наведение порядка. Если бы потомок сохранил свою копию конца для записи, канал никогда не лишился бы последнего писателя, `tr` вечно ждал бы ввода, а вместе с ним и родитель в `waitpid`.

Так оболочка выполняет `ls | wc -l`: она создаёт канал, дважды вызывает `fork`, делает конец для записи стандартным выводом потомка, выполняющего `ls`, а конец для чтения — стандартным вводом потомка, выполняющего `wc`, и закрывает оба конца у себя. Ни одна из программ не знает, что общается с другой.

**Сколько вмещает канал.** На Apple M1, использованном здесь (macOS 26), писатель, который никогда не читает, смог поместить в канал 65 536 байт, прежде чем неблокирующий `write` завершился ошибкой `EAGAIN` (раздел «Код»). Linux по умолчанию даёт каналу 16 страниц — 65 536 байт при страницах по 4 КиБ ([pipe(7)](#references)). Программы не должны полагаться ни на одно из этих чисел: писатель просто блокируется, пока канал полон. Важна родственная гарантия. Запись не более чем `PIPE_BUF` байт атомарна: когда несколько процессов пишут в один канал, такая запись никогда не перемешивается с байтами другой. POSIX требует, чтобы `PIPE_BUF` был не меньше 512; в macOS он равен 512, в Linux — 4096.

**Поток, а не сообщения.** Две записи по 10 байт могут быть прочитаны одним чтением в 20 байт, а запись в 100 байт может прийти двумя чтениями по 50. Программа, отправляющая записи (records) через канал, должна сама отмечать их границы: перевод строки после каждой строки или длина перед каждой записью.

### FIFO: каналы с именем \{#fifos-pipes-with-a-name\}

**FIFO**, или именованный канал (named pipe), — это канал с записью в файловой системе. Его создаёт `mkfifo("/tmp/jobs", 0600)`; после этого любой процесс, у которого есть права, может открыть его с помощью `open` — один для чтения, другой для записи, — не будучи родственником другого. Открытие FIFO на чтение блокируется, пока какой-нибудь процесс не откроет его на запись, и наоборот, так что два процесса встречаются. Данные никогда не попадают на диск: имя — лишь способ найти буфер ядра. В оболочке `mkfifo /tmp/f; wc -c < /tmp/f & ls > /tmp/f` соединяет две программы, запущенные по отдельности.

## Сигналы \{#signals\}

**Сигнал** (signal) — уведомление, которое ядро доставляет процессу асинхронно, на какой бы команде процесс в этот момент ни находился ([Kerrisk, 2010](#references), главы 20–22; [Bryant and O'Hallaron, 2016](#references), §8.5). Кроме своего номера он не несёт никаких данных. Сигналы приходят из трёх источников:

- **Другие процессы**, через `kill(pid, sig)` (и команду `kill`): `SIGTERM` просит процесс завершиться, `SIGKILL` завершает его принудительно, `SIGUSR1` и `SIGUSR2` означают то, что решит программа.
- **Терминал**: Ctrl-C посылает `SIGINT`, Ctrl-Z — `SIGTSTP`.
- **Само ядро**: `SIGSEGV` при недопустимом обращении к памяти и `SIGFPE` при арифметической ошибке — каждый из них видимое пользователю завершение [исключения](/ru/notes/acos/exceptions-and-interrupts); `SIGCHLD`, когда завершается потомок; `SIGPIPE` при записи в канал без читателя.

У каждого сигнала есть действие по умолчанию: завершить процесс (у большинства), завершить и записать дамп памяти (core dump) (`SIGSEGV`, `SIGQUIT`), игнорировать (`SIGCHLD`), остановить (`SIGTSTP`, `SIGSTOP`) или продолжить (`SIGCONT`). Процесс может заменить действие на **игнорирование** или на **обработчик** (handler) — функцию, которую ядро вызывает при приходе сигнала; исключение составляют `SIGKILL` и `SIGSTOP`, которые действуют всегда.

**Как выполняется обработчик.** Сигнал, посланный процессу, сначала помечается в его PCB как *ожидающий доставки* (pending). Когда процесс в следующий раз возвращается из ядра в пользовательский режим — после системного вызова, прерывания или кванта времени, — ядро проверяет, есть ли ожидающие сигналы, которые не *заблокированы* (blocked). Для каждого из них, у которого есть обработчик, ядро сохраняет регистры процесса на пользовательском стеке, устраивает так, чтобы выполнение продолжилось в обработчике, и делает так, чтобы возврат из обработчика входил в ядро через `sigreturn`, который восстанавливает сохранённые регистры. После этого прерванный код продолжается, как будто ничего не произошло. Системный вызов, который был заблокирован в момент прихода сигнала, например `read` из пустого канала, возвращает $-1$ с `errno`, равным `EINTR`, если обработчик не был установлен с флагом `SA_RESTART`.

**Устанавливайте обработчики через `sigaction`**: она точно определяет, что происходит; старая функция `signal` ведёт себя в разных системах по-разному. `sigprocmask` блокирует и разблокирует сигналы: заблокированный сигнал остаётся ожидающим, пока его не разблокируют. Стандартные сигналы не ставятся в очередь: признак ожидания — один бит на сигнал. В разделе «Код» процесс блокирует `SIGUSR1`, трижды посылает его себе и разблокирует; обработчик выполняется один раз.

**Безопасность в обработчиках сигналов.** Обработчик может прервать основную программу на любой команде, в том числе посреди обновления списка свободных блоков в `malloc` или заполнения буфера в `printf`. Если обработчик затем сам вызовет `malloc` или `printf`, он будет работать с наполовину обновлённой структурой данных, и программа может аварийно завершиться или попасть во взаимную блокировку на блокировке, которую держит прерванный код. Поэтому POSIX перечисляет функции, **безопасные для асинхронных сигналов** (async-signal-safe), то есть такие, которые можно вызывать из обработчика: `write`, `read`, `_exit`, `kill`, `sigaction` и другие, но не `printf`, `malloc` или `exit` ([signal-safety(7)](#references)). Обычный приём — почти ничего не делать в обработчике: он устанавливает флаг типа `volatile sig_atomic_t`, который записывается за один шаг, а основной цикл проверяет флаг и выполняет настоящую работу.

```c
static volatile sig_atomic_t stop = 0;
static void on_term(int sig) { (void)sig; stop = 1; }     /* only set the flag */
/* main loop: while (!stop) { serve_one_request(); }  then clean up and exit */
```

## Разделяемая память \{#shared-memory\}

Канал копирует каждый байт дважды: `write` копирует его из буфера отправителя в ядро, `read` — из ядра в буфер получателя. Для больших данных, например кадров видео или кэша базы данных, эти копирования становятся основной затратой. **Разделяемая память** (shared memory) устраняет их: ядро отображает одни и те же физические страницы в два адресных пространства, и сохранение, выполненное одним процессом, видно загрузке в другом ([Kerrisk, 2010](#references), глава 54).

Интерфейс POSIX использует те же вызовы, что и файлы и [отображаемые в память файлы](/ru/notes/acos/files-and-io):

1. `int fd = shm_open("/acos-demo", O_CREAT | O_RDWR, 0600)` создаёт или открывает объект разделяемой памяти по имени.
2. `ftruncate(fd, size)` задаёт его размер; новый объект пуст.
3. `void *p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0)` отображает его. Именно `MAP_SHARED` делает сохранения видимыми другим процессам; с `MAP_PRIVATE` каждый процесс получил бы собственные страницы с копированием при записи (copy-on-write).
4. `close(fd)`; отображение остаётся действительным. `munmap` удаляет отображение, а `shm_unlink` — имя. Сам объект исчезает, когда имени больше нет и ни один процесс его не отображает.

Другой процесс, который откроет то же имя и отобразит его, увидит те же байты. Родственные процессы могут обойтись без имени: анонимное отображение, созданное с `MAP_SHARED | MAP_ANONYMOUS` до `fork`, разделяют родитель и потомок.

<SharedMapping />

Два отображения обычно начинаются с разных виртуальных адресов, поскольку `mmap` каждого процесса выбирает свободный диапазон в его собственном адресном пространстве. Поэтому указатель, сохранённый одним процессом в разделяемой области, бессмыслен для другого; разделяемые структуры данных вместо указателей хранят смещения от начала области.

**Разделяемой памяти нужна синхронизация.** После настройки отображения ядро ничего не делает: никакого копирования, но и никакого ожидания и взаимного исключения. Два процесса, увеличивающие общий счётчик, вступают в гонку (race condition) точно так же, как потоки из предыдущей заметки, а читатель может увидеть запись, которую писатель записал наполовину. Согласует их **именованный семафор** (named semaphore): `sem_open("/acos-lock", O_CREAT, 0600, 1)` даёт каждому процессу, открывшему то же имя, один и тот же семафор. В разделе «Код» родитель и потомок по 100 000 раз увеличивают счётчик в разделяемой памяти под семафором с начальным значением 1, используемым как блокировка, и итог равен ровно 200 000; второй семафор, с начальным значением 0, позволяет потомку сообщить родителю, что сообщение готово, так что родитель спит в `sem_wait`, а не опрашивает. (Мьютекс, разделяемый между процессами, — `pthread_mutexattr_setpshared` с `PTHREAD_PROCESS_SHARED`, — размещённый в разделяемой области, делает то же самое там, где он поддерживается.)

## Очереди сообщений \{#message-queues\}

**Очередь сообщений** (message queue) хранит отдельные сообщения, а не поток байтов: каждая отправка добавляет одно сообщение, каждый приём извлекает одно сообщение целиком, и границы сохраняются. Очереди сообщений POSIX ([Kerrisk, 2010](#references), глава 52) открываются по имени через `mq_open`, и каждое сообщение несёт приоритет: `mq_receive` возвращает самое старое сообщение с наивысшим приоритетом ([mq_receive(3)](#references)). В Linux очередь, созданная без атрибутов, вмещает не более 10 сообщений размером до 8192 байт каждое ([mq_overview(7)](#references)); отправитель блокируется, когда очередь полна, а получатель — когда она пуста.

```c
/* POSIX message queues. Linux only (macOS has no <mqueue.h>); run in a Debian 13 container, glibc 2.41, arm64.
   Compile with -lrt on older glibc. */
#include <fcntl.h>
#include <mqueue.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    struct mq_attr attr = { .mq_maxmsg = 10, .mq_msgsize = 64 };
    mqd_t q = mq_open("/acos-q", O_CREAT | O_RDWR, 0600, &attr);
    mq_send(q, "low",  strlen("low") + 1, 1);
    mq_send(q, "high", strlen("high") + 1, 7);
    mq_send(q, "mid",  strlen("mid") + 1, 4);
    char buf[64]; unsigned prio;
    for (int i = 0; i < 3; i++) {
        mq_receive(q, buf, sizeof buf, &prio);      /* the oldest message of the highest priority */
        printf("%s (%u)\n", buf, prio);             /* high (7), mid (4), low (1) */
    }
    mq_close(q);
    mq_unlink("/acos-q");
    return 0;
}
```

Более старый интерфейс System V (`msgget`, `msgsnd`, `msgrcv`) есть и в Linux, и в macOS ([Kerrisk, 2010](#references), глава 46). Его сообщения несут вместо приоритета положительный *тип*, и получатель может запросить первое сообщение заданного типа, так что несколько видов запросов могут делить одну очередь. Его использует запускаемый пример в разделе «Код». Его объекты обозначаются числовыми ключами, а не именами, и переживают процессы, пока их явно не удалят, поэтому их легко оставить неудалёнными.

## Как выбрать \{#choosing-among-them\}

| Канал | Данные | Границы | Кто может пользоваться | Встроенное ожидание | Копий на байт |
| --- | --- | --- | --- | --- | --- |
| Неименованный канал | байты, в одну сторону | нет | родственные процессы (унаследованные дескрипторы) | да | 2 |
| FIFO | байты, в одну сторону | нет | любой процесс, который может открыть путь | да | 2 |
| Сигнал | номер | одно событие | любой процесс, которому разрешён `kill` | обработчик выполняется асинхронно | — |
| Разделяемая память | что угодно | задают сами процессы | любой процесс, который может открыть имя | нет: добавьте семафор | 0 |
| Очередь сообщений | сообщения | сохраняются | любой процесс, который может открыть имя | да | 2 |
| Сокет | байты или датаграммы | зависят от типа | процессы на этой или другой машине | да | 2 |

Из таблицы следует несколько практических правил. Неименованный канал — выбор по умолчанию для потока данных от одного процесса к другому, и оболочка строит конвейеры только из них. Сигналы — для событий, а не для данных: остановиться, перечитать конфигурацию, потомок завершился. Разделяемая память — для больших данных, которые несколько процессов читают и обновляют на месте, и только с протоколом синхронизации, спроектированным вместе с размещением данных. Очереди сообщений подходят для запросов и ответов умеренного размера, где каждое сообщение важно само по себе. А когда процессы могут работать на разных машинах или программа должна быть к этому готова, [сокеты](/ru/notes/acos/sockets) предлагают тот же интерфейс `read`/`write` через сеть.

## Что изменилось \{#what-changed\}

| | Обмен через файл | Каналы ядра |
| --- | --- | --- |
| Где живут данные | в файловой системе, возможно на диске | в буфере ядра или на страницах, отображённых в оба процесса |
| Ожидание данных | опрос | `read` и `mq_receive` блокируются; для разделяемой памяти — семафор |
| Конец данных | неизвестен | конец файла, когда закрывает последний писатель |
| События | нет | сигналы |
| Уборка | файлы остаются | неименованные каналы исчезают вместе с процессами; именованным объектам нужен `unlink` |
| Копирования | запись и чтение через страничный кэш | 2 для неименованных каналов и очередей, 0 для разделяемой памяти |

## Ограничения \{#limitations\}

- **Неименованные каналы и FIFO переносят байты без структуры.** Процессы должны договориться о разметке границ, а FIFO с несколькими писателями перемешивает всё, что длиннее `PIPE_BUF`.
- **Сигналы грубы и хрупки.** Один бит на стандартный сигнал, никаких данных, обработчики ограничены безопасными для асинхронных сигналов вызовами, а системные вызовы прерываются с `EINTR`.
- **Разделяемая память перекладывает корректность на программиста.** Ей нужны протокол синхронизации, смещения вместо указателей и осторожность на случай, если процесс умрёт, удерживая блокировку.
- **Именованные объекты сохраняются.** Аварийно завершившаяся программа оставляет объекты разделяемой памяти, семафоры и очереди System V, пока их не удалят через unlink или машина не перезагрузится.
- **Переносимость.** В macOS нет очередей сообщений POSIX и неименованных семафоров; очереди System V в разных системах ведут себя немного по-разному.

## Что нужно запомнить \{#what-you-should-remember\}

- Процессы ничего не разделяют, поэтому общаются через объекты ядра: буферы, через которые ядро копирует данные, или страницы, которые оно отображает в оба процесса.
- `pipe` возвращает конец для чтения и конец для записи; после `fork` каждый процесс закрывает ненужный ему конец. `read` возвращает 0, только когда закрыты все концы для записи; запись без читателя вызывает `SIGPIPE`.
- Конвейер оболочки — это `pipe`, `fork`, `dup2` на дескрипторы 0 и 1 и `exec`. FIFO — канал с именем для неродственных процессов.
- Канал — поток байтов; записи до `PIPE_BUF` байт атомарны. Ёмкость — 64 КиБ на машине с macOS из этой заметки и по умолчанию в Linux, но программам не следует на неё полагаться.
- Сигнал — асинхронное событие с действием по умолчанию; `sigaction` устанавливает обработчик, `sigprocmask` блокирует. Стандартные сигналы не ставятся в очередь. Обработчик может вызывать только функции, безопасные для асинхронных сигналов: установите флаг `volatile sig_atomic_t`.
- Разделяемая память (`shm_open`, `ftruncate`, `mmap` с `MAP_SHARED`) избавляет от копирования и требует семафора или мьютекса, разделяемого между процессами.
- Очереди сообщений сохраняют границы сообщений; очереди POSIX добавляют приоритеты и есть в Linux, очереди System V — в обеих системах.

## Код \{#code\}

Канал от родителя к потомку, выполняющему `tr`, затем ёмкость канала. Компиляция и запуск: `clang -std=c17 -Wall -Wextra -O0 pipe.c -o pipe && ./pipe`:

```c
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    /* 1. parent | tr a-z A-Z: the parent writes, a child running tr reads */
    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return 1; }  /* fd[0] is the read end, fd[1] the write end */
    pid_t pid = fork();
    if (pid == 0) {
        close(fd[1]);                                /* the reader keeps only the read end */
        dup2(fd[0], STDIN_FILENO);                   /* tr reads its stdin from the pipe */
        close(fd[0]);
        execlp("tr", "tr", "a-z", "A-Z", (char *)NULL);
        _exit(127);
    }
    close(fd[0]);                                    /* the writer keeps only the write end */
    const char *msg = "bytes through a pipe\n";
    write(fd[1], msg, strlen(msg));
    close(fd[1]);                                    /* last write end closed: tr sees end of file */
    waitpid(pid, NULL, 0);

    /* 2. how much a pipe holds before a writer would block */
    pipe(fd);
    fcntl(fd[1], F_SETFL, O_NONBLOCK);               /* fail with EAGAIN instead of blocking */
    char page[4096] = {0};
    long total = 0;
    ssize_t n;
    while ((n = write(fd[1], page, sizeof page)) > 0) total += n;
    printf("capacity: %ld bytes (%s)\n", total, errno == EAGAIN ? "then EAGAIN" : strerror(errno));
    return 0;
}
/* Output (the capacity on macOS 26, Apple M1; Linux also gives 65536 by default):
BYTES THROUGH A PIPE
capacity: 65536 bytes (then EAGAIN)
*/
```

Сигналы: обработчик, установленный через `sigaction`, три сигнала, посланные во время блокировки, и потомок, завершённый сигналом `SIGTERM`:

```c
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static volatile sig_atomic_t hits = 0;

static void on_usr1(int sig) {
    (void)sig;
    hits++;                                          /* only async-signal-safe work here */
    write(STDOUT_FILENO, "  handler ran\n", 14);     /* write is async-signal-safe; printf is not */
}

int main(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_usr1;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    sigset_t block, old;
    sigemptyset(&block);
    sigaddset(&block, SIGUSR1);
    sigprocmask(SIG_BLOCK, &block, &old);            /* hold SIGUSR1 pending */
    for (int i = 0; i < 3; i++) kill(getpid(), SIGUSR1);
    printf("sent 3 while blocked, hits=%d\n", (int)hits);
    fflush(stdout);
    sigprocmask(SIG_SETMASK, &old, NULL);            /* unblock: the pending signal is delivered */
    printf("after unblocking, hits=%d (standard signals do not queue)\n", (int)hits);

    pid_t child = fork();
    if (child == 0) { pause(); _exit(0); }           /* sleeps until a signal arrives */
    sleep(1);
    kill(child, SIGTERM);                            /* no handler in the child: default action, terminate */
    int status;
    waitpid(child, &status, 0);
    printf("child terminated by SIGTERM: %s\n", WIFSIGNALED(status) && WTERMSIG(status) == SIGTERM ? "yes" : "no");
    return 0;
}
/* Output:
sent 3 while blocked, hits=0
  handler ran
after unblocking, hits=1 (standard signals do not queue)
child terminated by SIGTERM: yes
*/
```

Разделяемая память между родителем и потомком, с одним именованным семафором в роли блокировки и другим в роли сигнала:

```c
#include <fcntl.h>
#include <semaphore.h>
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

struct shared { long counter; char text[64]; };      /* the layout both processes agree on */
#define N 100000

int main(void) {
    int fd = shm_open("/acos-demo", O_CREAT | O_RDWR, 0600);
    if (fd < 0) { perror("shm_open"); return 1; }
    ftruncate(fd, sizeof(struct shared));            /* a new object has size 0 */
    struct shared *s = mmap(NULL, sizeof *s, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    close(fd);                                       /* the mapping stays valid */
    memset(s, 0, sizeof *s);

    sem_t *lock = sem_open("/acos-lock", O_CREAT, 0600, 1);   /* 1: a binary semaphore used as a lock */
    sem_t *ready = sem_open("/acos-ready", O_CREAT, 0600, 0); /* 0: nothing posted yet */
    if (lock == SEM_FAILED || ready == SEM_FAILED) { perror("sem_open"); return 1; }

    pid_t pid = fork();
    for (int i = 0; i < N; i++) {                    /* parent and child both run this loop */
        sem_wait(lock);
        s->counter++;
        sem_post(lock);
    }
    if (pid == 0) {
        snprintf(s->text, sizeof s->text, "hello from the child");
        sem_post(ready);                             /* tell the parent the text is there */
        _exit(0);
    }
    sem_wait(ready);                                 /* sleeps until the child posts */
    printf("text: %s\n", s->text);
    waitpid(pid, NULL, 0);
    printf("counter=%ld (expected %d)\n", s->counter, 2 * N);

    munmap(s, sizeof *s);
    shm_unlink("/acos-demo");                        /* remove the names; the objects go when unused */
    sem_close(lock); sem_close(ready);
    sem_unlink("/acos-lock"); sem_unlink("/acos-ready");
    return 0;
}
/* Output:
text: hello from the child
counter=200000 (expected 200000)
*/
```

Очередь сообщений System V, которая работает и в Linux, и в macOS: сообщения сохраняют границы, а получатель может выбрать сообщение по типу:

```c
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/msg.h>

struct note { long type; char text[32]; };          /* the type must be positive */

int main(void) {
    int q = msgget(IPC_PRIVATE, IPC_CREAT | 0600);   /* a new queue, known only to this process tree */
    if (q < 0) { perror("msgget"); return 1; }
    const char *texts[] = {"job 1", "status?", "job 2"};
    long types[] = {1, 2, 1};                        /* 1 = job, 2 = query */
    for (int i = 0; i < 3; i++) {
        struct note m = { types[i], "" };
        strcpy(m.text, texts[i]);
        msgsnd(q, &m, strlen(m.text) + 1, 0);
    }
    struct note m;
    msgrcv(q, &m, sizeof m.text, 2, 0);              /* the first message of type 2, ahead of the jobs */
    printf("type %ld: %s\n", m.type, m.text);
    while (msgrcv(q, &m, sizeof m.text, 0, IPC_NOWAIT) >= 0)   /* type 0: the oldest message */
        printf("type %ld: %s\n", m.type, m.text);
    msgctl(q, IPC_RMID, NULL);                       /* System V queues persist until removed */
    return 0;
}
/* Output:
type 2: status?
type 1: job 1
type 1: job 2
*/
```
