[Предыдущая заметка](/ru/notes/acos/procedures-and-the-stack) завершила картину программы на RISC-V: используемые значения лежат в 32 регистрах, а всё остальное — массивы, строки и кадры стека процедур — живёт в памяти, и до него добираются загрузками и сохранениями. Те заметки считали память одним длинным массивом байтов, в котором любой адрес стоит одинаково. Настоящая память ведёт себя не так. Регистр читается в пределах команды, которая его использует, а загрузка, которой приходится идти до самих микросхем DRAM, ждёт сотню тактов и больше. Эта заметка объясняет, как процессоры скрывают большую часть этого ожидания с помощью **кэшей** (caches) — небольших быстрых памятей, хранящих копии недавно использованных данных, — и что программа может сделать, чтобы им помочь.

**Обозначения.** Адреса имеют $m$ бит. Кэш хранит данные **блоками** (blocks; их называют также *строками*, lines) по $B = 2^b$ байтов, сгруппированными в $S = 2^s$ **наборов** (sets) по $E$ блоков; $E$ — **ассоциативность** (associativity), число **каналов** (ways). Ёмкость равна $C = S \cdot E \cdot B$ байтов, а адрес делится на $t = m - s - b$ битов тега, $s$ битов индекса и $b$ битов смещения. Для производительности $T_{\text{hit}}$ — время попадания (hit time), $M$ — доля промахов (miss rate, промахи на одно обращение), а $P$ — штраф за промах (miss penalty), дополнительное время, которого стоит промах.

## Отправная точка: каждая загрузка идёт в DRAM \{#baseline-every-load-goes-to-dram\}

Простейшая система памяти соединяет процессор прямо с основной памятью, построенной из микросхем DRAM. Каждая выборка команды, каждый `lw` и каждый `sw` — запрос к DRAM. Это работает, и так работали ранние микропроцессоры: в 1985 году обращение к DRAM занимало около 200 нс, а такт Intel 80286 — около 166 нс, так что обращение стоило примерно один такт ([Bryant and O'Hallaron](#references), §6.1.4).

Это перестаёт работать, когда процессоры становятся быстрее памяти. К 2015 году такт Core i7 сократился до 0.33 нс, в 500 раз по сравнению с 1985 годом, а время обращения к DRAM — в 10 раз, до 20 нс (та же таблица). Одно обращение теперь длилось около 60 тактов только из-за задержки самой микросхемы, а промах, который идёт через контроллер памяти в DRAM, стоит 50–200 тактов ([Bryant and O'Hallaron, слайды лекций](#references)). Цикл, загружающий одно значение каждые несколько команд, почти всё время проводил бы в ожидании. [Wulf и McKee (1995)](#references) назвали этот растущий разрыв **стеной памяти** (memory wall): пока скорость процессоров растёт быстрее скорости памяти, обращения к памяти рано или поздно начинают определять, насколько быстро работают программы.

## Насколько далеко память? \{#how-far-away-is-memory\}

Каждый уровень хранения обменивает размер на скорость. Типичные задержки для Intel Core i7, описанного у [Bryant and O'Hallaron](#references), и для флеш-памяти:

| Уровень | Типичный размер | Задержка | Кто управляет |
| --- | --- | --- | --- |
| Регистры | 32 регистра по 4 или 8 байтов | 0 тактов: читаются в пределах команды | компилятор |
| Кэш L1 | 32 КиБ на ядро | 4 такта | аппаратура |
| Кэш L2 | 256 КиБ на ядро | 10 тактов | аппаратура |
| Кэш L3 | 8 МиБ, общий для ядер | 40–75 тактов | аппаратура |
| Основная память (DRAM) | гигабайты | 50–200 тактов | аппаратура и операционная система |
| Флеш-память (SSD) | терабайты | 25–75 мкс на чтение страницы, около $10^5$ тактов при 3 ГГц | операционная система |

Цифры для кэшей — это цифры Core i7 у [Bryant and O'Hallaron](#references) (§6.4.6 и слайды лекций); цифра для флеш-памяти — время чтения одной страницы флеш-памяти без всяких программных накладных расходов: 25 мкс для микросхем, хранящих один бит в ячейке, и около 75 мкс для трёх битов в ячейке ([Arpaci-Dusseau and Arpaci-Dusseau](#references), рис. 44.2). Эти значения различаются между процессорами и поколениями и верны лишь по порядку величины. Apple M1, на котором сделаны замеры времени в этой заметке, сообщает (через `sysctl`) кэш данных L1 на 128 КиБ на каждое производительное ядро, кэш L2 на 12 МиБ, общий для четырёх производительных ядер, и строки по 128 байтов, тогда как у Core i7 выше 32 КиБ, 256 КиБ на ядро и блоки по 64 байта. Важна закономерность: каждый уровень в несколько раз медленнее вышестоящего и во много раз больше.

## Локальность: почему хватает небольшой памяти \{#locality-why-a-small-memory-is-enough\}

Небольшая память может заменить большую, только если программа использует свои данные неравномерно. Программы так и делают, причём двумя способами ([Bryant and O'Hallaron](#references), §6.2):

- **Временная локальность** (temporal locality): к ячейке, использованной сейчас, скорее всего, скоро обратятся снова. Счётчики циклов, накопители, команды тела цикла и вершина стека используются снова и снова.
- **Пространственная локальность** (spatial locality): если ячейка используется, то, скорее всего, скоро понадобятся и соседние. Массивы обходят элемент за элементом, команды выбираются одна за другой, а поля структуры лежат рядом.

**Разобранный пример.** Суммирование массива из 1024 значений `int`, `for (i = 0; i < 1024; i++) sum += a[i];`. Счётчик `i` и сумма `sum` живут в регистрах, а четыре-пять команд тела цикла выбираются по 1024 раза каждая: это временная локальность. Массив занимает 4 КиБ и читается в порядке адресов. Если память перемещается блоками по 64 байта, в каждом блоке 16 значений `int`, поэтому первое обращение к блоку промахивается, а следующие 15 попадают: 64 промаха на 1024 загрузки, доля попаданий $15/16 = 93.75\,\%$, хотя ни один элемент не читается дважды. Это пространственная локальность.

<aside class="callout"><strong>Ключевая идея.</strong> Хранить копии недавно использованных блоков в небольшой быстрой памяти рядом с процессором. Каждое обращение сначала искать там и идти на более медленный уровень только при промахе; а уж если идти, то приносить весь блок вокруг адреса, потому что его соседи, скорее всего, понадобятся следующими. Благодаря локальности большинство обращений попадает, так что среднее обращение стоит почти столько же, сколько обращение к быстрой памяти, а ёмкость остаётся ёмкостью медленной. Несколько таких уровней, поставленных друг за другом, образуют иерархию памяти.</aside>

## Как кэш находит блок \{#how-a-cache-finds-a-block\}

### Блоки, наборы и каналы \{#blocks-sets-and-ways\}

Память разбита на блоки по $B$ байтов; блок, содержащий адрес $a$, имеет номер $\lfloor a / B \rfloor$. Кэш вмещает $C / B$ блоков. Рядом с каждым хранимым блоком он держит **бит достоверности** (valid bit) $V$, который говорит, занято ли место, и **тег** (tag), который говорит, какой блок памяти здесь лежит. Номер блока определяет, куда блок можно поместить: в набор $\lfloor a/B \rfloor \bmod S$, в любой из $E$ каналов этого набора. Выбор $E$ даёт три организации ([Patterson and Hennessy](#references), §5.3–5.4):

- **с прямым отображением** (direct-mapped): $E = 1$, так что у каждого блока ровно одно возможное место;
- **$E$-канальный наборно-ассоциативный** (set-associative): $1 < E < C/B$, так что блок может попасть в любое из $E$ мест своего набора;
- **полностью ассоциативный** (fully associative): $S = 1$, так что блок может оказаться где угодно, и поиск должен проверить все теги.

### Разбиение адреса: тег, индекс и смещение \{#splitting-an-address-tag-index-and-offset\}

Поскольку $B$ и $S$ — степени двойки, деление и взятие остатка сводятся к битовым полям адреса. Младшие $b$ битов — **смещение** (offset) байта внутри блока, следующие $s$ битов — **индекс** (index) набора, а оставшиеся $t = m - s - b$ старших битов — **тег**:

$$
\boxed{\;\text{offset} = a \bmod 2^b, \qquad \text{index} = \left\lfloor a / 2^b \right\rfloor \bmod 2^s, \qquad \text{tag} = \left\lfloor a / 2^{b+s} \right\rfloor .\;}
$$

Индекс не хранится: у каждого блока в наборе 47 индекс 47. Тег вместе с индексом однозначно определяют блок, поэтому хранить и сравнивать нужно только тег.

**Разобранный пример.** У наборно-ассоциативного кэша на 16 КиБ с 4 каналами, блоками по 64 байта и 32-битными адресами $S = 16384 / (4 \cdot 64) = 64$ набора, так что $b = 6$, $s = 6$ и $t = 32 - 6 - 6 = 20$. Возьмём адрес загрузки `0x1234ABCC`. Его младшие 12 битов — `0xBCC` $= 1011\,1100\,1100_2$:

- смещение: младшие 6 битов, $001100_2 = 12$;
- индекс: следующие 6 битов, $101111_2 = 47$;
- тег: оставшиеся 20 битов, `0x1234A`.

У 8-канального кэша L1 на 32 КиБ из Core i7 выше тоже $32768 / (8 \cdot 64) = 64$ набора блоков по 64 байта, так что он делит адреса в тех же местах и отличается только тем, что у него 8 каналов.

<CacheLookup />

1. Адрес разбивается на три поля.
2. Индекс выбирает один набор, и все его каналы читаются одновременно.
3. Хранимый тег каждого канала сравнивается с тегом адреса, все параллельно; совпадение засчитывается, только если бит достоверности канала равен 1.
4. Совпадает один канал, так что обращение — **попадание** (hit), и мультиплексор пропускает блок этого канала.
5. Смещение выбирает в блоке запрошенные байты: байты 12–15, слово, которое `lw` запишет в свой регистр.

Если не совпал ни один канал, обращение — **промах** (miss): кэш запрашивает у следующего уровня весь 64-байтовый блок, помещает его в один из четырёх каналов набора 47 (в какой — говорит следующий раздел), устанавливает $V = 1$ и тег, а затем завершает загрузку, как в шагах 4 и 5.

### Почему не всегда прямое отображение или всегда полная ассоциативность? \{#why-not-always-direct-mapped-or-always-fully-associative\}

Для тех же 16 КиБ данных в блоках по 64 байта (256 блоков) и 32-битных адресов три организации различаются тем, что требуется для поиска:

| | Прямое отображение | 4 канала | Полностью ассоциативный |
| --- | --- | --- | --- |
| Наборов $S$ | 256 | 64 | 1 |
| Битов индекса $s$ | 8 | 6 | 0 |
| Битов тега $t$ | 18 | 20 | 26 |
| Сравнений тегов на поиск | 1 | 4 | 256 |
| Память под теги, $256 \cdot t$ | 4608 бит | 5120 бит | 6656 бит |

Кэш с прямым отображением самый простой и быстрый: одно сравнение, и данные можно читать ещё до того, как сравнение закончится. Его слабость в том, что два блока с одинаковым индексом вытесняют друг друга, даже когда остальной кэш пуст. **Разобранный пример.** Вычисление `s += a[k] * b[k]` по двум массивам `int` из 1024 элементов, лежащим ровно в 16 КиБ друг от друга: у `a[k]` и `b[k]` одинаковый индекс в кэше с прямым отображением на 16 КиБ, поэтому каждая загрузка вытесняет блок, нужный следующей, и все 2048 загрузок промахиваются. 2-канальный кэш того же размера держит оба блока в одном наборе и промахивается только при первом обращении к каждому блоку, 128 раз (по 64 блока на массив); раздел «Код» запускает оба варианта. Полностью ассоциативный кэш от этого не страдает, но ему нужен компаратор на каждый блок, что по карману только небольшим структурам, таким как буферы трансляции из следующей заметки. Реальные кэши находятся посередине: в Core i7 выше кэши L1 и L2 8-канальные, а кэш L3 16-канальный.

## Какой блок вытеснить: замещение \{#which-block-to-evict-replacement\}

При промахе в наборе, все каналы которого заняты, один блок должен уйти. У кэша с прямым отображением выбора нет. При $E > 1$ каналах обычная политика — **вытеснение давно не использовавшегося** (least recently used, LRU): вытеснить канал, последнее обращение к которому было раньше всех, делая ставку на временную локальность.

**Разобранный пример.** Один набор 2-канального кэша и блоки A, B и C, которые все отображаются в него, с обращениями в порядке A, B, A, C, A, B:

| Обращение | A | B | A | C | A | B |
| --- | --- | --- | --- | --- | --- | --- |
| Результат | промах | промах | попадание | промах, вытесняется B | попадание | промах, вытесняется C |
| Набор после, сначала самый старый | A | A, B | B, A | A, C | C, A | A, B |

Когда приходит C, к A обращались позже, чем к B, поэтому LRU оставляет A и получает попадание при следующем обращении. Политика «первым пришёл — первым ушёл» (FIFO) вытеснила бы A, пришедший раньше, и промахнулась бы на нём. Точный LRU должен отслеживать порядок $E$ каналов — один из $E!$ порядков на набор: 5 битов для 4 каналов, 16 битов для 8 каналов. Поэтому аппаратура с высокой ассоциативностью его приближает или выбирает вытесняемый блок случайно, что для больших кэшей мало сказывается на доле промахов ([Patterson and Hennessy](#references), §5.8).

## Что происходит при записи? \{#what-happens-on-a-write\}

Сохранение меняет данные, и кэш должен решить, когда об этом узнает следующий уровень ([Bryant and O'Hallaron](#references), §6.4.5):

- **Сквозная запись** (write-through): каждое сохранение обновляет и кэш, и следующий уровень. Следующий уровень всегда актуален, но каждое сохранение стоит обмена данными; небольшой буфер записи позволяет процессору продолжать работу, не дожидаясь его.
- **Отложенная запись** (write-back): сохранение обновляет только кэш и устанавливает **бит изменения** (dirty bit) блока. Блок записывается на следующий уровень один раз, когда его вытесняют, и только если он изменён.

А при сохранении, которое промахивается:

- **Запись с размещением** (write-allocate): принести блок в кэш, а затем записать в него, делая ставку на то, что соседние данные скоро будут записываться снова.
- **Запись без размещения** (no-write-allocate): отправить запись на следующий уровень и не трогать кэш.

Обычные пары — отложенная запись с размещением, распространённая в современных кэшах, особенно на нижних уровнях, и сквозная запись без размещения.

**Разобранный пример.** Цикл 1000 раз увеличивает счётчик в памяти (`lw`, `addi`, `sw` над одним и тем же словом). Каждое обращение после первого — попадание. При сквозной записи каждый `sw` ещё и записывает 4 байта на следующий уровень: 1000 записей, 4000 байтов. При отложенной записи следующий уровень видит один 64-байтовый блок, один раз, когда блок в конце концов вытесняется. Цена отложенной записи — на следующем уровне могут лежать устаревшие данные, что важно, когда память напрямую читает другое ядро или устройство; согласованию копий посвящена тема [когерентности кэшей](/ru/notes/acos/thread-level-parallelism).

## Почему случаются промахи: три C \{#why-misses-happen-the-three-cs\}

Каждый промах относится к одному из трёх видов («три C», three Cs; [Hill and Smith, 1989](#references); [Patterson and Hennessy](#references), §5.8), которые определяются сравнением реального кэша с двумя идеализированными:

- **Обязательные** (compulsory), или холодные (cold), промахи: первое обращение к блоку. Они были бы даже у бесконечного кэша.
- **Промахи ёмкости** (capacity misses): блоки, которые программа активно использует, не помещаются. Это промахи полностью ассоциативного кэша с LRU того же размера за вычетом обязательных.
- **Конфликтные промахи** (conflict misses): слишком много активных блоков отображается в один набор, хотя в других наборах есть место. Это промахи реального кэша сверх промахов полностью ассоциативного.

Классификация подсказывает, какое средство поможет: более крупные блоки уменьшают число обязательных промахов (блоков, которые нужно принести, меньше, но каждый дороже доставить); более крупный кэш уменьшает промахи ёмкости ценой большего времени попадания; больше каналов уменьшают конфликтные промахи ценой большего числа сравнений на поиск; а изменение порядка обращений в программе может уменьшить все три вида.

**Разобранный пример.** Матрица 64 × 64 из 4-байтовых `int`, 16 КиБ, хранится по строкам, так что каждая 256-байтовая строка занимает 4 блока по 64 байта, а всего блоков 256. Чтение по строкам обращается к каждому блоку 16 раз подряд: 256 промахов на 4096 чтений, все обязательные, каким бы ни был кэш. При чтении по столбцам соседние чтения отстоят на 256 байтов, и блок снова нужен только после того, как затронуты 64 блока целого столбца:

- Полностью ассоциативный кэш на 2 КиБ вмещает 32 блока, меньше 64, поэтому с LRU промахивается каждое чтение: 4096 промахов, из них 256 обязательных и 3840 промахов ёмкости.
- Полностью ассоциативный кэш на 4 КиБ вмещает 64 блока столбца: остаются только 256 обязательных промахов.
- Кэш с прямым отображением на 8 КиБ вдвое больше и всё равно промахивается при каждом чтении: 256 обязательных и 3840 конфликтных промахов. Номера блоков, отстоящих на 256 байтов, отличаются на 4, поэтому они попадают только в каждый четвёртый набор, и использовать удаётся лишь четверть ёмкости. 2- или 4-канальный кэш здесь не лучше; ему нужно 16 КиБ.

## Среднее время доступа к памяти \{#average-memory-access-time\}

Каждое обращение стоит времени попадания, а доля $M$ обращений, которые промахиваются, сверх того платит штраф за промах. Усредняя по обращениям, по линейности математического ожидания получаем **среднее время доступа к памяти** (average memory access time, AMAT):

$$
\boxed{\;\text{AMAT} = T_{\text{hit}} + M \cdot P .\;}
$$

При времени попадания 4 такта и штрафе 200 тактов доля промахов 3% даёт $4 + 0.03 \cdot 200 = 10$ тактов, а доля промахов 1% — $4 + 0.01 \cdot 200 = 6$ тактов: доля попаданий, выше всего на два процентных пункта, сокращает среднее время на 40%. Поэтому кэши оценивают по доле промахов, а не по доле попаданий.

**Несколько уровней.** Штраф за промах в L1 — это время, за которое отвечает кэш L2, и оно само является средним по его попаданиям и промахам. Применяя формулу к каждому уровню изнутри наружу,

$$
\begin{aligned}
\text{AMAT} &= T_{\text{L1}} + M_{\text{L1}} \cdot P_{\text{L1}} && \text{формула для L1} \\
&= T_{\text{L1}} + M_{\text{L1}} \left( T_{\text{L2}} + M_{\text{L2}} \cdot P_{\text{mem}} \right) && P_{\text{L1}} \text{ — это AMAT для L2,}
\end{aligned}
$$

где $M_{\text{L2}}$ — **локальная** (local) доля промахов L2: его промахи, делённые на обращения, которые до него доходят, а это только промахи L1. Доля всех обращений, которые идут в память, — **глобальная** (global) доля промахов $M_{\text{L1}} M_{\text{L2}}$.

**Разобранный пример (игрушечные числа в пределах таблицы).** L1: время попадания 4 такта, доля промахов 5%. L2: время попадания 12 тактов, локальная доля промахов 25%. Память: 200 тактов.

$$
\text{AMAT} = 4 + 0.05 \cdot (12 + 0.25 \cdot 200) = 4 + 0.05 \cdot 62 = 7.1 \text{ такта}.
$$

Без кэша L2 каждый промах L1 шёл бы в память: $4 + 0.05 \cdot 200 = 14$ тактов, примерно вдвое дольше. Глобальная доля промахов равна $0.05 \cdot 0.25 = 1.25\,\%$: до DRAM доходит одно обращение из 80. Локальная доля промахов 25% выглядит плохо, но L2 видит только обращения, которые L1 не смог обслужить, а это как раз трудные обращения.

## Код, дружественный к кэшу \{#writing-cache-friendly-code\}

### Обход по строкам и по столбцам \{#row-major-and-column-major-traversal\}

C хранит двумерный массив по строкам (построчный порядок, **row-major**): `a[i][j]` массива `int` размера `N` на `N` лежит по смещению $4(iN + j)$ байтов. Цикл, у которого внутренний — `j`, читает подряд идущие адреса и использует каждый байт каждого принесённого блока. Цикл, у которого внутренний — `i`, на каждом шаге перепрыгивает на $4N$ байтов и использует 4 байта каждого блока, прежде чем двинуться дальше ([Bryant and O'Hallaron](#references), §6.5).

**Измерено.** Программа на C из раздела «Код» суммирует матрицу `int` 4096 × 4096 (64 МиБ) обоими способами. На Apple M1 (macOS 26.5, Apple clang 21.0.0, `-O0`) один запуск занял 0.021 с по строкам и 0.137 с по столбцам, в 6.5 раза дольше; три запуска дали отношения от 6.1 до 6.8. Время зависит от машины и запуска; суть — в отношении. Оба цикла выполняют одни и те же команды над одними и теми же данными и печатают одну и ту же сумму: различается только порядок адресов. При $N = 4096$ шаг цикла по столбцам равен 16 КиБ, поэтому каждое чтение затрагивает новую 128-байтовую строку кэша, а столбец затрагивает 4096 строк, 512 КиБ, — гораздо больше, чем вмещает кэш L1 на 128 КиБ; к тому времени, как следующему столбцу понадобится строка, она уже вытеснена. Цикл по столбцам медленнее не в 32 раза, хотя использует одно значение `int` из каждой 128-байтовой строки вместо 32: большую часть его промахов обслуживает кэш L2 на 12 МиБ, а процессор может обрабатывать несколько промахов одновременно.

### Блочное разбиение \{#blocking\}

Некоторые вычисления нельзя переупорядочить в один проход вдоль строк. В произведении матриц $C = AB$ с порядком циклов $i, j, k$ внутренний цикл идёт вдоль строки $A$ и вниз по столбцу $B$. Посчитаем промахи для матриц $N \times N$ из `double` в блоках по 64 байта (по 8 чисел `double`) в кэше, который не может удержать $N$ блоков столбца $B$ от одного $j$ до следующего:

- строка $A$: 1 промах на 8 элементов, всего $N^3/8$;
- столбец $B$: 1 промах на элемент, всего $N^3$;
- итого около $\frac98 N^3$ промахов плюс немного для $C$.

**Блочное разбиение** (blocking, или tiling) делит матрицы на плитки $b \times b$ и перемножает их плитка за плиткой, выбирая $b$ так, чтобы три плитки одновременно помещались в кэш. Тогда плитка $A$ и плитка $B$ загружаются по одному разу на каждое произведение плиток, $2 \cdot b^2/8$ промахов, а произведений плиток $(N/b)^3$:

$$
\left(\frac{N}{b}\right)^3 \cdot \frac{2 b^2}{8} = \frac{N^3}{4b} \quad\text{промахов против}\quad \frac98 N^3 ,
$$

примерно в $4.5\,b$ раза меньше. Арифметика та же самая; просто каждый загруженный блок используется $b$ раз, прежде чем его вытеснят, а не один ([Bryant and O'Hallaron](#references), веб-врезка MEM:BLOCKING; [Patterson and Hennessy](#references), §5.15).

**Разобранный пример (симуляция).** $N = 64$ и полностью ассоциативный кэш с LRU на 2 КиБ (32 блока), с $b = 8$, так что три плитки занимают $3 \cdot 8 \cdot 8 \cdot 8 = 1\,536$ байтов. Формулы предсказывают $\frac98 \cdot 64^3 = 294\,912$ промахов для простого цикла плюс $64^2 = 4\,096$ для $C$, которая вытесняется между соседними $j$, итого 299 008; и $64^3/32 = 8\,192$ плюс $64^2/8 = 512$ для $C$, итого 8704, для блочного. Симулятор из раздела «Код» насчитывает ровно эти числа: блочное разбиение устраняет 97% промахов.

Та же идея работает уровнем ниже на GPU: [FlashAttention](/ru/notes/nlp/efficient-transformers#where-the-time-goes-memory-traffic-not-arithmetic) вычисляет внимание [плитками](/ru/notes/nlp/efficient-transformers#tiling-attention-one-block-at-a-time), которые остаются в небольшой внутрикристальной памяти SRAM, вместо того чтобы проходить через большую и более медленную HBM.

## Ограничения \{#limitations\}

- **Нет локальности — нет выигрыша.** Переходы по указателям в большой связной структуре или чтение большой таблицы в случайном порядке могут промахиваться почти при каждом обращении.
- **AMAT — это модель.** Процессоры с внеочередным исполнением (out-of-order) совмещают несколько промахов, а аппаратные блоки предвыборки (prefetchers) заранее приносят данные при регулярном шаге, так что измеренное время может оказаться лучше, чем предсказывает формула; решает только измерение.
- **Конфликты зависят от адресов.** Размеры и шаги, равные степеням двойки, — худший случай, как на рисунке. На 8-канальном кэше на 2 КиБ блочное произведение матриц из разобранного примера промахивается 299 008 раз против 275 584 у простого цикла: строки, отстоящие на 512 байтов, отправляют плитки в немногие наборы, и блочное разбиение перестаёт помогать. [Lam, Rothberg и Wolf (1991)](#references) проанализировали это самовмешательство (self-interference); средства — другой размер плитки, дополнение строк (padding) или копирование каждой плитки в непрерывный буфер.
- **Копии должны согласовываться.** Когда ядер несколько и у каждого свои кэши, сохранение в одном кэше должно стать видимым для остальных; это когерентность кэшей, о ней — [заметка о многоядерных процессорах](/ru/notes/acos/thread-level-parallelism).
- **Время выдаёт информацию.** Попала ли загрузка в кэш, можно измерить, поэтому кэш раскрывает, к каким адресам недавно обращались. Этим пользуются атаки по сторонним каналам (side-channel attacks), такие как Spectre ([Kocher et al., 2019](#references)).
- **Какие адреса?** Все адреса в этой заметке были физическими. Программы используют виртуальные адреса, и перевод одних в другие взаимодействует с кэшем, как покажет следующая заметка.

## Что нужно запомнить \{#what-you-should-remember\}

- Обращение к DRAM стоит 50–200 тактов против примерно 4 при попадании в L1; этот разрыв — стена памяти.
- Временная и пространственная локальность позволяют небольшому кэшу обслуживать большинство обращений; данные перемещаются блоками, обычно по 64 байта.
- Адрес делится на тег, индекс и смещение: смещение $= a \bmod B$, индекс $= \lfloor a/B \rfloor \bmod S$, тег $= \lfloor a/(BS) \rfloor$. Для 16 КиБ, 4 каналов и блоков по 64 байта: 6 битов смещения, 6 битов индекса, 20 битов тега.
- Кэши с прямым отображением просты и страдают от конфликтов; полностью ассоциативным нужен компаратор на каждый блок; наборно-ассоциативные находятся посередине.
- LRU вытесняет канал, к которому дольше всего не обращались; отложенная запись с размещением отправляет изменённый блок на следующий уровень один раз, при вытеснении.
- Промахи бывают обязательными, промахами ёмкости и конфликтными; они определяются через сравнение с бесконечным и с полностью ассоциативным кэшем.
- $\text{AMAT} = T_{\text{hit}} + M \cdot P$, применяемое уровень за уровнем; $4 + 0.05 \cdot (12 + 0.25 \cdot 200) = 7.1$ такта.
- Обходите массивы в том порядке, в каком они хранятся, и разбивайте на блоки вычисления, которые повторно используют данные, чтобы каждый загруженный блок использовался много раз.

## Код \{#code\}

Симулятор кэша с замещением LRU. Он печатает разбиение адреса из разобранного примера, трассу LRU, доли попаданий двух обходов матрицы 64 × 64, три C, конфликт между двумя массивами в 16 КиБ друг от друга, AMAT из разобранного примера и промахи простого и блочного произведений матриц:

```python
from collections import OrderedDict

class Cache:
    """A set-associative cache with LRU replacement; ways=None makes it fully associative."""
    def __init__(self, size, block=64, ways=None):
        self.block = block
        self.ways = ways or size // block
        self.nsets = size // (block * self.ways)
        self.sets = [OrderedDict() for _ in range(self.nsets)]   # для каждого набора: теги, сначала давно не использовавшийся
        self.hits = self.misses = 0

    def split(self, addr):
        blk = addr // self.block                               # отбросить смещение
        return blk // self.nsets, blk % self.nsets, addr % self.block   # тег, индекс, смещение

    def access(self, addr):
        tag, index, _ = self.split(addr)
        s = self.sets[index]
        if tag in s:
            s.move_to_end(tag)                                 # теперь использован последним
            self.hits += 1
            return True
        self.misses += 1
        if len(s) == self.ways:
            s.popitem(last=False)                              # вытеснить давно не использовавшийся
        s[tag] = True
        return False

def run(trace, size, ways):
    c = Cache(size, 64, ways)
    for a in trace:
        c.access(a)
    return c

# разбиение адреса из разобранного примера: 16 КиБ, 4 канала, блоки по 64 байта
tag, index, offset = Cache(16384, 64, 4).split(0x1234ABCC)
print(hex(tag), index, offset)                                # 0x1234a 47 12

# LRU в одном 2-канальном наборе: блоки A, B, A, C, A, B
c = Cache(128, 64, 2)
print(''.join('h' if c.access(64 * blk) else 'm' for blk in (0, 1, 0, 2, 0, 1)))   # mmhmhm

# два обхода матрицы 64 x 64 из 4-байтовых int (16 КиБ), хранящейся по строкам
N = 64
row = [(i * N + j) * 4 for i in range(N) for j in range(N)]
col = [(i * N + j) * 4 for j in range(N) for i in range(N)]
for name, trace in (('row-major', row), ('column-major', col)):
    for size, ways in ((2048, None), (4096, None), (8192, 1), (16384, 1)):
        c = run(trace, size, ways)
        print(f'{name:12} {size:5} B {"full" if ways is None else ways:>4}  hit rate {c.hits / len(trace):.4f}')
# row-major     2048 B full  hit rate 0.9375
# row-major     4096 B full  hit rate 0.9375
# row-major     8192 B    1  hit rate 0.9375
# row-major    16384 B    1  hit rate 0.9375
# column-major  2048 B full  hit rate 0.0000
# column-major  4096 B full  hit rate 0.9375
# column-major  8192 B    1  hit rate 0.0000
# column-major 16384 B    1  hit rate 0.9375

# три C: обязательные (бесконечный кэш), ёмкости (полностью ассоциативный того же размера), конфликтные (остальные)
def three_cs(trace, size, ways):
    compulsory = len({a // 64 for a in trace})
    full = run(trace, size, None).misses
    return compulsory, full - compulsory, run(trace, size, ways).misses - full
print(three_cs(col, 2048, 1), three_cs(col, 8192, 1))         # (256, 3840, 0) (256, 0, 3840)

# a[k] * b[k] при массивах ровно в 16 КиБ друг от друга: прямое отображение против 2 каналов, оба по 16 КиБ
ab = [x for k in range(1024) for x in (4 * k, 16384 + 4 * k)]
print(run(ab, 16384, 1).misses, run(ab, 16384, 2).misses)     # 2048 128

# среднее время доступа к памяти от L1 наружу: (время попадания, локальная доля промахов) на уровень, затем память
def amat(levels, memory):
    t = memory
    for hit, miss in reversed(levels):
        t = hit + miss * t
    return round(t, 2)
print(amat([(4, 0.05), (12, 0.25)], 200), amat([(4, 0.05)], 200))   # 7.1 14.0

# C = A B для матриц 64 x 64 из double, плитками b x b (b = 64 — простой цикл i-j-k), на кэше 2 КиБ
def matmul(N, b):
    A, B, C = 0, 8 * N * N, 16 * N * N                        # три матрицы одна за другой
    for ii in range(0, N, b):
        for jj in range(0, N, b):
            for kk in range(0, N, b):
                for i in range(ii, ii + b):
                    for j in range(jj, jj + b):
                        for k in range(kk, kk + b):
                            yield A + 8 * (i * N + k)
                            yield B + 8 * (k * N + j)
                        yield C + 8 * (i * N + j)
for ways in (None, 8):
    print([run(matmul(64, b), 2048, ways).misses for b in (64, 8)])
# [299008, 8704]     полностью ассоциативный: блочное разбиение устраняет 97% промахов
# [275584, 299008]   8 каналов: плитки сталкиваются в немногих наборах, и блочное разбиение не помогает
```

Замер времени обходов на C. Суммы одинаковы на любой машине, а время — нет, поэтому вывод ниже — пример одного запуска на Apple M1 с macOS 26.5 и Apple clang 21.0.0, компиляция `clang -std=c17 -Wall -Wextra -O0`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 4096                       /* a 4096 x 4096 matrix of int: 64 MiB, far larger than any cache */

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}

int main(void) {
    int *a = malloc(sizeof(int) * N * N);   /* row-major: a[i][j] is at a[i * N + j] */
    if (!a) return 1;
    for (long k = 0; k < (long)N * N; k++) a[k] = (int)(k % 7);

    double t0 = now();
    long row = 0;
    for (int i = 0; i < N; i++)              /* row by row: consecutive addresses */
        for (int j = 0; j < N; j++)
            row += a[(long)i * N + j];
    double t1 = now();
    long col = 0;
    for (int j = 0; j < N; j++)              /* column by column: a stride of N * 4 = 16 KiB */
        for (int i = 0; i < N; i++)
            col += a[(long)i * N + j];
    double t2 = now();

    printf("sums %ld %ld equal: %d\n", row, col, row == col);
    printf("row-major    %.3f s\n", t1 - t0);
    printf("column-major %.3f s\n", t2 - t1);
    printf("ratio %.1f\n", (t2 - t1) / (t1 - t0));
    free(a);
    return 0;
}
/* One run (Apple M1, -O0); the sums are fixed, the times vary:
   sums 50331645 50331645 equal: 1
   row-major    0.021 s
   column-major 0.137 s
   ratio 6.5 */
```

## Дальше \{#next\}

Каждый адрес в этой заметке был физическим — номером байта в микросхемах DRAM. Но RARS размещает данные каждой программы на RISC-V из предыдущих заметок по одному и тому же адресу, `0x10010000`, и две такие программы не смогли бы работать одновременно, будь это физический адрес. [Следующая заметка](/ru/notes/acos/virtual-memory) даёт каждой программе собственное **виртуальное** адресное пространство и позволяет аппаратуре переводить каждый адрес на лету с помощью таблиц страниц в памяти и небольшого кэша трансляций — TLB, устроенного в точности как кэши этой заметки.
