Сервис продаж хранит одну запись на заказ. Чтение заказа 106 должно сразу попадать на его узел. Отчёт за торговый день должен читать заказы этого дня. Ключ, удобный для одного запроса, может разнести данные второго по всему кластеру.

## Ключ определяет часть \{#a-key-determines-a-part\}

**Партиционирование** (partitioning) распределяет разные записи по разным логическим частям. Маршрутизация состоит из двух шагов. Функция определяет часть по ключу. Карта размещения говорит, какой узел сейчас её обслуживает. Один узел может обслуживать несколько частей. Перенос меняет размещение, а правило выбора части может остаться прежним. Репликация создаёт дополнительные копии части. К ней перейдём в следующем конспекте.

При **партиционировании по диапазонам** (range partitioning) каждая часть хранит непрерывный интервал упорядоченных ключей. Если ключ начинается с торговой даты, запрос за день может определить нужные интервалы. Полуоткрытые интервалы $[a,b)$ и $[b,c)$ делят границу и назначают ключ $b$ только один раз. Активная запись за текущий день может сосредоточить работу в одном интервале. Его разделение помогает, если запросы распределяются по нескольким новым интервалам. В исходном Bigtable ключи строк упорядочены лексикографически. Диапазоны ключей образуют части, которые называются tablets. ([Chang et al., §§2 и 5](#references))

При **хеш-партиционировании** (hash partitioning) вычисляем хеш ключа и назначаем часть по интервалу или корзине в пространстве хешей. Близкие номера заказов могут попасть в разные части, поэтому чтение диапазона номеров обычно охватывает больше частей. С неизменным хешем и актуальной картой точный номер заказа даёт один адрес. Равномерное распределение разных ключей помогает распределить записи. Оно не разделяет нагрузку на один особенно популярный ключ. ([DeCandia et al., §4.2](#references))

## Сохраним число логических слотов \{#keep-the-number-of-logical-slots-fixed\}

Возьмём двенадцать учебных записей одного размера с ключами от 0 до 11. Пусть $h(k)=k$, чтобы арифметика была видна. Для трёх узлов с номерами от 0 правило $h(k)\bmod 3$ даёт каждому по четыре записи. При переходе к $h(k)\bmod 4$ только ключи 0, 1 и 2 остаются у прежнего владельца. Остальные девять переезжают. При хешировании реальных ключей смена делителя тоже может изменить значительную часть назначений.

Оставим двенадцать логических слотов и зададим $\mathrm{slot}(k)=h(k)\bmod 12$. Сначала A, B и C получают по четыре слота. После подключения D отдадим ему слоты 9, 10 и 11. Каждый прежний владелец отдаёт один слот, и у всех четырёх узлов остаётся по три. В примере переезжают только три записи. Объём передачи равен сумме размеров переносимых слотов. В примере равное число слотов даёт равный объём, поскольку записи одинакового размера.

Redis Cluster использует фиксированное пространство хеш-слотов и переназначает слоты между узлами. Кольцо согласованного хеширования Dynamo устроено иначе. Узел может владеть несколькими диапазонами токенов, а изменение состава кластера переносит выбранные диапазоны. Обе схемы стремятся перемещать меньше данных, чем новое деление по числу узлов. Объём зависит от содержимого переносимых слотов или диапазонов. ([Redis Cluster Specification](#references), [DeCandia et al., §§4.2 и 6](#references))

## Перенесём владение при продолжающейся записи \{#move-ownership-while-writes-continue\}

Пусть слот 9 переезжает с A на D. A может обслуживать запросы, пока D копирует снимок и применяет последующие изменения. Перед переключением маршрутизации сервис должен определить, до какой записи дошёл D, и запретить A принимать записи по старому назначению. Простой вариант на короткое время приостанавливает запись в слот, переносит хвост изменений и публикует новую версию карты. Запрос со старой картой должен обновить её или перейти по перенаправлению. Если направить новые записи на D раньше, последующее чтение может пропустить изменение, ещё принятое A. Протокол Redis Cluster использует состояния миграции слота и перенаправления. Снимок и хвост изменений здесь приведены как отдельный пример. ([Redis Cluster Specification, Live reconfiguration](#references))

Для карты размещения нужна и мера нагрузки. Пусть 600 из 1000 записей идут по ключу одного магазина. Все 600 попадут в одну часть, если ключом служит идентификатор магазина. Перенос части сменит узел, сохранив концентрацию. Суффикс, вычисленный по номеру заказа, может разнести записи магазина по частям. Точечный запрос с номером заказа вычислит суффикс. Отчёт по магазину теперь должен посетить все суффиксы и объединить ответы. Ключ выбирают под запросы и их реальную, в том числе неравномерную, нагрузку.
