Аналитический кластер магазина может закончить отчёт и выключиться. Следующему кластеру всё ещё нужен тот же файл продаж. Хранилище должно сохранять данные независимо от процессов отчёта. Кроме того, нужно знать, какой сервис разрешает имя и какой передаёт байты.

## Имя файла разрешается в блоки \{#a-file-name-resolves-to-blocks\}

HDFS даёт клиентам пространство имён файлов и каталогов. **NameNode** ведёт пространство имён и карту размещения блоков на DataNode. **DataNode** хранят и выдают байты блоков. Клиент получает адреса от сервиса метаданных и читает напрямую с DataNode. Через NameNode байты файла не проходят. В исходной Google File System похожим образом разделены метаданные мастера и прямой доступ к серверам фрагментов. ([Hadoop 3.4.2, HDFS Architecture](#references), [Ghemawat et al., §2.3](#references))

Пусть файл занимает 300 МиБ, а размер блока настроен на 128 МиБ. При заполнении блоков до предела получаем 128, 128 и 44 МиБ. При трёх полных репликах каждого блока в хранилище находится $3\cdot300=900$ МиБ полезных данных файла. Для полного чтения нужна одна доступная копия каждого блока, поэтому передаётся 300 МиБ полезных данных. Дополнительные копии дают другой адрес, если одна недоступна. Реальное размещение зависит от топологии и политики репликации.

Планировщик, учитывающий HDFS, может поставить задачу рядом с репликой и сэкономить сетевой трафик. Локальность остаётся вариантом размещения задачи. Удалённые клиенты тоже читают файлы. Типичный режим — потоковое чтение больших файлов. Модель HDFS допускает дописывание и усечение. Произвольное изменение байтов по смещению требует другого контракта. ([Hadoop 3.4.2, HDFS Architecture](#references))

## Ключ объекта разрешается через API \{#an-object-key-resolves-through-an-api\}

В обычном бакете S3 **ключ** (key) адресует объект. В ключе могут быть косые черты, которые инструменты показывают как дерево каталогов. Клиент использует API хранилища и не запрашивает физические адреса внутренних копий объекта. Запрос `GET` может вернуть диапазон байтов конкретного объекта. Так можно прочитать хвост файла или выбранные фрагменты без скачивания всего объекта. Один запрос `GetObject` в Amazon S3 принимает один диапазон. ([Amazon S3 User Guide и API Reference](#references))

Пусть в том же объекте на 300 МиБ нужны два непересекающихся диапазона на 64 и 32 МиБ. Два запроса передадут 96 МиБ полезных данных. Если они используют общий канал с пределом 80 МиБ/с, одна передача займёт не меньше $96/80=1.2$ секунды. Полный объект займёт не меньше $300/80=3.75$ секунды. Накладные расходы запросов, конкуренция за канал и декодирование могут увеличить оба времени. Какие диапазоны нужны, сообщает формат файла. Объектный сервис видит ключи и байты.

В Amazon S3 успешно записанный объект виден последующему чтению того же ключа. Гарантия относится к операции с объектом. Если писатель меняет два ключа по очереди, читатель между операциями может увидеть один новый и один старый объект. Строгое чтение каждого ключа не даёт атомарного обновления обоих. В одном из следующих конспектов опубликуем для группы файлов одну версию. ([Amazon S3 User Guide, Data consistency model](#references))

## Масштабируем хранение и вычисления отдельно \{#let-storage-and-compute-scale-separately\}

Исполнители могут запуститься, прочитать неизменяемые входы, записать результат и остановиться. Независимое хранилище позволяет заменить исполнителей без предварительного копирования всех входов на новые машины. Совместное размещение хранилища и задач использует локальность. Отдельный вычислительный кластер масштабируется независимо, а удалённые чтения используют сетевой канал и могут увеличивать стоимость запросов. Сохранность файла определяется хранилищем и его политикой удержания данных, даже когда все исполнители остановлены.
