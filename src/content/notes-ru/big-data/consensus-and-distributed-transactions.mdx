Магазину нужны две гарантии. Копии базы остатков должны сохранять одну последовательность зафиксированных операций. Касса с отдельной базой платежей должна принять единое решение по остатку и платежу. Первая задача относится к копиям одной машины состояний. Во второй участники выполняют разную работу.

## Реплики согласуют порядок команд \{#replicas-agree-on-an-order-of-commands\}

**Консенсус** (consensus) позволяет узлам принять одно значение при некоторых отказах. Реплицированный журнал последовательно согласует команды. Назовём три реплики Raft A, B и C. Для большинства нужны два узла. Два большинства пересекаются, потому что для двух непересекающихся пар понадобилось бы четыре узла. Raft использует пересечение вместе с термами, правилами совпадения журналов и проверкой журнала кандидата при голосовании. Одного пересечения недостаточно для реализации протокола. [Ongaro и Ousterhout, 2014, §§5.2–5.4](#references)

Пусть A руководит в терме 8 и сохраняет команду новой брони в устойчивом хранилище в этом терме. B сохраняет запись. У A есть запись на двух репликах с учётом себя. По правилу текущего терма лидер может продвинуть индекс фиксации. Он применяет команду перед ответом клиенту. Если A станет недоступен, будущий избранный лидер должен содержать зафиксированную запись. Один изолированный узел не может самостоятельно зафиксировать другую команду. Подсчёт копий записи из более старого терма не даёт того же вывода. [Ongaro и Ousterhout, 2014, §§5.3–5.4](#references)

## Каждый участник должен быть готов к фиксации \{#participants-have-to-be-able-to-commit\}

У кассовой транзакции могут быть участник для остатков и участник для платежей. У них разные ограничения. Большинство некоторой группы не может подтвердить платёж, который платёжная база не принимает. Правило фиксации требует готовности каждого участника.

В **двухфазной фиксации** (two-phase commit, 2PC) координатор сначала просит всех подготовиться. Участник с ответом «да» сохраняет факт готовности и удерживает ресурсы для последующей фиксации. Если все ответили «да», координатор может надёжно записать решение о фиксации и сообщить его каждому. Неготовность участника требует отмены. Участники выполняют окончательное решение, когда узнают его. [Gray и Lamport, 2006, §3](#references)

Пусть база остатков ответила «да» и потеряла связь с координатором. Координатор мог записать фиксацию и сообщить её базе платежей. Он мог и остановиться до записи решения. Подготовленный участник не может безопасно выбрать отмену по одному тайм-ауту. Нужно узнать решение или воспользоваться правилами восстановления протокола. Это блокирующий сценарий классической 2PC. В PostgreSQL `PREPARE TRANSACTION` сохраняет подготовленную транзакцию для внешнего координатора, а она может продолжать удерживать блокировки. [Gray и Lamport, 2006, §3](#references) [PostgreSQL 18, PREPARE TRANSACTION](#references)

## Совмещаем механизмы на нужной границе \{#combine-mechanisms-at-the-correct-boundary\}

Сервис решений на основе консенсуса может пережить часть отказов координатора. Для фиксации ему всё равно нужна готовность каждого участника. Сама 2PC не ведёт реплицированный журнал отдельной базы. Гарантии совмещаются, когда у каждого протокола есть заданная роль и все записи участников ему следуют. Email, который отправил внешний сервис, находится за границей транзакции базы, если сервис не поддерживает отдельно согласованное действие.
