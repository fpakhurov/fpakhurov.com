Сумма заказа изменилась с 700 до 900 копеек. Во вчерашней копии осталось 700. Если просто добавить новую строку, один факт получит две суммы, и отчёт может посчитать 1600. При загрузке нужно выбрать границу входных данных и определить, как приёмник применяет записи внутри неё.

## Копируем состояние или переходим между состояниями \{#copy-one-state-or-move-between-states\}

**Полная загрузка** (full load) читает весь выбранный вход. Для таблицы текущих заказов можно собрать новую копию и опубликовать её, когда все строки доступны. Если заказа в источнике уже нет, в новой копии его тоже не будет. Это правильно, если отсутствие в полном входе означает удаление. Неполную выгрузку нельзя использовать как полную замену.

Несколько независимых чтений из меняющейся базы могут увидеть разные зафиксированные состояния. Транзакция PostgreSQL на уровне Repeatable Read может использовать один снимок для нескольких чтений. Для файлов фиксируем манифест неизменяемых объектов данного запуска. Для API с разбиением на страницы проверяем, удерживает ли курсор снимок или лишь указывает позицию в изменяющихся данных. Один и тот же номер страницы не задаёт устойчивую границу выгрузки. [PostgreSQL 18, §13.2.2](#references)

**Инкрементальная загрузка** (incremental load) читает часть данных после сохранённой позиции источника. Она объединяет изменившиеся строки с имеющейся копией по устойчивому ключу. Повтор версии может оставлять те же значения, если приёмник заменяет строку по ключу и версии. Прибавление может учесть ту же версию дважды. В расчётном примере полная загрузка миллиона строк по 120 байтов требует 120 МБ данных строк. Для пяти тысяч изменений той же ширины нужны 600 кБ. Разница в 200 раз без учёта индексов, метаданных, сканирования и слияния.

## Сохраняем обе границы \{#save-both-bounds\}

Пусть источник использует упорядоченный курсор `(updated_at, order_id)`. Сохранённый курсор — `(10:00, 101)`, следующая загрузка читает до `(10:02, 103)` включительно. Сравнение только времени через `updated_at > 10:00` потеряло бы заказ 102. Сравниваем пары лексикографически. Идентификатор заказа разрешает равенство времени. Это курсор загрузки. У водяного знака по времени события, который появится позже, другая задача. [Microsoft, Incremental copy](#references) [PostgreSQL 18, §9.25.5](#references)

<DeliveryTrace example="load" />

```sql
SELECT order_id
FROM (VALUES (TIME '10:00', 101),
             (TIME '10:00', 102),
             (TIME '10:02', 103),
             (TIME '10:03', 104)) AS changes(updated_at, order_id)
WHERE (updated_at, order_id) > (TIME '10:00', 101)
  AND (updated_at, order_id) <= (TIME '10:02', 103)
ORDER BY updated_at, order_id;
```

Запрос возвращает 102 и 103. Курсор продвигается после того, как изменения приёмника стали долговечными. Если сбой произойдёт после записи изменений, но до обновления курсора, загрузка может увидеть их снова. Замена по версии задаёт эффект такого повтора. Продвижение курсора до записи могло бы пропустить строки, которых в приёмнике ещё нет.

## Чего курсор строк не видит \{#what-a-row-cursor-cannot-see\}

Пары достаточно, если новые видимые изменения не могут появиться позади сохранённого курсора. Пусть транзакция записывает обновление с отметкой 09:59, но фиксируется после того, как загрузка сохранила 10:02. В снимок загрузки она не попала, а в следующий раз окажется ниже нижней границы. Разрешение равенства не устраняет проблему порядка. Перекрывающиеся интервалы выгрузки вместе с устранением повторов могут покрыть известную задержку. Без верхней границы задержки изменения всё ещё можно пропустить.

Опрос оставшихся строк также не видит обычное физическое удаление. Источник может отдавать записи об удалениях, хранить признак мягкого удаления или предоставить согласованный снимок и журнал более поздних изменений. В последнем варианте позиция относится к зафиксированной истории источника, а не к отметке времени в строке. [Debezium, PostgreSQL connector](#references)

Извлечение, преобразование и загрузка — отдельные этапы. В ETL преобразование предшествует загрузке в аналитический приёмник. В ELT необработанный вход сначала поступает туда, а преобразование выполняется там. В обоих случаях публикуем результат только для определённого и восстанавливаемого входа.
