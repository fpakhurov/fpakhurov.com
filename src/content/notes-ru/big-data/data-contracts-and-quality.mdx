Файл дневных продаж читается. Идентификаторы и суммы целочисленные. Но первая продажа записана дважды, в другой строке две единицы по 450 копеек стоят 990 копеек, а один ожидаемый магазин отсутствует. Схема, которая задаёт только столбцы и типы, принимает этот файл.

## Задаём единицу данных \{#state-the-unit-of-the-data\}

**Контракт данных** (data contract) фиксирует, что поставщик передаёт и на что могут рассчитывать потребители. Здесь строка представляет позицию заказа, а идентификатор заказа уникален среди магазинов. Строку определяет пара `(order_id, line_no)`. Контракт задаёт положительное количество, неотрицательную цену, сумму как произведение количества на цену и запись о завершении дня от каждого ожидаемого магазина. Цены указаны в копейках. Переход на рубли меняет контракт, даже если тип остаётся целочисленным. Open Data Contract Standard выделяет разделы схемы, качества данных и уровня обслуживания. [ODCS, The basics of a data contract](#references)

## Разбираем нарушения \{#work-through-the-violations\}

Возьмём четыре строки. Правило суммы сравнивает поля внутри строки. Правило ключа сравнивает строки между собой. Для поиска отсутствующего магазина нужна отдельная отметка о завершении от источника. По одним продажам магазин без продаж бывает неотличим от магазина, который ещё не прислал данные.

```sql
WITH feed(order_id, line_no, qty, unit_cents, amount_cents) AS (
    VALUES (201, 1, 2, 350, 700),
           (201, 1, 2, 350, 700),
           (202, 1, 1, 600, 600),
           (203, 1, 2, 450, 990)
)
SELECT order_id, line_no, 'duplicate key' AS issue
FROM feed
GROUP BY order_id, line_no
HAVING COUNT(*) > 1
UNION ALL
SELECT order_id, line_no, 'amount mismatch'
FROM feed
WHERE amount_cents IS DISTINCT FROM qty * unit_cents
ORDER BY order_id, line_no, issue;
```

Проверка ключа возвращает `201/1`. Проверка суммы возвращает `203/1`, потому что $2 \cdot 450 = 900$. Проверки показывают нарушенные правила. Из них нельзя узнать, неверно ли в источнике записали сумму или количество. Если убрать один дубликат и подставить 900, получится $700 + 600 + 900 = 2200$ копеек. Это только возможное исправление. Поставщик должен подтвердить правильную запись, а проверка полноты остаётся в силе. Модель табличных данных W3C аналогично разделяет чтение ячеек и проверку объявленных ключей. [W3C, Validating Tables](#references)

## Проверяем совместимость в обе стороны \{#check-compatibility-in-both-directions\}

Пусть новая версия записи Avro добавляет `terminal_id`. Старый читатель может пропустить неизвестное поле. Новому читателю старого файла нужно значение по умолчанию для добавленного поля, иначе запись не прочитается. Это разные направления, потому что у схем записи и чтения разные роли. Значение по умолчанию «неизвестно» сохраняет возможность чтения. Если новому отчёту нужен терминал для атрибуции, это значение всё равно нарушает его смысловое требование. [Avro 1.12.0, Schema Resolution](#references)

При провале проверки публикация может оставить видимым прежний результат за день. Записываем версию входа, правило и ключи нарушений, чтобы поставщик исправил источник или явно изменил контракт. Успех означает, что объявленные проверки прошли на проверенных данных. Правила без проверки, в том числе факты, которых поставщик не передал, остаются предположениями.

## Источники \{#references\}

1. Bitol. [Open Data Contract Standard](https://github.com/bitol-io/open-data-contract-standard). Описывает соглашение поставщика и потребителя, разделы схемы, качества и уровня обслуживания.
2. W3C. [Model for Tabular Data and Metadata on the Web](https://www.w3.org/TR/tabular-data-model/#validating-tables). Рекомендация, 2015. Раздел Validating Tables описывает проверку повторов первичного ключа в прочитанных данных.
3. Apache Avro. [Specification 1.12.0, Schema Resolution](https://avro.apache.org/docs/1.12.0/specification/#schema-resolution). Задаёт сопоставление схем чтения и записи при добавленных и отсутствующих полях.
