В отчёте 600 ГБ позиций, размещённых на четырёх исполнителях. SQL по-прежнему ссылается на одну таблицу. Чтобы выполнить запрос, СУБД решает, какую часть плана запускать рядом с каждым набором строк и какие результаты передавать по сети.

## Запускаем части плана рядом с данными \{#dispatch-a-plan-beside-the-data\}

В системе **без общих ресурсов** (shared nothing) у каждого узла свои процессоры, память и хранилище. Узлы обмениваются сообщениями, чтобы согласовать работу. В системе **массовой параллельной обработки** (MPP) исполнители запускают операторы одного запроса над разными частями входа. В Greenplum клиент отправляет SQL координатору. Документация Greenplum 6 называет эту роль master. Процессы сегментов выполняют фрагменты плана над своими частями данных. Сегмент — экземпляр базы, на одном сервере могут работать несколько сегментов. В модели используем один сегмент на исполнителя. ([DeWitt и Gray, 1992, §3](#references); [Greenplum 6, Query processing](#references))

```sql
SELECT store_id,
       SUM(quantity * unit_price_cents) AS revenue_cents
FROM order_lines
GROUP BY store_id
ORDER BY store_id;
```

Предположим, все строки одного магазина размещены у одного исполнителя, четыре части не пересекаются, а все читают выбранный снимок. Каждый сегмент читает свои строки и считает полные суммы по своим магазинам. В [модели с 600 ГБ](/ru/notes/big-data/beyond-one-machine) четыре равные части дают по 150 ГБ чтения на исполнителя. Координатору не нужно получать эти строки. Если отчёт охватывает 500 магазинов, исполнители могут отправить всего 500 строк с суммами. Ответ всё равно нужно упорядочить по магазину. Для этого подходит итоговая сортировка или слияние упорядоченных потоков.

## Перемещаем данные к следующему оператору \{#move-data-where-the-next-operator-needs-it\}

**Сбор** (gather) объединяет выходы исполнителей у одного получателя. **Обмен** (exchange) передаёт строки между частями распределённого плана. Greenplum показывает перемещения операторами Motion. Перераспределение направляет строки получателям по новому ключу. Широковещательная передача даёт копию входа каждому получателю. Сбор удобен для небольшого конечного ответа. Перераспределение позволяет следующим операторам продолжать работу на нескольких узлах. ([Greenplum 6, Query processing](#references))

Такое разделение есть и в других реализациях. Движок таблиц Distributed в ClickHouse может отправить работу удалённым шардам, агрегировать там и передать промежуточные состояния инициатору запроса. Названия операторов и правила оптимизации зависят от СУБД. Фильтр по известному ключу распределения иногда направляет запрос на один шард. Если вход запроса охватывает все шарды, нужны результаты каждого. ([ClickHouse, Distributed table engine](#references))

План был локальным для магазина, потому что один исполнитель хранил все его строки. Если в файлах каждого дня встречаются одни и те же магазины, исполнитель может посчитать только частичную сумму. В конспекте [«Распределённая агрегация и shuffle»](/ru/notes/big-data/distributed-aggregation) разберём, где должны встретиться частичные результаты и сколько данных нужно переместить.
