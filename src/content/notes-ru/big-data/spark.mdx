Магазину нужны прежние суммы и второй отчёт по тому же входу. Цепочка отдельных заданий MapReduce может записывать каждый промежуточный результат перед продолжением. Spark описывает преобразования зависимостями и может выполнить несколько локальных шагов вместе до обмена.

## Описываем работу до запуска \{#describe-work-before-starting-it\}

**RDD** — коллекция с партициями, которую Spark может пересчитать по зависимостям. **Преобразование** (transformation) вроде `map` или `filter` задаёт новую коллекцию. **Действие** (action) вроде `collect` запрашивает результат и запускает нужную работу. Драйвер координирует приложение. Исполнители запускают задачи обработки партиций. ([Zaharia и др., 2012, §§2–3](#references); [Spark 3.5.8, RDD Programming Guide](#references))

Пусть есть контекст Spark `sc`. Пример использует 12 учебных сумм из [распределённой агрегации](/ru/notes/big-data/distributed-aggregation#combine-values-before-sending). `parallelize` превращает маленький список в драйвере в распределённую коллекцию. В рабочем задании партиции обычно читаются из хранилища.

```python
from operator import add

raw = [
    (1, 100), (1, 200), (2, 50),
    (1, 150), (2, 70), (2, 30),
    (1, 100), (1, 50), (2, 200),
    (1, 200), (2, 120), (2, 80),
]
sales = sc.parallelize(raw, 4)
positive = sales.filter(lambda row: row[1] > 0)
totals = positive.reduceByKey(add, numPartitions=2)
print(sorted(totals.collect()))
```

Ожидаемый результат — `[(1, 800), (2, 550)]`. Сортируем две полученные пары только для определённого порядка показа. Большой результат лучше записать или агрегировать в кластере, чтобы он не занял память драйвера. ([Spark 3.5.8, RDD Programming Guide](#references))

## Находим границу этапов \{#find-the-boundary-between-stages\}

При **узкой зависимости** (narrow dependency) родительская партиция нужна не более чем одной дочерней. Здесь фильтрации нужны только строки её партиции. Фильтр может выполниться в задаче, которая готовит результат для shuffle. Свёртке по ключу нужны суммы нескольких входных партиций. Spark разделяет выполнение по границе shuffle. Задачи с одной стороны записывают части обмена, а задачи с другой читают нужные блоки. В примере четыре входные партиции дают две выходные. ([Zaharia и др., 2012, §§3.1 и 5](#references); [Spark 3.5.8, Shuffle operations](#references))

Граф зависимостей партиций называют **lineage**. Если потеряется партиция кэша, Spark может пересчитать её по доступным родителям. При потере результата shuffle может потребоваться повторить предшествующую задачу. Для этого вход должен оставаться доступным, а преобразования должны допускать повтор. Повтор задачи может повторить внешнее действие. Lineage описывает восстановление данных и не создаёт транзакцию с внешним сервисом.

Пример использует функции RDD, чтобы явно показать зависимости. Spark SQL и DataFrames также строят логические и физические планы. Оптимизатор может менять операторы до назначения задач. Тот же SQL может дать другой граф выполнения, чем пример с RDD. ([Armbrust и др., 2015, §§3–4](#references))
