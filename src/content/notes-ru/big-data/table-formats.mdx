Таблица продаж содержит файлы A и B с 600 и 400 строками. Уплотнение записывает C с теми же 1000 строками. Все три файла могут существовать одновременно. Читатель, который перечисляет и открывает все файлы префикса, увидит старые и новые копии вместе. Для таблицы нужно определить принадлежность независимо от существования файла.

## Разрешим имя таблицы в один снимок \{#resolve-a-table-name-to-one-snapshot\}

**Каталог** (catalog) по имени таблицы находит её текущие метаданные. В Iceberg они содержат схему, спецификации партиционирования и снимки. **Снимок** (snapshot) определяет состояние таблицы. В версиях формата Iceberg 1–3 снимок ссылается на список манифестов, а манифесты учитывают файлы данных и, если версия поддерживает, файлы удалений. Значения партиций и метрики файлов позволяют планировщику пропускать файлы без возможных совпадений. Читатель выбирает один снимок, проходит по метаданным и использует набор файлов этого снимка. Формат файла затем декодирует каждый файл. ([Apache Iceberg, Table Spec](#references))

Обозначим учебные снимки через S10, S11 и S12. Это имена в хронологическом порядке примера, независимо от назначения идентификаторов в Iceberg. S10 содержит A и B и даёт 1000 строк. Писатель может создать кандидат C без изменения S10. Уже начатое чтение S10 может продолжать использовать A и B, пока файлы удерживаются.

## Зафиксируем изменение относительно прочитанного состояния \{#commit-a-change-against-the-state-it-read\}

Писатель подготавливает данные и метаданные до публикации. Каталог Iceberg с metastore может при фиксации проверить, что текущий указатель на метаданные совпадает с исходным указателем писателя, и атомарно заменить его новым. Условное обновление служит границей публикации. Успешная загрузка C относится только к подготовке. ([Apache Iceberg, Optimistic Concurrency и Metastore Tables](#references))

Пусть второй писатель добавляет файл D с 50 новыми строками и фиксирует S11 до публикации уплотнения. S11 содержит A, B и D. Попытка заменить указатель с S10 теперь не проходит. Писатель уплотнения перечитывает текущее состояние, проверяет, что A и B всё ещё входят в таблицу и что проверки переписывания выполнены, затем предлагает новое изменение. S12 содержит C и D. В нём тоже 1050 строк. Если бы другое изменение убрало A, старый план нельзя было бы применять без проверки.

Проверка защищает конкурентные изменения. Безусловное обновление указателя только на C потеряло бы D. Чтение всех файлов A, B, C и D по префиксу посчитало бы $600+400+1000+50=2050$ строк вместо 1050. Снимок определяет набор файлов, даже когда хранилище верно перечисляет каждый объект.

После неудачной фиксации могут остаться файлы без ссылок. Файл, удалённый из новейшего снимка, ещё может быть нужен удерживаемому снимку. Удаление старых снимков и очистка файлов без ссылок — разные операции обслуживания. Их окно удержания учитывает читателей и выполняющиеся записи. Описанная гарантия относится к одной таблице. Атомарная замена её указателя не координирует запись в несколько таблиц или во внешний сервис. ([Apache Iceberg, Table Spec и Maintenance](#references))

## Сохраним идентичность поля при переименовании \{#keep-field-identity-through-a-rename\}

Пусть у поля `amount_cents` идентификатор 17 и мы переименовываем его в `net_cents`. При эволюции схемы Iceberg переименованное поле сохраняет идентификатор. Читатель сопоставляет старый файл с новым именем поля. Если позже создать новое поле со старым именем, оно получит новый идентификатор. Иначе повторное имя могло бы вернуть старые значения с другим смыслом. Переименование меняет имя, а смена единиц или бизнес-смысла требует явной миграции данных или нового поля. Iceberg также хранит старые спецификации партиционирования для старых файлов и может писать новые по новой схеме размещения. Планировщик читает файлы согласно записанной спецификации. ([Apache Iceberg 1.10.0, Evolution](#references))

Представление метаданных зависит от табличного формата. Delta Lake описывает упорядоченный журнал действий над файлами и метаданными с контрольными точками. Hudi представляет шкалу действий в состояниях requested, inflight и completed. Во всех трёх примерах читатель сначала разрешает зафиксированные метаданные и затем выбирает файлы. Протоколы публикации и конкуренции при этом различаются. ([Armbrust et al., §3](#references), [Apache Hudi, Timeline](#references))
