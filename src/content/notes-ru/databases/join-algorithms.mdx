Отчёту нужна категория каталога рядом с каждой позицией заказа. [Внутреннее соединение](/ru/notes/sql/inner-joins#match-rows-by-a-shared-field) определяет пары. СУБД может искать их перебором, через хеш-таблицу или проходом по упорядоченным входам. В результате по-прежнему шесть строк.

## Повторяем поиск для каждой внешней строки \{#repeat-a-lookup-for-each-outer-row\}

Возьмём шесть позиций заказа и четыре записи каталога из примера SQL. **Соединение вложенными циклами** (nested-loop join) читает одну внешнюю строку, находит все её совпадения на внутренней стороне, затем переходит к следующей внешней строке. Если внутренний цикл каждый раз просматривает весь каталог, проверяется $6 \cdot 4 = 24$ пары. Равенство выполняется для шести.

Внутренний шаг может искать `catalogue.product` по индексу. Получится шесть поисков, каждый с максимум одним совпадением благодаря уникальному ключу каталога. Один поиск может затронуть несколько страниц и потребовать чтения записи. Шесть поисков и 24 сравнения считают разные операции, поэтому сами числа не сравнивают время. Циклы с индексом на внутренней стороне полезны, когда до соединения доходит мало внешних строк. SQLite выполняет соединения вложенными проходами и показывает индексный поиск или просмотр для каждого цикла. ([PostgreSQL 18, §14.1](#references); [SQLite, §1.1](#references))

## Строим временную таблицу поиска \{#build-a-temporary-lookup-table\}

**Хеш-соединение** (hash join) по равенству сначала строит хеш-таблицу по одному входу, затем проверяет её по другому. Здесь заносим четыре строки каталога с ключом `product`. Каждая из шести позиций ищет свой товар. Совпадение хеша даёт кандидата, у которого ещё нужно проверить равенство. Если одному ключу соответствуют несколько строк в таблице, все они могут попасть в результат.

Пусть хеш распределяет ключи достаточно равномерно и вход для построения помещается в память. Обозначим через $n$ и $m$ число проверяемых и сохранённых строк, а через $o$ — число строк результата. Ожидаемая работа равна $O(n+m+o)$. Память растёт с числом и шириной сохранённых строк. Здесь четыре строки для построения, шесть обращений и шесть результатов. Большой вход может потребовать разбиения обеих сторон и записи временных данных. При перекосе одна часть может не поместиться, даже если средняя часть мала. ([PostgreSQL 18, §14.1](#references); [Microsoft, Hash joins](#references))

## Продвигаемся по упорядоченным ключам \{#advance-through-ordered-keys\}

**Соединение слиянием** (merge join) может использовать входы, упорядоченные по ключу соединения. Сравниваем текущие ключи. Если один меньше, продвигаем его вход. Этот ключ не может совпасть с текущим или последующими ключами с другой стороны. При равенстве соединяем серии строк с одним ключом и продолжаем. Здесь получается одна пара для какао, две для кофе и три для чая. Ключ мяты в каталоге находится между кофе и чаем, а на левом входе для него нет пары.

При повторах с двух сторон число пар равно произведению размеров серий. Для трёх позиций чая и двух предложений по-прежнему нужно выдать шесть пар. Оператор слияния должен уметь удерживать или повторно читать одну совпавшую серию. На упорядоченных входах работа растёт с числом прочитанных строк и выданных пар. Если СУБД сначала сортирует входы, добавляется стоимость сортировок, которые могут использовать временное хранилище. Подходящий порядок может дать индекс. ([PostgreSQL 18, §14.1](#references); [Microsoft, Merge joins](#references))

`INNER JOIN` задаёт условие совпадения. `Nested Loop`, `Hash Join` и `Merge Join` — типы физических узлов, которые могут выполнить это соединение в PostgreSQL. Выбор зависит от числа и ширины строк, индексов, порядка входов и стоимости выдачи всех совпавших пар.
