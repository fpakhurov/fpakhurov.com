В заказе 106 две позиции с одинаковой упаковкой чая на 50 г. В одной записана цена 350 копеек, в другой — 300. Для печати чека нужны оба факта о позициях и один факт из каталога, который даёт код упаковки. Реляционный запрос объединяет эти факты, сохраняя различие между позициями.

## Схема описывает допустимые кортежи \{#a-schema-describes-allowed-tuples\}

**Схема отношения** (relation schema) задаёт имена атрибутов и домен каждого из них. **Домен** описывает возможные значения, например целые количества или текстовые коды каталога. **Кортеж** сопоставляет каждому атрибуту одно значение. **Экземпляр отношения** (relation instance) — множество кортежей заданной схемы. Схема может оставаться прежней, пока меняется экземпляр. У кортежей нет собственного порядка, а множество содержит не больше одной копии каждого кортежа. ([Codd, 1970, §1.3](#references), [Pavlo, 2025, §4](#references))

Возьмём схему из [примера с заказами](/ru/notes/databases/data-modeling#put-the-rules-into-a-schema). Обозначим отношение позиций через $L$, а отношение товаров каталога через $P$. В алгебре ниже $o,n,p,q,c$ обозначают идентификатор заказа, номер позиции, идентификатор товара, количество и согласованную цену единицы в копейках. В каталоге также есть $p$, а $k$ обозначает код товара. Это имена атрибутов, поэтому $p$ означает идентификатор товара и на другой позиции в другом отношении.

| Отношение | Используемые атрибуты |
| --- | --- |
| $L$ | $(o,n,p,q,c)$ |
| $P$ | $(p,k)$ |

Две позиции заказа 106 имеют вид $(106,1,7,1,350)$ и $(106,2,7,1,300)$. В начальном состоянии у товара 7 код `TEA50`. Кортеж хранит один факт о позиции, даже когда в другой позиции указан тот же товар.

## Ключи и ссылки ограничивают экземпляры \{#keys-and-references-constrain-instances\}

**Суперключ** (superkey) — набор атрибутов, значения которых различают кортежи в каждом допустимом экземпляре. **Кандидатный ключ** (candidate key) — суперключ, который теряет эту гарантию после удаления любого атрибута. Для $L$ таким ключом служит $(o,n)$. В заказе 106 две позиции, поэтому $o$ сам по себе повторяется. У заказов 101 и 106 есть первая позиция, поэтому $n$ сам по себе тоже повторяется. Добавление количества даёт суперключ, который уже не минимален. В каталоге $p$ выбран первичным ключом, а $k$ служит ещё одним кандидатным ключом, поскольку каждый текущий код уникален и заполнен. ([Pavlo, 2025, §5](#references), [PostgreSQL 18, §§5.5.3–5.5.4](#references))

**Внешний ключ** (foreign key) ограничивает ссылки между экземплярами. Каждый идентификатор товара из $L$ должен встречаться среди идентификаторов товаров в $P$. В обозначениях множеств это $\pi_p(L)\subseteq\pi_p(P)$, где $\pi$ оставляет указанные атрибуты. Несколько позиций могут ссылаться на один товар. В каталоге могут быть товары без продаж. В примере SQL столбец `product_id` имеет ограничение `NOT NULL`, поэтому для каждой позиции внешний ключ требует совпадение в каталоге. Если внешний ключ допускает `NULL`, SQL может освободить такую строку от обычного требования о совпадении. ([PostgreSQL 18, §5.5.5](#references))

## Соберём чек из простых операций \{#build-a-receipt-from-smaller-operations\}

**Отбор** (selection) $\sigma$ оставляет кортежи, которые удовлетворяют предикату. $\sigma_{o=106}(L)$ оставляет две позиции заказа 106. **Проекция** (projection) $\pi$ оставляет перечисленные атрибуты и убирает повторы, потому что её результат — множество. **Соединение** (join) $\bowtie$ объединяет совпадающие кортежи. Здесь естественное соединение сопоставляет их по единственному общему атрибуту $p$. Чек можно выразить как композицию. ([Codd, 1970, §§2.1.2–2.1.3](#references), [Pavlo, 2025, §6](#references))

$$
\pi_{n,k,c}\bigl(\sigma_{o=106}(L)\bowtie P\bigr).
$$

У каждой отобранной позиции ровно одно совпадение в каталоге, поскольку ссылка обязательна, а $p$ служит ключом каталога. Проекция на номер позиции, код и цену единицы даёт два кортежа чека. Номера позиций различают эти кортежи.

Для запуска SQL ниже создадим заказы и каталог из [предыдущего примера](/ru/notes/databases/data-modeling#put-the-rules-into-a-schema) до необязательного исправления кода. Запрос явно называет общий столбец соединения.

```sql
SELECT l.line_no, c.catalog_code, l.unit_price_cents
FROM order_lines AS l
JOIN catalog_items AS c USING (product_id)
WHERE l.order_id = 106
ORDER BY l.line_no;
```

| line_no | catalog_code | unit_price_cents |
| --- | --- | --- |
| 1 | TEA50 | 350 |
| 2 | TEA50 | 300 |

Декартово произведение соединило бы обе отобранные позиции со всеми тремя товарами каталога и дало шесть пар. Равенство по $p$ оставляет две. Отбор, проекция и соединение возвращают отношения, поэтому результат каждой операции может стать входом следующей.

## Чем SQL отличается от модели \{#where-sql-differs-from-the-model\}

В проекции $\pi_p(\sigma_{o=106}(L))$ один кортеж $(7)$. Обычный `SELECT product_id` по двум позициям возвращает две строки со значением 7. SQL сохраняет эти вхождения по умолчанию. Добавим `DISTINCT`, чтобы получить проекцию как множество.

```sql
SELECT DISTINCT product_id
FROM order_lines
WHERE order_id = 106;
```

В этих примерах отношения содержат обычные значения, поэтому проверка вроде $o=106$ даёт истину или ложь. В SQL есть маркер `NULL` и неизвестный результат для многих сравнений. SQL также позволяет явно задать порядок вывода. Алгебра здесь описывает принадлежность кортежей результату, а в запросах SQL нужно учитывать повторы и пропуски. См. [типы и NULL](/ru/notes/sql/types-and-null) и [дубликаты и порядок строк](/ru/notes/sql/duplicates-and-order). ([PostgreSQL 18, SELECT](#references))
