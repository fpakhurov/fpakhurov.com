Магазин теперь учитывает оплаты заказов из [первой заметки SQL](/ru/notes/sql/tables-and-queries). Две кассовые программы почти одновременно принимают разные оплаты. Обе сообщают об успехе. В общем файле остаётся только вторая оплата. Как целый и читаемый файл потерял завершённую операцию?

## Два процесса читают один файл \{#two-writers-read-the-same-file\}

Храним по одной строке на оплату в `payments.csv`. В строке есть номер оплаты, номер заказа и сумма в целых копейках. По данным `order_lines`, заказ 101 стоит 1300 копеек по двум позициям на 700 и 600. Заказ 103 стоит 1550 копеек по позициям на 1200 и 350. Касса A записывает оплату 501 для заказа 101. Касса B записывает оплату 502 для заказа 103. В начале в файле есть заголовок и нет строк с оплатами.

Каждый процесс читает текущий файл в память, добавляет оплату в свою копию, записывает полную новую версию во временный файл в той же папке и заменяет `payments.csv`. Если один процесс завершает каждую операцию перед началом следующей, при втором чтении в файле уже есть первая оплата. Успешный вызов `os.replace` в пределах одной файловой системы за один шаг заменяет файл по общему имени на готовую новую версию. ([Python 3.14, `os.replace`](#references))

<FileReplacement />

На схеме оба чтения происходят до первой замены. A публикует файл со строкой 501. B публикует файл со строкой 502, составленный из прочитанной ранее версии без оплат. Запись об оплате A исчезает. В файле остаётся 1550 копеек из ожидаемых 2850. Все операции могут завершиться успешно, а каждая версия файла может быть корректным CSV. Обновление теряется, потому что B строит замену по устаревшим данным.

Один процесс может закончить чтение, изменение и замену файла перед следующим запросом. Несколько процессов могут пользоваться одной блокировкой, если каждый захватывает её эксклюзивно на весь этот цикл. Блокировка одной только замены всё ещё допускает два ранних чтения. Когда несколько программ меняют общие записи, координация становится частью интерфейса хранения. [Pavlo, 2025, §2](#references)

## Общими записями управляет одна система \{#one-system-owns-the-shared-records\}

**База данных** — организованная совокупность связанных данных. **Система управления базами данных**, или СУБД, — программа, через которую другие программы описывают, читают и меняют данные. Магазин может хранить записи в файлах и реализовать координацию самостоятельно. При использовании СУБД программы отправляют операции над именованными таблицами, а общими записями управляет эта система. ([Pavlo, 2025, §§1–3](#references))

Например, касса A может запросить вставку оплаты 501, а касса B — вставку оплаты 502. В каждом запросе передаётся одна новая строка `payments`. Вставки разных допустимых строк могут обе завершиться успешно, и в таблице останутся обе оплаты. Приложение задаёт изменение на уровне строки. СУБД вносит изменение в хранилище.

В PostgreSQL **клиент** — программа, которая отправляет запросы и получает результаты. Клиентом может быть кассовый сервис, программа для отчётов или консольная утилита `psql`. **Сервер** принимает их подключения и выполняет запросы к базе. Клиент и сервер могут работать на одной машине или обмениваться сообщениями по сети. Клиент передаёт SQL и значения через подключение. Сервер работает с файлами базы, которой управляет. ([PostgreSQL 18, §1.2](#references))

<DatabaseSessions />

**Подключение** передаёт сообщения между клиентом и сервером. **Сеанс** — контекст клиента на сервере в рамках этого подключения. Например, сервер хранит сведения о том, начата ли в сеансе транзакция. Два сеанса могут работать с одними таблицами и выполнять разные транзакции. После завершения одной транзакции в том же сеансе можно начать другую. Зафиксированные строки обычных таблиц доступны следующим сеансам после закрытия клиентского подключения. ([PostgreSQL 18, §§1.2 и 3.4](#references))

## Когда для оплаты нужны две записи \{#when-a-payment-takes-two-writes\}

Магазин также хранит статус заказа `open` или `paid`. Касса сначала вставляет оплату, затем меняет статус заказа на `paid`. В файловом варианте эти шаги заменяют `payments.csv` и `orders.csv`. Если отчёт прочитает оба файла между заменами, он получит новую оплату и старый статус. Если процесс кассы завершится после первой замены, та же пара файлов достанется следующему читателю. У каждого файла свой момент публикации.

Нужно, чтобы оба изменения вступали в силу вместе. **Транзакция** объединяет операции в одно целое. В PostgreSQL команда `BEGIN` открывает блок транзакции, `COMMIT` фиксирует изменения, а `ROLLBACK` их отменяет. Оба изменения выполняются в одном сеансе и в одной транзакции. Команды, отправленные по отдельности, могут выполняться в собственных транзакциях. Это зависит от клиента. Приложение выбирает границу транзакции по тому, какое изменение оно хочет опубликовать целиком. ([PostgreSQL 18, §3.4](#references))

Пример ниже рассчитан на пустую учебную базу. В `orders` хранится одна строка на заказ, в `payments` — одна строка на оплату. Номер оплаты отличает её от других оплат. Номер заказа ссылается на существующий заказ. Сумму оплаты для примера берём из цен записанных позиций.

```sql
CREATE TABLE orders (
    order_id integer PRIMARY KEY,
    status text NOT NULL
);

CREATE TABLE payments (
    payment_id integer PRIMARY KEY,
    order_id integer NOT NULL REFERENCES orders (order_id),
    amount_cents integer NOT NULL
);

INSERT INTO orders (order_id, status)
VALUES (101, 'open'), (103, 'open');
```

Следующий запрос возвращает текущий статус заказа 101 и количество строк с его оплатами. Выражение в скобках считает оплаты того же заказа. Начальный результат — `open, 0`.

```sql
SELECT status,
       (SELECT count(*) FROM payments WHERE order_id = 101) AS payment_count
FROM orders
WHERE order_id = 101;
```

Сначала запишем оплату и отменим операцию до изменения заказа. Если повторить чтение после `ROLLBACK`, получим `open, 0`. Вставка входила в отменённую транзакцию.

```sql
BEGIN;
INSERT INTO payments VALUES (501, 101, 1300);
ROLLBACK;
```

Теперь выполним оба изменения внутри одной транзакции. После `COMMIT` повторное чтение вернёт `paid, 1`.

```sql
BEGIN;
INSERT INTO payments VALUES (501, 101, 1300);
UPDATE orders SET status = 'paid' WHERE order_id = 101;
COMMIT;
```

## Что может увидеть отчёт? \{#what-can-the-report-see\}

Расписание начинается с зафиксированного начального состояния. Заказ 101 открыт, оплат пока нет. Касса выполняет каждую запись в сеансе A. Отчёт выполняет один `SELECT` из примера в сеансе B с настройкой PostgreSQL `READ COMMITTED` по умолчанию. Такой `SELECT` читает изменения, зафиксированные к началу запроса, и предыдущие записи собственной транзакции. Предположим, что отчёт только читает, а касса — единственный процесс, который меняет заказ 101. [PostgreSQL 18, §13.2.1](#references)

| Момент в расписании | Статус и число оплат при новом чтении в A | Статус и число оплат при новом чтении в B |
| --- | --- | --- |
| До `BEGIN` | `open, 0` | `open, 0` |
| После вставки внутри транзакции | `open, 1` | `open, 0` |
| После обновления статуса внутри транзакции | `paid, 1` | `open, 0` |
| После `COMMIT` | `paid, 1` | `paid, 1` |

Касса может прочитать записанные ею строки, пока решает, завершать ли операцию. Отчёт видит прежнюю пару значений, пока касса не зафиксирует транзакцию. Новое чтение после фиксации видит оба изменения. В примере гарантия относится к одному запросу, который читает обе таблицы. Если отчёт отправит два отдельных запроса и между ними произойдёт фиксация, эти запросы могут прочитать данные на разные моменты даже с той же настройкой. ([PostgreSQL 18, §§3.4 и 13.2.1](#references))

## Дальше \{#next\}

Транзакция публикует запрошенные изменения вместе. Она может опубликовать и ошибочную комбинацию, если касса передала неверную сумму или обновила другой заказ. При проектировании нужно определить, какой объект представляет каждая строка и как идентичность объектов и связи между ними ограничивают допустимые состояния. Эти решения разбираются в следующей запланированной теме «От предметной области к модели» в [курсе баз данных](/ru/notes/databases#section-1).
