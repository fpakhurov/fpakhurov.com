Отчёт читает диапазон дат для одного магазина в порядке даты и номера заказа. Индекс только по дате помещает рядом заказы всех магазинов. Если поставить магазин первым, поиск можно ограничить одним непрерывным интервалом ключей.

## Ставим равенство перед диапазоном \{#put-the-equality-before-the-range\}

Возьмём шесть учебных заказов из двух магазинов. В каждой строке уже есть сумма заказа.

```sql
CREATE TEMP TABLE report_orders (
    order_id integer,
    shop_id integer,
    paid_on date,
    total_cents integer
);

INSERT INTO report_orders VALUES
    (101, 1, DATE '2026-01-01', 1300),
    (102, 1, DATE '2026-01-02', 350),
    (103, 1, DATE '2026-01-02', 1550),
    (104, 1, DATE '2026-01-03', 1200),
    (201, 2, DATE '2026-01-02', 2400),
    (202, 2, DATE '2026-01-03', 800);

CREATE INDEX report_orders_shop_day_id
ON report_orders (shop_id, paid_on, order_id) INCLUDE (total_cents);
```

**Многостолбцовое B-дерево** упорядочивает кортежи лексикографически. Сначала сравнивается `shop_id`, при совпадении — `paid_on`, при совпадении обоих полей — `order_id`. Внутри магазина 1 ключи за 2 января стоят рядом. У магазина 2 тоже есть заказ в этот день, но он за пределами интервала. ([PostgreSQL 18, §11.3](#references); [SQLite, §1.6](#references))

```sql
SELECT order_id, paid_on, total_cents
FROM report_orders
WHERE shop_id = 1
  AND paid_on >= DATE '2026-01-02'
  AND paid_on < DATE '2026-01-03'
ORDER BY paid_on, order_id;
```

Получаем заказы 102 и 103 за 2 января с суммами 350 и 1550 копеек. Индекс позволяет начать с нижней границы даты внутри блока магазина 1 и остановиться у верхней. Ключи интервала уже идут в нужном порядке. При фиксированном магазине и без ограничения на дату индекс может дать тот же порядок по всему блоку магазина. В запросе сохраняем `ORDER BY`, потому что другой путь доступа может вернуть те же строки в ином порядке.

Без условия на магазин одна дата встречается в нескольких блоках. PostgreSQL 18 иногда использует **поиск с пропуском** (skip scan), повторяя поиск по поздним ключам при разных значениях раннего ключа. Это может быть выгодно, если различных ранних значений мало. Когда отчёты часто охватывают все магазины, индекс с датой на первом месте может сделать такой поиск непрерывным. ([PostgreSQL 18, §11.3](#references))

## Отделяем ключи поиска от дополнительных полей \{#distinguish-search-keys-from-payload\}

Запросу также нужен `total_cents`. `INCLUDE` хранит его в индексе как дополнительные данные и сохраняет прежний порядок ключей. Индекс **покрывает** запрос (covering index), когда содержит нужные ему значения. SQLite и SQL Server описывают покрывающие индексы с разным синтаксисом объявления. В PostgreSQL наличия выходных столбцов в индексе недостаточно для чтения только по индексу (index-only scan). СУБД проверяет видимость строки. Если страница кучи отмечена как полностью видимая, можно использовать эту отметку. Иначе может потребоваться обращение к куче даже при наличии всех нужных значений в индексе. ([PostgreSQL 18, §11.9](#references); [SQLite, §1.7](#references); [Microsoft, Included Columns](#references))

Дополнительное поле увеличивает размер записи индекса. Его имеет смысл включать, когда для нагрузки полезно избегать обращений к куче. Оно не задаёт границы поиска и порядок, которые может задать ключевое поле.

## Проверяем, какую долю отбирает условие \{#check-how-much-the-predicate-selects\}

**Селективность** (selectivity) — доля строк, удовлетворяющих условию. Два предиката выше оставляют 2 из 6 учебных заказов. На гораздо большей таблице такой же диапазон дат может выбрать малую долю или большую часть строк. При узком диапазоне может оказаться выгодным прочитать несколько страниц кучи. При широком обращения к индексу и куче могут стоить больше одного последовательного прохода. Поэтому объявление индекса само по себе не определяет план.
