Работают две стойки выдачи. Каждый руководитель может закрыть свою стойку, если другая останется открытой. Оба читают, что открыты две стойки, и затем закрывают по одной. Записи меняют разные строки. Результат всё равно нарушает правило, по которому в магазине должна работать хотя бы одна стойка.

## Читаем расписание \{#read-a-schedule\}

**Расписание** (schedule) перечисляет операции нескольких транзакций в порядке выполнения, сохраняя порядок команд внутри каждой. **Последовательное** расписание целиком выполняет одну транзакцию перед следующей. В последовательном порядке первый руководитель видит две стойки и закрывает одну. Второй видит одну и оставляет её открытой. При любом порядке работает одна стойка. Какая именно, зависит от порядка.

То же правило можно выполнить на общей таблице в отдельной тестовой базе PostgreSQL. Подготовка фиксируется до начала работы двух сеансов. Каждый сеанс по результату подсчёта решает, выполнять ли своё обновление.

```sql
CREATE TABLE pickup_counters (
    counter text PRIMARY KEY,
    is_open boolean NOT NULL
);
INSERT INTO pickup_counters VALUES ('A', true), ('B', true);
```

| Шаг | T1 | T2 |
| --- | --- | --- |
| 1 | Начинает `REPEATABLE READ` | Начинает `REPEATABLE READ` |
| 2 | Считает открытые стойки → 2 | |
| 3 | | Считает открытые стойки → 2 |
| 4 | Закрывает A | |
| 5 | | Закрывает B |
| 6 | Фиксируется | Фиксируется |

Для подсчёта используем `SELECT COUNT(*) FROM pickup_counters WHERE is_open`. Каждое обновление присваивает `is_open = false` с условием на ключ одной стойки. В PostgreSQL на уровне Repeatable Read обе транзакции в таком расписании могут зафиксироваться, потому что обновляют разные строки и СУБД допускает этот результат. Итоговое число открытых стоек равно нулю. Ни один последовательный порядок этих транзакций с тем же правилом не дал бы такой истории. Это **перекос записи** (write skew). [PostgreSQL 18, §13.2.2](#references) [Berenson et al., 1995, §4](#references)

## Что видит читающая сторона \{#what-does-a-reader-see\}

**Снимок** (snapshot) определяет, какие версии строк может наблюдать команда. В PostgreSQL на уровне Read Committed обычный `SELECT` видит данные, зафиксированные до начала этой команды, и предыдущие изменения своей транзакции. Две команды могут поэтому читать разные зафиксированные состояния. На уровне Repeatable Read границу задаёт первая команда, которая получает снимок транзакции. Последующее чтение использует тот же снимок и видит собственные изменения транзакции. [PostgreSQL 18, §§13.2.1–13.2.2](#references)

Пусть T1 читает, что A открыта, T2 закрывает A и фиксируется, а T1 снова читает A. На уровне Read Committed при втором чтении A может оказаться закрытой. Это **неповторяемое чтение** (nonrepeatable read) одной существующей строки. Если T2 добавит открытую стойку C, а повторный запрос ищет все открытые стойки, новая подходящая строка будет **фантомом** (phantom read). **Грязное чтение** (dirty read) увидело бы изменение до фиксации записывающей транзакции. PostgreSQL обрабатывает запрос Read Uncommitted как Read Committed, поэтому запрещает грязное чтение на всех уровнях. [PostgreSQL 18, §13.2](#references)

| Уровень PostgreSQL | Снимок для обычных чтений | Что ещё возможно |
| --- | --- | --- |
| Read Committed, в том числе при запросе Read Uncommitted | Один на команду | Неповторяемые чтения, фантомы, аномалии сериализации |
| Repeatable Read | Один на транзакцию для чтения снимка | Перекос записи |
| Serializable | Один на транзакцию для чтения снимка, с дополнительным учётом конфликтов | Транзакция может завершиться ошибкой и потребовать повтора |

Отсутствие изменений между чтениями даёт более слабую гарантию, чем правило о совместном эффекте чтений и записей. В примере со стойками каждый руководитель видит стабильный снимок. При этом оба решения зависят от значений, которые меняет другая сторона. Поэтому перечня аномалий чтения недостаточно, чтобы охарактеризовать изоляцию снимков. [Berenson et al., 1995, §§2 и 4](#references)

## Когда нужно последовательное объяснение \{#require-a-serial-explanation\}

**Сериализуемость** (serializability) требует, чтобы эффекты и наблюдения успешно завершённых транзакций соответствовали некоторому последовательному порядку. Сами операции могут пересекаться. В примере T1 читает B открытой до изменения T2, поэтому в последовательном объяснении T1 должна предшествовать T2. T2 читает A открытой до изменения T1, поэтому T2 должна предшествовать T1. Оба требования не могут выполняться одновременно. [Ports and Grittner, 2012, §§2–3](#references)

Если начать снова с двух открытых стоек и выполнить обе транзакции PostgreSQL на уровне `SERIALIZABLE`, такое расписание не может привести к двум успешным фиксациям. Сериализуемая изоляция снимков (Serializable Snapshot Isolation, SSI) отслеживает зависимости, из которых может возникнуть аномалия сериализации. СУБД может отменить транзакцию с SQLSTATE `40001`. Приложение повторяет всю транзакцию с новым снимком. Повтор только последней записи использовал бы решение, принятое по старому подсчёту. При повторе после успешного закрытия подсчёт даст одну стойку, поэтому оставшаяся стойка не закроется. [PostgreSQL 18, §13.2.3](#references) [Ports and Grittner, 2012, §3](#references)

Рассуждение охватывает транзакции, которые участвуют в этом протоколе изоляции и применяют одно правило принятия решения. Прямое обновление, которое закрывает последнюю стойку, ошибочно даже при последовательном выполнении. Уровень изоляции даёт гарантию о порядке пересечения операций. Инвариант и корректный переход задаёт приложение.

## Далее \{#next\}

Снимки объясняют, почему чтение может продолжаться, пока другая транзакция записывает данные. Когда две записи требуют одну строку, СУБД всё равно должна их координировать. [Блокировки и MVCC](/ru/notes/databases/locks-and-mvcc) прослеживают оба механизма на обновлении остатка и цикле ожидания.
