Касса бронирует две пачки чая. Операция проверяет небольшую часть текущих данных и меняет нужные строки, прежде чем сообщить об успехе. В конце дня отчёт суммирует продажи каждого магазина. Он читает много зафиксированных заказов и возвращает по одной строке на магазин. Оба запроса используют SQL. Объём работы для них считают по-разному.

## Считаем, сколько данных затрагивает запрос \{#count-what-each-request-touches\}

**Оперативная обработка транзакций** (online transaction processing, OLTP) обслуживает запросы вроде создания заказа, брони остатка и записи платежа. Бронь — короткая транзакция с поиском по ключу, для которого можно построить индекс, условным обновлением и вставкой. Система обслуживает много таких запросов одновременно. Она должна сохранить корректность изменений и ответить каждому клиенту за приемлемое время.

**Оперативная аналитическая обработка** (online analytical processing, OLAP) отвечает на вопросы о наборах данных. Для этого часто группируют, отбирают и объединяют исторические записи. Отчёту магазина нужна сумма каждой позиции за день, хотя на выходе всего два магазина. В других аналитических запросах те же записи можно сгруппировать по товару, магазину или времени. По числу выходных строк мало что можно сказать о количестве прочитанных. [Gray и др., 1997, §1](#references)

Возьмём небольшой аналитический набор за один день. Каждая строка представляет позицию заказа. Её сумма равна произведению количества на цену, записанную в позиции. Идентификатор магазина уже входит во входные данные. Если присоединить сумму всего заказа к каждой его позиции, получится другой показатель. Он может учесть одну сумму заказа несколько раз.

```sql
SELECT store_id, SUM(amount_cents) AS total_cents
FROM (
    VALUES
        (11, 700), (11, 600), (11, 350),
        (22, 1200), (22, 350), (22, 1200)
) AS day_order_lines(store_id, amount_cents)
GROUP BY store_id
ORDER BY store_id;
```

| store_id | total_cents |
| --- | --- |
| 11 | 1650 |
| 22 | 2750 |

Магазин 11 даёт $700 + 600 + 350 = 1650$ копеек. Магазин 22 даёт $1200 + 350 + 1200 = 2750$ копеек. Операция работает с данными выбранного дня, даже если магазин уже перешёл к следующему.

## Размещаем вместе поля, которые читаются вместе \{#lay-out-the-fields-that-are-read-together\}

При **построчном размещении** (row layout) поля записи лежат вместе. Это удобно, когда поиск по индексу находит несколько полных записей и запрос использует по несколько полей каждой. При **поколоночном размещении** (column layout) вместе лежат значения одного поля. Система может сопоставить поля, которые относятся к одной записи. Для сканирования двух полей можно прочитать их отдельно от других столбцов. C-Store обслуживает аналитические запросы с помощью поколоночных проекций. [Stonebraker и др., 2005, §§1–2](#references)

Возьмём учебный день с $N = 10{,}000{,}000$ позиций. Пусть каждая занимает 120 байт, из них 4 байта занимает `store_id`, 8 байт занимает `amount_cents`, а остальные поля занимают 108 байт. Считаем полное последовательное чтение, значения фиксированного размера без сжатия и без служебных заголовков. День уже выбран, поэтому поле даты читать не требуется.

При полном чтении построчного хранилища объём равен

$$
N \cdot 120 = 1{,}200{,}000{,}000\ \mathrm{bytes}.
$$

При чтении только двух потоков столбцов он равен

$$
N \cdot (4+8) = 120{,}000{,}000\ \mathrm{bytes}.
$$

Вторая модель читает в десять раз меньше байт. Это соотношение относится к выбранному запросу и размещению. Индекс, сжатие, выравнивание, уже загруженные в память данные и стоимость сборки целых строк могут изменить наблюдаемое время.

Два подхода можно сочетать. PAX хранит на диске вместе все значения одной страницы, а внутри страницы группирует значения по атрибутам. Это помогает использовать кэш процессора, когда сканирование обращается к нескольким атрибутам. При чтении страницы с диска всё равно загружаются остальные поля. Термин «поколоночное размещение» может скрывать различие этих двух затрат. [Ailamaki и др., 2001, §3](#references)

## Определяем, когда отчёт увидит изменение \{#decide-when-the-report-may-see-a-change\}

Кассе нужно знать, завершилась ли её операция. Отчёту за день нужны согласованные данные за выбранный период. Аналитическая копия может уменьшить конкуренцию за ввод-вывод и память в кассовой базе. Появляется ещё одна граница. Если копия обновилась в 02:00, заказ, зафиксированный в 02:01, станет в ней виден по правилу следующего обновления или доставки изменений.

Одна база может обслуживать оба вида запросов, если это допускают объём данных, требуемая свежесть и ресурсы. Разделение нагрузок полезнее, когда длинное сканирование мешает запросам, чувствительным к задержке. Решение также зависит от того, какие данные копировать, когда читатели увидят исправления и как восстановить запоздавшую загрузку. Эти вопросы остаются и при быстром сканировании.
