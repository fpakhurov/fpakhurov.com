Магазин соединяет веб-заказы с данными платежей. Индексный поиск для каждого заказа может быть дешёвым, если первый фильтр оставляет 60 строк. Если остаётся намного больше, может выиграть план с одним просмотром таблицы платежей. До выполнения планировщику нужно оценить, сколько строк дойдёт до соединения.

## Оцениваем число строк \{#estimate-the-number-of-rows\}

Оптимизатор рассматривает пути доступа, порядки соединений и операторы. Для каждого плана он оценивает объём работы. **Оценка кардинальности** (cardinality estimate) предсказывает число строк, которые вернёт узел. Она влияет на последующие оценки. Например, вложенный цикл может платить за один внутренний поиск на каждую строку внешнего узла. System R использовала такие оценки для выбора плана по стоимости. ([Selinger и др., 1979](#references); [PostgreSQL 18, §§14.1–14.2](#references))

Возьмём 1000 заказов. На магазин 1 приходится 200, на веб-канал — 300. Пусть $N$ — общее число строк, а $s_1$, $s_2$ — доли строк для двух предикатов. При независимости условий для их конъюнкции получаем оценку $N s_1 s_2$. При $N=1000$, $s_1=0.2$ и $s_2=0.3$ получается $1000 \cdot 0.2 \cdot 0.3 = 60$.

| Магазин | Веб | Прилавок | Всего |
| --- | ---: | ---: | ---: |
| 1 | 180 | 20 | 200 |
| 2 | 120 | 680 | 800 |
| Всего | 300 | 700 | 1000 |

Магазин 1 продаёт в основном онлайн, поэтому фактическое пересечение равно 180. Оценка занижена втрое. Точные счётчики по отдельным столбцам могут дать неточное пересечение. Leis и соавторы обнаружили большие ошибки оценивания в тесте на реальных данных и запросах с соединениями. Такие ошибки важны, когда меняют относительную стоимость планов. ([Leis и др., 2015](#references))

## Читаем оценку и фактическое число строк \{#read-estimated-and-actual-rows\}

Подготовим данные с теми же счётчиками и соберём статистику столбцов.

```sql
CREATE TEMP TABLE planner_orders AS
SELECT n AS order_id,
       CASE WHEN n <= 200 THEN 1 ELSE 2 END AS shop_id,
       CASE WHEN n <= 180 OR n BETWEEN 201 AND 320
            THEN 'web' ELSE 'counter' END AS channel
FROM generate_series(1, 1000) AS g(n);

ANALYZE planner_orders;

EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT order_id
FROM planner_orders
WHERE shop_id = 1 AND channel = 'web';
```

Узел чтения в PostgreSQL 18.6 показал оценку `rows=60`, фактические `actual rows=180.00 loops=1` и 820 строк, отброшенных фильтром. Оценка `rows` относится к выходу после фильтрации. Если узел выполнялся несколько раз, фактическое число строк усредняется по запускам. Обычный `EXPLAIN` описывает план, а `EXPLAIN ANALYZE` выполняет запрос. Используем запрос на чтение, чтобы увидеть фактическую работу без внесения изменений. ([PostgreSQL 18, §14.1](#references))

У записи стоимости `0.00..23.00` два поля. Начальная стоимость оценивает работу до первого результата. Полная стоимость оценивает работу до завершения вместе с дочерними узлами. Это единицы модели планировщика, а время выполнения измеряется отдельно. Изменение оценки может поменять выбранный план при том же смысле запроса.

## Сообщаем планировщику о сочетаниях значений \{#tell-the-planner-about-joint-values\}

PostgreSQL может собирать **расширенные статистики** (extended statistics) для столбцов, которые используются вместе. Многомерный список наиболее частых значений может хранить частоту конкретного сочетания. Добавим его для магазина и канала, соберём данные и повторим просмотр плана. ([PostgreSQL 18, §14.2.2.3](#references))

```sql
CREATE STATISTICS shop_channel (mcv)
ON shop_id, channel FROM planner_orders;

ANALYZE planner_orders;

EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT order_id
FROM planner_orders
WHERE shop_id = 1 AND channel = 'web';
```

В том же запуске оценка выросла до 180, а фактическое число осталось 180. Сам узел остался последовательным чтением. В учебной таблице нет более быстрого альтернативного пути доступа. Новая статистика улучшает прогноз для этих данных и предиката. Она не гарантирует точность на больших выборках, для неучтённых сочетаний и соединений разных таблиц.

Если план ведёт себя неожиданно, сравним оценки с фактами, начиная с узлов чтения. Найдём первое крупное расхождение, прежде чем объяснять всё последним оператором. Проверим, отражает ли статистика текущее распределение и нужны ли связанные сведения для нескольких условий. Даже точная оценка не гарантирует лучший физический план. Подходящий путь доступа может отсутствовать, а модель стоимости даёт приближение.

## Дальше \{#next\}

Физический план объясняет, как СУБД читает и меняет строки. Если несколько записей образуют одну операцию, нужны правила на случай ошибки и пересечения с другими операциями. В конспекте [«Транзакции и инварианты»](/ru/notes/databases/transactions-and-invariants) начнём с состояния, которое должно остаться допустимым после применения набора изменений.
