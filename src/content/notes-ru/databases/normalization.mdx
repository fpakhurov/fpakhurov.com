В [объединённой таблице заказов](/ru/notes/databases/functional-dependencies#an-agreement-rule-between-rows) повторяются текущее состояние заказа 106 и текущий код товара 7. Разделение даёт каждому факту своё место. Произвольное разделение может создать чек, которого не было, или скрыть правило, которое легко проверялось в исходной таблице.

## Найдём повторяющийся факт \{#detect-which-fact-repeats\}

Сохраним обозначения $R(o,n,p,q,c,k,s)$. Кандидатный ключ — $on$. Пусть $F$ состоит из зависимостей $on\to pqc$, $o\to s$, $p\to k$ и $k\to p$. Обозначим через $F^+$ все зависимости, следующие из $F$. Нормальные формы ниже относятся к схеме при этих правилах. Четырёх строк примера для проверки недостаточно.

**Первая нормальная форма** (1NF) использует простые значения на выбранном уровне детализации. Операции над отношением рассматривают значение как единое целое. В этой схеме номер позиции, товар и количество — отдельные поля. Если поместить переменное число записей о позициях в одно поле заказа, модель изменится, а атрибуты позиции перестанут быть обычными столбцами этого отношения. ([Codd, 1970, §1.4](#references))

**Вторая нормальная форма** (2NF) дополнительно требует, чтобы ни один неключевой атрибут не зависел от собственного подмножества кандидатного ключа. **Ключевой атрибут** (prime attribute) входит хотя бы в один кандидатный ключ. Здесь $s$ неключевой, а зависимость $o\to s$ использует только часть ключа $on$. Вынесем состояние в $O(o,s)$. В оставшейся схеме $R'(o,n,p,q,c,k)$ ни $o$, ни $n$ по отдельности не определяет неключевого атрибута. Условие второй нормальной формы выполнено. ([Bernstein, 1976, §2](#references))

В оставшейся схеме всё ещё повторяется код товара. Для **третьей нормальной формы** (3NF) у каждой нетривиальной выводимой зависимости $X\to A$ с одним атрибутом $A$ справа либо $X$ служит суперключом, либо $A$ входит в кандидатный ключ. Зависимость нетривиальна при $A\notin X$. **Нормальная форма Бойса — Кодда** (BCNF) требует суперключ $X$ для каждой такой зависимости, включая зависимости с ключевым атрибутом справа. В $R'$ для $p\to k$ детерминант не является суперключом, а правая часть не входит в ключ. Нарушены оба условия. ([Silberschatz et al., гл. 7](#references))

Перенесём код в $P(p,k)$ и оставим $L(o,n,p,q,c)$ для позиции. Относительно заявленных правил $O$, $P$ и $L$ находятся в BCNF. Детерминант каждой нетривиальной зависимости содержит ключ. В $O$ ключом служит $o$, в $P$ — $p$ или $k$, в $L$ — $on$.

## Восстановим допустимое отношение \{#reconstruct-a-valid-relation\}

Декомпозиция **без потерь** (lossless decomposition) при $F$ означает, что естественное соединение проекций каждого экземпляра, удовлетворяющего $F$, даёт исходный экземпляр. Для разбиения на две схемы $U$ и $V$ с объединением $R$ при одних лишь функциональных зависимостях это равносильно тому, что $U\cap V$ определяет все атрибуты $U$ или все атрибуты $V$ в $F^+$. ([Silberschatz et al., гл. 7](#references), [Berkeley CS 186, DB Design](#references))

Достаточность условия видна из результата соединения. Один кортеж соединения собирается из проекции первого исходного кортежа на $U$ и проекции второго на $V$. Исходные кортежи совпадают на $U\cap V$. Если пересечение определяет $V$, они совпадают на всём $V$. Тогда собранный кортеж равен первому исходному. Каждый исходный кортеж соединяет свои проекции, поэтому пропавших или лишних кортежей нет.

При первом разбиении общим остаётся $o$, который определяет $O$. При втором общим остаётся $p$, который определяет $P$. Оба разбиения идут без потерь, поэтому два соединения в обратном порядке восстанавливают объединённые позиции. В проекциях SQL используем `DISTINCT`, чтобы сохранить по одной копии каждого кортежа.

```sql
WITH flat(order_id, line_no, product_id, quantity, cents, code, state) AS (
    VALUES (101, 1, 7, 2, 350, 'TEA50', 'open'),
           (101, 2, 9, 1, 600, 'COFFEE', 'open'),
           (106, 1, 7, 1, 350, 'TEA50', 'paid'),
           (106, 2, 7, 1, 300, 'TEA50', 'paid')
),
lines AS (
    SELECT DISTINCT order_id, line_no, product_id, quantity, cents FROM flat
),
orders AS (
    SELECT DISTINCT order_id, state FROM flat
),
products AS (
    SELECT DISTINCT product_id, code FROM flat
)
SELECT order_id, line_no, product_id, quantity, cents, code, state
FROM lines
JOIN orders USING (order_id)
JOIN products USING (product_id)
ORDER BY order_id, line_no;
```

Запрос даёт исходные четыре строки. Для заказа 106 он восстанавливает позицию 1 с кодом `TEA50`, ценой 350 и состоянием `paid` и позицию 2 с тем же кодом и состоянием по цене 300. В рабочей базе черновик заказа 105 и непроданная упаковка на 100 г тоже хранятся в родительских таблицах. Пример строит проекции из позиций, поэтому этих независимых фактов нет во входе.

Другое разбиение только двух позиций заказа 106 на $(n,p)$ и $(p,c)$ сохраняет общим $p$. Первая проекция содержит $(1,7)$ и $(2,7)$. Вторая содержит $(7,350)$ и $(7,300)$. Каждый номер позиции теперь совпадает с обеими ценами, и получаются четыре кортежа. В частности, продажи $(1,7,300)$ не было. При разбиении исчезла связь номера позиции с ценой. Соединение обнаруживает потерю, создавая лишние комбинации.

## Сохраним проверяемость правил на частях \{#keep-the-rules-enforceable-on-the-parts\}

Для каждой полученной схемы $R_i$ обозначим через $F_i$ зависимости из $F^+$, все атрибуты которых лежат в $R_i$. Декомпозиция **сохраняет зависимости** (dependency preservation), если из объединения локальных зависимостей следуют все зависимости $F$. Равносильно тому, что замыкание этого объединения равно $F^+$. В разбиении магазина каждая из четырёх исходных зависимостей целиком лежит в одной части. Чтобы проверить эти функциональные правила, соединение не нужно. Ссылки между таблицами по-прежнему требуют внешних ключей. ([Silberschatz et al., гл. 7](#references), [Berkeley CS 186, DB Design](#references))

Соединение без потерь и сохранение зависимостей могут расходиться. Пусть $T(o,v,b)$ хранит номер стойки $b$, которая обслуживает заказ $o$ по услуге $v$. У заказа не больше одной стойки на услугу, поэтому $ov\to b$. Стойка обслуживает одну услугу, поэтому $b\to v$. Других порождающих зависимостей нет. Из $ov$ или $ob$ выводятся все три атрибута. Из $b$ выводится $bv$, а $o$ и $v$ по отдельности определяют только себя. Кандидатные ключи — $ov$ и $ob$. Все атрибуты входят в какой-либо ключ, поэтому выполняется 3NF. Поскольку $b$ не суперключ, зависимость $b\to v$ нарушает BCNF.

Разбиение на $(b,v)$ и $(o,b)$ даёт BCNF и идёт без потерь, поскольку общий $b$ определяет первую часть. Из локальных зависимостей $ov\to b$ не следует. Например, запишем в первую часть $(7,\text{pickup})$ и $(8,\text{pickup})$, а во вторую — $(106,7)$ и $(106,8)$. У каждой стойки одна услуга, и обе части удовлетворяют локальным зависимостям. Соединение назначает две стойки одному заказу для одной услуги. Гарантия соединения без потерь относится к проекциям допустимого исходного экземпляра. Произвольные независимые правки частей могут дать недопустимый исходный экземпляр.

Синтез 3NF позволяет сохранить зависимости и получить соединение без потерь. Один стандартный способ начинает с эквивалентного минимального набора зависимостей, строит отношения из детерминантов и зависимых атрибутов и добавляет отношение для исходного кандидатного ключа, если ни одна часть его не содержит. Точная конструкция и доказательство приведены в источниках. Если оставить $T$ в 3NF, исходное правило $ov\to b$ проверяется в одном отношении. При этом услуга может повторяться для заказов, использующих одну стойку. ([Bernstein, 1976, §§6–7](#references), [Silberschatz et al., гл. 7](#references))
