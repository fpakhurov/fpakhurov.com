Касса записывает две упаковки `tea` по 350 копеек. В каталоге теперь есть упаковки по 50 и 100 г. На витрине обе называются «Чай». По чеку с двумя упаковками чая за 700 копеек можно узнать сумму оплаты. На складе по-прежнему два варианта, что положить в заказ.

## Какие объекты различаем \{#decide-what-has-an-identity\}

В [первом примере SQL](/ru/notes/sql/tables-and-queries#what-does-one-row-mean) строка представляет одну позицию одного заказа. Для чтения примера хватает названия товара. При сборке заказа нужно различать товары, которые можно продать. Здесь товар каталога представляет один вид упаковки. Упаковки по 50 и 100 г — два товара. Две отдельные упаковки по 50 г на полке — две единицы одного товара. Если магазин ведёт поштучный учёт экземпляров, ему нужна отдельная идентификация на этом уровне. Выбор зависит от того, что система должна уметь различать. Для товаров с идентификатором GTIN стандарт GS1 проводит похожую границу. При изменении обязательного по закону количества содержимого, указанного на упаковке, нужен новый GTIN. [GS1, §2.3](#references)

**Сущность** — отдельный объект, который мы хотим представить. Заказ 101 и вид упаковки по 50 г — экземпляры двух типов сущностей, «Заказ» и «Товар каталога». **Атрибут** хранит свойство, например отображаемое название товара. **Связь** сопоставляет сущности. Например, заказ содержит позицию. Концептуальная модель задаёт нужные предметной области объекты, атрибуты и связи до выбора способа представить их в таблицах. [Чен, 1976, §§2.1–2.2](#references)

Позиция фиксирует выбранный товар, количество и согласованную цену за единицу. Цена относится к позиции, потому что следующая продажа того же товара может пройти по другой цене. Если пересчитать старый заказ по текущей цене каталога, её повышение с 350 до 400 копеек изменит сумму двух упаковок с 700 до 800 копеек. Согласованную цену храним в той позиции, к которой она относится.

## Сколько объектов связано с каждой стороны \{#count-links-in-both-directions\}

Каждая позиция относится ровно к одному заказу и указывает ровно один товар каталога. В заказе может быть несколько позиций. В черновике их может быть ноль. Товар может встретиться во многих позициях или пока ни разу не продаться. **Кратность** ограничивает число сущностей, связанных с одной сущностью на другом конце связи. Указываем минимум и максимум. Метка `0..*` разрешает ноль и оставляет верхнюю границу открытой. [Чен, 1976, §3.1](#references)

Между заказами и товарами возникает связь «многие ко многим». Позиция фиксирует отдельное вхождение в эту связь. Заказ 106 может содержать одну упаковку чая по 50 г за 350 копеек и ещё одну за 300 копеек в разных позициях. Обе относятся к одному заказу и одному товару. Запись с ключом из номера заказа и товара позволила бы сохранить только одну из них. Отдельная позиция хранит своё количество и цену.

Минимум может зависеть от состояния. В черновике магазин допускает ноль позиций, а при оформлении требует хотя бы одну. На схеме показаны связи для всех заказов, включая черновики. Дополнительное правило относится к переходу из одного состояния в другое. Два внешних ключа в примере ниже задают, на какие записи может ссылаться позиция. Добавление заказа без позиций не нарушает ограничения внешних ключей.

## Как выбрать ключи и сохранить остальные правила \{#choose-keys-and-keep-the-other-rules\}

**Потенциальный ключ** — набор атрибутов с двумя свойствами. Их значения присутствуют и однозначно определяют запись в любом допустимом состоянии. При удалении любого атрибута эта гарантия теряется. Номер позиции здесь назначается в пределах заказа. У позиций 101/1 и 106/1 совпадают номера позиций, у 101/1 и 101/2 — номера заказа. Пара `(order_id, line_no)` служит потенциальным ключом, потому что магазин запрещает повторять номер позиции в одном заказе. Четыре разные пары показывают, как действует правило. По четырём строкам его нельзя вывести. **Первичный ключ** — потенциальный ключ, выбранный главным идентификатором. [Чен, 1976, §2.3.1](#references) [PostgreSQL 18, §5.5.4](#references)

Пусть магазин назначает каждому товару код каталога и требует, чтобы действующие коды различались. Для этой базы код — **естественный ключ**. Он уже идентифицирует товар в работе с каталогом. Отображаемое название для этого не подходит. Сотрудники могут исправить опечатку в коде. Если позиции ссылаются на код, при исправлении нужно сохранить их связи, например каскадно обновить ссылки. **Суррогатный ключ** вводят для самой базы. Назначим упаковке по 50 г значение `product_id = 7` и сохраним его при исправлении кода с `TEA50` на `TEA-50`. [Чен, 1976, §2.3.1](#references) [PostgreSQL 18, §5.5.5](#references)

Первичный ключ на `product_id` допускает две записи с разными идентификаторами и одинаковым кодом каталога. Модель запрещает такую пару, поэтому на коде сохраняем отдельное ограничение уникальности. Оно проверяет текущее состояние каталога. Если при импорте нужно распознавать старые коды после исправлений, придётся хранить историю их назначений. Постоянный внутренний идентификатор сохраняет существующие ссылки. По нему нельзя угадать, какому товару принадлежал отсутствующий старый код.

## Как перенести правила в схему \{#put-the-rules-into-a-schema\}

Выполним пример в новом сеансе PostgreSQL. Заведём таблицу заказов, каталог и таблицу позиций. Первичный ключ позиции задаёт её идентичность. `REFERENCES` требует существования связанной записи. Первичный ключ в связанной таблице гарантирует единственность совпадения. Для обязательной связи нужно также исключить `NULL`. У столбца в составе первичного ключа это свойство уже есть, как у `order_id` в `order_lines`. [PostgreSQL 18, §§5.5.2–5.5.5](#references)

```sql
CREATE TEMP TABLE orders (
    order_id integer PRIMARY KEY
);

CREATE TEMP TABLE catalog_items (
    product_id integer PRIMARY KEY,
    catalog_code text NOT NULL UNIQUE,
    display_name text NOT NULL
);

CREATE TEMP TABLE order_lines (
    order_id integer REFERENCES orders (order_id),
    line_no integer CHECK (line_no > 0),
    product_id integer NOT NULL REFERENCES catalog_items (product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price_cents integer NOT NULL CHECK (unit_price_cents >= 0),
    PRIMARY KEY (order_id, line_no)
);

INSERT INTO orders VALUES (101), (105), (106);

INSERT INTO catalog_items VALUES
    (7, 'TEA50', 'Tea'),
    (8, 'TEA-100', 'Tea'),
    (9, 'COFFEE', 'Coffee');

INSERT INTO order_lines VALUES
    (101, 1, 7, 2, 350),
    (101, 2, 9, 1, 600),
    (106, 1, 7, 1, 350),
    (106, 2, 7, 1, 300);
```

Коды различаются, поэтому в каталоге могут быть две строки с названием `Tea`. У заказа 105 нет позиций, что допустимо для черновика. Две позиции заказа 106 ссылаются на один товар и имеют разные номера. Модель принимает все три случая. Внешний ключ указывает из дочерней записи на родительскую. Он допускает родительскую запись без дочерних и несколько дочерних записей с одной родительской.

Исправим код и соединим позиции заказа 106 с каталогом. `JOIN` сопоставляет каждой позиции ту строку каталога, у которой `product_id` равен значению ссылки в позиции.

```sql
UPDATE catalog_items SET catalog_code = 'TEA-50' WHERE product_id = 7;

SELECT l.line_no, c.catalog_code,
       l.quantity * l.unit_price_cents AS amount_cents
FROM order_lines AS l
JOIN catalog_items AS c ON c.product_id = l.product_id
WHERE l.order_id = 106
ORDER BY l.line_no;
```

| line_no | catalog_code | amount_cents |
| --- | --- | --- |
| 1 | TEA-50 | 350 |
| 2 | TEA-50 | 300 |

Код взят из текущей строки каталога. Суммы по-прежнему рассчитаны по ценам, записанным в двух позициях. Если товар переименуют, это же соединение не восстановит название, напечатанное в старом чеке. Если оно нужно, в модели надо представить и его историческое значение.

Чтобы увидеть, что база отклоняет, выполним после подготовки каждый оператор отдельно. Каждая вставка нарушает своё ограничение.

```sql
INSERT INTO order_lines VALUES (106, 1, 7, 1, 350);
INSERT INTO order_lines VALUES (106, 3, 99, 1, 350);
INSERT INTO catalog_items VALUES (10, 'TEA-50', 'Tea');
```

Первая вставка повторно использует пару `(106, 1)`, которая уже определяет позицию. Во второй свободный номер позиции, но товара 99 нет в каталоге. Третья передаёт новый идентификатор и занятый код. База отклоняет каждую вставку по соответствующему ограничению. Она приняла бы `(106, 3, 8, 1, 350)`, даже если кассир имел в виду упаковку по 50 г. Внешний ключ проверяет, что товар 8 существует. Выбор покупателя ему неизвестен.
