Касса резервирует две пачки чая. Пять пачек были доступны и одна уже находилась в резерве, всего шесть. Если доступный остаток уменьшится до трёх, а новый резерв пропадёт, в данных останется четыре пачки. Быстрый план может выполнить обе команды. Ещё нужно правило, какие состояния операция вправе оставить после себя.

## Корректный переход сохраняет правило \{#a-correct-transition-preserves-a-rule\}

**Инвариант** (invariant) — свойство, которое должно выполняться в каждом допустимом состоянии. В этой модели во время резервирования пачки не поступают на склад и не покидают его. Пусть $a$ — число доступных пачек, а $r$ — суммарное количество чая в резервах. Правило учёта имеет вид $a+r=6$. Ещё требуем $a \ge 0$ и положительное количество в каждом резерве. Эти правила относятся к данной модели склада. Отгрузка или поступление пачек изменили бы учёт. [Gray, 1981, General model](#references)

При резервировании $q$ пачек планируем два изменения $a \mapsto a-q$ и $r \mapsto r+q$. Их сумма остаётся $a+r$, потому что два слагаемых с $q$ сокращаются. Для $q=2$ переходим из $(a,r)=(5,1)$ в $(3,3)$. Частичное изменение оставило бы $(3,1)$ и нарушило правило.

Атомарность допускает и сохранение исходного состояния при отмене операции. Она не сверяет два количества в программе. Уменьшение остатка на два и резервирование одной пачки могут пройти ограничения строк. Они могут атомарно зафиксироваться и оставить $3+2=5$. Инвариант затрагивает две таблицы, поэтому проверка одной строки вроде `available >= 0` сама его не обеспечит. Связь должна выражать программа или схема.

## Обе записи используют одно количество \{#make-both-writes-use-the-same-quantity\}

Выполним пример в новом сеансе PostgreSQL. Исходное состояние взято из [примера резерва в SQL](/ru/notes/sql/transactions#where-does-one-operation-end). Временные таблицы ограничивают пример этим сеансом.

```sql
CREATE TEMP TABLE stock (
    product text PRIMARY KEY,
    available integer NOT NULL CHECK (available >= 0)
);

CREATE TEMP TABLE reservations (
    reservation_id integer PRIMARY KEY,
    product text NOT NULL REFERENCES stock (product),
    quantity integer NOT NULL CHECK (quantity > 0)
);

INSERT INTO stock VALUES ('tea', 5);
INSERT INTO reservations VALUES (700, 'tea', 1);
```

Следующая команда использует запрошенное количество в обеих записях. Обновление возвращает строку, только если нашло достаточный остаток. Вставка берёт данные из этой строки. Команда выполняется внутри транзакции, в том числе когда клиент запускает её отдельно с автоматической фиксацией. [PostgreSQL 18, §§3.4 и 7.8.4](#references)

```sql
WITH request (product, quantity) AS (
    VALUES ('tea', 2)
), moved AS (
    UPDATE stock AS s
    SET available = s.available - r.quantity
    FROM request AS r
    WHERE s.product = r.product AND s.available >= r.quantity
    RETURNING s.product, r.quantity
)
INSERT INTO reservations
SELECT 701, product, quantity
FROM moved
RETURNING reservation_id, quantity;
```

Команда возвращает резерв 701 с количеством 2. В таблицах три доступные и три зарезервированные пачки. Если остатка недостаточно, `moved` не возвращает строк, вставка тоже ничего не возвращает, обе таблицы остаются прежними. Если при достаточном остатке запрос указывает занятый номер 701, вставка завершается ошибкой, и обновление остатка в той же команде не может сохраниться отдельно. Вызывающая сторона различает возвращённый резерв, результат без строк и ошибку. Выбор клиентом `COMMIT` или `ROLLBACK` для нескольких команд уже рассматривался в курсе SQL.

## Что описывает ACID \{#what-acid-describes\}

**Атомарность** (atomicity) определяет единицу успеха или отказа. Резервирование не может оставить зафиксированное списание остатка без соответствующей зафиксированной вставки. Две физические записи при этом могут выполняться в разное время. Журнал отката SQLite — один из примеров механизма, который даёт эффект «всё или ничего» с помощью отдельных операций записи. [SQLite, Atomic Commit, §§1–3](#references)

**Согласованность** (consistency) означает переход из допустимого состояния в другое допустимое состояние. Здесь равенство для количества пачек входит в определение допустимости. Объявленные ограничения защищают те правила, которые выражают. Сохранение остальных правил зависит от операций, разрешённых приложением, и от их координации. [Gray, 1981, General model](#references)

**Изоляция** (isolation) определяет, что могут наблюдать пересекающиеся операции и как их эффекты взаимодействуют. Самый строгий уровень SQL, serializable, требует, чтобы результат успешно зафиксированных сериализуемых транзакций совпадал с некоторым последовательным порядком. Более слабые уровни допускают другие результаты. Поэтому корректность одного перехода сама по себе составляет лишь часть обоснования работы приложения. [PostgreSQL 18, §13.2](#references)

**Долговечность** (durability) определяет, какие зафиксированные эффекты переживают предполагаемые сбои. При настройках с гарантией долговечной фиксации и сохранности накопителя перезапуск после сбоя процесса или машины должен сохранить зафиксированный резерв. Точная гарантия зависит от СУБД, настроек и сохранившихся компонентов хранения. Таблицы выше временные, поэтому пример демонстрирует переход состояния. Долговечность после сбоя проверяют отдельно. [PostgreSQL 18, §§3.4 и 28.4](#references)

Граница транзакции охватывает изменения, которыми управляет база данных. Письмо, отправленное во время операции, может дойти до покупателя до фиксации. Откат не может вернуть его. Приложение может сохранить намерение отправить письмо внутри транзакции и обработать доставку отдельно. Тогда процесс доставки сможет продолжить работу по зафиксированной записи. [Gray, 1981, General model](#references)

## Далее \{#next\}

Для одного запроса правило учёта проверить легко. Когда две транзакции читают общее состояние и затем пишут в разные строки, каждая может принять корректное решение отдельно, а вместе они оставят недопустимый результат. [Изоляция и сериализуемость](/ru/notes/databases/isolation) разбирает порядок действий, при котором это происходит.
