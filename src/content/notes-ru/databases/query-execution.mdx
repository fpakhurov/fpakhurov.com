Магазину нужны заказы точки 2 в порядке суммы. Индекс таблицы начинается с магазина, но его следующий ключ — дата. В запросе нужно упорядочить строки по сумме. SQL задаёт требуемый результат. СУБД нужна программа, которая получит нужные строки и выдаст их в требуемом порядке.

## Читаем план как дерево \{#read-the-plan-as-a-tree\}

Перед выполнением PostgreSQL разбирает запрос и определяет имена и типы. Планировщик выбирает **физический план** (physical plan) из способов получить тот же логический результат. Узел плана реализует одну операцию. Узлы чтения получают строки из источника. Другие узлы берут строки у дочерних узлов и возвращают свой результат. `EXPLAIN` показывает эту программу. ([PostgreSQL 18, §14.1](#references); [DuckDB 1.4, EXPLAIN](#references))

Выполним [подготовку заказов для отчёта](/ru/notes/databases/index-design#put-the-equality-before-the-range), затем прочитаем план.

```sql
ANALYZE report_orders;

EXPLAIN (COSTS OFF)
SELECT order_id, total_cents
FROM report_orders
WHERE shop_id = 2
ORDER BY total_cents DESC, order_id;
```

Запуск PostgreSQL 18.6 на шести строках дал такой план. `COSTS OFF` скрывает оценки.

```text
Sort
  Sort Key: total_cents DESC, order_id
  ->  Seq Scan on report_orders
        Filter: (shop_id = 2)
```

Узел чтения с отступом поставляет строки сортировке. Он проходит таблицу и применяет фильтр. Четыре строки отбрасываются, две подходят. Сортировка получает заказ 201 на 2400 копеек и заказ 202 на 800 копеек и возвращает их в таком порядке. Итоговая проекция оставляет только `order_id` и `total_cents`. Узлу чтения всё равно нужен `shop_id` для проверки фильтра.

Тот же запрос мог бы выполнить индексный проход с последующей сортировкой. На маленьком входе последовательное чтение может оказаться разумным. На другом наборе данных или с другим индексом план может измениться. `EXPLAIN QUERY PLAN` в SQLite может показать просмотр таблицы или индекса и временное B-дерево для сортировки. Имена узлов читаем в контексте той СУБД, которая их выдала. ([PostgreSQL 18, §14.1](#references); [SQLite, §§1.1–1.2](#references))

## Отличаем фильтр от блокирующей операции \{#distinguish-a-filter-from-a-blocking-operation\}

Узел чтения может передать подходящую строку наверх и продолжить просмотр. Полной сортировке обычно нужно получить весь вход, прежде чем вернуть первую строку в итоговом порядке. Первая полученная строка может оказаться последней. Поэтому время до первой строки отличается от времени завершения запроса. На большом входе сортировке может потребоваться временное хранилище. Если узел чтения уже даёт нужный порядок, планировщик может обойтись без отдельной сортировки. ([PostgreSQL 18, §14.1](#references))

Для агрегации тоже нужен физический способ. Рассмотрим сумму по магазину.

```sql
SELECT shop_id, SUM(total_cents) AS sales_cents
FROM report_orders
GROUP BY shop_id
ORDER BY shop_id;
```

Получаем 4400 копеек для магазина 1 и 3200 для магазина 2. Хеш-агрегация может хранить текущую сумму на магазин в хеш-таблице и добавлять каждую входную строку к состоянию группы. Обычно она читает весь вход, прежде чем выдать группы. Если вход сгруппирован по магазину, оператор может завершить одну группу, как только появится следующий ключ. Для получения такого порядка входа может потребоваться сортировка. Порядок показа по-прежнему задаёт итоговый `ORDER BY`, поскольку сама агрегация не требует порядка результата.
