Магазин загружает все позиции заказа 103. Условие `order_id = 103` простое. При последовательном просмотре всё равно нужно пройти таблицу, чтобы найти две подходящие позиции. Индекс добавляет путь от номера заказа к сохранённым записям.

## Отделяем ключ поиска от строки \{#separate-a-search-key-from-the-row\}

**Индекс** хранит ключи поиска и сведения, по которым можно обратиться к подходящим строкам. B-дерево PostgreSQL по `order_id` может сопоставлять каждому номеру заказа физические адреса позиций. Номер здесь служит ключом поиска и может повторяться. Две записи индекса с ключом 103 могут ссылаться на разные строки. У таблицы может быть несколько индексов для разных групп запросов. ([PostgreSQL 18, Index Types](#references); [SQLite, Query Planning](#references))

Выполним [подготовку шести позиций](/ru/notes/sql/tables-and-queries#a-reproducible-table) и создадим индекс в той же сессии.

```sql
CREATE INDEX order_lines_by_order ON order_lines (order_id);

SELECT line_no, product, quantity
FROM order_lines
WHERE order_id = 103
ORDER BY line_no;
```

| line_no | product | quantity |
| ---: | --- | ---: |
| 1 | coffee | 2 |
| 2 | tea | 1 |

Запрос возвращает одни и те же строки с индексом и без него. **Путь доступа** (access path) — способ получить эти строки. Для таблицы из шести строк СУБД может предпочесть просмотр кучи. Индекс даёт ещё один возможный план. Порядок результата по-прежнему задан `ORDER BY line_no`.

## Спускаемся по B-дереву \{#descend-through-a-b-tree\}

**B-дерево** хранит ключи в порядке и держит листья на одной глубине. Во внутренних страницах есть разделители и ссылки на дочерние страницы. На каждой странице поиск выбирает ветвь по разделителям. Листовые страницы содержат записи, через которые получаем подходящие строки. На учебной схеме левый лист содержит ключи меньше 103, а правый начинается с 103. Поиск по равенству читает корень, затем правый лист. В нём находятся оба адреса для 103. В реальном индексе записи могут лежать на нескольких листовых страницах, а повторяющиеся ключи могут храниться иначе. ([Bayer и McCreight, 1972](#references); [PostgreSQL 18, B-tree Implementation](#references))

Если две найденные ссылки указывают на разные страницы кучи, обычный поиск по индексу в этой модели может обратиться к четырём разным страницам. Две относятся к индексу, две к куче. Если обе строки лежат на одной странице кучи, получится три. Это обращения к страницам учебной раскладки. Попадания в буфер позволяют избежать части загрузок из хранилища. Для диапазона `order_id >= 102 AND order_id < 104` дерево находит первый подходящий ключ и читает следующие записи по порядку до верхней границы. Широкий диапазон может затронуть столько страниц кучи, что дешевле окажется полный просмотр.

## Выбираем путь доступа под предикат \{#use-the-access-path-that-fits-the-predicate\}

**Хеш-индекс** (hash index) PostgreSQL хранит хеш-код, вычисленный по индексируемому значению. Сравнение по равенству может использовать этот код для поиска кандидатов. У разных значений возможен одинаковый хеш, поэтому одного совпадения хеша для проверки равенства недостаточно. Порядок хешей отличается от порядка ключей. Хеш-индексы PostgreSQL поддерживают равенство и не дают упорядоченный проход по диапазону. B-деревья поддерживают равенство и сравнения по порядку ключей. ([PostgreSQL 18, Index Types](#references))

Индекс занимает место, и его нужно обслуживать при вставке строк и изменении индексируемых значений. В B-дереве добавление записи на заполненную страницу может разделить её и добавить разделитель в родителя. Разделение может распространиться вверх по дереву. Компромисс зависит от запросов, которые используют индекс, и записей, при которых он обновляется. ([Bayer и McCreight, 1972](#references); [PostgreSQL 18, B-tree Implementation](#references))

## Источники \{#references\}

1. PostgreSQL Global Development Group. Документация PostgreSQL 18. [Index Types, §11.2](https://www.postgresql.org/docs/18/indexes-types.html) сравнивает предикаты для B-дерева и хеш-индекса. [B-tree Implementation, §65.1.4](https://www.postgresql.org/docs/18/btree.html#BTREE-IMPLEMENTATION) описывает ссылки из листьев и деление страниц.
2. Rudolf Bayer и Edward M. McCreight. [Organization and Maintenance of Large Ordered Indexes](https://rtheunissen.github.io/bst/docs/references/1972_bayer_mccreight.pdf). Acta Informatica, 1, 173–189, 1972. Определяет страницы B-дерева и описывает поиск и разделение.
3. SQLite Project. [Query Planning, §§1.3–1.4](https://www.sqlite.org/queryplanner.html). Описывает поиск по упорядоченному индексу с последующим чтением строк и стоимость нескольких совпадений.
