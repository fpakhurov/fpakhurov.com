Магазину нужен список проданных товаров. У [шести позиций заказа](/ru/notes/sql/tables-and-queries#what-does-one-row-mean) разные идентификаторы. Название описывает товар, и чай встречается в трёх позициях. Ответ зависит от того, что означает одна строка результата. Это может быть позиция заказа или товар.

## Почему запрос повторяет значение \{#why-a-query-repeats-a-value\}

Первый запрос читает название товара из каждой позиции заказа. Второй возвращает по одной строке на каждое название.

```sql
SELECT product
FROM order_lines
ORDER BY product;

SELECT DISTINCT product
FROM order_lines
ORDER BY product;
```

| Товар | Повторы в `SELECT` | Повторы в `SELECT DISTINCT` |
| --- | --- | --- |
| cocoa | 1 | 1 |
| coffee | 2 | 1 |
| tea | 3 | 1 |

В первом результате шесть строк. Проекция на столбец `product` оставляет по одной выходной строке на каждую входную. **Мультимножество** хранит число вхождений каждого элемента. Кратность `tea` равна трём, потому что это значение дают позиции 101/1, 102/1 и 103/2. Математическое множество хранит только принадлежность элемента. В классической реляционной алгебре проекция даёт множество кортежей, по одному на каждое различное сочетание оставшихся атрибутов. В SQL обычный `SELECT` подразумевает `ALL` и сохраняет кратности. [Павло, 2025, §§4, 6](#references) [PostgreSQL 18, SELECT](#references)

`DISTINCT` сравнивает выходные строки целиком. В `SELECT DISTINCT product, quantity` две строки `('tea', 1)` сливаются в одну, а `('tea', 2)` остаётся отдельно. Результат содержит пять пар. Если добавить к выходу `order_id` и `line_no`, по ним можно различить все шесть позиций из примера. Тогда `DISTINCT` ничего не удалит. Сначала выберите поля, которые описывают одну единицу ответа, и затем убирайте повторы.

## Пропуски в результате DISTINCT \{#missing-values-in-a-distinct-result\}

Пусть в поступивших данных не хватает двух предварительных цен, а одна известна и равна 350 копейкам. `VALUES` задаёт эти три строки, не меняя данные магазина.

```sql
SELECT DISTINCT price_cents
FROM (VALUES (NULL::integer), (350), (NULL)) AS feed(price_cents)
ORDER BY price_cents NULLS LAST;
```

Результат содержит `350`, затем один `NULL`. Сравнение `price_cents = NULL` по-прежнему даёт неизвестное значение. При удалении дубликатов действует другое правило сравнения. Два пропуска на одном месте выходной строки для этой операции неразличимы. Одна строка с `NULL` говорит, что во входе есть хотя бы один пропуск. По ней нельзя определить число пропусков. [PostgreSQL 18, Select Lists](#references) [SQLite, §2.6](#references)

## Ограничению нужен порядок \{#a-limit-needs-an-order\}

Магазину также нужна самая дорогая позиция. Вычислим сумму в копейках и запросим одну строку.

```sql
SELECT order_id, line_no,
       quantity * unit_price_cents AS line_total_cents
FROM order_lines
ORDER BY line_total_cents DESC
LIMIT 1;
```

Позиции 103/1 и 104/1 стоят по 1200 копеек. По единственному ключу сортировки они равны, поэтому запрос может вернуть любую из них. Даже если несколько запусков подряд возвращают одну и ту же строку, это не даёт гарантии на случай равенства. Без `ORDER BY` результат вообще не обязан попасть в группу с суммой 1200 копеек. Само удаление дубликатов тоже не гарантирует порядок. [PostgreSQL 18, §§7.5–7.6](#references)

Для выбора одной позиции зададим правило на случай равенства. Сначала сравним суммы от большей к меньшей. При равной сумме возьмём меньший номер заказа. Если совпадают и номера заказов, возьмём меньший номер позиции. Пара `(order_id, line_no)` различает все позиции в примере.

```sql
SELECT order_id, line_no,
       quantity * unit_price_cents AS line_total_cents
FROM order_lines
ORDER BY line_total_cents DESC, order_id ASC, line_no ASC
LIMIT 1;
```

Позиция 103/1 идёт первой, потому что 103 меньше 104. Направление сортировки действует на тот ключ, после которого оно указано. Здесь по убыванию идёт только сумма. [PostgreSQL 18, §7.5](#references)

Если нужны все позиции с максимальной суммой, оставьте сумму единственным ключом и замените `LIMIT 1` на `FETCH FIRST 1 ROW WITH TIES`. Запрос вернёт обе позиции по 1200 копеек. Равенство проверяется по всему ключу сортировки, поэтому добавление идентификатора позиции изменит состав результата. [PostgreSQL 18, SELECT](#references)

Если сумма может быть неизвестна, укажите положение пропусков. В PostgreSQL `DESC` по умолчанию ставит их первыми, поэтому единственное место в результате может занять строка с пропуском. С `DESC NULLS LAST` известные суммы идут первыми. Если в результате допустимы только известные суммы, исключите пропуски ещё и в `WHERE`. В SQLite при `DESC` пропуски по умолчанию идут последними. В запросах для обеих систем положение пропусков стоит задать явно. [PostgreSQL 18, §7.5](#references) [SQLite, §4](#references)

## Порядок при изменении данных \{#a-stable-order-over-changing-data\}

`OFFSET` пропускает строки отсортированного результата. Для исходных шести строк порядок с дополнительными ключами начинается с 103/1, 104/1, 101/1. Запрос с `LIMIT 2` возвращает первые две, а `LIMIT 2 OFFSET 2` начинает с 101/1. Пусть между запросами стала видна позиция 107/1 на 1500 копеек. Второй запрос теперь пропускает 107/1 и 103/1. Он начинает с 104/1 и повторяет строку с первой страницы, хотя оба запроса используют одни и те же ключи сортировки. [PostgreSQL 18, §§7.6, 13.2.1](#references)

Полный порядок однозначно определяет позиции для заданных входных данных. Чтобы несколько запросов увидели одни и те же входные данные, нужна отдельная гарантия. [Вводный конспект по базам данных](/ru/notes/databases/why-databases) объясняет, когда подтверждённые изменения становятся видны между запросами.

## Дальше \{#next\}

`DISTINCT` сообщает, какие товары встретились в данных. Чтобы получить количество или общую сумму по каждому товару, нужно собрать его строки вместе и вычислить результат для группы. Тема «Группировка и агрегация» в разделе [«Объединение строк»](/ru/notes/sql#section-2) разбирает эту операцию.
