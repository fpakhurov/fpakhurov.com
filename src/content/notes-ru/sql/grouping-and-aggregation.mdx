В отчёте о продажах нужна строка на каждый товар, с количеством проданных единиц и суммой. В [таблице заказов](/ru/notes/sql/tables-and-queries#what-does-one-row-mean) чай занимает три позиции. `DISTINCT product` оставит одно название, но количества и цены уже не попадут в отчёт. Прежде чем вывести одну строку, нужно объединить данные из трёх позиций.

## Одна строка результата на группу \{#one-result-row-per-group\}

**Агрегат** вычисляет одно значение по набору входных строк. В запросе ниже `GROUP BY product` относит все строки одного товара к одной группе. Затем три вызова в `SELECT` вычисляют показатели по каждой группе. Сначала выполним [подготовку позиций заказа](/ru/notes/sql/tables-and-queries#a-reproducible-table) в той же сессии. ([PostgreSQL 18, §§2.7 и 7.2.3](#references))

```sql
SELECT product,
       COUNT(*) AS lines,
       SUM(quantity) AS units,
       SUM(quantity * unit_price_cents) AS revenue_cents
FROM order_lines
GROUP BY product
ORDER BY product;
```

| product | lines | units | revenue_cents |
| --- | ---: | ---: | ---: |
| cocoa | 1 | 3 | 1200 |
| coffee | 2 | 3 | 1800 |
| tea | 3 | 4 | 1400 |

В группу чая попадают количества 2, 1 и 1. Считаем три строки и получаем четыре единицы товара. Выражение для суммы даёт 700, 350 и 350 копеек, затем `SUM` складывает их в 1400. Зерно результата — одна строка на товар. Если добавить `order_id` в `GROUP BY`, получится одна строка на каждую встретившуюся пару товара и заказа. Чай в таком результате займёт три строки.

<GroupTea lang="ru" />

Во входных данных возможны повторы. Каждая продажа учитывается отдельно, даже если совпадают количество и цена. `SUM(DISTINCT quantity)` сложит для чая только различные значения 1 и 2. Получится 3 единицы вместо 4. `COUNT(DISTINCT order_id)` отвечает на другой вопрос. Он считает разные заказы для товара, пропуская отсутствующие идентификаторы. Для чая это 3. Совпадение с `COUNT(*)` в этом примере следует из данных. В одном заказе могли быть две позиции с одним и тем же товаром. ([PostgreSQL 18, §§4.2.7 и 9.21](#references); [DuckDB 1.4, DISTINCT clause in aggregate functions](#references))

## Фильтруем входные строки или группы \{#filter-input-rows-or-filter-groups\}

Пусть отчёт должен показывать товары, выручка по которым достигла 1500 копеек. Кофе подходит, потому что его две позиции в сумме дают 1800. Ни одна из них по отдельности не достигает 1500. Если применить порог к отдельным позициям, обе будут отброшены ещё до вычисления суммы.

```sql
SELECT product,
       SUM(quantity * unit_price_cents) AS revenue_cents
FROM order_lines
GROUP BY product
HAVING SUM(quantity * unit_price_cents) >= 1500
ORDER BY product;
```

`HAVING` видит один итог на группу, поэтому результат содержит одну строку `(coffee, 1800)`. Если нужно ограничить позиции, которые участвуют в подсчёте, используем `WHERE`. Например, добавим `WHERE order_id >= 103` перед `GROUP BY`. Для кофе останется только позиция на 1200 копеек. Тогда ни одна группа не пройдёт `HAVING`. `WHERE` отбирает вход, а `HAVING` — итоги. Это логическое описание результата. СУБД может выбрать любой физический план, который вычисляет тот же ответ. ([PostgreSQL 18, §§2.7 и 7.2.3](#references))

## Какие значения может вернуть группа \{#which-values-can-the-group-return\}

Попробуем добавить `order_id` к результату первого запроса, сохранив группировку только по `product`. Для чая есть заказы 101, 102 и 103. Запрос не задаёт правило выбора одного из них, и PostgreSQL его отклоняет. Можно запросить по одной строке на товар и заказ или указать агрегат, например `MIN(order_id)`, чтобы получить одно определённое значение на товар. Минимальный идентификатор имеет смысл, если отчёту действительно нужен наименьший номер. Он не обязательно относится к самому раннему заказу.

PostgreSQL может разрешить столбец без группировки и агрегирования, когда в ключ группировки входит первичный ключ его таблицы. Ключ определяет столбец, поэтому возможное значение только одно. SQLite допускает более широкий класс запросов со столбцами вне группировки и может выбрать значение из произвольной строки. Явное указание группировки или агрегата делает правило выбора видимым в разных СУБД. ([PostgreSQL 18, §7.2.3](#references); [SQLite, §2.5](#references))

## Пропуски и пустой вход \{#missing-values-and-empty-input\}

В отдельной загрузке пришли две позиции с чаем. Для одной известна сумма 700 копеек, для другой сумма пока отсутствует. Нужно отделить известную часть суммы от полноты загрузки.

```sql
SELECT COUNT(*) AS input_rows,
       COUNT(amount_cents) AS known_amounts,
       SUM(amount_cents) AS known_total_cents,
       AVG(amount_cents) AS mean_known_cents
FROM (VALUES (700), (NULL::integer)) AS batch(amount_cents);
```

Получаем 2 входные строки, 1 известную сумму, итог 700 и среднее 700. `COUNT(*)` считает строки. `COUNT(amount_cents)` считает значения выражения без `NULL`. `SUM` и `AVG` здесь также используют только известные значения. Среднее делит известный итог на число известных сумм. Если бы вместо пропуска был записан ноль, он считался бы известным значением, а среднее стало бы равно 350. ([PostgreSQL 18, §9.21](#references); [DuckDB 1.4, Handling NULL values](#references))

Если `WHERE` отбрасывает все строки, запрос с агрегатом без `GROUP BY` всё равно возвращает одну итоговую строку. Оба счётчика равны нулю, сумма и среднее равны `NULL`. С `GROUP BY product` на пустом входе не образуется ни одной группы, поэтому результат пуст. В непустой группе все суммы также могут оказаться равными `NULL`. Тогда `COUNT(*)` больше нуля, `COUNT(amount_cents)` равен нулю, а `SUM(amount_cents)` равен `NULL`. Выражение `COALESCE(SUM(amount_cents), 0)` намеренно показывает ноль вместо отсутствующего итога. Если отчёту важно различие, сохраним счётчик известных значений.
