Магазину нужна таблица с каждой продажей, её суммой и итогом по товару. Запрос с группировкой даёт итог и сворачивает продажи. Второй запрос мог бы присоединить итог к каждой продаже. Оконная функция выражает вычисление по связанным строкам и сохраняет каждую продажу в результате.

## Добавим к каждой строке итог товара \{#give-every-row-its-product-total\}

В примере новый набор из семи продаж. Выполним подготовку один раз в новом сеансе. Одна строка представляет одну продажу, `sold_on` хранит её дату, а `cents` — полную сумму. Две продажи чая приходятся на одну дату, и у двух продаж чая совпадает сумма.

```sql
CREATE TEMP TABLE sales (
    sale_id integer PRIMARY KEY,
    product text NOT NULL,
    sold_on date NOT NULL,
    cents integer NOT NULL
);

INSERT INTO sales VALUES
    (201, 'tea',    DATE '2026-01-01', 100),
    (202, 'tea',    DATE '2026-01-02', 200),
    (203, 'tea',    DATE '2026-01-02', 300),
    (204, 'tea',    DATE '2026-01-05', 300),
    (205, 'tea',    DATE '2026-01-06', 500),
    (206, 'coffee', DATE '2026-01-01', 300),
    (207, 'coffee', DATE '2026-01-05', 300);
```

```sql
SELECT sale_id, product, cents,
       SUM(cents) OVER (PARTITION BY product) AS product_total
FROM sales
ORDER BY sale_id;
```

Конструкция `OVER` превращает агрегат в **оконную функцию** (window function). `PARTITION BY product` делит входные строки на связанные группы, которые называются **разделами** (partitions). Здесь агрегат использует весь раздел текущей строки. Для чая сумма равна $100+200+300+300+500=1400$. Для кофе она равна $300+300=600$. В новом столбце у каждой из пяти строк чая стоит 1400, у каждой из двух строк кофе — 600. В результате по-прежнему семь строк. С `GROUP BY product` осталось бы две. ([PostgreSQL 18, §3.5](#references), [SQLite, §§1–2.1](#references))

Итог по товару повторяется как контекст каждой продажи. Если сложить его по всем семи строкам, получится $5\cdot1400+2\cdot600=8200$. Одни и те же итоги посчитаны несколько раз. Сумма отдельных продаж равна 2000. После оконного вычисления строка по-прежнему описывает продажу.

## Упорядочим связанные строки \{#put-related-rows-in-order\}

Магазину нужны две самые крупные продажи каждого товара. `ORDER BY` внутри `OVER` задаёт порядок для вычисления. Конечный `ORDER BY` задаёт порядок вывода. Эти решения принимаются отдельно. ([PostgreSQL 18, §3.5](#references), [SQLite, §2](#references))

```sql
SELECT sale_id, product, cents,
       ROW_NUMBER() OVER (
           PARTITION BY product ORDER BY cents DESC, sale_id
       ) AS position,
       RANK() OVER (PARTITION BY product ORDER BY cents DESC) AS rank,
       DENSE_RANK() OVER (PARTITION BY product ORDER BY cents DESC) AS dense_rank
FROM sales
ORDER BY product, position;
```

Для чая порядок по убыванию суммы ставит продажу на 500 копеек первой. Суммы двух продаж на 300 копеек равны. Строки с одинаковыми значениями всех ключей оконной сортировки называются **равными по порядку** (peers). Уникальный идентификатор продажи разрешает совпадение для `ROW_NUMBER()`, которая назначает разные позиции. Две другие функции используют только сумму, поэтому строки с 300 копейками для них равны по порядку.

| ID продажи чая | Сумма | `ROW_NUMBER` | `RANK` | `DENSE_RANK` |
| --- | --- | --- | --- | --- |
| 205 | 500 | 1 | 1 | 1 |
| 203 | 300 | 2 | 2 | 2 |
| 204 | 300 | 3 | 2 | 2 |
| 202 | 200 | 4 | 4 | 3 |
| 201 | 100 | 5 | 5 | 4 |

`RANK` даёт позицию начала группы равных строк. Две строки с рангом 2 занимают позиции 2 и 3, поэтому следующий ранг равен 4. `DENSE_RANK` считает группы равных строк, и его следующее значение равно 3. Если нужно не больше двух продаж каждого товара, используем номера строк с дополнительным ключом. Если нужно включить все строки с суммой на второй позиции, используем ранг только по сумме. Добавление идентификатора к ключам ранжирования разделило бы равные строки. ([PostgreSQL 18, §9.22](#references))

## Возьмём соседнюю строку \{#read-a-neighbour\}

Для сравнения во времени упорядочим продажи по дате, затем по идентификатору. Второй ключ фиксирует порядок внутри каждой даты в этом примере. `LAG` берёт значение из предыдущей строки, а `LEAD` — из следующей. По умолчанию обе функции смещаются на одну строку и возвращают `NULL`, если нужная строка лежит за пределами раздела. Конструкция `WINDOW` даёт общему определению имя. ([PostgreSQL 18, §9.22](#references), [DuckDB 1.4, Window Functions](#references))

```sql
SELECT sale_id, cents,
       LAG(cents) OVER by_time AS previous_cents,
       LEAD(cents) OVER by_time AS next_cents
FROM sales
WHERE product = 'tea'
WINDOW by_time AS (ORDER BY sold_on, sale_id)
ORDER BY sold_on, sale_id;
```

Для продажи чая 203 предыдущая сумма равна 200 из продажи 202, а следующая равна 300 из продажи 204. У продажи 201 нет предыдущей строки. У продажи 205 нет следующей. Разность `cents - LAG(cents) OVER by_time` сравнивает соседние продажи в этом порядке. Это могут быть продажи за одну дату или за даты с пропуском нескольких дней.

## Отфильтруем после вычисления \{#filter-after-calculating\}

PostgreSQL вычисляет оконные функции по строкам, которые дошли до них после `WHERE`, группировки и `HAVING`. Условие в `WHERE` того же оператора ещё не видит оконный результат. Вынесем вычисление в CTE или подзапрос и отфильтруем его выход. ([PostgreSQL 18, §3.5](#references))

```sql
WITH ranked AS (
    SELECT sale_id, product, cents,
           ROW_NUMBER() OVER (
               PARTITION BY product ORDER BY cents DESC, sale_id
           ) AS position
    FROM sales
)
SELECT sale_id, product, cents
FROM ranked
WHERE position <= 2
ORDER BY product, position;
```

Запрос оставляет продажи кофе 206 и 207 и продажи чая 205 и 203. Если поместить фильтр по `cents` внутрь CTE, изменится набор строк, которые претендуют на эти позиции. В DuckDB 1.4 условие `QUALIFY` фильтрует оконный результат в том же запросе. Пример с CTE использует синтаксис PostgreSQL. ([DuckDB 1.4, Window Functions](#references))
