Одна единица чая стоит 350 копеек. Если поделить 350 на 100 в запросе PostgreSQL, получится 3 рубля. Для другой позиции цена ещё не поступила. Произведение количества на цену не даёт суммы, которую можно сравнить с порогом. В обоих случаях результат зависит от операндов. Сначала проверяем тип каждого операнда, затем наличие значения.

## Тип определяет операцию \{#the-type-chooses-the-operation\}

**Тип данных** (data type) определяет, какие значения даёт выражение и какие операторы их принимают. В [расчёте стоимости позиции](/ru/notes/sql/select-and-expressions#which-boundaries-are-included) количество и цена имели тип `integer`. После умножения получилось целое число копеек. При переводе в рубли нужно сохранить дробную часть.

```sql
SELECT 350 / 100 AS whole_dollars,
       CAST(350 / 100 AS numeric) AS cast_after,
       CAST(350 AS numeric) / 100 AS cast_before;
```

| whole_dollars | cast_after | cast_before |
| --- | --- | --- |
| 3 | 3 | 3,5 |

В PostgreSQL оба небольших целых литерала получают тип `integer`. При делении целых дробная часть отбрасывается в сторону нуля. Конструкция `CAST(expression AS type)` приводит результат выражения к указанному типу. Если записать `CAST` снаружи, на вход попадёт уже вычисленная тройка. Если привести один из операндов, PostgreSQL получит `numeric` и `integer`. Для такого деления PostgreSQL приведёт целое число к `numeric` и сохранит полрубля. В таблице приведены значения. Клиент может напечатать дробный результат с нулями в конце. [PostgreSQL 18, §§4.1.2.6 и 9.3](#references)

Выбор операции зависит от диалекта. В DuckDB выражение `350 / 100` с целыми операндами даёт 3,5. Целочисленное деление там записывается как `//`. При переносе запроса на другой движок запись может остаться прежней, а значение измениться. [DuckDB 1.4, Numeric functions](#references)

## Где округлять \{#choose-where-rounding-happens\}

В целых копейках можно представить суммы с шагом в одну копейку. Их можно складывать, вычитать и умножать на целое количество, пока результаты помещаются в выбранный целочисленный тип. При расчёте процентов может получиться доля копейки. Сначала вычисляем сумму, затем применяем правило округления до копеек.

PostgreSQL хранит конечные десятичные дроби вроде 0,1 и 0,2 точно в типе `numeric`. Тип `double precision` хранит многие такие дроби приближённо в двоичной системе. У конечной двоичной дроби знаменатель является степенью двойки. У несократимой дроби для 0,1 знаменатель равен 10 и содержит множитель 5. Конечной двоичной записи для неё нет. В следующем сравнении сумма двух приближений округляется до другого числа с плавающей точкой, чем число, которым представлена дробь 0,3.

```sql
SELECT 0.1 + 0.2 = 0.3 AS decimal_equal,
       CAST(0.1 AS double precision) + CAST(0.2 AS double precision)
           = CAST(0.3 AS double precision) AS float_equal,
       CAST(3.505 AS numeric(5, 2)) AS rounded_amount;
```

| decimal_equal | float_equal | rounded_amount |
| --- | --- | --- |
| `TRUE` | `FALSE` | 3,51 |

В первом сравнении литералы имеют тип `numeric`. В последнем столбце запись `numeric(5, 2)` задаёт **точность** (precision) в пять десятичных цифр и **масштаб** (scale) в две цифры после запятой. У конечного значения, округлённого до такого масштаба, остаётся до трёх цифр перед запятой. Число 3,505 лежит ровно посередине между 3,50 и 3,51. Для `numeric` PostgreSQL округляет такие случаи в сторону от нуля, поэтому получается 3,51. Если после округления нужны четыре цифры до запятой, возникает ошибка. Этот предел важен, когда поле для цены одной единицы начинают использовать для более крупной суммы. [PostgreSQL 18, §8.1](#references)

## Для сравнения нужны совместимые типы \{#a-comparison-needs-compatible-types\}

Пусть в выгрузке CSV цена приходит текстом. PostgreSQL может сравнить целое число 350 с литералом `'350'` в кавычках. Сначала тип литерала не задан. PostgreSQL определяет его как целочисленный по другому операнду. У столбца типа `text` тип уже известен. Сопоставим эти случаи с явным приведением.

```sql
SELECT 350 = '350' AS literal_match,
       350 = CAST(text '350' AS integer) AS converted_match;
```

Оба результата равны `TRUE`. В следующем запросе литерал `text '350'` имеет заданный тип и заменяет текстовый столбец. PostgreSQL сообщает `operator does not exist: integer = text`. Явное приведение из предыдущего запроса разбирает текст как целое число. На значении вроде `'pending'` такое приведение выдаёт ошибку, поэтому при загрузке нужно решить, как обрабатывать некорректные значения. [PostgreSQL 18, §§4.1.2 и 10.2](#references)

```sql
SELECT 350 = text '350';
```

SQLite тоже учитывает операнды при выборе преобразования. Например, его правила сравнения применяют числовое сродство (affinity) к тексту с корректной записью числа, когда другой операнд — столбец с числовым сродством. Сродство задаёт предпочтительный тип. В SQLite оно есть у каждого столбца таблицы и у некоторых выражений. Ошибка в примере выше следует из правил выбора оператора в PostgreSQL. [SQLite, Datatypes, §§3.2 и 4.2](#references)

## Неизвестная цена даёт неизвестную стоимость \{#an-unknown-price-leaves-an-unknown-amount\}

Магазин готовит расчёт до того, как поступят все цены. Возьмём четыре позиции. Для 103/1 цена ещё неизвестна, а 105/1 — бесплатный образец с известной ценой ноль.

```sql
CREATE TEMP TABLE order_line_quotes (
    line_key text,
    quantity integer,
    unit_price_cents integer
);

INSERT INTO order_line_quotes VALUES
    ('101/1', 2, 350),
    ('102/1', 1, 350),
    ('103/1', 2, NULL),
    ('105/1', 1, 0);
```

`NULL` обозначает отсутствие значения. В целочисленном столбце, допускающем пропуски, одна строка может содержать этот маркер, а другая — обычное целое число. В нашем примере приложение трактует маркер как «цена ещё не поступила». Выражения `2 * NULL` и `NULL >= 700` дают `NULL`. В первом случае неизвестна сумма, во втором неизвестен результат сравнения. Для позиции 105/1 известны и количество, и нулевая цена, поэтому стоимость равна нулю.

```sql
SELECT line_key,
       quantity * unit_price_cents AS amount_cents,
       quantity * unit_price_cents >= 700 AS reaches_threshold
FROM order_line_quotes
ORDER BY line_key;
```

| line_key | amount_cents | reaches_threshold |
| --- | --- | --- |
| 101/1 | 700 | `TRUE` |
| 102/1 | 350 | `FALSE` |
| 103/1 | `NULL` | `NULL` |
| 105/1 | 0 | `FALSE` |

## Фильтр оставляет строки с TRUE \{#a-filter-keeps-only-true\}

Обозначим сравнение с порогом через $P$. SQL использует **трёхзначную логику** (three-valued logic). Третье значение означает «неизвестно» и представлено в логическом выражении как `NULL`. Отрицание неизвестного результата тоже даёт неизвестный результат. Поэтому `WHERE NOT (quantity * unit_price_cents >= 700)` вернёт 102/1 и 105/1. Позиция 103/1 не войдёт в выборку. Для неё ни $P$, ни `NOT P` не истинны, а `WHERE` требует истинного результата. [PostgreSQL 18, §§7.2.2 и 9.1](#references)

<NullFilter />

Иногда одного известного операнда хватает для ответа. Ложный операнд делает `AND` ложным при любом втором операнде. Истинный операнд делает `OR` истинным. Для позиции 103/1 условие `quantity = 1 AND P` ложно, потому что количество равно 2. Условие `quantity >= 2 OR P` истинно. Здесь `P` обозначает сравнение с порогом. Правила дают логический результат при любом порядке вычисления операндов.

| Выражение с неизвестным `P` | Результат |
| --- | --- |
| `NOT P` | `NULL` |
| `FALSE AND P` | `FALSE` |
| `TRUE AND P` | `NULL` |
| `FALSE OR P` | `NULL` |
| `TRUE OR P` | `TRUE` |

## Проверка пропуска и подстановка значения \{#test-for-absence-before-choosing-a-substitute\}

Обычное сравнение отдельных значений на равенство даёт неизвестный результат, если один или оба операнда равны `NULL`. Поэтому `WHERE unit_price_cents = NULL` возвращает ноль строк по стандартным правилам сравнения. Проверка `IS NULL` отвечает на вопрос о наличии значения и даёт определённый логический результат. Следующий запрос вернёт 103/1. [PostgreSQL 18, §9.2](#references)

```sql
SELECT line_key
FROM order_line_quotes
WHERE unit_price_cents IS NULL;
```

Для вывода можно подготовить текстовую подпись. `COALESCE` возвращает первый аргумент, для которого есть значение, и приводит аргументы к общему типу. Здесь оба аргумента можно представить текстом, а для пропуска используется надпись «pending».

```sql
SELECT line_key,
       COALESCE(CAST(unit_price_cents AS text), 'pending') AS display_price
FROM order_line_quotes
ORDER BY line_key;
```

Получаем строки `350`, `350`, `pending` и `0`. Если подставить `COALESCE(unit_price_cents, 0)` в исходное умножение, стоимость позиции 103/1 станет нулевой. Цена ещё неизвестна, но после подстановки позиция пройдёт фильтр на суммы ниже 700. Подстановка внутри вычисления задаёт правило обработки данных и может изменить состав выборки. [PostgreSQL 18, §9.18.2](#references)
