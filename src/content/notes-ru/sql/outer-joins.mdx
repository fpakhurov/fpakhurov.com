Мята есть в каталоге, но у неё нет продаж. Отчёт на основе [внутреннего соединения](/ru/notes/sql/inner-joins) получает строки для чая, кофе и какао. Мята исчезает до подсчёта продаж. Чтобы показать отсутствие продаж, сохраним строку каталога при соединении.

## Что происходит со строкой без пары \{#what-happens-to-an-unmatched-row\}

Используем [каталог](/ru/notes/sql/inner-joins#match-rows-by-a-shared-field) и шесть строк `order_lines` из того же примера. Поместим каталог слева, потому что в отчёте нужны все его товары. **Левое внешнее соединение** (left outer join) возвращает все подходящие пары и добавляет по одной строке для каждой левой строки без пары. В добавленной строке все столбцы правой стороны равны `NULL`. Слово `OUTER` в `LEFT OUTER JOIN` можно опустить. ([PostgreSQL 18, §7.2.1](#references); [DuckDB 1.4, Outer joins](#references))

```sql
SELECT c.product, l.order_id, l.line_no, l.quantity
FROM catalogue AS c
LEFT JOIN order_lines AS l ON l.product = c.product
ORDER BY c.product, l.order_id, l.line_no;
```

| product | order_id | line_no | quantity |
| --- | ---: | ---: | ---: |
| cocoa | 104 | 1 | 3 |
| coffee | 101 | 2 | 1 |
| coffee | 103 | 1 | 2 |
| mint | NULL | NULL | NULL |
| tea | 101 | 1 | 2 |
| tea | 102 | 1 | 1 |
| tea | 103 | 2 | 1 |

У мяты есть одна строка, хотя позиций заказа для неё нет. Значения `NULL` появились при соединении. Для остальных товаров получается столько строк, сколько найдено совпадений. Сохранение строк каталога гарантирует хотя бы одну строку на товар. При нескольких совпадениях будут дополнительные строки.

## Считаем совпадения \{#count-the-matches\}

Отчёту нужен один результат на товар. Сгруппируем строки и посчитаем значения выражения, которое известно для каждого настоящего совпадения. В примере `l.order_id` есть в каждой реальной позиции и отсутствует в добавленной строке мяты. ([PostgreSQL 18, §9.21](#references))

```sql
SELECT c.product,
       COUNT(*) AS joined_rows,
       COUNT(l.order_id) AS sales_lines,
       COALESCE(SUM(l.quantity), 0) AS units
FROM catalogue AS c
LEFT JOIN order_lines AS l ON l.product = c.product
GROUP BY c.product
ORDER BY c.product;
```

| product | joined_rows | sales_lines | units |
| --- | ---: | ---: | ---: |
| cocoa | 1 | 1 | 3 |
| coffee | 2 | 2 | 3 |
| mint | 1 | 0 | 0 |
| tea | 3 | 3 | 4 |

`COUNT(*)` учитывает добавленную строку мяты, а `COUNT(l.order_id)` её пропускает. `SUM(l.quantity)` дала бы для мяты `NULL`, поэтому `COALESCE` заменяет итог нулём. Здесь это уместно, потому что все настоящие количества известны. Если бы количество могло отсутствовать у настоящего совпадения, то группа из одних пропусков также получила бы ноль. Число совпадений и сумма тогда по-прежнему сообщали бы разное.

## Фильтруем пары или результат соединения \{#filter-the-pairs-or-the-joined-result\}

Пусть отчёт должен сохранять все товары и считать только позиции с тремя единицами или более. Включим это требование в условие совпадения. Для позиции с двумя единицами чая коды совпадают, но количество меньше порога. Эта строка не образует пару. Остальные позиции чая также не подходят, поэтому левое соединение добавляет для него одну строку.

```sql
SELECT c.product, COUNT(l.order_id) AS large_lines
FROM catalogue AS c
LEFT JOIN order_lines AS l
    ON l.product = c.product AND l.quantity >= 3
GROUP BY c.product
ORDER BY c.product;
```

Получаем какао с 1, а затем кофе, мяту и чай с 0. Если перенести условие на количество в `WHERE`, результат изменится.

```sql
SELECT c.product, COUNT(l.order_id) AS large_lines
FROM catalogue AS c
LEFT JOIN order_lines AS l ON l.product = c.product
WHERE l.quantity >= 3
GROUP BY c.product
ORDER BY c.product;
```

Теперь соединение находит пары для чая и кофе, поэтому добавленных строк для них нет. Последующий `WHERE` отбрасывает все их строки, потому что количество в каждой меньше 3. Строка мяты также отбрасывается: `NULL >= 3` даёт неизвестное значение. Остаётся только `(cocoa, 1)`. Если добавить в этот `WHERE` условие `OR l.order_id IS NULL`, мята сохранится, но чай и кофе всё равно исчезнут. Их строки образовали пары по коду, а у этих пар известны идентификаторы заказов. ([PostgreSQL 18, §7.2.1](#references); [SQLite, §2.3](#references))

Одно правило определяет пары, другое отбирает уже соединённые строки. Условие в `ON` задаёт, какие строки считать совпадениями для левой строки, которую требуется сохранить. Если нарушение условия должно удалить всю соединённую строку, используем `WHERE`.

## Какую сторону нужно сохранить \{#which-side-must-be-preserved\}

**Правое внешнее соединение** (right outer join) сохраняет правый вход. Его можно выразить левым соединением с переставленными входами и нужным порядком столбцов. **Полное внешнее соединение** (full outer join) добавляет строки без пары с обеих сторон. Для сверки пусть в каталоге A есть чай и кофе, а в каталоге B чай и какао. Соединение по коду даёт пару для чая. Полное соединение также даёт кофе с пропусками в полях B и какао с пропусками в полях A. Если код встречается несколько раз, по-прежнему возвращаются все подходящие пары. ([PostgreSQL 18, §7.2.1](#references); [DuckDB 1.4, Outer joins](#references))

По результату видно, что продаж мяты было ноль. Если вопрос лишь в том, какие товары продавались, можно проверить наличие подходящей строки и не строить пары. В [подзапросах и проверке существования](/ru/notes/sql/subqueries-and-exists) выразим этим способом наличие и отсутствие связанной записи.
