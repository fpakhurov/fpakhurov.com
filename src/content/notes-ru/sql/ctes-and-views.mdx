Магазину нужны заказы на сумму от 1200 копеек. Начинаем с [шести позиций](/ru/notes/sql/tables-and-queries#a-reproducible-table), вычисляем стоимость каждой позиции, складываем стоимости по заказам и фильтруем суммы. Два отчёта используют одну формулу стоимости. Третьему нужно раскрыть вложенные наборы, поэтому число этапов зависит от данных.

## Дадим каждому этапу имя \{#give-each-stage-a-name\}

**Обобщённое табличное выражение** (common table expression, CTE) — именованный результат запроса в пределах одного оператора. В конструкции `WITH` указываем имя и после `AS` помещаем запрос в скобки. Первое CTE ниже содержит по одной строке на позицию. Второе читает этот результат и даёт по одной строке на заказ. Перед примером создаём позиции из [первого запроса](/ru/notes/sql/tables-and-queries#a-reproducible-table). ([PostgreSQL 18, §7.8.1](#references), [SQLite, §2](#references))

```sql
WITH line_amounts AS (
    SELECT order_id, line_no, quantity * unit_price_cents AS cents
    FROM order_lines
),
order_totals AS (
    SELECT order_id, SUM(cents) AS total_cents
    FROM line_amounts
    GROUP BY order_id
)
SELECT order_id, total_cents
FROM order_totals
WHERE total_cents >= 1200
ORDER BY order_id;
```

Первые две позиции дают для заказа 101 сумму $700+600=1300$ копеек. Заказ 102 даёт 350, заказ 103 — $1200+350=1550$, заказ 104 — 1200. Основной `SELECT` оставляет заказы 101, 103 и 104 с суммами 1300, 1550 и 1200. Заказ 104 попадает ровно на границу отбора.

Внешний `WHERE` читает результат, где на заказ уже приходится одна строка. Фильтр `cents >= 1200` в первом CTE проверял бы отдельные позиции. Он потерял бы обе позиции заказа 101, хотя их общая сумма проходит отбор. Если отслеживать гранулярность на каждой именованной границе, разница становится явной.

Имена описывают логические входы. Они не задают способ хранения результата. В PostgreSQL нерекурсивное CTE с `SELECT` без побочных эффектов может быть встроено во внешний запрос, обычно при одном обращении к CTE. При нескольких обращениях PostgreSQL обычно вычисляет его отдельно. В документации DuckDB 1.4 приведены другое поведение по умолчанию и другие условия встраивания. В запросе выше имена нужны для композиции, которая не зависит от этих решений движка. ([PostgreSQL 18, §7.8.3](#references), [DuckDB 1.4, WITH](#references))

## Сохраним определение между операторами \{#keep-a-definition-between-statements\}

Следующий оператор не видит CTE из предыдущего. Если нескольким запросам нужна одна формула стоимости, **представление** (view) даёт определению запроса имя в базе данных. В примере представление временное, потому что исходная таблица временная. К нему можно обращаться из других операторов до конца текущего сеанса.

```sql
CREATE TEMP VIEW line_amounts AS
SELECT order_id, line_no, quantity * unit_price_cents AS cents
FROM order_lines;

SELECT order_id, SUM(cents) AS total_cents
FROM line_amounts
GROUP BY order_id
HAVING SUM(cents) >= 1200
ORDER BY order_id;
```

Получаем те же три заказа. PostgreSQL вычисляет обычное представление по данным, видимым запросу, который его читает. Если добавить к заказу 104 позицию на 200 копеек и следующему чтению она будет видна, сумма этого заказа станет 1400. **Материализованное представление** хранит результат запроса. В нём может остаться прежнее значение до обновления. Изменение логики представления затрагивает его потребителей, поэтому имена, типы и смысл выходных столбцов образуют интерфейс. ([PostgreSQL 18, CREATE VIEW и §39.3](#references))

## Пройдём заранее неизвестное число шагов \{#follow-an-unknown-number-of-steps\}

Подарочный набор содержит чай и кофе. В состав чая входят листья. Пусть каталог ошибочно указывает, что в состав листьев входит сам подарочный набор. Цепочка из фиксированного числа соединений проходит фиксированное число связей. В рекурсивном CTE результат одного шага становится входом следующего.

```sql
WITH RECURSIVE
edges(bundle, part) AS (
    VALUES ('gift', 'tea'), ('gift', 'coffee'),
           ('tea', 'leaf'), ('leaf', 'gift')
),
walk(item, depth, path) AS (
    SELECT 'gift'::text, 0, ARRAY['gift']::text[]
    UNION ALL
    SELECT e.part, w.depth + 1, w.path || e.part
    FROM walk AS w
    JOIN edges AS e ON e.bundle = w.item
    WHERE NOT (e.part = ANY(w.path))
)
SELECT item, depth
FROM walk
WHERE depth > 0
ORDER BY depth, item;
```

Первая ветка задаёт начальную строку `gift` на глубине 0. Рекурсивная ветка читает текущие рабочие строки `walk`, находит связи, которые начинаются в этих элементах, и формирует новые рабочие строки. На глубине 1 получаем `coffee` и `tea`. На глубине 2 только чай даёт новую строку `leaf`. Следующая связь вернула бы нас к `gift`. Этот элемент уже есть в пути, поэтому предикат его отбрасывает. Рабочих строк больше нет, и запрос останавливается. Внешний `WHERE` исключает начальную строку. Получаем `(coffee, 1)`, `(tea, 1)` и `(leaf, 2)` в заданном порядке. ([PostgreSQL 18, §7.8.2](#references), [SQLite, §§3.2–3.3](#references))

Проверка пути действует внутри одного маршрута. Если две ветки доходят до одного элемента, обе могут его вернуть. Одна выходная строка соответствует посещению элемента по пути. Для списка достижимых элементов оставляем только имена и убираем дубликаты отдельной операцией. Замена `UNION ALL` на `UNION` сама по себе не устраняет повторные посещения, если выход содержит меняющуюся глубину или путь. Внешний `ORDER BY` задаёт порядок вывода и не предписывает движку порядок обхода графа. ([PostgreSQL 18, §§7.8.2.1–7.8.2.2](#references))
