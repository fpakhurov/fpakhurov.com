Магазин в Нью-Йорке закрывает отчёт за 9 марта 2025 года в полночь. Заказ поступил 9 марта в 04:59:59 UTC. В магазине ещё было 8 марта. Нужно правило, которое относит момент времени к дню работы магазина. В том же отчёте заказы группируются по источнику. Если при импорте один источник называется `' WEB '` и `'web'`, нужно задать правило и для этих меток.

## Момент времени и показание календаря \{#an-instant-and-a-calendar-value\}

Тип `date` хранит календарный день. Тип `timestamp without time zone` соединяет календарную дату с показанием часов. В нём можно записать, что в будущую дату магазин открывается в 09:00. Тип `timestamp with time zone`, сокращённо `timestamptz` в PostgreSQL, хранит момент времени. При вводе PostgreSQL интерпретирует значение по часовому поясу или смещению, переводит его в UTC и сохраняет момент. При выводе используется часовой пояс сеанса. Исходное имя пояса не сохраняется. Если отчёту нужен календарь конкретного магазина, пояс нужно хранить отдельно. [PostgreSQL 18, §8.5](#references)

У оператора `AT TIME ZONE` два направления. Для локального `timestamp` он интерпретирует показание часов в заданном поясе и возвращает момент времени. Для `timestamptz` он возвращает локальный `timestamp`, который показывают часы в этом поясе. Здесь момент из первого преобразования показываем в UTC. Результат тогда не зависит от настройки сеанса.

```sql
SELECT
    (TIMESTAMP '2025-03-09 00:00'
        AT TIME ZONE 'America/New_York') AT TIME ZONE 'UTC' AS utc_clock,
    TIMESTAMPTZ '2025-03-09 04:59:59+00'
        AT TIME ZONE 'America/New_York' AS shop_clock;
```

| utc_clock | shop_clock |
| --- | --- |
| 2025-03-09 05:00:00 | 2025-03-08 23:59:59 |

В примерах указываем тип литерала явно. В PostgreSQL у `TIMESTAMP '2025-03-09 05:00+00'` тип `timestamp without time zone`, поэтому `+00` игнорируется. В литерале `TIMESTAMPTZ` явное смещение используется для определения момента времени. Если у значения `timestamptz` нет смещения или пояса, PostgreSQL интерпретирует его с учётом настройки сеанса. [PostgreSQL 18, §§8.5 и 9.9](#references)

## Две полуночи задают период \{#two-midnights-define-the-period\}

Пусть $t_0$ — момент местной полуночи в начале отчётного дня, а $t_1$ — момент следующей местной полуночи. Для заказа с моментом записи $t$ условие отбора имеет вид $t_0 \le t < t_1$. Следующий день использует $t_1$ как нижнюю границу. Строгая верхняя граница относит событие на стыке ровно к одному дню. `BETWEEN` включает оба конца, поэтому два соседних отчёта с таким условием могут посчитать событие на границе дважды.

В Нью-Йорке 9 марта 2025 года часы переводят вперёд. Начальная полночь имеет смещение −05:00. Следующая полночь имеет смещение −04:00. После преобразования получаем 05:00 UTC 9 марта и 04:00 UTC 10 марта. Разность составляет 23 часа. Именованный пояс задаёт правило, которое зависит от даты. Смещение −05:00 для обеих полуночей сдвинуло бы верхнюю границу на час позже. [IANA, Scope and timezone identifiers](#references) [PostgreSQL 18, §9.9](#references)

Создадим четыре учебных заказа около границ интервала, с исходными метками источника.

```sql
CREATE TEMP TABLE order_events (
    order_id integer,
    paid_at timestamptz,
    raw_channel text
);

INSERT INTO order_events VALUES
    (101, '2025-03-09 04:59:59+00', ' web '),
    (102, '2025-03-09 05:00:00+00', ' WEB '),
    (103, '2025-03-09 07:00:00+00', 'web'),
    (104, '2025-03-10 04:00:00+00', NULL);
```

```sql
SELECT order_id
FROM order_events
WHERE paid_at >= (TIMESTAMP '2025-03-09 00:00'
                    AT TIME ZONE 'America/New_York')
  AND paid_at <  (TIMESTAMP '2025-03-10 00:00'
                    AT TIME ZONE 'America/New_York')
ORDER BY order_id;
```

Запрос возвращает 102 и 103. Заказ 101 поступил за секунду до нижней границы. Заказ 104 находится на верхней границе и попадает в следующий день. Границы можно вычесть в SQL. Результат имеет тип `interval`, который представляет промежуток времени.

```sql
SELECT (TIMESTAMP '2025-03-10 00:00' AT TIME ZONE 'America/New_York')
     - (TIMESTAMP '2025-03-09 00:00' AT TIME ZONE 'America/New_York')
       AS day_length;
```

Результат равен `23:00:00`. При переводе часов календарный день может иметь другую длительность. Длина месяцев тоже различается. Например, прибавление `INTERVAL '1 month'` к `DATE '2025-01-31'` даёт полночь 28 февраля, потому что номер последнего дня января больше длины февраля. Прибавление `INTERVAL '30 days'` даёт 2 марта. Когда вопрос относится к календарю, шаг выбираем в календарных единицах. [PostgreSQL 18, §9.9](#references)

Для преобразования местного показания часов в момент времени могут понадобиться дополнительные данные. В Нью-Йорке 2 ноября 2025 года 01:30 наступает дважды. Смещения −04:00 и −05:00 различают 05:30 UTC и 06:30 UTC. Если поток событий передаёт только местное показание часов, источник должен устранить неоднозначность, чтобы можно было установить, какой из двух моментов записан. [IANA, Scope and timezone identifiers](#references)

## Группировка по календарю магазина \{#group-by-the-shop-calendar\}

Для дневного отчёта можно вычислить местную дату каждого события и сгруппировать строки по ней. Сначала переводим момент в показание часов магазина, затем приводим к `date`. Прямое приведение `timestamptz` к `date` использовало бы пояс сеанса.

```sql
SELECT (paid_at AT TIME ZONE 'America/New_York')::date AS shop_day,
       COUNT(*) AS orders
FROM order_events
GROUP BY shop_day
ORDER BY shop_day;
```

| shop_day | orders |
| --- | --- |
| 2025-03-08 | 1 |
| 2025-03-09 | 2 |
| 2025-03-10 | 1 |

Ключ месяца получим выражением `date_trunc('month', paid_at AT TIME ZONE 'America/New_York')::date`. Преобразование выбирает часы магазина, а `date_trunc` устанавливает день и время на начало месяца. Все четыре строки имеют ключ месяца `2025-03-01`. Ключ типа `date` сохраняет календарный порядок при сортировке результата. [PostgreSQL 18, §9.9](#references)

## Для текстового ключа нужно правило \{#a-text-key-needs-a-rule\}

Магазин игнорирует регистр ASCII-кодов источников и пробелы по краям. `trim` по умолчанию удаляет начальные и конечные пробелы. `lower` переводит буквы в нижний регистр по правилам применяемой локали. Для преобразования регистра ASCII-кодов пример выбирает правила сравнения `"C"`. Поэтому и `' WEB '`, и `'web'` дают `'web'`. Правило предназначено для кодов источников. Для имени покупателя нужна отдельная политика сравнения.

```sql
SELECT lower(trim(raw_channel) COLLATE "C") AS channel_key,
       COUNT(*) AS orders
FROM order_events
GROUP BY channel_key
ORDER BY channel_key NULLS LAST;
```

| channel_key | orders |
| --- | --- |
| web | 3 |
| NULL | 1 |

`trim(NULL)` и `lower(NULL)` дают `NULL`. Группа из одной строки представляет заказ с неизвестным источником. Строка из пробелов дала бы пустую строку. Если по договору импорта её тоже следует считать пропуском, это выражает `NULLIF(lower(trim(raw_channel) COLLATE "C"), '')`. У других преобразований свои задачи. `split_part('web:partner', ':', 1)` даёт `web`, а `replace('web:partner', ':', '/')` — `web/partner`. Для метки без разделителя по-прежнему нужно правило обработки неверного формата. [PostgreSQL 18, §9.4](#references)

Unicode может представить один абстрактный символ разными последовательностями кодовых точек. Последняя буква `Café` может быть U+00E9 или U+0065, за которой идёт U+0301. В базе PostgreSQL с кодировкой UTF-8 `char_length` даёт соответственно 4 и 5 символов для этих строк. `octet_length` даёт 5 и 6 байтов. Нормализация NFC приводит оба примера к первой последовательности. Правила регистра, удаления знаков препинания и сопоставления бизнес-меток нужно задать отдельно. [PostgreSQL 18, §9.4](#references) [Unicode, §§1.1–1.2](#references)

```sql
SELECT char_length(U&'Caf\00E9') AS composed_chars,
       octet_length(U&'Caf\00E9') AS composed_bytes,
       char_length(U&'Cafe\0301') AS decomposed_chars,
       octet_length(U&'Cafe\0301') AS decomposed_bytes,
       normalize(U&'Cafe\0301', NFC) AS normalized;
```
