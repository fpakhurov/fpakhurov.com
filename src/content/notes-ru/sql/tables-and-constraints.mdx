Два импорта передают позицию 101/1. В первом заказ содержит две единицы чая, во втором — три. Оба значения подходят по типу столбца. Если сохранить обе строки, сумма может дать пять единиц. Магазин считает пару из номера заказа и номера позиции одним идентификатором. Нужно объявление таблицы, которое отклонит вторую строку с таким идентификатором.

## Объявление таблицы и ключей \{#declare-a-table-and-its-identities\}

В новом сеансе PostgreSQL используем две таблицы. Одна строка `orders` представляет один заказ. Одна строка `order_lines` представляет одну позицию. Код чека может отсутствовать. Если он назначен, он должен быть уникальным. Номер позиции действует в пределах заказа. Магазин допускает бесплатные товары, поэтому цена может быть нулевой.

```sql
CREATE TEMP TABLE orders (
    order_id integer PRIMARY KEY,
    receipt_code text UNIQUE
);

CREATE TEMP TABLE order_lines (
    order_id integer,
    line_no integer CONSTRAINT line_no_positive CHECK (line_no > 0),
    product text NOT NULL,
    quantity integer NOT NULL
        CONSTRAINT quantity_positive CHECK (quantity > 0),
    unit_price_cents integer NOT NULL
        CONSTRAINT unit_price_nonnegative CHECK (unit_price_cents >= 0),
    CONSTRAINT order_lines_pk PRIMARY KEY (order_id, line_no),
    CONSTRAINT order_lines_order_fk
        FOREIGN KEY (order_id) REFERENCES orders (order_id)
);
```

`CREATE TABLE` описывает форму будущих строк даже в пустой таблице. Здесь `TEMP` ограничивает время жизни каждой таблицы текущим сеансом. **Ограничение** (constraint) добавляет правило о допустимых состояниях таблицы. `PRIMARY KEY` требует, чтобы перечисленные поля были заполнены, а их сочетание было уникальным. У таблицы может быть один первичный ключ. Для других сочетаний можно задать отдельные ограничения `UNIQUE`. Ключ из двух полей допускает одновременное наличие `(101, 1)` и `(102, 1)`. Он отклоняет вторую пару `(101, 1)` даже с другим количеством. [PostgreSQL 18, §5.5 и CREATE TABLE](#references)

Ограничение столбца, например `CHECK (quantity > 0)`, записывают рядом со столбцом. Ограничение таблицы может ссылаться на несколько полей, как первичный ключ в этом примере. Некоторым ограничениям даём имена, чтобы обращаться к ним в сообщениях об ошибках или при изменении схемы.

```sql
INSERT INTO orders (order_id, receipt_code) VALUES
    (101, 'R-101'),
    (102, NULL),
    (103, NULL);

INSERT INTO order_lines (
    order_id, line_no, product, quantity, unit_price_cents
) VALUES
    (101, 1, 'tea', 2, 350),
    (101, 2, 'coffee', 1, 600),
    (102, 1, 'tea', 1, 350);
```

По умолчанию PostgreSQL считает пропуски различными для проверки `UNIQUE`, поэтому код чека может отсутствовать сразу у заказов 102 и 103. Второй код `'R-101'` будет отклонён. Если допустима только одна строка без кода, PostgreSQL поддерживает `UNIQUE NULLS NOT DISTINCT`. В SQL Server ограничение `UNIQUE` на одном столбце допускает не более одного `NULL`. При переносе схемы между СУБД важно учитывать правила для пропусков. [PostgreSQL 18, §5.5.3](#references) [Microsoft, Unique constraints](#references)

## Проверка значений и ссылок \{#check-values-and-references\}

В `CHECK` и `WHERE` действуют одни и те же три логических значения, а правила приёма различаются. Фильтр сохраняет строки, для которых условие истинно. Проверка отклоняет строку, когда условие ложно. Если количество неизвестно, `quantity > 0` тоже неизвестно, поэтому одного `CHECK (quantity > 0)` недостаточно для запрета пропуска. `NOT NULL` задаёт отдельное требование о наличии количества. [PostgreSQL 18, §§5.5.1–5.5.2](#references)

<CheckTruth />

**Внешний ключ** (foreign key) требует, чтобы заполненная ссылка из позиции соответствовала строке `orders`. Первичный ключ `orders` гарантирует единственное совпадение. Здесь `order_id` в `order_lines` обязательно заполнен, потому что входит в первичный ключ. Для внешнего ключа вне первичного добавляем `NOT NULL`, если связь обязательна. Внешний ключ из одного столбца, в котором допустим `NULL`, может представлять необязательную связь. [PostgreSQL 18, §§5.5.4–5.5.5](#references)

Попытки вставки ниже иллюстрируют правила на одних и тех же исходных данных. Выполним их по отдельности, чтобы увидеть каждую ошибку.

```sql
INSERT INTO order_lines VALUES (101, 1, 'tea', 3, 350);
INSERT INTO order_lines VALUES (101, 3, 'tea', 0, 350);
INSERT INTO order_lines VALUES (101, 3, 'tea', NULL, 350);
INSERT INTO order_lines VALUES (109, 1, 'tea', 1, 350);
INSERT INTO orders VALUES (104, 'R-101');
```

| Предложенное значение | Причина отказа |
| --- | --- |
| Вторая позиция 101/1 | Повтор первичного ключа |
| Количество 0 | Нарушение `quantity_positive` |
| Количество `NULL` | Количество обязательно |
| Позиция заказа 109 | Заказ, на который ссылается позиция, отсутствует |
| Заказ 104 с кодом `R-101` | Код чека уже занят |

Удаление заказа 101 тоже завершится ошибкой, поскольку на него ещё ссылаются позиции. Действие по умолчанию в этой схеме — `ON DELETE NO ACTION` с немедленной проверкой. При объявленном `ON DELETE CASCADE` удаление родительской строки удалило бы и ссылающиеся на неё позиции. Выбор действия зависит от того, нужно ли магазину их хранить. В SQLite контроль внешних ключей задаётся в настройках соединения. Для сборки с поддержкой внешних ключей включаем `PRAGMA foreign_keys = ON` вне транзакции и проверяем настройку в каждом соединении. [PostgreSQL 18, §5.5.5](#references) [SQLite, §§1–2](#references)

Ограничение на каждой позиции допускает заказы без позиций. Таким уже является заказ 103. Правило «в оплаченном заказе есть хотя бы одна позиция» затрагивает несколько таблиц и смену состояния заказа. Проверка строки в PostgreSQL не может обращаться к строкам другой таблицы для такого контроля. [Курс баз данных](/ru/notes/databases/data-modeling#count-links-in-both-directions) разделяет правила о ссылках и правила о модели в целом. [PostgreSQL 18, §5.5.1](#references)

## Добавление правила к существующим строкам \{#add-a-rule-to-existing-rows\}

Теперь магазин хочет записывать источник каждого заказа. Добавление столбца меняет схему и существующих, и будущих строк. Первая команда добавляет столбец с допустимым `NULL` без значения по умолчанию. Во всех трёх существующих строках сначала будет `NULL`. На этом этапе команда установки `NOT NULL` завершилась бы ошибкой. Источники известны из учебного импорта. Заполним их перед тем, как потребовать наличие значения.

```sql
ALTER TABLE orders ADD COLUMN sales_channel text;

UPDATE orders SET sales_channel = 'web' WHERE order_id IN (101, 102);
UPDATE orders SET sales_channel = 'shop' WHERE order_id = 103;

ALTER TABLE orders
    ADD CONSTRAINT orders_sales_channel_check
    CHECK (sales_channel IN ('web', 'shop'));

ALTER TABLE orders ALTER COLUMN sales_channel SET NOT NULL;
```

Проверка убеждается, что каждый известный источник входит в разрешённое множество. Последняя команда проверяет наличие источника у каждого заказа. После успеха обеих команд в новом заказе требуется указать `'web'` или `'shop'`. Для реальных исторических данных значения нужно заполнить из источника, который позволяет их обосновать. На большой таблице PostgreSQL обычная проверка нового ограничения может потребовать чтения существующих строк, а изменение схемы может потребовать блокировок. Пример выполняется на трёх строках в одном сеансе. [PostgreSQL 18, ALTER TABLE](#references)
