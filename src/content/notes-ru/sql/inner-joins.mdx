В отчёте уже известно, что продано четыре единицы чая. В таблице заказов записан код `tea`, а каталог относит его к категории `drinks`. Код связывает эти два факта. Отчёту нужна одна категория на каждую позицию заказа.

## Сопоставляем строки по общему полю \{#match-rows-by-a-shared-field\}

Возьмём шесть [позиций заказа](/ru/notes/sql/tables-and-queries#a-reproducible-table) и добавим каталог в той же сессии. У каждого товара одна запись в каталоге.

```sql
CREATE TEMP TABLE catalogue (
    product text PRIMARY KEY,
    category text NOT NULL
);

INSERT INTO catalogue VALUES
    ('tea', 'drinks'),
    ('coffee', 'drinks'),
    ('cocoa', 'pantry'),
    ('mint', 'herbs');
```

**Внутреннее соединение** (inner join) даёт одну строку результата на каждую пару входных строк, для которой условие в `ON` истинно. Каждой таблице дан псевдоним, `l` или `c`. Выражение `l.product = c.product` сравнивает два поля, а `SELECT` определяет, что показать для каждой подходящей пары. ([PostgreSQL 18, §7.2.1](#references); [SQLite, §2.1](#references))

```sql
SELECT l.order_id, l.line_no, l.product, c.category
FROM order_lines AS l
JOIN catalogue AS c ON c.product = l.product
ORDER BY l.order_id, l.line_no;
```

| order_id | line_no | product | category |
| ---: | ---: | --- | --- |
| 101 | 1 | tea | drinks |
| 101 | 2 | coffee | drinks |
| 102 | 1 | tea | drinks |
| 103 | 1 | coffee | drinks |
| 103 | 2 | tea | drinks |
| 104 | 1 | cocoa | pantry |

**Декартово произведение** (cross join) соединяет каждую строку со всеми строками с другой стороны. Здесь вышло бы 24 пары из 6 позиций заказа и 4 записей каталога. Чтобы понять результат внутреннего соединения, можно проверить равенство кодов для каждой пары и оставить шесть подходящих. Это описывает результат. Для вычисления СУБД может обойтись без построения всех 24 пар. ([PostgreSQL 18, §7.2.1](#references); [DuckDB 1.4, Cross product and conditional joins](#references))

Первичный ключ каталога допускает не более одного совпадения для каждой позиции. В примере для всех шести позиций есть подходящий код. Если убрать из каталога какао, соответствующая позиция исчезнет из результата. Уникальный ключ ограничивает кратность и сам по себе не требует наличия пары для каждой позиции.

## Сколько пар даёт один ключ \{#how-many-pairs-can-one-key-create\}

Теперь автор отчёта берёт список предложений поставщиков вместо каталога. Каждый поставщик может дать одно предложение на товар. Чай предлагают двое. Снова сравниваем по товару.

```sql
CREATE TEMP TABLE supplier_offers (
    product text,
    supplier text,
    PRIMARY KEY (product, supplier)
);

INSERT INTO supplier_offers VALUES
    ('tea', 'A'),
    ('tea', 'B'),
    ('coffee', 'A'),
    ('cocoa', 'C');

SELECT l.product, COUNT(*) AS pairs,
       SUM(l.quantity) AS summed_units
FROM order_lines AS l
JOIN supplier_offers AS s ON s.product = l.product
GROUP BY l.product
ORDER BY l.product;
```

| product | pairs | summed_units |
| --- | ---: | ---: |
| cocoa | 1 | 3 |
| coffee | 2 | 3 |
| tea | 6 | 8 |

Каждая из трёх позиций чая образует пару с обоими предложениями. В результате шесть строк для чая, и одни и те же четыре проданные единицы учитываются дважды. Зерно стало другим: одна строка на пару позиции и предложения. Восемь — сумма по этим парам. Продано по-прежнему четыре единицы чая.

Для соединения по равенству непустого ключа $k$ обозначим через $n_k$ и $m_k$ число входных строк со значением $k$ слева и справа. Каждой из $n_k$ строк подходят все $m_k$ строк справа. Ключ даёт $n_k m_k$ строк результата. Для чая получаем $3 \cdot 2 = 6$. Кофе и какао дают 2 и 1, поэтому всего получается девять строк. В обычном условии равенства сравнение с `NULL` даёт неизвестное значение. Два отсутствующих ключа не образуют пару. ([PostgreSQL 18, §7.2.1](#references); [SQLite, §2.1](#references))

## Сопоставляем строки на нужном зерне \{#match-at-the-intended-grain\}

Первичный ключ таблицы предложений — пара `(product, supplier)`. Запрос сравнивает только одну часть ключа. Уникальность пары допускает два предложения на одну позицию. Если другой вход действительно указывает выбранного поставщика, можно сравнить оба поля. Если вход указывает только товар, а отчёту нужна одна категория на товар, исходный каталог имеет нужное зерно.

Та же логика действует при повторении отображаемых значений. В двух позициях чая записано по одной единице. `SUM(DISTINCT l.quantity)` сложит различные количества 1 и 2, получив 3. Для отчёта важны обе позиции по одной единице. Замена агрегата поменяет смысл расчёта, а зерно соединения сохранится.

Перед агрегацией определим, что представляет каждая пара. Если на левую строку нужно одно совпадение, сравниваемые поля должны однозначно определять строку справа. Отсутствие пары — отдельный случай. Если каждой позиции нужна запись каталога, эту связь следует проверять или ограничивать отдельно.

## Дальше \{#next\}

Внутреннее соединение отбросило мяту, потому что для неё нет продажи. В отчёте по каталогу может понадобиться показать мяту с нулём продаж. [Внешние соединения](/ru/notes/sql/outer-joins) сохраняют строку без пары и позволяют посчитать настоящие совпадения.
