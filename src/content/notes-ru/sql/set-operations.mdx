Магазин собирает позиции продаж с сайта и из торгового зала. Для списка всех проданных товаров нужны оба источника. Для списка товаров, проданных в обоих каналах, нужно их пересечение. При сверке можно пойти дальше и погасить по одной строке сайта за каждую совпадающую строку зала. Каждый вопрос объединяет два результата с одинаковой структурой строки.

## Сложить вхождения или убрать повторы \{#add-occurrences-or-collapse-them\}

Каждый источник выдаёт одно название товара на позицию. Пропущенное название хранится как `NULL`. Три позиции сайта со значением `tea` представляют три наблюдения, хотя после проекции их значения одинаковы.

```sql
CREATE TEMP TABLE online_products (product text);
CREATE TEMP TABLE store_products (product text);

INSERT INTO online_products VALUES
    ('tea'), ('tea'), ('tea'), ('coffee'), (NULL);
INSERT INTO store_products VALUES
    ('tea'), ('tea'), ('cocoa'), (NULL);
```

```sql
SELECT product FROM online_products
UNION ALL
SELECT product FROM store_products
ORDER BY product NULLS LAST;
```

`UNION ALL` возвращает девять строк. Название `tea` встречается пять раз, `coffee` и `cocoa` по одному, а `NULL` дважды. Для списка различных названий уберём `ALL`. Тогда `UNION` вернёт четыре строки, по одной на каждое различное значение, включая один `NULL`. Проверка на дубликаты сравнивает выходную строку целиком. Два маркера `NULL` в одном столбце при такой проверке совпадают. Предикат равенства в `WHERE` подчиняется отдельным правилам [трёхзначной логики](/ru/notes/sql/types-and-null#a-filter-keeps-only-true). ([PostgreSQL 18, SELECT](#references), [SQLite, §3](#references))

## Сопоставить или погасить копии \{#match-or-cancel-copies\}

`INTERSECT` возвращает различные строки, которые встречаются с обеих сторон. Здесь это один `tea` и один `NULL`. Вариант с `ALL` сохраняет столько копий, сколько можно попарно сопоставить между результатами.

```sql
SELECT product FROM online_products
INTERSECT ALL
SELECT product FROM store_products
ORDER BY product NULLS LAST;
```

Трём строкам `tea` с сайта соответствуют только две строки зала. Поэтому в результате две строки с чаем. С каждой стороны есть одно пропущенное название, так что результат также содержит один `NULL`. В `EXCEPT ALL` каждая правая копия погашает одну левую копию той же строки.

```sql
SELECT product FROM online_products
EXCEPT ALL
SELECT product FROM store_products
ORDER BY product NULLS LAST;
```

Результат содержит по одному `coffee` и `tea`. Две копии чая из зала погашают две из трёх копий сайта. Строка с какао ничего не погашает. Обычный `EXCEPT` возвращает только `coffee`, поскольку он оставляет различные строки левого результата, которых нет в правом. Перестановка операндов меняет вопрос. ([PostgreSQL 18, SELECT](#references))

Пусть $a$ и $b$ обозначают число вхождений некоторой выходной строки слева и справа. Правила с `ALL` следуют из сложения копий, составления пар или погашения этих пар.

| Операция | Число выходных копий | Для `tea` при $a=3$, $b=2$ |
| --- | --- | --- |
| `UNION ALL` | $a+b$ | 5 |
| `INTERSECT ALL` | $\min(a,b)$ | 2 |
| `EXCEPT ALL` | $\max(a-b,0)$ | 1 |

Те же правила действуют после проекции на несколько столбцов. Если вместе с `product` вывести идентификатор позиции, оператор сопоставит пары значений. Соединение по `product` отвечает на другой вопрос, о парах наблюдений. Внутреннее соединение трёх строк сайта с двумя строками зала для чая создаёт $3\cdot 2=6$ пар. Пересечение с `ALL` даёт две копии.

## Какие столбцы сравниваются \{#which-columns-are-compared\}

Обе стороны должны вернуть одинаковое число столбцов. Оператор сопоставляет столбцы по позиции и определяет общий тип для каждой позиции. Псевдонимы во второй ветке не переставляют значения. Имена выходных столбцов берутся из первой ветки. ([PostgreSQL 18, §§7.4 и 10.5](#references), [DuckDB 1.4, Set Operations](#references))

```sql
SELECT 101 AS order_id, 2 AS line_no
UNION ALL
SELECT 1 AS line_no, 104 AS order_id;
```

Строка из правой части даёт `(1, 104)` в выходных столбцах `order_id, line_no`. Оба поля целочисленные, поэтому база примет строку с перепутанным смыслом полей. В каждой ветке указываем столбцы в одном порядке. В DuckDB 1.4 есть диалектная форма `UNION BY NAME` для входов с именованными столбцами. В примерах PostgreSQL сопоставление позиционное. ([DuckDB 1.4, Set Operations](#references))

## Какая операция выполняется первой \{#which-operation-runs-first\}

В PostgreSQL `INTERSECT` связывает части сильнее, чем `UNION` и `EXCEPT`. Последние два группируются слева направо. Составные запросы SQLite группируются слева направо. Если вычисление зависит от конкретной группировки, дадим промежуточному результату имя или явно зададим группировку средствами нужного диалекта. ([PostgreSQL 18, §7.4](#references), [SQLite, §3](#references))

Внешний `ORDER BY` задаёт порядок строк всего результата. Сам по себе `UNION ALL` не обещает показать сначала левые строки. В составном запросе PostgreSQL конечный `ORDER BY` ссылается на имя или позицию выходного столбца. Чтобы отсортировать по новому выражению, поместим составной запрос внутрь ещё одного `SELECT`. ([PostgreSQL 18, SELECT](#references))
