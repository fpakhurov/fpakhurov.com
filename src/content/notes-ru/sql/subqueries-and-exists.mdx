Каталогу нужна отметка для каждого товара с хотя бы одной продажей. [Левое соединение](/ru/notes/sql/outer-joins) сохраняет мяту в отчёте и позволяет посчитать совпадения, но для чая оно сначала строит три пары. Для отметки достаточно одной подходящей позиции. Подзапрос позволяет выразить это условие напрямую.

## Запрос может дать значение \{#a-query-can-supply-a-value\}

**Подзапрос** (subquery) — запрос, вложенный в другой запрос. Когда он даёт одно значение, его называют **скалярным подзапросом** (scalar subquery). Чтобы найти позиции с суммой выше средней, возьмём шесть [позиций заказа](/ru/notes/sql/tables-and-queries#a-reproducible-table) и вычислим среднюю сумму внутри сравнения. ([PostgreSQL 18, §4.2.11](#references); [DuckDB 1.4, Scalar subquery](#references))

```sql
SELECT order_id, line_no,
       quantity * unit_price_cents AS line_cents
FROM order_lines
WHERE quantity * unit_price_cents > (
    SELECT AVG(quantity * unit_price_cents)
    FROM order_lines
)
ORDER BY order_id, line_no;
```

Сумма шести позиций равна 4400 копейкам. Среднее равно $4400 / 6$, то есть примерно 733.33 копейки. Позиции 103/1 и 104/1 стоят по 1200 и проходят сравнение. Внутренний запрос не обращается к внешней строке, поэтому для всех шести строк действует одно среднее.

В PostgreSQL скалярному подзапросу нужен один столбец и не более одной строки. Если строк нет, он даёт `NULL`, а если их несколько — ошибку. Например, выбор `unit_price_cents` у всех позиций с кофе возвращает две строки. Обе цены равны 600, но строк всё равно две, поэтому скалярный подзапрос завершится ошибкой. Выбор цены у позиций с мятой даёт пустой результат и скалярный `NULL`. Если по правилу нужна самая поздняя строка, перед `ORDER BY … LIMIT 1` определим поле порядка и правило разрешения совпадений. Скалярный подзапрос в SQLite берёт первую строку, поэтому запрос может выполниться даже при неоднозначном выборе. ([PostgreSQL 18, §4.2.11](#references); [SQLite, §11](#references))

## Проверяем, существует ли совпадение \{#check-whether-a-match-exists\}

В той же сессии выполним [подготовку каталога](/ru/notes/sql/inner-joins#match-rows-by-a-shared-field). `EXISTS` проверяет, есть ли у подзапроса хотя бы одна строка. Внутреннее условие ссылается на `c.product` из внешнего запроса. Это **коррелированный подзапрос** (correlated subquery). Чтобы разобрать его результат, зафиксируем текущий товар каталога и проверим, найдётся ли подходящая позиция заказа. ([PostgreSQL 18, §9.24.1](#references); [DuckDB 1.4, EXISTS](#references))

```sql
SELECT c.product
FROM catalogue AS c
WHERE EXISTS (
    SELECT 1
    FROM order_lines AS l
    WHERE l.product = c.product
)
ORDER BY c.product;
```

Какао, кофе и чай проходят условие. Для чая подходят три внутренние строки и `EXISTS` истинен. Внешний запрос сохраняет одну строку чая. Для мяты совпадений нет, и `EXISTS` ложен. Запись `SELECT 1` подчёркивает, что важно только наличие. Предикат был бы истинен и для одной строки, единственное значение которой равно `NULL`. С `NOT EXISTS` сохраняется только мята. Рассуждение для каждой внешней строки определяет ответ. СУБД сама выбирает, как часто выполнять внутренний запрос. ([PostgreSQL 18, §9.24.1](#references); [SQLite, §§10 и 12](#references))

Здесь важно указывать псевдоним. Если написать внутри `product` с обеих сторон без псевдонимов, PostgreSQL возьмёт оба столбца из внутренней таблицы. Тогда товар в каждой позиции будет сравниваться сам с собой независимо от товара каталога. Хотя бы одно такое сравнение истинно, и ошибочный `EXISTS` сохранит даже мяту.

## Проверяем принадлежность при пропусках \{#test-membership-when-values-can-be-missing\}

Условие принадлежности можно записать как `c.product IN (SELECT product FROM order_lines)`. Подзапрос теперь даёт один столбец значений-кандидатов. У каждого из трёх проданных товаров в нём есть равное значение, поэтому фильтр возвращает то же, что `EXISTS`. Повторяющиеся значения-кандидаты не меняют принадлежность. ([PostgreSQL 18, §9.24.2](#references))

В новом файле продаж одна строка содержит код чая, а другая пока без кода. Нам нужны товары каталога, для которых в файле нет совпадающего известного кода. Сравним два предиката.

```sql
SELECT c.product,
       c.product NOT IN (
           SELECT product
           FROM (VALUES ('tea'::text), (NULL)) AS incoming(product)
       ) AS absent_in,
       NOT EXISTS (
           SELECT 1
           FROM (VALUES ('tea'::text), (NULL)) AS incoming(product)
           WHERE incoming.product = c.product
       ) AS absent_exists
FROM catalogue AS c
ORDER BY c.product;
```

| product | absent_in | absent_exists |
| --- | --- | --- |
| cocoa | NULL | TRUE |
| coffee | NULL | TRUE |
| mint | NULL | TRUE |
| tea | FALSE | FALSE |

Для мяты сравнение с чаем ложно, а сравнение с отсутствующим кодом даёт неизвестное значение. Поэтому результат `IN` неизвестен, и `NOT IN` тоже даёт неизвестное значение. Во втором предикате ни одно сравнение не делает внутренний `WHERE` истинным. Подзапрос не даёт строк, поэтому `NOT EXISTS` истинен. Если использовать первый предикат в `WHERE`, результат будет пустым. Со вторым в нём окажутся три товара. ([PostgreSQL 18, §§9.24.2–9.24.3](#references); [SQLite, §8](#references))

Если внешний код известен, а подзапрос возвращает только известные коды, `NOT IN` и соответствующая проверка равенства через `NOT EXISTS` совпадают. Такое ограничение уместно, когда пропущенные коды следует игнорировать. Если неизвестный код позже может оказаться мятой, отсутствие совпадения в текущих данных ещё не доказывает отсутствие продажи. Нужно отдельное правило, как показать эту неопределённость.

## Дальше \{#next\}

Проверка существования сохраняет или отбрасывает каждую строку одного входа. Иногда нужно объединить оба входа, оставить общие строки или сравнить кратности после выбора нескольких полей. [Операции над результатами](/ru/notes/sql/set-operations) выражают такие запросы над результатами целиком.
