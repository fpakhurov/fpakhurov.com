[Предыдущая заметка](/ru/notes/devops/builds-and-dependencies) закончилась артефактом: программой, собранной один раз из коммита, с версией и хешем. Сама по себе программа не работает. Сервису на Python нужны интерпретатор нужной версии, точные пакеты из его файла блокировки, системные библиотеки вроде OpenSSL, сертификаты удостоверяющих центров и база часовых поясов, и у каждой машины, где он работает, обо всём этом своё представление. **Образ контейнера** (container image) поставляет программу вместе со всем деревом файлов, которого она ожидает. [Курс ACOS](/ru/notes/acos/virtual-machines-and-containers#containers-one-kernel-many-views) показал, как работает контейнер: пространства имён дают частный взгляд на систему, cgroups — ограничения, а OverlayFS накладывает слои друг на друга. Эта заметка — об образе: из чего он состоит, как его собирать, чтобы пересборки были быстрыми, а результат маленьким и безопасным, и как его называть, чтобы работало именно то, что протестировали.

**Соглашения.** Сквозной пример раздела отсюда и дальше — калькулятор, превращённый в небольшой веб-сервис `calc`: пакет на Python 3.14, который отвечает на `POST /eval` значением выражения, с зависимостями, заблокированными в `uv.lock`. Данные реестров в этой заметке получены с Docker Hub и `gcr.io` 23 октября 2026 года. Docker для этой заметки не запускался: Dockerfile и файл Compose написаны по справочнику Dockerfile и спецификации Compose для Docker Engine 29.9 и Compose 5.6 (актуальных в октябре 2026 года), и их поведение описано по этой документации, а не показано выводом.

## Отправная точка: скопировать программу на сервер \{#baseline-copy-the-program-to-a-server\}

Традиционное развёртывание копирует артефакт на сервер и запускает его там. Всё остальное — интерпретатор, пакеты, системные библиотеки — то, что есть на сервере. Тогда программа ведёт себя по-разному на ноутбуке, на машине CI и на каждом сервере, в зависимости от того, что и когда на каждом установили. Обновление Python для одного сервиса ломает другой на той же машине. Инструменты управления конфигурацией (Ansible, Puppet, Chef) делают серверы более похожими, приводя их к описанию, но приводят медленно и никогда до конца, и у каждого сервера остаётся своя история.

Образы виртуальных машин решают это, поставляя весь диск вместе с ядром, и весят гигабайты, а загружаются минутами. Образ контейнера поставляет только дерево файлов пространства пользователя и метаданные, чтобы запустить в нём одну программу на ядре хоста.

## Что такое образ \{#what-an-image-is\}

Образ — не один файл. По спецификации образов OCI ([OCI Image Format Specification v1.1](#references)) это небольшой граф **блобов** (blobs), каждый из которых хранится и называется по дайджесту SHA-256 своих байтов:

- **Слои.** Каждый слой (layer) — tar-архив, обычно сжатый gzip или zstd, с файлами, которые один шаг сборки добавил, изменил или удалил. Наложенные по порядку, слои образуют дерево файлов.
- **Конфигурация** (config). JSON-документ с метаданными образа: архитектура процессора и операционная система, запускаемая команда, переменные окружения, рабочий каталог, пользователь и `rootfs.diff_ids` — дайджесты *несжатых* слоёв по порядку.
- **Манифест** (manifest). JSON-документ, который называет конфигурацию и слои по их дайджестам, размерам и типам содержимого. Дайджест манифеста — идентичность образа.
- **Индекс** (index). Для образов, собранных под несколько платформ, — JSON-список манифестов, по одному на архитектуру, у каждого свой дайджест. Тег вроде `alpine:3.22` обычно указывает на индекс, и клиент выбирает манифест своей платформы.

Каждая ссылка идёт через дайджест (digest), поэтому весь образ — дерево Меркла, как [граф объектов Git](/ru/notes/devops/git): изменение одного байта одного файла меняет дайджест этого слоя, а тот меняет манифест, и больше ничего. Два образа с общим слоем делят его блоб на диске и в реестре.

**Разобранный пример: образ вручную.** Ничто в этой структуре не требует Docker. `mkimage.py` записывает образ в **раскладке образа OCI** (OCI image layout) — формате для образов, хранящихся в виде файлов, — с двумя слоями: в одном `/etc/passwd`, который определяет непривилегированного пользователя 65532, в другом код сервиса (здесь версия из одного файла, `calc.py`). Каждый блоб попадает в `blobs/sha256/` под собственным дайджестом:

```python
# Записать раскладку образа OCI вручную: два слоя, конфигурация и манифест, каждый блоб назван своим SHA-256.
import gzip, hashlib, io, json, pathlib, sys, tarfile

OUT = pathlib.Path('image')
BLOBS = OUT / 'blobs' / 'sha256'

def sha(data: bytes) -> str:
    return 'sha256:' + hashlib.sha256(data).hexdigest()

def put(data: bytes) -> str:                         # сохранить блоб под его собственным дайджестом
    BLOBS.mkdir(parents=True, exist_ok=True)
    digest = sha(data)
    (BLOBS / digest.split(':')[1]).write_bytes(data)
    return digest

def layer(files: dict[str, bytes]):
    """A layer is a tar of files; returns (compressed blob, diff_id of the uncompressed tar)."""
    raw = io.BytesIO()
    with tarfile.open(fileobj=raw, mode='w', format=tarfile.PAX_FORMAT) as tar:
        for name in sorted(files):
            info = tarfile.TarInfo(name)
            info.size, info.mtime, info.mode = len(files[name]), 0, 0o644
            tar.addfile(info, io.BytesIO(files[name]))
    tar_bytes = raw.getvalue()
    return gzip.compress(tar_bytes, mtime=0), sha(tar_bytes)

app_source = pathlib.Path(sys.argv[1]).read_bytes()
layers = [
    layer({'etc/passwd': b'root:x:0:0:root:/root:/sbin/nologin\nnonroot:x:65532:65532::/home/nonroot:/sbin/nologin\n'}),
    layer({'app/calc.py': app_source}),
]
config = json.dumps({
    'architecture': 'amd64', 'os': 'linux',
    'config': {'User': '65532', 'WorkingDir': '/app', 'Cmd': ['python3', '/app/calc.py']},
    'rootfs': {'type': 'layers', 'diff_ids': [diff_id for _, diff_id in layers]},
}, indent=1).encode() + b'\n'
manifest = json.dumps({
    'schemaVersion': 2,
    'mediaType': 'application/vnd.oci.image.manifest.v1+json',
    'config': {'mediaType': 'application/vnd.oci.image.config.v1+json', 'digest': put(config), 'size': len(config)},
    'layers': [{'mediaType': 'application/vnd.oci.image.layer.v1.tar+gzip', 'digest': put(blob), 'size': len(blob)}
               for blob, _ in layers],
}, indent=1).encode() + b'\n'
index = {'schemaVersion': 2, 'mediaType': 'application/vnd.oci.image.index.v1+json',
         'manifests': [{'mediaType': 'application/vnd.oci.image.manifest.v1+json', 'digest': put(manifest),
                        'size': len(manifest), 'annotations': {'org.opencontainers.image.ref.name': '1.4.0'}}]}
(OUT / 'index.json').write_text(json.dumps(index, indent=1) + '\n')
(OUT / 'oci-layout').write_text('{"imageLayoutVersion": "1.0.0"}\n')
print('manifest', index['manifests'][0]['digest'][:19])
```

В настоящем образе первые слои — базовая система и зависимости, сотни мегабайт, а слой кода — несколько килобайт. Собранный здесь образ не запустится: в нём нет интерпретатора Python. Настоящие образы начинаются с базового образа, который его предоставляет, и остальная часть заметки собирает такой образ.

## Слои на диске: объединяющие файловые системы и копирование при записи \{#layers-on-disk-union-file-systems-and-copy-on-write\}

Чтобы запустить образ, среда выполнения контейнеров один раз распаковывает каждый слой в каталог и накладывает каталоги друг на друга с помощью объединяющей файловой системы (union file system), в Linux обычно OverlayFS: слои — доступные только для чтения нижние каталоги, а каждый контейнер получает поверх них пустой доступный для записи верхний каталог. Чтение находит файл в самом верхнем слое, где он есть; запись в файл из нижнего слоя сначала копирует его наверх (копирование при записи, copy-on-write); удаление оставляет маркер удаления (whiteout), который скрывает файл ниже. [Заметка ACOS](/ru/notes/acos/virtual-machines-and-containers#layered-images-a-private-file-tree-shared-on-disk) монтирует такую стопку вручную. Два следствия определяют, как собирают образы:

- **Удалённый файл остаётся в образе.** Tar слоя записывает удаление как маркер удаления — файл с именем `.wh.`, за которым следует удалённое имя ([спецификация образов OCI, layer changesets](#references)). Байты файла остаются в нижнем слое и скачиваются вместе с ним. Секрет, скопированный на одном шаге и удалённый на следующем, может прочитать любой, кто скачает образ, а большая загрузка, удалённая на более позднем шаге, всё равно стоит своего полного размера.
- **Контейнеры делят свои слои.** Сотня контейнеров из одного образа на одном хосте использует одну копию слоёв на диске и в страничном кэше; каждый добавляет только свой верхний каталог. Всё, что контейнер туда пишет, исчезает вместе с контейнером, поэтому данные, которые должны пережить его, помещают в том (volume).

## Dockerfile, инструкция за инструкцией \{#a-dockerfile-instruction-by-instruction\}

**Dockerfile** — сценарий сборки образа ([Dockerfile reference](#references)). Каждая инструкция — один шаг сборки поверх результата предыдущего:

| Инструкция | Что делает | Что даёт |
| --- | --- | --- |
| `FROM image` | начинает с базового образа | его слои |
| `WORKDIR /app` | задаёт (и создаёт) рабочий каталог | маленький слой и конфигурацию |
| `COPY src dst` | копирует файлы из контекста сборки | слой |
| `RUN command` | выполняет команду в образе, собранном к этому шагу | слой из изменённых ею файлов |
| `ENV`, `USER`, `EXPOSE`, `CMD`, `ENTRYPOINT`, `LABEL` | задают метаданные | только конфигурацию |
| `ARG name` | переменная времени сборки | ничего в образе |

**Контекст сборки** (build context) — папка, отправляемая сборщику, обычно `.`; `COPY` может брать файлы только из неё. BuildKit, сборщик, который стоит за `docker build` начиная с Docker 23, выполняет шаги как граф и запускает независимые этапы параллельно.

**Кэш сборки.** Пересборка каждого шага при каждом изменении сделала бы образы такими же медленными, как исходный сценарий сборки из предыдущей заметки. BuildKit хранит кэш результатов каждого шага и переиспользует шаг, если его ключ совпадает ([документация Docker, Build cache invalidation](#references)):

- ключ включает ключ кэша родительского шага, поэтому шаг можно переиспользовать, только если были переиспользованы все шаги до него;
- для `RUN` ключ — строка команды. Сборщик не смотрит, что команда загрузила бы: `RUN apt-get update && apt-get install -y curl` переиспользуется месяцами, со списками пакетов того дня, когда он впервые выполнился;
- для `COPY` и `ADD` ключ включает контрольную сумму содержимого (и прав доступа) копируемых файлов, а не их времена изменения.

Именно первое правило определяет вид Dockerfile. Когда один шаг промахивается мимо кэша, каждый следующий шаг выполняется заново, изменились его собственные входы или нет. Отсюда **правило порядка** (order rule): ставить первыми шаги, входы которых меняются реже всего. У сервиса базовый образ меняется раз в несколько недель, зависимости — раз в несколько дней, а код — с каждым коммитом, поэтому Dockerfile копирует файл блокировки, устанавливает зависимости и только потом копирует код:

<ImageLayers />

1. Меняется один файл кода сервиса; больше ничего.
2. С `COPY . .` перед установкой контрольная сумма копии меняется, шаг промахивается мимо кэша, и каждый шаг после него выполняется заново: все зависимости заново скачиваются, устанавливаются и отправляются в реестр новым слоем.
3. Если файл блокировки скопирован первым, копирование `pyproject.toml` и `uv.lock` и установка зависимостей берутся из кэша. Промах приходится на `COPY src/`, и заново выполняются только дешёвые последние шаги.

<aside class="callout"><strong>Ключевая идея.</strong> Образ — стопка слоёв, адресуемых по содержимому и названных манифестом, а шаг сборки переиспользуется, только если не изменились его собственные входы и все шаги под ним. Упорядочивать Dockerfile от того, что меняется реже всего, к тому, что меняется чаще всего, не пускать в финальный этап то, что программе не нужно, и ссылаться на результат по его дайджесту.</aside>

## Многоэтапные сборки \{#multi-stage-builds\}

Сборке нужно то, что работающему сервису не нужно: компиляторы, заголовки, менеджер пакетов, его кэш, инструменты тестирования. У **многоэтапной сборки** (multi-stage build) несколько инструкций `FROM`, каждая начинает этап, а более поздние этапы копируют из ранних только выбранные файлы с помощью `COPY --from=stage`. Образом становится только последний этап. На этапе сборки `calc` есть `uv`, который разрешает файл блокировки в виртуальное окружение; этап выполнения начинается со свежей базы и копирует готовое окружение, так что `uv`, его кэша и инструментов сборки в образе нет. Полный Dockerfile разобран построчно в [Примере](#example).

Для компилируемого языка эффект больше: сервис на Go или Rust, статически собранный на этапе со всем набором инструментов (сотни мегабайт), можно скопировать в одиночку на пустую базу (`FROM scratch`) или на distroless.

## Маленькие базовые образы \{#small-base-images\}

Базовый образ определяет большую часть размера и содержимого образа. Сжатые размеры образов linux/amd64, просуммированные по слоям, как их показывали реестры 23 октября 2026 года:

| Базовый образ | Слоёв | Размер в сжатом виде | Что в нём |
| --- | --- | --- | --- |
| `gcr.io/distroless/static-debian12:nonroot` | 12 | 0.7 МБ | сертификаты УЦ, часовые пояса, `/etc/passwd`; ни оболочки, ни libc |
| `busybox:1.37` | 1 | 2.2 МБ | один статический исполняемый файл с обычными командами |
| `alpine:3.22` | 1 | 3.8 МБ | musl libc, BusyBox, менеджер пакетов `apk` |
| `gcr.io/distroless/base-debian12` | 14 | 8.2 МБ | glibc и OpenSSL, без оболочки |
| `python:3.14-alpine` | 4 | 17.8 МБ | Python на Alpine |
| `gcr.io/distroless/python3-debian12` | 43 | 19.7 МБ | Python из Debian, ни оболочки, ни pip |
| `ubuntu:24.04` | 1 | 29.8 МБ | минимальная Ubuntu |
| `debian:trixie-slim` | 1 | 29.8 МБ | минимальный Debian 13 |
| `python:3.14-slim` | 4 | 43.5 МБ | Python 3.14.9 на Debian slim |
| `python:3.14` | 7 | 415.8 МБ | Python на полном Debian с компиляторами и заголовками |

Выбор — компромисс, а не рейтинг:

- **Debian slim** (`-slim`) сохраняет glibc, поэтому готовые колёса (wheels) для Linux (`manylinux`) устанавливаются как есть, а для отладки есть оболочка и `apt`. Это обычный выбор по умолчанию для сервисов на Python.
- **Alpine** маленький, потому что использует musl libc и BusyBox. Колёса Python должны быть собраны под musl (`musllinux`); пакеты, которые их не публикуют, компилируются из исходников во время сборки. musl отличается от glibc в деталях, которые иногда важны, например в DNS-резолвере и размере стека потока по умолчанию.
- **Distroless**-образы ([GoogleContainerTools/distroless](#references)) содержат среду выполнения и её библиотеки и больше ничего: ни оболочки, ни менеджера пакетов. У злоумышленника, добившегося выполнения кода, нет инструментов для работы, а сканеру меньше о чём сообщать. Цена — отладка: `docker exec ... sh` не работает, и нужен отладочный вариант образа или временный отладочный контейнер. Их образ Python следует версии Python из Debian, а не самой новой.
- **scratch** пуст и годится только для статических исполняемых файлов.

**Размер и время.** Размер — это не только диск. Узел, который запускает сервис впервые, должен скачать его образ, и время скачивания — примерно размер, делённый на пропускную способность. При 100 Мбит/с, то есть $12.5$ МБ/с:

$$
t_{\text{full}} = \frac{415.8\ \text{МБ}}{12.5\ \text{МБ/с}} \approx 33\ \text{с}, \qquad
t_{\text{slim}} = \frac{43.5\ \text{МБ}}{12.5\ \text{МБ/с}} \approx 3.5\ \text{с},
$$

до распаковки. Когда всплеск трафика заставляет автомасштабирование запустить сразу 50 новых узлов, они скачивают из реестра $50 \times 415.8 \approx 20.8$ ГБ с полной базой и $2.2$ ГБ со slim-базой, и всё время, пока длится разница, сервису не хватает мощности.

## Запуск без прав root \{#running-as-non-root\}

По умолчанию процесс контейнера работает от root, UID 0. Пространства имён дают ему собственный взгляд, но, как сказано в [заметке ACOS](/ru/notes/acos/virtual-machines-and-containers#limitations), root внутри контейнера — это root в общем ядре, если только пространство имён пользователей не отображает его в непривилегированный UID, и тогда ошибка ядра или неверно настроенное монтирование достаёт до хоста. Поэтому образ должен назвать непривилегированного пользователя в `USER`:

- создать пользователя в образе (`useradd --uid 10001 ...`) или взять того, которого предоставляет база (образы distroless `:nonroot` работают от 65532);
- дать `USER` **числовой** UID. Тогда Kubernetes может проверить политику `runAsNonRoot` по одной конфигурации образа, не читая `/etc/passwd`;
- сделать файлы приложения доступными этому пользователю для чтения, но не для записи, чтобы скомпрометированный процесс не мог изменить код, который выполняет. Файлы, которые нужно писать, помещают в том или `/tmp`;
- слушать порт выше 1023, для чего не нужны привилегии.

## `.dockerignore` \{#dockerignore\}

`COPY . .` копирует весь контекст сборки, и всё, что в контексте, отправляется сборщику. Файл `.dockerignore` с синтаксисом `.gitignore` исключает пути:

```text
.git
.venv
__pycache__/
*.pyc
.env
.pytest_cache/
tests/
```

Три причины, и за каждой стоит сбой. Размер: папка `.git` или локальный `.venv` могут быть больше самого сервиса. Кэш: файлы, которые меняются при каждом запуске (`.git`, кэши, файлы редактора), меняют контрольную сумму любого широкого `COPY` и без причины ломают кэш. Секреты: файл `.env` с учётными данными, скопированный в слой, остаётся в образе навсегда, по причине, объяснённой выше в разделе о маркерах удаления. Секреты сборки, которые нужны шагу, например токен для частного индекса пакетов, передают с помощью `RUN --mount=type=secret`: он делает их доступными одной этой команде, не записывая в слой.

## Размер образа и поверхность атаки \{#image-size-and-attack-surface\}

Каждый пакет в образе — это код, в котором могут быть уязвимости, а **сканер уязвимостей** (vulnerability scanner: Trivy, Grype, Docker Scout) работает так: составляет список пакетов образа, его перечень программных компонентов (software bill of materials, SBOM), и сверяет его с базами известных уязвимостей. Полная база Debian с компиляторами несёт сотни пакетов, которые сервис на Python никогда не вызывает, и каждый из них может появиться в отчёте, который кому-то придётся прочитать. У меньшего образа:

- меньше пакетов, которые нужно обновлять, и меньше находок для разбора;
- меньше инструментов у злоумышленника, который проник внутрь: ни оболочки, ни `curl`, ни менеджера пакетов, чтобы загрузить ещё;
- меньше и быстрее скачивание, как подсчитано выше.

Маленький — не то же самое, что актуальный. Базовый образ, закреплённый однажды и никогда не обновляемый, копит известные уязвимости по мере их публикации. Регулярная пересборка на обновлённой базе, которую следующий раздел делает осознанной, важна не меньше, чем выбор маленькой базы, а то, какие находки исправлять первыми, — вопрос [политики обновлений](/ru/notes/devops/incidents-and-security#patching-and-dependency-updates).

## Реестры, теги и дайджесты \{#registries-tags-and-digests\}

**Реестр** (registry) хранит блобы и манифесты и отдаёт их через описанный выше HTTP API. К образу обращаются как `registry/repository:tag` или `registry/repository@sha256:digest`. Дайджест навсегда называет ровно один манифест, потому что это хеш его байтов. **Тег** (tag) — изменяемый указатель на манифест, который издатель может передвинуть в любой момент. Официальные образы двигают свои теги намеренно. Если `R` указывает на репозиторий `python`, а `TOKEN` и `get` определены как выше:

```console
$ for tag in 3.14-slim 3.14.9-slim 3.14.8-slim; do
  m=$(get manifests/$tag | jq -r '.manifests[] | select(.platform.architecture == "amd64") | .digest')
  c=$(get manifests/$m | jq -r .config.digest)
  echo "$tag ${m:7:12} $(get blobs/$c | jq -r '.created[0:16] + " " + (.config.Env[] | select(startswith("PYTHON_VERSION")))')"
done
3.14-slim 0214bda9af26 2026-10-21T22:26 PYTHON_VERSION=3.14.9
3.14.9-slim 0214bda9af26 2026-10-21T22:26 PYTHON_VERSION=3.14.9
3.14.8-slim 9b629e83e1a5 2026-10-21T01:06 PYTHON_VERSION=3.14.8
```

В этот день `3.14-slim` и `3.14.9-slim` — один и тот же образ amd64, собранный поздно вечером 21 октября; образ 3.14.8, собранный в начале того же дня, сохраняет собственный тег. Dockerfile с `FROM python:3.14-slim`, собранный 20 октября, получил Python 3.14.8, а пересобранный 22 октября — 3.14.9, без единого изменения в репозитории. Базовые образы ещё и пересобирают без смены версии, когда Debian публикует обновления безопасности. Поэтому тег — не версия входа сборки, и действует правило [предыдущей заметки](/ru/notes/devops/builds-and-dependencies#reproducible-builds): закреплять входы точно.

**Закрепление по дайджесту** записывает и то и другое: `FROM python:3.14.9-slim-trixie@sha256:b347e2dc…`. Тег документирует намерение, а дайджест, который побеждает, когда указаны оба, фиксирует байты. То же относится к образам, которые запускает развёртывание: развёртывание, которое ссылается на `calc:1.4.0`, может изменить любой, кто может отправить этот тег, а `calc@sha256:…` — нет. Закрепления устаревают, поэтому бот вроде Renovate или Dependabot предлагает обновления дайджестов в виде пул-реквестов (pull requests), которые затем проходят CI, как любое другое изменение: обновления базовых образов становятся видимыми, протестированными и обратимыми. Дайджесты доказывают, какие байты пришли, но не кто их создал. Это делают **подписи**: `cosign` из Sigstore подписывает дайджест и хранит подпись в реестре рядом с образом, а кластер можно настроить так, чтобы он запускал только образы, подпись которых может проверить; [последняя заметка курса](/ru/notes/devops/incidents-and-security#the-supply-chain-sboms-signatures-and-slsa) сводит вместе подписи, перечни компонентов и сведения о происхождении.

## Compose: несколько контейнеров на одной машине \{#compose-several-containers-on-one-machine\}

Сервис редко работает один: `calc` хранит историю вычисленных выражений в PostgreSQL. **Docker Compose** описывает локальную установку из нескольких контейнеров, их сетей и томов в одном файле `compose.yaml` ([Compose specification](#references)) и запускает её командой `docker compose up`:

```yaml
services:
  calc:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://calc:calc@db:5432/calc
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:18.6-trixie
    environment:
      POSTGRES_USER: calc
      POSTGRES_PASSWORD: calc
      POSTGRES_DB: calc
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "calc"]
      interval: 2s
      retries: 15
volumes:
  pgdata:
```

Compose помещает оба сервиса в одну сеть, где каждый доступен по имени своего сервиса, поэтому `calc` подключается к хосту `db`. `depends_on` с `condition: service_healthy` запускает `calc` только после того, как прошла проверка здоровья базы данных, а не просто после старта её контейнера. Именованный том `pgdata` сохраняет данные, когда контейнеры пересоздаются. Пароль здесь годится только для ноутбука. Compose предназначен для разработки и тестов на одной машине; запуск контейнеров на многих машинах, с перезапусками, масштабированием и поэтапными обновлениями, — работа оркестратора из [заметки о Kubernetes](/ru/notes/devops/kubernetes).

(2) Один шаг выполняет `RUN curl -o model.bin https://example.com/model.bin && python prepare.py && rm model.bin`, а другой Dockerfile разбивает его на три строки `RUN`. Почему второй образ больше? (3) В образе два слоя, и слой кода пересжат zstd вместо gzip. Какие дайджесты меняются: слоя, его `diff_id`, конфигурации, манифеста? (4) Кластер Kubernetes отвергает под с сообщением «container has runAsNonRoot and image has non-numeric user (app), cannot verify user is non-root». Что должно быть написано в Dockerfile? Назовите способ, которым так может запуститься код, который никогда не тестировали.<details><summary>Ответы</summary>(1) `COPY . .` копирует и README, поэтому его контрольная сумма меняется, он промахивается мимо кэша, и `uv sync` и всё после него выполняются заново, хотя ни одна зависимость не изменилась. Сначала скопировать файл блокировки и установить зависимости, потом скопировать код; кроме того, перечислить документацию в `.dockerignore`. (2) Каждый `RUN` — это слой, а более позднее удаление только добавляет маркер удаления: версия из трёх строк сохраняет `model.bin` в первом слое. Внутри одного `RUN` файл создаётся и удаляется до того, как снимается слой. (3) Сжатый блоб меняется, поэтому меняется дайджест слоя в манифесте, а с ним и дайджест манифеста. Несжатый tar прежний, поэтому `diff_id`, а с ним и конфигурация не меняются. (4) `USER 10001` (числовой UID, созданный в образе), чтобы kubelet мог проверить, что это не 0, по одной конфигурации. (5) Любой, у кого есть права на отправку, может передвинуть тег `1.4.0` на другой манифест, по ошибке (пересборка с новым базовым образом) или намеренно; следующий запуск пода, например после отказа узла, скачает новый образ. Развёртывать по дайджесту.</details></aside>

## Ограничения \{#limitations\}

- **Образ — не ВМ.** Он делит ядро с хостом, поэтому версия ядра и его возможности не входят в образ, а образ, собранный для amd64, требует эмуляции на arm64, если его не собрали для обеих архитектур.
- **Кэш локален, пока его не экспортировали.** Свежий раннер CI начинает с пустым кэшем BuildKit; [следующая заметка](/ru/notes/devops/continuous-integration) экспортирует его в реестр или кэш сервиса CI, чтобы правило порядка чего-то стоило.
- **Шаги `RUN` сами по себе не воспроизводимы.** `apt-get install` и загрузки дают разные байты в разные дни; для повторяемых дайджестов нужны закреплённые базовые образы, заблокированные зависимости и фиксированные метки времени (`SOURCE_DATE_EPOCH`, который поддерживает BuildKit).
- **Образы distroless и scratch затрудняют отладку**, а маленьким базам может не хватать того, чего программа молча ожидает: сертификатов УЦ, данных о часовых поясах, доступного для записи `/tmp`, записи о пользователе для её UID.
- **Сканеры сообщают об известных уязвимостях в перечисленных пакетах**, а не о том, достижим ли уязвимый код, и не о проблемах в коде, которого не видно в списке пакетов.
- **Быстро меняющиеся факты.** Размеры, теги и версии выше — на 23 октября 2026 года; теги и размеры меняются при каждой пересборке базового образа.

## Что нужно запомнить \{#what-you-should-remember\}

- Образ OCI — это блобы, названные по SHA-256: слои (tar-архивы изменений), конфигурация (метаданные и `diff_ids` несжатых слоёв), манифест, который называет и то и другое, и индекс с одним манифестом на платформу. Дайджест манифеста — идентичность образа.
- Одинаковые слои хранятся и передаются один раз. Удалённый файл остаётся в слое под ним, поэтому секреты и большие временные файлы никогда нельзя записывать отдельным шагом.
- Шаг Dockerfile переиспользуется, только если были переиспользованы все шаги до него: `RUN` — по строке команды, `COPY` — по контрольным суммам файлов. Упорядочивать шаги от редко меняющихся к часто меняющимся: файл блокировки, зависимости, затем код.
- Многоэтапные сборки не пускают в финальный образ компиляторы, менеджеры пакетов и кэши. Базовые образы бывают от меньше 1 МБ (distroless static) до больше 400 МБ (полный Python); slim, Alpine и distroless обменивают размер на совместимость и удобство отладки.
- Работать от числового пользователя без прав root, держать контекст сборки маленьким с помощью `.dockerignore` и передавать секреты сборки через монтирование секретов.
- Теги двигаются; дайджесты — нет. Закреплять базовые и развёрнутые образы по дайджесту и поручить боту предлагать обновления в виде протестированных пул-реквестов.
- Compose запускает установку из нескольких контейнеров на одной машине для разработки и тестов.

## Пример \{#example\}

Боевой Dockerfile для `calc` — приложения на FastAPI, которое обслуживает Uvicorn, с `pyproject.toml`, `uv.lock` и пакетом в `src/calc/`. Он следует руководству uv по Docker ([документация uv, Using uv in Docker](#references)). Здесь не собирался; дайджесты актуальны на 23 октября 2026 года.

```dockerfile
# syntax=docker/dockerfile:1

# Stage 1: resolve the lockfile into a virtual environment.
FROM python:3.14.9-slim-trixie@sha256:b347e2dcbc7f0b6f9fb7182e9da6a187fb10ae715e0692518c1aed0eec94a700 AS build
COPY --from=ghcr.io/astral-sh/uv:0.12.9@sha256:8b940d3a9d65bed080436972241af2e21c84b5e8c9193f7014ed71479ee795ff /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=0
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-install-project
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-editable

# Stage 2: the same Python, the environment, and nothing else.
FROM python:3.14.9-slim-trixie@sha256:b347e2dcbc7f0b6f9fb7182e9da6a187fb10ae715e0692518c1aed0eec94a700
RUN groupadd --system --gid 10001 calc \
 && useradd --system --uid 10001 --gid 10001 --no-create-home calc
COPY --from=build /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1
USER 10001
EXPOSE 8000
CMD ["uvicorn", "calc.web:app", "--host", "0.0.0.0", "--port", "8000"]

ARG GIT_COMMIT=unknown
LABEL org.opencontainers.image.revision=$GIT_COMMIT \
      org.opencontainers.image.source=https://git.example.com/team/calc
```

- **`# syntax=docker/dockerfile:1`.** Просит BuildKit использовать текущую версию 1 фронтенда Dockerfile, которая поддерживает опции `--mount` ниже.
- **`FROM python:3.14.9-slim-trixie@sha256:… AS build`.** Этап сборки на Debian 13 slim с Python 3.14.9, закреплённый по дайджесту; тег оставлен для читателей и для бота обновлений.
- **`COPY --from=ghcr.io/astral-sh/uv:0.12.9@sha256:… /uv /usr/local/bin/uv`.** `COPY --from` принимает и образ: эта инструкция копирует единственный статический исполняемый файл `uv` из собственного образа uv, закреплённого так же, как база.
- **`ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=0`.** Компилировать файлы `.pyc` во время сборки, чтобы сервис не компилировал их при каждом запуске в образе, доступном только для чтения; копировать файлы из кэша uv, а не ссылаться на них, потому что кэш — это монтирование, которого нет в образе; и использовать Python базового образа, а не скачивать другой.
- **`COPY pyproject.toml uv.lock ./`, затем `RUN … uv sync --locked --no-dev --no-install-project`.** Правило порядка: эти два файла меняются, только когда меняются зависимости, поэтому этот слой, самый дорогой, переиспользуется при изменениях кода. `--locked` прерывает сборку, если `uv.lock` не соответствует `pyproject.toml`, вместо того чтобы молча разрешить зависимости заново; `--no-dev` не ставит инструменты тестирования; `--no-install-project` устанавливает зависимости, но не сам `calc`, код которого ещё не скопирован. Монтирование кэша сохраняет кэш загрузок uv между сборками на одном сборщике, не помещая его в слой.
- **`COPY src/ ./src/`, затем `RUN … uv sync --locked --no-dev --no-editable`.** Код, который меняется с каждым коммитом, и установка проекта в окружение. `--no-editable` копирует пакет в `.venv`, а не указывает на `src/`, так что окружение работает само по себе.
- **Второй `FROM`.** Этап выполнения снова начинается с той же базы, поэтому пути к интерпретатору внутри `.venv` верны, и ничего с этапа сборки не попадает сюда, если его не скопировать.
- **`RUN groupadd … && useradd …`.** Непривилегированные системные пользователь и группа с фиксированными числовыми идентификаторами и без домашнего каталога.
- **`COPY --from=build /app/.venv /app/.venv`.** Единственное, что берётся с этапа сборки. Владельцем файлов остаётся root, поэтому пользователь сервиса может их читать и запускать, но не изменять.
- **`ENV PATH=… PYTHONUNBUFFERED=1`.** Ставит `bin/` окружения первым, так что `uvicorn` берётся из окружения; небуферизованный вывод сразу отправляет строки журнала на стандартный вывод контейнера.
- **`USER 10001`.** Все последующие инструкции и процесс контейнера выполняются от этого числового UID.
- **`EXPOSE 8000`.** Документирует порт, но не публикует его. Публикуют `docker run -p`, `ports` в Compose или Service в Kubernetes.
- **`CMD [...]`.** Форма JSON (exec) запускает `uvicorn` напрямую как процесс 1, поэтому он получает `SIGTERM`, когда контейнер останавливают; форма оболочки запустила бы `/bin/sh -c`, который не передаёт сигнал дальше.
- **`ARG GIT_COMMIT` и `LABEL` в конце.** Конвейер CI передаёт коммит через `--build-arg GIT_COMMIT=…`. Изменившийся аргумент сборки инвалидирует кэш начиная с первого шага, который его использует, поэтому этот шаг стоит последним, где новое значение при каждой сборке ничего не стоит. Метки — стандартные аннотации OCI, которые ведут от образа обратно к его исходному коду.

## Дальше \{#next\}

Образ — это артефакт, который передвигает остальная часть раздела, а каждый шаг до сих пор выполнялся вручную: собрать, протестировать, собрать образ, отправить его в реестр. [Следующая заметка](/ru/notes/devops/continuous-integration) заставляет всё это происходить при каждом изменении, на машинах, куда никто не входит, с графом сборки из предыдущей заметки, выросшим до конвейера заданий, и выясняет, что нужно, чтобы основная ветка всегда оставалась зелёной.
