[Предыдущая заметка](/ru/notes/devops/kubernetes) запустила в Kubernetes сервис без состояния: Deployment из четырёх подов за Service, выкатываемый контроллерами и проверяемый пробами. Этот сервис не читал конфигурацию, ничего не хранил, был доступен только изнутри кластера, работал в фиксированном числе копий и устанавливался одной командой `kubectl apply` с чьего-то ноутбука. Эта заметка добавляет то, что нужно настоящему сервису, и каждое добавление следует одному образцу: объект, который объявляет, чего хотят, и контроллер, который делает так, чтобы это стало правдой. Заканчивается она вопросом, который стоило бы задать первым: когда Kubernetes стоит своей цены.

**Соглашения.** Kubernetes 1.37 (октябрь 2026 года). Кластера не было, поэтому ничего к кластеру не применялось. `kubectl create ... --dry-run=client` и `kubectl kustomize` работают без кластера, и их вывод здесь настоящий — от `kubectl` 1.25 со встроенным Kustomize 4.5.7; остальные манифесты написаны по актуальной документации и разобраны PyYAML. Версии других инструментов — их последние выпуски на 23 октября 2026 года: Gateway API 1.6.3, Helm 4.3.1, Argo CD 3.5.6, Flux 2.9.6.

## Отправная точка: зашить, привязать, скопировать \{#baseline-bake-it-in-pin-it-down-copy-it\}

Самый быстрый способ доделать сервис из предыдущей заметки — зашить пароль базы данных и уровень журналирования в образ, хранить загрузки в каталоге на том узле, куда попал под, открыть порт на каждом узле для балансировщика нагрузки, угадать число реплик и скопировать YAML для каждого окружения, правя каждую копию вручную. Каждое такое сокращение пути проваливается в первый же настоящий день:

1. Изменение конфигурации требует нового образа, а пароль может прочитать любой, кто может скачать образ.
2. Когда под переезжает на другой узел, загрузки остаются на старом.
3. Каждому сервису нужен свой порт и своё правило балансировщика, а TLS не обрабатывается нигде.
4. Угаданного числа реплик слишком много ночью и слишком мало в вечерний пик.
5. Копии расходятся: в продакшен попадает исправление, которого staging никогда не видит.
6. Никто не знает, что работает в кластере, кроме как спросив сам кластер, и любой, у кого есть учётные данные, может его изменить.

<aside class="callout"><strong>Ключевая идея.</strong> Всё, что нужно сервису помимо его контейнеров, — это ещё один объект с контроллером за ним. Конфигурация и секреты — объекты, на которые ссылаются поды; хранилище — заявка, которую контроллер связывает с диском; трафик снаружи — Gateway и маршруты, которые контроллер превращает в балансировщик нагрузки; число реплик записывает автомасштабировщик, который тоже контроллер. А само желаемое состояние уходит из терминалов людей в Git, из которого кластер согласует ещё один контроллер. Модель предыдущей заметки не меняется: объяви, и цикл сойдётся.</aside>

## ConfigMap и Secret \{#configmaps-and-secrets\}

**ConfigMap** хранит конфигурацию в виде пар «ключ — значение» отдельно от образа, чтобы один образ работал в каждом окружении с разными настройками, — правило из [заметки о доставке](/ru/notes/devops/continuous-delivery#one-artifact-many-environments). Под использует его как переменные окружения или как файлы в смонтированном томе, по файлу на ключ. При изменении ConfigMap эти два способа ведут себя по-разному: переменные окружения читаются один раз, при запуске контейнера, поэтому изменение доходит до работающего пода, только когда его перезапустят; смонтированные файлы kubelet обновляет на месте с задержкой, которая может достигать минуты и больше, и приложение должно это заметить. (Kustomize, о котором ниже, превращает изменение конфигурации в выкатку, а обычно именно это и нужно.)

**Secret** устроен так же и предназначен для паролей, токенов и ключей. С ним обращаются чуть осторожнее: на узлах он хранится в памяти (`tmpfs`), выдаётся только подам, которые на него ссылаются, а доступ к нему можно выдавать отдельно. Но Secret не зашифрован:

```console
$ kubectl create secret generic db --from-literal=password=not-a-real-password --dry-run=client -o yaml
apiVersion: v1
data:
  password: bm90LWEtcmVhbC1wYXNzd29yZA==
kind: Secret
metadata:
  creationTimestamp: null
  name: db
$ echo bm90LWEtcmVhbC1wYXNzd29yZA== | base64 -d
not-a-real-password
```

Значение записано в **base64** — кодировке, которая позволяет передавать в YAML произвольные байты, и для декодирования не нужен ключ. Почему Secret по умолчанию не шифруются? Потому что API-сервер хранит их в etcd как есть, если администратор не настроит **шифрование при хранении** (encryption at rest): `EncryptionConfiguration`, которая велит API-серверу шифровать Secret перед записью, в идеале ключом, хранящимся во внешнем сервисе управления ключами (KMS), чтобы ключ не лежал на том же диске, что и данные ([Kubernetes documentation, Secrets](#references)). Без него любой, кто может прочитать etcd, его диск или его резервные копии, читает все Secret. И даже с ним API-сервер расшифровывает Secret для любого, кому разрешено их `get`, а любой, кому разрешено создать под в пространстве имён, может смонтировать любой Secret этого пространства имён и напечатать его. Поэтому настоящих защит три: шифрование при хранении, правила доступа, которые разрешают чтение Secret почти никому, и хранение источника секретов вне кластера. Обычный выбор для последнего — внешнее хранилище секретов (HashiCorp Vault, OpenBao или менеджер секретов облачного провайдера), которое оператор синхронизирует в Secret, или секреты, зашифрованные в Git с помощью SOPS или Sealed Secrets, чтобы репозиторий из раздела о GitOps ниже никогда не хранил пароль открытым текстом ([University of Helsinki, part 2](#references)).

## Тома, PersistentVolumeClaim и StatefulSet \{#volumes-persistentvolumeclaims-and-statefulsets\}

Файловая система контейнера — это слои образа плюс тонкий записываемый слой, [overlay](/ru/notes/acos/virtual-machines-and-containers#layered-images-a-private-file-tree-shared-on-disk) из курса о системах, и она исчезает вместе с контейнером. **Том** (volume) — каталог, который под монтирует откуда-то ещё. Одни тома живут столько же, сколько под (`emptyDir`, временное пространство, общее для его контейнеров), другие проецируют объекты (ConfigMap или Secret в виде файлов), а третьи **постоянные** (persistent): они переживают любой под.

Постоянное хранилище разделено на два объекта, чтобы приложениям не нужно было знать, откуда берутся диски:

- **PersistentVolumeClaim** (PVC, заявка на том), которую пишет команда приложения, запрашивает хранилище: размер, **режим доступа** (access mode) и **класс хранилища** (storage class). `ReadWriteOnce` означает, что том можно смонтировать для чтения и записи на одном узле за раз, — режим диска блочного хранилища; `ReadWriteMany` — на многих узлах, для чего нужно файловое хранилище; `ReadWriteOncePod` ограничивает доступ одним подом.
- **PersistentVolume** (PV) — реальный кусок хранилища. При наличии **StorageClass** провизионер создаёт PV по требованию: когда появляется заявка, он вызывает облачный API, создаёт диск блочного хранилища из [заметки об облаке](/ru/notes/devops/cloud-building-blocks#storage-block-object-and-file) и связывает с ним заявку.

Диск блочного хранилища живёт в одной зоне, поэтому под, который его использует, может работать только на узлах этой зоны. Класс хранилища с `volumeBindingMode: WaitForFirstConsumer` ждёт, пока планировщик выберет узел для пода, и затем создаёт диск в зоне этого узла, вместо того чтобы сначала создать диск, а потом обнаружить, что ни у одного узла в его зоне нет места. Политика освобождения (reclaim policy) класса решает, что происходит с диском при удалении заявки: `Delete` уничтожает его вместе с данными, `Retain` сохраняет, чтобы с ним разобрался человек.

**StatefulSet** вкратце. Поды Deployment взаимозаменяемы: случайные имена, любой порядок, общие заявки или никаких. Реплицируемым базам данных и очередям нужно больше, и StatefulSet это даёт: поды со стабильными именами (`db-0`, `db-1`, `db-2`), которые сохраняют имя при замене; создание по порядку и удаление в обратном порядке; по одной PVC на под, созданной по шаблону и следующей за подом по имени, так что `db-1` всегда получает обратно диск `db-1`; и, вместе с *headless*-Service, стабильное DNS-имя для каждого пода (`db-0.db.shop.svc.cluster.local`), чтобы реплики могли найти друг друга. StatefulSet не делает базу данных реплицируемой или согласованной: это делает сама база данных, а чтобы хорошо эксплуатировать её в Kubernetes, нужен **оператор** (operator) — контроллер, который умеет переключать её при отказе, делать резервные копии и обновлять. Многие команды предпочитают управляемую базу данных из заметки об облаке и оставляют Kubernetes для частей без состояния.

## Трафик снаружи: Ingress и Gateway API \{#traffic-from-outside-ingress-and-the-gateway-api\}

Service типа `LoadBalancer` получает по одному облачному балансировщику нагрузки на каждый Service, что годится для одного сервиса и становится дорогим и неуправляемым для пятидесяти. HTTP-трафик лучше обслуживать одним общим обратным прокси — [прокси L7](/ru/notes/devops/networking-for-services#reverse-proxies-one-front-door-for-many-backends) из заметки о сети, работающим в кластере, — который маршрутизирует по имени хоста и пути ко многим Service и терминирует TLS.

**Ingress** (`networking.k8s.io/v1`, стабилен начиная с Kubernetes 1.19) был первым API для этого: объект перечисляет правила вида «хост `www.example.com`, путь `/api` → Service `api`, порт 80», а **ingress-контроллер** (ingress controller) — прокси, который следит за объектами Ingress, — настраивает себя по ним. Ingress мал намеренно, и всё, что выходит за рамки хоста и пути (сопоставление заголовков, разделение трафика, таймауты), добавлялось через аннотации, специфичные для контроллера, поэтому Ingress, написанный для одного контроллера, редко работает с другим.

**Положение на октябрь 2026 года.** Документация Kubernetes описывает API Ingress как замороженный, без новых возможностей, и рекомендует вместо него Gateway API. Самый распространённый контроллер, Ingress NGINX, проект Kubernetes вывел из эксплуатации: поддержка по мере возможностей закончилась в марте 2026 года, его репозиторий архивирован, и он больше не получает ни выпусков, ни исправлений безопасности, хотя существующие установки продолжают работать ([Kubernetes blog, 11 November 2025](#references)). Новым кластерам следует использовать реализацию Gateway API; существующие объекты Ingress остаются действительными, и многие реализации Gateway тоже их принимают.

**Gateway API** (`gateway.networking.k8s.io`, версия 1.0 в октябре 2023 года, 1.6.3 в октябре 2026 года) устанавливается как дополнение из пользовательских ресурсов и делит работу по ролям ([Gateway API documentation](#references)):

- **GatewayClass**, который настраивает тот, кто предоставляет инфраструктуру, называет реализацию (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, балансировщик облачного провайдера и другие);
- **Gateway**, которым владеет команда платформы, — один балансировщик нагрузки: его слушатели (listeners), порты, имена хостов, сертификаты TLS и то, из каких пространств имён к нему можно присоединять маршруты;
- **HTTPRoute** (или GRPCRoute и другие), которым владеет каждая команда приложения в своём пространстве имён, присоединяется к Gateway и сопоставляет имена хостов и пути с Service, с весами для разделения трафика между ними.

Gateway для всей компании, написанный один раз командой платформы:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public
  namespace: gateways
spec:
  gatewayClassName: example-lb
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.example.com"
      tls:
        mode: Terminate
        certificateRefs:
          - name: wildcard-example-com
      allowedRoutes:
        namespaces:
          from: All
```

Слушатель принимает HTTPS на порту 443 для любого имени внутри `example.com`, терминирует TLS с сертификатом, хранящимся в Secret `wildcard-example-com`, и позволяет присоединяться маршрутам из любого пространства имён. HTTPRoute команды приложения, в разделе «Пример», ссылается на этот Gateway по имени и никогда не трогает сертификаты и порты. `backendRefs` маршрута может перечислить два Service с весами, например 95 и 5, — это [канарейка](/ru/notes/devops/continuous-delivery#canary) из заметки о доставке, реализованная прокси, а не числом подов.

## Автомасштабирование: HPA и автомасштабировщик кластера \{#autoscaling-the-hpa-and-the-cluster-autoscaler\}

**HorizontalPodAutoscaler** — горизонтальное автомасштабирование подов (HPA) — это контроллер, который записывает `replicas` объекта Deployment. Каждые 15 секунд он читает метрику подов цели, чаще всего использование ими CPU как долю их **запроса** CPU, и вычисляет

$$
\boxed{n_{\text{desired}} = \left\lceil n \cdot \frac{m}{m^{*}} \right\rceil} ,
$$

где $n$ — текущее число реплик, $m$ — текущее среднее значение метрики, а $m^{*}$ — целевое ([Kubernetes documentation, horizontal Pod autoscaling](#references)).

**Откуда берётся формула.** Общая нагрузка распределяется по подам поровну. При $n$ подах со средней загрузкой $m$ общий объём работы — $n \cdot m$ «подов» работы в единицах запроса одного пода. Чтобы снизить среднее до цели $m^*$, число подов $n'$ должно удовлетворять $n' \cdot m^* = n \cdot m$, так что $n' = n \cdot m / m^*$. Округление вверх держит среднее на уровне цели или ниже, поскольку $\lceil x \rceil \ge x$. Это предполагает, что нагрузка на под падает пропорционально по мере добавления подов, что верно для сервисов без состояния за балансировщиком и неверно, когда узкое место в другом месте, например в базе данных, которую делят все поды.

**Разобранные примеры.** Цель — 60% запроса CPU.

- 4 реплики в среднем загружены на 90%: $\lceil 4 \times 90 / 60 \rceil = \lceil 6.0 \rceil = 6$ реплик.
- 4 реплики в среднем загружены на 63%: отношение $63 / 60 = 1.05$ лежит в пределах **допуска** (tolerance) 10% вокруг 1, поэтому ничего не происходит. Без допуска мелкие колебания добавляли бы и убирали под каждые 15 секунд.
- 10 реплик в среднем загружены на 20% после вечернего пика: $\lceil 10 \times 20 / 60 \rceil = \lceil 3.33 \rceil = 4$. HPA действует не сразу. Уменьшение сдерживает **окно стабилизации** (stabilization window) в 5 минут: HPA использует наибольшую рекомендацию за последние 300 секунд, так что провал на несколько минут не убирает поды, которые понадобятся в следующую минуту. У увеличения по умолчанию окна нет, но оно не превышает 4 подов или 100% (что больше) за каждые 15 секунд.

HPA вычисляет загрузку относительно запроса, поэтому HPA по CPU требует запросов CPU у каждого контейнера. При запросе `250m` под на «100%» использует четверть ядра, а под, использующий половину ядра, загружен на 200%: загрузка выше 100% нормальна, потому что запросы — это резервирование, а не лимиты.

Рисунок воспроизводит правило каждые 15 секунд на игрушечной нагрузке, которая растёт с 200 до 600 запросов в секунду и падает обратно. Увеличение начинается на 5 мин 30 с, когда отношение впервые выходит за пределы допуска, и достигает 10 реплик, когда нагрузка достигает 600. Уменьшение ждёт пять минут после падения, до 16 мин 45 с, а затем идёт с 10 до 4 за один шаг. В одном отношении настоящий контроллер осторожнее этого воспроизведения: он не учитывает поды, которые ещё не готовы, и консервативно обращается с отсутствующими метриками, чтобы поды, которые ещё запускаются, не создавали видимость низкого среднего.

**Автомасштабировщик кластера** (cluster autoscaler) работает уровнем ниже. HPA добавляет поды; если ни у одного узла не хватает незарезервированных CPU или памяти для их запросов, они остаются в `Pending`. Автомасштабировщик кластера следит за такими подами и добавляет машины в группу узлов через облачный API; он удаляет узел, когда запросы его подов занимают меньше половины узла в течение 10 минут, а его поды могут переехать в другое место. Добавление узла занимает минуты, а не секунды (виртуальная машина должна загрузиться и присоединиться к кластеру), так что вместе они реагируют на двух скоростях, и сервисы с внезапными пиками держат запас мощности. Karpenter, более новый автомасштабировщик узлов от AWS, ставший теперь проектом Kubernetes, подбирает типы машин под ожидающие поды вместо того, чтобы наращивать фиксированные группы. Третий автомасштабировщик, вертикальный (VPA), подстраивает сами запросы по измеренному использованию.

## Упаковка: Helm и Kustomize \{#packaging-helm-and-kustomize\}

Один и тот же сервис работает в staging и продакшене с небольшими различиями: реплики, тег образа, имена хостов, уровень журналирования, размеры ресурсов. Копирование YAML для каждого окружения — это расхождение из отправной точки. Два инструмента решают задачу противоположными способами.

**Helm** (версия 4 с ноября 2025 года) использует шаблоны. **Чарт** (chart) — каталог манифестов, написанных как шаблоны Go с заполнителями вроде `{{ .Values.image.tag }}`, файл `values.yaml` со значениями по умолчанию и метаданные. `helm install web ./chart -f values-prod.yaml` отрисовывает шаблоны со значениями продакшена и применяет результат; Helm записывает каждую установку как пронумерованную ревизию **релиза** (release), хранящуюся как Secret в пространстве имён, так что `helm rollback web 3` возвращает к ревизии 3. Чарты — версионируемые пакеты, которые распространяются через репозитории и реестры OCI, и они — обычный способ установить в кластер стороннее программное обеспечение: стек мониторинга, оператор базы данных, реализацию Gateway. Цена шаблонов в том, что манифесты существуют только после отрисовки, а шаблон со множеством условий трудно читать.

**Kustomize**, встроенный в `kubectl` как `kubectl kustomize` и `kubectl apply -k`, не использует шаблонов. **База** (base) — каталог обычных корректных манифестов; **оверлей** (overlay) для окружения перечисляет базу и изменения, которые в неё нужно внести: патчи, пространство имён, новый тег образа, генерируемые ConfigMap. [Пример](#example) строит с его помощью оверлей продакшена для веб-сервиса, и вывод там настоящий. Один из генераторов Kustomize заслуживает здесь внимания. Он называет сгенерированный ConfigMap с хешем его содержимого и переписывает каждую ссылку на него:

```console
$ kubectl kustomize overlays/prod | grep -n 'web-config-'
6:  name: web-config-b6dh7b267t
39:            name: web-config-b6dh7b267t
$ sed -i '' 's/LOG_LEVEL=warning/LOG_LEVEL=error/' overlays/prod/kustomization.yaml
$ kubectl kustomize overlays/prod | grep -n 'web-config-'
6:  name: web-config-68d5cgcdf4
39:            name: web-config-68d5cgcdf4
```

Изменение одного значения меняет имя ConfigMap, а с ним шаблон пода Deployment, который на него ссылается, а с ним и хеш шаблона: изменение конфигурации становится поэтапным обновлением из предыдущей заметки, с проверками готовности и откатом, вместо файлов, которые молча меняются под работающими подами. Возврат строки восстанавливает первое имя. (Форма `sed -i ''` — вариант для macOS; GNU `sed` принимает просто `-i`.)

Команды часто сочетают оба инструмента: чарты Helm для программ, сделанных другими, оверлеи Kustomize для собственных сервисов, а Kustomize умеет отрисовывать чарт Helm как часть оверлея.

## GitOps: согласование из Git \{#gitops-reconciliation-from-git\}

[Заметка о доставке](/ru/notes/devops/continuous-delivery#one-artifact-many-environments) ввела **GitOps** как практику: желаемое состояние каждого окружения живёт в репозитории Git, а развёртывание — это коммит. Kubernetes делает из этого механизм. Контроллер GitOps, **Argo CD** или **Flux** (оба — выпускные проекты Cloud Native Computing Foundation), работает внутри кластера и выполняет цикл из предыдущей заметки, где роль spec играет Git:

1. **Получить** (fetch) репозиторий на заданной ветке или теге — по расписанию (по умолчанию в Argo CD каждые 3 минуты) или когда веб-хук сообщает о push.
2. **Отрисовать** (render) манифесты из каталога с помощью Kustomize или Helm.
3. **Сравнить** (compare) их с живыми объектами в кластере: приложение находится в состоянии *Synced* или *OutOfSync*.
4. **Применить** (apply) разницу. С **удалением лишнего** (pruning) объекты, убранные из Git, удаляются из кластера; с **самовосстановлением** (self-healing) изменение, сделанное вручную через `kubectl`, откатывается при следующем сравнении — дрейф конфигурации из [заметки об инфраструктуре как коде](/ru/notes/devops/infrastructure-as-code#configuration-state-and-reality), исправляемый непрерывно.
5. **Сообщить** (report) о здоровье по собственному статусу объектов: Deployment, выкатка которого застряла, переводит приложение в состояние *Degraded*.

**Application** в Argo CD говорит контроллеру, что согласовывать:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/shop/deploy.git
    targetRevision: main
    path: web/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

`source` называет репозиторий, ветку и каталог оверлея из «Примера»; `destination` — кластер, в котором работает Argo CD (`kubernetes.default.svc` — адрес API-сервера изнутри кластера), и пространство имён; `automated` с `prune` и `selfHeal` делает Git единственным способом изменить эти объекты. Тогда конвейер CI сервиса заканчивается коммитом нового тега образа в этот репозиторий, а кластер сам его забирает.

Отсюда следуют два свойства. **Модель вытягивания** (pull model) означает, что CI никогда не держит учётных данных для кластера: он может только писать в репозиторий, а применяет контроллер внутри кластера, и это убирает мощный секрет из каждого конвейера. А история кластера — это история репозитория: кто что изменил, показывает `git log`, а откат — это `git revert`. Цена — ещё один компонент, за которым нужно следить, и одно практическое правило: поле, которым владеет контроллер в кластере, например `replicas`, которое записывает HPA, нужно не включать в Git, иначе контроллер GitOps и HPA будут за него бороться. Поэтому в базе из «Примера» нет `replicas`.

## Когда не стоит использовать Kubernetes \{#when-not-to-use-kubernetes\}

Kubernetes решает проблемы отправной точки предыдущей заметки за определённую цену. Кто-то должен обновлять кластер: проект выпускает три минорные версии в год и поддерживает каждую около 14 месяцев, так что кластер, который не обновляют, выходит из поддержки в течение полутора лет. Кто-то должен понимать его сеть, хранилище, правила доступа, дополнения и их взаимодействие и отлаживать их ночью. Управляемый управляющий слой снимает часть этой работы, но не дополнения, не манифесты и не обновления рабочих нагрузок.

Цена оправдана, когда сервисов много, несколько команд развёртываются независимо, нужно плотно упаковать много рабочих нагрузок на общие машины или есть команда платформы, чья работа — предоставлять всё это другим. Обычно она не оправдана для одного приложения с базой данных: бессерверный сервис контейнеров или платформа как сервис (PaaS), управляемая база данных или пара виртуальных машин с обратным прокси и скриптом развёртывания дают тот же результат с малой долей движущихся частей. Вопросы, которые стоит задать первыми: сколько сервисов и команд, какую часть эксплуатации кластера команда может взять на себя и не даёт ли уже недостающее более простой блок из [заметки об облаке](/ru/notes/devops/cloud-building-blocks#compute-virtual-machines-containers-functions).

## Что изменилось \{#what-changed\}

| Проблема отправной точки | Объект | Контроллер |
| --- | --- | --- |
| Конфигурация зашита в образ | ConfigMap, Secret | kubelet (переменные окружения и файлы) |
| Пароли доступны всем | Secret, шифрование при хранении, внешние хранилища | API-сервер, операторы секретов |
| Данные застряли на узле | PersistentVolumeClaim, StorageClass, StatefulSet | провизионер, контроллер StatefulSet |
| Порт и балансировщик на каждый сервис | Gateway, HTTPRoute (Ingress заморожен) | реализация Gateway |
| Угаданное число реплик | HorizontalPodAutoscaler; группы узлов | HPA; автомасштабировщик кластера |
| Копии для каждого окружения | оверлеи Kustomize, чарты и значения Helm | отрисовка перед применением |
| Изменения с ноутбуков | Git как желаемое состояние | Argo CD или Flux |

## Ограничения \{#limitations\}

- Каждое добавление — ещё один контроллер со своими видами отказов, версиями и правами. Кластер с реализацией Gateway, контроллером GitOps, оператором секретов, драйвером хранилища и тремя автомасштабировщиками состоит из множества движущихся частей, которые могут не соглашаться друг с другом.
- HPA реагирует на метрику, которая отстаёт от нагрузки: нужно, чтобы метрика выросла, затем один или несколько 15-секундных периодов, затем поды, которые запустятся и пройдут проверку готовности, а затем, возможно, новые узлы. Сервисы с резкими пиками масштабируются заранее, по расписанию или по длине очереди, или держат запас.
- Загрузка CPU — косвенный показатель нагрузки. Сервис, ограниченный базой данных, памятью или внешним API, не масштабируется вместе с CPU, и добавление подов может ухудшить узкое место.
- Рабочие нагрузки с состоянием остаются трудными. Зональные диски привязывают поды к зонам, StatefulSet не делает базу данных высокодоступной, а оператор хорош ровно настолько, насколько хорошо он справляется с конкретным отказом.
- GitOps делает Git источником истины только для того, что есть в Git: объекты, созданные контроллерами, операторами или вручную вне управляемых пространств имён, не охвачены, а секретам нужен отдельный путь.

## Что нужно запомнить \{#what-you-should-remember\}

- ConfigMap и Secret отделяют конфигурацию от образов. Переменные окружения читаются при запуске, смонтированные файлы обновляются позже. Secret — это base64, они хранятся в etcd незашифрованными, если не настроено шифрование при хранении; защищайте их шифрованием, правилами доступа и внешним источником.
- PVC запрашивает хранилище, StorageClass создаёт PV (облачный диск), а режимы доступа следуют за хранилищем: `ReadWriteOnce` для блочного диска. StatefulSet даёт стабильные имена, упорядоченный запуск и по одной заявке на под.
- Ingress заморожен, а Ingress NGINX выведен из эксплуатации (март 2026 года); Gateway API делит GatewayClass, Gateway и HTTPRoute по ролям, и маршруты могут разделять трафик по весам.
- HPA: $n_{\text{desired}} = \lceil n \cdot m / m^* \rceil$ каждые 15 с, с допуском 10% и 5-минутной стабилизацией при уменьшении; загрузка измеряется относительно запросов. Автомасштабировщик кластера добавляет узлы для подов, которые не помещаются.
- Helm отрисовывает шаблоны со значениями и записывает релизы; Kustomize патчит обычные базы оверлеями и перезапускает поды, когда меняется сгенерированная конфигурация.
- GitOps: контроллер в кластере получает Git, отрисовывает, сравнивает, применяет, удаляет лишнее и самовосстанавливается. CI пишет в Git, но никогда в кластер. Не включайте в Git поля, которыми владеют контроллеры, такие как `replicas`.
- Используйте Kubernetes, когда много сервисов и команд оправдывают платформу; иначе более простой облачный блок дешевле.

## Пример \{#example\}

Оверлей продакшена для веб-сервиса в том виде, в каком его хранил бы репозиторий GitOps: база Kustomize с Deployment, Service и генерируемым ConfigMap и оверлей `overlays/prod`, который добавляет пространство имён, новый тег образа, уровень журналирования продакшена, HPA и HTTPRoute. `kubectl kustomize` действительно собрал его (вывод ниже); к кластеру он не применялся.

База, `base/kustomization.yaml`, перечисляет `deployment.yaml` (Deployment из предыдущей заметки без `replicas` и, для краткости, без проб, читающий окружение из `web-config`), `service.yaml` и генератор:

```yaml
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: web-config
    literals:
      - LOG_LEVEL=info
```

Оверлей, `overlays/prod/kustomization.yaml`:

```yaml
namespace: shop
resources:
  - ../../base
  - hpa.yaml
  - httproute.yaml
images:
  - name: registry.example.com/web
    newTag: 1.4.3
configMapGenerator:
  - name: web-config
    behavior: merge
    literals:
      - LOG_LEVEL=warning
```

`overlays/prod/hpa.yaml`:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 4
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```

`overlays/prod/httproute.yaml`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
spec:
  parentRefs:
    - name: public
      namespace: gateways
  hostnames:
    - www.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web
          port: 80
```

Kustomization построчно:

- `namespace: shop` помещает каждый объект оверлея в пространство имён `shop`, что бы ни говорил его источник.
- `resources` перечисляет, что собирать: всю базу (каталог со своим `kustomization.yaml`) и два файла, которые есть только в продакшене.
- `images` заменяет тег каждого контейнера, использующего `registry.example.com/web`, на `1.4.3`. Продвижение новой версии здесь — коммит в одну строку, и именно такой коммит пишет конвейер и применяет Argo CD.
- `configMapGenerator` с `behavior: merge` берёт `web-config` из базы и переопределяет `LOG_LEVEL`; сгенерированное имя получает хеш содержимого.

HPA: `scaleTargetRef` называет Deployment, полем `replicas` которого он владеет; `minReplicas: 4` и `maxReplicas: 20` ограничивают его (четырёх хватает на под в каждой из трёх зон и ещё один, даже ночью); метрика — загрузка CPU относительно запросов с целью 60%, числа с рисунка; а `behavior.scaleDown.stabilizationWindowSeconds: 300` явно задаёт окно по умолчанию, чтобы его увидел ревьюер.

HTTPRoute: `parentRefs` присоединяет его к Gateway `public` в пространстве имён `gateways`, которым владеет команда платформы и который принимает маршруты из всех пространств имён; `hostnames` заявляет `www.example.com`, который подпадает под `*.example.com` слушателя; единственное правило отправляет каждый путь (`PathPrefix /`) в Service `web` на порт 80. Канарейка добавила бы вторую запись в `backendRefs` с полем `weight`.

Вывод сборки — то, что Argo CD сравнивал бы с кластером:

```console
$ kubectl kustomize overlays/prod
apiVersion: v1
data:
  LOG_LEVEL: warning
kind: ConfigMap
metadata:
  name: web-config-b6dh7b267t
  namespace: shop
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: shop
spec:
  ports:
  - name: http
    port: 80
    targetPort: http
  selector:
    app: web
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
spec:
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - envFrom:
        - configMapRef:
            name: web-config-b6dh7b267t
        image: registry.example.com/web:1.4.3
        name: web
        ports:
        - containerPort: 8080
          name: http
        resources:
          limits:
            memory: 256Mi
          requests:
            cpu: 250m
            memory: 256Mi
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
  namespace: shop
spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
  maxReplicas: 20
  metrics:
  - resource:
      name: cpu
      target:
        averageUtilization: 60
        type: Utilization
    type: Resource
  minReplicas: 4
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
  namespace: shop
spec:
  hostnames:
  - www.example.com
  parentRefs:
  - name: public
    namespace: gateways
  rules:
  - backendRefs:
    - name: web
      port: 80
    matches:
    - path:
        type: PathPrefix
        value: /
```

Теперь у каждого объекта есть `namespace: shop`; ConfigMap называется `web-config-b6dh7b267t`, и `configMapRef` в Deployment переписан ему в соответствие; у образа тег `1.4.3`; `LOG_LEVEL` равен `warning`; пространство имён в ссылке на Gateway осталось нетронутым, потому что оно намеренно называет другое пространство имён. Kustomize сортирует вывод по виду объектов, а ключи каждого объекта — по алфавиту, поэтому порядок отличается от входного. У Deployment нет `replicas`: при первом применении Kubernetes задаёт одну реплику, и HPA сразу поднимает число до своего минимума, 4.

## Дальше \{#next\}

Теперь сервис работает, масштабируется, доступен и развёртывается из Git. Работает ли он как надо — другой вопрос: успешны ли запросы, сколько они длятся, какая из четырёх реплик медленная и почему. Kubernetes сообщает о состоянии своих объектов, а не об опыте пользователей. [Следующая заметка](/ru/notes/devops/observability) начинает раздел о надёжности с трёх сигналов, которые испускает работающая система, — журналов, метрик и трассировок — и того, как их читать.
