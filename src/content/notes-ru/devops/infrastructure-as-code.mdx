## Отправная точка: консоль и скрипт из команд \{#baseline-a-console-and-a-script-of-commands\}

Первую инфраструктуру проекта создают вручную, в веб-консоли облачного провайдера: нажать «создать инстанс», заполнить форму, скопировать адрес в зону DNS. Это работает, но после себя не оставляет ничего, кроме результата. Никто не может проверить изменение до того, как оно произойдёт, никто потом не скажет, зачем существует правило межсетевого экрана, а построить второе окружение — значит повторить щелчки по памяти, и никогда не совсем так же. Серверы, созданные таким образом, каждый немного другой и невоспроизводимый, называют **снежинками** (snowflakes).

Следующий шаг — скрипт из команд: `create-instance`, `create-record`, `open-port`, выполняемых по порядку. Он записывает шаги, но описывает *действия*, а действия зависят от того, с чего они начинаются. Вот проблема в миниатюре, на двух командах оболочки, которые создают каталог и добавляют строку в файл конфигурации:

```console
$ mkdir logs
$ mkdir logs
mkdir: logs: File exists
$ mkdir -p logs; echo "exit status $?"
exit status 0
$ echo "max_connections = 100" >> app.conf
$ echo "max_connections = 100" >> app.conf
$ wc -l < app.conf
       2
$ grep -qxF "workers = 4" app.conf || echo "workers = 4" >> app.conf
$ grep -qxF "workers = 4" app.conf || echo "workers = 4" >> app.conf
$ cat app.conf
max_connections = 100
max_connections = 100
workers = 4
```

При повторном запуске `mkdir` падает, а `echo >>` молча дублирует строку. `mkdir -p` и защита `grep ... ||` устроены иначе: они проверяют, достигнут ли уже результат, и действуют, только если нет, так что двукратный запуск оставляет тот же результат, что и однократный. Это свойство — **идемпотентность** (idempotence): применение операции $n \ge 1$ раз даёт тот же эффект, что и однократное. Скрипт из команд `create` не идемпотентен. Запущенный повторно, он создаёт вторую машину; остановленный ошибкой на полпути, он оставляет половину окружения и никакой записи о том, какую половину; а удаление строки из него ничего не удаляет в облаке.

## Декларативный подход против императивного \{#declarative-against-imperative\}

**Императивное** описание перечисляет шаги: создать это, потом изменить то. **Декларативное** описание говорит о результате: должны существовать вот эти машины, эти записи, эти правила, с такими настройками. Инструмент сравнивает описание с тем, что существует, и сам вычисляет шаги. [Заметка о сборке](/ru/notes/devops/builds-and-dependencies#a-build-is-a-graph-of-targets) встречала ту же идею в `make`: Makefile объявляет цели и их входы, а `make` решает, какие команды выполнить. Декларативный инструмент идемпотентен по построению: когда существующее уже совпадает с описанием, делать нечего.

<aside class="callout"><strong>Ключевая идея.</strong> Инфраструктура как код (infrastructure as code, IaC) хранит три картины одной и той же инфраструктуры: **конфигурацию** — файлы в Git, которые говорят, что должно существовать; **состояние** — запись инструмента о том, какой реальный объект он создал для каждой части конфигурации; и **реальность**, прочитанную через API провайдера. **План** — разница между конфигурацией и реальностью, найденная через состояние; **применение** (apply) выполняет план и записывает результат. Тогда каждое изменение проходит через коммит, прошедший ревью, и план, который человек читает до того, как что-то произойдёт, а повторный запуск инструмента на неизменённой конфигурации даёт пустой план.</aside>

## Конфигурация, состояние и реальность \{#configuration-state-and-reality\}

Зачем инструменту вообще состояние, если можно спросить у провайдера, что существует? Затем, что API провайдера не знает, какие из его объектов относятся к этой конфигурации. Конфигурация называет ресурс собственным **адресом**, например `aws_s3_bucket.logs`; провайдер называет объект выбранным им идентификатором, например ID инстанса `i-0a1b2c...` или сгенерированным именем. Состояние — отображение адресов в идентификаторы вместе с последними известными атрибутами каждого объекта. Оно отвечает на три вопроса, на которые не может ответить ничто другое:

1. **С каким объектом сравнивать.** Чтобы проверить `aws_instance.web`, инструмент должен знать, какой это из тысяч инстансов в аккаунте.
2. **Что удалять.** Ресурс, удалённый из конфигурации, не оставляет в файлах следа. Его по-прежнему перечисляет только состояние, поэтому только состояние показывает, что реальный объект должен исчезнуть.
3. **В каком порядке.** Чтобы удалить объекты, конфигурации которых больше нет, инструменту нужны зависимости между ними, а их записывает состояние.

Построение плана занимает три шага. Инструмент читает конфигурацию и вычисляет её (переменные, ссылки между ресурсами), читает состояние и выполняет **обновление** (refresh): для каждого объекта из состояния он запрашивает у API провайдера текущие атрибуты объекта. Затем он сравнивает каждый ресурс конфигурации с его реальным объектом и назначает одно из пяти действий:

| Символ | Действие | Когда |
| --- | --- | --- |
| `+` | создание | есть в конфигурации, нет в состоянии (или его объекта больше не существует) |
| `~` | изменение на месте | атрибут отличается, и API может изменить его у работающего объекта |
| `-/+` | замена | отличается атрибут, который нельзя изменить у работающего объекта, например имя бакета или образ диска машины |
| `-` | удаление | есть в состоянии, нет в конфигурации |
| | ничего | конфигурация и реальность совпадают |

Замену стоит читать дважды: она удаляет объект и создаёт другой, и всё, что хранилось в старом, например данные на диске или объекты в бакете, в новый не переходит.

<PlanDiff />

1. Прочитать конфигурацию: что должно существовать.
2. Прочитать состояние: какой реальный объект стоит за каждым адресом.
3. Обновление: прочитать каждый объект через API. Кто-то вручную перенаправил запись `www`.
4. Сравнение: срок хранения меняется на месте, ручная правка откатывается, очередь создаётся, виртуальная машина, исчезнувшая из файла, удаляется.
5. Применение: план превращается в вызовы API в порядке, учитывающем зависимости.
6. Записать новое состояние с порядковым номером (serial), увеличенным на единицу.

**Дрейф конфигурации** (drift) — расхождение между реальностью и состоянием, которое внёс не инструмент: правка в консоли во время инцидента, изменившееся значение по умолчанию у провайдера, объект, удалённый другим скриптом. Обновление его находит, и следующий план предлагает его отменить, что правильно, когда правка была ошибкой, и неправильно, когда это было исправление, которое никто не записал. Либо конфигурацию меняют так, чтобы она соответствовала исправлению, либо правку откатывают. Команды обнаруживают дрейф, запуская план по расписанию: `tofu plan -detailed-exitcode` завершается с кодом 0, когда делать нечего, 1 при ошибке и 2, когда есть изменения, так что задание CI по расписанию может сообщать о коде 2 как о дрейфе.

**Разобранный пример.** Игрушечный планировщик из 50 строк показывает весь цикл: один словарь играет роль провайдера, другой — состояния, третий — конфигурации.

```python
import itertools

cloud = {}                        # провайдер: реальные объекты по ID
ids = itertools.count(101)

def plan(desired, state):
    """Compare the configuration with reality, reached through the state's IDs."""
    actions = []
    for addr, want in desired.items():
        obj = cloud.get(state.get(addr))         # обновление: прочитать реальный объект
        if obj is None:
            actions.append(("+", addr, want))
        elif obj["name"] != want["name"]:        # имя нельзя изменить на месте
            actions.append(("-/+", addr, want))
        elif obj != want:
            diff = ", ".join(f"{k}: {obj.get(k)} -> {v}" for k, v in want.items() if obj.get(k) != v)
            actions.append(("~", addr, diff))
    actions += [("-", addr, None) for addr in state if addr not in desired]
    return actions

def apply(actions, state):
    for op, addr, arg in actions:
        if op in ("-", "-/+"):
            del cloud[state.pop(addr)]
        if op in ("+", "-/+"):
            state[addr] = next(ids)
            cloud[state[addr]] = dict(arg)
        if op == "~":
            cloud[state[addr]] = dict(desired[addr])

def show(title, actions):
    print(f"{title}:" + (" no changes" if not actions else ""))
    for op, addr, arg in actions:
        print(f"  {op:>3} {addr}" + (f"  {arg}" if op == "~" else ""))

desired = {
    "bucket.logs": {"name": "web-logs", "expire_days": 30},
    "record.www":  {"name": "www", "target": "lb-1.example.net"},
}
state = {}                                     # адрес -> ID реального объекта

show("plan 1", p := plan(desired, state)); apply(p, state)
print("  state:", state)
show("plan 2", plan(desired, state))           # идемпотентность: делать нечего
cloud[state["record.www"]]["target"] = "lb-2.example.net"   # дрейф: правка вручную
show("plan 3", p := plan(desired, state)); apply(p, state)
desired["bucket.logs"]["name"] = "web-logs-v2"              # изменение, которое требует замены
del desired["record.www"]                                   # ресурс, удалённый из файла
show("plan 4", p := plan(desired, state)); apply(p, state)
print("  state:", state, " cloud:", cloud)
```

```console
$ python3.14 toyplan.py
plan 1:
    + bucket.logs
    + record.www
  state: {'bucket.logs': 101, 'record.www': 102}
plan 2: no changes
plan 3:
    ~ record.www  target: lb-2.example.net -> lb-1.example.net
plan 4:
  -/+ bucket.logs
    - record.www
  state: {'bucket.logs': 103}  cloud: {103: {'name': 'web-logs-v2', 'expire_days': 30}}
```

Первый план создаёт оба объекта, и состояние записывает их идентификаторы. Второй план пуст: операция идемпотентна. После ручной правки третий план откатывает дрейф. В четвёртом переименованный бакет заменяется, получая новый идентификатор 103, а запись, которой больше нет в конфигурации, удаляется; планировщик знал о ней только через состояние. Настоящий инструмент добавляет то, что опускает игрушка: граф зависимостей между ресурсами, провайдеры для сотен API и блокировку, чтобы двое не могли выполнять применение одновременно.

## OpenTofu и Terraform \{#opentofu-and-terraform\}

**Положение на октябрь 2026 года.** Terraform, который HashiCorp разрабатывает с 2014 года, — инструмент, сделавший эту модель общепринятой. В августе 2023 года HashiCorp перевела Terraform с открытой лицензии Mozilla Public License 2.0 на Business Source License 1.1, начиная с версии 1.6: исходный код остаётся доступным для чтения и бесплатным для использования в продакшене, кроме как для предложения продукта, конкурирующего с продуктами HashiCorp; лицензиаром теперь является IBM, завершившая покупку HashiCorp в феврале 2025 года. Группа компаний и пользователей создала из последней открытой версии форк **OpenTofu** — проект Linux Foundation под MPL 2.0, первый стабильный выпуск которого, 1.6.0, вышел в январе 2024 года. У них общий язык, общий протокол провайдеров и бо́льшая часть поведения, и конфигурация, написанная для одного, обычно работает и в другом; с тех пор они добавили разные возможности, например шифрование состояния в OpenTofu 1.7 (апрель 2024 года). Текущие выпуски — OpenTofu 1.13.2 и Terraform 1.17.0, оба от 21 октября 2026 года. Эта заметка использует OpenTofu и его команду `tofu`; команды `terraform` называются так же.

Язык — **HCL**, а конфигурация — каталог файлов `.tf` с пятью видами блоков.

- **Провайдеры** (providers) — плагины, которые переводят ресурсы в вызовы API одной платформы: облачного провайдера, сервиса DNS, Kubernetes, GitHub. Блок `required_providers` называет каждый из них адресом источника и диапазоном версий. `tofu init` скачивает их и записывает точные версии и их хеши в `.terraform.lock.hcl` — lock-файл в смысле [заметки о сборке](/ru/notes/devops/builds-and-dependencies#dependencies-from-outside-ranges-and-lockfiles), который коммитят в Git.
- **Ресурсы** (resources), `resource "TYPE" "NAME" { ... }`, — объекты, которыми управляет конфигурация; `TYPE.NAME` — адрес. **Источники данных** (data sources), `data "TYPE" "NAME"`, читают объекты, которыми конфигурация не управляет, например идентификатор общей сети.
- **Переменные** (variables) — входы конфигурации, **локальные значения** (locals) — именованные выражения, **выходные значения** (outputs) — значения, которые она сообщает.
- Ссылка вроде `aws_s3_bucket.logs.id` в другом ресурсе — ребро **графа зависимостей**: бакет создаётся первым, а удаляется последним. Инструмент обходит граф, по умолчанию выполняя до 10 независимых операций одновременно.
- **Модули** (modules) — каталоги файлов `.tf`, вызываемые с входными значениями, `module "NAME" { source = "...", ... }`, и именно так одно описание обслуживает несколько окружений: тот же модуль с `environment = "staging"` и с `environment = "prod"`.

**Удалённое состояние и блокировка.** Файл состояния на одном ноутбуке служит одному человеку. Команда хранит состояние в **бэкенде** (backend), например в бакете объектного хранилища, и бэкенд берёт **блокировку** (lock) на время плана или применения, чтобы два применения не могли перемешать свои вызовы и записи состояния. Начиная с OpenTofu 1.10 и Terraform 1.10 бэкенд S3 может блокировать файлом блокировки, записанным условной записью в самом бакете (`use_lockfile`), тогда как раньше ему требовалась отдельная таблица DynamoDB. Состояние содержит все атрибуты всех объектов, включая пароли баз данных и закрытые ключи, если их создают ресурсы, — открытым текстом, если оно не зашифровано, поэтому доступ к бакету состояния — это доступ к этим секретам; состояние никогда не коммитят в Git.

**Рабочий процесс.** Изменение — это коммит в конфигурацию, открытый как merge request. CI выполняет `tofu plan -out=plan.bin` и публикует план для ревью (такой конвейер описывает [заметка о непрерывной интеграции](/ru/notes/devops/continuous-integration)); после одобрения `tofu apply plan.bin` применяет ровно тот план, который прошёл ревью, и отказывается работать, если состояние изменилось с момента построения плана. Агент, который применяет всё, что говорит основная ветка, и продолжает это применять, — стиль GitOps из [заметки о доставке](/ru/notes/devops/continuous-delivery#one-artifact-many-environments); [заметки о Kubernetes](/ru/notes/devops/kubernetes-in-practice) строят такой агент.

## Управление конфигурацией и создание инфраструктуры \{#configuration-management-and-provisioning\}

OpenTofu **создаёт инфраструктуру** (provisioning): машины, сети, записи и бакеты через API провайдеров. То, что происходит *внутри* машины (пакеты, файлы, пользователи, службы), — это **управление конфигурацией** (configuration management), задача таких инструментов, как Ansible, Puppet, Chef и Salt, появившихся раньше облаков.

**Ansible** работает без агентов: он подключается к каждой машине по SSH, по списку хостов, который называется **инвентарём** (inventory), и выполняет **задачи** (tasks), сгруппированные в **плейбуки** (playbooks), написанные на YAML. Каждая задача вызывает **модуль**, и модули написаны так, чтобы быть идемпотентными: они читают текущее положение дел, меняют его, только если оно отличается от запрошенного, и сообщают `ok` (делать нечего) или `changed`. Плейбук для веб-серверов из предыдущей заметки:

```yaml
- name: Configure the web servers
  hosts: web
  become: true
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Write the site configuration
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: "0644"
      notify: Reload nginx

    - name: Keep nginx running and start it at boot
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

`hosts: web` выбирает группу `web` инвентаря, а `become: true` выполняет задачи от имени root. `state: present` требует, чтобы пакет был установлен, а не чтобы выполнилась установка: на машине, где nginx уже стоит, задача сообщает `ok`. Задача `template` отрисовывает `site.conf.j2` и записывает его, только если содержимое отличается; когда она всё же пишет файл, она **уведомляет** (notify) обработчик (handler), который перезагружает nginx один раз в конце прогона, сколько бы задач его ни уведомили. Первый запуск на свежей машине сообщает о всех трёх задачах как об изменённых и запускает обработчик; второй запуск сообщает о них `ok` и ничего не меняет. (Файл разбирается как YAML; против машин он здесь не запускался.) Идемпотентность — свойство каждого модуля, а не Ansible в целом: `ansible.builtin.command` выполняет свою команду при каждом запуске, если ему не указать через `creates:`, какой файл показывает, что работа уже сделана.

Два вида инструментов пересекаются на границах, и разделение обычно такое: OpenTofu создаёт машины, затем Ansible их настраивает. Ansible применяет изменения, когда его кто-то запускает; Puppet и Chef запускают на каждой машине агент, который забирает свою конфигурацию и приводит машину в соответствие с ней примерно каждые полчаса, что заодно исправляет дрейф внутри машин.

## Неизменяемая инфраструктура \{#immutable-infrastructure\}

Управление конфигурацией меняет серверы, которые работают месяцами, и каждое изменение, применённое к работающему серверу, — шанс, что он станет отличаться от соседей: обновление пакета, которое не удалось на одной машине, файл, отредактированный вручную во время инцидента. Альтернатива — вообще никогда не менять работающий сервер. **Неизменяемая инфраструктура** (immutable infrastructure) собирает полный образ — образ виртуальной машины или [образ контейнера](/ru/notes/devops/container-images) — с приложением и его конфигурацией внутри; изменение она развёртывает, запуская новые машины из нового образа, переводя на них трафик и уничтожая старые. Сервер, который никогда не изменяют, не может дрейфовать, все работающие копии одной версии идентичны, а откат — это предыдущий образ. Управление конфигурацией не исчезает: оно переезжает в сборку образа, где выполняется один раз, а его результат тестируется.

Два стиля иногда называют **питомцами и стадом** (pets and cattle): у сервера-питомца есть имя, его выхаживают, когда он болен, и по нему скучают, когда его нет; стадо пронумеровано, одинаково, и заболевшую особь заменяют. Неизменяемая инфраструктура превращает серверы в стадо. Ей нужно всё, что построили предыдущие заметки: автоматическая сборка, которая производит образы, развёртывание, которое постепенно переводит трафик, а также проверки здоровья и плавный вывод из ротации, чтобы старые экземпляры уходили, не теряя запросов. Данные должны жить вне заменяемых машин — в базах данных, томах и объектном хранилище, — и это одна из причин, по которым [следующая заметка](/ru/notes/devops/cloud-building-blocks) отделяет вычисления от хранения. Kubernetes, в разделе после неё, применяет ту же идею к контейнерам и выполняет согласование из этой заметки непрерывно.

## Что изменилось \{#what-changed\}

| Проблема инфраструктуры, созданной вручную | Механизм | Где он живёт |
| --- | --- | --- |
| Нет записи и ревью изменений | конфигурация в Git, планы в merge request | репозиторий и CI |
| Скрипт не идемпотентен | декларативное описание; действия вычисляет инструмент | OpenTofu или Terraform |
| Какой реальный объект какой | состояние: адрес → ID и последние атрибуты | удалённый бэкенд с блокировкой |
| Ручные правки остаются незамеченными | обновление и обнаружение дрейфа планами по расписанию | CI, `-detailed-exitcode` |
| Окружения расходятся | модули с переменными для каждого окружения | каталоги модулей |
| Серверы дрейфуют изнутри | идемпотентное управление конфигурацией, затем неизменяемые образы | Ansible, сборка образов |

## Ограничения \{#limitations\}

- План — это прогноз. Применение всё равно может упасть на полпути — на квоте, правах доступа или ошибке API — и оставить одни объекты изменёнными, а другие нет; состояние записывает то, что произошло, и следующий план продолжает с этого места.
- Состояние драгоценно. Потерянное или повреждённое состояние оставляет объекты, о которых инструмент больше не знает и которые нужно вернуть под управление через `tofu import`; зависшая блокировка блокирует любые изменения, пока её не снимут вручную. Переименование ресурса в конфигурации выглядит как удаление и создание, если блок `moved` не говорит, что это тот же объект.
- Инструмент видит только то, чем управляет. Объекты, созданные вручную, другими конфигурациями или самим провайдером, для него невидимы, поэтому «план пуст» не значит «аккаунт соответствует описанию».
- Провайдеры — толстые переводчики больших API, и их ошибки и значения по умолчанию становятся поведением конфигурации; обновление провайдера может изменить план без единого изменения в файлах.
- Секреты в состоянии и потребность в блокировке делают бэкенд чувствительной общей зависимостью; длинные цепочки зависимых конфигураций, где одна читает выходные значения другой, замедляют распространение изменений.

## Что нужно запомнить \{#what-you-should-remember\}

- Императивные скрипты перечисляют действия и ломаются при повторном запуске или неожиданной начальной точке; декларативное описание говорит о результате, а действия вычисляет инструмент, и это делает его идемпотентным.
- Три картины: конфигурация (что должно существовать), состояние (адрес → реальный ID, последние атрибуты) и реальность (её читает обновление). План — их разница: `+` создание, `~` изменение, `-/+` замена, `-` удаление.
- Только состояние показывает, что удалять, когда ресурс исчезает из файлов. Храните его в удалённом бэкенде с блокировкой, ограничивайте доступ к нему и никогда не коммитьте его.
- Дрейф конфигурации — реальность, изменённая за спиной инструмента; планы по расписанию с `-detailed-exitcode` его находят, а человек решает, принять его или откатить.
- OpenTofu (MPL 2.0, Linux Foundation) — открытый форк Terraform (BSL 1.1 начиная с 1.6, теперь IBM); оба используют HCL, провайдеры, ресурсы, переменные, модули и один и тот же рабочий процесс plan/apply.
- Создание инфраструктуры создаёт машины и сети; управление конфигурацией (Ansible: SSH, плейбуки, идемпотентные модули, сообщающие `ok` или `changed`) формирует то, что внутри. Неизменяемая инфраструктура заменяет машины вместо того, чтобы их менять.

## Пример \{#example\}

Конфигурация бакета, который хранит журналы доступа сервиса: с версионированием, с удалением журналов через 30 дней, в одном из двух окружений, с состоянием в удалённом бэкенде с блокировкой. Она написана для OpenTofu 1.13 и провайдера AWS 6.x по их документации и здесь не запускалась, поскольку для запуска нужен облачный аккаунт.

```hcl
terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  backend "s3" {
    bucket       = "example-tofu-state"
    key          = "web/logs.tfstate"
    region       = "eu-central-1"
    use_lockfile = true
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  type    = string
  default = "eu-central-1"
}

variable "environment" {
  type = string
  validation {
    condition     = contains(["staging", "prod"], var.environment)
    error_message = "The environment must be staging or prod."
  }
}

locals {
  tags = {
    service     = "web"
    environment = var.environment
    managed-by  = "opentofu"
  }
}

resource "aws_s3_bucket" "logs" {
  bucket = "example-web-logs-${var.environment}"
  tags   = local.tags
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_lifecycle_configuration" "logs" {
  bucket = aws_s3_bucket.logs.id
  rule {
    id     = "expire-old-logs"
    status = "Enabled"
    filter {}
    expiration {
      days = 30
    }
  }
}

output "logs_bucket" {
  value = aws_s3_bucket.logs.bucket
}
```

- `terraform { ... }` содержит настройки самого инструмента; OpenTofu сохраняет имя блока ради совместимости. `required_version` отказывается работать с OpenTofu старше 1.10, первой версии с `use_lockfile`.
- `required_providers` запрашивает провайдер AWS по адресу реестра `hashicorp/aws`, любой версии 6.x (`~> 6.0` разрешает 6.1 и 6.9, но не 7.0). `tofu init` выбирает одну и записывает её вместе с хешами в `.terraform.lock.hcl`.
- `backend "s3"` хранит состояние как объект `web/logs.tfstate` в уже существующем бакете `example-tofu-state` и блокирует его файлом блокировки рядом. Бакет состояния создают один раз, вручную или отдельной конфигурацией: конфигурация не может хранить своё состояние в бакете, который ей ещё предстоит создать.
- `provider "aws"` настраивает плагин: регион берётся из переменной. Учётных данных в файле нет; провайдер читает их из окружения машины, на которой запущен `tofu`.
- У `variable "region"` есть значение по умолчанию; у `variable "environment"` его нет, поэтому его нужно передать, как `-var environment=prod` или в файле `.tfvars` для каждого окружения. Блок `validation` отвергает любое другое значение ещё до построения плана.
- `locals { tags = ... }` определяет теги один раз, чтобы повесить их на каждый ресурс; тогда счёт и консоль показывают, к какому сервису и окружению относится объект.
- `resource "aws_s3_bucket" "logs"`: адрес — `aws_s3_bucket.logs`. Его имя строится из переменной, в продакшене это `example-web-logs-prod`; имена бакетов глобальны для всех аккаунтов, поэтому у него есть префикс.
- `aws_s3_bucket_versioning.logs` и `aws_s3_bucket_lifecycle_configuration.logs` — отдельные ресурсы, которые настраивают бакет. Каждый ссылается на `aws_s3_bucket.logs.id`, и это делает бакет зависимостью: он создаётся первым.
- Правило жизненного цикла `rule` применяется ко всем объектам (пустой `filter {}`) и удаляет их через 30 дней после создания. Поскольку версионирование включено, истёкший объект становится неактуальной версией, а не исчезает; полная конфигурация добавила бы блок `noncurrent_version_expiration`, чтобы удалять и их.
- `output "logs_bucket"` печатает имя бакета после применения и делает его доступным для чтения другим конфигурациям.

**План словами.** С `-var environment=prod` и пустым состоянием `tofu plan` перечисляет три ресурса, каждый с префиксом `+`. Он показывает атрибуты, которые задаёт файл, например `bucket = "example-web-logs-prod"` и теги, а те, что назначает провайдер, например ARN бакета, помечает как известные только после применения. Он заканчивается сводкой «3 to add, 0 to change, 0 to destroy». После применения второй план сообщает, что изменений нет. Замена `days = 30` на `days = 90` даёт один ресурс, помеченный `~`, изменяемый на месте: «0 to add, 1 to change, 0 to destroy». Изменение имени бакета даёт `-/+` для бакета с пометкой, что имя вынуждает замену, и замены двух ресурсов, которые на него ссылаются; применение затем упало бы на удалении старого бакета, если в нём ещё есть журналы, если только ресурс не задаёт `force_destroy` — а это ровно та строка, которую должен искать ревьюер.
