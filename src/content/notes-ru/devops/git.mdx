[Предыдущая заметка](/ru/notes/devops/the-shell) закончилась скриптами, конфигурацией и кодом — текстовыми файлами, которые меняются каждый день, часто несколькими людьми одновременно. Каждая сборка в остальной части курса начинается с точной версии этих файлов, и каждое развёртывание должно прослеживаться до одной из них. Эту историю хранит Git. У его команд репутация произвольных, но это операции над небольшой и регулярной структурой данных: хранилищем неизменяемых объектов, названных по их хешам и связанных в граф, с несколькими подвижными именами, которые указывают внутрь него. Эта заметка строит такую структуру на настоящем одноразовом репозитории, затем разбирает слияние, перебазирование, отмену изменений и отправку как операции над графом и заканчивается тем, как команды организуют вокруг него свои ветки.

Поэтому каждый хеш ниже воспроизводим: те же команды с теми же датами дают те же имена объектов на любой машине.

## Отправная точка: копии файлов \{#baseline-copies-of-files\}

Без системы контроля версий историю хранят в виде копий: `app_v2_final.py`, папка с датой на каждый релиз или общий сетевой диск. Ломаются три вещи. Изменение нескольких файлов не записывается как одно изменение, поэтому «состояние проекта во вторник» вернуть невозможно. Два человека, правящие один файл, затирают правки друг друга или вручную выясняют, что изменил другой. И ничто не записывает, почему строка изменилась и кто её изменил.

Централизованные системы, такие как CVS (1990) и Subversion (2000), решили первую и третью проблемы с помощью сервера, который хранит историю, а вторую — блокировками или слияниями на сервере. Каждой операции нужен был сервер, а ветки были дорогими копиями. Git, написанный Линусом Торвальдсом в апреле 2005 года для ядра Linux, сделал каждый клон полным репозиторием со всей историей, так что коммиты, ветвление и чтение истории стали локальными операциями, а обмен работой — копированием объектов между репозиториями.

## Объекты: blob-объекты, деревья и коммиты \{#objects-blobs-trees-and-commits\}

Хранилище Git — это **хранилище «ключ — значение»** (key–value store) в `.git/objects`. Значение — объект; ключ — хеш от типа объекта, его размера и содержимого. Здесь важны три вида объектов ([Pro Git, ch. 10](#references)):

- **blob-объект** (blob) хранит байты одного файла, без имени и без прав доступа;
- **дерево** (tree) хранит один каталог: список записей, у каждой из которых есть режим, тип, хеш и имя;
- **коммит** (commit) хранит хеш одного корневого дерева, хеши нуля или более родительских коммитов, автора, коммитера, метки времени и сообщение.

Четвёртый вид, аннотированная метка (annotated tag), даёт коммиту имя вместе с сообщением и, часто, подписью.

**Разобранный пример.** Новый репозиторий с README и одним файлом на Python. `git add` сохраняет содержимое каждого файла как blob-объект и записывает его в индекс; закоммичено пока ничего не было.

```console
$ git init -q -b main shop && cd shop
$ echo 'Shop service' > README.md
$ mkdir src && printf 'def total(prices):\n    return sum(prices)\n' > src/app.py
$ git add README.md src/app.py
$ git ls-files --stage
100644 968833021ad0e455854d495ed63783700c559153 0	README.md
100644 aa11c8780835909b20ba5d886e45b00f65b2026c 0	src/app.py
$ find .git/objects -type f
.git/objects/96/8833021ad0e455854d495ed63783700c559153
.git/objects/aa/11c8780835909b20ba5d886e45b00f65b2026c
$ git cat-file -t 9688330
blob
$ git cat-file -p 9688330
Shop service
```

Существуют два объекта, по одному на файл, каждый в файле, названном по его хешу: первые две шестнадцатеричные цифры — каталог, остальные 38 — имя файла. `git cat-file` читает объект обратно: `-t` печатает его тип, `-p` — содержимое. Имя не произвольно. Это хеш SHA-1 от заголовка — типа, пробела, размера в байтах и нулевого байта, — за которым следует содержимое. `Shop service` с переводом строки занимает 13 байт, и хеширование тех же байтов обычным инструментом даёт то же имя:

```console
$ printf 'blob 13\0Shop service\n' | shasum -a 1
968833021ad0e455854d495ed63783700c559153  -
$ git hash-object README.md
968833021ad0e455854d495ed63783700c559153
```

Коммит записывает деревья и объект коммита:

```console
$ git commit -q -m 'Add README and total()'
$ git cat-file -p HEAD
tree f31a99ca63ff20a7a758d0b9d1e47abe829a64b4
author Ada Example <ada@example.com> 1792660260 +0000
committer Ada Example <ada@example.com> 1792660260 +0000

Add README and total()
$ git cat-file -p 'HEAD^{tree}'
100644 blob 968833021ad0e455854d495ed63783700c559153	README.md
040000 tree 54955cdb23c8e01de7f84d02c260622e1920d748	src
$ git cat-file -p HEAD:src
100644 blob aa11c8780835909b20ba5d886e45b00f65b2026c	app.py
```

Коммит называет своё корневое дерево и не имеет родителя, потому что он первый. Метка времени — число секунд с 1970 года со смещением часового пояса: 1792660260 — это 22 октября 2026 года, 09:11 UTC. Корневое дерево перечисляет blob-объект `README.md` с режимом `100644` (обычный файл) и поддерево `src` с режимом `040000`; поддерево перечисляет `app.py`. Второй коммит меняет одну строку `app.py`:

```console
$ printf 'def total(prices):\n    return round(sum(prices), 2)\n' > src/app.py
$ git commit -q -am 'Round the total'
$ git cat-file -p HEAD
tree 6aca1b53c821cf4e1bf8d46687d36df3cbd9d8f6
parent aba6e652e101170a8a0d2546a19a0ae27257699d
author Ada Example <ada@example.com> 1792660620 +0000
committer Ada Example <ada@example.com> 1792660620 +0000

Round the total
$ git ls-tree -r HEAD
100644 blob 968833021ad0e455854d495ed63783700c559153	README.md
100644 blob b7332794ea787bc9b0e3495d430886e3c45e681c	src/app.py
$ git count-objects
9 objects, 36 kilobytes
$ git log --oneline
1702a7d Round the total
aba6e65 Add README and total()
```

Каждый коммит — полный снимок, а не diff: он называет полное дерево. И всё же второй коммит добавил только четыре объекта — новый blob-объект для `app.py`, новое дерево `src`, новое корневое дерево и сам коммит, — потому что содержимое README не изменилось, так что у его blob-объекта то же имя, и он уже сохранён. Всего девять объектов: два коммита, четыре дерева, три blob-объекта. (Каждый неупакованный объект занимает на диске блок в 4 КиБ, отсюда 36 килобайт на несколько сотен байт данных; позже Git упаковывает объекты в один сжатый файл, храня похожие объекты как дельты.)

<aside class="callout"><strong>Ключевая идея.</strong> Git — хранилище с адресацией по содержимому (content-addressed store): каждый объект назван по хешу своего содержимого, и объекты ссылаются друг на друга по этим именам. Коммит называет дерево и своих родителей, поэтому его хеш покрывает весь снимок и всю историю за ним. Объекты никогда не меняются; всё, что выглядит как изменение, — новый коммит, слияние, перебазирование, сброс, — добавляет объекты или передвигает имя.</aside>

У адресации по содержимому три следствия, на которые опирается остальной курс. **Дедупликация**: одинаковое содержимое хранится один раз, в каком бы файле, каталоге или коммите оно ни встречалось. **Целостность**: изменение любого байта любого файла в истории изменило бы имя его blob-объекта, а значит, и дерева, которое его перечисляет, а значит, и каждого коммита выше, так что хеш коммита — отпечаток всего, что из него достижимо (такая структура называется деревом Меркла, Merkle tree). Два репозитория, согласные в хеше коммита, согласны во всей истории. **Неизменяемость**: объект нельзя отредактировать, его можно только заменить новым, с новым именем. Поэтому сборку, которая записывает хеш коммита, из которого она сделана, можно воспроизвести по одному этому хешу, и с этого начинается [заметка о сборке](/ru/notes/devops/builds-and-dependencies).

## Ссылки, HEAD и индекс \{#refs-head-and-the-index\}

Хешами люди не пользуются как именами. **Ссылка** (ref) — файл, в котором записан хеш: ветка `main` — это файл `.git/refs/heads/main`, метка `v1.0` — `.git/refs/tags/v1.0`. **HEAD** говорит, что сейчас извлечено. Обычно это *символическая* ссылка, которая хранит имя ветки, а не хеш:

```console
$ cat .git/HEAD .git/refs/heads/main
ref: refs/heads/main
aba6e652e101170a8a0d2546a19a0ae27257699d
```

(Это напечатано после первого коммита.) Коммит делает три вещи: записывает дерево из индекса, записывает объект коммита, родитель которого — коммит, на который указывает HEAD, и передвигает ветку, названную в HEAD, на новый коммит. Поэтому ветка — подвижный указатель, и её создание записывает 41 байт. Когда HEAD хранит хеш напрямую, а не имя ветки, репозиторий находится в состоянии *отсоединённого HEAD* (detached HEAD): новые коммиты создаются, но ни одна ветка к ним не передвигается.

**Индекс** (`.git/index`, его также называют областью подготовки, staging area) — дерево следующего коммита, которое собирается. `git add` сохраняет blob-объект и направляет на него запись индекса для этого пути; `git commit` превращает индекс в деревья. Так у каждого файла появляются три версии для сравнения:

| Где | Что хранит | Чем сравнивать |
| --- | --- | --- |
| рабочий каталог (working tree) | файлы на диске в том виде, в каком их правят | `git diff` (рабочий каталог с индексом) |
| индекс | снимок, который запишет следующий коммит | `git diff --staged` (индекс с HEAD) |
| HEAD | снимок последнего коммита | `git diff HEAD` (рабочий каталог с HEAD) |

<ObjectGraph />

1. Blob-объекты хранят содержимое файлов. Blob-объект README `9688330` хранится один раз и перечислен в обоих корневых деревьях.
2. Деревья перечисляют имена, режимы и хеши; `src` — дерево внутри корневого дерева.
3. Коммиты называют корневое дерево и своего родителя: `1702a7d` указывает на `aba6e65`.
4. Ветка `main` хранит хеш `1702a7d`; HEAD хранит имя ветки.
5. Индекс перечисляет те же blob-объекты, что и дерево HEAD, потому что после коммита ничего не менялось.

## SHA-1, SHA-256 и переход на новый хеш \{#sha-1-sha-256-and-the-hash-transition\}

Безопасность адресации по содержимому зависит от хеша. Если бы у двух разных объектов было одно имя, один можно было бы подменить другим. В феврале 2017 года атака SHAttered дала первую практическую коллизию SHA-1 — два разных PDF-файла с одинаковым SHA-1 ([Stevens et al., 2017](#references)). Git ответил в два шага (по состоянию на октябрь 2026 года):

- **Обнаружение коллизий.** Начиная с Git 2.13 (май 2017 года) Git вычисляет SHA-1 усиленной реализацией SHA-1DC, которая распознаёт шаблон известных атак на коллизии и отвергает такие входные данные. Имена объектов не изменились.
- **Новый формат объектов.** Git 2.29 (октябрь 2020 года) в порядке эксперимента добавил репозитории, объекты которых называются по SHA-256. Git 2.42 (август 2023 года) убрал предупреждение «experimental» и пообещал, что SHA-256-репозитории, созданные с этого момента, останутся читаемыми. Репозиторий использует либо один формат, либо другой; обмен объектами между SHA-1- и SHA-256-репозиториями в 2026 году всё ещё не поддерживался, а поддержка на хостингах была частичной, поэтому большинство репозиториев по-прежнему используют SHA-1.
- **Умолчание.** Список запланированных несовместимых изменений Git делает SHA-256 умолчанием для новых репозиториев в Git 3.0 — вместе с `main` как именем ветки по умолчанию, — как только это поддержит экосистема. В октябре 2026 года у Git 3.0 не было даты выпуска ([Git, BreakingChanges](#references)).

В SHA-256-репозитории тот же README получает имя из 64 цифр, и это снова хеш заголовка и содержимого:

```console
$ git init -q --object-format=sha256 -b main shop256 && cd shop256
$ echo 'Shop service' > README.md && git hash-object README.md
456d2d4af7b3d0b91048f814e52142db640bfc8dc4e9e452b7213ad8640ca6f1
$ git rev-parse --show-object-format
sha256
```

## Коммиты образуют граф \{#commits-form-a-graph\}

Каждый коммит называет своих родителей, поэтому коммиты образуют **направленный ациклический граф** (directed acyclic graph, DAG): рёбра идут от коммита к его родителям, назад во времени, и ни один коммит не может быть собственным предком, поскольку имя коммита зависит от имён его родителей, которые должны существовать раньше. История ветки — всё, что достижимо из коммита, на который она указывает. Расходящиеся ветки — просто два имени, указывающих на коммиты с общим предком.

Пример продолжается: коммит в `main` добавляет функцию `greet`, затем ветка `discount` добавляет в `total` параметр скидки и тест, тем временем `main` переводит `greet` на f-строку, а ветка `currency`, созданная в этой точке, форматирует сумму в евро.

```console
$ git log --graph --oneline --all
* 38b0e01 Format the total in euros
* 64e3131 Use an f-string in greet()
| * 3e85af1 Test the discount
| * 5059e4d Add a discount to total()
|/  
* ff2de94 Add greet()
* 1702a7d Round the total
* aba6e65 Add README and total()
$ git merge-base main discount
ff2de943b308ab39c6dd3b5ae78215901cc55ecc
```

`git merge-base` находит лучшего общего предка двух коммитов: коммит, достижимый из обоих, от которого не происходит ни один другой такой коммит. Здесь это `ff2de94`, где ответвилась `discount`. База слияния (merge base) — то, что делает слияние возможным.

## Слияние и перебазирование \{#merge-and-rebase\}

Объединить работу `discount` с `main` можно двумя способами: записать, что истории соединились, или переписать одну историю поверх другой.

**Трёхстороннее слияние** (three-way merge) сравнивает три версии каждого файла: базу слияния, *нашу* (текущая ветка) и *их* (сливаемая ветка). Для каждого участка каждого файла:

- если его изменила только одна сторона, берётся версия этой стороны;
- если обе стороны внесли одинаковое изменение, оно берётся один раз;
- если обе стороны изменили его по-разному, это **конфликт** (conflict), который оставляют человеку.

Работает это благодаря сравнению с базой. Двустороннее сравнение нашей и их версий не могло бы отличить «они добавили эту строку» от «мы её удалили»; ответ даёт база. Результат записывается как новый **коммит слияния** (merge commit) с двумя родителями.

```console
$ git merge --no-edit discount
Auto-merging src/app.py
Merge made by the 'ort' strategy.
 src/app.py        | 4 ++--
 tests/test_app.py | 5 +++++
 2 files changed, 7 insertions(+), 2 deletions(-)
 create mode 100644 tests/test_app.py
$ git cat-file -p HEAD
tree 981d4c985f533f4066767d8b5734de6b582956a8
parent 64e3131590ec51878ddc789c5c31da3082d725c7
parent 3e85af12326bf50c0384daa3e033add3b7046793
author Ada Example <ada@example.com> 1792662120 +0000
committer Ada Example <ada@example.com> 1792662120 +0000

Merge branch 'discount'
```

Обе ветки правили `src/app.py`, но в разных функциях, поэтому слияние без вопросов взяло новую `greet` из `main` и новую `total` из `discount`. `ort` — стратегия слияния Git по умолчанию начиная с версии 2.34 (2021). С веткой `currency` всё иначе: она изменила строку `return` функции `total`, которую изменила и `discount`. Если задать `merge.conflictStyle` равным `diff3`, конфликт покажет все три версии:

```console
$ git config merge.conflictStyle diff3
$ git merge currency
Auto-merging src/app.py
CONFLICT (content): Merge conflict in src/app.py
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU src/app.py
$ sed -n '4,14p' src/app.py

<<<<<<< HEAD
def total(prices, discount=0):
    return round(sum(prices) * (1 - discount), 2)
||||||| 64e3131
def total(prices):
    return round(sum(prices), 2)
=======
def total(prices):
    return f"{sum(prices):.2f} EUR"
>>>>>>> currency
```

Между `<<<<<<<` и `|||||||` — наша версия, `main` со скидкой; между `|||||||` и `=======` — база, `64e3131`; дальше — их версия, `currency`. База показывает, чего хотела каждая сторона: наша добавила скидку, их — изменила форматирование. Никакое правило не объединит это автоматически, а человек может: сохранить оба изменения, как `f"{sum(prices) * (1 - discount):.2f} EUR"`. После правки файла `git add` помечает конфликт разрешённым (`UU` означает «не слито, изменено обеими сторонами»), а `git commit` записывает слияние.

**Перебазирование** (rebase) берёт коммиты ветки, которых нет в целевой ветке, и по одному воспроизводит их изменения поверх целевой ветки как новые коммиты. Для сравнения со слиянием копия `discount` была перебазирована на `main` до слияния:

```console
$ git branch discount-rebased discount
$ git rebase main discount-rebased
Rebasing (1/2)
Rebasing (2/2)
Successfully rebased and updated refs/heads/discount-rebased.
$ git log --graph --oneline main discount-rebased
* 39e52f2 Test the discount
* e51616d Add a discount to total()
* 64e3131 Use an f-string in greet()
* ff2de94 Add greet()
* 1702a7d Round the total
* aba6e65 Add README and total()
```

У двух коммитов те же сообщения и те же изменения, но это новые коммиты, `e51616d` и `39e52f2` вместо `5059e4d` и `3e85af1`. Их родители другие, значит, другое и их содержимое, значит, другие и имена. История — прямая линия, как будто работу начали после `64e3131`.

<MergeRebase />

Что выбрать, следует из того, что каждый способ делает с графом.

- **Слияние** сохраняет правдивую историю: граф показывает, что работа шла параллельно и где она соединилась, и ни один существующий коммит не меняется. Оно безопасно для веток, которые забрали другие. Цена — граф со множеством соединений, который труднее читать и в котором труднее вести бисекцию.
- **Перебазирование** сохраняет историю линейной и удобной для чтения; это обычный способ подтянуть ветку с функцией к `main` перед ревью или привести в порядок локальные коммиты (`git rebase -i` переставляет, объединяет и правит их). Цена в том, что оно создаёт новые коммиты и бросает старые. У каждого, кто строил работу на старых коммитах, теперь есть коммиты, которых больше нет в ветке, и их следующее слияние продублирует изменения. Отсюда правило: перебазируйте только коммиты, которых больше ни у кого нет.
- **Слияние со сплющиванием** (squash merge), которое предлагают хостинги, объединяет всю ветку в один новый коммит в `main`: линейно, как при перебазировании, и по одному коммиту на каждое прошедшее ревью изменение.

## Отмена: reset, revert, reflog \{#undoing-reset-revert-reflog\}

Поскольку объекты никогда не меняются, «отменить» означает передвинуть имена или добавить коммиты.

**`git reset <commit>`** передвигает текущую ветку на другой коммит. С `--soft` передвигается только ветка, так что индекс и рабочий каталог по-прежнему содержат более новое содержимое, готовое к повторному коммиту; с `--mixed`, режимом по умолчанию, сбрасывается и индекс; с `--hard` сбрасываются и индекс, и рабочий каталог, а незакоммиченные изменения теряются. Команда переписывает историю ветки, поэтому она — для коммитов, которыми ещё ни с кем не поделились.

**`git revert <commit>`** добавляет новый коммит, применяющий изменение, обратное данному. История только растёт, поэтому это безопасная отмена на общей ветке.

**Reflog** записывает каждое положение, в котором побывали HEAD и каждая ветка, локально. Именно он делает ошибочный сброс обратимым: брошенный коммит всё ещё лежит в хранилище объектов, и reflog всё ещё его называет.

```console
$ echo 'print("debug")' >> src/app.py && git commit -q -am 'WIP debug'
$ git reset --hard HEAD~1
HEAD is now at 0df5ce9 Merge branch 'currency'
$ git reflog -3
0df5ce9 HEAD@{0}: reset: moving to HEAD~1
bfbe147 HEAD@{1}: commit: WIP debug
0df5ce9 HEAD@{2}: commit (merge): Merge branch 'currency'
$ git reset --hard 'HEAD@{1}'
HEAD is now at bfbe147 WIP debug
$ git revert --no-edit HEAD
[main 2c22ec0] Revert "WIP debug"
 Date: Thu Oct 22 09:57:00 2026 +0000
 1 file changed, 1 deletion(-)
$ git log --oneline -3
2c22ec0 Revert "WIP debug"
bfbe147 WIP debug
0df5ce9 Merge branch 'currency'
```

`HEAD~1` — первый родитель HEAD. Сброс оставил `bfbe147` недостижимым из любой ветки, а `HEAD@{1}`, «где HEAD был один шаг назад», вернул его. Затем revert отменил его общепринятым способом: и ошибка, и её исправление остаются в истории. Записи reflog устаревают — по умолчанию через 90 дней или через 30 для коммитов, которые больше не достижимы из текущей вершины ссылки; только после этого сборка мусора может удалить объекты ([git-reflog, git-gc](#references)).

**Поиск коммита, который что-то сломал**, — это поиск по графу. `git bisect` принимает плохой коммит и хороший и извлекает коммит посередине между ними; пользователь отвечает, хороший он или плохой, и команда снова делит диапазон пополам, так что $n$ коммитов требуют около $\log_2 n$ проверок — это поиск из [рассуждения о размере пакета](/ru/notes/devops/what-devops-is#why-small-batches-lower-risk). С `git bisect run` решение принимает команда: статус завершения 0 означает «хороший», от 1 до 127 (кроме 125) — «плохой». Тест того, что сумма 10 и 20 — число 30:

```console
$ printf 'from src.app import total\nassert total([10, 20]) == 30\n' > check.py
$ git bisect start HEAD aba6e65
Bisecting: 5 revisions left to test after this (roughly 2 steps)
[3e85af12326bf50c0384daa3e033add3b7046793] Test the discount
$ git bisect run python3 check.py 2>/dev/null
running 'python3' 'check.py'
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[38b0e019e24e1d880fcbec5be7141e3581731e6e] Format the total in euros
running 'python3' 'check.py'
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[64e3131590ec51878ddc789c5c31da3082d725c7] Use an f-string in greet()
running 'python3' 'check.py'
38b0e019e24e1d880fcbec5be7141e3581731e6e is the first bad commit
commit 38b0e019e24e1d880fcbec5be7141e3581731e6e
Author: Ada Example <ada@example.com>
Date:   Thu Oct 22 09:34:00 2026 +0000

    Format the total in euros

 src/app.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit
$ git bisect reset
```

Три запуска теста среди коммитов между `aba6e65` и HEAD нашли `38b0e01` — коммит, после которого `total` стала возвращать строку. Бисекция работает и через слияния, но точнее всего она, когда каждый коммит сам по себе собирается и проходит свои тесты, — ещё один довод в пользу маленьких самодостаточных коммитов.

## Удалённые репозитории: fetch и push перемещают объекты \{#remotes-fetch-and-push-move-objects\}

**Удалённый репозиторий** (remote) — другой репозиторий, которому локально дано имя вместе с URL, например `origin`. Его ветки отражаются **ссылками отслеживания** (remote-tracking refs) `refs/remotes/origin/main`, которые меняются только при обмене с удалённым репозиторием. Сам обмен — это передача объектов:

- **push** спрашивает удалённый репозиторий, какие у него есть ссылки, вычисляет, каких объектов там не хватает (всё, что достижимо из ваших коммитов и не достижимо из его), отправляет их одним сжатым **pack-файлом** (packfile) и просит удалённый репозиторий передвинуть его ветку. Удалённый репозиторий принимает только **перемотку вперёд** (fast-forward) — перемещение от его текущего коммита к его потомку, — если отправка не принудительная.
- **fetch** делает то же в обратном направлении и обновляет ссылки отслеживания. Он никогда не трогает ваши ветки; это делают затем `merge` или `rebase`. `pull` — это fetch, за которым следует одна из них.

Репозиторий примера отправляется в голый репозиторий (bare repository — репозиторий без рабочего каталога, как на сервере), второй клон добавляет коммит, а первый забирает его. Строки о ходе выполнения сокращены до их итогового состояния:

```console
$ git init -q --bare -b main ../origin.git
$ git remote add origin ../origin.git
$ git push --progress -u origin main
Enumerating objects: 42, done.
Counting objects: 100% (42/42), done.
Delta compression using up to 8 threads
Compressing objects: 100% (30/30), done.
Writing objects: 100% (42/42), 3.46 KiB | 3.46 MiB/s, done.
Total 42 (delta 8), reused 0 (delta 0), pack-reused 0 (from 0)
To ../origin.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git -C ../origin.git count-objects
42 objects, 168 kilobytes
$ git clone -q ../origin.git ../alice
$ cd ../alice && echo '- run tests with pytest' >> README.md && git commit -q -am 'Document the tests' && git push -q && cd ../shop
$ git fetch --progress origin
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (2/2), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
From ../origin
   2c22ec0..d6cd86a  main       -> origin/main
$ git status -sb | head -n 1
## main...origin/main [behind 1]
$ git merge --ff-only origin/main
Updating 2c22ec0..d6cd86a
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

Push отправил 42 объекта, достижимых из `main` (ветка `discount-rebased` не отправлялась, так что два её коммита остались на месте), в пакете размером 3.46 КиБ, 8 из них — как дельты относительно похожих объектов. Принимающая сторона распаковала их в 42 отдельных файла, поскольку Git хранит небольшие отправки, по умолчанию меньше 100 объектов, в виде неупакованных объектов. Fetch принёс ровно 3 объекта: новый коммит, его корневое дерево и новый blob-объект README; дерево `src` и всё остальное уже были на месте и опознаны по имени. Тогда локальная `main` отставала от `origin/main` на один коммит, и `--ff-only` передвинул её вперёд, не создавая коммита слияния. Если бы коммитили обе стороны, push был бы отвергнут как не являющийся перемоткой вперёд, и исправлять это нужно через fetch и слияние или перебазирование, а не принудительной отправкой. Когда принудительная отправка действительно нужна — после перебазирования собственной ветки, — `git push --force-with-lease` отказывается затирать удалённую ветку, которая сдвинулась с момента последнего fetch.

## Схемы ветвления \{#branching-workflows\}

Git допускает любую структуру ветвления; команды выбирают одну. Распространены три ([Driessen, 2010](#references); [Chacon, 2011](#references); [Hammant, trunkbaseddevelopment.com](#references)):

- **Магистральная разработка** (trunk-based development). Все вливают изменения в одну ветку, магистраль (trunk, `main`), не реже раза в день — напрямую или через ветки, которые живут часы. Незаконченные функции вливаются скрытыми за **флагами функциональности** (feature flags) — переключателями в конфигурации, — а не держатся на долгих ветках. Релизы делаются из магистрали.
- **GitHub flow.** Короткоживущая ветка на каждое изменение, запрос на слияние для ревью и CI, слияние в `main`, и `main` всегда готова к развёртыванию и развёрнута. Если ветки держать короткими, это магистральная разработка с обязательным ревью.
- **Git flow.** Долгоживущие ветки `develop` и `master`, ветки функций от `develop`, ветки релизов для стабилизации и ветки срочных исправлений от `master`. Подходит для программ, которые выпускаются версиями, поддерживаемыми параллельно, например устанавливаемого продукта или библиотеки. В 2020 году автор добавил примечание, что командам, которые непрерывно поставляют веб-приложение, стоит выбрать схему попроще.

| | Магистральная разработка | GitHub flow | Git flow |
| --- | --- | --- | --- |
| Долгоживущие ветки | только `main` | только `main` | `master` и `develop` |
| Время жизни ветки | часы | от часов до дней | от дней до недель |
| Интеграция | непрерывная | при каждом слиянии | во время релиза |
| Незаконченная работа | за флагами функциональности | в своей ветке | в своей ветке |
| Подходит для | непрерывной доставки | непрерывной доставки с ревью | версионных релизов, поддерживаемых параллельно |
| Главный риск | флаги, забытые в коде | ветки, которые стареют | большие слияния, долгое время выполнения изменений |

Исследования DORA связывают первый стиль с производительностью поставки. Команды, у которых было не больше трёх активных веток, которые вливали их в магистраль не реже раза в день и у которых не было заморозок кода и фаз интеграции, показывали более высокую производительность поставки в опросах 2016 и 2017 годов ([Forsgren, Humble and Kim, 2018](#references); [DORA, trunk-based development](#references)). Это рассуждение о размере пакета из [первой заметки](/ru/notes/devops/what-devops-is#why-small-batches-lower-risk), применённое к интеграции: ветка, которая живёт день, мало с чем конфликтует, а ветка, которая живёт месяц, вливает сразу месяц чужих изменений.

## Ревью кода и защищённые ветки \{#code-review-and-protected-branches\}

Большинство команд требуют, чтобы изменение прочитал кто-то кроме автора, прежде чем оно попадёт в `main`; обычно это **запрос на слияние** (pull request, в GitLab — merge request): предложение слить ветку вместе с её diff, обсуждением и результатами CI. Ревью ловит дефекты, но в исследованиях ревью в Microsoft и Google его бо́льшими эффектами оказались распространение знаний о коде и поддержание его единообразия ([Bacchelli and Bird, 2013](#references); [Sadowski et al., 2018](#references)). Качество ревью падает с размером изменения — ещё одна причина держать пакеты маленькими.

Правила обеспечивает хостинг, а не Git: **защищённая ветка** (protected branch) или, в более новой форме GitHub, **набор правил** (ruleset) отвергает отправки, которые их нарушают. Типичные правила: никаких прямых отправок, только слитые запросы на слияние; хотя бы одно одобрение от владельцев затронутых файлов, перечисленных в файле `CODEOWNERS`; проверки CI, которые должны пройти на ветке, приведённой в актуальное состояние; линейная история; никаких принудительных отправок и никакого удаления. **Очередь слияния** (merge queue) идёт на шаг дальше: она тестирует каждый запрос на слияние вместе с запросами, стоящими перед ним, чтобы два изменения, которые проходят по отдельности, не могли сломать `main` вместе. Раздел «Пример» построчно разбирает один набор правил.

## Большие файлы и монорепозитории, кратко \{#large-files-and-monorepos-briefly\}

Git хранит каждую версию каждого файла, и каждый клон получает их все. Для исходного кода это дёшево, потому что текст хорошо сжимается и хорошо хранится дельтами. Для больших двоичных файлов — наборов данных, весов моделей, видео и результатов сборки — каждая версия файла размером 2 ГБ навсегда остаётся в каждом клоне. С этим справляются три инструмента:

- **Git LFS** (Large File Storage) коммитит вместо файла небольшой текстовый указатель — три строки с версией спецификации, SHA-256 содержимого и его размером, — а само содержимое хранит на отдельном сервере и скачивает только для извлечённой версии.
- **Частичный клон** (partial clone), `git clone --filter=blob:none`, забирает коммиты и деревья, но не blob-объекты, и забирает каждый blob-объект, когда он впервые нужен какой-нибудь команде. **Неглубокий клон** (shallow clone), `--depth 1`, забирает только последний коммит, и этого достаточно для многих заданий CI.
- **Разреженное извлечение** (sparse checkout) записывает в рабочий каталог только некоторые каталоги дерева.

**Монорепозиторий** (monorepo) хранит много проектов в одном репозитории. Тогда изменение, затрагивающее библиотеку и всех её пользователей, — один атомарный коммит, который проходит ревью и тестирование целиком, и у всего есть ровно одна версия. Цена — масштаб (монорепозиторий Google работает на собственной системе Piper, а не на Git), необходимость в системе сборки, которая пересобирает и тестирует только то, что затрагивает изменение, о чём говорит [заметка о сборке](/ru/notes/devops/builds-and-dependencies), и правила владения для многих команд в одном дереве. Собственная команда Git `scalar` настраивает для больших репозиториев частичный клон, разреженное извлечение и фоновое обслуживание. Альтернатива — по репозиторию на проект — даёт каждой команде самостоятельность и расплачивается за неё согласованием версий между репозиториями.

| --- | --- | --- | --- |
| Единица истории | скопированный файл или папка | пронумерованная ревизия на сервере | коммит: полный снимок, названный по своему хешу |
| Работа без сети | да, без истории | нет | да, со всей историей |
| Ветка | скопированная папка | копия на сервере | файл в 41 байт с хешем |
| Целостность | никакой | та, что обеспечивает сервер | каждый хеш покрывает всю историю под ним |
| Объединение параллельной работы | вручную | слияние на сервере | трёхстороннее слияние или перебазирование, локально |
| Обмен работой | копирование файлов | коммит на сервер | fetch и push недостающих объектов |

## Ограничения \{#limitations\}

- **Интерфейс скрывает модель.** Одна и та же команда делает несвязанные вещи (`checkout` переключает ветки и восстанавливает файлы, поэтому в 2.23 добавили `switch` и `restore`), а разрушительные команды, такие как `reset --hard` и `push --force`, ни о чём не предупреждают.
- **Слияния текстовые.** Два изменения в разных местах могут слиться чисто и всё же быть неверными вместе: одно переименовывает функцию, которую вызывает другое. Поймать это может только сборка и тестирование результата слияния, как это делает CI.
- **История вечна.** Секрет, однажды закоммиченный, есть в каждом клоне и в каждом форке, и чтобы его убрать, нужно переписать историю и всё равно сменить секрет. Большие двоичные файлы, однажды закоммиченные, отягощают каждый клон.
- **SHA-1 по-прежнему умолчание** в октябре 2026 года; обнаружение коллизий защищает от известных атак, а переход на SHA-256 ждёт экосистему.
- **Git записывает содержимое, а не намерение.** Переименование распознаётся задним числом по сходству содержимого, а сообщение коммита полезно ровно настолько, насколько его сделал полезным автор.

## Что нужно запомнить \{#what-you-should-remember\}

- Git хранит blob-объекты (содержимое файлов), деревья (каталоги) и коммиты (дерево, родители, автор, сообщение), каждый назван по хешу от `type size\0content`. Коммит — снимок; одинаковое содержимое хранится один раз; хеш коммита покрывает всю историю за ним.
- Ветка — файл с хешем коммита, HEAD называет текущую ветку, а индекс — следующее дерево. Коммит записывает объекты и передвигает ветку.
- Git 2.42 вывел SHA-256-репозитории из экспериментального статуса; SHA-1 с обнаружением коллизий по-прежнему умолчание, а Git 3.0 планирует сменить умолчание для новых репозиториев, без даты на октябрь 2026 года.
- Коммиты образуют DAG. Трёхстороннее слияние решает судьбу каждого участка по базе слияния и записывает коммит с двумя родителями; конфликт — это два разных изменения одного участка. Перебазирование воспроизводит коммиты как новые коммиты с новыми хешами: никогда не перебазируйте то, что есть у других.
- `reset` передвигает ветку, `revert` добавляет обратный коммит, reflog помнит, где были ветки, а `bisect` находит первый плохой коммит примерно за $\log_2 n$ проверок.
- Push и fetch отправляют объекты, которых не хватает другой стороне, и передвигают ссылки; push должен быть перемоткой вперёд, если он не принудительный.
- Магистральная разработка с ветками, которые вливаются в течение дня, в данных DORA сопутствует более высокой производительности поставки; защищённые ветки и ревью обеспечивают соблюдение правил на сервере.

## Пример \{#example\}

Набор правил GitHub для ветки по умолчанию в JSON-форме, которую принимает REST-эндпоинт `POST /repos/{owner}/{repo}/rulesets`; в той же форме наборы правил экспортируются и импортируются в настройках репозитория. Он написан по документации REST по состоянию на октябрь 2026 года и проверен на корректность JSON, но к репозиторию не применялся.

```json
{
  "name": "protect main",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "bypass_actors": [],
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 1,
        "require_code_owner_review": true,
        "dismiss_stale_reviews_on_push": true,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true,
        "allowed_merge_methods": ["squash", "rebase"]
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [{ "context": "test" }, { "context": "lint" }]
      }
    }
  ]
}
```

Построчно:

- `target: "branch"` и `conditions.ref_name.include: ["~DEFAULT_BRANCH"]` применяют правила к ветке по умолчанию, как бы она ни называлась; шаблоны вроде `"refs/heads/release/*"` добавили бы другие ветки. `enforcement: "active"` включает правила (`"disabled"` сохраняет набор правил, но без действия).
- `bypass_actors: []`: никто, включая администраторов, не может обходить правила. Аварийный путь, например команда, которой разрешён обход, — осознанное решение, записываемое здесь, а не привычка.
- `deletion` запрещает удалять ветку, а `non_fast_forward` запрещает принудительные отправки: история `main` может только расти, поэтому каждый коммит, который когда-либо был в ней, а значит, и каждый когда-либо развёрнутый коммит, остаётся достижимым. Ошибки в `main` отменяются через `revert`.
- `required_linear_history` отвергает коммиты слияния в `main`, так что запросы на слияние попадают туда сплющенными или перебазированными коммитами; `allowed_merge_methods` предлагает ровно эти две кнопки.
- `pull_request` требует запроса на слияние с ревью для каждого изменения. Нужно одно одобрение, и оно должно прийти от владельца кода затронутых файлов (`require_code_owner_review`), указанного в файле `CODEOWNERS`. `dismiss_stale_reviews_on_push` отзывает одобрения, когда приходят новые коммиты, а `require_last_push_approval` требует, чтобы последнюю отправку одобрил кто-то кроме её автора, так что никто не может отправить непроверенный код после одобрения. Открытые обсуждения в ревью должны быть сначала закрыты.
- `required_status_checks` требует, чтобы прошли задания CI с именами `test` и `lint`. `strict_required_status_checks_policy: true` требует перед слиянием привести ветку в актуальное состояние относительно `main`, чтобы проверки выполнялись на том коде, который действительно попадёт в ветку; в загруженном репозитории это вынуждает часто перебазировать, что очередь слияния делает автоматически.

Соответствующий файл `CODEOWNERS` в `.github/CODEOWNERS` с вымышленными названиями команд:

```text
# Каждая строка: шаблон пути и владельцы, которые должны проверять его изменения. Действует последнее совпадение.
*                 @example-org/shop-team
/deploy/          @example-org/platform
/src/payments/    @example-org/payments @example-org/security
```

Теперь коммит — точный именованный снимок исходного кода. Но исходные файлы — не то, что выполняет машина: между ними и работающим сервисом лежат компиляция, упаковка и получение чужого кода, и каждый из этих шагов должен давать один и тот же результат при каждом запуске.
