[Предыдущая заметка](/ru/notes/devops/what-devops-is) описала поставку как поток шагов от коммита до продакшена и показала, что шаги должны быть настолько дешёвыми, чтобы их можно было выполнять для каждого изменения. Шаг становится дешёвым, когда его может выполнить машина, а почти каждый шаг — сборка, тестирование, упаковка, копирование, перезапуск — в конечном счёте последовательность команд. Язык, на котором эти команды набирают, комбинируют и сохраняют в скрипты, — командная оболочка (shell). Эта заметка объясняет, что оболочка делает со строкой текста, почему правила, по которым она разбивает строку на слова, вызывают большинство ошибок в скриптах, как конвейеры соединяют программы через файловые дескрипторы, как скрипт обнаруживает сбой и где оболочка перестаёт быть подходящим инструментом.

**Условия.** `/bin/bash` 3.2.57 на macOS 26 с BSD-версиями `grep`, `sed`, `awk`, `sort`, `xargs` и `find`, которые поставляются с macOS, и `jq` 1.7.1. Дистрибутивы Linux поставляют bash 5 и инструменты GNU; каждая команда этой заметки даёт там тот же результат, если в тексте не сказано иное. Команды каждого листинга подавались одному процессу bash, поэтому сообщение об ошибке называет строку этого сеанса (`bash: line 8:`), а интерактивная оболочка напечатала бы только `bash:`.

## Отправная точка: команды, набранные вручную \{#baseline-commands-typed-by-hand\}

Простейшая автоматизация — её отсутствие: инженер заходит на сервер и набирает команды со страницы вики. Один раз это работает. Как шаг поставки это не работает по причинам из предыдущей заметки: процедура живёт в чьей-то голове и на странице, которая расходится с действительностью, опечатка в пятой команде остаётся незамеченной до десятой, и никто не может выполнять это пятьдесят раз в день.

Если сохранить те же команды в файл, само по себе это ничего не исправит. Вот скрипт очистки из трёх строк, запущенный там, где каталога сборки нет, а переменная `BUILD_DIR` пуста (`rm` не выполняется, а печатается через `echo`):

```bash
#!/usr/bin/env bash
cd /nonexistent/build
echo "still running, in ${PWD##*/}"
echo rm -rf "$BUILD_DIR/tmp"
```

```console
$ BUILD_DIR= bash nosafety.sh
nosafety.sh: line 2: cd: /nonexistent/build: No such file or directory
still running, in project
rm -rf /tmp
```

Команда `cd` не выполнилась, и скрипт продолжил работу не в том каталоге. Пустая переменная превратила `$BUILD_DIR/tmp` в `/tmp`. Без `echo` скрипт попытался бы удалить `/tmp`. Обе ошибки по умолчанию проходят молча, и остальная часть заметки — о правилах, которые к ним приводят, и привычках, которые их предотвращают.

## Что такое командная оболочка \{#what-the-shell-is\}

Командная оболочка — цикл «прочитать — вычислить — напечатать», значения которого — процессы. Она читает строку, разбивает её на слова, выполняет подстановки и считает первое слово командой. Если команда **встроенная** (builtin), оболочка выполняет её сама; иначе она ищет программу с таким именем в каталогах из `PATH`, создаёт дочерний процесс через `fork`, заменяет программу потомка через `exec` и ждёт завершения потомка, как в [заметке о процессах](/ru/notes/acos/processes-and-threads#creating-a-process-fork-exec-and-wait). Статус завершения (exit status) потомка сохраняется в `$?`, и цикл читает следующую строку.

```console
$ type cd ls printf awk
cd is a shell builtin
ls is /bin/ls
printf is a shell builtin
awk is /usr/bin/awk
```

`cd` обязана быть встроенной: текущий каталог — свойство процесса, и потомок, который сменил бы свой каталог и завершился, оставил бы оболочку там, где она была. То же верно для присваивания переменных, `export`, `set` и `source`. Всё остальное — обычные программы, и работа оболочки — запустить их с правильными аргументами, правильным окружением и правильными открытыми файлами.

<aside class="callout"><strong>Ключевая идея.</strong> Программа на языке оболочки — это программа, операторы которой — процессы, значения — потоки байтов и небольшие целые статусы завершения, а синтаксис определяется тем, как строка разбивается на слова. Заключайте в кавычки каждую подстановку, чтобы слова оставались целыми, соединяйте программы через файловые дескрипторы и проверяйте каждый статус завершения, иначе ошибки молча перейдут в следующую команду.</aside>

## Слова, кавычки и подстановки \{#words-quoting-and-expansion\}

Прежде чем что-либо запускать, bash превращает строку в список слов фиксированной последовательностью шагов ([Bash manual, §3.5](#references)):

1. **Раскрытие фигурных скобок** (brace expansion): `file{1..3}.log` превращается в три слова.
2. **Раскрытие тильды** (`~` становится домашним каталогом), **подстановка параметров и переменных** (parameter expansion: `$x`, `${x:-default}`), **арифметическая подстановка** (`$((n + 1))`) и **подстановка команд** (command substitution: `$(cmd)`) — всё за один проход слева направо.
3. **Разбиение на слова** (word splitting): результаты шага 2, которые *не* стояли внутри двойных кавычек, разбиваются по символам из `IFS`, по умолчанию пробелу, табуляции и переводу строки.
4. **Подстановка имён файлов** (pathname expansion): слово без кавычек, содержащее `*`, `?` или `[`, заменяется подходящими именами файлов.
5. **Удаление кавычек** (quote removal): сами символы кавычек исчезают.

Одинарные кавычки запрещают все подстановки. Двойные кавычки разрешают шаг 2, кроме тильды, но запрещают шаги 3 и 4, так что значение переменной остаётся одним словом, что бы оно ни содержало. Большинство ошибок в скриптах — это шаги 3 и 4, применённые к значению, которое должно было остаться целым. Команда `printf '<%s>\n'` печатает каждый свой аргумент на отдельной строке в угловых скобках, и слова становятся видны. В каталоге, где лежат `my report.txt` и `notes.txt`:

```console
$ f='my report.txt'
$ printf '<%s>\n' $f
<my>
<report.txt>
$ printf '<%s>\n' "$f"
<my report.txt>
$ ls -l $f
ls: my: No such file or directory
ls: report.txt: No such file or directory
$ x='*.txt'
$ printf '<%s>\n' $x
<my report.txt>
<notes.txt>
$ printf '<%s>\n' "$x"
<*.txt>
```

Без кавычек значение `my report.txt` разбилось на два слова, и `ls` искал два файла. Без кавычек значение `*.txt` раскрылось как шаблон после подстановки переменной. В кавычках каждое осталось одним словом. Порядок шагов объясняет и большее:

```console
$ printf '<%s>\n' '$HOME' "$HOME" ~ "~"
<$HOME>
</Users/ada>
</Users/ada>
<~>
$ n=3; printf '<%s>\n' {1..$n}
<{1..3}>
$ printf '<%s>\n' "$(echo 'a  b')" $(echo 'a  b')
<a  b>
<a>
<b>
$ empty=''; [ $empty = yes ] && echo yes
bash: line 24: [: =: unary operator expected
$ [ "$empty" = yes ] || echo 'not yes'
not yes
$ [[ $empty = yes ]] || echo 'not yes, [[ ]] does not split'
not yes, [[ ]] does not split
```

`{1..$n}` остаётся как есть, потому что раскрытие фигурных скобок, шаг 1, выполняется до того, как на шаге 2 подставляется `$n`: на шаге 1 текст `{1..$n}` — не допустимый диапазон, и его оставляют в покое, а шаг 2 лишь подставляет 3. Подстановка команды в кавычках сохраняет оба пробела, без кавычек — разбивается. `[` — команда (встроенная, а также программа `/bin/[`), которая получает слова, как любая другая: при `$empty` без кавычек она получила `=`, `yes` и `]` — на одно слово меньше, чем нужно для сравнения, — и завершилась ошибкой. `[[ … ]]` — часть грамматики bash, а не команда, и слова внутри неё не разбиваются и не раскрываются как шаблоны.

Привычек отсюда следует немного. Ставьте двойные кавычки вокруг каждой `$variable` и `$(command)`, если только разбиение не нужно намеренно. Храните список имён файлов в массиве, `files=(*.log)`, и передавайте его как `"${files[@]}"`: это раскрывается в одно слово на элемент. Используйте `[[ … ]]` в скриптах на bash. Статический анализатор ShellCheck сообщает о подстановках без кавычек как о SC2086 ([ShellCheck wiki](#references)).

## Конвейеры и перенаправление \{#pipes-and-redirection\}

Каждый процесс начинает работу с тремя открытыми файловыми дескрипторами — небольшими целыми числами, индексами в его таблице открытых файлов ([заметка о файлах](/ru/notes/acos/files-and-io#what-a-program-sees-descriptors-and-five-calls)): 0 — стандартный ввод, 1 — стандартный вывод, 2 — стандартный поток ошибок. Программа, которая читает из 0 и пишет в 1, не знает и не интересуется, терминал это, файл или другая программа. Это решает оболочка до вызова `exec`, в потомке.

- `cmd > file` открывает `file` на запись (создавая или обрезая его) и делает его дескриптором 1 команды `cmd`; `>>` дописывает в конец; `< file` делает `file` дескриптором 0.
- `2> file` делает то же для дескриптора 2, а `2>&1` делает дескриптор 2 копией того, чем дескриптор 1 является *в этот момент*, системным вызовом `dup2(1, 2)`.
- `a | b` создаёт **канал** (pipe) — буфер в ядре с концом для записи и концом для чтения ([каналы](/ru/notes/acos/inter-process-communication#pipes)), — делает конец для записи дескриптором 1 процесса `a`, конец для чтения — дескриптором 0 процесса `b` и запускает оба процесса одновременно.

Перенаправления применяются слева направо, поэтому их порядок важен:

```console
$ ls /etc/hosts /nonexistent > out.txt; cat out.txt
ls: /nonexistent: No such file or directory
/etc/hosts
$ ls /etc/hosts /nonexistent > all.txt 2>&1; wc -l < all.txt
       2
$ ls /etc/hosts /nonexistent 2>&1 > all.txt; wc -l < all.txt
ls: /nonexistent: No such file or directory
       1
$ ls /etc/hosts /nonexistent 2> /dev/null | wc -l
       1
```

В первой команде в файл ушёл только дескриптор 1, поэтому ошибка всё равно попала в терминал. Во второй сначала стояло `> all.txt`, а затем `2>&1` скопировало дескриптор 1, то есть файл, в 2: обе строки ушли в файл. В третьей `2>&1` скопировало дескриптор 1, пока тот ещё был терминалом, и только потом 1 был направлен в файл, поэтому ошибка ушла в терминал, а файл получил одну строку. В четвёртой ошибки были отброшены, и в канал попало только имя файла. Стоит знать ещё две формы: here-строка (here-string) `<<< text` подаёт строку в дескриптор 0, а подстановка процессов (process substitution) bash `<(cmd)` запускает `cmd`, соединив его вывод с каналом, и передаёт имя канала, например `/dev/fd/63`, как аргумент-файл:

```console
$ sort <<< $'pear\napple\nfig'
apple
fig
pear
$ diff <(printf 'a\nb\n') <(printf 'a\nc\n')
2c2
< b
---
> c
```

1. В строке `awk '$9 >= 500 {print $7}' < access.log | sort | uniq -c > report.txt` bash находит три команды и два символа канала. Он создаёт два канала и порождает три дочерних процесса.
2. В первом потомке `< access.log` открывает файл журнала как дескриптор 0; затем потомок выполняет `exec` программы `awk`.
3. Конец первого канала для записи становится дескриптором 1 процесса `awk`, а конец для чтения — дескриптором 0 процесса `sort`.
4. Второй канал соединяет дескриптор 1 процесса `sort` с дескриптором 0 процесса `uniq`.
5. `> report.txt` открывает выходной файл как дескриптор 1 процесса `uniq`.
6. Дескриптор 2 никто не перенаправлял, поэтому сообщения об ошибках всех трёх процессов идут прямо в терминал, а не в каналы и не в отчёт.
7. Оболочка ждёт все три процесса; статус конвейера — статус `uniq`, его последней команды.

Три программы работают одновременно. `awk` пишет в первый канал по мере чтения, и когда буфер канала заполнен (в Linux по умолчанию 64 КиБ), ядро блокирует его, пока `sort` не прочитает данные. `sort` не может ничего вывести, пока не прочитает весь свой ввод, а `uniq` затем считает соседние одинаковые строки. Настоящий запуск на журнале из следующего раздела:

```console
$ awk '$9 >= 500 {print $7}' < access.log | sort | uniq -c > report.txt; cat report.txt
   4 /api/orders
   5 /api/search?q=desk
   9 /api/search?q=lamp
   5 /api/search?q=mug
   6 /api/search?q=shoes
```

## Коды завершения и строгий режим \{#exit-codes-and-strict-mode\}

Программа заканчивается **статусом завершения** — целым числом от 0 до 255. Ноль означает успех, всё остальное — неудачу, и что означает каждое значение, решает программа. Несколько соглашений общие ([Bash manual, §3.7.5](#references)): 126 означает, что файл найден, но не может быть выполнен, 127 — что команда не найдена, а $128 + n$ — что процесс убит сигналом $n$. `grep` использует три значения: 0, если строка нашлась, 1, если не нашлось ни одной, и 2 при ошибке.

```console
$ grep -q ' 502 ' ../demo/logs/access.log; echo $?
0
$ grep -q ' 503 ' ../demo/logs/access.log; echo $?
1
$ grep -q ' 503 ' /no/such/file; echo $?
grep: /no/such/file: No such file or directory
2
$ nosuchcommand; echo $?
bash: line 8: nosuchcommand: command not found
127
$ false && echo 'not printed'; echo "status $?"
status 1
```

Управление выполнением в оболочке строится на статусах завершения. `a && b` выполняет `b`, только если `a` завершилась успешно, `a || b` — только если неудачно, а `if cmd; then` проверяет статус `cmd`, а не булево значение. В `false && echo` команда `echo` была пропущена, и список сохранил статус 1 от `false`.

Однако по умолчанию скрипт игнорирует неудачи: команда завершается ошибкой, печатает сообщение, и выполняется следующая строка, как в отправной точке. Это меняют три опции `set`, которые обычно пишут вместе как `set -euo pipefail` в начале скрипта:

- **`-e` (errexit)**: завершиться, как только команда завершилась неудачно. Защищает от продолжения после неудавшихся `cd`, `cp` или загрузки.
- **`-u` (nounset)**: считать ошибкой подстановку неустановленной переменной. Защищает от того, что `$BUILD_DIR/tmp` молча превратится в `/tmp`.
- **`-o pipefail`**: делать статусом конвейера статус последней команды, завершившейся неудачно, а не статус последней команды. Без этой опции `curl … | tar x` успешен всякий раз, когда успешен `tar`, даже если загрузка не удалась.

```console
$ bash safety.sh; echo "exit $?"
safety.sh: line 3: RELEASE: unbound variable
exit 1
$ bash pipefail.sh
without pipefail: 0
with pipefail: 1
yes | head: 141  PIPESTATUS: 141 0
```

`safety.sh` — это `set -euo pipefail`, за которым идёт `echo "deploying ${RELEASE}"`: скрипт остановился, вместо того чтобы развёртывать релиз с пустым именем. `pipefail.sh` дважды выполняет `false | true`, без опции и с ней. Его последняя строка показывает цену опции — **ловушку pipefail** (pipefail trap). `head -n 1` завершается после одной строки; следующая запись `yes` в канал, у которого теперь нет читателя, заставляет ядро послать `yes` сигнал `SIGPIPE` с номером 13, и `yes` умирает со статусом $128 + 13 = 141$ ([сигналы](/ru/notes/acos/inter-process-communication#signals)). `PIPESTATUS` хранит статус каждой команды последнего конвейера. Конвейер сделал ровно то, что от него хотели, но при `pipefail` он считается неудачным, а при `-e` завершает скрипт. То же происходит, когда конвейер законно ничего не находит:

```bash
#!/usr/bin/env bash
# trap.sh
set -euo pipefail
count=$(grep ' 503 ' ../demo/logs/access.log | wc -l)
echo "503 responses: $count"
```

```bash
#!/usr/bin/env bash
# sigpipe.sh
set -euo pipefail
first=$(seq 1 100000 | head -n 1)
echo "first: $first"
```

```console
$ bash trap.sh; echo "exit $?"
exit 1
$ bash sigpipe.sh; echo "exit $?"
exit 141
```

Оба скрипта умерли, не сказав ни слова. В `trap.sh` ни одна строка не содержит ` 503 `, `grep` завершился с 1, и `pipefail` превратил «ноль совпадений» в неудачу. В `sigpipe.sh` команда `seq` записала больше, чем вмещает канал, `head` ушёл после первой строки, и `seq` был убит сигналом `SIGPIPE`: пять запусков из пяти дали 141. Исправления локальны: явно указать, где «нет совпадений» допустимо, и использовать читателя, который потребляет весь свой ввод. `grep -c` печатает 0, но всё равно завершается с 1, если совпадений нет, поэтому ему нужен явный `|| true`; `awk 'NR == 1'` печатает первую строку и продолжает читать, так что пишущий процесс никогда не встречает закрытый канал:

```bash
#!/usr/bin/env bash
set -euo pipefail
count=$(grep -c ' 503 ' ../demo/logs/access.log || true)
first=$(seq 1 100000 | awk 'NR == 1')
echo "503 responses: $count, first: $first"
```

```console
$ bash fixed.sh; echo "exit $?"
503 responses: 0, first: 1
exit 0
```

У `-e` есть и собственные дыры. Опция игнорируется для команды, статус которой проверяется: в условии `if` или `while`, слева от `&&` или `||` и после `!`. Правило распространяется на всё, что выполняется внутри такой команды, включая целые функции. А `local x=$(cmd)` возвращает статус `local`, которая завершилась успешно, а не статус `cmd`:

```bash
#!/usr/bin/env bash
# efunc.sh
set -e
check() { false; echo "check went on after false"; }
if check; then echo "check succeeded"; fi
check
echo "never printed"
```

```bash
#!/usr/bin/env bash
# local.sh
set -e
f() { local out=$(false); echo "local hid the failure: $?"; }
f
g() { local out; out=$(false); echo "not reached"; }
g
echo "never printed"
```

```console
$ bash efunc.sh; echo "exit $?"
check went on after false
check succeeded
exit 1
$ bash local.sh; echo "exit $?"
local hid the failure: 0
exit 1
```

Внутри `if check` команда `false` в функции её не остановила, и `check` «завершилась успешно», потому что успешно завершилась её последняя команда, `echo`. Вызванная отдельной строкой, та же функция остановила скрипт на `false`. В `local.sh` функция `f` продолжила работу, потому что `local` скрыла статус `$(false)`; `g` сначала объявляет переменную, а присваивает отдельно, и неудача останавливает скрипт. Строгий режим (strict mode) — страховочная сетка с известными дырами, а не доказательство того, что скрипт проверяет каждую ошибку ([Wooledge, BashFAQ 105](#references)).

## Набор текстовых инструментов \{#a-toolkit-of-text-tools\}

У программ Unix один общий формат данных — строки текста, и большинство полезных программ делают с потоком строк что-то одно. Небольшой набор покрывает бо́льшую часть работы эксплуатации:

| Инструмент | Что делает | Типичное применение |
| --- | --- | --- |
| `grep` | печатает строки, подходящие под регулярное выражение | найти ошибки, сосчитать совпадения с `-c`, проверить с `-q` |
| `sed` | редактирует каждую строку по скрипту, чаще всего `s/old/new/` | нормализовать, переписать, удалить строки |
| `awk` | разбивает каждую строку на поля `$1 … $NF` и выполняет небольшую программу | фильтровать по полю, суммировать, группировать с помощью массивов |
| `cut`, `tr` | выбирают поля по разделителю; заменяют или удаляют символы | взять первый столбец, убрать кавычки |
| `sort`, `uniq` | упорядочивают строки; схлопывают соседние повторы, `-c` их считает | таблица частот `sort \| uniq -c \| sort -rn` |
| `head`, `tail`, `wc` | первые или последние строки; считают строки, слова, байты | заглянуть в начало, следить за журналом через `tail -f` |
| `find` | обходит каталоги и печатает пути, прошедшие проверки | файлы по имени, возрасту, размеру |
| `xargs` | превращает строки ввода в аргументы команды | выполнить команду для каждого файла, найденного `find` |
| `jq` | те же идеи для значений JSON | фильтровать структурированные журналы и ответы API |

Инструменты соединяются через каналы, и в этом их смысл ([McIlroy, Pinson and Tague, 1978](#references)). Пользоваться ими нужно так: строить конвейер по одной стадии, глядя на вывод после каждой.

**Разобранный пример.** У веб-сервиса за nginx 22 октября 2026 года с 14:00 до 15:00 выдался плохой час, и всё, что у нас есть, — его журнал доступа. (Журнал синтетический, сгенерирован с фиксированным начальным значением генератора в формате combined из nginx, с добавленным в конец временем обработки запроса в секундах.) Вопрос: что отказало, когда и у кого?

```console
$ wc -l logs/access.log
    1200 logs/access.log
$ head -n 2 logs/access.log
203.0.113.7 - - [22/Oct/2026:14:00:01 +0000] "GET /api/orders/1666 HTTP/1.1" 200 1079 "-" "curl/8.7.1" 0.015
203.0.113.61 - - [22/Oct/2026:14:00:02 +0000] "GET /api/orders/1564 HTTP/1.1" 200 1114 "-" "python-httpx/0.28.1" 0.026
```

При разбиении по пробелам поле 1 — адрес клиента, `$4` — время, `$6` — метод с открывающей кавычкой, `$7` — путь, `$9` — статус, а `$NF` (последнее поле) — время обработки запроса. У ошибок сервера статусы от 500 до 599. `grep` может сосчитать их шаблоном, привязанным к закрывающей кавычке запроса, но `awk` сравнивает само поле, которое не может случайно совпасть с цифрой 5 в каком-нибудь другом столбце:

```console
$ grep -c '" 5[0-9][0-9] ' logs/access.log
29
$ awk '$9 >= 500' logs/access.log | wc -l
      29
```

Какие эндпоинты? Напечатаем метод и путь, уберём кавычку через `tr`, затем с помощью `sed` отбросим строку запроса и заменим числовые идентификаторы на `:id`, чтобы `/api/orders/1842` и `/api/orders/1666` считались одним эндпоинтом. Затем идиома частот: `sort` собирает одинаковые строки вместе, `uniq -c` считает каждую серию, `sort -rn` ставит наибольшее число первым.

```console
$ awk '$9 >= 500 {print $6, $7}' logs/access.log | head -n 3
"POST /api/orders
"POST /api/orders
"GET /api/search?q=lamp
$ awk '$9 >= 500 {print $6, $7}' logs/access.log | tr -d '"' | sed -E 's/[?].*//; s#/[0-9]+#/:id#g' | sort | uniq -c | sort -rn
  25 GET /api/search
   4 POST /api/orders
```

Когда? Символы с 14-го по 17-й поля времени `[22/Oct/2026:14:23:05` — это `14:2`; если дописать `0`, получатся десятиминутные интервалы. И сколько длились неудачные запросы?

```console
$ awk '$9 >= 500 {print $9, substr($4, 14, 4) "0"}' logs/access.log | sort | uniq -c
   2 500 14:10
   1 500 14:20
   1 500 14:40
  15 502 14:20
  10 502 14:30
$ awk '$9 == 502 {print $NF}' logs/access.log | sort -n | sed -n '1p;$p'
5.000
5.010
```

Проблемы оказываются двумя разными. Ответы 502, «bad gateway», приходили только с 14:20 до 14:40, и каждый из них занял от 5.000 до 5.010 секунды (`sed -n '1p;$p'` печатает первую и последнюю строки отсортированного списка): такая однородность — признак таймаута, то есть прокси сдавался, прождав поисковый бэкенд 5 секунд. Четыре ответа 500 от `POST /api/orders` разбросаны по всему часу — это отдельная и меньшая проблема. Одни счётчики скрывают, насколько плохим было окно, поэтому следующая стадия — небольшая программа на `awk`, которая ведёт два массива, запросы и ошибки по интервалам, и печатает долю:

```console
$ awk '$7 ~ /^\/api\/search/ {b = substr($4, 14, 4) "0"; n[b]++; if ($9 >= 500) e[b]++} END {for (b in n) printf "%s %4d %4d %6.1f%%\n", b, n[b], e[b], 100 * e[b] / n[b]}' logs/access.log | sort
14:00   32    0    0.0%
14:10   34    0    0.0%
14:20   24   15   62.5%
14:30   34   10   29.4%
14:40   20    0    0.0%
14:50   32    0    0.0%
```

Эндпоинт поиска отказывал в 62.5% случаев с 14:20 до 14:30 и в 29.4% в следующие десять минут, а затем восстановился. У кого? `cut` берёт первое поле, разделённое пробелами:

```console
$ awk '$9 == 502' logs/access.log | cut -d ' ' -f 1 | sort | uniq -c | sort -rn | head -n 3
  10 198.51.100.3
   4 203.0.113.7
   4 203.0.113.12
$ cut -d ' ' -f 1 logs/access.log | sort | uniq -c | sort -rn | head -n 3
 247 203.0.113.7
 246 198.51.100.3
 199 203.0.113.12
```

Клиенты с наибольшим числом сбоев — это клиенты с наибольшим трафиком: сбои следуют за эндпоинтом и временем, а не за клиентом. Был ли это первый такой час? Старые журналы ротированы и сжаты. `find` перечисляет их, `-print0` и `xargs -0` передают имена, разделённые нулевыми байтами, чтобы уцелело имя с пробелом или переводом строки, а `gzip -dcf` распаковывает файлы `.gz` и пропускает обычные файлы без изменений:

```console
$ find logs -name 'access.log*' -mtime -2
logs/access.log.1.gz
logs/access.log
$ find logs -name 'access.log*' -print0 | xargs -0 gzip -dcf | awk '$9 >= 500 {print $9, substr($4, 1, 12)}' | tr -d '[' | sort | uniq -c
   7 500 20/Oct/2026
   3 500 21/Oct/2026
   4 500 22/Oct/2026
  25 502 22/Oct/2026
```

(`-mtime -2` выбирает файлы, изменённые меньше чем за двое суток до момента запуска команды, поэтому её вывод зависит от часов; остальное от них не зависит.) Ответы 500 эндпоинта заказов случаются каждый день; ответы 502 — новые. Собственный журнал приложения записан в JSON, по одному объекту на строку, и `jq` фильтрует его по полю, а не по позиции:

```console
$ jq -r 'select(.level == "error") | [.ts, .svc, .msg] | @tsv' logs/app.jsonl
2026-10-22T14:20:09Z	search	upstream timeout
2026-10-22T14:21:40Z	search	upstream timeout
2026-10-22T14:27:13Z	orders	db deadlock, retrying
$ jq -s 'map(select(.svc == "search" and .ms != null) | .ms) | max' logs/app.jsonl
5000
```

Каждая стадия проверялась до того, как добавлялась следующая, и каждый ответ занял одну строку. К такому стилю относятся два предостережения. `sort` упорядочивает строки по правилам текущей локали, поэтому скрипты, которые сравнивают отсортированный вывод, задают `LC_ALL=C` для побайтового порядка, а это ещё и быстрее. И позиции полей — хрупкий контракт: user agent с пробелом безвреден здесь только потому, что стоит после используемых нами полей, а смена формата журнала молча ломает каждый конвейер — это одна из причин, почему сервисы пишут журналы в JSON.

## Скрипты \{#scripts\}

Конвейеру, который будут запускать снова, место в файле. Скрипт — текстовый файл, первая строка которого, **шебанг** (shebang), называет его интерпретатор: когда выполняется файл, начинающийся с `#!`, вызов ядра `execve` запускает названный интерпретатор и передаёт ему путь к файлу как аргумент. `#!/usr/bin/env bash` находит `bash` через `PATH`, поэтому тот же скрипт работает там, где bash лежит не в `/bin`. `chmod +x` устанавливает бит выполнения.

Четыре привычки делают скрипт безопасным для запуска без присмотра.

- **Падать рано.** `set -euo pipefail` в начале, проверки аргументов и сообщение о правильном вызове в стандартный поток ошибок с ненулевым статусом.
- **Функции с локальными переменными.** Функция — именованная группа команд со своими `$1`, `$2` и `"$@"`; `local` не даёт её переменным утечь в остальную часть скрипта. Её статус — статус её последней команды.
- **Уборка через `trap`.** `trap 'rm -f "$tmp"' EXIT` регистрирует команду, которую bash выполняет при выходе из скрипта, — закончил ли он работу, упал ли при `-e` или был остановлен через Ctrl-C или `kill` (но не `kill -9`, который не может перехватить ни один процесс). Тогда временные файлы никогда не переживают скрипт.
- **Идемпотентность.** Двукратный запуск скрипта должен оставлять то же состояние, что и однократный, потому что шаг поставки будут повторять после сбоя. `mkdir -p` успешен, если каталог существует, `ln -sfn` заменяет ссылку, а добавление строки защищено проверкой, что её там ещё нет.

```console
$ bash naive.sh; bash naive.sh; echo "exit $?"; cat profile
mkdir: releases: File exists
exit 1
export APP_ENV=staging
export APP_ENV=staging
$ rm -rf releases profile
$ bash setup.sh; bash setup.sh; echo "exit $?"; cat profile; ls releases; readlink releases/current
exit 0
export APP_ENV=staging
2026-10-22
current
2026-10-22
```

`naive.sh` дописывает `export APP_ENV=staging` в `profile`, а затем выполняет `mkdir releases`. Второй запуск снова дописал строку и затем завершился ошибкой. `setup.sh` делает ту же работу идемпотентно:

```bash
#!/usr/bin/env bash
set -euo pipefail
release=releases/2026-10-22
mkdir -p "$release"
ln -sfn "${release#releases/}" releases/current
line='export APP_ENV=staging'
grep -qxF "$line" profile 2>/dev/null || echo "$line" >> profile
```

`${release#releases/}` удаляет префикс `releases/`, поэтому ссылка `releases/current` указывает на `2026-10-22` относительно собственного каталога. `grep -qxF` тихо (`-q`) спрашивает, равна ли целая строка (`-x`) фиксированной строке (`-F`, без регулярного выражения); только если нет, строка дописывается. Последняя привычка касается выходных файлов: писать во временный файл в том же каталоге и перемещать его на место через `mv`. Переименование в пределах одной файловой системы атомарно ([заметка о файлах](/ru/notes/acos/files-and-io#where-the-bytes-live-inodes-and-directories)), поэтому читатель видит старый файл или новый, но никогда не половину. Раздел «Пример» собирает всё это в один скрипт.

## Когда перестать писать на языке оболочки \{#when-to-stop-writing-shell\}

Оболочка — лучший язык для того, чтобы запускать программы и соединять их. Для большинства остальных задач это плохой язык: его единственные типы данных — строки и массивы строк, арифметика у него только целочисленная, обработка ошибок имеет дыры, показанные выше, а код трудно тестировать. Руководство по стилю Google называет границу прямо: если скрипт длиннее примерно 100 строк или в нём нетривиальное управление выполнением, перепишите его на структурированном языке ([Google Shell Style Guide](#references)). Другие признаки того, что время пришло:

- у данных есть структура сверх строк и полей: вложенный JSON, CSV с запятыми в кавычках, даты, с которыми нужно считать;
- логике нужны структуры данных: словари списков, записи из нескольких полей;
- скрипту нужны тесты или сообщения об ошибках с контекстом;
- он должен работать в Windows или на системах с другими версиями инструментов.

Тот же отчёт об ошибках сервера на Python, только со стандартной библиотекой:

```python
import gzip
import re
import sys
from collections import Counter
from pathlib import Path

LINE = re.compile(r'"(?P<method>\S+) (?P<path>\S+) [^"]*" (?P<status>\d{3}) ')
counts = Counter()
for log in sorted(Path(sys.argv[1]).glob("access.log*")):
    opener = gzip.open if log.suffix == ".gz" else open
    with opener(log, "rt") as f:
        for line in f:
            m = LINE.search(line)
            if m and int(m["status"]) >= 500:
                path = re.sub(r"/\d+", "/:id", m["path"].split("?")[0])
                counts[f'{m["method"]} {path}'] += 1
print(f"5xx responses: {counts.total()}")
for endpoint, n in counts.most_common():
    print(f"{n:4} {endpoint}")
```

```console
$ python3 -I errors.py logs
5xx responses: 39
  25 GET /api/search
  14 POST /api/orders
```

Программа длиннее конвейера, но разбирает строку запроса регулярным выражением, а не доверяет позициям полей, падает с трассировкой стека, которая называет файл и строку, если сжатый журнал обрезан, и каждую её часть можно протестировать инструментами из [заметки о тестировании](/ru/notes/python/testing). Практическое правило: исследовать в оболочке, однострочные конвейеры и короткие связующие скрипты оставлять в оболочке и переходить на Python, когда скрипту нужно расти.

<aside class="callout"><strong>Проверьте себя.</strong> (1) `dir="My Files"; rm -r $dir/tmp` — что получает `rm` и что может пойти не так? (2) Что отправляют в `less` команды `cmd 2>&1 | less` и `cmd | less 2>&1`? (3) Скрипт под `set -euo pipefail` содержит `n=$(ls *.log | wc -l)`. В каком случае он остановится и как сосчитать файлы иначе? (4) Почему `cd` — встроенная команда и почему `(cd /tmp; ls)` не меняет каталог оболочки, в которой это набрано?<details><summary>Ответы</summary>(1) Два слова, `My` и `Files/tmp`: она пытается удалить каталог `My` и `Files/tmp` относительно текущего каталога, а они могут существовать и оказаться не тем, что нужно. Пишите `rm -r "$dir/tmp"`. (2) Первая отправляет в канал и стандартный вывод, и стандартный поток ошибок, потому что `2>&1` применяется в `cmd` после того, как канал стал её дескриптором 1. Вторая отправляет только стандартный вывод; `2>&1` относится к `less`. (3) Когда нет ни одного файла `.log`: несовпавший шаблон остаётся буквальным словом `*.log`, `ls` завершается ошибкой, и `pipefail` вместе с `-e` останавливают скрипт. Используйте массив: `shopt -s nullglob; logs=(*.log); n=${#logs[@]}`. (4) Текущий каталог принадлежит процессу; потомок, сменивший свой каталог и завершившийся, оставил бы оболочку без изменений. Скобки выполняют свои команды в подоболочке (subshell) — порождённой копии оболочки, так что `cd` происходит в копии.</details></aside>

## Ограничения \{#limitations\}

- **Переносимость.** Bash — не POSIX `sh`: `[[`, массивов, `PIPESTATUS`, `<(…)` и `$'…'` нет в `dash`, который исполняет `/bin/sh` в Debian и Ubuntu. Инструменты GNU и BSD различаются флагами: `sed -i` в macOS требует обязательного аргумента-суффикса, `xargs` без `-r` на пустом вводе один раз запускает свою команду в GNU и не запускает её вовсе в BSD, а `find -printf` есть только в GNU.
- **macOS поставляет bash 3.2** 2006 года — по лицензионным причинам; ассоциативным массивам (`declare -A`), `mapfile` и `${var,,}` нужен bash 4 или новее. Примеры здесь их избегают.
- **В строгом режиме есть дыры**, показанные выше: `-e` игнорируется в условиях и в вызванных из них функциях, `local` скрывает статусы, а `pipefail` превращает `SIGPIPE` и «нет совпадений» в неудачи.
- **Текстовые конвейеры доверяют форматам.** Поле, сдвинувшееся на одну позицию, локаль, меняющая порядок сортировки, или значение, содержащее разделитель, ломают конвейер без единой ошибки.
- **Секреты легко утекают через оболочку.** Аргументы командной строки видны другим пользователям в `ps`, `set -x` печатает раскрытые переменные в журналы, а файл истории записывает всё, что было набрано. Передавайте секреты в файлах или в окружении одной команды, но никогда не аргументами.

## Что нужно запомнить \{#what-you-should-remember\}

- Оболочка читает строку, разбивает её на слова и выполняет подстановки, а затем запускает первое слово как встроенную команду или как программу через `fork`, `exec` и `wait`; `$?` хранит статус завершения.
- Подстановки выполняются в фиксированном порядке: фигурные скобки, тильда, параметры, арифметика и подстановка команд, затем разбиение на слова и подстановка имён файлов для результатов без кавычек, затем удаление кавычек. Заключайте каждую подстановку в двойные кавычки.
- Дескрипторы 0, 1 и 2 настраивает оболочка до `exec`; перенаправления применяются слева направо, поэтому `> file 2>&1` отправляет оба потока в файл, а `2>&1 > file` — нет. Канал соединяет дескриптор 1 одного процесса с дескриптором 0 следующего, и все стадии работают одновременно.
- Статус завершения 0 — успех; 127 — «команда не найдена»; $128 + n$ — смерть от сигнала $n$, так что 141 — это `SIGPIPE`.
- `set -e` останавливает скрипт при неудаче, `-u` — при неустановленных переменных, `pipefail` — при неудачах внутри конвейеров. Знайте ловушки: `grep`, ничего не нашедший, `head`, закрывающий канал, `-e`, игнорируемый в условиях, `local`, скрывающий статусы.
- Стройте конвейеры по стадиям и смотрите на каждый вывод; `sort | uniq -c | sort -rn` — таблица частот; `find -print0 | xargs -0` переживает любое имя файла; `jq` — это `awk` для JSON.
- Скрипты: шебанг, строгий режим, функции с `local`, `trap … EXIT` для уборки, идемпотентные шаги, `mv` для атомарного вывода. Переходите на Python, когда скрипт перерастает примерно 100 строк или у данных появляется структура.

## Пример \{#example\}

Скрипт подсчитывает ошибки сервера по эндпоинтам в текущих и ротированных журналах доступа. Это конвейер из разобранного примера, обёрнутый привычками из раздела «Скрипты».

```bash
#!/usr/bin/env bash
# error-report.sh: считает ответы 5xx по эндпоинтам в журналах доступа nginx, текущих и ротированных.
# Запуск: error-report.sh LOG_DIR [OUT_FILE]
set -euo pipefail

usage() {
  echo "usage: ${0##*/} LOG_DIR [OUT_FILE]" >&2
  exit 2
}

log_lines() {                     # все журналы доступа в $1, ротированные — распакованными
  find "$1" -name 'access.log*' -type f -print0 | xargs -0 -r gzip -dcf
}

endpoint() {                      # "GET /api/orders/17?x=1  ->  GET /api/orders/:id
  tr -d '"' | sed -E 's/[?].*//; s#/[0-9]+#/:id#g'
}

main() {
  [[ $# -ge 1 && $# -le 2 ]] || usage
  local dir=$1 out=${2:-}
  [[ -d $dir ]] || { echo "no such directory: $dir" >&2; exit 1; }

  tmp=$(mktemp "${out:-/tmp/error-report}.XXXXXX")   # рядом с OUT_FILE, чтобы mv был переименованием
  trap 'rm -f "$tmp"' EXIT        # срабатывает при успехе, при ошибке и при Ctrl-C

  log_lines "$dir" | awk '$9 >= 500 {print $6, $7}' | endpoint |
    sort | uniq -c | sort -rn |
    awk '{n += $1; s = s $0 "\n"} END {printf "5xx responses: %d\n%s", n, s}' > "$tmp"

  if [[ -z $out ]]; then
    cat "$tmp"
  else
    mv "$tmp" "$out"              # читатели видят старый отчёт или новый, но не половину
  fi
}

main "$@"
```

```console
$ ./error-report.sh
usage: error-report.sh LOG_DIR [OUT_FILE]
$ ./error-report.sh logs
5xx responses: 39
  25 GET /api/search
  14 POST /api/orders
$ ./error-report.sh logs report.txt && ls report.txt*
report.txt
$ ./error-report.sh empty
5xx responses: 0
$ ./error-report.sh nologs; echo "exit $?"
no such directory: nologs
exit 1
$ ./error-report.sh bad report.txt; echo "exit $?"; ls report.txt* /tmp/error-report.* 2>&1; head -n 1 report.txt
gzip: bad/access.log.1.gz: unexpected end of file
gzip: bad/access.log.1.gz: uncompress failed
exit 1
ls: /tmp/error-report.*: No such file or directory
report.txt
5xx responses: 39
```

Построчно:

- Шебанг находит bash через `PATH`; `set -euo pipefail` заставляет любую неудачу, неустановленную переменную или неудавшуюся стадию конвейера завершать скрипт. Ловушка pipefail здесь не срабатывает: ни одна стадия не закрывает свой ввод раньше времени, а `awk` завершается успешно, даже если ничего не совпало.
- `usage` пишет в дескриптор 2 через `>&2`, чтобы вызывающий, который перенаправил отчёт в файл, всё равно увидел сообщение, и завершается с 2 — условным статусом для неправильного вызова. `${0##*/}` отрезает каталог от пути скрипта.
- `log_lines` находит журналы через `-type f -print0` и передаёт их `gzip -dcf` через `xargs -0`. `-r` не даёт GNU `xargs` один раз запустить `gzip` без аргументов-файлов, когда `find` ничего не нашёл; BSD `xargs` и так ведёт себя именно так. Здесь лишний запуск был бы безвреден, поскольку GNU `xargs` даёт команде `/dev/null` в качестве стандартного ввода, но с командой, которая без аргументов что-то делает, например `xargs ls -l`, выводящей содержимое текущего каталога, это не так. Запуск на каталоге `empty` показывает результат: журналов нет, 0 ошибок.
- `endpoint` — функция, используемая как стадия конвейера: она читает свой стандартный ввод и пишет в свой стандартный вывод, как любая программа.
- В `main` выражение `[[ $# -ge 1 && $# -le 2 ]]` проверяет число аргументов, а `${2:-}` даёт пустое значение по умолчанию, которое иначе отверг бы `-u`.
- `mktemp` создаёт временный файл рядом с выходным, `report.txt.XXXXXX` с заменёнными X, чтобы итоговый `mv` был переименованием в пределах одного каталога. Без выходного файла временный файл создаётся в `/tmp`.
- `trap` удаляет временный файл, что бы ни случилось. После `mv` файла под этим именем больше нет, и `rm -f` ничего не делает.
- Конвейер взят из разобранного примера; последний `awk` складывает счётчики и печатает строку с итогом перед таблицей.
- Последний запуск показывает страховочную сетку в работе: обрезанный ротированный журнал заставляет `gzip` завершиться ошибкой, `pipefail` передаёт неудачу конвейеру, `-e` завершает скрипт со статусом 1, `trap` удаляет временный файл, а прежний `report.txt` остаётся нетронутым и по-прежнему содержит свои 39.
