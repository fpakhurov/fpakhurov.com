[Предыдущая заметка](/ru/notes/devops/git) сделала коммит единицей изменения: точным именованным деревом исходных файлов. Исходные файлы — ещё не то, что машина может запустить, а пользователь установить. Между ними стоит **сборка** (build): компиляция, компоновка, упаковка в бандлы и архивы и загрузка чужого кода, от которого зависит проект. В этой заметке мы выясняем, как инструмент сборки решает, что переделать после изменения, почему ответ «всё, что старше своих входов» дёшев, но ненадёжен, как диапазоны версий зависимостей превращаются в один точный набор версий и что нужно, чтобы две сборки одного коммита дали одни и те же байты. Результат сборки, **артефакт** (artifact) с версией, — то, что доставляет остальная часть раздела.

**Соглашения.** Команды запускались в macOS 26.5 (arm64) 23 октября 2026 года с GNU Make 3.81 от Apple, Apple clang 21, Python 3.14.7 и Git 2.47; современные дистрибутивы Linux поставляют GNU Make 4.4, который во всём показанном ведёт себя так же, кроме оговорённых мест. Каждый листинг в заметке — настоящий сеанс.

## Отправная точка: сценарий сборки \{#baseline-a-build-script\}

Первая сборка проекта — сценарий оболочки, который выполняет все шаги по порядку:

```bash
#!/bin/bash
set -e
mkdir -p build
cc -O2 -c -o build/eval.o src/eval.c
cc -O2 -c -o build/parse.o src/parse.c
cc -O2 -c -o build/main.o src/main.c
cc -o build/calc build/eval.o build/main.o build/parse.o
```

Он корректен, потому что переделывает всё, и в этом же его беда. Изменение одного файла из тысячи перекомпилирует всю тысячу. Шаги выполняются один за другим, хотя три компиляции независимы. Порядок записан вручную, поэтому добавление файла требует найти для него правильное место, а шаг, который кто-то передвинул слишком рано, читает устаревшие результаты. И сценарий не отвечает на вопрос, который разработчик задаёт после каждой правки: какой наименьший объём работы приводит результаты в актуальное состояние?

## Сборка — это граф целей \{#a-build-is-a-graph-of-targets\}

Инструмент сборки заменяет сценарий описанием того, что от чего зависит. Каждая **цель** (target) — файл, который нужно получить (или действие, которое нужно выполнить); у каждой есть **зависимости** (prerequisites) — файлы, из которых она делается, — и **рецепт** (recipe) — команды, которые её делают. Зависимости сами являются целями, поэтому описание — ориентированный граф, и он должен быть ациклическим: файл не может требоваться для собственной сборки. Инструмент выполняет рецепты в топологическом порядке, то есть в любом порядке, в котором каждая цель идёт после своих зависимостей.

Сквозной пример — небольшой калькулятор на C: `parse.c` разбирает строку вида `3 + 4` на операнды и оператор, `eval.c` применяет оператор, а `main.c` читает строки и печатает результаты. `main.c` включает оба заголовка, `parse.c` и `eval.c` — каждый свой. В графе пять исходных файлов, три объектных файла, программа `calc` и цель `test`, которая её запускает:

<BuildGraph />

1. Разработчик правит заголовок `eval.h`.
2. Устаревает каждый объектный файл, исходник которого его включает: `eval.o` и `main.o`. `parse.o` от него не зависит и остаётся.
3. Программа перекомпоновывается из двух новых объектных файлов и старого `parse.o`.
4. Тест запускается на новой программе.

<aside class="callout"><strong>Ключевая идея.</strong> Описать сборку как граф от входов к выходам, а остальное поручить инструменту. После изменения затронуты могут быть только цели, достижимые из изменённых файлов: это множество и есть наименьший объём работы. Цели, которые не зависят друг от друга, можно собирать одновременно. Тогда весь вопрос об инструменте сборки сводится к тому, как он решает, что вход изменился: по времени изменения, как make, или по хешу содержимого, как Bazel.</aside>

## make: правила и времена изменения \{#make-rules-and-timestamps\}

GNU make читает граф из файла `Makefile`, состоящего из **правил** (rules) ([руководство GNU Make, Rules](#references)):

```make
build/calc: build/eval.o build/main.o build/parse.o
	cc -o build/calc build/eval.o build/main.o build/parse.o
```

Слово перед двоеточием называет цель, список после него — зависимости, а строка с отступом, которая обязана начинаться с табуляции, — рецепт. Правило, по которому make решает, что делать, короткое. Чтобы привести цель в актуальное состояние, make сначала рекурсивно приводит в актуальное состояние каждую её зависимость; затем выполняет рецепт цели, если цели нет или если у какой-нибудь зависимости время изменения позже, чем у цели. Иначе цель остаётся как есть. Стюарт Фельдман написал первый make в 1976 году ровно вокруг этого правила ([Feldman, 1979](#references)), и каждый make с тех пор его сохранил.

Полный Makefile калькулятора разобран построчно в [Примере](#example) в конце заметки. Первая сборка выполняет все рецепты; вторая не находит, что делать; затем мы правим заголовок и спрашиваем make, что он пересобрал бы:

```console
$ make
mkdir -p build
cc -MMD -MP -O2 -Wall -Wextra -c -o build/eval.o src/eval.c
cc -MMD -MP -O2 -Wall -Wextra -c -o build/main.o src/main.c
cc -MMD -MP -O2 -Wall -Wextra -c -o build/parse.o src/parse.c
cc -o build/calc build/eval.o build/main.o build/parse.o
$ make
make: Nothing to be done for `all'.
$ make test
build/calc < tests/input.txt | diff - tests/expected.txt
test passed
$ echo '/* Operators: + - * / */' >> src/eval.h
$ stat -f '%Sm %N' -t '%T' src/eval.h build/*.o build/calc
04:31:28 src/eval.h
04:31:26 build/eval.o
04:31:27 build/main.o
04:31:27 build/parse.o
04:31:27 build/calc
$ make -n
cc -MMD -MP -O2 -Wall -Wextra -c -o build/eval.o src/eval.c
cc -MMD -MP -O2 -Wall -Wextra -c -o build/main.o src/main.c
cc -o build/calc build/eval.o build/main.o build/parse.o
```

Заголовок новее, чем `eval.o` и `main.o`, поэтому оба перекомпилируются; `parse.o` новее всего, от чего зависит, поэтому остаётся; а `calc` нужно перекомпоновать, потому что две её зависимости окажутся новее неё. Это в точности множество пересборки с рисунка. `make -n` печатает рецепты, не выполняя их, — дешёвый способ проверить граф Makefile.

**Как make узнаёт о заголовках.** В правиле для `main.c` никто вручную не упоминает `eval.h`. Флаги `-MMD -MP` заставляют компилятор записать рядом с каждым объектным файлом маленький makefile из заголовков, которые он действительно прочитал:

```console
$ cat build/main.d
build/main.o: src/main.c src/parse.h src/eval.h
src/parse.h:
src/eval.h:
```

Makefile включает эти файлы, поэтому граф достраивает компилятор — единственная программа, которая по-настоящему знает, от чего зависит файл на C. Пустые правила для заголовков (`-MP`) не дают make упасть, когда заголовок удалён. Без этого написанный вручную список заголовков всегда отстаёт на один `#include`, и сборка молча переиспользует объектный файл, скомпилированный со старым заголовком.

### Где ошибаются времена изменения \{#what-timestamps-get-wrong\}

Время изменения — суррогат утверждения «содержимое изменилось», и этот суррогат ошибается в обе стороны. Он сообщает об изменениях, которых не было:

```console
$ touch src/eval.h
$ make
cc -MMD -MP -O2 -Wall -Wextra -c -o build/eval.o src/eval.c
cc -MMD -MP -O2 -Wall -Wextra -c -o build/main.o src/main.c
cc -o build/calc build/eval.o build/main.o build/parse.o
```

В заголовке ничего не изменилось, а пересобрана половина проекта. То же происходит в большом масштабе после `git checkout` или `git stash`: Git записывает изменяемые файлы с текущим временем, поэтому переключение на другую ветку и обратно делает каждый затронутый файл новым. Хуже того, суррогат может пропустить изменения, которые были. Этот make сравнивает времена с точностью до целых секунд, поэтому правка, сделанная в ту же секунду, что и сборка, невидима:

```console
$ make > /dev/null; perl -pi -e "s/case '\\*':/case 'x': case '*':/" src/eval.c; make
make: Nothing to be done for `all'.
$ echo '6 x 7' | build/calc
bad input: 6 x 7
$ stat -f '%Fm %N' src/eval.c build/eval.o
1792719095.900911904 src/eval.c
1792719095.809431379 build/eval.o
```

Правка, которая принимает `x` как знак умножения, пришла через 0.09 секунды после записи `eval.o`, в ту же секунду, и программа продолжила выполнять старый код. Make 4.x в Linux использует наносекундные времена файловой системы и сужает это окно, но остальные сбои остаются: часы, которые расходятся между сетевой файловой системой и машиной, где работает make, файлы, восстановленные из архива со старыми временами, и сгенерированные файлы, которые генератор переписывает без изменений. Каждый из этих случаев — либо напрасная пересборка, либо устаревший результат, а устаревший результат — это сборка, которая неверна и молчит об этом.

## Фиктивные цели \{#phony-targets\}

Некоторые цели — не файлы: `all`, `test`, `clean`. Make этого не знает. Если существует файл с именем цели, а у цели нет зависимостей, цель считается актуальной, и её рецепт никогда не выполняется. Это показывает makefile из одного правила без объявления:

```console
$ touch clean
$ make -f nophony.mk clean
make: `clean' is up to date.
$ make clean
rm -rf build
```

Настоящий Makefile объявляет `.PHONY: all test clean`, и это сообщает make, что эти имена — действия (фиктивные цели, phony targets), всегда устаревшие, так что рецепт выполняется даже при наличии файла `clean`.

## Параллельная сборка: `-j` \{#parallel-builds--j\}

Независимые цели можно собирать одновременно. `make -j4` выполняет до четырёх рецептов сразу, выбирая любую цель, все зависимости которой готовы:

```console
$ make clean > /dev/null; time make -j1 > /dev/null

real	0m0.111s
user	0m0.083s
sys	0m0.042s
$ make clean > /dev/null; time make -j4 > /dev/null

real	0m0.068s
user	0m0.091s
sys	0m0.046s
```

Ускорение ограничено графом, а не числом процессоров. Пусть $T_1$ — суммарное время всех рецептов, то есть время с одним заданием, а $T_\infty$ — время самой длинной цепочки зависимых рецептов, **критического пути** (critical path): никакое число заданий не завершит работу быстрее этой цепочки. С $p$ заданиями жадный планировщик, такой как в make, заканчивает не позже чем за

$$
T_p \le \frac{T_1}{p} + T_\infty
$$

(оценка Брента): работа, распределённая между $p$ исполнителями, плюс цепочка, которую распределить нельзя. Если по одной замерить их с помощью `/usr/bin/time` на той же машине, каждая компиляция занимает около 20 мс, а компоновка около 30 мс, так что $T_1 \approx 3 \cdot 20 + 30 = 90$ мс и $T_\infty \approx 20 + 30 = 50$ мс: одна компиляция, затем компоновка. Четыре задания не могут уложиться меньше чем примерно в 50 мс, сколько бы ни было процессоров. Измеренные 111 и 68 мс включают ещё запуск make и создание каталога, и параллельный запуск близок к своему пределу. В настоящем проекте с тысячами файлов $T_\infty$ задают длинные цепочки вроде генерации кода, затем компиляции, затем компоновки большого исполняемого файла, и именно сокращение этих цепочек ускоряет сборку. Та же арифметика возвращается для целых конвейеров CI в [заметке о непрерывной интеграции](/ru/notes/devops/continuous-integration#the-time-arithmetic-of-a-pipeline).

Параллелизм заодно проверяет граф. Последовательный make обходит зависимости слева направо, поэтому зависимость, которой нет в Makefile, может удовлетвориться случайно: шаг, который создаёт файл, оказался раньше в списке. При `-j` оба шага выполняются одновременно, и сборка падает от раза к разу. Сборка, которая работает только с `-j1`, описана неверным графом.

## Хеши содержимого вместо времён изменения \{#content-hashes-instead-of-timestamps\}

Лекарство от времён изменения — смотреть на содержимое. **Сборка с адресацией по содержимому** (content-addressed build) даёт каждому действию ключ — хеш его командной строки и содержимого всех его входов — и хранит кэш, отображающий ключи в результаты. Перед выполнением действия инструмент вычисляет ключ; если ключ есть в кэше, результат копируется из кэша, и действие не выполняется. Так работают Bazel ([документация Bazel, Remote caching](#references)), Buck2, Pants и Nix. Идея умещается в короткую программу на Python для того же калькулятора, где граф объявлен как список действий в порядке зависимостей:

```python
# Сборка с адресацией по содержимому: действие выполняется, только если в кэше нет результата для хеша его команды и входов.
import hashlib, pathlib, shutil, subprocess

CACHE = pathlib.Path('.cache')
ACTIONS = [  # (выход, входы, команда): граф сборки, объявленный явно
    ('build/eval.o',  ['src/eval.c', 'src/eval.h'], 'cc -O2 -c -o build/eval.o src/eval.c'),
    ('build/parse.o', ['src/parse.c', 'src/parse.h'], 'cc -O2 -c -o build/parse.o src/parse.c'),
    ('build/main.o',  ['src/main.c', 'src/parse.h', 'src/eval.h'], 'cc -O2 -c -o build/main.o src/main.c'),
    ('build/calc',    ['build/eval.o', 'build/main.o', 'build/parse.o'], 'cc -o build/calc build/eval.o build/main.o build/parse.o'),
]

def digest(data: bytes) -> str:
    return hashlib.sha256(data).hexdigest()

pathlib.Path('build').mkdir(exist_ok=True)
for out, inputs, cmd in ACTIONS:                       # уже в порядке зависимостей
    key = digest('\n'.join([cmd] + [digest(pathlib.Path(p).read_bytes()) for p in inputs]).encode())
    cached = CACHE / key
    if cached.exists():
        shutil.copyfile(cached, out)
        print(f'hit   {out:14} key {key[:12]}')
    else:
        subprocess.run(cmd, shell=True, check=True)
        CACHE.mkdir(exist_ok=True)
        shutil.copyfile(out, cached)
        print(f'run   {out:14} key {key[:12]}  output {digest(pathlib.Path(out).read_bytes())[:12]}')
pathlib.Path('build/calc').chmod(0o755)                # копия из кэша не исполняемая
```

Запуск на свежем проекте, а затем после тех же трёх правок, что и раньше:

```console
$ python3.14 hashbuild.py
run   build/eval.o   key 2a1097422cdc  output fa590a7d7951
run   build/parse.o  key b3e9740416cb  output aca80f845bcc
run   build/main.o   key d9e831d5d8c5  output 7290a32cc37c
run   build/calc     key f30c0774722f  output 3e38c4584cef
$ touch src/eval.h; python3.14 hashbuild.py
hit   build/eval.o   key 2a1097422cdc
hit   build/parse.o  key b3e9740416cb
hit   build/main.o   key d9e831d5d8c5
hit   build/calc     key f30c0774722f
$ echo '/* Operators: + - * / */' >> src/eval.h; python3.14 hashbuild.py
run   build/eval.o   key 8db202bd36de  output fa590a7d7951
hit   build/parse.o  key b3e9740416cb
run   build/main.o   key 97518ecdd122  output 7290a32cc37c
hit   build/calc     key f30c0774722f
$ perl -pi -e "s/case '\\*':/case 'x': case '*':/" src/eval.c; python3.14 hashbuild.py
run   build/eval.o   key 43e4201326e2  output 503d76bf4ec4
hit   build/parse.o  key b3e9740416cb
hit   build/main.o   key 97518ecdd122
run   build/calc     key de0f2ad9bbd4  output cb3f52f703fd
$ echo '6 x 7' | build/calc
42
```

В четырёх запусках видны три свойства:

- **`touch` ничего не стоит.** Содержимое прежнее, поэтому все ключи прежние, и каждое действие — попадание в кэш.
- **Раннее отсечение** (early cutoff). Комментарий в заголовке меняет входы `eval.o` и `main.o`, поэтому оба перекомпилируются, но объектные файлы выходят байт в байт такими же, как раньше (снова `fa590a7d7951` и `7290a32cc37c`). Ключ компоновки зависит от содержимого объектных файлов, а не от их времён, поэтому компоновка — попадание в кэш: изменение перестаёт распространяться, как только какой-то результат оказывается неизменным. Make перекомпоновал бы программу, а с ней запустил бы и все тесты ниже по графу. [Мохов, Митчелл и Пейтон Джонс (2018)](#references) дали этому свойству имя и классифицируют системы сборки по тому, есть ли оно у них.
- **Нет слепоты в пределах секунды.** Правка поведения меняет содержимое `eval.c`, что бы ни показывали часы.

Кэш корректен ровно настолько, насколько полон список входов. Если компиляция читает заголовок, который действие не объявляет, изменение этого заголовка не меняет ключ, и кэш возвращает устаревший объектный файл — сбой хуже, чем у make, потому что устаревший результат теперь приходит из кэша, общего для всех разработчиков. Поэтому Bazel делает действия **герметичными** (hermetic): каждое выполняется в песочнице, где есть только объявленные входы, так что необъявленный вход приводит к ошибке действия, а не молча игнорируется, и компилятор тоже объявлен как вход с версией. Взамен кэш можно разделять. **Удалённый кэш** (remote cache) с ключами-хешами позволяет ноутбуку разработчика или раннеру (runner) CI скачать результаты, которые кто-то другой уже собрал из тех же входов, а **удалённое выполнение** (remote execution) отправляет сами действия на ферму машин. Изменение одного файла в репозитории из миллионов строк тогда пересобирает только действия ниже него по графу, один раз, для всех ([документация Bazel, Hermeticity](#references)).

## Внешние зависимости: диапазоны и файлы блокировки \{#dependencies-from-outside-ranges-and-lockfiles\}

Большая часть кода современной программы приходит из пакетов, написанных другими людьми и загруженных из реестра: PyPI, npm, crates.io, Maven Central. Проект объявляет, что ему нужно, в виде **диапазонов версий** (version ranges), а **резолвер** (resolver) выбирает по одной точной версии каждого пакета так, чтобы выполнялся каждый диапазон во всём графе.

Диапазоны имеют смысл благодаря **семантическому версионированию** (semantic versioning, [SemVer 2.0.0](#references)): версия `MAJOR.MINOR.PATCH` обещает, что рост PATCH только исправляет ошибки, рост MINOR совместимо добавляет возможности, и только рост MAJOR может сломать вызывающий код. При таком обещании диапазон может принимать всё, что должно быть совместимо. В нотации npm, которую по умолчанию использует и Cargo:

| Диапазон | Означает | Принимает |
| --- | --- | --- |
| `^2.1.0` | та же старшая версия, не ниже 2.1.0 | от 2.1.0 до 2.x, но не 3.0.0 |
| `~2.1.0` | та же минорная версия, не ниже 2.1.0 | от 2.1.0 до 2.1.x, но не 2.2.0 |
| `^0.3.1` | до 1.0 несовместимые изменения выражает минорная версия | от 0.3.1 до 0.3.x |
| `2.4.1` | ровно эта версия | 2.4.1 |

[PEP 440](#references) в Python записывает те же идеи как `>=2.1,<3` и `~=2.1.0`, как показал [курс Python](/ru/notes/python/modules-and-packages#installing-packages-pip-and-uv). Резолвер для таких диапазонов умещается в сорок строк на Python. Он берёт самую новую версию, подходящую под первый неразрешённый диапазон, добавляет в список собственные зависимости этой версии и выполняет перебор с возвратом (backtracking), когда более поздний диапазон выполнить нельзя:

```python
# Игрушечный резолвер: на входе диапазоны semver, на выходе по одной точной версии на пакет, с перебором с возвратом.
import json, sys

def ver(s):                                    # '2.4.1' -> (2, 4, 1)
    return tuple(int(x) for x in s.split('.'))

def allows(rng, v):
    """npm-style ranges: ^1.2.3 is >=1.2.3 <2.0.0 (^0.2.3 is <0.3.0); ~1.2.3 is >=1.2.3 <1.3.0."""
    op, low = rng[0], ver(rng[1:])
    if op == '^':
        high = (low[0] + 1, 0, 0) if low[0] > 0 else (0, low[1] + 1, 0)
    else:
        high = (low[0], low[1] + 1, 0)
    return low <= ver(v) < high

INDEX = json.load(open(sys.argv[1]))           # {пакет: {версия: {зависимость: диапазон}}}

def resolve(wanted, chosen):
    """wanted: list of (package, range, who asked); chosen: {package: version}."""
    if not wanted:
        return chosen
    (pkg, rng, who), rest = wanted[0], wanted[1:]
    if pkg in chosen:                          # уже выбран: должен удовлетворять и этому диапазону
        return resolve(rest, chosen) if allows(rng, chosen[pkg]) else None
    for v in sorted(INDEX[pkg], key=ver, reverse=True):   # сначала самые новые
        if allows(rng, v):
            deps = [(d, r, f'{pkg} {v}') for d, r in INDEX[pkg][v].items()]
            found = resolve(rest + deps, {**chosen, pkg: v})
            if found:
                return found
            print(f'  backtrack: {pkg} {v} (asked by {who}) leads to a conflict')
    return None

app = json.load(open(sys.argv[2]))             # прямые зависимости проекта в виде диапазонов
lock = resolve([(p, r, 'app') for p, r in app.items()], {})
print(json.dumps(dict(sorted(lock.items())), indent=1) if lock else 'no solution')
```

В игрушечном индексе `http` есть в пяти версиях, а `auth` в двух, из которых более новой нужны более новый `http` и пакет `json`:

```console
$ cat index.json
{
 "http":  {"2.0.0": {}, "2.1.0": {}, "2.1.3": {}, "2.4.1": {}, "3.0.0": {}},
 "auth":  {"1.2.0": {"http": "^2.0.0"}, "1.3.0": {"http": "^2.4.0", "json": "^1.1.0"}},
 "json":  {"1.0.0": {}, "1.1.2": {}}
}
```

Приложению нужны `http` и `auth`, и оба пути ведут к `http`: это **ромб** (diamond):

```console
$ cat app.json
{"http": "^2.1.0", "auth": "^1.2.0"}
$ python3.14 resolve.py index.json app.json | tee lock.json
{
 "auth": "1.3.0",
 "http": "2.4.1",
 "json": "1.1.2"
}
$ cat app-tilde.json
{"http": "~2.1.0", "auth": "^1.2.0"}
$ python3.14 resolve.py index.json app-tilde.json
  backtrack: auth 1.3.0 (asked by app) leads to a conflict
{
 "auth": "1.2.0",
 "http": "2.1.3"
}
```

С `^2.1.0` всё сходится на самых новых версиях. С `~2.1.0` приложение отказывается от `http` 2.4, самый новый `auth` на нём настаивает, и резолвер отступает к более старому `auth`, отчего из графа заодно исчезает `json`. Настоящие резолверы ищут в том же пространстве лучшими алгоритмами (pip использует перебор с возвратом, uv и Poetry — PubGrub, который учится на каждом конфликте), и общая задача NP-полна ([Cox, 2016](#references)), но форма у неё именно такая.

Результат разрешения зависит от того, что лежит в реестре в день запуска. Неделю спустя публикуется `http` 2.5.0:

```console
$ jq -c '.http += {"2.5.0": {}}' index.json > new.json && mv new.json index.json
$ python3.14 resolve.py index.json app.json | diff lock.json -
3c3
<  "http": "2.4.1",
---
>  "http": "2.5.0",
```

В проекте ничего не изменилось, а его сборка теперь содержит другой код. Поэтому результат разрешения записывают. **Файл блокировки** (lockfile: `uv.lock`, `package-lock.json`, `Cargo.lock`, `go.sum`) фиксирует точную версию каждого пакета, прямого и косвенного, его источник и хеш каждого файла; установка из файла блокировки воспроизводит тот же набор, а скачанный файл с другим хешем отвергается. [Курс Python](/ru/notes/python/modules-and-packages#lockfiles-and-reproducible-experiments) подробно разбирает `uv.lock`. У двух файлов разные задачи: диапазоны говорят, что код поддерживает, файл блокировки — что использовала одна сборка. Файл блокировки коммитят, и меняется он только намеренно, отдельным коммитом, обычно в пул-реквесте (pull request), который открывает бот вроде Dependabot или Renovate при появлении новой версии, чтобы обновление прошло те же тесты, что и любое другое изменение.

Экосистемы расходятся в одном решении, которое определяет форму задачи. Python допускает одну версию пакета на окружение, поэтому ромб должен сойтись. npm умеет ставить две версии рядом, и каждый пакет видит свою; это избавляет от конфликтов ценой дублированного кода и двух копий любого глобального состояния. Go идёт третьим путём, **выбором минимальной версии** (minimal version selection): он берёт *самую старую* версию, удовлетворяющую всем требованиям; она определяется одними требованиями и не меняется при публикации новых версий, так что файл блокировки нужен Go только для хешей ([Cox, 2018](#references)).

## Воспроизводимые сборки \{#reproducible-builds\}

Файл блокировки фиксирует входы. Это ещё не делает результат повторяемым. Сборка **воспроизводима** (reproducible), если при одних и тех же исходном коде, окружении сборки и инструкциях сборки любая сторона может получить побитно идентичные копии артефактов ([проект Reproducible Builds, Definitions](#references)). Обычно её ломают три вещи.

**Время.** Сборка, которая записывает, когда она произошла, при каждом запуске даёт другой результат. Макросы C `__DATE__` и `__TIME__` — классический случай:

```console
$ cat version.c
#include <stdio.h>
int main(void) { printf("calc, built %s %s\n", __DATE__, __TIME__); return 0; }
$ cc -c -o a.o version.c; sleep 1; cc -c -o b.o version.c; shasum -a 256 a.o b.o
81d60a37d8d6d3c9c08ea689ec6d3a26484d6c5945f23ae36df6f2372166eef1  a.o
0133aceb22006455ee2069d0f8cd8724039d9b781b5399dc84beb7db5c41597c  b.o
$ export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)   # the time of the last commit
$ echo $SOURCE_DATE_EPOCH
1792670400
$ cc -c -o c.o version.c; sleep 1; cc -c -o d.o version.c; shasum -a 256 c.o d.o
6ba486070c407aaf8ad01a88e871c80391fc140ba88586a40fcac5258e00f1f9  c.o
6ba486070c407aaf8ad01a88e871c80391fc140ba88586a40fcac5258e00f1f9  d.o
```

Соглашение `SOURCE_DATE_EPOCH` ([Reproducible Builds, спецификация SOURCE_DATE_EPOCH](#references)) даёт инструментам одну метку времени вместо часов, обычно время последнего коммита, которое принадлежит исходному коду. GCC, Clang и многие архиваторы и инструменты документации его учитывают; программа, скомпонованная из `c.o`, при каждой пересборке печатает `calc, built Oct 22 2026 12:00:00` — время коммита.

**Порядок и метаданные.** Архив записывает порядок, в котором добавлялись файлы, их времена изменения и учётную запись владельца. Инструмент, который добавляет файлы в том порядке, в каком их перечисляет файловая система, ставит им текущие времена и пишет время в заголовок gzip, при каждом запуске даёт новый архив. `package.py` упаковывает одну и ту же папку `dist/` обоими способами; воспроизводимый режим сортирует имена, ставит всем файлам время `SOURCE_DATE_EPOCH`, очищает владельца и не пишет метку времени в заголовок gzip:

```console
$ find dist -type f
dist/bin/calc
dist/share/README
$ python3.14 package.py default; sleep 1; python3.14 package.py default
default 626585c6a91ed567 1759 bytes
default dfb689c90f01b336 1759 bytes
$ export SOURCE_DATE_EPOCH=1792670400
$ python3.14 package.py reproducible; touch dist/bin/calc; python3.14 package.py reproducible
reproducible 8ed98cea04ac6e10 1587 bytes
reproducible 8ed98cea04ac6e10 1587 bytes
```

Два обычных запуска с разницей в секунду уже различаются; воспроизводимые совпадают даже после того, как время одного файла изменилось. Та же проблема прячется в файлах сборки: GNU make с 3.82 по 4.2 возвращал `$(wildcard src/*.c)` в порядке каталога, который различается между файловыми системами, и поэтому на разных машинах компоновал объектные файлы в разном порядке; Makefile в [Примере](#example) оборачивает его в `$(sort …)`. Обход хеш-таблиц, порядок которого может меняться от запуска к запуску, — та же ловушка внутри программы.

**Окружение.** Абсолютный путь каталога сборки попадает в отладочную информацию и в сообщения об ошибках; имя пользователя, имя хоста, локаль и часовой пояс попадают в сгенерированные файлы; а версия компилятора меняет код. Лекарства — вырезать или переназначать пути (`-ffile-prefix-map`), фиксировать локаль и часовой пояс и считать набор инструментов сборки закреплённым входом; именно это делает образ контейнера с окружением сборки, как показывает [следующая заметка](/ru/notes/devops/container-images).

**Зачем это нужно.** Воспроизводимая сборка делает артефакт проверяемым. Если каждый, кто собирает помеченный тегом исходный код, получает тот же хеш, что и у опубликованного исполняемого файла, в этом файле нет ничего, чего нет в исходниках. Две атаки показывают, для чего эта проверка. При компрометации SolarWinds, раскрытой в декабре 2020 года, злоумышленники не меняли репозиторий исходного кода: вредоносная программа на сервере сборки вставляла бэкдор в продукт во время компиляции, и собственные подписанные обновления компании доставили его клиентам ([CISA, 2021](#references)). В бэкдоре xz-utils, найденном в марте 2024 года (CVE-2024-3094), вредоносный сценарий сборки был только в архивах релиза, но не в репозитории Git, так что сборка из Git и сборка из архива различались бы ([Freund, 2024](#references)). Независимая пересборка со сравнением хешей ловит оба случая. [Последняя заметка курса](/ru/notes/devops/incidents-and-security#the-supply-chain-sboms-signatures-and-slsa) достраивает остальную защиту: перечни компонентов, подписи и подписанные сведения о происхождении, оценённые по уровням SLSA.

## Артефакты и версионирование \{#artifacts-and-versioning\}

**Артефакт** — результат сборки, сохранённый на будущее: исполняемый файл, wheel, JAR, tar-архив или, начиная со [следующей заметки](/ru/notes/devops/container-images), образ контейнера. Полезным его делают три свойства:

- **Неизменяемость и идентификация.** Артефакт с версией никогда не пересобирают и не перезаписывают. Его идентичность — его хеш, а реестр или репозиторий артефактов (PyPI, Maven Central, Nexus, Artifactory, реестр OCI) хранит его под именем, версией и контрольной суммой.
- **Прослеживаемость.** Он хранит сведения о том, откуда взялся: коммит, файл блокировки, сборщик. В формате образов OCI для этого есть стандартные аннотации, как показывает следующая заметка.
- **Однократная сборка.** Артефакт, прошедший тесты, — тот самый артефакт, который развёртывают. Пересборка для продакшена с теми версиями, которые реестр предлагает в этот день, отправляет в продакшен код, который никто не тестировал; на этом правиле строится [заметка о непрерывной доставке](/ru/notes/devops/continuous-delivery#one-artifact-many-environments).

Библиотеки несут семантические версии, потому что их пользователям нужно обещание совместимости. Сервисы, которые развёртывают, а не устанавливают, часто версионируют по коммиту: он уникален и ведёт обратно к исходному коду. `git describe` сочетает оба подхода: ближайший тег, число коммитов после него и сокращённое имя коммита:

```console
$ git describe --tags
v1.4.0-2-g0ecda82
$ git checkout -q v1.4.0 && git describe --tags && git checkout -q main
v1.4.0
$ echo wip >> notes.txt; git describe --tags --dirty
v1.4.0-2-g0ecda82-dirty
$ git rev-parse --short=12 HEAD
0ecda825d1a6
```

`v1.4.0-2-g0ecda82` — это два коммита после тега `v1.4.0`, на коммите `0ecda82` (`g` означает Git). Сборка из рабочего дерева с незакоммиченными изменениями помечается `-dirty` — это версия, которую не может воспроизвести ни один коммит и которую конвейер выпуска должен отвергнуть. SemVer отводит суффикс после `+` под метаданные сборки (`1.4.0+0ecda82`), которые не влияют на упорядочение версий.

## Ограничения \{#limitations\}

- **Язык make стар и лаконичен.** Переменные раскрываются двумя разными способами (`=` и `:=`), рецепты — это строки оболочки, выполняемые по одной, табуляция значима, а рекурсивные makefile, вызывающие make в каждом подкаталоге, разрезают граф и теряют общую картину ([Miller, 1998](#references)). Поэтому крупные проекты на C и C++ генерируют файлы сборки с помощью CMake или Meson и выполняют их с помощью Ninja, который ничего не делает, кроме быстрого выполнения графа.
- **Хеширование содержимого стоит работы.** Хешировать каждый вход, объявлять каждую зависимость и выполнять действия в песочницах — это труд, и системы в стиле Bazel окупаются скорее для больших репозиториев и многих разработчиков, чем для небольшого сервиса.
- **Файлы блокировки фиксируют версии, а не поведение.** Закреплённый пакет всё равно может загружать данные во время работы, а сценарий установки пакета может выполнить произвольный код при установке; файлы блокировки с хешами останавливают изменённый файл, но не вредоносный, который попал в блокировку.
- **Воспроизводимость — это спектр.** Побитная идентичность требует, чтобы сотрудничал каждый инструмент цепочки, и некоторые (подпись кода, оптимизация по профилю, недетерминированные компоновщики) требуют дополнительной работы. Многие проекты сначала добиваются сборок, одинаковых по функциональности, и применяют побитную воспроизводимость там, где проверка цепочки поставок важнее всего.
- **Экосистемы языков различаются.** У каждой свой резолвер, свой файл блокировки и свой реестр; эта заметка показывает общую форму, а не подробности npm, Cargo, Maven или uv.

## Что нужно запомнить \{#what-you-should-remember\}

- Сборка — ориентированный ациклический граф целей, зависимостей и рецептов. После изменения пересобирать нужно только цели, достижимые из изменённых входов.
- make пересобирает цель, которой нет или которая старше какой-либо зависимости. Времена изменения дёшевы и ошибаются в обе стороны: `touch` и `git checkout` вызывают ненужные пересборки, а правки в ту же секунду или расходящиеся часы — устаревшие результаты.
- `.PHONY` объявляет цели-действия; `-MMD -MP` поручает компилятору сообщить зависимости от заголовков; `-j` выполняет независимые рецепты параллельно, а критический путь ограничивает ускорение: $T_p \le T_1/p + T_\infty$.
- Сборки с адресацией по содержимому дают каждому действию ключ из хеша его команды и входов, что даёт раннее отсечение и общие удалённые кэши и требует герметичных действий с объявленными входами.
- Диапазоны говорят, что код поддерживает; файл блокировки — что использовала одна сборка, вместе с хешами. Разрешение меняется вместе с реестром, поэтому файл блокировки коммитят и обновляют намеренно.
- Сборка воспроизводима, если одни и те же исходники, окружение и инструкции дают одинаковые байты. Её ломают время, порядок и окружение; чинят `SOURCE_DATE_EPOCH`, сортировка и закреплённые инструменты. Независимые пересборки ловят подменённые сборщики и подменённые архивы релизов.
- Артефакт собирают один раз, идентифицируют по хешу и версии, прослеживают до коммита и продвигают без изменений.

## Пример \{#example\}

Полный Makefile калькулятора, тот самый, который дал все сеансы make выше:

```make
# Build the calculator in build/, test it, clean up. GNU make 3.81 or later.
CC       = cc
CFLAGS   = -O2 -Wall -Wextra
CPPFLAGS = -MMD -MP
BUILD    = build
SRCS     := $(sort $(wildcard src/*.c))
OBJS     := $(SRCS:src/%.c=$(BUILD)/%.o)

.PHONY: all test clean

all: $(BUILD)/calc

$(BUILD)/calc: $(OBJS)
	$(CC) -o $@ $^

$(BUILD)/%.o: src/%.c | $(BUILD)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c -o $@ $<

$(BUILD):
	mkdir -p $@

test: $(BUILD)/calc
	$(BUILD)/calc < tests/input.txt | diff - tests/expected.txt
	@echo "test passed"

clean:
	rm -rf $(BUILD)

-include $(OBJS:.o=.d)
```

- **`CC`, `CFLAGS`, `CPPFLAGS`.** Общепринятые имена переменных для компилятора, его опций и опций препроцессора. Встроенные правила make используют те же имена, и пользователь может переопределить любую из них в командной строке (`make CC=gcc CFLAGS=-O0`), не правя файл.
- **`SRCS := $(sort $(wildcard src/*.c))`.** Все файлы на C в `src/`, отсортированные, чтобы список, а с ним и порядок компоновки, был одинаковым на любой файловой системе. `:=` раскрывает правую часть один раз, когда строка прочитана; `=` раскрывал бы её заново при каждом использовании.
- **`OBJS := $(SRCS:src/%.c=$(BUILD)/%.o)`.** Ссылка с подстановкой: каждый `src/name.c` становится `build/name.o`. Добавление исходного файла добавляет объектный файл, не трогая Makefile.
- **`.PHONY: all test clean`.** Эти три — действия, а не файлы, и всегда выполняются, когда их просят.
- **`all: $(BUILD)/calc`.** Первая цель — цель по умолчанию, поэтому `make` без аргументов означает `make all`.
- **`$(BUILD)/calc: $(OBJS)` и её рецепт.** Компоновка. `$@` — цель, `$^` — все зависимости, так что рецепт — `cc -o build/calc build/eval.o build/main.o build/parse.o`. Строка рецепта начинается с табуляции.
- **`$(BUILD)/%.o: src/%.c | $(BUILD)`.** Шаблонное правило: любой `build/X.o` делается из `src/X.c`. `$<` — первая зависимость. `| $(BUILD)` — зависимость только для порядка (order-only prerequisite): каталог должен существовать до компиляции, но более новое время каталога, которое меняется при каждом добавлении в него файла, не должно делать устаревшими все объектные файлы.
- **`$(BUILD):`.** Создаёт выходной каталог.
- **`test`.** Зависит от программы, поэтому `make test` сначала её собирает; рецепт сравнивает её вывод с ожидаемым, и при различии `diff`, а с ним и make, завершается с ошибкой. `@` скрывает саму команду echo и печатает только её вывод.
- **`clean`.** Удаляет все результаты; `rm -rf` завершается успешно, даже если удалять нечего.
- **`-include $(OBJS:.o=.d)`.** Читает файлы зависимостей, которые компилятор записал с `-MMD -MP`. `-` игнорирует файлы, которых ещё нет, как при первой сборке.
