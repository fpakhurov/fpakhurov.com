## Отправная точка: скрипт, который запускает контейнеры на машинах \{#baseline-a-script-that-starts-containers-on-machines\}

При трёх машинах и [образе](/ru/notes/devops/container-images) в реестре первое развёртывание — скрипт: `ssh node1 docker run -d registry.example.com/web:1.4.2`, то же на `node2` и список адресов для балансировщика нагрузки. Он ломается пятью способами:

1. **Размещение вручную.** Скрипт решает, какой контейнер куда идёт, не зная, насколько заполнена каждая машина.
2. **Никто не следит.** Когда контейнер падает или машина умирает, сервис работает с меньшим числом копий, пока это не заметит человек.
3. **Развёртывания — это циклы.** Замена версии 1.4.2 на 1.4.3 означает цикл по машинам со своей обработкой ошибок, а сбой на полпути оставляет смесь.
4. **Адреса переезжают.** Каждый перезапущенный контейнер может получить новый адрес, и список балансировщика устаревает.
5. **Ресурсы не учитываются.** Один контейнер с утечкой памяти утягивает за собой соседей на той же машине.

## Желаемое состояние и цикл управления \{#desired-state-and-the-control-loop\}

<aside class="callout"><strong>Ключевая идея.</strong> В Kubernetes никто не отдаёт команд вроде «запусти три контейнера». Пользователь сохраняет в одном API **объекты**, которые описывают, что должно существовать, у каждого из которых есть `spec` (желаемое состояние, desired state) и `status` (наблюдаемое состояние). Множество независимых **контроллеров** (controllers) следят каждый за одним видом объектов и бесконечно выполняют один и тот же цикл, который называется **согласованием** (reconciliation): наблюдать фактическое состояние, сравнивать его со spec, действовать так, чтобы уменьшить разницу, и записывать увиденное в status. Цикл **срабатывает по уровню** (level-triggered): он реагирует на разницу между состояниями, а не на события, которые её вызвали, поэтому контроллер, который перезапустился, пропустил событие или увидел два изменения сразу, всё равно сходится к правильному состоянию.</aside>

Термостат — классический цикл управления: он не помнит, что кто-то открыл окно; он измеряет температуру, сравнивает её с уставкой и греет или не греет. Этот подход пришёл из кластерных менеджеров Google Borg и Omega ([Verma et al., 2015](#references); [Burns et al., 2016](#references)), и он объясняет всё остальное в Kubernetes: каждая возможность — это вид объекта плюс контроллер, который приводит мир в соответствие с ним.

## Кластер: API-сервер, etcd, контроллеры, планировщик, kubelet \{#the-cluster-the-api-server-etcd-controllers-the-scheduler-the-kubelet\}

У кластера есть **управляющий слой** (control plane), обычно на трёх выделенных машинах (или запущенный облачным провайдером как управляемый сервис), и **узлы** (nodes) — машины, на которых работают контейнеры.

- **API-сервер** — единственная точка входа. Он аутентифицирует каждый запрос, проверяет права (управление доступом на основе ролей, RBAC), выполняет проверки **допуска** (admission), которые проверяют или изменяют объекты, и сохраняет их. Клиенты и компоненты могут **наблюдать** (watch) за видом объектов: они получают поток изменений вместо опроса.
- **etcd** — база данных за API-сервером, хранилище «ключ — значение», которое поддерживает согласованность нескольких реплик по протоколу консенсуса Raft. Запись успешна, когда её сохранило большинство участников, **кворум**: $\lfloor n/2 \rfloor + 1$ из $n$. Три участника переживают потерю одного (остаются $2$ из $3$), пять — двух; четыре переживают потерю только одного, как и три, поэтому размеры нечётные. С etcd говорит только API-сервер.
- **Менеджер контроллеров** (controller manager) запускает встроенные контроллеры: для Deployment, ReplicaSet, узлов, заданий, конечных точек и ещё десятков объектов. Каждый из них — цикл по своему виду объектов.
- **Планировщик** (scheduler) следит за подами, у которых ещё нет узла. Для каждого он **отфильтровывает** узлы, которые могут его запустить (достаточно незарезервированных CPU и памяти, выполнены ограничения), **оценивает** оставшиеся (распределение копий, плотная упаковка, предпочтения) и записывает выбранный узел в под: это **привязка** (binding).
- **kubelet**, агент на каждом узле, следит за подами, привязанными к его узлу, просит **среду выполнения контейнеров** (containerd или CRI-O, через Container Runtime Interface) создать их контейнеры, выполняет их пробы здоровья и сообщает их статус.
- **kube-proxy** или замена на основе eBPF программирует фильтрацию пакетов на каждом узле так, чтобы виртуальные адреса Service доходили до подов.

Ни один компонент не вызывает другой. Каждый читает объекты из API-сервера и записывает туда результаты, поэтому любой компонент может перезапуститься незаметно для остальных, а каждое промежуточное состояние можно посмотреть через `kubectl get`.

<ReconcileLoop />

1. `kubectl apply` отправляет Deployment API-серверу, который проверяет его и сохраняет в etcd.
2. Контроллер Deployment видит Deployment без ReplicaSet и создаёт его.
3. Контроллер ReplicaSet видит 0 подов из 3 и создаёт 3 пода без узла.
4. Планировщик видит поды без узла, выбирает узел для каждого и записывает привязку.
5. kubelet каждого узла видит привязанные к нему поды и просит среду выполнения запустить их контейнеры.
6. Агенты kubelet сообщают статус. Контроллеры снова сравнивают status со spec; если под позже умрёт, контроллер ReplicaSet увидит два пода там, где должно быть три, и создаст новый, и тот же путь повторится.

## Объекты: поды, ReplicaSet, Deployment, Service, пространства имён \{#objects-pods-replicasets-deployments-services-namespaces\}

**Под** (Pod) — единица, которую планирует Kubernetes: один или несколько контейнеров, которые работают вместе на одном узле и делят сетевое пространство имён, а значит, один IP-адрес и `localhost` между собой, и могут делить тома. Изоляцию обеспечивают [пространства имён и cgroups](/ru/notes/acos/virtual-machines-and-containers#containers-one-kernel-many-views) из курса о системах. Обычно в поде один контейнер приложения, иногда плюс вспомогательный рядом с ним (*sidecar*, например прокси или отправитель журналов). Под смертен: когда его узел отказывает, его не переносят; контроллер создаёт новый под, с новым именем и новым адресом, где-то в другом месте.

**Метки** (labels) — пары «ключ — значение» на любом объекте, например `app: web` или `tier: frontend`, а **селекторы** (selectors) выбирают множества объектов по меткам. Они — клей Kubernetes: ReplicaSet владеет подами, которые подходят под его селектор, а Service отправляет трафик подам, которые подходят под его селектор. Никто не хранит список имён подов, поэтому поды могут свободно появляться и исчезать.

**ReplicaSet** поддерживает работу заданного числа подов, подходящих под его селектор, создавая их по шаблону пода. **Deployment** управляет объектами ReplicaSet: по одному на каждую версию шаблона. Изменение шаблона, например образа, создаёт новый ReplicaSet и переносит реплики из старого в новый; старые ReplicaSet остаются, уменьшенные до нуля, как история, к которой возвращается откат. Пользователи создают Deployment и почти никогда не трогают ReplicaSet напрямую.

`kubectl` умеет строить Deployment без кластера:

```console
$ kubectl create deployment web --image=registry.example.com/web:1.4.2 --replicas=3 --port=8080 --dry-run=client -o yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: null
  labels:
    app: web
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy: {}
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: web
    spec:
      containers:
      - image: registry.example.com/web:1.4.2
        name: web
        ports:
        - containerPort: 8080
        resources: {}
status: {}
```

Вся идея — в этой структуре в миниатюре. `spec.replicas` и `spec.template` — желаемое состояние; `spec.selector` говорит, какие поды учитываются; метки шаблона, `app: web`, подходят под этот селектор, так что поды, которые создаёт Deployment, — именно те, которые он считает. `status: {}` пуст, потому что ни один контроллер ещё ничего не наблюдал: в кластере контроллер Deployment заполнил бы его числами реплик, которые существуют, обновлены и доступны. Пустые поля вроде `strategy: {}` и `resources: {}` принимают значения по умолчанию или означают «ничего»; раздел «Пример» их заполняет.

**Service** даёт множеству подов одно стабильное имя и один виртуальный адрес. Его селектор выбирает поды; контроллер **EndpointSlice** поддерживает список адресов тех из них, которые *готовы*; а kube-proxy на каждом узле превращает соединения с адресом Service в соединения с одним из этих подов. Внутри кластера Service `web` в пространстве имён `shop` доступен через DNS как `web.shop.svc.cluster.local` или просто `web` из того же пространства имён. Тип `ClusterIP` (по умолчанию) доступен только внутри кластера; `NodePort` открывает порт на каждом узле; `LoadBalancer` запрашивает у облачного провайдера балансировщик нагрузки из [предыдущей заметки](/ru/notes/devops/cloud-building-blocks#networks-vpc-subnets-security-groups) перед этими портами. Маршрутизация HTTP по хосту и пути — тема [следующей заметки](/ru/notes/devops/kubernetes-in-practice).

**Пространство имён** (namespace) — область видимости для имён (у двух команд может быть по Deployment `web`) и единица, к которой привязываются правила доступа и квоты ресурсов. Само по себе оно не граница безопасности: без сетевых политик поды из разных пространств имён могут обращаться друг к другу.

## Как происходит выкатка, контроллер за контроллером \{#how-a-rollout-happens-controller-by-controller\}

[Заметка о доставке](/ru/notes/devops/continuous-delivery#rolling-update) выбрала поэтапное обновление как стратегию. Вот что делают контроллеры, когда меняется образ Deployment с `replicas: 4` и значениями по умолчанию `maxSurge: 25%` и `maxUnavailable: 25%`.

1. `kubectl apply` сохраняет Deployment с новым образом. Его шаблон изменился, поэтому изменился и хеш шаблона: контроллер Deployment помечает каждый ReplicaSet меткой `pod-template-hash` шаблона, по которому тот создан.
2. Ни у одного ReplicaSet нет нового хеша, поэтому контроллер создаёт ReplicaSet с 0 реплик.
3. Он вычисляет границы. `maxSurge` округляется вверх, а `maxUnavailable` — вниз: $\lceil 0.25 \times 4 \rceil = 1$ и $\lfloor 0.25 \times 4 \rfloor = 1$. Значит, одновременно может существовать не больше $4 + 1 = 5$ подов, а **доступными** должны быть не меньше $4 - 1 = 3$: готовыми, причём не меньше `minReadySeconds` (по умолчанию 0).
4. На каждом проходе контроллер либо увеличивает новый ReplicaSet настолько, насколько позволяет превышение (surge), либо уменьшает старый настолько, насколько позволяет доступность. Под новой версии считается доступным только после того, как проходит его проба готовности, о чём сообщает kubelet.
5. Когда старый ReplicaSet доходит до 0, а каждый новый под доступен, выкатка завершена. Старый ReplicaSet остаётся с 0 реплик; `kubectl rollout undo` снова увеличивает его той же процедурой.

**Разобранный пример.** Скрипт, который повторяет арифметику контроллера, при условии что каждый новый под становится готовым через один проход после запуска:

```python
import math

# Арифметика контроллера Deployment при поэтапном обновлении (apps/v1).
# Каждый проход — одна синхронизация контроллера: он увеличивает новый ReplicaSet, если может,
# а иначе уменьшает старый. Новые поды проходят пробу готовности через один проход после запуска.
replicas = 4
max_surge = math.ceil(0.25 * replicas)          # 25%, с округлением вверх
max_unavailable = math.floor(0.25 * replicas)   # 25%, с округлением вниз
min_available = replicas - max_unavailable

old, new, new_ready, started = replicas, 0, 0, 0
print("pass  action          old  new  new ready  pods  available")
print(f"{0:>4}  {'':15} {old:>3} {new:>4} {new_ready:>10} {old + new:>5} {old + new_ready:>10}")
for step in range(1, 20):
    new_ready = started                          # поды, запущенные на одном из прошлых проходов, уже готовы
    up = min(replicas, new + max(0, replicas + max_surge - (old + new))) - new
    if up > 0:
        new += up
        action = f"new +{up}"
    else:
        down = max(0, min(old, (old + new) - min_available - (new - new_ready)))
        old -= down
        action = f"old -{down}" if down else "done"
    started = new
    print(f"{step:>4}  {action:15} {old:>3} {new:>4} {new_ready:>10} {old + new:>5} {old + new_ready:>10}")
    if old == 0 and new_ready == replicas:
        break
print("maxSurge", max_surge, "maxUnavailable", max_unavailable, "minAvailable", min_available)
```

```console
$ python3.14 rollout.py
pass  action          old  new  new ready  pods  available
   0                    4    0          0     4          4
   1  new +1            4    1          0     5          4
   2  old -2            2    1          1     3          3
   3  new +2            2    3          1     5          3
   4  old -2            0    3          3     3          3
   5  new +1            0    4          3     4          3
   6  done              0    4          4     4          4
maxSurge 1 maxUnavailable 1 minAvailable 3
```

Прочитаем уменьшение на проходе 2: подов 5, доступными должны остаться не меньше 3, а новый под уже готов, поэтому могут уйти $5 - 3 - 0 = 2$ старых пода. На проходе 4 то же правило убирает два последних старых пода, потому что два новых пода, запущенные на проходе 3, к этому времени готовы. Число подов никогда не превышает 5, а число доступных подов никогда не падает ниже 3 — это две границы из шага 3. Если новая версия так и не становится готовой, выкатка останавливается, как только неготовые новые поды исчерпают бюджет: здесь после третьего прохода, с двумя неготовыми новыми подами и тремя старыми, которые продолжают обслуживать запросы, а через `progressDeadlineSeconds` (по умолчанию 600 с) Deployment сообщает, что не смог продвинуться. Сам Kubernetes не откатывается; это делает конвейер или человек.

## Планирование: запросы ресурсов и лимиты \{#scheduling-requests-and-limits\}

Каждый контейнер объявляет для каждого ресурса, что ему нужно и что он может использовать:

- **Запрос** (request) — то, что резервирует планировщик. Под помещается на узел, только если сумма запросов всех подов на узле, включая новый, остаётся в пределах **выделяемой** (allocatable) мощности узла (его размера минус то, что резервирует система). Запросы — не измерения: планировщик никогда не смотрит на фактическое использование.
- **Лимит** (limit) — то, что обеспечивает ядро, через [контрольные группы](/ru/notes/acos/virtual-machines-and-containers#control-groups-limits) из курса о системах. Лимит CPU становится квотой в `cpu.max`: контейнер, превысивший квоту, **притормаживается** (throttling), то есть ждёт следующего периода. Лимит памяти становится `memory.max`: контейнер, превысивший его, убивается механизмом OOM killer и перезапускается с кодом завершения 137.

CPU считают в ядрах и **миллиядрах** (millicores): `250m` — четверть ядра. Память считают в байтах, с `Mi` и `Gi` для степеней 1024.

**Разобранный пример.** Лимит CPU `500m` — это половина ядра. kubelet записывает его как `50000 100000` в `cpu.max` контейнера: 50 мс процессорного времени в каждые 100 мс периода — ровно та настройка, что в [эксперименте с cgroups](/ru/notes/acos/virtual-machines-and-containers#control-groups-limits) из курса о системах, где занятый цикл под таким лимитом получал $0.50$ процессора и притормаживался в каждом периоде. Лимит памяти `256Mi` становится $256 \times 2^{20} = 268{,}435{,}456$ байтами в `memory.max`. Запрос CPU `250m` становится относительным весом (`cpu.weight`): он важен только при конкуренции за CPU, когда контейнеры делят процессор пропорционально своим запросам.

**Разобранный пример.** У узла выделяемая мощность — 4 ядра и 16 GiB. Поды веб-сервиса запрашивают `500m` CPU и `1Gi` памяти. По CPU помещается $4{,}000 / 500 = 8$ подов, по памяти — $16 / 1 = 16$. Планировщик размещает не больше 8, даже если каждый на деле использует лишь `100m`, а девятый остаётся в состоянии `Pending` с событием о том, что ни на одном узле не хватает CPU. Слишком высокие запросы тратят машины впустую; слишком низкие набивают узел подами, которые затем конкурируют за CPU и память, которых нет.

Две настройки вместе дают каждому поду **класс качества обслуживания** (quality-of-service class): *Guaranteed*, когда запросы каждого контейнера равны его лимитам, *Burstable*, когда задан хоть какой-то запрос, *BestEffort*, когда не задано ничего. Когда на узле заканчивается память, kubelet вытесняет первыми поды BestEffort, а последними — Guaranteed. Распространённая практика — задавать лимит памяти равным запросу памяти (под не должен рассчитывать на память, которую не зарезервировал планировщик) и задавать запрос CPU без лимита CPU, потому что притормаживание добавляет задержку, даже когда на узле есть простаивающие ядра.

## Пробы: жив ли, готов ли, запустился ли \{#probes-is-it-alive-is-it-ready-has-it-started\}

kubelet проверяет каждый контейнер с помощью до трёх проб; каждая — HTTP-запрос, TCP-соединение, проверка здоровья gRPC или команда, выполняемая внутри контейнера.

- **Проба живости** (liveness probe): работает ли процесс вообще? Когда она проваливается `failureThreshold` раз подряд, kubelet убивает контейнер и запускает его снова. Она ловит взаимные блокировки и зависшие процессы, которые взгляд «упал или не упал» пропустил бы.
- **Проба готовности** (readiness probe): должен ли под сейчас получать трафик? Когда она проваливается, под убирается из конечных точек своих Service, но не перезапускается; когда она снова проходит, под возвращается. Именно эта проверка делает поэтапные обновления безопасными — форма [проверок здоровья](/ru/notes/devops/networking-for-services#load-balancers-l4-and-l7-algorithms-health-checks) балансировщика из заметки о сети в Kubernetes.
- **Проба запуска** (startup probe): закончило ли медленно запускающееся приложение запуск? Пока она не пройдёт, две другие не выполняются, так что проба живости не убивает приложение, которое ещё загружается.

По умолчанию проба выполняется каждые `periodSeconds: 10`, с таймаутом 1 с и `failureThreshold: 3`. С такими значениями зависший процесс перезапускается через время от $2 \times 10 + 1 = 21$ до $3 \times 10 + 1 = 31$ с, по той же арифметике, что и проверка здоровья балансировщика. Контейнер, который продолжает падать, перезапускается с растущими задержками — 10 с, 20 с, 40 с и так далее, до 5 минут, — что `kubectl get pods` показывает как `CrashLoopBackOff`.

Правило для пробы живости — правило из заметки о сети: проверяй процесс, а не его зависимости. Проба живости, которая обращается к базе данных, перезапускает каждый под сервиса, когда база медленная, и это делает сбой хуже и дольше. Проба готовности может учитывать, способен ли под делать полезную работу. Во время остановки kubelet отправляет `SIGTERM`, и одновременно под убирается из конечных точек Service; в течение следующих `terminationGracePeriodSeconds` (по умолчанию 30 с) приложение должно завершить текущие запросы и принять новые, которые приходят с опозданием, и лишь затем выйти; после окончания льготного периода kubelet отправляет `SIGKILL`.

| Проблема скрипта | Механизм | Компонент |
| --- | --- | --- |
| Размещение вручную | запросы ресурсов, фильтрация и оценка узлов | планировщик |

| Адреса переезжают | метки, селекторы, Service со стабильным именем и адресом, конечные точки готовых подов | контроллер EndpointSlice, kube-proxy |

## Ограничения \{#limitations\}

- Kubernetes согласован в конечном счёте (eventually consistent). Между изменением и его эффектом проходят несколько наблюдений и проходов, и какое-то время разные компоненты видят разные состояния: удаляемый под ещё может получить запрос, новый может ещё не попасть в конечные точки.
- Контроллер может сойтись только к возможному. Под, запрашивающий больше, чем есть у любого узла, навсегда остаётся в `Pending`, выкатка сломанного образа останавливается на полпути, и кластер сообщает о проблеме, не исправляя её.
- Запросы ресурсов — догадки, которые пишут люди. Слишком высокие тратят деньги, слишком низкие перегружают узлы, и они устаревают по мере изменения кода. Измерение фактического использования и подстройка — постоянная работа.
- Управляющий слой — сам по себе распределённая система: etcd нужны кворум, резервные копии и быстрые диски, а API-сервер могут перегрузить клиенты, запрашивающие списки больших коллекций. Управляемые сервисы снимают эту работу, но не её виды отказов.
- Эта заметка рассматривает сервисы без состояния. Конфигурация, хранение, маршрутизация снаружи, автомасштабирование и упаковка — в [следующей заметке](/ru/notes/devops/kubernetes-in-practice).

## Что нужно запомнить \{#what-you-should-remember\}

- У объектов есть spec (желаемое) и status (наблюдаемое). Контроллеры бесконечно повторяют цикл: наблюдать, сравнивать, действовать. Цикл срабатывает по уровню, поэтому сходится после пропущенных событий и перезапусков.
- С etcd говорит только API-сервер, и ни один компонент не вызывает другой: они наблюдают за объектами и записывают результаты. etcd нужно большинство, $\lfloor n/2 \rfloor + 1$ из $n$ участников.
- Под: контейнеры на одном узле, делящие сетевое пространство имён; смертен, его заменяют, а не переносят. Метки и селекторы связывают ReplicaSet и Service с подами. Deployment владеет одним ReplicaSet на каждую версию шаблона.
- Поэтапное обновление держит не больше `replicas + maxSurge` подов и не меньше `replicas - maxUnavailable` доступных, с округлением превышения вверх и недоступности вниз; что считается доступным, решает проба готовности.
- Запросы — то, что резервирует планировщик; лимиты — то, что обеспечивают cgroups: CPU сверх лимита притормаживается, память сверх лимита — это смерть контейнера (код 137).
- Проба живости перезапускает, проба готовности убирает из трафика, проба запуска защищает медленный старт. Проверяйте процесс, а не его зависимости.

## Пример \{#example\}

Deployment и Service для веб-сервиса, одним файлом из двух документов. Он написан по справочнику API Kubernetes 1.37 и разобран PyYAML; к кластеру здесь не применялся. При применении через `kubectl apply -f web.yaml` он напечатал бы по строке на объект, сообщив, что `deployment.apps/web` и `service/web` созданы.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
  labels:
    app: web
spec:
  replicas: 4
  revisionHistoryLimit: 5
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 256Mi
          startupProbe:
            httpGet:
              path: /healthz/live
              port: http
            periodSeconds: 2
            failureThreshold: 30
          livenessProbe:
            httpGet:
              path: /healthz/live
              port: http
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /healthz/ready
              port: http
            periodSeconds: 5
            failureThreshold: 2
          securityContext:
            runAsNonRoot: true
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: shop
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
```

- `apiVersion: apps/v1`, `kind: Deployment`: каждый объект называет свою группу API, версию и вид; Deployment живут в группе `apps`.
- `metadata.name` и `namespace`: объект — `shop/web`. Пространство имён должно существовать. Метка на самом Deployment нужна людям и инструментам; метки, важные для подов, находятся в шаблоне.
- `replicas: 4` — желаемое число подов. `revisionHistoryLimit: 5` хранит пять последних старых ReplicaSet с нулём реплик для откатов (по умолчанию 10).
- `selector.matchLabels: app: web` говорит, какие поды принадлежат Deployment; после создания его нельзя изменить, и он должен совпадать с `template.metadata.labels`, иначе API-сервер отвергнет объект.
- `strategy`: поэтапное обновление в границах разобранного примера: при 4 репликах не больше 5 подов и не меньше 3 доступных.
- `template` — полное описание пода, та часть, хеш которой даёт имя ReplicaSet. Изменение чего угодно в нём, образа или переменной окружения, запускает выкатку; изменение `replicas` — нет.
- `terminationGracePeriodSeconds: 30`: после `SIGTERM` у контейнера есть 30 с, чтобы завершить свои запросы до `SIGKILL`.
- `image`: тег ради читаемости. В продакшене [заметка об образах](/ru/notes/devops/container-images#registries-tags-and-digests) рекомендует дайджест, чтобы поды одного ReplicaSet не могли запустить разные сборки под одним и тем же тегом.
- `ports`: контейнер слушает 8080, и порт назван `http`, так что пробы и Service могут ссылаться на него по имени.
- `resources`: планировщик резервирует для каждого пода четверть ядра и 256 MiB; лимит памяти равен запросу, так что утечка убивает только этот контейнер; лимита CPU нет, так что контейнер может использовать простаивающий CPU узла. Под относится к классу Burstable.
- `startupProbe`: до $30 \times 2 = 60$ с на запуск приложения, прежде чем начнутся пробы живости.
- `livenessProbe`: `GET /healthz/live` каждые 10 с; три неудачи подряд перезапускают контейнер. Эта конечная точка должна сообщать только о том, что процесс работает.
- `readinessProbe`: `GET /healthz/ready` каждые 5 с; две неудачи выводят под из Service, пока он не восстановится. Эта конечная точка может проверять, способен ли под обслуживать запросы, например загрузил ли он свои данные.
- `securityContext`: отказаться запускаться, если образ будет работать от root ([заметка об образах](/ru/notes/devops/container-images#running-as-non-root) собрала его для работы от обычного пользователя), запретить получение привилегий через программы с setuid и смонтировать файловую систему образа только для чтения, чтобы атакующий внутри не мог изменить программу.
- Второй документ, после `---`, — это Service. `type: ClusterIP` даёт ему адрес только внутри кластера. `selector: app: web` выбирает те же поды, что и Deployment, и трафик получают только готовые из них. `port: 80` — порт Service, `targetPort: http` — именованный порт контейнеров, так что клиенты обращаются к `http://web.shop.svc.cluster.local/` и попадают на порт 8080 какого-нибудь готового пода.

## Дальше \{#next\}

Deployment выше ниоткуда не берёт конфигурацию, не хранит данных, доступен только изнутри кластера и запускает фиксированное число реплик. Настоящий сервис читает настройки и секреты, иногда хранит состояние, доступен из интернета по имени хоста и пути, масштабируется вслед за нагрузкой и устанавливается в несколько окружений по одному описанию. [Следующая заметка](/ru/notes/devops/kubernetes-in-practice) добавляет эти части: ConfigMap и Secret, тома, Ingress и Gateway API, автомасштабирование, Helm и Kustomize и GitOps.
