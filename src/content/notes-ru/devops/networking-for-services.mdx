## Отправная точка: один сервер с публичным адресом \{#baseline-one-server-with-a-public-address\}

Простейший сервис — одна виртуальная машина с публичным IP-адресом. Серверный процесс слушает порт 443, хранит сертификат TLS и его закрытый ключ, а пользователи обращаются к нему по адресу. Для демонстрации этого достаточно, но как только от сервиса начинают зависеть люди, он ломается пятью способами:

1. **Адрес — это машина.** Замена машины меняет адрес, и ломается каждый клиент, который его запомнил.
2. **Одна машина — один отказ.** Когда она падает или развёртывание перезапускает процесс, сервис недоступен. Когда нагрузка превышает то, что она может обслужить, замедляется каждый запрос.
3. **Секреты на каждом сервере.** Если серверов десять, а не один, закрытый ключ хранят десять машин, и обновление сертификата означает работу со всеми десятью.
4. **Сервер нельзя вывести мягко.** Ничто не говорит клиентам перестать слать запросы серверу, который вот-вот перезапустится.
5. **Расстояние стоит круговых обращений.** Пользователь в 2000 км платит не меньше 20 мс на распространение сигнала за каждое круговое обращение, а установка соединения требует нескольких таких обращений.

Остальная часть заметки отвечает на эти проблемы по порядку: имена (1), прокси и балансировщики нагрузки (2–4) и меньше круговых обращений (5).

<aside class="callout"><strong>Ключевая идея.</strong> Запрос проходит через цепочку участков, и каждый участок — это косвенность: клиент знает имя, имя указывает на прокси, прокси выбирает бэкенд. Каждый уровень за именем может меняться — его машины, версии и адреса, — и клиент этого не замечает, а каждый уровень может проверять здоровье следующего и обходить отказы. Платить за это приходится круговыми обращениями и кэшами, которые могут устареть, поэтому проектирование сети сервиса — в основном подсчёт круговых обращений и выбор того, как долго можно кэшировать каждый ответ.</aside>

1. **DNS.** Клиент спрашивает у рекурсивного резолвера адрес `www.example.com`; ответ из кэша приходит вместе со временем, в течение которого его ещё можно хранить.
2. **TCP.** Клиент открывает соединение с прокси: одно круговое обращение.
3. **TLS.** Клиент и прокси договариваются о ключах, и прокси доказывает, что владеет именем: ещё одно круговое обращение.
4. **HTTP.** Запрос доходит до прокси, который читает из него имя хоста и путь.
5. **Здоровье.** Прокси сам опрашивал свои бэкенды и знает, что `web2` не отвечает.
6. **Передача.** Прокси отправляет запрос здоровому бэкенду по соединению, которое открыл заранее, и ответ возвращается тем же путём.

## DNS: что контролирует эксплуатация \{#dns-what-an-operator-controls\}

Как резолвер проходит по дереву от корня до ответа, рассказано в [заметке о сетях](/ru/notes/acos/networking#dns-from-names-to-addresses). Эксплуатация видит DNS с другого конца: ей принадлежит **зона** (zone), например `example.com`; она публикует записи зоны на авторитетных серверах (обычно в управляемом сервисе DNS) и для каждой записи выбирает, как долго резолверы могут её кэшировать, — её **TTL** (time to live, время жизни в секундах).

| Запись | Сопоставляет имени | Типичное применение для сервиса |
| --- | --- | --- |
| `A`, `AAAA` | адрес IPv4 или IPv6 | адрес балансировщика нагрузки |
| `CNAME` | другое имя (псевдоним) | `www`, указывающий на имя балансировщика у провайдера |
| `NS` | авторитетные серверы зоны | делегирование `example.com` провайдеру DNS |
| `TXT` | произвольный текст | доказательство владения доменом для удостоверяющего центра |
| `CAA` | удостоверяющие центры, которым разрешено выпускать сертификаты для имени | отказ в сертификатах от любого другого центра |
| `HTTPS` | подсказки для соединения: протоколы, порты, адреса | объявление о том, что доступен HTTP/3 ([RFC 9460](#references)) |

**Разобранный пример.** Спросим публичный резолвер о `www.wikipedia.org`, а затем зададим тот же вопрос собственному серверу имён Wikimedia (`+norec` просит его не выполнять рекурсию; `+nocmd +nostats` убирают заголовок и строки со временем):

```console
$ dig +tcp +nocmd +nostats @1.1.1.1 www.wikipedia.org A
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 850
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;www.wikipedia.org.		IN	A

;; ANSWER SECTION:
www.wikipedia.org.	86331	IN	CNAME	dyna.wikimedia.org.
dyna.wikimedia.org.	111	IN	A	185.15.58.224
```

```console
$ dig +tcp +nocmd +nostats +norec @ns0.wikimedia.org www.wikipedia.org A
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 38118
;; flags: qr aa; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
...
;; ANSWER SECTION:
www.wikipedia.org.	86400	IN	CNAME	dyna.wikimedia.org.
$ dig +tcp +nocmd +nostats +norec @ns0.wikimedia.org dyna.wikimedia.org A
...
;; ANSWER SECTION:
dyna.wikimedia.org.	180	IN	A	185.15.58.224
```

(Строки `...` заменяют разделы OPT и вопроса, которые повторяют первый вывод.) Прочитаем вывод построчно:

- `status: NOERROR`: имя существует. Для несуществующего имени ответ — `NXDOMAIN`, и этот отрицательный ответ тоже кэшируется, на время, заданное в записи SOA зоны ([RFC 2308](#references)). Клиент, который запросил запись до её создания, может продолжать получать `NXDOMAIN` и после того, как она появилась.
- Флаги различаются. В ответе резолвера есть `rd ra` (рекурсия запрошена и доступна) и нет `aa`: это копия из кэша. В ответе авторитетного сервера есть `aa`, authoritative answer: он взят из самой зоны.
- `www.wikipedia.org` — это `CNAME`, псевдоним, для `dyna.wikimedia.org`, у которого есть запись `A`. Резолвер прошёл по псевдониму и вернул обе записи. Эксплуатация может перенести все псевдонимы сразу, изменив одно имя, на которое они указывают.
- Главное здесь — TTL. Зона задаёт 86 400 с (одни сутки) для псевдонима и 180 с для адреса. Резолвер показывает 86 331 и 111: он получил обе записи $86{,}400 - 86{,}331 = 180 - 111 = 69$ с назад и ведёт обратный отсчёт. Пока его копия не истекла, он отвечает из кэша и не обращается к Wikimedia. Псевдоним меняется редко и получает длинный TTL; адрес может измениться за минуты, например чтобы направить пользователей в другой центр обработки данных, и получает короткий.

**TTL — это компромисс.** Длинный TTL означает меньше запросов и более быстрые ответы, короткий — более быстрые изменения. Если имя кэшируют 10 000 резолверов, TTL 60 с приносит авторитетным серверам $10{,}000 / 60 \approx 167$ запросов в секунду, а TTL 3600 с — 2.8. Когда адрес нужно изменить, изменение доходит до клиентов только после того, как истечёт старый TTL. Поэтому миграция сначала уменьшает TTL: с 86 400 с до 300 с не позже чем за один старый TTL, то есть за сутки, до переключения, чтобы в каждом кэше уже лежала короткоживущая копия; после переключения клиенты, соблюдающие TTL, переходят на новый адрес в течение 300 с; затем TTL снова увеличивают. Некоторые клиенты хранят ответы дольше, чем позволяет TTL, поэтому старый адрес ещё какое-то время получает запросы.

`CNAME` не может соседствовать с другими записями для того же имени ([RFC 1034](#references), §3.6.2). Вершина зоны (apex), сам `example.com`, обязана нести записи `SOA` и `NS`, поэтому не может быть `CNAME`; провайдеры DNS предлагают нестандартную запись-«псевдоним» (alias, flattening), которая разрешает цель на их стороне и публикует обычные записи `A`.

## TCP и TLS 1.3: два круговых обращения до закрытого канала \{#tcp-and-tls-13-two-round-trips-to-a-private-channel\}

Теперь у клиента есть адрес. Он открывает TCP-соединение, одно круговое обращение [тройного рукопожатия](/ru/notes/acos/networking#tcp-a-reliable-byte-stream), и затем запускает поверх него **TLS**. TLS даёт три вещи: **конфиденциальность** (наблюдатель на пути видит шифротекст), **целостность** (изменённый байт обнаруживается) и **аутентификацию сервера** (клиент знает, что говорит с владельцем имени, а не с тем, кто ответил по этому адресу). Версия 1.3 ([RFC 8446](#references)) делает это за одно круговое обращение:

1. Клиент отправляет **ClientHello**: поддерживаемые версии и наборы шифров (cipher suites), свежую **долю ключа** (key share, эфемерный открытый ключ Диффи — Хеллмана, обычно на кривой X25519), **имя сервера**, которое ему нужно (**SNI**, [RFC 6066](#references)), и прикладные протоколы, на которых он говорит (**ALPN**, [RFC 7301](#references)), например `h2` и `http/1.1`.
2. Сервер отвечает **ServerHello**: выбранный набор шифров и свою долю ключа. Из двух долей обе стороны вычисляют один и тот же секрет, и всё после этого сообщения зашифровано.
3. В той же серии пакетов сервер отправляет **EncryptedExtensions** (среди них — свой выбор ALPN), цепочку сертификатов **Certificate**, **CertificateVerify** (подпись под всем рукопожатием до этого момента, сделанную закрытым ключом сертификата) и сообщение **Finished** (MAC от рукопожатия).
4. Клиент проверяет сертификат и подпись, отправляет свой Finished и может в том же пакете отправить HTTP-запрос.

TLS 1.2 требовалось для той же работы два круговых обращения. Поскольку ключи эфемерные, украденный ключ сертификата не расшифровывает записи прошлых сеансов (прямая секретность, forward secrecy).

**Разобранный пример.** `curl -v` печатает каждое сообщение рукопожатия. Первая часть его вывода для Wikipedia:

```console
$ curl -sv -o /dev/null https://www.wikipedia.org/

* IPv6: 2a02:ec80:600:ed1a::1
* IPv4: 185.15.58.224
*   Trying 185.15.58.224:443...
* Connected to www.wikipedia.org (185.15.58.224) port 443
* ALPN: curl offers h2,http/1.1
* (304) (OUT), TLS handshake, Client hello (1):
} [322 bytes data]
*  CAfile: /etc/ssl/cert.pem
*  CApath: none
* (304) (IN), TLS handshake, Server hello (2):
{ [122 bytes data]
* (304) (IN), TLS handshake, Unknown (8):
{ [19 bytes data]
* (304) (IN), TLS handshake, Certificate (11):
{ [4143 bytes data]
* (304) (IN), TLS handshake, CERT verify (15):
{ [79 bytes data]
* (304) (IN), TLS handshake, Finished (20):
{ [36 bytes data]
* (304) (OUT), TLS handshake, Finished (20):
} [36 bytes data]
* SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256 / [blank] / UNDEF
* ALPN: server accepted h2

*  subject: CN=*.wikipedia.org
*  start date: Oct  4 18:34:51 2026 GMT
*  expire date: Jan  2 18:34:50 2027 GMT

*  issuer: C=US; O=Let's Encrypt; CN=YE2

```

- Имя разрешилось в адрес IPv6 и адрес IPv4; curl подключился по IPv4.
- `ALPN: curl offers h2,http/1.1`: список протоколов клиента, который передаётся в ClientHello.
- `(304)` — версия TLS на проводе, `0x0304`, что означает 1.3. Числа в скобках после имени каждого сообщения — типы сообщений из RFC 8446: ClientHello — 1, ServerHello — 2, EncryptedExtensions — 8 (эта сборка curl печатает его как `Unknown`), Certificate — 11, CertificateVerify — 15, Finished — 20. Порядок в точности соответствует четырём шагам выше: одно сообщение наружу, пять внутрь, одно наружу.
- Сообщение с сертификатом самое большое, 4143 байта: в нём цепочка, а не один сертификат.
- `CAfile: /etc/ssl/cert.pem` — **хранилище доверенных сертификатов** (trust store), корневые сертификаты, которые принимает эта машина.
- `server accepted h2`: сервер выбрал HTTP/2 из списка клиента, внутри зашифрованной части рукопожатия.
- Сертификат действителен 90 дней, с 4 октября 2026 года по 2 января 2027 года, выпущен для `*.wikipedia.org`, и запрошенное имя ему соответствует. Шаблонный сертификат (wildcard) покрывает ровно одну метку: `www.wikipedia.org`, но не `wikipedia.org` и не `a.b.wikipedia.org`.

### Сертификаты и цепочки \{#certificates-and-chains\}

Сертификат ([X.509, RFC 5280](#references)) связывает открытый ключ с именами, а **удостоверяющий центр** (certificate authority, CA) подписывает эту связь. Браузеры и операционные системы поставляются с хранилищем корневых центров, их больше сотни. Корневой центр не подписывает сертификаты серверов напрямую; он подписывает промежуточные, которые подписывают сертификаты серверов, и сервер отправляет свой сертификат вместе с промежуточными. OpenSSL показывает, что отправляет Wikipedia:

```console
$ openssl s_client -connect www.wikipedia.org:443 -servername www.wikipedia.org </dev/null 2>/dev/null | grep -E '^ [0-9] s:|^   i:'
 0 s:CN=*.wikipedia.org
   i:C=US, O=Let's Encrypt, CN=YE2
 1 s:C=US, O=Let's Encrypt, CN=YE2
   i:C=US, O=ISRG, CN=Root YE
 2 s:C=US, O=ISRG, CN=Root YE
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X2
 3 s:C=US, O=Internet Security Research Group, CN=ISRG Root X2
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X1
```

Каждое `s:` — субъект (subject) сертификата, `i:` под ним — его издатель (issuer), и каждый издатель — субъект следующей записи. Клиент поднимается по цепочке, проверяет каждую подпись ключом издателя, проверяет сроки действия и имя и останавливается на сертификате из своего хранилища доверенных сертификатов. Две последние записи — **перекрёстные подписи** (cross-signatures): новые корни, подписанные старыми, чтобы клиент, в хранилище которого есть только старый корень, всё равно нашёл путь.

Сертификаты истекают, и истёкший сертификат кладёт сервис так же надёжно, как падение процесса. С марта 2026 года CA/Browser Forum разрешает публично доверенным сертификатам действовать не дольше 200 дней, с марта 2027 года — 100 дней, а с марта 2029 года — 47 дней ([CA/Browser Forum, ballot SC-081](#references)). При таких сроках продление должно быть автоматическим: протокол **ACME** ([RFC 8555](#references)) позволяет серверу доказать контроль над именем (отдав токен по HTTP или опубликовав запись `TXT`) и получить новый сертификат без участия человека.

### SNI: много имён на одном адресе \{#sni-many-names-on-one-address\}

Wikimedia обслуживает десятки сайтов с одних и тех же адресов, и многие сервисы делят один балансировщик нагрузки. Сервер должен выбрать правильный сертификат ещё до того, как появится какое-либо шифрование, поэтому ClientHello называет хост открытым текстом: это и есть SNI, опция `-servername` выше. Прокси может и маршрутизировать по одному только SNI, не расшифровывая трафик (**сквозная передача** TLS, passthrough), и тогда ключ остаётся на бэкенде. Сертификат Wikimedia перечисляет 41 имя в альтернативных именах субъекта (subject alternative names), так что один сертификат обслуживает их все. Поскольку SNI виден любому на пути, расширение Encrypted Client Hello (ECH) шифрует его ключом, опубликованным в DNS; его внедряют браузеры и крупные провайдеры, но в 2026 году оно далеко не повсеместно.

**Возобновление и 0-RTT.** Клиент, который уже общался с сервером, может возобновить сеанс с ключом из предыдущего сеанса и отправить первый запрос в самой первой серии пакетов — это данные **0-RTT**. Цена в том, что атакующий может повторить эту первую серию, поэтому серверы принимают 0-RTT только для запросов, которые безопасно повторять, например `GET` без побочных эффектов ([RFC 8446](#references), §8).

## HTTP/1.1, HTTP/2 и HTTP/3 вкратце \{#http11-http2-and-http3-in-brief\}

Семантика HTTP — методы, коды состояния и заголовки — одна и та же во всех трёх версиях ([RFC 9110](#references)). Меняется то, как передаются запросы.

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| Транспорт | TCP, обычно с TLS | TCP с TLS | QUIC поверх UDP, TLS 1.3 внутри |
| Запросы в одном соединении | по одному | много потоков вперемешку | много независимых потоков |
| Потерянный пакет задерживает | это соединение | каждый поток в нём | только свой поток |
| Круговых обращений до первого запроса | 2 (TCP, TLS) | 2 (TCP, TLS) | 1, или 0 при возобновлении |
| Заголовки | текст | двоичные, сжатые (HPACK) | двоичные, сжатые (QPACK) |
| Как клиент узнаёт о доступности | по умолчанию | ALPN в рукопожатии TLS | заголовок `Alt-Svc` или запись `HTTPS` |

HTTP/1.1 ([RFC 9112](#references)) отправляет по соединению один запрос за раз, поэтому браузеры открывают к хосту несколько соединений. HTTP/2 ([RFC 9113](#references)) режет запросы на кадры в пронумерованных потоках и перемежает многие из них в одном TCP-соединении; цена в том, что TCP доставляет байты по порядку, поэтому один потерянный сегмент задерживает все потоки, пока его не передадут повторно. HTTP/3 ([RFC 9114](#references)) работает поверх **QUIC** ([RFC 9000](#references)) — транспорта в пространстве пользователя поверх UDP, который держит потоки независимыми, объединяет своё рукопожатие с TLS 1.3 в одно круговое обращение и опознаёт соединение по идентификатору, а не по адресам, так что телефон, переходящий с Wi-Fi на мобильные данные, сохраняет соединение. Клиент сначала приходит на сайт по TCP и узнаёт об HTTP/3 из заголовка; `example.com` его отправляет:

```console
$ curl -sI https://example.com/ | grep -iE '^(HTTP|server|alt-svc)'
HTTP/2 200 
server: cloudflare
alt-svc: h3=":443"; ma=86400
```

`h3=":443"` говорит, что HTTP/3 обслуживается на UDP-порту 443 того же хоста, а `ma=86400` — что клиент может помнить это сутки ([RFC 7838](#references)). Сети, блокирующие UDP, существуют, поэтому клиенты откатываются на TCP.

Для балансировки нагрузки важна вторая строка. Клиент HTTP/2 отправляет все свои запросы по одному долгоживущему соединению. Балансировщик, выбирающий бэкенд для каждого соединения, отправляет все запросы этого клиента на один бэкенд, сколько бы бэкендов ни было.

## Обратные прокси: одна входная дверь для многих бэкендов \{#reverse-proxies-one-front-door-for-many-backends\}

**Обратный прокси** (reverse proxy) принимает соединения от имени серверов: для клиента он и есть сервер, и каждый запрос он передаёт выбранному им бэкенду. (Прямой прокси, forward proxy, — зеркальный случай: он действует от имени клиентов.) Он решает проблемы 2–4 отправной точки и попутно выполняет ещё несколько задач:

- **Терминирование TLS** (TLS termination). Сертификаты и ключи хранятся только на прокси; бэкенды говорят на обычном HTTP внутри частной сети или используют отдельный внутренний TLS.
- **Маршрутизация.** По имени хоста и пути: `/api` — в один пул бэкендов, `/static` — в другой, новая версия — на 5% запросов.
- **Буферизация.** Прокси целиком читает запрос медленного клиента, прежде чем передать его дальше, и принимает ответ со скоростью бэкенда, так что процесс бэкенда не занят секундами из-за телефона в слабой сети.
- **Кэширование и сжатие.** Ответ, который запрашивают многие пользователи, можно отдать из кэша прокси.
- **Сведения о клиенте.** Бэкенд видит адрес прокси, а не клиента, поэтому прокси добавляет адрес клиента в заголовок `Forwarded` или `X-Forwarded-For` ([RFC 7239](#references)). Бэкенд должен доверять этому заголовку, только если он пришёл от его собственных прокси, ведь отправить его может кто угодно.
- **Ограничения.** Таймауты для медленных клиентов, ограничения размера запроса и частоты запросов не дают одному клиенту занять весь сервис.

**Разобранный пример.** Заголовки ответа на тот же запрос к Wikipedia показывают, кто на него ответил (выбраны отдельные строки, остальная часть ответа обрезана):

```console
< HTTP/2 200 
< date: Thu, 22 Oct 2026 08:01:28 GMT
< cache-control: s-maxage=86400, must-revalidate, max-age=3600
< server: ATS/9.2.15
< age: 62975
< x-cache: cp6016 miss, cp6002 hit/753406
< x-cache-status: hit-front
```

- `age: 62975`: ответ пришёл из кэша, который держит его 62 975 с, 17.5 часа ([RFC 9111](#references)). `date` — момент, когда ответ был сформирован: 08:01:28 плюс 62 975 с — это 01:31:03 следующего дня, момент отправки запроса.
- `cache-control`: общие кэши (`s-maxage`) могут хранить ответ сутки, браузер (`max-age`) — час.
- `x-cache` называет два кэширующих сервера уровня доставки контента, а `x-cache-status: hit-front` говорит, что копия была у переднего из них. Ни один сервер приложений над этим запросом вообще не работал; `server` называет Apache Traffic Server, кэширующий прокси этого уровня.

## Балансировщики нагрузки: L4 и L7, алгоритмы, проверки здоровья \{#load-balancers-l4-and-l7-algorithms-health-checks\}

Балансировщик нагрузки (load balancer) — это прокси, главная задача которого — распределять запросы по бэкендам. Номера уровней — уровни модели OSI из [заметки о сетях](/ru/notes/acos/networking#layers-who-solves-which-problem).

- Балансировщик **L4** (транспортного уровня) видит адреса и порты. Он пересылает пакеты или сшивает TCP-соединения и выбирает бэкенд один раз на соединение, часто по хешу пятёрки параметров соединения. Он быстр, может пропускать TLS нетронутым и ничего не знает о запросах: нет маршрутизации по пути, нет повторов неудавшегося запроса, и есть описанный выше перекос из-за HTTP/2.
- Балансировщик **L7** (прикладного уровня) терминирует TCP и TLS, разбирает HTTP и выбирает бэкенд для каждого запроса. Он может маршрутизировать, повторять запросы, добавлять заголовки и измерять задержку и статус каждого запроса; платит он за это процессорным временем на TLS и разбор и должен хранить сертификаты.

Крупные сервисы ставят их друг за другом: слой L4 распределяет соединения по парку прокси L7, а те распределяют запросы по бэкендам ([Eisenbud et al., 2016](#references); [Beyer et al., 2016](#references), гл. 19–20).

**Алгоритмы.** *Циклический перебор* (round robin) отправляет запрос $k$ на бэкенд $k \bmod N$, с весами для неравных машин; он не учитывает, что одни запросы медленнее других. *Наименьшее число соединений* (least connections, или наименьшее число незавершённых запросов) отправляет каждый запрос на бэкенд с наименьшим числом выполняемых запросов, что следует за реальной нагрузкой. Проверять каждый бэкенд в большом пуле дорого, а выбор двух случайных бэкендов и отправка запроса менее загруженному из них — *сила двух случайных выборов* (power of two choices) — работает почти так же хорошо ([Mitzenmacher, 2001](#references)). *Хеширование* отправляет один и тот же ключ, например идентификатор пользователя, на один и тот же бэкенд, что сохраняет кэш бэкенда тёплым для его пользователей. Простое хеширование по модулю $N$ перемещает почти каждый ключ, когда меняется $N$, и это разом опустошает все эти кэши; *согласованное хеширование* (consistent hashing, [Karger et al., 1997](#references)) размещает бэкенды во многих точках кольца значений хеша и отдаёт каждый ключ следующей точке по часовой стрелке, так что добавление бэкенда перемещает только те ключи, которые забирает новый бэкенд. Скрипт сравнивает два способа на 100 000 ключей при переходе с четырёх бэкендов на пять:

```python
import bisect, hashlib

def h(s):                                   # 64-битный хеш строки
    return int.from_bytes(hashlib.sha256(s.encode()).digest()[:8], "big")

keys = [f"user-{i}" for i in range(100_000)]

# Хеширование по модулю N: бэкенд ключа — h(key) % N
moved = sum(h(k) % 4 != h(k) % 5 for k in keys)
print(f"mod N, 4 -> 5 backends: {moved / len(keys):.1%} of keys move")

# Согласованное хеширование: каждому бэкенду принадлежат 100 точек на кольце значений хеша,
# а ключ принадлежит первой точке по часовой стрелке от h(key)
def ring(n):
    return sorted((h(f"web{b}#{p}"), b) for b in range(n) for p in range(100))

def owner(r, key):
    return r[bisect.bisect(r, (h(key),)) % len(r)][1]

r4, r5 = ring(4), ring(5)
moved = sum(owner(r4, k) != owner(r5, k) for k in keys)
print(f"ring, 4 -> 5 backends: {moved / len(keys):.1%} of keys move")
```

```console
$ python3.14 hashing.py
mod N, 4 -> 5 backends: 79.9% of keys move
ring, 4 -> 5 backends: 20.2% of keys move
```

Идеал — $1/5 = 20\,\%$, доля нового бэкенда, и кольцо отличается от него меньше чем на процент. При хешировании по модулю ключ остаётся на месте, только когда $k \bmod N = k \bmod (N+1)$, что выполняется для $N$ из каждых $N(N+1)$ последовательных целых чисел, так что перемещается доля ключей $1 - 1/(N+1)$: здесь $4/5$.

**Проверки здоровья** (health checks). Балансировщик должен перестать отправлять запросы бэкенду, который не может их обслужить. **Активная** проверка опрашивает каждый бэкенд по расписанию, например `GET /healthz` каждые 5 с с таймаутом 2 с; после `fall` неудач подряд бэкенд помечается неработающим, после `rise` успехов подряд он возвращается. **Пассивная** проверка (обнаружение выбросов, outlier detection) следит за реальным трафиком и исключает бэкенд, скажем, после пяти ошибок подряд.

**Разобранный пример.** Интервал 5 с, таймаут 2 с, `fall` 3. Бэкенд умирает в момент 0. Следующая проверка начинается в течение 5 с и завершается неудачей через 2 с; третья неудача наступает через два интервала после первой. Бэкенд помечается неработающим через время от $2 \cdot 5 + 2 = 12$ до $3 \cdot 5 + 2 = 17$ с после смерти. При 200 запросах в секунду, распределённых по четырём бэкендам, он получает в это время 50 запросов в секунду, до $17 \times 50 = 850$ неудавшихся запросов, если балансировщик не повторяет их на других бэкендах. Пассивная проверка, исключающая бэкенд после пяти ошибок подряд, реагирует через $5 / 50 = 0.1$ с. Балансировщики используют обе: пассивные проверки быстро реагируют на реальные отказы, активные замечают, что простаивающий или исключённый бэкенд восстановился.

Проверка здоровья должна проверять, может ли обслуживать запросы *этот* процесс, а не всё, что стоит за ним. Проверка, которая заодно обращается к базе данных, помечает неработающими все бэкенды сразу, когда база медленная, и превращает медленный сервис в отсутствующий. Kubernetes делает то же различие между пробами готовности и живости, в [заметке о Kubernetes](/ru/notes/devops/kubernetes).

**Плавный вывод из ротации** (draining). Прежде чем остановить бэкенд для развёртывания, его сначала выводят из ротации: балансировщик не отправляет ему новых запросов и даёт завершиться текущим, и только затем процесс останавливают. Книга SRE называет это состоянием *хромой утки* (lame duck): бэкенд ещё отвечает, но просит не давать ему новой работы ([Beyer et al., 2016](#references), гл. 20). Вместе с проверками здоровья именно это делает [поэтапные обновления](/ru/notes/devops/continuous-delivery#rolling-update) предыдущей заметки незаметными для пользователей.

## Бюджет задержки на каждом участке \{#latency-budget-per-hop\}

Сколько длится один запрос? Посчитаем круговые обращения. Для нового соединения по TCP с TLS 1.3 и HTTP/2, где $\mathrm{RTT}$ — время кругового обращения между клиентом и прокси,

$$
T_{\text{new}} = T_{\text{DNS}} + \underbrace{\mathrm{RTT}}_{\text{TCP}} + \underbrace{\mathrm{RTT}}_{\text{TLS}} + \underbrace{\mathrm{RTT}}_{\text{запрос}} + T_{\text{proxy}} + T_{\text{backend}} ,
$$

где круговое обращение запроса покрывает отправку запроса и получение первых байтов небольшого ответа; большой ответ добавляет время своей передачи, член $8S/B$ из [заметки о сетях](/ru/notes/acos/networking#latency-versus-bandwidth).

**Разобранный пример.** Игрушечная постановка: резолвер отвечает из кэша за $T_{\text{DNS}} = 5$ мс, $\mathrm{RTT} = 40$ мс, прокси добавляет $T_{\text{proxy}} = 1$ мс (собственная работа и круговое обращение внутри центра обработки данных по соединению из пула), а бэкенд работает $T_{\text{backend}} = 60$ мс.

- Новое соединение HTTP/2: $5 + 40 + 40 + 40 + 1 + 60 = 186$ мс.
- Новое соединение HTTP/3, где QUIC и TLS делят одно круговое обращение: $5 + 40 + 40 + 1 + 60 = 146$ мс.
- Возобновлённый сеанс с 0-RTT, который отправляет запрос в первой же серии пакетов: $5 + 40 + 1 + 60 = 106$ мс.
- Уже открытое соединение, имя закэшировано в браузере: $40 + 1 + 60 = 101$ мс.

Отсюда три вывода. Во-первых, на новом соединении рукопожатия стоят больше, чем бэкенд: $80$ из $186$ мс против его $60$. Повторное использование соединений убирает их, поэтому браузеры держат соединения открытыми, а прокси держат пулы открытых соединений к своим бэкендам; прокси, который для каждого запроса открывал бы новое TLS-соединение с бэкендом в другом регионе, добавлял бы два круговых обращения по этому более длинному пути. Во-вторых, круговое обращение задаётся расстоянием, которое не сократит ни один сервер, поэтому провайдеры ставят прокси рядом с пользователями (сеть доставки контента, CDN) и доносят запрос до бэкенда по уже открытым соединениям. В-третьих, поиск в DNS, промахнувшийся мимо всех кэшей, может стоить намного больше 5 мс — около 90 мс в примере из [заметки о сетях](/ru/notes/acos/networking#dns-from-names-to-addresses), — и то, как часто это происходит, решают TTL.

**Бюджеты и перцентили.** Команда, которая обещает задержку, скажем 300 мс для 99% запросов, делит её между участками: столько-то на сеть, столько-то на прокси, столько-то на каждый вызов бэкенда. Средние складываются, перцентили — нет. 99-й перцентиль суммы не равен сумме 99-х перцентилей участков, поэтому бюджет для хвоста проверяют, измеряя сумму. Веерные вызовы (fan-out) ухудшают хвост: когда один запрос параллельно вызывает $N$ бэкендов и ждёт их всех, а каждый отвечает в пределах 10 мс с вероятностью 0.99, все $N$ ответят в пределах 10 мс с вероятностью $0.99^N$, если они независимы: $0.904$ при $N = 10$ и $0.366$ при $N = 100$. Редкий медленный ответ одной машины становится обычным случаем для запроса ([Dean and Barroso, 2013](#references)). Почему перцентили нельзя усреднять, показано в заметке о [наблюдаемости](/ru/notes/devops/observability#why-percentiles-cannot-be-averaged), а таймауты и повторы, которые их ограничивают, — в заметке об [устойчивости и ёмкости](/ru/notes/devops/resilience-and-capacity).

## Что изменилось \{#what-changed\}

| Проблема одиночного сервера | Механизм | Где он живёт |
| --- | --- | --- |
| Адрес — это машина | имена DNS, псевдонимы, TTL, выбранные для каждой записи | авторитетные серверы, кэши резолверов |
| Любой на пути может прочитать или подделать | TLS 1.3: эфемерные ключи, цепочка сертификатов, подпись под рукопожатием | клиент и прокси, терминирующий TLS |
| Одна машина — один отказ | пул бэкендов за балансировщиком нагрузки | балансировщики L4 и L7 |
| Ключи на каждом сервере | терминирование TLS, сертификаты, продлеваемые по ACME | слой прокси |
| Сервер нельзя вывести мягко | проверки здоровья, плавный вывод из ротации, хромая утка | балансировщик и бэкенд вместе |
| Круговые обращения стоят расстояния | TLS 1.3, повторное использование соединений, HTTP/3, 0-RTT, прокси рядом с пользователями | клиент, пограничные прокси |

## Ограничения \{#limitations\}

- Проверки здоровья и DNS видят отказ с одной точки обзора. Бэкенд может проходить проверку здоровья и всё равно проваливать реальные запросы, а имя может разрешаться в одной сети и не разрешаться в другой; что видят пользователи, показывают только измерения реального трафика.
- TTL — лишь рекомендация. Некоторые клиенты и среды выполнения кэшируют ответы дольше TTL, поэтому изменение DNS никогда не завершается в точно определённый момент, и запись, которая была неверной час, может оставаться неверной для части пользователей сутки.
- Бюджет задержки считает круговые обращения и не учитывает потери, окна перегрузки и очереди в бэкенде, которые доминируют под нагрузкой; очереди добавляет [заметка об устойчивости](/ru/notes/devops/resilience-and-capacity).
- Каждый прокси — ещё один компонент, который может отказать, быть неправильно настроен или исчерпать соединения, и его собственные ограничения (таймауты, размеры буферов, пулы соединений) становятся частью поведения сервиса.
- Заметка рассматривает один регион. Глобальная маршрутизация (адреса anycast, ответы DNS, зависящие от местоположения клиента, переключение между регионами) строится из тех же частей и выходит за рамки заметки.

## Что нужно запомнить \{#what-you-should-remember\}

- Запрос проходит через резолвер, прокси, балансировщик и бэкенд; каждый из них — косвенность, позволяющая меняться уровню за ним, и у каждого есть кэш или представление о здоровье, которое может устареть.
- DNS: записи сопоставляют именам адреса (`A`, `AAAA`) или другие имена (`CNAME`). TTL — компромисс между нагрузкой запросов и скоростью распространения изменения; уменьшайте его перед миграцией не позже чем за один старый TTL.
- TLS 1.3 стоит одного кругового обращения после одного обращения TCP: ClientHello с долей ключа, SNI и ALPN; ServerHello; затем зашифрованные цепочка сертификатов, подпись и Finished. Клиент проверяет цепочку до своего хранилища доверенных сертификатов и имя по сертификату.
- HTTP/2 мультиплексирует потоки в одном TCP-соединении; HTTP/3 делает это поверх QUIC, с независимыми потоками и рукопожатием за одно круговое обращение.
- Обратный прокси терминирует TLS, маршрутизирует, буферизует, кэширует и добавляет адрес клиента. Балансировщик L4 выбирает бэкенд на соединение, балансировщик L7 — на запрос.
- Проверки здоровья: активные проверки обнаруживают мёртвый бэкенд примерно за `fall` интервалов плюс таймаут, пассивные — за несколько неудавшихся запросов; проверка тестирует процесс, а не его зависимости. Перед остановкой выводите бэкенд из ротации.
- Задержка: $T_{\text{new}} = T_{\text{DNS}} + 3\,\mathrm{RTT} + T_{\text{server}}$ для нового соединения HTTP/2, $\mathrm{RTT} + T_{\text{server}}$ для повторно используемого. Средние по участкам складываются, перцентили — нет, а веерные вызовы превращают редкие медленные ответы в частые медленные запросы.

## Пример \{#example\}

Конфигурация HAProxy, широко используемого балансировщика нагрузки с открытым кодом, для сервиса с рисунка: она терминирует TLS для `www.example.com`, перенаправляет обычный HTTP на HTTPS и распределяет запросы по трём бэкендам с активными проверками здоровья. Она написана для HAProxy 3.4 (2026) по его руководству по конфигурации и здесь не запускалась; `haproxy -c -f haproxy.cfg` проверяет такой файл, не запуская балансировщик.

```text
global
    log stdout format raw local0

defaults
    mode http
    log global
    option httplog
    timeout connect 3s
    timeout client 30s
    timeout server 30s
    timeout http-request 10s
    timeout check 2s

frontend www
    bind :80
    bind :443 ssl crt /etc/haproxy/certs/www.example.com.pem alpn h2,http/1.1
    http-request redirect scheme https code 301 unless { ssl_fc }
    http-request set-header X-Forwarded-Proto https
    option forwardfor
    default_backend web

backend web
    balance leastconn
    option httpchk
    http-check send meth GET uri /healthz ver HTTP/1.1 hdr Host www.example.com
    http-check expect status 200
    default-server inter 5s fall 3 rise 2
    server web1 10.0.1.11:8080 check
    server web2 10.0.2.12:8080 check
    server web3 10.0.3.13:8080 check
```

- `log stdout format raw local0` пишет журнал доступа в стандартный вывод, где его собирает среда выполнения контейнеров.
- `mode http` делает это прокси уровня L7: он разбирает запросы. С `mode tcp` это был бы прокси L4, который только сшивает соединения.
- `timeout connect 3s`: отказаться от бэкенда, который не принял соединение за 3 с. `timeout client` и `timeout server`: закрыть соединение, молчащее 30 с. `timeout http-request 10s`: клиент должен прислать полные заголовки запроса за 10 с, что обезвреживает клиентов, которые цедят запрос по байту, чтобы держать соединения открытыми. `timeout check 2s` — таймаут проверки из разобранного примера.
- `frontend www` — слушающая сторона. `bind :80` принимает обычный HTTP; `bind :443 ssl crt ...` принимает TLS с сертификатом и ключом в одном файле PEM и предлагает по ALPN `h2` и `http/1.1`. Это и есть терминирование TLS.
- `http-request redirect scheme https code 301 unless { ssl_fc }`: запрос, пришедший не по TLS (`ssl_fc`, «переднее соединение — SSL», ложно), получает постоянное перенаправление на HTTPS. Фигурные скобки ограничивают анонимное условие.
- `set-header X-Forwarded-Proto https` сообщает бэкенду, что клиент использовал HTTPS (после перенаправления это верно для каждого запроса, дошедшего до бэкенда); `option forwardfor` добавляет `X-Forwarded-For` с адресом клиента. Обе директивы перезаписывают то, что прислал клиент, поэтому бэкенд может им доверять.
- `backend web` — пул. `balance leastconn` отправляет каждый запрос серверу с наименьшим числом текущих соединений.
- `option httpchk` включает проверки здоровья по HTTP; строка `http-check send` задаёт проверку, `GET /healthz` с заголовком `Host`, а `http-check expect status 200` говорит, что здоровым считается только ответ 200.
- `default-server inter 5s fall 3 rise 2` задаёт для каждого сервера ниже проверку каждые 5 с, вывод после трёх неудач и возврат после двух успехов: числа разобранного примера.
- Каждая строка `server` называет бэкенд по частному адресу и порту; `check` включает для него проверку здоровья. Вывод сервера из ротации для развёртывания выполняется во время работы через runtime API HAProxy (перевод сервера в состояние `drain`), без перезагрузки файла.

## Дальше \{#next\}

Прокси, балансировщики, записи DNS и адреса из этой заметки должен был кто-то где-то создать, и они меняются по мере роста сервиса. Созданные вручную в консоли, они не поддаются ревью, повторению и пересозданию после ошибки.
