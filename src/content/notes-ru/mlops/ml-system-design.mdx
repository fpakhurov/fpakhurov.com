[Предыдущая заметка](/ru/notes/mlops/what-mlops-is) показала, что модель — маленький прямоугольник в большой системе, и прошла один круг петли, которая поддерживает модель актуальной. Все эти механизмы напрасны, если служат не той цели: модель оптимизирует метрику, которая продукту не нужна, отвечает слишком медленно для вызывающей её страницы, стоит больше, чем экономит, или причиняет вред, когда ошибается, — а ошибается иногда любая модель. Эти вопросы решаются до всякого обучения, на бумаге. Заметка разбирает их для проверки на мошенничество из сквозного примера: использовать ли машинное обучение вообще, какие качества помимо доли правильных ответов (accuracy) нужны системе, какие числа измеряют успех, как ограничить вред от ошибок и как проверить арифметикой бюджет задержки и бюджет стоимости. Заканчивается она проектным документом (design document), который фиксирует ответы.

## Отправная точка: начать с модели \{#baseline-start-from-the-model\}

Обычный первый шаг — задача моделирования: «постройте модель мошенничества с наилучшим возможным AUC». Специалист по данным получает таблицу, пробует градиентный бустинг и нейронную сеть, достигает 0.95 и показывает результат. Затем приходят вопросы, и все они запаздывают. Команда оформления заказа спрашивает, сколько длится одна оценка, потому что у страницы на всю проверку риска 50 миллисекунд, а ансамблю нужно 200. Финансовая команда спрашивает, сколько потерь от мошенничества это сэкономит, и никто не может ответить, потому что AUC измеряется не в евро. Служба поддержки спрашивает, что сказать клиенту, если его платёж отклонён по ошибке. Аналитики по мошенничеству спрашивают, какие платежи им проверять, ведь модель, которая говорит только «мошенничество» или «не мошенничество», не оставляет им работы. Каждый вопрос меняет модель, которую следовало построить.

Проектировать систему — значит задать эти вопросы первыми. Ответы умещаются на нескольких страницах, и остальная часть заметки их выводит.

## Нужно ли здесь ML вообще? \{#should-this-be-ml-at-all\}

Машинное обучение окупается, когда выполняются три условия ([Kästner, 2025, гл. 4](#references); [Huyen, 2022, гл. 1](#references)): правило нельзя записать, но примеров правильного ответа много; редкие ошибки допустимы или их последствия можно ограничить; закономерности меняются, так что выученное правило дешевле выучить заново, чем переписать написанное. Обнаружение мошенничества удовлетворяет всем трём. Расчёт НДС с платежа — ни одному, и модель там только добавила бы способ ошибиться.

Даже когда ML подходит, первая версия не обязана его использовать. Первое из правил ML от Google советует не бояться запуска без машинного обучения, а третье — переходить на ML, когда эвристика становится сложной ([Zinkevich, правила 1 и 3](#references)). Эвристика — **базовое решение** (baseline), которое должна превзойти любая модель, и превосходство измеряется в валюте продукта, а не в AUC. Для проверки на мошенничество валюта — евро: сколько стоит каждый вид ошибки. Возьмём условные стоимости: пропущенное мошенничество стоит своей суммы плюс 15 € комиссии за чарджбэк (chargeback); отклонённый добросовестный платёж стоит 10% своей суммы в потерянной марже плюс 5 € лояльности клиента; ручная проверка стоит 4 € времени аналитика, и считается, что аналитик решает правильно; проверить аналитики могут не больше 2% платежей. Программа сравнивает четыре плана на синтетической неделе из 20 000 платежей с долей мошенничества 2% (преувеличенной, как и в предыдущей заметке, чтобы в неделе было достаточно мошенничества для измерений):

```python
"""Cost of four ways to handle payments: approve all, a rule, a model with one threshold, a model with a review band."""
import numpy as np
from sklearn.linear_model import LogisticRegression

rng = np.random.default_rng(11)
N = 20_000

def week():
    fraud = rng.random(N) < 0.02
    amount = np.where(fraud, rng.lognormal(5.0, 0.8, N), rng.lognormal(3.5, 1.0, N)).round(2)
    new_device = rng.random(N) < np.where(fraud, 0.6, 0.1)
    foreign = rng.random(N) < np.where(fraud, 0.5, 0.15)
    return amount, new_device, foreign, fraud

def features(amount, new_device, foreign):
    return np.column_stack([np.log1p(amount), new_device, foreign])

# Стоимости в евро, на один платёж.
FEE = 15            # комиссия за чарджбэк сверх потерянной суммы
MARGIN = 0.10       # доля отклонённого добросовестного платежа, теряемая как маржа
GOODWILL = 5        # добросовестный клиент, которому отказали, может не вернуться
REVIEW = 4          # время аналитика на один проверенный платёж; аналитик решает правильно
CAPACITY = 0.02     # аналитики могут проверить не больше 2% платежей

def cost(decision, amount, fraud):
    """decision: 0 approve, 1 review, 2 decline. Returns euros per 1,000 payments."""
    c = np.where(fraud & (decision == 0), amount + FEE, 0.0)
    c += np.where(~fraud & (decision == 2), MARGIN * amount + GOODWILL, 0.0)
    c += np.where(decision == 1, REVIEW, 0.0)
    return 1000 * c.mean()

train, valid, test = week(), week(), week()
model = LogisticRegression().fit(features(*train[:3]), train[3])
p_valid = model.predict_proba(features(*valid[:3]))[:, 1]
p_test = model.predict_proba(features(*test[:3]))[:, 1]

# Пороги выбираются на валидационной неделе, результат считается на тестовой.
grid = np.quantile(p_valid, np.linspace(0.90, 0.9995, 300))
amount_v, *_, fraud_v = valid
one = min(grid, key=lambda t: cost(np.where(p_valid >= t, 2, 0), amount_v, fraud_v))
best = None
for lo in grid:
    for hi in grid[grid > lo]:
        d = np.where(p_valid >= hi, 2, np.where(p_valid >= lo, 1, 0))
        if (d == 1).mean() <= CAPACITY:
            c = cost(d, amount_v, fraud_v)
            if best is None or c < best[0]:
                best = (c, lo, hi)
_, lo, hi = best

amount, new_device, foreign, fraud = test
plans = {
    'approve everything': np.zeros(N, int),
    'rule: review if > 200 € and new device': np.where((amount > 200) & new_device, 1, 0),
    'model, decline above one threshold': np.where(p_test >= one, 2, 0),
    'model, review band, decline the top': np.where(p_test >= hi, 2, np.where(p_test >= lo, 1, 0)),
}
print(f'{"plan":<40} {"cost per 1,000":>14} {"reviewed":>9} {"declined":>9} {"fraud caught":>13}')
for name, d in plans.items():
    caught = (d[fraud] > 0).mean()
    print(f'{name:<40} {cost(d, amount, fraud):>12.0f} € {(d == 1).mean():>9.1%} {(d == 2).mean():>9.1%} {caught:>13.0%}')
print(f'fraud rate {fraud.mean():.2%}, mean fraudulent amount {amount[fraud].mean():.0f} €')
```

```console
$ python3 plans.py
plan                                     cost per 1,000  reviewed  declined  fraud caught
approve everything                               4398 €      0.0%      0.0%            0%
rule: review if > 200 € and new device           2623 €      0.9%      0.0%           24%
model, decline above one threshold               1852 €      0.0%      3.0%           53%
model, review band, decline the top              1547 €      1.9%      1.1%           53%
fraud rate 2.02%, mean fraudulent amount 203 €
```

Отсюда три следствия, и ни одно не касается AUC модели.

- **Сначала бо́льшую часть работы делает эвристика.** Однострочное правило — проверять платежи больше 200 € с нового устройства — снижает стоимость мошенничества с 4398 € до 2623 € на 1000 платежей и использует меньше половины пропускной способности проверки. Ему не нужны обучающие данные, конвейер и мониторинг модели, и запускать первым стоит именно его.
- **Модель должна окупаться по сравнению с правилом, а не с пустым местом.** Лучший план с моделью экономит ещё 2623 − 1547 = 1076 € на 1000 платежей. Если построение и эксплуатация ML-системы стоят, скажем, 25 000 € в месяц на людей и инфраструктуру, она окупается при объёме больше $25\,000 / 1.076 \approx 23\,000$ платежей в месяц в этом синтетическом магазине. Настоящее мошенничество в десять–сто раз реже, чем здесь, и пороговый объём соответственно выше: ниже него правильная система — правило.
- **Устройство системы вокруг модели важно не меньше самой модели.** Два последних плана используют одну и ту же модель с одним и тем же AUC. Отклонять всё выше одного порога стоит 1852 €; если добавить полосу неуверенных платежей для ручной проверки (review band) и отклонять только самые очевидные случаи, выходит 1547 €, потому что проверки дешевле ошибочных отклонений. Эта разница, 305 € на 1000 платежей, получена проектным решением, а не лучшим моделированием.

Сам выбор порога — рабочей точки по стоимостям двух видов ошибок — тот же, что в [заметке о метриках классификации](/ru/notes/ml/classification-metrics#costs-decide-the-threshold); проектирование системы добавляет к нему третье действие, ограничение пропускной способности для него и сравнение с базовым решением, которому модель не нужна.

## Качества помимо доли правильных ответов \{#qualities-beyond-accuracy\}

Модель — один компонент продукта, а у продукта есть требования, которых не отражает доля правильных ответов. Kästner называет их **атрибутами качества** (quality attributes) ML-компонента ([Kästner, 2025, гл. 9](#references); см. также [Huyen, 2022, гл. 2](#references)). Каждый из них ограничивает выбор модели и архитектуры, и каждый нужно записать числом.

| Качество | Вопрос | Для проверки на мошенничество |
| --- | --- | --- |
| Задержка | сколько может длиться одно предсказание, в медиане и в хвосте | 50 мс на p99 для всей проверки риска, внутри страницы оформления заказа |
| Пропускная способность | сколько предсказаний в секунду в пике | 42 в секунду в пике (1.2 млн платежей в день, пик втрое выше среднего) |
| Стоимость | сколько может стоить одно предсказание и одно переобучение | мало по сравнению с потерями, которые оно предотвращает; см. бюджет ниже |
| Свежесть | насколько старыми могут быть модель и признаки, которые она читает | модель переобучается не реже раза в месяц; признаки истории карты — не старше минуты |
| Обновляемость | как быстро исправление или новая модель доходит до продакшена | новая модель — в течение дня, изменение порога — за минуты |
| Объяснимость | нужно ли объяснять решение и кому | аналитики видят основные причины по каждому проверяемому платежу |
| Устойчивость | какие входы модель должна выдерживать | некорректные и враждебные платежи; мошенники прощупывают систему |
| Занимаемые ресурсы (footprint) | где работает модель и что ей можно занимать | сервис на CPU рядом с оформлением заказа; никаких GPU на пути запроса |

Эти качества конкурируют друг с другом и с долей правильных ответов. Ансамбль градиентного бустинга из тысячи деревьев может выиграть пункт полноты и выйти за бюджет задержки; модель, переобучаемая каждый час, свежа, но её дорого валидировать; большая языковая модель, которая пишет обоснование каждого решения, объяснима и слишком медленна для оформления заказа, но может подойти для очереди проверки у аналитиков, где счёт идёт на минуты, а не на миллисекунды. Записанные качества превращают эти компромиссы в явный выбор. Таблица — ядро проектного документа из примера.

## Офлайн-, онлайн- и суррогатные метрики \{#offline-online-and-proxy-metrics\}

ML-систему измеряют числа трёх видов, и путать их — частый способ оптимизировать не то ([Huyen, 2022, гл. 2 и 6](#references); [Kästner, 2025, гл. 5](#references)).

- **Офлайн-метрики** (offline metrics) вычисляются на отложенных данных до развёртывания: AUC, точность (precision) и полнота (recall) при бюджете проверки, стоимость на 1000 платежей из предыдущего раздела. Они дёшевы, повторяемы и доступны сразу, и именно их оптимизируют обучение и гейт (gate) оценки.
- **Онлайн-метрики** (online metrics) измеряются в продакшене по настоящей цели продукта: потери от мошенничества в евро, доля ложных отклонений (отказов добросовестным клиентам), конверсия оформления заказа, длина очереди проверки, жалобы клиентов. Именно они важны бизнесу, и измерить их можно только на живом трафике, обычно [A/B-тестом](/ru/notes/probability/hypothesis-tests#the-ab-test) или [канареечным выпуском](/ru/notes/devops/continuous-delivery#judging-a-canary-on-a-small-sample), которые для моделей развивает [заметка о выкатке](/ru/notes/mlops/rolling-out-models).
- **Суррогатные метрики** (proxy metrics) заменяют цель, которая измеряется слишком поздно или слишком редко. Чарджбэк, окончательная метка мошенничества, приходит через недели или месяцы после платежа. Ждать его — значит судить о модели через два месяца после того, как она начала работать. Суррогат, например мошенничество, подтверждённое аналитиками в течение 48 часов, или доля помеченных платежей, доступен сразу.

Офлайн- и онлайн-метрики расходятся по причинам, которые стоит перечислить в проекте. Офлайн-тестовая выборка взята из прошлого; решения модели меняют данные, которые она увидит (отклонённые платежи никогда не получают метку, поэтому модель так и не узнаёт, были ли они мошенничеством); а онлайн-цель включает эффекты, которых нет ни в одной офлайн-выборке, например клиентов, которые уходят после ложного отклонения. Суррогат несёт собственный риск: чем сильнее команда оптимизирует суррогат, тем хуже он обычно следует за целью — это закон Гудхарта. Если помечать меньше платежей, доля помеченных выглядит лучше, а потери от мошенничества растут. Поэтому каждому суррогату нужна **защитная метрика** (guardrail metric), которая не должна ухудшаться, и периодическая сверка с настоящим исходом, когда он придёт.

## Планирование на случай ошибок \{#planning-for-mistakes\}

Модель будет ошибаться на некоторых входах по причинам, которые трудно предсказать и которые не случайны: целые группы платежей, например одна новая схема мошенничества или клиенты одной страны, могут оцениваться неверно все сразу. Правило Kästner — проектировать систему так, чтобы ошибки были терпимы, а не надеяться, что они редки ([Kästner, 2025, гл. 7](#references)). Его стратегии в применении к проверке на мошенничество:

- **Человек в контуре** (human in the loop). Решить, сколько модель решает сама. Здесь: автоматически одобрять ниже полосы проверки, отправлять полосу аналитикам, автоматически отклонять только самые очевидные случаи. Автоматизация подходит для дешёвых ошибок, проверка человеком — для дорогих или неуверенных, а пропускная способность проверки ограничивает ширину полосы.
- **Обратимые действия.** Предпочитать действия, результат которых можно отменить. *Приостановку* (hold: платёж несколько минут ждёт проверки или подтверждения клиентом в приложении банка) можно отменить; *отклонение* может навсегда лишить магазин клиента; *одобрение* мошеннического платежа магазин отменить не может вовсе. Поэтому проект превращает многие отклонения в приостановки и дополнительные проверки (step-up).
- **Защитные правила** (guardrails). Правила вне модели, которые ограничивают её возможности, чтобы одно предсказание никогда не было единственным основанием для решения: никогда не отклонять автоматически платёж постоянного клиента меньше 10 €, всегда требовать подтверждения банка для суммы больше 2000 € с нового устройства, блокировать карты из списка известных украденных номеров независимо от оценки. Защитное правило также ограничивает долю действий, как предел действия в примере предыдущей заметки.
- **Обнаружение ошибок и восстановление.** Следить за симптомами ошибок, такими как жалобы, обжалования, чарджбэки или резкое изменение доли помеченных, и дать клиентам способ обжаловать отклонение. Когда сама модель недоступна, деградировать плавно: сервис риска переходит на правила базового решения, а не на «одобрять всё» (что пропускает мошенничество) или «отклонять всё» (что останавливает магазин).
- **Избыточность и изоляция.** Запускать правила рядом с моделью, чтобы каждый ловил часть промахов другого, и не давать модели мошенничества становиться зависимостью систем, которым она не нужна, — это долг необъявленных потребителей из [предыдущей заметки](/ru/notes/mlops/what-mlops-is#undeclared-consumers).

Четыре плана предыдущего раздела — этот список в миниатюре: полоса проверки — человек в контуре, её пропускная способность — защитное правило, а план только с правилом — запасной путь (fallback).

## Бюджеты задержки и стоимости как арифметика \{#latency-and-cost-budgets-as-arithmetic\}

Бюджет — требование, которое можно проверить арифметикой ещё до того, как что-либо построено, и снова проверить по измерениям после. Словарь определяет [заметка об SLO](/ru/notes/devops/slos-and-alerting#sli-slo-and-sla); здесь он применяется к модели на пути запроса.

### Бюджет задержки \{#the-latency-budget\}

У страницы оформления заказа есть цель по задержке, и её владельцы выделяют проверке риска 50 мс на 99-м процентиле. У проверки четыре этапа, измеренных на прототипе (числа условные): сетевой переход в сервис риска и обратно (медиана 2 мс, p99 5 мс); три запроса признаков, отправляемые параллельно в три хранилища — история карты, история устройства и учётная запись клиента (у каждого медиана 4 мс, p99 20 мс); модель (медиана 3 мс, p99 8 мс); правила и ответ (медиана 1 мс, p99 3 мс).

Два факта делают арифметику менее очевидной, чем простое сложение чисел.

**Параллельные вызовы ждут самого медленного.** Запросы выполняются одновременно, поэтому этап длится столько, сколько максимальная из трёх задержек. Если один запрос медленнее 20 мс с вероятностью 0.01 независимо от остальных, то

$$
P(\text{самый медленный из 3} > 20\ \text{мс}) = 1 - 0.99^3 = 0.0297 ,
$$

то есть втрое чаще: p99 одного вызова — примерно p97 веерного вызова (fan-out). Чтобы найти p99 максимума, спросим, какой квантиль одного вызова $q$ даёт $q^3 = 0.99$: $q = 0.99^{1/3} = 0.99666$. Предположим, как это обычно для задержек сервисов, что задержка каждого запроса логнормальна, $\ln T \sim \mathcal N(\mu, \sigma^2)$. Тогда квантиль равен $T_q = e^{\mu + \sigma z_q}$, где $z_q$ — квантиль стандартного нормального распределения, а медиана равна $e^\mu$. По медиане и p99

$$
\sigma = \frac{\ln(p_{99} / p_{50})}{z_{0.99}} = \frac{\ln(20/4)}{2.326} = 0.692 ,
$$

а p99 веерного вызова равен

$$
T_{0.99666} = 4 \cdot e^{0.692 \cdot 2.712} = 4 \cdot 6.53 = 26.1\ \text{мс} .
$$

Эффект растёт с числом параллельных вызовов: при 100 вызовах $1 - 0.99^{100} = 63\%$ запросов ждут хотя бы одного вызова медленнее его p99, поэтому [Dean and Barroso (2013)](#references) называют это хвостом в масштабе (the tail at scale).

**Процентили не складываются.** Сумма p99 этапов, $5 + 26.1 + 8 + 3 = 42.1$ мс, не равна p99 общей задержки, потому что медленные хвосты независимых этапов редко совпадают на одном запросе. Моделирование миллиона запросов, в котором каждый этап берётся из своего логнормального распределения, даёт настоящую величину:

```python
"""The latency budget of a fraud check: stages with log-normal latencies, three feature lookups in parallel."""
import numpy as np
from scipy.stats import norm

rng = np.random.default_rng(3)
n = 1_000_000
z99 = norm.ppf(0.99)

def lognormal(p50, p99, size):
    sigma = np.log(p99 / p50) / z99
    return p50 * np.exp(sigma * rng.standard_normal(size))

stages = {                        # (p50, p99) в миллисекундах
    'network in and out': (2, 5),
    'feature lookup (each of 3)': (4, 20),
    'model': (3, 8),
    'rules and response': (1, 3),
}
net = lognormal(*stages['network in and out'], n)
lookups = np.max([lognormal(*stages['feature lookup (each of 3)'], n) for _ in range(3)], axis=0)
model = lognormal(*stages['model'], n)
rules = lognormal(*stages['rules and response'], n)
total = net + lookups + model + rules

sigma = np.log(20 / 4) / z99
z = norm.ppf(0.99 ** (1 / 3))
print(f'one lookup slower than 20 ms: 1%;  any of three: {1 - 0.99**3:.2%}')
print(f'p99 of the slowest of three: analytic 4 * exp({sigma:.3f} * {z:.3f}) = {4 * np.exp(sigma * z):.1f} ms, '
      f'simulated {np.quantile(lookups, 0.99):.1f} ms')
print(f'sum of the stage p99s: {5 + 20 + 8 + 3} ms (one lookup), {5 + 4*np.exp(sigma*z) + 8 + 3:.1f} ms (fan-out)')
print(f'end to end: p50 {np.median(total):.1f} ms, p99 {np.quantile(total, 0.99):.1f} ms, '
      f'p99.9 {np.quantile(total, 0.999):.1f} ms')
for t in (40, 60):
    print(f'share of checks over {t} ms: {(total > t).mean():.3%}')
# При таймауте 25 мс на запросы признаков вместо полного пути отвечает запасной (только правила).
capped = net + np.minimum(lookups, 25) + model + rules
print(f'with a 25 ms lookup timeout: fallback on {(lookups > 25).mean():.2%} of checks, '
      f'p99 {np.quantile(capped, 0.99):.1f} ms, max {capped.max():.1f} ms')
```

2. Три запроса параллельно: этап заканчивается, когда возвращается самый медленный, — 26.1 мс на p99, а не 20.
3. Модель: 3 мс в медиане, 8 мс на p99.
4. Правила и ответ: 1 мс и 3 мс.
5. Сквозной p99 равен 33.0 мс, это меньше суммы p99 этапов (42.1 мс), и обе величины укладываются в бюджет 50 мс.

Здесь сумма p99 завышает хвост, поэтому она годится как безопасная первая проверка. Это свойство этих этапов с лёгкими хвостами, а не закон: при тяжёлых хвостах квантили суммы могут превышать сумму квантилей, так что сумма — первая оценка, а проверка — моделирование или нагрузочный тест. На p99 бюджет выполняется с запасом 17 мс. Выполняется он не на каждом процентиле: 0.03% проверок длятся больше 60 мс. Исправление — не более быстрая модель, а **крайний срок** (deadline): таймаут 25 мс на запросы признаков, после которого сервис отвечает только по правилам (запасной путь из предыдущего раздела). Он срабатывает на 1.19% проверок и ограничивает общее время 44.5 мс. Таймауты и крайние сроки развивает [заметка об устойчивости](/ru/notes/devops/resilience-and-capacity#timeouts-and-deadlines); специфичная для ML часть в том, что запасной путь должен давать решение, а не ошибку.

Арифметика также говорит, куда тратить усилия. Модель, которую в отправной точке оптимизировали бы первой, занимает 8 из 33 мс на p99. Запросы признаков занимают 26: кэширование истории карты или её заблаговременный расчёт дают больше, чем любое изменение модели.

### Бюджет стоимости \{#the-cost-budget\}

Стоимость инференса следует из пропускной способности. Магазин обрабатывает 1.2 млн платежей в день, в среднем $1\,200\,000 / 86\,400 = 13.9$ в секунду, и втрое больше, 41.7 в секунду, в вечерний пик. Модели нужно 3 мс одного ядра CPU на предсказание, поэтому одно ядро обслуживает не больше $1000 / 3 = 333$ предсказаний в секунду, а при планировании на загрузку 50%, чтобы задержка в очереди оставалась малой ([задержка в зависимости от загрузки](/ru/notes/devops/resilience-and-capacity#latency-against-utilization)), — 167. Пику нужно $41.7 / 167 = 0.25$ ядра.

Размер задаёт доступность, а не вычисления: три реплики по одному виртуальному CPU в двух зонах, чтобы потеря одной зоны оставляла достаточно мощности. Это $3 \times 730 = 2\,190$ vCPU-часов в месяц, что по условной цене 0.04 € за vCPU-час составляет 87.6 € в месяц. В месяце $1.2 \times 365 / 12 = 36.5$ млн предсказаний, поэтому модель стоит

$$
\frac{87.6 \text{ евро}}{36\,500 \text{ тысяч предсказаний}} = 0.0024 \text{ евро на тысячу предсказаний} .
$$

При экономии порядка сотен евро на 1000 платежей вычисления для инференса маленькой табличной модели — ошибка округления; значимые затраты — хранилища признаков, конвейеры, команда проверки и инженеры. Та же арифметика даёт совсем другие ответы для модели, которой нужен GPU на каждые несколько запросов, или для большой языковой модели с оплатой за токен, где стоимость 1000 предсказаний может соперничать с ценностью самого предсказания. Эту арифметику проделывает [последняя заметка курса](/ru/notes/mlops/cost-and-efficiency).

<aside class="callout"><strong>Ключевая идея.</strong> Проектировать систему раньше модели. Спросить, не хватит ли правила, и сделать лучшее правило базовым решением, которое модель должна превзойти в собственных единицах продукта. Записать нужные компоненту качества числами: задержка на процентиле, пропускная способность в пике, стоимость предсказания, свежесть, обновляемость. Выбрать онлайн-метрики для цели, офлайн-метрики для разработки и суррогаты с защитными метриками для того, что приходит слишком поздно. Исходить из того, что модель будет ошибаться, и спроектировать, как именно: кто проверяет, что можно отменить, какие правила её ограничивают, что происходит, когда она недоступна. Каждый бюджет сначала проверить арифметикой, а потом измерениями.</aside>

| Первый вопрос | какая модель даёт лучшую метрику | нужно ли здесь ML и чего достигает лучшее правило |

| Требования | неявные | задержка, пропускная способность, стоимость, свежесть, обновляемость, объяснимость — числами |
| Метрики | одна офлайн-метрика | офлайн для разработки, онлайн для цели, суррогаты с защитными метриками |

| Задержка | измеряется после построения, если вообще измеряется | бюджет по этапам с рассчитанными веерными вызовами и хвостами и крайним сроком |

## Ограничения \{#limitations\}

- **Стоимости — допущения.** Евро за ошибку, пропускная способность проверки и цена vCPU-часа выше условны, а настоящие трудно оценить: потеря лояльности от ложного отклонения — догадка. Переносится структура расчёта, а не числа.
- **В арифметике хвостов предполагается независимость.** Параллельные вызовы, которые делят сеть, кэш или хост со сборкой мусора, замедляются вместе; из-за этого веерные вызовы ведут себя лучше расчёта, а сквозной хвост — хуже. Формулу заменяют нагрузочные тесты на настоящей системе.
- **Логнормальные задержки — модель.** У настоящих распределений задержки есть горбы (попадания и промахи кэша, повторы), которые двухпараметрическая подгонка не передаёт; квантили нужно брать из измеренных гистограмм ([процентили нельзя усреднять](/ru/notes/devops/observability#why-percentiles-cannot-be-averaged)).
- **Офлайн-выигрыш не гарантирует онлайн-выигрыша.** Сравнение стоимостей использует отложенные данные из того же распределения и не учитывает влияния модели на данные, которые она увидит; решает только онлайн-эксперимент.
- **Проект — гипотеза.** Требования меняются по мере того, как продукт узнаёт новое, и проектный документ, который не обновляют, становится ещё одной формой долга конфигурации.

## Что нужно запомнить \{#what-you-should-remember\}

- ML используют, когда правило нельзя записать, примеры есть, последствия ошибок можно ограничить, а закономерности меняются. Сначала запускают лучшую эвристику; это базовое решение, которое модель должна превзойти.
- Планы сравнивают в единицах продукта. В примере правило снизило стоимость мошенничества с 4398 € до 2623 € на 1000 платежей; модель с полосой проверки дошла до 1547 €, и 305 € из этого дала полоса проверки, а не модель.
- Качества помимо доли правильных ответов задают числами: задержка на процентиле, пропускная способность в пике, стоимость, свежесть, обновляемость, объяснимость, устойчивость, занимаемые ресурсы.
- Офлайн-метрики направляют разработку, онлайн-метрики измеряют цель, суррогаты заменяют запаздывающие метки и требуют защитных метрик.
- Ошибки планируют заранее: человек в контуре, обратимые действия, защитные правила, обнаружение и восстановление, запасной путь, который даёт решение.
- Веерные вызовы умножают вероятность хвоста, $1 - (1 - p)^k$, а процентили не складываются. Бюджет задержки проверяют по этапам, затем моделированием или нагрузочным тестом и ограничивают крайним сроком и запасным путём.
- Стоимость предсказания следует из пропускной способности, времени CPU на предсказание и целевой загрузки; для маленьких моделей размер задаёт доступность, а не вычисления.

## Пример \{#example\}

Проектный документ для проверки на мошенничество из сквозного примера, достаточно короткий, чтобы прочитать его за десять минут и отрецензировать до того, как написан какой-либо код. Магазин вымышлен, а числа документа условны и подобраны согласованными друг с другом, а не с преувеличенными синтетическими данными этой заметки. Порядок разделов следует рассуждению этой заметки и шаблону проектного документа из курса НИУ ВШЭ по инженерии LLM-систем, который ставит контракт и бюджеты раньше оценки и выбора модели ([НИУ ВШЭ, 2026](#references)); документ также покрывает вопросы глав Kästner о требованиях и главы Huyen о проектировании. Документ приведён в оригинале, на английском.

```markdown
# Design doc: payment risk check v1

Owner: risk team · Reviewers: checkout, fraud operations, data platform · Status: in review · Updated: 2026-10-20

## 1. Problem and goal
Card fraud costs the shop 0.6% of card revenue (chargebacks and fees, last 12 months).
Goal: halve fraud losses within two quarters without raising false declines above 0.5% of good payments.
Non-goals: account takeover, refund abuse, fraud by merchants.

## 2. Baseline
Today: rule R1 (review if amount > 200 EUR and new device) and the card network's own checks.
Offline on the last full month: R1 catches 30% of fraud and reviews 0.1% of payments.
The model ships only if it beats R1 on cost per 1,000 payments at the same review capacity.

## 3. Contract
Input: one payment at checkout (card, device, account, amount, country).
Output: APPROVE | HOLD (review or bank confirmation) | DECLINE, with up to three reason codes.
If the model is unavailable or late: rules R1-R4 decide. Never "approve all", never "decline all".

## 4. Budgets and qualities
Latency: risk check <= 50 ms at p99 (checkout SLO); feature lookups have a 25 ms deadline.
Throughput: 42 checks/s at peak, 1.2 M per day. Availability: 99.95% (same as checkout).
Cost: serving <= 0.01 EUR per 1,000 checks; review queue <= 0.2% of payments (2,400 a day, 30 analysts).
Freshness: model retrained at least every 30 days; card-history features <= 60 s old.
Explainability: reason codes for every HOLD and DECLINE, visible to analysts and support.

## 5. Metrics
Online (goal): fraud loss per 1,000 EUR of revenue; false-decline rate; checkout conversion.
Proxy (daily): analyst-confirmed fraud among HOLDs; share of HOLD and DECLINE (action limit: 2x plan).
Offline (gate): cost per 1,000 payments on the latest held-out week; recall at 0.2% reviewed.
Guardrails: false-decline rate and conversion must not worsen by a significant amount in the rollout test.

## 6. Planning for mistakes
Human in the loop: HOLD band sized to analyst capacity. Undo: HOLD instead of DECLINE where possible;
appeal path through support. Guardrails: R2 never auto-decline returning customers under 10 EUR;
R3 bank confirmation above 2,000 EUR on a new device; R4 known stolen cards always declined.

## 7. Data
Sources: checkout events, card network authorisations, chargebacks (arrive up to 120 days later),
analyst decisions. Labels: chargeback or analyst-confirmed fraud. Declined payments have no label:
keep 1% of would-be declines as HOLD to measure what the model blocks.

## 8. Rollout and monitoring
Shadow for two weeks (score, do not act), then 5% / 25% / 100% with the online metrics above.
Monitor input distributions, action shares, latency, fallback rate; recall as labels arrive.

## 9. Risks and open questions
Feedback loop from declines (section 7). Drift as fraudsters adapt. Fairness of declines across countries.
Who else may consume the score? Access to the score table is restricted to the risk team.
```

Разберём его по разделам:

- **Заголовок.** Владелец и названные рецензенты от каждой команды, которой касается система, — так избегают необъявленных потребителей и сюрпризов при запуске. Статус и дата делают документ живым.
- **1. Problem and goal** (задача и цель). Цель сформулирована в единицах бизнеса и со сроком и стоит в паре с защитной метрикой (ложные отклонения), чтобы её нельзя было достичь, отклоняя всех. Не-цели (non-goals) не дают объёму работ расползаться.
- **2. Baseline** (базовое решение). Правило, работающее в продакшене, и его измеренное качество. Критерий выпуска сравнивает модель с правилом в тех же единицах и при той же пропускной способности проверки, как в таблице стоимостей этой заметки.
- **3. Contract** (контракт). Что входит и что выходит, включая третье действие и коды причин, и что происходит, когда модель недоступна: решение запасного пути из раздела о планировании на случай ошибок.
- **4. Budgets and qualities** (бюджеты и качества). Таблица качеств в виде чисел, у каждого — источник: 50 мс берутся из SLO оформления заказа, 0.2% — из числа аналитиков (их 30, у каждого около 80 проверок в день). Потолок стоимости 0.01 € на 1000 проверок оставляет запас над рассчитанными 0.0024 €.
- **5. Metrics** (метрики). По строке на онлайн-, суррогатные и офлайн-метрики, с пределом действия и защитными метриками. Офлайн-гейт — тот самый, который автоматически применял пример предыдущей заметки.
- **6. Planning for mistakes** (планирование на случай ошибок). Стратегии из главы Kästner, превращённые в правила с именами (R2–R4), чтобы их можно было реализовать, протестировать и упоминать при разборе инцидентов.
- **7. Data** (данные). Откуда берутся метки и насколько они запаздывают, и мера против петли обратной связи: если не превращать небольшую долю несостоявшихся отклонений в приостановки, модель никогда не узнает, были ли её отклонения правильными.
- **8. Rollout and monitoring** (выкатка и мониторинг). Теневой режим (shadow), затем постепенное расширение охвата, оцениваемое по онлайн-метрикам; механизмы для этого дают [заметка о выкатке](/ru/notes/mlops/rolling-out-models) и [заметка о мониторинге](/ru/notes/mlops/monitoring-and-drift).
- **9. Risks and open questions** (риски и открытые вопросы). То, чего авторы пока не знают, записанное, чтобы рецензенты могли ответить или отслеживать это.

Ни в одном месте документа не названа архитектура модели. Это решение принимается позже, внутри бюджетов раздела 4.
