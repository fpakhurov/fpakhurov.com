## Отправная точка: словарь как запись \{#baseline-a-dictionary-as-a-record\}

Без классов банковский счёт можно хранить в словаре, а операции над ним сделать функциями, которые принимают этот словарь:

```python
def deposit(account, amount):
    account["balance"] += amount
    return account["balance"]
```

```text
>>> acct = {"owner": "Ada", "balance": 100}
>>> deposit(acct, 50)
150
>>> acct["balanse"] = 150
>>> acct
{'owner': 'Ada', 'balance': 150, 'balanse': 150}
```

Это работает, и [заметка о словарях](/ru/notes/python/dicts-and-sets) объясняет, почему поиск в нём быстрый. Подводит структура. Ничто не говорит, какие ключи обязаны быть у счёта, поэтому ключ с опечаткой `"balanse"` молча создаёт новую запись. Ничто не связывает `deposit` со счетами: функция принимает любой словарь с ключом `"balance"`. А `type(acct)` — это `dict`, так что ни читатель, ни программа не могут спросить, счёт ли это. Класс даёт записи имя, фиксированный способ создания и принадлежащие ей операции.

## Класс и его экземпляры \{#a-class-and-its-instances\}

Инструкция `class` создаёт **объект класса** (class object) и связывает с ним имя — так же, как `def` создаёт объект функции и связывает его имя. Вызов класса создаёт **экземпляр** (instance):

```python
class Account:
    interest = 0.02

    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        return self.balance
```

```text
>>> a = Account("Ada", 100)
>>> b = Account("Grace")
>>> a.deposit(50)
150
>>> type(a), type(a) is Account
(<class '__main__.Account'>, True)
```

Правила в том порядке, в котором их применяет Python:

1. **Инструкция class выполняет своё тело.** Тело — обычный код. Каждое присваивание и каждый `def` в нём создают имя в новом пространстве имён: здесь `interest`, `__init__` и `deposit`. Когда тело заканчивается, Python строит из этого пространства имён объект класса и связывает с ним `Account`.
2. **Вызов класса создаёт экземпляр.** `Account("Ada", 100)` сначала создаёт пустой объект типа `Account` (это работа метода `__new__`, который классы определяют редко), затем вызывает `__init__`, передавая новый объект первым аргументом, а `"Ada"` и `100` — остальными.
3. **`__init__` инициализирует, а не создаёт.** Его задача — дать новому объекту атрибуты: `self.owner = owner` и `self.balance = balance`. Он обязан вернуть `None`; вызов `Account(...)` возвращает сам объект.

Имя, ссылающееся на класс, такое как `Account`, ведёт себя как любое другое имя курса: `MyAccount = Account` связывает второе имя с тем же объектом класса, и тогда `isinstance(a, MyAccount)` равно `True`.

## Где хранятся атрибуты \{#where-attributes-live\}

У каждого экземпляра есть собственный **словарь экземпляра** (instance dictionary), `obj.__dict__`, который отображает имена атрибутов в объекты. У класса тоже есть словарь, и в нём лежит то, что определило тело класса:

```text
>>> a.__dict__
{'owner': 'Ada', 'balance': 150}
>>> b.__dict__
{'owner': 'Grace', 'balance': 0}
>>> Account.__dict__["interest"]
0.02
>>> a.interest, b.interest
(0.02, 0.02)
>>> a.interest = 0.05
>>> a.__dict__
{'owner': 'Ada', 'balance': 150, 'interest': 0.05}
>>> a.interest, b.interest, Account.interest
(0.05, 0.02, 0.02)
>>> del a.interest
>>> a.interest
0.02
>>> a.nothing
Traceback (most recent call last):
  ...
AttributeError: 'Account' object has no attribute 'nothing'
```

Прочитаем сеанс построчно. Ни у одного экземпляра нет `interest` в собственном словаре, но оба находят 0.02: чтение провалилось до класса. Присваивание `a.interest = 0.05` не изменило класс. Оно создало новую запись в `a.__dict__`, которая с этого момента **заслоняет** (shadows) атрибут класса, но только для `a`. Удаление этой записи снова открывает атрибут класса.

<aside class="callout"><strong>Ключевая идея.</strong> Чтение `obj.name` ищет сначала в собственном словаре экземпляра, затем в классе, затем в базах класса в фиксированном порядке, который называется **порядком разрешения методов** (method resolution order, MRO), и возвращает первое совпадение. Присваивание `obj.name = value` всегда пишет в собственный словарь экземпляра. Классы хранят то, что у экземпляров общее, прежде всего методы; экземпляры хранят свои данные.</aside>

Исключение из обоих правил — **дескриптор данных** (data descriptor), определённый в классе, например свойство (ниже): при чтении он проверяется раньше словаря экземпляра, а запись он перехватывает. [Заметка о модели данных](/ru/notes/python/the-data-model#descriptors-what-powers-properties-and-methods) даёт полное правило. Всё остальное в этой заметке следует из простой версии.

**Типичная ошибка: изменяемый атрибут класса.** Список, определённый в теле класса, — это один объект, общий для всех экземпляров:

```python
class Basket:
    items = []

    def add(self, x):
        self.items.append(x)
```

```text
>>> p = Basket()
>>> q = Basket()
>>> p.add("apple")
>>> q.items
['apple']
>>> p.items is q.items is Basket.items
True
```

`self.items.append(x)` — это чтение `self.items`, а не присваивание ему, поэтому оно находит список класса и меняет его на месте. Это сюрприз общей ссылки из [заметки об именах](/ru/notes/python/values-and-names#mutable-and-immutable-objects) в новом месте. Исправление — создавать список для каждого экземпляра в `__init__`: `self.items = []`. Узнать ошибку можно по симптому: изменение одного экземпляра проявляется в другом, который его не трогал.

## Методы и `self` \{#methods-and-self\}

**Метод** (method) — это функция, определённая в теле класса. В самой функции нет ничего особенного; особенное происходит, когда к ней обращаются через экземпляр:

```text
>>> Account.deposit
<function Account.deposit at 0x108fdc9e0>
>>> a = Account("Ada", 100)
>>> a.deposit
<bound method Account.deposit of <__main__.Account object at 0x108f31be0>>
>>> m = a.deposit
>>> m.__self__ is a, m.__func__ is Account.deposit
(True, True)
>>> m(10)
110
>>> Account.deposit(a, 10)
120
>>> a.deposit is a.deposit
False
```

Через класс `Account.deposit` — это обычная функция, и она принимает два аргумента. Через экземпляр `a.deposit` — это **связанный метод** (bound method): небольшой объект, который хранит функцию (`__func__`) и экземпляр (`__self__`). Его вызов вызывает функцию, подставляя экземпляр перед остальными аргументами. Поэтому `a.deposit(10)` и `Account.deposit(a, 10)` делают одно и то же, а `self` — просто имя, которое функция даёт своему первому параметру. Это имя — соглашение, а не ключевое слово, но его ожидает каждый программист на Python.

Связанный метод создаётся при каждом обращении, поэтому `a.deposit is a.deposit` равно `False` (по `==` они всё же равны). [Заметка о модели данных](/ru/notes/python/the-data-model#descriptors-what-powers-properties-and-methods) показывает механизм, который их строит.

**Типичная ошибка: забытый `self`.** Метод, определённый без параметра, всё равно получает экземпляр:

```text
>>> class Broken:
...     def hello():
...         return "hi"
...
>>> Broken().hello()
Traceback (most recent call last):
  ...
TypeError: Broken.hello() takes 0 positional arguments but 1 was given
```

«Takes 0 but 1 was given», когда в вызове явно ничего не передаётся, означает, что этим единственным аргументом был экземпляр. Добавьте `self`.

Два декоратора меняют то, что получает метод. `@classmethod` получает класс вместо экземпляра и служит обычным способом написать альтернативный конструктор, например `Account.from_dict(d)`; `from_pretrained` в библиотеках Hugging Face — один из них. `@staticmethod` не получает ни того, ни другого и представляет собой обычную функцию, хранящуюся в пространстве имён класса. Синтаксис `@` объясняет [заметка о декораторах](/ru/notes/python/closures-and-decorators).

Приватных атрибутов в Python нет. Подчёркивание в начале, `self._balance`, — соглашение, означающее «внутреннее, не использовать снаружи». Два подчёркивания в начале, `self.__balance`, заставляют Python переименовать атрибут внутри тела класса в `_Account__balance`, что не даёт подклассу случайно его затереть; это не мера защиты.

## Наследование и `super()` \{#inheritance-and-super\}

Класс можно определить как расширение другого: `class Dog(Animal)` делает `Animal` **базовым классом** (base class) для `Dog`, а `Dog` — **подклассом** (subclass) `Animal`. Подкласс наследует каждый атрибут, который не определяет сам, потому что поиск атрибута продолжается в базе.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound"

    def describe(self):
        return f"{type(self).__name__} {self.name}: {self.speak()}"

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)
        self.breed = breed

    def speak(self):
        return f"{self.name} barks"
```

```text
>>> d = Dog("Rex", "collie")
>>> d.describe()
'Dog Rex: Rex barks'
>>> d.__dict__
{'name': 'Rex', 'breed': 'collie'}
>>> isinstance(d, Animal), issubclass(Dog, Animal), type(d) is Animal
(True, True, False)
>>> Dog.__mro__
(<class '__main__.Dog'>, <class '__main__.Animal'>, <class 'object'>)
```

`describe` нет в `Dog`, поэтому поиск находит его в `Animal`. Внутри него `self.speak()` снова ищется в `self`, а это `Dog`, и первым находится `Dog.speak`: подкласс **переопределяет** (overrides) метод базы, и код, написанный в базе, вызывает переопределённую версию. `super().__init__(name)` вызывает следующий после `Dog` метод `__init__` в MRO, здесь `Animal.__init__`, чтобы база подготовила свою часть объекта. Любой класс в конечном счёте происходит от `object`, который даёт поведение по умолчанию, например `__repr__` и `__eq__`.

**Типичная ошибка: забытый `super().__init__`.** Если бы `Dog.__init__` его не вызывал, `Animal.__init__` не выполнился бы никогда, и `d.name` возбудил бы `AttributeError: 'Dog' object has no attribute 'name'`. PyTorch делает эту ошибку громкой: сеть — подкласс `nn.Module`, и присваивание слоя в `self` до вызова `super().__init__()` возбуждает `AttributeError: cannot assign module before Module.__init__() call`, потому что базовый класс ещё не создал реестр, в который записывает слои ([конвейер обучения](/ru/notes/deep-learning/pytorch-and-autograd#the-training-pipeline) в курсе «Глубокое обучение»).

## Множественное наследование и MRO \{#multiple-inheritance-and-the-mro\}

У класса может быть несколько баз. Тогда «искать в базах» требует порядка, и интересный случай — **ромб** (diamond), когда у двух баз есть общая база:

```python
class A:
    kind = "from A"
    def hello(self):
        return ["A"]

class B(A):
    def hello(self):
        return ["B"] + super().hello()

class C(A):
    kind = "from C"
    def hello(self):
        return ["C"] + super().hello()

class D(B, C):
    def hello(self):
        return ["D"] + super().hello()
```

```text
>>> [k.__name__ for k in D.__mro__]
['D', 'B', 'C', 'A', 'object']
>>> D().kind
'from C'
>>> D().hello()
['D', 'B', 'C', 'A']
>>> B().hello()
['B', 'A']
```

<AttributeLookup />

1. `d.kind` сначала ищется в словаре экземпляра, который пуст.
2. Затем в `D`, который определяет только `hello`.
3. Затем в `B`, который тоже определяет только `hello`.
4. Затем в `C`, который определяет `kind = "from C"`: найдено, поиск останавливается.
5. `A` тоже определяет `kind`, но стоит в MRO после `C`, поэтому его значение никогда не видно.

**Правило.** MRO класса вычисляется **линеаризацией C3** (C3 linearization) ([Barrett et al., 1996](#references)), которую Python принял в версии 2.3 ([Simionato](#references)). Обозначим $L[X]$ MRO класса $X$ в виде списка. Для класса без баз, кроме `object`, $L[A] = [A, \text{object}]$. Для класса $X$ с базами $B_1, \dots, B_n$:

$$
L[X] = [X] + \operatorname{merge}\bigl(L[B_1], \dots, L[B_n], [B_1, \dots, B_n]\bigr).
$$

`merge` раз за разом берёт **голову** (head, первый элемент) первого списка, голова которого не встречается в **хвосте** (tail, на любой последующей позиции) ни одного списка; она добавляет этот класс к результату и убирает его из начала каждого списка, где он стоит головой. Если такой головы нет ни у одного списка, согласованного порядка не существует, и инструкция class завершается ошибкой.

**Разобранный пример.** $L[B] = [B, A, \text{object}]$ и $L[C] = [C, A, \text{object}]$. Для $D$:

$$
\begin{aligned}
L[D] &= [D] + \operatorname{merge}([B, A, \text{object}],\ [C, A, \text{object}],\ [B, C]) \\
&= [D, B] + \operatorname{merge}([A, \text{object}],\ [C, A, \text{object}],\ [C]) \\
&= [D, B, C] + \operatorname{merge}([A, \text{object}],\ [A, \text{object}]) \\
&= [D, B, C, A, \text{object}].
\end{aligned}
$$

Строка за строкой: $B$, голова первого списка, не встречается ни в одном хвосте, поэтому берётся она (вторая строка). Новая голова первого списка — $A$, но $A$ всё ещё есть в хвосте $[C, A, \text{object}]$, поэтому слияние пропускает её и берёт $C$, голову следующего списка (третья строка). Теперь $A$, а затем `object` стоят во главе всех оставшихся списков и берутся по очереди (четвёртая строка). Важен шаг третьей строки: если взять $A$ раньше $C$, $A$ оказался бы перед собственным подклассом $C$. C3 гарантирует два свойства: каждый класс стоит раньше всех своих баз, и базы каждого класса сохраняют порядок, в котором их перечислила его инструкция `class`. Раздел «Код» реализует слияние в дюжину строк и сверяет его с `D.__mro__`.

Когда ни один порядок не удовлетворяет обоим свойствам, Python отказывается создавать класс:

```python
class A: ...
class B(A): ...
class X(A, B): ...
```

```text
Traceback (most recent call last):
  ...
TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B
```

`X(A, B)` требует `A` раньше `B`, а `B(A)` требует `B` раньше `A`.

**Что на самом деле означает `super()`.** `super().hello()` внутри `B` означает не «базовый класс `B`», а «класс, следующий за `B` в MRO типа объекта». Для экземпляра `B` это `A`, поэтому `B().hello()` даёт `['B', 'A']`. Для экземпляра `D` MRO — это `D, B, C, A`, поэтому та же строка в `B` вызывает `C.hello` — класс, который `B` нигде не упоминает; так `D().hello()` доходит до каждого класса ровно один раз. Такое **кооперативное** (cooperative) использование `super()` делает ромбы безопасными: каждый класс вызывает `super()` один раз, а MRO нанизывает вызовы в цепочку. Это работает, только если каждый класс цепочки вызывает `super()` и принимает аргументы, передаваемые по ней.

## Композиция против наследования \{#composition-against-inheritance\}

Наследование говорит «`Dog` **является** `Animal`» (is a): `Dog` можно передать любой функции, которая ожидает `Animal`, и он обязан там вести себя правильно. **Композиция** (composition) говорит «у `Trainer` **есть** модель» (has a): объект хранит другие объекты в атрибутах и вызывает их.

```python
class Stack(list):          # наследование: стек — это список?
    def push(self, x):
        self.append(x)

class Stack2:               # композиция: у стека есть список
    def __init__(self):
        self._items = []
    def push(self, x):
        self._items.append(x)
    def pop(self):
        return self._items.pop()
```

`Stack` наследует весь `list`, включая `insert(0, x)`, `sort()` и индексацию, поэтому ничто не мешает коду нарушить дисциплину «последним пришёл — первым ушёл». `Stack2` предоставляет ровно две операции, которые есть у стека, а его список можно заменить на `collections.deque`, не меняя ни одного вызывающего кода. Обычный совет ([Fluent Python, гл. 14](#references)) — предпочитать композицию и наследовать, когда подкласс действительно частный случай базы или когда этого требует фреймворк. Код глубокого обучения делает и то и другое: сеть **является** `nn.Module` (наследование, потому что фреймворк вызывает `forward`, собирает параметры и переносит модель между устройствами), и у неё **есть** слои, каждый из которых — `nn.Module`, хранящийся в атрибуте (композиция).

## Свойства \{#properties\}

Иногда атрибут должен вычисляться при чтении или проверяться при записи, причём так, чтобы использующий его код не менялся. Это делает **свойство** (property):

```python
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius            # проходит через метод записи ниже

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError(f"below absolute zero: {value}")
        self._celsius = value

    @property
    def fahrenheit(self):
        return self._celsius * 9 / 5 + 32
```

```text
>>> t = Temperature(25)
>>> t.celsius, t.fahrenheit
(25, 77.0)
>>> t.celsius = 100
>>> t.fahrenheit
212.0
>>> t.__dict__
{'_celsius': 100}
>>> t.fahrenheit = 0
Traceback (most recent call last):
  ...
AttributeError: property 'fahrenheit' of 'Temperature' object has no setter
>>> t.celsius = -300
Traceback (most recent call last):
  ...
ValueError: below absolute zero: -300
```

`@property` превращает метод `celsius` в объект типа `property`, который хранится в классе под именем `celsius`. Чтение `t.celsius` вызывает метод чтения (getter), а присваивание — метод записи (setter), хотя синтаксис тот же, что у обычного атрибута. Само значение хранится в экземпляре под другим именем, `_celsius`; если бы метод чтения хранил его как `self.celsius`, он вызывал бы сам себя и уходил бы в рекурсию, пока Python её не остановит. Свойство без метода записи доступно только для чтения.

Смысл свойств в том, что можно начать с обычного атрибута и позже, когда понадобится проверка или вычисление, превратить его в свойство, и ни один вызывающий код не придётся менять. Поэтому в коде на Python нет методов `get_balance()` и `set_balance()`: интерфейсом остаётся `obj.balance`.

## Классы данных \{#dataclasses\}

Большинство классов, которые хранят данные, повторяют одни и те же три метода: `__init__`, копирующий аргументы в атрибуты, `__repr__`, печатающий их, и `__eq__`, сравнивающий их. Декоратор `@dataclass` ([PEP 557](#references), Python 3.7) пишет их по аннотированным полям класса; такой класс называется **классом данных** (dataclass):

```python
from dataclasses import dataclass, field

@dataclass
class Point:
    x: float
    y: float = 0.0
```

```text
>>> p = Point(1.5)
>>> p
Point(x=1.5, y=0.0)
>>> p == Point(1.5, 0.0), p is Point(1.5, 0.0)
(True, False)
>>> {Point(1, 2)}
Traceback (most recent call last):
  ...
TypeError: cannot use 'Point' as a set element (unhashable type: 'Point')
```

Строки `x: float` — это **аннотации** (annotations): они называют поля и их типы, а `@dataclass` читает их, чтобы сгенерировать методы. Типы не проверяются: `Point("a")` работает. Что аннотации делают и чего не делают, объясняет [заметка об аннотациях типов](/ru/notes/python/type-hints). Класс данных сравнивает по значению, а поскольку у равных объектов должны быть равные хеши, изменяемый класс данных делается нехешируемым. Это правило объясняет [заметка о модели данных](/ru/notes/python/the-data-model#equality-and-hashing-__eq__-and-__hash__).

Три параметра покрывают большинство потребностей:

- **Изменяемым значениям по умолчанию нужна фабрика.** `items: list = []` повторило бы ошибку с общим списком из раздела выше, поэтому `@dataclass` отвергает это с `ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory`. Пишите `items: list = field(default_factory=list)`, и каждый экземпляр получит новый список.
- **`frozen=True`** заставляет присваивание полю возбуждать `FrozenInstanceError: cannot assign to field 'lr'` и делает экземпляры хешируемыми, так что они могут быть ключами словаря и элементами множества. Замороженные классы данных хорошо подходят для конфигураций экспериментов: у двух запусков с равными конфигурациями равные ключи.
- **`slots=True`** (Python 3.10) даёт классу `__slots__` — предмет следующего раздела.

```python
@dataclass(frozen=True, slots=True)
class Config:
    lr: float
    epochs: int = 10
```

```text
>>> c = Config(0.001)
>>> c
Config(lr=0.001, epochs=10)
>>> c.lr = 0.1
Traceback (most recent call last):
  ...
dataclasses.FrozenInstanceError: cannot assign to field 'lr'
>>> {c: "run 1"}[Config(0.001)]
'run 1'
```

## `__slots__` и память экземпляра \{#\_\_slots\_\_-and-the-memory-of-an-instance\}

Обычный экземпляр может в любой момент получить любой атрибут, потому что его атрибуты ведут себя как словарь. Класс, объявляющий `__slots__`, от этого отказывается: у его экземпляров фиксированный набор атрибутов, хранящихся на фиксированных позициях внутри объекта, и `__dict__` нет вовсе.

```python
class P:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x = x
        self.y = y
```

```text
>>> p = P(1, 2)
>>> p.z = 3
Traceback (most recent call last):
  ...
AttributeError: 'P' object has no attribute 'z' and no __dict__ for setting new attributes
```

Выигрыш — память. Раздел «Код» создаёт 100 000 экземпляров по три атрибута, которые все ссылаются на один общий float, чтобы учитывались только сами экземпляры, и измеряет занятую ими память через `tracemalloc`. CPython 3.14.7 на Apple M1 (macOS, arm64):

| Объект с полями `x`, `y`, `z` | Байтов на объект |
| --- | --- |
| обычный класс | 96 |
| обычный класс после однократного чтения `obj.__dict__` | 160 |
| класс с `__slots__` (а также `@dataclass(slots=True)`) | 56 |
| обычный `dict` с тремя ключами | 184 |

Вторая строка объясняет первую. CPython хранит значения атрибутов обычного экземпляра в компактном массиве, прикреплённом к объекту, а имена атрибутов — общими для всех экземпляров класса, и строит настоящий словарь, только когда код запрашивает `__dict__`; одно такое чтение стоит ещё 64 байта на объект. `__slots__` убирает даже служебные данные компактного массива: 56 байтов, на 40 меньше, чем у обычного класса. `@dataclass` без `slots=True` дал при измерении те же 96 байтов, что и обычный класс. `sys.getsizeof` сообщает для обычного экземпляра 48 байтов, потому что учитывает сам объект, но не прикреплённое к нему хранилище атрибутов; измеряйте память через `tracemalloc`, как в разделе «Код», а не через `getsizeof`. Эти числа относятся к этой версии и этой машине: старые версии CPython хранили атрибуты каждого экземпляра в отдельном словаре, и экономия от `__slots__` была больше.

Цена — гибкость: никаких новых атрибутов, никакого `__dict__` и некоторая осторожность при множественном наследовании. Используйте `__slots__` для классов с множеством мелких экземпляров, таких как узлы дерева или записи парсера; для дюжины объектов это не важно.

## Где классы используются в курсах по ML \{#where-the-ml-courses-use-classes\}

- **Модели PyTorch** — подклассы `nn.Module`, которые вызывают `super().__init__()`, хранят слои в атрибутах и определяют `forward` ([Глубокое обучение](/ru/notes/deep-learning/pytorch-and-autograd#the-training-pipeline)). Присваивание слоя в `self` — это и есть его регистрация: базовый класс перехватывает присваивание, и этот механизм объясняет [заметка о модели данных](/ru/notes/python/the-data-model).
- **Оценщики scikit-learn** (estimators) — классы, чей `__init__` только сохраняет гиперпараметры в атрибутах, а `fit` вычисляет выученные атрибуты с подчёркиванием в конце, такие как `coef_`, и возвращает `self`, чтобы можно было писать цепочку `model.fit(X, y).predict(X_new)`.
- **Конфигурации** экспериментов часто — замороженные классы данных, которые печатаются в журналах через сгенерированный `__repr__` и сравниваются сгенерированным `__eq__`.

## Что изменилось \{#what-changed\}

| | Словарь как запись (отправная точка) | Класс |
| --- | --- | --- |
| Что такое объект | `type(acct)` — это `dict` | `type(a)` — это `Account`; `isinstance` работает |
| Где хранятся данные | ключи словаря | словарь экземпляра или фиксированные слоты с `__slots__` |
| Операции | отдельные функции, принимающие любой словарь | методы, найденные через класс и связанные с экземпляром |
| Поле с опечаткой | молча создаёт новый ключ | тоже создаёт новый атрибут, если класс не использует `__slots__` или замороженный класс данных |
| Общее поведение | копировать функции | наследование, поиск в порядке MRO |
| Проверки при присваивании | нет | свойства |
| Шаблонный код | нет, но нет и структуры | `@dataclass` пишет `__init__`, `__repr__` и `__eq__` |

## Ограничения \{#limitations\}

- Правило поиска здесь — упрощённая версия. Свойства, методы и другие дескрипторы меняют его вполне определённым образом, а класс может перехватывать поиск через `__getattr__` и `__getattribute__`; полное правило — в [заметке о модели данных](/ru/notes/python/the-data-model#descriptors-what-powers-properties-and-methods).
- Классы сами являются объектами, экземплярами `type`, и инструкцию class можно настроить **метаклассом** (metaclass). Он нужен немногим программам, и этот курс метаклассы не рассматривает.
- Таблица памяти — одно измерение на одной машине с одной версией CPython. Устройство экземпляров менялось в 3.11 и позже и ещё изменится.
- Ничто в Python не обеспечивает приватность или типы: подчёркивания — соглашения, а аннотации классов данных во время выполнения не проверяются.

## Что нужно запомнить \{#what-you-should-remember\}

- `class` выполняет своё тело и строит объект класса из определённых в нём имён. Вызов класса создаёт экземпляр и выполняет для него `__init__`.
- Чтение `obj.name` ищет в словаре экземпляра, затем по порядку в классах MRO; присваивание `obj.name` пишет в экземпляр. Изменяемые атрибуты класса общие для всех экземпляров.
- `obj.method` — связанный метод: функция плюс экземпляр, который приходит в виде `self`.
- MRO — это линеаризация C3: каждый класс раньше своих баз, базы в порядке перечисления. `super()` означает «следующий в MRO типа объекта», а не «мой базовый класс».
- Предпочитайте композицию; наследуйте, когда отношение «является» настоящее или когда этого требует фреймворк.
- Свойства делают вычисляемые и проверяемые атрибуты похожими на обычные. `@dataclass` пишет шаблонные методы; `frozen=True` делает экземпляры неизменяемыми и хешируемыми; `__slots__` (или `slots=True`) экономит память на каждом экземпляре.

## Код \{#code\}

Скрипт проверяет каждый механизм заметки: словарь экземпляра против атрибутов класса, функцию, которая сообщает, где простой поиск находит имя, разобранный на части связанный метод, ромб со слиянием C3, реализованным вручную и сверенным с `D.__mro__`, свойство, замороженный класс данных со слотами и измерение памяти, на котором основана таблица. Ему нужна только стандартная библиотека; запуск — `python -I classes.py`. Работает около секунды.

```python
"""Classes: attribute lookup, bound methods, the MRO, properties and memory per instance (Python 3.14)."""
import tracemalloc
from dataclasses import FrozenInstanceError, dataclass, field

# 1. Атрибуты экземпляра хранятся в экземпляре; атрибуты класса общие
class Account:
    interest = 0.02                      # атрибут класса

    def __init__(self, owner, balance=0):
        self.owner = owner               # атрибуты экземпляра
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        return self.balance

a, b = Account("Ada", 100), Account("Grace")
a.interest = 0.05                        # создаёт атрибут экземпляра; класс не меняется
print(a.__dict__, b.__dict__, b.interest)

def where(obj, name):
    """Where plain attribute lookup finds `name`: the instance, or the first class in the MRO."""
    if name in vars(obj):
        return "instance"
    for klass in type(obj).__mro__:
        if name in vars(klass):
            return klass.__name__
    return None

print(where(a, "interest"), where(b, "interest"), where(a, "deposit"), where(a, "__repr__"))

# 2. Связанный метод — это функция плюс экземпляр
m = a.deposit
print(m.__self__ is a, m.__func__ is Account.deposit, m(10), Account.deposit(a, 10))

# 3. Ромб, его MRO и C3, вычисленная вручную
class A:
    kind = "from A"
    def hello(self):
        return ["A"]

class B(A):
    def hello(self):
        return ["B"] + super().hello()

class C(A):
    kind = "from C"
    def hello(self):
        return ["C"] + super().hello()

class D(B, C):
    def hello(self):
        return ["D"] + super().hello()

def c3(cls):
    """The C3 linearization: cls, then a merge of the bases' linearizations and the list of bases."""
    seqs = [c3(base) for base in cls.__bases__] + [list(cls.__bases__)]
    result = [cls]
    while any(seqs):
        seqs = [s for s in seqs if s]
        for s in seqs:                   # первая голова, которой нет ни в одном хвосте
            head = s[0]
            if not any(head in t[1:] for t in seqs):
                break
        else:
            raise TypeError("no consistent MRO")
        result.append(head)
        seqs = [t[1:] if t[0] is head else t for t in seqs]
    return result

print([k.__name__ for k in c3(D)], c3(D) == list(D.__mro__))
print(D().hello(), D().kind, where(D(), "kind"))
try:
    type("X", (A, B), {})                # A раньше собственного подкласса B: невозможно
except TypeError as err:
    print("TypeError:", err)

# 4. Свойство: вычисляется при чтении, проверяется при записи
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius           # проходит через метод записи

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError(f"below absolute zero: {value}")
        self._celsius = value

    @property
    def fahrenheit(self):
        return self._celsius * 9 / 5 + 32

t = Temperature(100)
print(t.fahrenheit, t.__dict__)
try:
    t.celsius = -300
except ValueError as err:
    print("ValueError:", err)

# 5. Классы данных: сгенерированные __init__, __repr__, __eq__; frozen и slots
@dataclass(frozen=True, slots=True)
class Config:
    lr: float
    epochs: int = 10
    tags: tuple = ()

@dataclass
class Batch:
    items: list = field(default_factory=list)

c = Config(0.001)
print(c, c == Config(0.001, 10), {c: "run 1"}[Config(0.001)], hasattr(c, "__dict__"))
try:
    c.lr = 0.1
except FrozenInstanceError as err:
    print("FrozenInstanceError:", err)
print(Batch().items is Batch().items)

# 6. Память на экземпляр с тремя атрибутами, измеренная через tracemalloc
class Plain:
    def __init__(self, x, y, z):
        self.x, self.y, self.z = x, y, z

class Slotted:
    __slots__ = ("x", "y", "z")
    def __init__(self, x, y, z):
        self.x, self.y, self.z = x, y, z

def plain_with_dict(x, y, z):
    p = Plain(x, y, z)
    p.__dict__                           # чтение __dict__ заставляет CPython построить настоящий словарь
    return p

N, v = 100_000, 1.5                      # одно общее значение, чтобы считались только сами экземпляры
for name, make in [("Plain", Plain), ("Plain after __dict__", plain_with_dict),
                   ("Slotted", Slotted), ("dict", lambda x, y, z: {"x": x, "y": y, "z": z})]:
    objs = [None] * N
    tracemalloc.start()
    for i in range(N):
        objs[i] = make(v, v, v)
    used = tracemalloc.get_traced_memory()[0]
    tracemalloc.stop()
    print(f"{name:21s} {used / N:5.0f} bytes per object")

# Вывод в CPython 3.14.7 на macOS (arm64); число байтов зависит от версии и платформы:
# {'owner': 'Ada', 'balance': 100, 'interest': 0.05} {'owner': 'Grace', 'balance': 0} 0.02
# instance Account Account object
# True True 110 120
# ['D', 'B', 'C', 'A', 'object'] True
# ['D', 'B', 'C', 'A'] from C C
# TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B
# 212.0 {'_celsius': 100}
# ValueError: below absolute zero: -300
# Config(lr=0.001, epochs=10, tags=()) True run 1 False
# FrozenInstanceError: cannot assign to field 'lr'
# False
# Plain                    96 bytes per object
# Plain after __dict__    160 bytes per object
# Slotted                  56 bytes per object
# dict                    184 bytes per object
```

`where` не учитывает дескрипторы, поэтому отвечает на вопрос простого правила поиска: `deposit` находится в `Account`, а `__repr__` — в `object`. `type("X", (A, B), {})` — функциональная форма инструкции `class`; она использована здесь, чтобы ошибку создания класса можно было перехватить через `try`.
