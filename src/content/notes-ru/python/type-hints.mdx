[Предыдущая заметка](/ru/notes/python/modules-and-packages) дала проекту объявленный список зависимостей, чтобы любой мог установить то, что нужно коду. Функции внутри проекта по-прежнему не объявляют, что нужно им. Принимает ли `tax` число с плавающей точкой или строку, может ли `find` вернуть `None`, какие ключи обязаны быть в словаре конфигурации — читатель узнаёт это из документации, из тела функции или из падения программы. **Аннотации типов** (type hints) записывают эти сведения в код в нотации, которую могут читать инструменты. В этой заметке мы разбираем, что такое аннотация и что Python 3.14 делает с ней при выполнении программы (очень мало и, начиная с 3.14, позже, чем раньше); как записывать типы, которые встречаются на практике, от объединений до обобщённых типов и протоколов; и что делает с ними проверяющая программа типов до запуска программы.

**Соглашения.** **Проверяющая программа типов** (type checker) — это отдельная программа, которая читает исходный код и сообщает о расхождениях между аннотациями и кодом, не выполняя его. Здесь упоминаются mypy и pyright; их версии указаны там, где показан их вывод.

## Отправная точка: типы в строках документации \{#baseline-types-in-docstrings\}

Без аннотаций типы живут в прозе:

```python
def find(words, target):
    """Return the position of target in words (a list of str), or None if absent."""
    for i, w in enumerate(words):
        if w == target:
            return i
    return None
```

Вызывающий код, который пишет `find(words, "b") + 1`, получает программу, которая работает на каждом тесте, где слово присутствует, и падает с `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'` в тот день, когда его нет. Строка документации об этом предупреждала, но её никто не читал. Те же сведения в виде аннотаций, `def find(words: list[str], target: str) -> int | None`, может прочитать проверяющая программа, и она сообщит о строке с `+ 1` ещё до запуска программы, как покажет раздел о проверяющих программах.

## Аннотации: хранятся, но не проверяются \{#annotations-stored-not-enforced\}

**Аннотация** (annotation) — это выражение, прикреплённое к параметру, возвращаемому значению или переменной через двоеточие или стрелку:

```python
def area(width: float, height: float) -> float:
    return width * height
```

```text
>>> area(3, 4)
12
>>> area("ab", 3)
'ababab'
>>> area.__annotations__
{'width': <class 'float'>, 'height': <class 'float'>, 'return': <class 'float'>}
>>> count: int = "not a number"
>>> count
'not a number'
>>> total: int
>>> total
Traceback (most recent call last):
  ...
NameError: name 'total' is not defined
```

<aside class="callout"><strong>Ключевая идея.</strong> Python не проверяет аннотации. «Наличие аннотаций не меняет семантику кода во время выполнения» ([справочник Python, Annotations](#references)): `area("ab", 3)` умножает строку на 3 так же, как без них. Аннотации хранятся в функции, классе или модуле, где их могут прочитать инструменты: проверяющие программы — до запуска программы, а библиотеки вроде `dataclasses` — во время её работы.</aside>

Прочитаем сеанс построчно. `area(3, 4)` возвращает целое число 12: `int` принимается там, где аннотирован `float`, по соглашению системы типов, и ничто его не преобразует. `area("ab", 3)` нарушает аннотацию и всё равно выполняется. Аннотации хранятся в словаре `__annotations__`. Аннотация переменной со значением, `count: int = ...`, — это обычное присваивание плюс аннотация; без значения `total: int` ничего не связывает, поэтому `total` по-прежнему не определена.

## Отложенные аннотации в Python 3.14 \{#lazy-annotations-in-python-314\}

Когда вычисляются выражения аннотаций? До Python 3.13 включительно — когда выполнялся `def`. Поэтому функция не могла упомянуть класс, определённый ниже в файле, не записав его имя строкой, `"Node"`. Начиная с Python 3.14 ([PEP 649 и PEP 749](#references)) аннотации **вычисляются отложенно** (lazily): `def` сохраняет небольшую функцию, которая их вычисляет, а само вычисление выполняется, когда кто-то запрашивает аннотации.

```python
def link(node: Node) -> Node | None:
    return node.next

class Node:
    def __init__(self, value: int):
        self.value = value
        self.next: Node | None = None
```

```text
>>> link.__annotations__
{'node': <class '__main__.Node'>, 'return': __main__.Node | None}
```

<LazyAnnotations />

1. Когда выполняется `def link`, аннотации не вычисляются. Компилятор превратил их в функцию, сохранённую как `link.__annotate__`, поэтому имя `Node` пока не нужно.
2. `class Node` определяется после этого.
3. Первое обращение к `link.__annotations__` вызывает `__annotate__`, вычисляет выражения — теперь, когда `Node` существует, — и кэширует словарь.
4. Новый модуль `annotationlib` умеет возвращать аннотации в других **форматах** (formats), не вычисляя их; это нужно инструментам, когда некоторых имён во время выполнения не существует.
5. Проверяющая программа ничего не вычисляет: она читает исходный текст.

У этого правила есть следствия, которые видны напрямую. Аннотация, которая называет что-то неопределённое, безвредна, пока её не прочитают, а аннотация с побочным эффектом выполняет его один раз, при первом обращении:

```python
def broken(x: Undefined) -> int:
    return 1
```

```text
>>> broken(5)
1
>>> broken.__annotations__
Traceback (most recent call last):
  ...
NameError: name 'Undefined' is not defined
>>> import annotationlib
>>> annotationlib.get_annotations(broken, format=annotationlib.Format.STRING)
{'x': 'Undefined', 'return': 'int'}
>>> annotationlib.get_annotations(broken, format=annotationlib.Format.FORWARDREF)
{'x': ForwardRef('Undefined', owner=<function broken at 0x106398b40>), 'return': <class 'int'>}
```

`Format.VALUE`, формат по умолчанию, вычисляет аннотации и может возбудить исключение. `Format.FORWARDREF` вычисляет то, что может, и ставит заглушку `ForwardRef` там, где имени нет. `Format.STRING` возвращает исходный текст каждой аннотации. Библиотеки, которые изучают аннотации, такие как `dataclasses`, используют эти форматы, чтобы класс мог ссылаться на типы, определённые позже.

**Старый механизм.** `from __future__ import annotations` ([PEP 563](#references), Python 3.7) превращает каждую аннотацию в модуле в строку, `{'x': 'Undefined', 'return': 'int'}`, и он встречается во многих существующих программах. В 3.14 он по-прежнему работает; справочник говорит, что он будет объявлен устаревшим и удалён, но не раньше, чем закончится срок поддержки Python 3.13 ([PEP 749](#references)). Новому коду для 3.14 он не нужен.

## Как записывать типы \{#writing-types\}

Словарь здесь — небольшой набор правил, которые свободно комбинируются ([PEP 484](#references) и последующие):

| Аннотация | Означает | С версии |
| --- | --- | --- |
| `int`, `str`, `Vector` | экземпляр этого класса или подкласса | 3.5 |
| `list[int]`, `dict[str, float]`, `set[str]` | контейнер с элементами указанных типов | 3.9 ([PEP 585](#references)) |
| `tuple[int, str]`, `tuple[float, ...]` | пара из `int` и `str`; кортеж любой длины из float | 3.9 |
| `int \| None` | `int` или `None` (старое написание — `Optional[int]`) | 3.10 ([PEP 604](#references)) |
| `Sequence[str]`, `Iterable[int]`, `Mapping[str, int]` | что угодно с этим протоколом, из `collections.abc` | 3.9 |
| `Callable[[int, str], bool]` | функция, которая принимает `int` и `str` и возвращает `bool` | 3.9 |
| `Any` | что угодно; проверяющая программа перестаёт проверять | 3.5 |

Две привычки делают аннотации полезными, а не стесняющими:

- **Принимать протоколы, возвращать конкретные типы.** Функция, которая только перебирает свой аргумент, должна принимать `Iterable[str]`, а не `list[str]`, чтобы вызывающий код мог передать кортеж, множество или генератор; возвращать она должна конкретный `list[str]`, чтобы вызывающий код знал, что можно делать с результатом. Это утиная типизация из [заметки о модели данных](/ru/notes/python/the-data-model#abstract-base-classes-against-duck-typing), записанная явно.
- **Писать `None`, когда он возможен.** Большинство настоящих ошибок, которые находят проверяющие программы, — это значение, которое может быть `None`, используемое так, будто оно есть всегда. `-> int | None` заставляет каждый вызывающий код обработать случай отсутствия.

## Обобщённые типы в синтаксисе 3.12 \{#generics-with-the-312-syntax\}

**Обобщённая** (generic) функция работает со многими типами, но сохраняет их согласованность. `first` возвращает элемент любой переданной ей последовательности; её аннотация должна говорить, что тип результата — тип элемента аргумента. Это делает **параметр типа** (type parameter) в квадратных скобках после имени ([PEP 695](#references), Python 3.12):

```python
from collections.abc import Sequence

def first[T](items: Sequence[T]) -> T:
    return items[0]

class Stack[T]:
    def __init__(self) -> None:
        self.items: list[T] = []
    def push(self, x: T) -> None:
        self.items.append(x)
    def pop(self) -> T:
        return self.items.pop()

type Pair[T] = tuple[T, T]
```

```text
>>> first([3, 1, 2]), first("abc")
(3, 'a')
>>> first.__type_params__
(T,)
>>> type(first.__type_params__[0])
<class 'typing.TypeVar'>
>>> type(Pair), Pair.__value__, Pair[int]
(<class 'typing.TypeAliasType'>, tuple[T, T], Pair[int])
>>> s = Stack[int]()
>>> s.push(1); s.push("two")
>>> s.items
[1, 'two']
```

Правила:

- **`[T]` объявляет переменную типа** (type variable) для этой функции или класса. Проверяющая программа находит `T` при каждом вызове: в `first([3, 1, 2])` `T` — это `int`, и результат — `int`; в `first("abc")` `str` — последовательность `str`, поэтому результат — `str`. Во время выполнения `T` — объект `TypeVar` и ничего больше, поэтому `Stack[int]` без возражений принял `"two"`. Проверяющая программа эту строку отвергла бы.
- **Границы и ограничения.** `[H: Hashable]` ограничивает `T` подтипами `Hashable` — это **граница** (bound). `[N: (int, float)]` ограничивает его ровно одним из перечисленных типов — это **ограничение** (constraint), так что `biggest(1, 2.5)` должен выбрать один тип для обоих аргументов. Начиная с Python 3.13 у параметра типа может быть значение по умолчанию, `[T = int]` ([PEP 696](#references)).
- **`type` создаёт псевдоним** (alias), `type Vec = list[float]`. Его значение вычисляется отложенно, как аннотации, поэтому псевдоним может ссылаться на самого себя, `type Tree = list[Tree] | int`, или на имена, определённые позже.

Синтаксис 3.12 заменяет более старое написание, которое встречается в библиотеках: `T = TypeVar("T")` на уровне модуля, затем `def first(items: Sequence[T]) -> T` и `class Stack(Generic[T])`. Оба означают одно и то же.

## Структурная типизация с `Protocol` \{#structural-typing-with-protocol\}

[Заметка о модели данных](/ru/notes/python/the-data-model#abstract-base-classes-against-duck-typing) предложила два способа описать «что угодно с методом `area`»: утиную типизацию, которую не может проверить ни один инструмент, и абстрактный базовый класс, от которого каждый класс должен наследовать или в котором должен регистрироваться. **Протокол** (protocol, [PEP 544](#references), Python 3.8) — третий способ: он описывает методы, и ему соответствует любой класс, у которого они есть, без наследования. Проверяющая программа проверяет соответствие по определению класса. Это **структурная** (structural) типизация, в противоположность **номинальной** (nominal) типизации обычных классов, где соответствуют только объявленные подклассы.

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class SupportsArea(Protocol):
    def area(self) -> float: ...

class Square:
    def __init__(self, side: float) -> None:
        self.side = side
    def area(self) -> float:
        return self.side ** 2

class Label:
    text = "hi"

def total_area(shapes: list[SupportsArea]) -> float:
    return sum(s.area() for s in shapes)
```

```text
>>> isinstance(Square(2), SupportsArea), isinstance(Label(), SupportsArea)
(True, False)
>>> total_area([Square(1), Square(2)])
5
```

`Square` нигде не упоминает `SupportsArea` и всё же ему соответствует. `@runtime_checkable` дополнительно позволяет `isinstance` проверять протокол во время выполнения, причём проверяется только наличие методов, а не их сигнатуры. Протоколы — это способ, которым аннотации типов описывают собственную утиную типизацию Python: `collections.abc.Iterable`, `Sized` и `Hashable` служат протоколами для проверяющих программ, а `ArrayLike` из NumPy — объединение множества вещей, которые можно превратить в массив.

## `TypedDict`, `Literal` и `Self` \{#typeddict-literal-and-self\}

Ещё три инструмента покрывают частые шаблоны.

**`TypedDict`** ([PEP 589](#references)) описывает словарь с фиксированными ключами, у каждого из которых свой тип, например конфигурацию, загруженную из JSON или YAML. Во время выполнения это обычный `dict`:

```python
from typing import TypedDict, NotRequired, Literal

class RunConfig(TypedDict):
    lr: float
    epochs: int
    optimizer: Literal["sgd", "adam"]
    seed: NotRequired[int]
```

```text
>>> cfg: RunConfig = {"lr": 3e-4, "epochs": 10, "optimizer": "adam"}
>>> cfg, type(cfg)
({'lr': 0.0003, 'epochs': 10, 'optimizer': 'adam'}, <class 'dict'>)
>>> sorted(RunConfig.__required_keys__), sorted(RunConfig.__optional_keys__)
(['epochs', 'lr', 'optimizer'], ['seed'])
>>> bad: RunConfig = {"lr": "fast"}
>>> bad
{'lr': 'fast'}
```

Проверяющая программа отвергает `bad`: mypy 1.7.0 сообщает о недостающих ключах `epochs` и `optimizer`, а когда их добавят, — о `str`, переданном в `lr`. Python сохраняет словарь как есть. `NotRequired` ([PEP 655](#references), Python 3.11) помечает ключ, которого может не быть.

**`Literal`** ([PEP 586](#references)) ограничивает значение несколькими точными константами: `Literal["sgd", "adam"]` принимает эти две строки и никакие другие. Он документирует строковые варианты, по которым функции выбирают поведение, и проверяющая программа ловит опечатку `"adamw"` задолго до того, как выбор сломается во время выполнения. `typing.get_args` возвращает допустимые значения, `('sgd', 'adam')`, так что код может проверять их и во время выполнения.

**`Self`** ([PEP 673](#references), Python 3.11) — тип экземпляра, на котором вызван метод. Метод, который возвращает `self` для цепочки вызовов и аннотирован `-> Self`, при вызове на подклассе возвращает тип подкласса:

```python
from typing import Self

class Builder:
    def __init__(self) -> None:
        self.parts: list[str] = []
    def add(self, part: str) -> Self:
        self.parts.append(part)
        return self

class LoudBuilder(Builder):
    def shout(self) -> Self:
        self.parts = [p.upper() for p in self.parts]
        return self
```

```text
>>> LoudBuilder().add("a").add("b").shout().parts
['A', 'B']
```

Без `Self` метод `add` был бы аннотирован `-> Builder`, и проверяющая программа отвергла бы `.shout()` на его результате, потому что у `Builder` нет `shout`. Знакомый пример — `fit` из scikit-learn, который возвращает `self`.

## Проверяющие программы типов \{#type-checkers\}

Проверяющая программа читает аннотации и код вместе и сообщает о каждом месте, где они расходятся. Вот файл, который собирает ошибки этой заметки:

```python
# check.py: определения area, find, SupportsArea, Square, Label и total_area
# из этой заметки, RunConfig как в разделе «Код» (без ключа epochs), а затем:
area("ab", 3)
position = find(["a", "b"], "b") + 1
total_area([Square(1), Label()])
cfg: RunConfig = {"lr": 3e-4, "optimizer": "adamw"}
```

mypy сообщает о четырёх ошибках, ничего не запуская (mypy 1.7.0 — версия, установленная на машине, на которой готовился курс; ей указано считать версией Python 3.12, потому что она старше 3.14; файл не использует более нового синтаксиса):

```text
$ mypy --python-version 3.12 check.py
check.py:40: error: Argument 1 to "area" has incompatible type "str"; expected "float"  [arg-type]
check.py:41: error: Unsupported operand types for + ("None" and "int")  [operator]
check.py:41: note: Left operand is of type "int | None"
check.py:42: error: List item 1 has incompatible type "Label"; expected "SupportsArea"  [list-item]
check.py:43: error: Incompatible types (expression has type "Literal['adamw']", TypedDict item "optimizer" has type "Literal['sgd', 'adam']")  [typeddict-item]
Found 4 errors in 1 file (checked 1 source file)
```

Запуск того же файла в Python рассказывает другую историю. Строка 40 возвращает `'ababab'`, строка 41 работает, потому что `"b"` случайно есть в списке, а программа останавливается на строке 42 с `AttributeError: 'Label' object has no attribute 'area'` внутри `total_area`. До строки 43 дело не доходит, а если бы и дошло, она бы не упала. Проверяющая программа нашла все четыре ошибки за один проход, включая две, которые выполнились бы молча.

Каждая ошибка называет строку, ожидаемый и фактический тип и код в квадратных скобках; `# type: ignore[arg-type]` в строке подавляет эту одну ошибку, когда мы знаем лучше проверяющей программы. Распространённые проверяющие программы на 22 октября 2026 года:

- **mypy**, самая старая из них, начатая Юккой Лехтосало (Jukka Lehtosalo); выпуск 2.4.0 от 1 октября 2026 года.
- **pyright** от Microsoft, движок расширения Pylance для VS Code; выпуск 1.1.414 на PyPI от 10 сентября 2026 года. Редакторы запускают его прямо во время набора.
- Новые, более быстрые проверяющие программы, написанные на Rust: **Pyrefly** от Meta (1.4.0, помечена как стабильная) и **ty** от Astral, создателей uv (0.0.90, в бета-версии).

Проверяющие программы сходятся на большинстве программ и различаются деталями и настройками по умолчанию, например тем, насколько строго они относятся к неаннотированному коду. Стоит выбрать одну на проект, запускать её в непрерывной интеграции вместе с тестами из [следующей заметки](/ru/notes/python/testing) и аннотировать постепенно: проверяющая программа проверяет только функции с аннотациями, так что проект может начать с самых используемых модулей.

**Чего проверяющие программы знать не могут.** Формы массивов, диапазоны чисел, содержимое файлов: аннотация `float` не говорит «от 0 до 1», а `np.ndarray` не говорит «формы (batch, 784)». Такие свойства проверяются во время выполнения утверждениями (assertions) или библиотеками, которые читают аннотации во время выполнения (ниже).

## Где аннотации типов используются в коде ML \{#where-ml-code-uses-type-hints\}

- **Объекты конфигурации** — классы данных или `TypedDict`, и библиотеки вроде pydantic читают аннотации во время выполнения, чтобы проверить и преобразовать файл конфигурации, — именно ту проверку во время выполнения, которой не делает сам Python. Раздел «Код» пишет десятистрочную версию этой идеи.
- **Сигнатуры библиотек.** PyTorch, NumPy (`numpy.typing.ArrayLike`, `NDArray[np.float32]`) и Hugging Face аннотируют свои публичные функции, и благодаря этому автодополнение в редакторе и документация становятся точными.
- **Формы в аннотациях.** Библиотеки вроде jaxtyping записывают в аннотации формы и типы данных массивов, `Float[Tensor, "batch 784"]`, и умеют проверять их во время выполнения; стандартные проверяющие программы считают их непрозрачными.

## Что изменилось \{#what-changed\}

| | Типы в строках документации (отправная точка) | Аннотации типов |
| --- | --- | --- |
| Где записаны типы | проза, в любой форме | аннотации в стандартной нотации |
| Влияние на выполнение программы | никакого | никакого, кроме хранения и инструментов, которые их читают |
| Когда вычисляются аннотации | — | отложенно, при первом обращении (3.14) |
| Кто их проверяет | никто | проверяющая программа типов, до запуска программы |
| `None`, возвращаемый на некоторых путях | сюрприз во время выполнения | ошибка, сообщённая в каждом небезопасном месте использования |
| Обобщённый код и утиная типизация | описаны словами | параметры типов и протоколы |

## Ограничения \{#limitations\}

- Аннотации типов — постепенная (gradual) система: неаннотированный код и `Any` не проверяются, а проверяющая программа строга ровно настолько, насколько строга её конфигурация.
- Заметка не рассматривает `ParamSpec` и `Concatenate` для аннотирования декораторов, `TypeIs` и `TypeGuard` для сужающих функций, перегрузки, вариантность, `Final`, `ClassVar` и `@override` (3.12). Их описывает [спецификация системы типов](#references).
- Показанный вывод mypy получен старым выпуском, запущенным на этой машине; более новые выпуски могут формулировать сообщения иначе или добавлять примечания.
- Вычисление аннотаций во время выполнения следует PEP 649 и PEP 749 в том виде, как они реализованы в CPython 3.14; код, который должен работать и на 3.13 или более старых версиях, не может полагаться на отложенное вычисление.

## Что нужно запомнить \{#what-you-should-remember\}

- Аннотация хранится, но не проверяется: Python выполняет `area("ab", 3)` так, будто её нет.
- Начиная с 3.14 аннотации вычисляются отложенно, при первом обращении к `__annotations__`; `annotationlib` читает их как значения, ссылки вперёд или строки.
- Пишите `X | None`, когда может вернуться `None`, принимайте протоколы вроде `Iterable[T]`, возвращайте конкретные типы.
- `def f[T](x: T) -> T` и `class C[T]` объявляют параметры типов (3.12); `type Alias = ...` создаёт псевдоним с отложенным вычислением.
- `Protocol` проверяет структуру, а не наследование; `TypedDict` типизирует ключи словаря; `Literal` ограничивает значение константами; `Self` типизирует методы, возвращающие экземпляр.
- Проверяющая программа (mypy, pyright, Pyrefly, ty) читает исходный код и находит несоответствия до запуска программы; её стоит запускать в CI и аннотировать постепенно.

## Код \{#code\}

Скрипт показывает всё, что сам Python делает с аннотациями типов, — хранение, отложенное вычисление и интроспекцию — и заканчивается небольшим декоратором, который делает то, чего Python не делает: при каждом вызове проверяет аргументы по простым аннотациям. Ему нужна только стандартная библиотека и Python 3.14 из-за отложенных аннотаций и синтаксиса 3.12; запуск — `python -I hints.py`. Проверяющая программа типов — отдельный инструмент, и здесь она не запускается.

```python
"""Type hints at run time in Python 3.14: storage, lazy evaluation, generics, Protocol, TypedDict, a checker."""
import annotationlib
import functools
import inspect
from collections.abc import Sequence
from dataclasses import dataclass
from typing import Literal, NotRequired, Protocol, Self, TypedDict, get_args, runtime_checkable

# 1. Аннотации хранятся, но не проверяются
def area(width: float, height: float) -> float:
    return width * height

print(area(3, 4), area("ab", 3), area.__annotations__)

# 2. Отложенное вычисление (PEP 649/749): функция может упоминать класс, определённый позже
def link(node: Node) -> Node | None:
    return node.next

class Node:
    def __init__(self, value: int) -> None:
        self.value = value
        self.next: Node | None = None

print(link.__annotations__)

def broken(x: Undefined) -> int:         # всё в порядке, пока кто-нибудь не запросит аннотации
    return 1

print(broken(5))
print("STRING", annotationlib.get_annotations(broken, format=annotationlib.Format.STRING))
refs = annotationlib.get_annotations(broken, format=annotationlib.Format.FORWARDREF)
print("FORWARDREF", {name: type(v).__name__ for name, v in refs.items()}, refs["x"].__forward_arg__)
try:
    broken.__annotations__
except NameError as err:
    print("NameError:", err)

evaluations = 0
def counted():
    global evaluations
    evaluations += 1
    return int

def f(x: counted()) -> None: ...
print("after def:", evaluations)
f.__annotations__, f.__annotations__
print("after two reads:", evaluations)

# 3. Обобщённые типы в синтаксисе 3.12 и псевдонимы типов с отложенным вычислением
def first[T](items: Sequence[T]) -> T:
    return items[0]

type Pair[T] = tuple[T, T]
type Tree = list[Tree] | int             # рекурсивный псевдоним допустим: значение вычисляется отложенно

class Stack[T]:
    def __init__(self) -> None:
        self.items: list[T] = []
    def push(self, x: T) -> Self:
        self.items.append(x)
        return self

print(first([3, 1, 2]), first("abc"), first.__type_params__, Pair.__value__, Tree.__value__)
print(Stack[int]().push(1).push("two").items)    # во время выполнения проверки нет

# 4. Protocol: структурная типизация; runtime_checkable разрешает isinstance (только по именам методов)
@runtime_checkable
class SupportsArea(Protocol):
    def area(self) -> float: ...

class Square:
    def __init__(self, side: float) -> None:
        self.side = side
    def area(self) -> float:
        return self.side ** 2

class Label:
    text = "hi"

print(isinstance(Square(2), SupportsArea), isinstance(Label(), SupportsArea))

# 5. TypedDict и Literal: во время выполнения — обычный dict и кортеж допустимых значений
class RunConfig(TypedDict):
    lr: float
    optimizer: Literal["sgd", "adam"]
    seed: NotRequired[int]

cfg: RunConfig = {"lr": 3e-4, "optimizer": "adamw"}      # проверяющая программа отвергает "adamw"; Python — нет
print(type(cfg).__name__, sorted(RunConfig.__required_keys__), get_args(RunConfig.__annotations__["optimizer"]))

# 6. Инструменты читают аннотации во время выполнения: dataclasses и небольшой проверяющий декоратор
@dataclass
class Run:
    lr: float
    tags: list[str]

print(Run("fast", "not a list"))          # dataclass использует имена, а не типы

def checked(func):
    """Check arguments against plain-class annotations on every call."""
    sig = inspect.signature(func)
    hints = annotationlib.get_annotations(func)
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        for name, value in sig.bind(*args, **kwargs).arguments.items():
            expected = hints.get(name)
            if isinstance(expected, type) and not isinstance(value, expected):
                raise TypeError(f"{name}={value!r} is not {expected.__name__}")
        return func(*args, **kwargs)
    return wrapper

@checked
def scale(x: float, k: int) -> float:
    return x * k

print(scale(1.5, 2))
try:
    scale(1.5, "2")
except TypeError as err:
    print("TypeError:", err)

# Вывод в CPython 3.14.7 на macOS (arm64):
# 12 ababab {'width': <class 'float'>, 'height': <class 'float'>, 'return': <class 'float'>}
# {'node': <class '__main__.Node'>, 'return': __main__.Node | None}
# 1
# STRING {'x': 'Undefined', 'return': 'int'}
# FORWARDREF {'x': 'ForwardRef', 'return': 'type'} Undefined
# NameError: name 'Undefined' is not defined
# after def: 0
# after two reads: 1
# 3 a (T,) tuple[T, T] list[Tree] | int
# [1, 'two']
# True False
# dict ['lr', 'optimizer'] ('sgd', 'adam')
# Run(lr='fast', tags='not a list')
# 3.0
# TypeError: k='2' is not int
```

«after def: 0» и «after two reads: 1» — это отложенное вычисление в двух числах: определение `f` ничего не вычислило, первое чтение `__annotations__` вычислило аннотацию один раз, а второе использовало закэшированный словарь. Декоратор `checked` нарочно наивен: он обрабатывает только простые классы и отверг бы `scale(2, 2)`, потому что целое число 2 — не `float`, хотя система типов принимает `int` там, где ожидается `float`. Библиотеки проверки во время выполнения реализуют эти правила как следует.
