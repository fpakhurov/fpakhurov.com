[Предыдущая заметка](/ru/notes/python/strings-and-text) рассматривала строку как последовательность символов, которая никогда не меняется. Большинству программ нужна и последовательность, которая меняется: прочитанные на данный момент измерения, слова документа, значения функции потерь при обучении, по одному на шаг. Ответ Python — **список** (list) и его родственник фиксированного размера, **кортеж** (tuple). Оба используются начиная с [заметки о значениях](/ru/notes/python/values-and-names), которая показала, что имя ссылается на объект, а присваивание ничего не копирует. Эта заметка открывает сам объект списка. Она выясняет, что такое список в памяти, почему добавление в его конец дёшево, а в начало — нет, что копирует копия списка, когда вместо списка брать кортеж и как `sorted` упорядочивает список.

**Обозначения.** $n$ — длина списка, `len(xs)`. Стоимость $O(1)$ («константная») не растёт с $n$; $O(n)$ («линейная») растёт пропорционально $n$: вдвое больше элементов — примерно вдвое больше времени. **Амортизированная** (amortized) сложность $O(1)$ означает, что отдельная операция изредка может стоить больше, но длинная серия из $m$ операций стоит в сумме $O(m)$, так что в среднем на операцию приходится константа.

## Отправная точка: блок фиксированного размера \{#baseline-a-block-of-fixed-size\}

Самый простой способ хранить последовательность — блок памяти с местом для фиксированного числа элементов, массив языка C ([C для системного программирования](/ru/notes/acos/c-for-systems-programming#pointers-and-arrays)). Элемент $i$ лежит по известному смещению от начала, поэтому его чтение — одно вычисление адреса. Беда в размере. Заполненный блок не может принять ещё один элемент; программа должна выделить блок побольше и скопировать в него всё содержимое.

Пусть блок каждый раз растёт ровно на одну ячейку. Тогда добавление $k$-го элемента копирует $k - 1$ уже сохранённых элементов, и построение списка из $n$ элементов копирует

$$
0 + 1 + 2 + \dots + (n-1) = \frac{n(n-1)}{2}
$$

элементов в сумме. При $n = 10^6$ это около $5 \cdot 10^{11}$ копирований — минуты работы ради того, чтобы собрать миллион чисел. Список должен расти, не платя такую цену.

## Что такое список: массив ссылок \{#what-a-list-is-an-array-of-references\}

<aside class="callout"><strong>Ключевая идея.</strong> Список — это **динамический массив** (dynamic array) **ссылок**. Объект списка хранит свою длину, ёмкость и указатель на отдельный массив ячеек; каждая ячейка хранит ссылку на объект, лежащий в другом месте. Чтение или замена `xs[i]` вычисляет адрес одной ячейки, поэтому стоит $O(1)$. Когда массив заполнен, `append` выделяет новый, больше в постоянное число раз, а не на одну ячейку, и благодаря этому добавление стоит $O(1)$ амортизированно. Всё, что сдвигает ячейки, — вставка или удаление не в конце, — стоит $O(n)$, а копирование списка копирует ссылки, но никогда не объекты.</aside>

**Правило.** В CPython у объекта списка, помимо заголовка объекта, три поля: `ob_size` — длина; `allocated` — ёмкость (capacity), число ячеек в его массиве; и `ob_item` — указатель на этот массив ([исходный код CPython, `Include/cpython/listobject.h`](#references)). Ячейка — это указатель, 8 байт на 64-битной машине, на какой бы объект она ни ссылалась. `sys.getsizeof` сообщает размер объекта списка вместе с массивом ячеек и не учитывает ничего, на что ячейки ссылаются:

```text
>>> import sys
>>> sys.getsizeof([])
56
>>> xs = []
>>> for v in (10, 20, 30, 40, 50):
...     xs.append(v)
...     print(len(xs), sys.getsizeof(xs))
...
1 88
2 88
3 88
4 88
5 120
>>> sys.getsizeof([10**100] * 3) == sys.getsizeof([0] * 3)
True
```

Пустой список занимает 56 байт, и всё это заголовок. Первый `append` увеличивает размер на 32 байта, четыре ячейки по 8, хотя в списке один элемент: список **выделяет память с запасом** (over-allocates). Добавления со 2-го по 4-е не стоят никакой памяти, а пятое добавляет ещё 32 байта, до ёмкости 8. Последняя строка показывает, что размер элементов не учитывается: 101-значное целое число и 0 занимают в списке по одной 8-байтовой ячейке.

<ListLayout />

1. `xs = []` создаёт объект списка с длиной 0, ёмкостью 0 и без массива.
2. Первый `append` не находит места. Он выделяет массив из 4 ячеек и записывает в ячейку 0 ссылку на объект `10`.
3. Следующие три добавления пишут в запасные ячейки. Память не выделяется, и ничего не перемещается.
4. Пятое добавление находит массив заполненным. CPython запрашивает массив из 8 ячеек, копирует в него 4 ссылки, освобождает старый массив и записывает ссылку на `50` в ячейку 4. Сами объекты `int` остаются на своих местах.
5. `xs[4]` вычисляет адрес `ob_item + 8 × 4` и читает лежащую там ссылку. Ни поиска, ни цикла здесь нет, поэтому индексация стоит $O(1)$ при любой длине.

Одна подробность шага 4: CPython расширяет массив через `realloc` ([Динамическое выделение памяти и строки](/ru/notes/acos/memory-allocation#the-contract-of-malloc-and-free)), а он может расширить блок на месте, если память за ним свободна, так что копирование происходит не всегда. Маленькие массивы берутся из собственного распределителя памяти CPython для блоков до 512 байт, большие — из `malloc` библиотеки C ([Языки высокого уровня и операционная система](/ru/notes/acos/language-runtimes#memory-reference-counting-and-a-cycle-collector)). Анализ ниже считает, что копирование происходит всегда, и это даёт верхнюю оценку.

## Почему `append` в среднем дёшев \{#why-append-is-cheap-on-average\}

`list_resize` в `Objects/listobject.c` выбирает новую ёмкость, когда списку длины $n - 1$ нужно место для $n$ элементов ([исходный код CPython](#references)):

$$
\text{новая ёмкость} = \Big(n + \big\lfloor n/8 \big\rfloor + 6\Big) \text{, округлённое вниз до кратного } 4.
$$

Применённое к пустому списку, это правило даёт ёмкости 4, 8, 16, 24, 32, 40, 52, 64, 76, 92, … Левая панель рисунка сверяет правило с измерениями: если после каждого добавления читать ёмкость как `(sys.getsizeof(xs) - 56) // 8`, все 13 изменений до 148 ячеек в точности ложатся на правило.

<ListGrowth />

**Стоимость, шаг за шагом.** Пусть $c_1 < c_2 < \dots$ — ёмкости, через которые проходит список. Посчитаем ссылки, скопированные при расширениях за $n$ добавлений.

1. Расширение происходит, когда список заполнен, при длине $c_k$, и приходит следующее добавление. Оно копирует не больше $c_k$ уже сохранённых ссылок.
2. Каждая ёмкость больше $9/8$ предыдущей. Расширение при $c_k$ запрашивает место для $n = c_k + 1$ элементов, правило даёт $n + \lfloor n/8 \rfloor + 6$ ячеек, а округление вниз отнимает не больше 3, и остаётся больше $c_k + c_k/8$. По всем расширениям до $10^6$ элементов наименьшее отношение равно 1.125005, чуть больше $9/8$. Поэтому, отсчитывая назад от последнего расширения $K$ перед $n$,

   $$
   c_{K-j} \le \left(\tfrac{8}{9}\right)^{j} c_K .
   $$

3. Расширения за $n$ добавлений копируют в сумме

   $$
   \sum_{k=1}^{K} c_k \;\le\; c_K \sum_{j=0}^{\infty} \left(\tfrac{8}{9}\right)^{j} \;=\; c_K \cdot \frac{1}{1 - 8/9} \;=\; 9\,c_K \;<\; 9n,
   $$

   где средний шаг — сумма геометрической прогрессии, а последний верен потому, что расширение при $c_K$ произошло до $n$-го добавления, так что $c_K < n$.
4. Каждое добавление ещё записывает одну ссылку в свою ячейку. Вместе $n$ добавлений стоят меньше $9n + n = 10n$ записей ссылок:

   $$
   \boxed{\;\text{стоимость } n \text{ добавлений} < 10\,n \quad\Longrightarrow\quad O(1) \text{ амортизированно на добавление}\;}
   $$

Правая панель считает копирования точно: после $10^6$ добавлений расширения скопировали 8 445 096 ссылок, 8.45 на добавление, и текущее отношение остаётся ниже 9, как требует шаг 3. По сравнению с отправной точкой, растущей на одну ячейку, работа падает с $5 \cdot 10^{11}$ копирований до менее чем $10^7$.

**Почему $9/8$, а не 2.** Любой постоянный множитель $r > 1$ даёт то же рассуждение, только с $r/(r-1)$ вместо 9: удвоение копирует не больше $2n$ ссылок. Больший множитель копирует меньше и тратит впустую больше памяти, потому что сразу после расширения пустой может оказаться доля ячеек до $1 - 1/r$: половина при удвоении, около одной из девяти у CPython. CPython выбрал экономию памяти. Другие языки выбирают иначе; `ArrayList` в Java, например, растёт в полтора раза.

**Ошибка.** Построение списка через `xs = xs + [v]` в цикле выбрасывает всё это. `+` каждый раз создаёт новый список и копирует в него все ссылки — снова $n(n-1)/2$, как в отправной точке. Нужно писать `xs.append(v)` или `xs += [v]`, что расширяет список на месте, или строить список за один шаг включением ([заметка об итерации](/ru/notes/python/iteration-and-generators)).

## Индексация и срезы \{#indexing-and-slicing\}

**Правило.** Для списка длины $n$ выражение `xs[i]` при $0 \le i < n$ — элемент в позиции $i$, а отрицательный индекс отсчитывается от конца: `xs[-1]` — это `xs[n - 1]`. Любой другой индекс возбуждает `IndexError`. **Срез** (slice) `xs[start:stop:step]` строит новый список из позиций `start`, `start + step`, …, идущих перед `stop`; опущенные границы означают «с начала» и «до конца», а границы за пределами списка обрезаются, а не вызывают ошибку.

```text
>>> xs = ['a', 'b', 'c', 'd', 'e']
>>> xs[0], xs[-1]
('a', 'e')
>>> xs[1:4]
['b', 'c', 'd']
>>> xs[::2]
['a', 'c', 'e']
>>> xs[::-1]
['e', 'd', 'c', 'b', 'a']
>>> xs[3:100]
['d', 'e']
>>> xs[5]
Traceback (most recent call last):
  ...
IndexError: list index out of range
>>> xs[1:3] = ['X']
>>> xs
['a', 'X', 'd', 'e']
```

Позиция `stop` не включается, как в `range`, поэтому `xs[:k]` и `xs[k:]` делят список на две части без потерь и повторов, а в `xs[1:4]` ровно $4 - 1 = 3$ элемента. Индексация стоит $O(1)$; срез из $k$ элементов стоит $O(k)$, потому что строит новый список и копирует в него $k$ ссылок. Присваивание срезу заменяет эти позиции элементами справа, и список может вырасти или сократиться: выше два элемента превратились в один, а элементы после них сдвинулись влево.

## Копирование: поверхностное и глубокое \{#copying-shallow-and-deep\}

Присваивание ничего не копирует, как установила [заметка о значениях](/ru/notes/python/values-and-names#names-are-references-and-assignment-copies-nothing). Когда копия нужна, бывает два её вида.

**Правило.** **Поверхностная копия** (shallow copy) — `xs.copy()`, `list(xs)`, `xs[:]` или `copy.copy(xs)` — это новый объект списка, ячейки которого хранят те же ссылки, что и оригинал: новый контейнер, те же элементы. **Глубокая копия** (deep copy), `copy.deepcopy(xs)`, копирует контейнер и, рекурсивно, каждый изменяемый объект внутри него; она ведёт таблицу уже скопированных объектов, поэтому объект, на который в оригинале две ссылки, и в копии окажется общим для двух мест, а список, содержащий сам себя, не уводит её в бесконечный цикл ([документация Python, `copy`](#references)).

```text
>>> import copy
>>> rows = [[1, 2], [3, 4]]
>>> shallow = rows.copy()
>>> deep = copy.deepcopy(rows)
>>> shallow is rows, shallow[0] is rows[0], deep[0] is rows[0]
(False, True, False)
>>> rows[0].append(99)
>>> shallow
[[1, 2, 99], [3, 4]]
>>> deep
[[1, 2], [3, 4]]
```

Поверхностная копия — другой список, но её первая ячейка ссылается на тот же внутренний список, что и `rows[0]`, поэтому изменение, сделанное через `rows`, видно в `shallow`. Изменить, на какой объект ссылается ячейка, — другое дело: `rows[0] = [7]` перепривязывает ячейку `rows` и не трогает `shallow`. Для списка чисел или строк, которые неизменяемы, поверхностная копия не хуже глубокой, поскольку ничто достижимое из неё не может измениться.

**Повторённая строка.** Ловушка `[[0] * 3] * 3`, встреченная в [заметке о значениях](/ru/notes/python/values-and-names#aliasing-surprises), — тот же механизм в другой операции. `*` над списком строит список, ячейки которого повторяют ссылки операнда, в точности как поверхностная копия. `[0] * 3` повторяет ссылку на неизменяемый `0`, и это безвредно. `[row] * 3` трижды повторяет ссылку на один изменяемый список:

```text
>>> grid = [[0] * 3] * 3
>>> grid[0][0] = 1
>>> grid
[[1, 0, 0], [1, 0, 0], [1, 0, 0]]
>>> grid[0] is grid[1]
True
>>> grid = [[0] * 3 for _ in range(3)]
>>> grid[0][0] = 1
>>> grid
[[1, 0, 0], [0, 0, 0], [0, 0, 0]]
```

<SharedRows />

**Как это распознать.** Изменение, сделанное в одном месте, появляется в нескольких. Подозреваемых нужно проверить через `is`: две строки, или строка и её копия, для которых `is` отвечает `True`, — один объект. Лекарство — создавать каждый внутренний объект отдельно, как делает включение, или через `copy.deepcopy`. Для сеток чисел правильный инструмент — массив NumPy, который хранит сами числа в одном блоке, а не ссылки на отдельные объекты ([Массивы NumPy](/ru/notes/python/numpy-arrays)).

## Вставка и удаление в начале \{#inserting-and-deleting-at-the-front\}

**Правило.** Ячейки списка идут подряд и по порядку, поэтому вставка или удаление в позиции $i$ должны сдвинуть каждую ячейку после $i$. `xs.insert(i, x)` и `del xs[i]` или `xs.pop(i)` стоят $O(n - i)$: $O(n)$ в начале, $O(1)$ в конце. `x in xs`, `xs.index(x)` и `xs.remove(x)` сравнивают с элементами по одному и тоже стоят $O(n)$.

```text
>>> xs = [1, 2, 3]
>>> xs.insert(0, 0)
>>> xs
[0, 1, 2, 3]
>>> xs.pop(0), xs
(0, [1, 2, 3])
```

Каждый из двух вызовов сдвинул три ссылки — на одну ячейку вправо, а затем обратно. Для трёх элементов это неважно; для миллиона — важно. Рисунок измеряет одну вставку и одно удаление в начале против той же пары в конце:

<FrontCost />

При $n = 10^6$ операция в начале стоит 211 мкс, а в конце 16 нс — разница больше чем в десять тысяч раз, и стоимость в начале растёт пропорционально $n$: около 0.2 нс на каждую сдвинутую 8-байтовую ссылку, это цена `memmove`, который сдвигает ячейки.

**`collections.deque`.** Когда элементы добавляются или удаляются с обоих концов, как в очереди, нужен `collections.deque` (произносится «дек», двусторонняя очередь, double-ended queue). CPython строит его как двусвязный список блоков по 64 ссылки ([исходный код CPython, `Modules/_collectionsmodule.c`](#references)): добавление с любого конца пишет в крайний блок или присоединяет новый, и ничего не сдвигается. `append`, `appendleft`, `pop` и `popleft` стоят $O(1)$; цена в том, что `d[i]` в середине должен пройти по блокам и стоит $O(n)$. С `maxlen` дек хранит только последние элементы, отбрасывая их с другого конца:

```text
>>> from collections import deque
>>> d = deque([1, 2, 3], maxlen=3)
>>> d.appendleft(0)
>>> d
deque([0, 1, 2], maxlen=3)
>>> d.append(4)
>>> d
deque([1, 2, 4], maxlen=3)
```

Поиск в ширину держит свою границу в деке, забирая слева и добавляя справа ([Поиск и планирование](/ru/notes/agents/search-and-planning#baseline-breadth-first-search)), а ограниченный дек — распространённый способ хранить последние $k$ значений функции потерь или наград в цикле обучения для скользящего среднего.

## Кортежи \{#tuples\}

**Правило.** **Кортеж** — неизменяемая последовательность. Его индексируют и режут на срезы, как список, но после создания он не может получить, потерять или заменить элемент, и у него нет `append` или `sort`. Кортеж создаёт запятая, а не скобки: `3, 4` — кортеж, `(1)` — целое число 1, а кортежу из одного элемента нужна завершающая запятая, `(1,)`.

```text
>>> point = 3, 4
>>> point
(3, 4)
>>> point[0] = 5
Traceback (most recent call last):
  ...
TypeError: 'tuple' object does not support item assignment
>>> (1), (1,)
(1, (1,))
>>> import sys
>>> sys.getsizeof(()), sys.getsizeof((1, 2, 3)), sys.getsizeof([1, 2, 3])
(48, 72, 88)
```

**Зачем он нужен.** Поскольку длина кортежа никогда не меняется, он хранит ссылки внутри самого объекта, без отдельного массива и без запасных ячеек: $48 + 8 \cdot 3 = 72$ байта на три элемента против 88 у списка (литералу которого досталась одна запасная ячейка). Поскольку содержимое кортежа никогда не меняется, кортеж, все элементы которого хешируемы, сам **хешируемый** (hashable) и может быть ключом словаря или элементом множества, а список не может; почему — объясняет [следующая заметка](/ru/notes/python/dicts-and-sets). CPython 3.14 хранит хеш внутри кортежа, однажды его вычислив, и на это уходят 8 из 48 байт ([исходный код CPython, `Include/cpython/tupleobject.h`](#references)). Как показала заметка о значениях, неизменяемость поверхностна: кортеж, содержащий список, не может заменить этот список другим, но сам список меняться может, и такой кортеж не хешируем.

**Упаковка и распаковка.** Выражение через запятую **упаковывает** (packs) значения в кортеж; цель через запятую **распаковывает** (unpacks) любой итерируемый объект в имена, позиция за позицией. Имя со звёздочкой собирает всё оставшееся в список:

```text
>>> x, y = point
>>> x, y
(3, 4)
>>> a, b = 1, 2
>>> a, b = b, a
>>> a, b
(2, 1)
>>> first, *rest = [1, 2, 3, 4]
>>> first, rest
(1, [2, 3, 4])
>>> x, y = (1, 2, 3)
Traceback (most recent call last):
  ...
ValueError: too many values to unpack (expected 2, got 3)
```

`a, b = b, a` меняет местами два имени без временной переменной: правая часть вычисляется полностью, до объектов, на которые ссылаются `b` и `a`, прежде чем перепривязывается любое из имён. Та же распаковка происходит в `for i, word in enumerate(words)`, где каждый элемент — пара, и в `return mean, std` из функции, которая возвращает один кортеж, а вызывающий код его распаковывает.

**Кортежи как записи.** Кортеж фиксированной длины, позиции которого что-то значат, (имя, балл) или (x, y), — это запись. `collections.namedtuple` даёт позициям имена без затрат памяти, поскольку именованный кортеж (namedtuple) остаётся кортежем:

```text
>>> from collections import namedtuple
>>> Point = namedtuple('Point', ['x', 'y'])
>>> p = Point(3, 4)
>>> p
Point(x=3, y=4)
>>> p.x, p[1]
(3, 4)
>>> p._replace(x=5)
Point(x=5, y=4)
>>> p.x = 5
Traceback (most recent call last):
  ...
AttributeError: can't set attribute
```

`_replace` возвращает новую запись с одним изменённым полем — обычный способ «изменить» неизменяемый объект. `typing.NamedTuple` объявляет то же самое синтаксисом класса с аннотациями типов, а класс данных (dataclass) из [заметки о классах](/ru/notes/python/classes-and-objects) — изменяемая альтернатива. Код машинного обучения в следующих курсах полон кортежей: форма массива NumPy или тензора PyTorch, `x.shape`, — кортеж вроде `(64, 3, 32, 32)`, а `Dataset` возвращает каждый пример как пару (вход, метка), которую цикл обучения распаковывает.

## Сортировка \{#sorting\}

**Правило.** `sorted(iterable)` возвращает новый отсортированный список и не трогает свой аргумент; `xs.sort()` сортирует список на месте и возвращает `None`. Оба принимают `key` — функцию, которая вызывается один раз для каждого элемента и результаты которой сравниваются вместо самих элементов, — и `reverse=True`. Обе сортировки **устойчивы** (stable): элементы с равными ключами сохраняют исходный порядок.

```text
>>> words = ['pear', 'fig', 'apple', 'kiwi', 'banana']
>>> sorted(words)
['apple', 'banana', 'fig', 'kiwi', 'pear']
>>> sorted(words, key=len)
['fig', 'pear', 'kiwi', 'apple', 'banana']
>>> scores = [('cid', 90), ('bob', 85), ('ann', 90), ('dan', 85)]
>>> sorted(scores, key=lambda r: r[1], reverse=True)
[('cid', 90), ('ann', 90), ('bob', 85), ('dan', 85)]
>>> sorted(scores, key=lambda r: (-r[1], r[0]))
[('ann', 90), ('cid', 90), ('bob', 85), ('dan', 85)]
```

При сортировке по длине `'pear'` остаётся перед `'kiwi'`: у обоих длина 4, и устойчивость сохраняет их порядок во входных данных. В списке баллов `'cid'` остаётся перед `'ann'` по той же причине. Последняя строка сортирует по ключу-кортежу: кортежи сравниваются позиция за позицией, поэтому ключ упорядочивает по убыванию балла (благодаря знаку минус), а при равенстве — по имени. Устойчивость позволяет сортировать и в несколько проходов: сначала по второстепенному ключу, потом по главному, и второстепенный порядок сохранится внутри каждой группы.

**Две ошибки.** `xs = xs.sort()` связывает `xs` с `None`, потому что `sort` возвращает `None` — намеренный сигнал, что список изменён на месте. И элементы, которые нельзя сравнить через `<`, нельзя отсортировать: `sorted([3, 'a', 1])` возбуждает `TypeError: '<' not supported between instances of 'str' and 'int'`.

**Алгоритм.** CPython сортирует алгоритмом **Timsort**, который написал Тим Петерс в 2002 году ([`Objects/listsort.txt`](#references)). Он проходит по списку в поиске **серий** (runs) — участков, которые уже упорядочены по возрастанию или строго по убыванию (последние разворачиваются на месте), дополняет короткие серии до минимальной длины сортировкой бинарными вставками и сливает серии, переходя на поиск галопом (galloping), когда одна серия раз за разом выигрывает. Начиная с Python 3.11 порядок слияния серий следует политике **powersort** Манро и Вильда, которая доказуемо близка к оптимальной при любом распределении длин серий; поиск серий, вставки и галоп не изменились ([Munro and Wild, 2018](#references); `listsort.txt` в 3.11 против 3.10). В худшем случае Timsort делает $O(n \log n)$ сравнений, а на уже упорядоченных входных данных — $n - 1$. Подсчёт вызовов `__lt__` на 1000 элементах (раздел «Код»):

| Входные данные | Сравнений |
| --- | --- |
| уже отсортированы | 999 |
| две возрастающие серии: чётные числа, затем нечётные | 1999 |
| случайный порядок | 8667 |

На случайных входных данных никакая сортировка сравнениями не может в среднем обойтись меньше чем $\log_2(1000!) \approx 8529$ сравнениями, поскольку каждое сравнение в лучшем случае вдвое сокращает $1000!$ возможных порядков; 8667 у Timsort — в пределах 2% от этой границы. Реальные данные часто частично упорядочены — журнал, отсортированный по времени, с несколькими опоздавшими записями, — и на них Timsort работает гораздо меньше.

**Где это используется в курсах по ML.** Метрики ранжирования сортируют предсказания по значению модели ([метрики классификации](/ru/notes/ml/classification-metrics) для ROC-кривых), а методы ближайших соседей сортируют расстояния; для больших массивов работа переходит к `np.sort` и `np.argsort`, которые сортируют числа, не вызывая код на Python при каждом сравнении.

## Ограничения \{#limitations\}

- **Числа CPython.** Правило роста, 56-байтовый заголовок и размер блока дека — детали CPython 3.14 в 64-битной сборке, а не языка. Сборка без GIL (free-threaded) при каждом расширении выделяет новый массив вместо вызова `realloc`, чтобы другие потоки могли продолжать читать старый ([исходный код CPython](#references)).
- **`sys.getsizeof` поверхностен.** Он учитывает список и его ячейки, но не объекты, на которые ячейки ссылаются. Список из миллиона целых чисел занимает около 8 МБ ячеек плюс от 28 до 32 байт на каждый отдельный объект `int`; [заметка об итерации](/ru/notes/python/iteration-and-generators) измеряет полный объём через `tracemalloc`.
- **Время измерено на одной машине.** Рисунки и раздел «Код» измеряют Apple M1 с CPython 3.14.7; форма кривых, линейная против постоянной, переносится на другие машины, а наносекунды — нет.
- **Что не рассмотрено.** `array.array` — компактный массив машинных чисел из стандартной библиотеки, `heapq` для очередей с приоритетом и `bisect` для двоичного поиска в отсортированном списке.

## Что нужно запомнить \{#what-you-should-remember\}

- Список — динамический массив ссылок: заголовок с длиной, ёмкостью и указателем на ячейки. Индексация и замена элемента стоят $O(1)$.
- `append` стоит $O(1)$ амортизированно, потому что ёмкость растёт в постоянное число раз, в CPython примерно в 9/8: $n$ добавлений копируют в сумме меньше $9n$ ссылок.
- Вставка или удаление не в конце сдвигает следующие ячейки и стоит $O(n)$; для очереди нужен `collections.deque`.
- Срезы, `list(xs)`, `xs.copy()` и `*` копируют ссылки, а не объекты: это поверхностные копии. `copy.deepcopy` копирует всё изменяемое внутри. В `[[0] * 3] * 3` одна строка, повторённая трижды.
- Кортеж — фиксированная неизменяемая последовательность: меньше списка, хешируем, когда хешируемы его элементы, и естественная форма записи. Распаковка через запятые и `*` работает с любым итерируемым объектом.
- `sorted` возвращает новый список, `list.sort` сортирует на месте и возвращает `None`; оба принимают `key` и устойчивы. Timsort в CPython, с политикой слияния powersort начиная с 3.11, использует уже упорядоченные серии.

## Код \{#code\}

Скрипт по очереди измеряет каждое утверждение: ёмкости по `sys.getsizeof` и правило роста, которое их воспроизводит, ссылки, скопированные за миллион добавлений, поверхностные и глубокие копии и повторённую строку, цену начала списка против дека, кортежи и именованный кортеж, а также число сравнений Timsort. Ему нужна только стандартная библиотека; запуск — `python -I lists.py`. Он работает меньше секунды. Размеры — для 64-битной сборки, время меняется от машины к машине.

```python
"""Lists, tuples and deques: growth, copying and the cost of each operation (Python 3.14)."""
import copy
import random
import sys
import timeit
from collections import deque, namedtuple

# 1. Список выделяет память с запасом: читаем ёмкость по sys.getsizeof (8 байт на ячейку)
EMPTY = sys.getsizeof([])
def capacity(xs):
    return (sys.getsizeof(xs) - EMPTY) // 8

xs, caps = [], [0]
for i in range(130):
    xs.append(i)
    if capacity(xs) != caps[-1]:
        caps.append(capacity(xs))
print("empty list:", EMPTY, "bytes; capacities:", caps)

# 2. Правило роста из Objects/listobject.c воспроизводит каждую ёмкость
def grow(newsize, oldsize):
    new = (newsize + (newsize >> 3) + 6) & ~3
    if newsize - oldsize > new - newsize:      # большой скачок: без запаса
        new = (newsize + 3) & ~3
    return new

model, cap = [0], 0
for n in range(1, 131):
    if n > cap:
        cap = grow(n, n - 1)
        model.append(cap)
print("rule matches:", model == caps)

# 3. Амортизированная стоимость: ссылки, скопированные всеми расширениями, если каждое переносит массив
cap = copies = 0
for n in range(1, 10**6 + 1):
    if n > cap:
        copies += n - 1
        cap = grow(n, n - 1)
print(f"copies for 10**6 appends: {copies}, per append {copies / 10**6:.2f}")

# 4. Копии поверхностные, если не попросить глубокую; * повторяет ссылки
rows = [[1, 2], [3, 4]]
shallow, deep = rows.copy(), copy.deepcopy(rows)
rows[0].append(99)
print("shallow:", shallow, " deep:", deep)
grid = [[0] * 3] * 3
grid[0][0] = 1
print("[[0] * 3] * 3:", grid, grid[0] is grid[2])

# 5. Начало списка стоит O(n), начало дека — нет
n, k = 100_000, 2000
xs, d = list(range(n)), deque(range(n))
def front():
    for _ in range(k): xs.insert(0, None); xs.pop(0)
def back():
    for _ in range(k): xs.append(None); xs.pop()
def dq():
    for _ in range(k): d.appendleft(None); d.popleft()
for name, f in [("list insert(0)/pop(0)", front), ("list append/pop", back), ("deque appendleft/popleft", dq)]:
    t = min(timeit.repeat(f, number=1, repeat=5)) / (2 * k) * 1e9
    print(f"{name:26s} {t:9.1f} ns per operation at n = {n}")

# 6. Кортежи: фиксированный размер, без запасных ячеек, записи с именами
Point = namedtuple("Point", ["x", "y"])
p = Point(3, 4)
x, y = p
print(p, x + y, p._replace(x=5), sys.getsizeof((1, 2, 3)), sys.getsizeof([1, 2, 3]))

# 7. Сортировка устойчива и использует порядок, уже имеющийся в данных
class Counted:
    calls = 0
    def __init__(self, v): self.v = v
    def __lt__(self, other):
        Counted.calls += 1
        return self.v < other.v

random.seed(0)
for name, data in [("sorted", list(range(1000))), ("two-run", list(range(0, 1000, 2)) + list(range(1, 1000, 2))),
                   ("random", random.sample(range(1000), 1000))]:
    Counted.calls = 0
    sorted(Counted(v) for v in data)
    print(f"comparisons to sort 1000 {name} items: {Counted.calls}")
scores = [("cid", 90), ("bob", 85), ("ann", 90), ("dan", 85)]
print(sorted(scores, key=lambda r: r[1], reverse=True))

# Вывод в CPython 3.14.7 на Apple M1, macOS (arm64); размеры — для 64-битной сборки, время меняется:
# empty list: 56 bytes; capacities: [0, 4, 8, 16, 24, 32, 40, 52, 64, 76, 92, 108, 128, 148]
# rule matches: True
# copies for 10**6 appends: 8445096, per append 8.45
# shallow: [[1, 2, 99], [3, 4]]  deep: [[1, 2], [3, 4]]
# [[0] * 3] * 3: [[1, 0, 0], [1, 0, 0], [1, 0, 0]] True
# list insert(0)/pop(0)        18026.2 ns per operation at n = 100000
# list append/pop                 14.4 ns per operation at n = 100000
# deque appendleft/popleft        15.4 ns per operation at n = 100000
# Point(x=3, y=4) 7 Point(x=5, y=4) 72 88
# comparisons to sort 1000 sorted items: 999
# comparisons to sort 1000 two-run items: 1999
# comparisons to sort 1000 random items: 8667
# [('cid', 90), ('ann', 90), ('bob', 85), ('dan', 85)]
```
