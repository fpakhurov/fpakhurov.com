## Зачем тестировать? \{#why-test\}

Программа, которая работала вчера, может перестать работать сегодня, хотя никто не трогал сломавшуюся строку. Кто-то изменил функцию, которую она вызывает, или библиотеку, которую она импортирует, или форму данных, которые она читает. Запуск программы вручную с просмотром вывода ловит часть таких поломок — один раз и для тех входных данных, о которых подумали в этот день. **Автоматический тест** — это код, который смотрит вместо человека: он вызывает проверяемый код с фиксированными входными данными и сравнивает результат с тем, каким он должен быть. Набор тестов (test suite) запускать дёшево, поэтому его запускают после каждого изменения, и изменение, которое что-то сломало, обнаруживается через несколько минут, а не через несколько недель.

Тесты также фиксируют, что значит «правильно». Строка `assert mean([1, 3]) == 2.0` заставляет решить, чему равно среднее пустого списка, и это решение дальше живёт в наборе тестов, а не в чьей-то памяти.

**Модульный тест** (unit test) проверяет одну небольшую единицу кода, обычно одну функцию, в изоляции: фиксированный вход, один вызов, проверка результата. Он выполняется за миллисекунды и при падении указывает на одну функцию. **Интеграционный тест** (integration test) запускает несколько частей вместе (прочитать файл, очистить данные, обучить модель) и ловит ошибки, которые живут на стыках между единицами. Проекту нужны оба вида; эта заметка о модульных тестах, из которых состоит большая часть набора.

## Отправная точка: проверка вручную \{#baseline-checking-by-hand\}

Возьмём модуль `stats.py` с функцией, которую мы будем тестировать до конца заметки:

```python
def mean(values):
    if not values:
        raise ValueError("mean of an empty sequence")
    return sum(values) / len(values)
```

Отправная точка — попробовать её в REPL: `mean([1, 2, 3])` печатает `2.0`, это похоже на правду, и можно двигаться дальше. Здесь не работают три вещи. Проверка не сохранена, поэтому никто не повторит её после следующего изменения. Она покрывает только те случаи, которые случилось набрать. И решение, что `2.0` «похоже на правду», принимает человек, который на двадцатый раз будет смотреть уже не так внимательно.

Первое улучшение — записать проверку в виде **утверждения** (assert), инструкции `assert`. `assert expr` вычисляет `expr`; если результат истинен, ничего не происходит, если ложен, Python возбуждает `AssertionError`:

```text
$ python -c "assert 2.5 == 2"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
    assert 2.5 == 2
           ^^^^^^^^
AssertionError
```

Проверка теперь автоматическая, но сообщение бесполезно. Для `assert mean([1, 2, 3, 4]) == 2` в скрипте отчёт покажет строку исходного кода и `AssertionError`, но не то, что вернула `mean`. Кроме того, при запуске Python с ключом `-O` инструкции `assert` удаляются целиком (`python -O -c "assert 2.5 == 2; print('assert skipped')"` печатает `assert skipped`), так что `assert` никогда ничего не защищает в рабочем коде. pytest исправляет сообщение и добавляет всё остальное, что нужно набору тестов.

## pytest: обычные функции и обычные assert \{#pytest-plain-functions-and-plain-asserts\}

<aside class="callout"><strong>Ключевая идея.</strong> Тест для pytest — обычная функция, имя которой начинается с `test`, в файле, имя которого начинается с `test_`, и в ней используется обычный `assert`. pytest находит тесты по этим именам, при импорте файла переписывает каждый `assert` так, чтобы при падении было видно участвующие значения, и передаёт тесту аргументы из **фикстур** (fixtures) — функций, которые готовят то, что нужно тесту, и убирают за ним.</aside>

Правила сбора тестов из документации pytest ([pytest, «Conventions for Python test discovery»](#references)):

1. Начиная с аргументов команды (с текущей папки, если аргументов нет), pytest обходит папки и собирает файлы с именами `test_*.py` или `*_test.py`.
2. Он импортирует каждый файл и собирает функции уровня модуля с именами `test*`, а также методы с именами `test*` у классов с именами `Test*`, в которых нет `__init__`.
3. Каждый собранный тест выполняется отдельно. Тест **проходит** (passes), если функция возвращает управление, **падает** (fails), если она возбуждает исключение (`AssertionError` или любое другое), и считается **ошибкой** (error), если исключение возбуждает при подготовке нужная ему фикстура.

Файл тестов для `stats.py` с одним намеренно неверным ожиданием:

```python
# test_stats.py
from stats import mean

def test_mean_of_three():
    assert mean([1, 2, 3]) == 2.0

def test_mean_of_four():
    assert mean([1, 2, 3, 4]) == 2   # a wrong expectation, on purpose
```

```text
$ python -m pytest
============================= test session starts ==============================
platform darwin -- Python 3.14.7, pytest-9.1.1, pluggy-1.7.0
rootdir: .../t1
collected 10 items

test_stats.py .F....F...                                                 [100%]

=================================== FAILURES ===================================
______________________________ test_mean_of_four _______________________________

    def test_mean_of_four():
>       assert mean([1, 2, 3, 4]) == 2   # a wrong expectation, on purpose
        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
E       assert 2.5 == 2
E        +  where 2.5 = mean([1, 2, 3, 4])

test_stats.py:13: AssertionError
```

(В полном файле, который ниже показан по частям, десять тестов и ещё одно падение, которое объясняет раздел о числах; эта часть отчёта здесь вырезана.) Отчёт читают со строки, помеченной `>`: это строка, где произошло падение. Строки с пометкой `E` показывают сравнение с подставленными значениями, `2.5 == 2`, и откуда взялось 2.5: из вызова `mean([1, 2, 3, 4])`. Каждая точка в строке прогресса — прошедший тест, каждая `F` — упавший, в порядке следования в файле. Последняя строка, `2 failed, 8 passed in 0.05s`, — итог, а код завершения команды отличен от нуля, если что-то упало; именно его проверяет сервис непрерывной интеграции (continuous integration).

**Откуда такое подробное сообщение: переписывание утверждений.** Простой `assert` возбуждает голый `AssertionError`, как показала отправная точка. pytest получает значения потому, что выполняет файл тестов не в том виде, в каком он написан. Когда pytest импортирует модуль тестов, **хук импорта** (import hook) читает исходный код, разбирает его в синтаксическое дерево и заменяет каждую инструкцию `assert` кодом, который вычисляет каждое подвыражение во временную переменную, а при падении теста форматирует эти значения в сообщение ([pytest, «Assertion introspection details»](#references)). Переписанный модуль компилируется и кэшируется в `__pycache__`, как любой другой. Два следствия: переписываются только модули тестов и файлы `conftest.py` (во вспомогательных модулях `assert` остаются простыми, если их не зарегистрировать через `pytest.register_assert_rewrite`), а [синтаксическое дерево](/ru/notes/python/how-cpython-runs-code) — то же самое, которое строит компилятор CPython, и именно поэтому переписывание вообще возможно.

**Типичная ошибка: тест, который не может упасть.** `assert (mean([1, 2]), 1.5)` утверждает кортеж, а непустой кортеж всегда истинен. pytest замечает это при переписывании и печатает в сводке предупреждений `PytestAssertRewriteWarning: assertion is always true, perhaps remove parentheses?` (обычный Python выдаёт `SyntaxWarning` с тем же текстом), но тест считается прошедшим, что бы ни вернула `mean`: прогон заканчивается строкой `1 passed, 1 warning`. Родственная ловушка: тестовая функция, имя которой не начинается с `test`, или файл с именем не вида `test_*.py` никогда не собираются, а «0 тестов выполнено» с первого взгляда выглядит как успех. Прежде чем доверять новому тесту, его стоит один раз намеренно уронить (поменяв ожидаемое значение).

## Фикстуры: что нужно тесту \{#fixtures-what-a-test-needs\}

Тесту часто нужно что-то подготовленное: файл для чтения, небольшой набор данных, модель с известными весами. **Фикстура** — функция, помеченная декоратором `@pytest.fixture`. Тест запрашивает её, называя её имя среди своих параметров, а pytest вызывает фикстуру и передаёт тесту возвращённое значение ([pytest, «How to use fixtures»](#references)). `tmp_path` — встроенная фикстура: новая пустая папка в виде `pathlib.Path`, своя для каждого теста, так что тесты не видят файлов друг друга.

```python
import pytest
from stats import read_scores

@pytest.fixture
def scores_file(tmp_path):
    path = tmp_path / "scores.csv"
    path.write_text("ada,91.5\nalan,78\n", encoding="utf-8")
    return path

def test_read_scores(scores_file):
    assert read_scores(scores_file) == {"ada": 91.5, "alan": 78.0}
```

Правило: pytest сопоставляет каждому имени параметра теста фикстуру с тем же именем, определённую в файле тестов, в файле `conftest.py` в той же папке или выше либо встроенную. Фикстура сама может запрашивать фикстуры (`scores_file` запрашивает `tmp_path`), поэтому фикстуры образуют граф, и pytest готовит их в порядке зависимостей.

**Очистка через `yield`.** Фикстура, после которой нужно убрать, не возвращает значение, а отдаёт его через `yield`; код после `yield` выполняется после теста, прошёл тест или упал. **Область действия** (scope) задаёт, сколько живёт значение: `"function"` (по умолчанию, новое значение для каждого теста), `"module"`, `"session"`. Ключ `--setup-show` печатает порядок:

```python
@pytest.fixture(scope="module")
def database():
    yield {"users": 0}               # готовится один раз на весь файл

@pytest.fixture
def user(database):
    database["users"] += 1
    yield "ada"
    database["users"] -= 1           # отменяем, чтобы следующий тест начал с чистого листа

def test_one(user, database):
    assert database["users"] == 1

def test_two(user, database):
    assert database["users"] == 1
```

```text
$ python -m pytest --setup-show -q test_order.py

    SETUP    M database
        SETUP    F user (fixtures used: database)
        test_order.py::test_one (fixtures used: database, user) .
        TEARDOWN F user
        SETUP    F user (fixtures used: database)
        test_order.py::test_two (fixtures used: database, user) .
        TEARDOWN F user
    TEARDOWN M database
2 passed in 0.00s
```

`M` отмечает фикстуру с областью действия «модуль»: она готовится один раз и убирается после последнего теста файла; `F` отмечает фикстуру с областью действия «функция», которая готовится и убирается вокруг каждого теста. Оба теста видят одного пользователя, потому что `user` отменяет своё изменение. Если удалить строку после её `yield`, `test_two` падает с `assert 2 == 1`: состояние просочилось из одного теста в следующий. Это самая частая причина того, что тест проходит отдельно и падает в полном наборе, и причина, по которой область действия по умолчанию — самая короткая.

<PytestRun />

1. **Сбор.** pytest находит `test_stats.py`, импортирует его и составляет список тестов. `parametrize` (следующий раздел) превращает одну функцию в несколько элементов.
2. **Переписывание.** При импорте хук импорта переписывает каждый `assert` так, чтобы тот запоминал значения своих подвыражений.
3. **Поиск фикстур.** У `test_read_scores` параметр `scores_file` называет фикстуру, которой нужна встроенная фикстура `tmp_path`.
4. **Подготовка.** Фикстуры выполняются в порядке зависимостей, до своего `return` или `yield`: `tmp_path` создаёт папку, `scores_file` записывает в неё файл.
5. **Вызов.** Тест выполняется со значениями фикстур в качестве аргументов.
6. **Очистка и отчёт.** Код после каждого `yield` выполняется в порядке, обратном подготовке, и записывается исход: `.` для прошедшего теста, `F` с переписанным сообщением для упавшего.

## Много случаев: `parametrize` \{#many-cases-parametrize\}

Три теста, которые различаются только данными, — это один тест с таблицей. **Параметризация** (parametrization): `@pytest.mark.parametrize` принимает имена аргументов одной строкой и список кортежей, и pytest порождает по тесту на каждый кортеж:

```python
@pytest.mark.parametrize("values, expected", [
    ([5], 5.0),
    ([1, 3], 2.0),
    ([-1, 0, 1], 0.0),
])
def test_mean_cases(values, expected):
    assert mean(values) == expected
```

```text
$ python -m pytest -v -k cases
...
test_stats.py::test_mean_cases[values0-5.0] PASSED                       [ 33%]
test_stats.py::test_mean_cases[values1-2.0] PASSED                       [ 66%]
test_stats.py::test_mean_cases[values2-0.0] PASSED                       [100%]

======================= 3 passed, 7 deselected in 0.03s ========================
```

У каждого случая свой идентификатор в квадратных скобках, построенный из значений параметров (список превращается в `values0`, число — в своё значение), и каждый случай проходит или падает сам по себе: одна плохая строка не скрывает остальные, а цикл внутри одного теста скрыл бы. `-k cases` выбирает тесты, в имени которых есть `cases`, а `-v` печатает по строке на тест.

## Ожидаемые исключения: `pytest.raises` \{#expected-exceptions-pytestraises\}

Пустой список — часть контракта `mean`: на нём она должна возбуждать `ValueError`. Тест этого использует `pytest.raises` как контекстный менеджер:

```python
def test_mean_of_empty_raises():
    with pytest.raises(ValueError, match="empty"):
        mean([])
```

Правило: тест проходит, если блок возбуждает исключение указанного типа (или его подкласса), сообщение которого соответствует регулярному выражению `match`; поиск выполняется функцией `re.search`. Если блок завершается нормально, тест падает с `DID NOT RAISE`, а исключение другого типа проходит насквозь и роняет тест как обычно. Блок стоит ограничить одним вызовом, который должен возбудить исключение: блок `with` из десяти строк пройдёт, если исключение ожидаемого типа возбудит любая из них, в том числе не та, которую имели в виду. [Заметка о файлах и исключениях](/ru/notes/python/files-and-exceptions) разбирает инструкцию `with` и иерархию исключений, на которые опирается `pytest.raises`.

## Доктесты \{#doctests\}

**Доктест** (doctest) — пример в строке документации, записанный как сеанс REPL, который инструмент выполняет и посимвольно сравнивает с показанным выводом ([документация Python, `doctest`](#references)):

```python
def mean(values):
    """Return the arithmetic mean of a non-empty sequence.

    >>> mean([1, 2, 3])
    2.0
    >>> mean([])
    Traceback (most recent call last):
        ...
    ValueError: mean of an empty sequence
    """
```

```text
$ python -m doctest -v stats.py
...
1 item passed all tests:
   2 tests in stats.mean
2 tests in 4 items.
2 passed.
Test passed.
$ python -m pytest --doctest-modules stats.py -v
...
stats.py::stats.mean PASSED                                              [100%]
```

Для исключения сравниваются только первая строка (`Traceback (most recent call last):`) и последняя; `...` между ними заменяет кадры стека. Доктесты поддерживают документацию в честном состоянии: пример, который перестал быть верным, падает. Во всём остальном они плохи, потому что сравнивается напечатанный текст. Их ломает словарь, напечатанный в другом порядке, число с плавающей точкой с одной лишней цифрой или адрес в памяти в `repr`. Их стоит использовать для нескольких наглядных примеров, а настоящие тесты писать в файлах тестов.

## Свойства вместо примеров \{#properties-instead-of-examples\}

Все тесты до сих пор проверяют примеры, которые кто-то выбрал. Выживают же ошибки на тех входных данных, о которых никто не подумал. **Свойство** (property) — утверждение, которое должно выполняться для любых входных данных некоторого вида, а **тестирование на основе свойств** (property-based testing) порождает много случайных входных данных и проверяет свойство на каждом.

Возьмём кодировщик длин серий (run-length encoding), `encode("aaab") == [("a", 3), ("b", 1)]`, и обратную к нему функцию `decode`. Тесты на примерах проходят. Свойство таково: декодирование отменяет кодирование, `decode(encode(text)) == text` для любой строки. Написанный вручную тест свойства берёт случайные строки из стандартного модуля `random` с фиксированным начальным значением генератора (seed), чтобы падение можно было воспроизвести:

```python
import random
from rle import decode, encode

def test_roundtrip_property():
    rng = random.Random(0)
    for trial in range(1000):
        text = "".join(rng.choice("ab") for _ in range(rng.randint(0, 8)))
        assert decode(encode(text)) == text, f"trial {trial}: {text!r}"
```

```text
$ python -m pytest -q
.F                                                                       [100%]
=================================== FAILURES ===================================
...
text = ''

        """'aaab' -> [('a', 3), ('b', 1)]"""
```

В испытании 21 выпала пустая строка, и `encode` обратилась к её первому символу. Тесты на примерах `""` не пробовали. После добавления `if not text: return []` в начало `encode` оба теста проходят. Короткие строки из двухбуквенного алфавита выбраны намеренно: маленькие входы попадают в крайние случаи (пустая строка, одна серия, чередующиеся буквы) гораздо чаще длинных случайных, а падение на коротком входе легко прочитать.

**Hypothesis.** Библиотека [Hypothesis](#references) делает это как следует; в окружении этого курса она не установлена, поэтому дальнейшее описано по её документации и здесь не запускалось. Тест объявляет вид входных данных **стратегией** (strategy): `@given(st.text())` для строк или `@given(st.lists(st.integers()))` для списков целых, после `from hypothesis import given, strategies as st`. По умолчанию Hypothesis порождает 100 входов (настройка `max_examples`) со смещением в сторону крайних случаев. Когда один из них роняет тест, библиотека его **сжимает** (shrinking): пробует более простые варианты упавшего входа и сообщает простейший, на котором тест всё ещё падает, так что отчёт назвал бы `text=''`, даже если бы первым упал тест на длинной строке. Кроме того, она сохраняет упавшие входы в локальной папке `.hypothesis` и при следующем запуске пробует их первыми. У написанного выше вручную цикла нет ни сжатия, ни смещения к крайним случаям, ни памяти; у него есть только сама идея.

Хорошие свойства стоит искать среди таких: путь туда и обратно (закодировать и декодировать, сохранить и загрузить, сериализовать и разобрать); инвариант (сортировка сохраняет те же элементы и расставляет их по порядку; среднее лежит между минимумом и максимумом); сравнение с медленной, но очевидно правильной версией той же функции.

## Тестирование численного кода \{#testing-numerical-code\}

Арифметика с плавающей точкой округляет каждый результат до ближайшего числа, которое может хранить формат, поэтому вычисленное значение обычно не равно в точности значению, которое даёт математика ([заметка о числах с плавающей точкой](/ru/notes/acos/floating-point#why-01--02-is-not-03) объясняет, почему `0.1 + 0.2` не равно `0.3`). Точное `==` для чисел с плавающей точкой проверяет округление, а не формулу:

```text
$ python -m pytest
...
E       assert 0.19999999999999998 == 0.2
E        +  where 0.19999999999999998 = mean([0.1, 0.2, 0.3])
```

Правило — сравнивать с **допуском** (tolerance). Это делают два инструмента:

```text
>>> import math, pytest
>>> x = sum([0.1, 0.2, 0.3]) / 3
>>> x
0.19999999999999998
>>> x == 0.2
False
>>> math.isclose(x, 0.2)
True
>>> x == pytest.approx(0.2)
True
>>> pytest.approx(0.2)
0.2 ± 2.0e-07
>>> err = 0.1 + 0.2 - 0.3
>>> err
5.551115123125783e-17
>>> math.isclose(err, 0.0)
False
>>> math.isclose(err, 0.0, abs_tol=1e-12)
True
>>> err == pytest.approx(0.0)
True
```

Точные правила ([документация Python, `math.isclose`](#references); [pytest, `approx`](#references)):

- `math.isclose(a, b, rel_tol=1e-09, abs_tol=0.0)` истинно, когда $|a - b| \le \max(\text{rel\_tol} \cdot \max(|a|, |b|),\ \text{abs\_tol})$.
- `actual == pytest.approx(expected, rel=1e-6, abs=1e-12)` истинно, когда $|\text{actual} - \text{expected}| \le \max(\text{rel} \cdot |\text{expected}|,\ \text{abs})$. Оно также принимает списки, словари и массивы NumPy и сравнивает их поэлементно: `normalize([1, 3]) == pytest.approx([0.25, 0.75])`.

Относительный допуск масштабируется вместе с величиной чисел, и для большинства результатов это правильно. Возле нуля он не работает: допуск $10^{-9} \cdot |0|$ равен нулю, поэтому `math.isclose(err, 0.0)` ложно для ошибки $5.6 \cdot 10^{-17}$. Для сравнения с нулём нужен абсолютный допуск, который у `pytest.approx` есть по умолчанию, а у `math.isclose` нет. Для массивов NumPy есть `numpy.testing.assert_allclose` — та же идея с отчётом о худшем элементе.

Допуск должен следовать из вычисления, а не ослабляться, пока тест не пройдёт. Сумма $n$ чисел может накопить ошибку порядка $n$ единиц округления (unit roundoff); итерационный метод останавливается на собственном допуске; у стохастической оценки есть стандартная ошибка. Тест с допуском $10^{-2}$ для величины, которая должна быть точной до $10^{-12}$, не поймает ошибку, меняющую третью цифру.

**Начальные значения генератора.** Код, который берёт случайные числа, при каждом запуске даёт другой ответ, и его тест либо падает случайным образом, либо настолько слаб, что ничего не проверяет. Правило — передавать генератор в код как аргумент и задавать ему начальное значение в тесте: `random.Random(42)` для стандартной библиотеки, `numpy.random.default_rng(42)` для NumPy. Одно и то же начальное значение даёт одну и ту же последовательность при каждом запуске, поэтому тест воспроизводим, а падение можно повторить. Проверять стоит то, что должно выполняться при любом начальном значении (средние бутстрэп-выборок лежат между минимумом и максимумом данных), плюс статистические утверждения с допуском, выведенным из разброса. Курсы по машинному обучению по той же причине фиксируют начальное значение в каждом запуске, как объясняет заметка об [обучении на практике](/ru/notes/deep-learning/training-in-practice#make-runs-reproducible); разделы «Код» курса ML печатают числа, которые цитирует текст, и это работает только потому, что начальные значения в скриптах зафиксированы.

## Ограничения \{#limitations\}

- **Тесты показывают наличие ошибок, а не их отсутствие.** Прошедший набор говорит, что работают проверенные им случаи. Инструменты покрытия (`coverage.py`, `pytest-cov`) сообщают, какие строки выполнялись во время тестов; так находится непротестированный код, но ничего не говорится о том, хорошо ли проверен протестированный.
- **Тесты — тоже код.** Они могут быть неверными, и неверное ожидаемое значение — это ошибка, которую набор тестов охраняет. Каждый новый тест стоит один раз намеренно уронить.
- **Модульные тесты изолируют, реальный мир — нет.** Замена базы данных или сетевого сервиса подделкой (`unittest.mock`) делает тесты быстрыми и детерминированными, но может оставить их проходящими против подделки, которая уже не соответствует настоящему сервису. Несколько интеграционных тестов против настоящего сервиса всё равно нужны.
- **pytest — не единственное средство запуска тестов.** Модуль `unittest` стандартной библиотеки использует классы и `self.assertEqual`; pytest умеет запускать и тесты `unittest`. Заметка показывает pytest, потому что в научном Python обычно выбирают его.
- **Hypothesis здесь не запускалась.** Её описание следует документации; запускалась только та часть, где тест свойства написан вручную.

## Что нужно запомнить \{#what-you-should-remember\}

- Модульный тест вызывает одну функцию с фиксированными входными данными и автоматически проверяет результат. Набор тестов запускают после каждого изменения.
- pytest собирает функции `test_*` из файлов `test_*.py` и переписывает простые `assert` так, чтобы при падении было видно участвующие значения. Падение читают по строке `>` и строкам `E`.
- Фикстуры запрашиваются по имени параметра; `yield` отделяет подготовку от очистки; область действия по умолчанию даёт каждому тесту новое значение. `tmp_path` — новая папка для каждого теста.
- `parametrize` превращает таблицу случаев в отдельные тесты; `pytest.raises(Type, match=...)` проверяет, что вызов возбуждает исключение.
- Доктесты проверяют примеры в строках документации, сравнивая напечатанный текст; их должно быть немного.
- Тест свойства проверяет утверждение на многих порождённых входах; Hypothesis добавляет сжатие и запоминает падения.
- Числа с плавающей точкой сравнивают с допуском, выбранным исходя из вычисления: `pytest.approx`, `math.isclose` (с `abs_tol` возле нуля). Генераторы случайных чисел передают в код как аргументы и задают им начальные значения в тестах.

## Код \{#code\}

Скрипт — модуль и его тесты в одном файле. При запуске командой `python -I test_scores.py` он вызывает pytest на самом себе: тестируемые функции, доктест, параметризованные случаи, ожидаемое исключение, фикстура `tmp_path`, допуски, стохастическая функция с фиксированным начальным значением и тест свойства. Ему нужен pytest; прогон занимает гораздо меньше секунды.

```python
"""Tests for a small scores module, in one file (Python 3.14, pytest 9).

Run with `python -I test_scores.py`; it calls pytest on itself.
"""
import math
import random
import sys

import pytest

# ---- тестируемый код ----------------------------------------------------
def mean(values):
    """Arithmetic mean of a non-empty sequence.

    >>> mean([1, 2, 3])
    2.0
    """
    if not values:
        raise ValueError("mean of an empty sequence")
    return sum(values) / len(values)

def read_scores(path):
    """Read lines 'name,score' into a dict of floats."""
    scores = {}
    with open(path, encoding="utf-8") as f:
        for line in f:
            name, score = line.strip().split(",")
            scores[name] = float(score)
    return scores

def bootstrap_means(values, n_resamples, rng):
    """Means of n_resamples resamples drawn with replacement."""
    k = len(values)
    return [mean([values[rng.randrange(k)] for _ in range(k)])
            for _ in range(n_resamples)]

def encode(text):
    """Run-length encoding: 'aaab' -> [('a', 3), ('b', 1)]."""
    if not text:
        return []
    runs = []
    current, count = text[0], 0
    for ch in text:
        if ch == current:
            count += 1
        else:
            runs.append((current, count))
            current, count = ch, 1
    runs.append((current, count))
    return runs

def decode(runs):
    return "".join(ch * n for ch, n in runs)

# ---- тесты -----------------------------------------------------------------
@pytest.mark.parametrize("values, expected", [([5], 5.0), ([1, 3], 2.0), ([-1, 0, 1], 0.0)])
def test_mean_cases(values, expected):
    assert mean(values) == expected

def test_mean_of_empty_raises():
    with pytest.raises(ValueError, match="empty"):
        mean([])

def test_mean_of_tenths():
    assert mean([0.1, 0.2, 0.3]) != 0.2                  # точное сравнение не проходит
    assert mean([0.1, 0.2, 0.3]) == pytest.approx(0.2)   # относительный допуск 1e-6
    assert math.isclose(mean([0.1, 0.2, 0.3]), 0.2)      # относительный допуск 1e-9

@pytest.fixture
def scores_file(tmp_path):
    path = tmp_path / "scores.csv"
    path.write_text("ada,91.5\nalan,78\n", encoding="utf-8")
    return path

def test_read_scores(scores_file):
    assert read_scores(scores_file) == {"ada": 91.5, "alan": 78.0}

def test_bootstrap_is_reproducible():
    data = [2.0, 4.0, 4.0, 5.0, 9.0]
    first = bootstrap_means(data, 200, random.Random(42))
    second = bootstrap_means(data, 200, random.Random(42))
    assert first == second                               # то же начальное значение, те же числа
    assert min(data) <= min(first) and max(first) <= max(data)
    assert mean(first) == pytest.approx(mean(data), abs=0.3)

def test_roundtrip_property():
    rng = random.Random(0)
    for trial in range(1000):
        text = "".join(rng.choice("ab") for _ in range(rng.randint(0, 8)))
        assert decode(encode(text)) == text, f"trial {trial}: {text!r}"

if __name__ == "__main__":
    sys.exit(pytest.main([__file__, "-v", "-p", "no:cacheprovider", "--doctest-modules"]))

# Вывод на CPython 3.14.7 и pytest 9.1.1 на macOS (arm64); заголовок и время меняются:
# ============================= test session starts ==============================
# platform darwin -- Python 3.14.7, pytest-9.1.1, pluggy-1.7.0 -- .../bin/python
# rootdir: ...
# collecting ... collected 9 items
#
# test_scores.py::test_scores.mean PASSED                                  [ 11%]
# test_scores.py::test_mean_cases[values0-5.0] PASSED                      [ 22%]
# test_scores.py::test_mean_cases[values1-2.0] PASSED                      [ 33%]
# test_scores.py::test_mean_cases[values2-0.0] PASSED                      [ 44%]
# test_scores.py::test_mean_of_empty_raises PASSED                         [ 55%]
# test_scores.py::test_mean_of_tenths PASSED                               [ 66%]
# test_scores.py::test_read_scores PASSED                                  [ 77%]

# test_scores.py::test_roundtrip_property PASSED                           [100%]
```

## Дальше \{#next\}

Упавший тест говорит, что что-то не так и где не прошла проверка. Он не всегда говорит почему: неверное значение могло быть вычислено тремя вызовами раньше или только на 10 000-й строке данных. [Следующая заметка](/ru/notes/python/debugging-and-profiling) о поиске причины: внимательное чтение трассировок, остановка работающей программы отладчиком, чтобы посмотреть на её переменные, журналирование того, что делает долгий запуск, и, когда программа правильна, но медленна, измерение того, куда уходят время и память.
