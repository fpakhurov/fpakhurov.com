[Заметка об отладке и профилировании](/ru/notes/python/debugging-and-profiling) нашла медленную функцию и исправление и оставила открытыми два вопроса: почему одна операция стоит наносекунды, а другая — микросекунды, и что на самом деле представляют собой кадры, по которым ходит отладчик. Ответы — в интерпретаторе. [Первая заметка](/ru/notes/python/running-python#what-happens-when-you-run-a-file) дала общую схему: CPython компилирует файл в байт-код, а затем цикл выполняет байт-код. Эта заметка раскрывает каждую стадию на примере одной маленькой функции, выполняет её на стеке значений интерпретатора команду за командой, показывает, как интерпретатор переписывает собственные команды, узнавая типы, которые ему встречаются, и объясняет, как освобождается память. Курс ACOS прослеживает тот же интерпретатор вниз, [до операционной системы](/ru/notes/acos/language-runtimes); эта заметка остаётся на уровне Python.

Имена команд, специализации и пороги сборщика мусора — подробности CPython: они меняются от версии к версии, а у других реализаций (например, PyPy) их нет вовсе. Всё показанное — настоящий вывод этой сборки; папки сокращены до `...`.

## Отправная точка: «Python читает код строка за строкой» \{#baseline-python-reads-your-code-line-by-line\}

Распространённое представление об интерпретаторе — программа, которая читает строку текста, выясняет, что она значит, выполняет её и читает следующую строку. Если бы CPython работал так, цикл, выполняющийся миллион раз, миллион раз разбирал бы своё тело, синтаксическая ошибка в последней строке обнаруживалась бы только после выполнения первых строк, и одну и ту же строку никак нельзя было бы ускорить при втором выполнении.

Ничего из этого не верно. Синтаксическая ошибка в любом месте останавливает файл до выполнения его первой строки, как показала первая заметка. Тело цикла анализируется один раз. А одна и та же строка действительно становится быстрее после нескольких выполнений, что показывает раздел о специализации. CPython переводит код, прежде чем выполнять его, и выполняет не текст.

## От текста к синтаксическому дереву \{#from-text-to-a-syntax-tree\}

Возьмём одну инструкцию, `total = price * 2`. Первая стадия, **токенизатор** (tokenizer), режет текст на токены: имена, операторы, числа и метки конца строки. Его открывает модуль `tokenize`:

```text
>>> import io, tokenize
>>> src = "total = price * 2\n"
>>> for tok in tokenize.generate_tokens(io.StringIO(src).readline):
...     print(tokenize.tok_name[tok.type], repr(tok.string))
...
NAME 'total'
OP '='
NAME 'price'
OP '*'
NUMBER '2'
NEWLINE '\n'
ENDMARKER ''
```

**Парсер** (parser) проверяет, что токены следуют грамматике языка, и строит **абстрактное синтаксическое дерево** (abstract syntax tree, AST): дерево узлов, по узлу на каждую конструкцию, без знаков препинания и с явной структурой. Его печатает модуль `ast`:

```text
>>> import ast
>>> print(ast.dump(ast.parse("total = price * 2"), indent=2))
Module(
  body=[
    Assign(
      targets=[
        Name(id='total', ctx=Store())],
      value=BinOp(
        left=Name(id='price', ctx=Load()),
        op=Mult(),
        right=Constant(value=2)))])
```

Это дерево читается как смысл инструкции: присваивание, цель которого — имя `total` (в контексте `Store`: в него записывают), а значение — бинарная операция, умножение, имени `price` (его читают) и константы 2. Приоритет операторов уже учтён: `a + b * c` разбирается в `BinOp`, правый операнд которого — ещё один `BinOp`. Инструменты, которые работают с кодом, а не выполняют его, работают именно с этим деревом: линтеры, форматировщики, проверка типов и pytest, который [переписывает инструкции `assert`](/ru/notes/python/testing#pytest-plain-functions-and-plain-asserts), редактируя дерево перед компиляцией.

## От дерева к байт-коду \{#from-the-tree-to-bytecode\}

**Компилятор** обходит дерево и выдаёт **байт-код** (bytecode): последовательность простых команд для виртуальной машины, которая хранится вместе со всем остальным, что нужно функции, в **объекте кода** (code object). Для функции компилятор работает один раз, когда выполняется инструкция `def`, и объект кода прикрепляется к функции как `f.__code__`. Модуль `dis` его дизассемблирует:

```text
>>> import dis
>>> def f(price, qty):
...     total = price * qty
...     return total + 1
...
>>> dis.dis(f)
  1           RESUME                   0

  2           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (price, qty)
              BINARY_OP                5 (*)
              STORE_FAST               2 (total)

  3           LOAD_FAST_BORROW         2 (total)
              LOAD_SMALL_INT           1
              BINARY_OP                0 (+)
              RETURN_VALUE
>>> f.__code__.co_varnames
('price', 'qty', 'total')
>>> f.__code__.co_stacksize
2
```

Каждая строка листинга — одна команда: строка исходного кода, из которой она получена (только там, где номер меняется), имя команды (её **код операции**, opcode), её аргумент и в скобках — что этот аргумент значит. `RESUME` отмечает начало функции; здесь интерпретатор проверяет, нет ли отложенной работы, например сигналов. `co_varnames` перечисляет локальные переменные, начиная с аргументов, и `LOAD_FAST_BORROW 2 (total)` обращается к `total` по её позиции, 2, в этом списке. `co_stacksize` — наибольшая глубина, которой стек значений достигает в этой функции; её вычисляет компилятор.

Три имени в листинге появились недавно. `LOAD_SMALL_INT` (3.14) кладёт на стек малое целое, закодированное в самой команде, а не извлечённое из таблицы констант. `LOAD_FAST_LOAD_FAST` (3.13) — первая загрузка листинга без суффиксов `_BORROW` — это **суперкоманда** (superinstruction), которая выполняет работу двух загрузок за одну диспетчеризацию. Наконец, формы `_BORROW` (3.14) кладут на стек локальную переменную без увеличения её счётчика ссылок; это безопасно, когда компилятор может доказать, что кадр удерживает объект живым всё время, пока объект лежит на стеке. Поэтому документация 3.14 предупреждает, что `sys.getrefcount` может возвращать не те значения, что раньше ([What's New in Python 3.14](#references)). Набор команд — подробность реализации, он документируется для каждой версии в модуле `dis` и не стабилен между версиями.

## Цикл вычисления и стек значений \{#the-evaluation-loop-and-the-value-stack\}

<aside class="callout"><strong>Ключевая идея.</strong> Байт-код CPython выполняется на **стековой машине** (stack machine). Каждый вызов функции получает **кадр** (frame): массив слотов для локальных переменных, **стек значений** (value stack) для промежуточных результатов и указатель на следующую команду. Цикл, написанный на C, выбирает команду, выполняет её (обычно снимая операнды со стека значений и кладя на него результат) и переходит к следующей. Всё, что делает код на Python, он делает через этот цикл, по одной команде за раз.</aside>

Правило для каждой команды `f` по документации `dis` ([документация Python, `dis`](#references)):

- `LOAD_FAST_BORROW i` кладёт на стек значение локального слота `i`; `LOAD_FAST_BORROW_LOAD_FAST_BORROW` кладёт два значения.
- `LOAD_SMALL_INT n` кладёт на стек целое `n`.
- `BINARY_OP op` снимает два верхних значения, применяет к ним оператор (нижнее значение — левый операнд) и кладёт на стек результат.
- `STORE_FAST i` снимает верхнее значение в локальный слот `i`.
- `RETURN_VALUE` снимает верхнее значение и возвращает его вызывающей функции.

Вот `f(3, 4)`, выполненная команда за командой в **цикле вычисления** (evaluation loop):

<ValueStack />

1. Аргументы уже лежат в своих слотах: `price` равно 3, `qty` равно 4. Одна команда кладёт на стек оба значения.
2. `BINARY_OP 5 (*)` снимает 4 и 3, перемножает их и кладёт 12.
3. `STORE_FAST 2` снимает 12 в слот `total`. Стек пуст, как всегда между инструкциями.
4. `LOAD_FAST_BORROW 2` кладёт значение `total` обратно.
5. `LOAD_SMALL_INT 1` кладёт 1.
6. `BINARY_OP 0 (+)` снимает 1 и 12 и кладёт 13.
7. `RETURN_VALUE` снимает 13 и передаёт вызывающей функции, которая кладёт его на свой стек значений.

Рисунок показывает, почему локальная переменная дешёвая. Её имя превращается в номер слота во время компиляции, поэтому чтение — это обращение к массиву. С глобальным именем иначе: `LOAD_GLOBAL` во время выполнения ищет имя в словаре модуля и, если его там нет, в словаре встроенных имён. [Заметка о производительности](/ru/notes/python/performance) измеряет, сколько это стоит сегодня, а стоит это меньше, чем раньше, — по причине, описанной в следующем разделе.

**Сам цикл.** Сердце CPython — одна функция на C, `_PyEval_EvalFrameDefault` в `Python/ceval.c`, а код каждой команды генерируется из определений в `Python/bytecodes.c` ([исходный код и внутренняя документация CPython](#references)). Начиная с 3.14, CPython можно собрать и с **интерпретатором на хвостовых вызовах** (tail-calling interpreter), где каждая команда — маленькая функция на C, которая заканчивается прямым переходом в следующую; с Clang 19 и новее он на несколько процентов быстрее на стандартных бенчмарках ([What's New in Python 3.14](#references)). Сборка, которой пользуется курс, скомпилирована именно так (её `sysconfig.get_config_var('CONFIG_ARGS')` содержит `--with-tail-call-interp`). Код на Python разницы заметить не может.

**Кадры.** Кадр хранит объект кода, локальные слоты, стек значений, позицию текущей команды и ссылку на кадр вызывающей функции. Цепочка этих ссылок — стек вызовов, который печатает трассировка и по которому ходит команда `where` отладчика `pdb`. Из Python текущий кадр в виде объекта возвращает `sys._getframe()`:

```text
>>> import sys
>>> def outer():
...     return inner(10)
...
>>> def inner(n):
...     frame = sys._getframe()
...     print(frame.f_code.co_name, frame.f_locals, frame.f_lineno)
...     caller = frame.f_back
...     print(caller.f_code.co_name, caller.f_lineno)
...     return n
...
>>> outer()
inner {'n': 10, 'frame': <frame at 0x1019b6d40, file '<python-input-2>', line 3, code inner>} 3
outer 2
10
```

Начиная с 3.11, кадры живут в компактной внутренней форме на стеке каждого потока, а *объект* кадра, который видит код на Python, создаётся только тогда, когда его кто-то запрашивает, например `sys._getframe`, трассировка или отладчик ([What's New in Python 3.11](#references)). Это удешевило вызовы, но вызов функции на Python всё ещё серьёзная операция: он выделяет кадр, копирует аргументы в его слоты и начинает новый проход по последовательности команд цикла. [Заметка о производительности](/ru/notes/python/performance) оценивает его примерно в 13 нс на этой машине против примерно 34 нс на целую итерацию простого цикла.

## Специализирующий адаптивный интерпретатор \{#the-specializing-adaptive-interpreter\}

*Необязательное углубление: как CPython 3.11 и новее ускоряет команды, переписывая их. Остальная часть заметки от этого раздела не зависит.*

`BINARY_OP 5 (*)` не знает, что умножает. Это могут быть два целых, два числа с плавающей точкой, строка и целое или два массива NumPy, поэтому общая команда выясняет типы операндов и вызывает операцию умножения, которую даёт тип левого операнда (`__mul__` из [модели данных](/ru/notes/python/the-data-model)), а при неудаче — `__rmul__` правого операнда. Этот поиск составляет большую часть стоимости команды. Между тем в реальной программе конкретное `*` почти всегда видит одни и те же типы.

Начиная с Python 3.11, интерпретатор этим пользуется ([PEP 659](#references)). У каждой команды, которой это может помочь, есть **встроенный кэш** (inline cache) — несколько ячеек, зарезервированных сразу после неё в байт-коде; первая из них — счётчик. После короткого разогрева интерпретатор смотрит на операнды, которые он действительно видел, и **переписывает команду на месте** в специализированную форму для этих типов. Специализированная команда сначала выполняет **охранную проверку** (guard) — дешёвую проверку того, что её предположение всё ещё верно (например, что оба операнда — в точности `int`), — и затем идёт коротким путём. Если проверка не проходит, команда выполняет общую операцию и засчитывает промах; после достаточного числа промахов команда возвращается к адаптивной форме и заново специализируется под то, что видит теперь. `dis(f, adaptive=True)` показывает текущий, переписанный байт-код:

```text
>>> for _ in range(1000):
...     _ = f(3, 4)
...
>>> dis.dis(f, adaptive=True)
  1           RESUME_CHECK             0

  2           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (price, qty)
              BINARY_OP_MULTIPLY_INT   5 (*)
              STORE_FAST               2 (total)

  3           LOAD_FAST_BORROW         2 (total)
              LOAD_SMALL_INT           1
              BINARY_OP_ADD_INT        0 (+)
              RETURN_VALUE
>>> for _ in range(1000):
...     _ = f(2.5, 4.0)
...
>>> dis.dis(f, adaptive=True)
  1           RESUME_CHECK             0

  2           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (price, qty)
              BINARY_OP_MULTIPLY_FLOAT 5 (*)
              STORE_FAST               2 (total)

  3           LOAD_FAST_BORROW         2 (total)
              LOAD_SMALL_INT           1
              BINARY_OP_EXTEND         0 (+)
              RETURN_VALUE
```

<Specialization />

1. После компиляции умножение — это общая команда `BINARY_OP 5 (*)` с её кэшем.
2. После вызовов с целыми она становится `BINARY_OP_MULTIPLY_INT`. В этой сборке переписывание произошло уже на втором вызове новой функции: разогрев намеренно короткий.
3. Вызовы с числами с плавающей точкой не проходят её охранную проверку: каждый выполняет общий путь и засчитывает промах.
4. После достаточного числа промахов команда становится `BINARY_OP_MULTIPLY_FLOAT`. Сложение, которое теперь видит float и целое 1, стало `BINARY_OP_EXTEND` — специализацией 3.14 для операндов разных типов, например float и int.

Обращения к атрибутам и вызовы специализируются так же. На объектах одного класса `p.x` становится `LOAD_ATTR_INSTANCE_VALUE`: команда читает атрибут из известной позиции в объекте, проверив, что тип объекта не изменился; `len(items)` становится `LOAD_GLOBAL_BUILTIN`, за которой следует `CALL_LEN`:

```text
  8           LOAD_FAST_BORROW         0 (p)
              LOAD_ATTR_INSTANCE_VALUE 0 (x)
  ...
 11           LOAD_GLOBAL_BUILTIN      1 (len + NULL)
              LOAD_FAST_BORROW         0 (items)
              CALL_LEN                 1
```

(из `dis(..., adaptive=True)` для `def norm2(p): return p.x * p.x + p.y * p.y` и `def call_len(items): return len(items)` после 500 вызовов, с сокращениями). `LOAD_GLOBAL_BUILTIN` запоминает, где была найдена `len`, вместе с метками версий словаря модуля и словаря встроенных имён, поэтому поиск по словарям пропускается, пока никто не присвоит новое глобальное имя.

**Что это значит для кода.** Код со стабильными типами, а такого большинство, после нескольких вызовов выполняется на специализированных командах; код, который в одном месте смешивает типы (функция, которую по очереди вызывают с целыми, числами с плавающей точкой и строками), раз за разом откатывается на общий путь. Специализация не меняет того, что вычисляет программа, и ничто в языке от неё не зависит. Она же объясняет, почему микрооптимизации, важные в старых версиях Python, например копирование глобального имени в локальную переменную перед циклом, теперь почти ничего не дают; [заметка о производительности](/ru/notes/python/performance) их измеряет.

## Подсчёт ссылок \{#reference-counting\}

[Заметка о значениях и именах](/ru/notes/python/values-and-names) установила, что имена ссылаются на объекты и объект живёт, пока на него что-то ссылается. CPython реализует это «пока» через **счётчик ссылок** (reference count) в каждом объекте: сохранение ссылки увеличивает его, удаление ссылки уменьшает, и объект освобождается в тот момент, когда счётчик доходит до нуля. Курс ACOS [описывает этот механизм на C](/ru/notes/acos/language-runtimes#memory-reference-counting-and-a-cycle-collector); здесь — как **подсчёт ссылок** (reference counting) выглядит из Python. `sys.getrefcount` возвращает счётчик, включая одну временную ссылку из собственного аргумента, а `weakref.finalize` регистрирует функцию, которая выполнится при освобождении объекта, не удерживая его живым:

```python
import sys, weakref

class Node:
    pass

freed = []
a = Node()
b = a
weakref.finalize(a, freed.append, "a")
print(sys.getrefcount(a))   # a, b и аргумент getrefcount
del a
print(freed)                # b всё ещё ссылается на объект
del b
print(freed)                # освобождён сразу
```

```text
3
[]
['a']
```

`del a` удаляет имя, а не объект: у объекта остаётся ссылка из `b`, и он продолжает жить. `del b` удаляет последнюю ссылку, и объект освобождается во время этой инструкции, до выполнения следующей строки. Поэтому файл, открытый без `with`, в CPython обычно закрывается, как только исчезает последнее имя, которое на него ссылается. Язык этого не гарантирует: PyPy, у которого другой сборщик, закроет файл позже, и это одна из причин, по которым [заметка о файлах](/ru/notes/python/files-and-exceptions) настаивает на `with`. То же правило действует для больших данных: буфер чисел массива NumPy освобождается в момент, когда исчезает последняя ссылка на массив, и именно так промежуточные массивы долгого вычисления в скриптах курсов по машинному обучению возвращают память без всякого явного освобождения.

## Циклы и сборщик мусора \{#cycles-and-the-garbage-collector\}

Подсчёт ссылок не может освободить **цикл** (cycle): объекты, которые ссылаются друг на друга, держат счётчики друг друга выше нуля и после того, как программа отпустила все ссылки на них. Для них в CPython есть **циклический сборщик мусора** (cyclic garbage collector). Он рассматривает только объекты-контейнеры (списки, словари, экземпляры классов; не целые числа и не строки, которые не могут ссылаться на другие объекты) и находит группы, на которые ссылаются только изнутри самой группы ([документация Python, `gc`](#references)):

```python
import gc, weakref

class Node:
    pass

gc.collect()                  # начинаем с чистого состояния
x, y = Node(), Node()
x.other, y.other = y, x       # цикл из двух объектов
r = weakref.ref(x)            # ссылка, которая не удерживает x
del x, y
print(r() is None)            # цикл недостижим, но ещё в памяти
print(gc.collect())           # сколько объектов нашёл сборщик
print(r() is None)
print(gc.get_threshold())
```

```text
False
2
True
(2000, 10, 10)
```

После `del x, y` до двух узлов ничем не добраться, но они всё ещё существуют: слабая ссылка всё ещё находит `x`. `gc.collect()` находит оба, освобождает их и возвращает 2. Сборщик запускается и сам. В 3.14.7 он **поколенческий** (generational), как в 3.13: новые контейнеры попадают в поколение 0, которое собирается, когда число выделений контейнеров за вычетом освобождений превысит первый порог, 2000; выжившие переходят в старшие поколения, которые собираются реже (два других числа). Python с 3.14.0 по 3.14.4 поставлялся с новым **инкрементальным** (incremental) сборщиком всего с двумя поколениями, который должен был сократить паузы; из-за сообщений о росте памяти в рабочих системах в 3.14.5 его заменили обратно поколенческим сборщиком из 3.13, и именно этот сборщик работает в 3.14.7 и в 3.15 ([What's New in Python 3.14](#references); [документация `gc`](#references)). Код, который вызывает только `gc.collect()` и `gc.get_threshold()`, разницы не видит.

**Практические следствия.** Циклы распространены и безвредны: дерево, дети которого ссылаются на родителя, исключение, которое держит трассировку, кадры которой ссылаются на это исключение. Они занимают память до следующей сборки, а сборка стоит времени, пропорционального числу отслеживаемых контейнеров. Программа, которая строит миллионы долгоживущих контейнеров, может заметное время тратить на сборки, которые ничего не находят; `gc.freeze()` переносит всё, что существует сейчас, в постоянное поколение, которое последующие сборки пропускают, а `gc.disable()` выключает автоматическую сборку (подсчёт ссылок при этом продолжает работать). Это средства для измеренных проблем, а не для повседневного использования. Память, которую программа удерживает по ошибке, например в кэше, который только растёт, — не мусор, и никакой сборщик её не освободит; её находит [tracemalloc](/ru/notes/python/debugging-and-profiling#memory-tracemalloc).

## Бессмертные объекты и малые целые \{#immortal-objects-and-small-integers\}

Некоторые объекты используются повсюду: `None`, `True`, `False`, малые целые. Обновление их счётчиков ссылок из каждого потока и каждого процесса, который делит память с родителем, тратит время и впустую загрязняет страницы памяти. Начиная с 3.12, эти объекты **бессмертны** (immortal) ([PEP 683](#references)): их счётчику присваивается особое большое значение, которое увеличения и уменьшения не трогают, и они никогда не освобождаются.

```text
>>> import sys
>>> sys.getrefcount(None)
3221225472
>>> sys._is_immortal(None), sys._is_immortal(7), sys._is_immortal(10**6)
(True, True, False)
>>> a = 256; b = int("256")
>>> a is b
True
>>> a = 257; b = int("257")
>>> a is b
False
>>> a == b
True
```

Целые от −5 до 256 создаются один раз при запуске интерпретатора и используются повторно: любое вычисление, результат которого попадает в этот диапазон, возвращает кэшированный объект. Поэтому `int("256") is int("256")` истинно, а та же проверка для 257 ложна (в этой сборке; проверка от −6 до 1025 показывает, что кэш — ровно от −5 до 256). `sys._is_immortal` появилась в 3.14 и, как говорит подчёркивание, — подробность реализации.

**Типичная ошибка** следует отсюда напрямую: сравнивать числа или строки через `is`. `x is 256` случайно истинно для кэшированного значения и ложно для 257, так что код, который «работает» в тесте с малыми числами, ломается на больших. Python 3.8 и новее печатают `SyntaxWarning: "is" with 'int' literal. Did you mean "=="?`, если с одной стороны стоит литерал. Значения сравнивают через `==`, а `is` оставляют для идентичности, что на практике означает `is None`.

## Экспериментальный JIT-компилятор \{#the-experimental-jit\}

*Необязательное углубление: состояние компиляции на лету в CPython 3.14. Остальная часть заметки от этого раздела не зависит.*

Специализирующий интерпретатор всё ещё платит за диспетчеризацию: каждую команду нужно выбрать, декодировать и перейти к ней. **JIT-компилятор** (just-in-time compiler) убирает эту плату, превращая горячий код в машинный код прямо во время работы программы; заметка курса ACOS объясняет, [как устроены JIT-компиляторы вообще](/ru/notes/acos/language-runtimes#just-in-time-compilation-briefly). JIT-компилятор CPython, описанный в [PEP 744](#references) и впервые доступный как опция сборки в 3.13, работает с трассами специализированных микроопераций и порождает машинный код методом **копирования с заплатками** (copy-and-patch): шаблоны машинного кода для каждой микрооперации компилируются при сборке самого CPython, а во время выполнения JIT копирует шаблоны для горячей трассы в память и вписывает в них значения операндов.

Его состояние в 3.14 по примечаниям к выпуску ([What's New in Python 3.14](#references)):

- Официальные сборки для macOS и Windows содержат JIT-компилятор, **выключенный по умолчанию**; `PYTHON_JIT=1` в окружении включает его. Сборки из исходников ведут себя так же с `--enable-experimental-jit=yes-off`; так сконфигурирована и сборка, которой здесь пользуются.
- Он экспериментальный и не рекомендуется для рабочих систем. Типичный эффект — от замедления на 10% до ускорения на 20% в зависимости от нагрузки.
- `sys._jit.is_available()` говорит, собран ли интерпретатор с ним, `sys._jit.is_enabled()` — включён ли он.
- Сборка без GIL (free-threaded) его не поддерживает.

Замер в описанных условиях — функция, которая 3 000 000 раз выполняет цикл `while` с целочисленной арифметикой, лучшее из 7 запусков, дважды для каждой настройки: 0.159 и 0.160 с с выключенным JIT-компилятором, 0.165 и 0.165 с с `PYTHON_JIT=1`. На этом цикле JIT-компилятор оказался примерно на 3% медленнее, в пределах диапазона из примечаний к выпуску. (`python -I` игнорирует переменные окружения `PYTHON_*`, поэтому запуски с JIT делались без `-I`.) В списке изменений Python 3.15 значится значительно улучшенный JIT-компилятор; здесь он не измерялся.

## Что изменилось \{#what-changed\}

| | Исходное представление | CPython 3.14 |
| --- | --- | --- |
| Единица работы | строка текста, разбираемая каждый раз | байт-код, компилируемый один раз для каждой функции |
| Перед выполнением | ничего | токены → синтаксическое дерево → объект кода; синтаксические ошибки останавливают всё |
| Выполнение | интерпретация текста | цикл на C по командам, операнды на стеке значений |
| Локальные переменные | ищутся по имени | пронумерованные слоты в кадре |
| Повторное выполнение | каждый раз одна и та же стоимость | команды специализируются под встреченные типы (3.11+) |
| Освобождение памяти | (не рассматривается) | счётчики ссылок освобождают сразу; поколенческий сборщик циклов освобождает циклы |
| Частые объекты | обычные | бессмертные: `None`, булевы значения, малые целые (3.12+); −5..256 кэшируются |
| Машинный код | нет | экспериментальный JIT-компилятор, выключенный по умолчанию (3.13+, в официальных сборках с 3.14) |

## Ограничения \{#limitations\}

- **Одна реализация, одна версия.** Каждое имя кода операции, правила специализации, пороги сборщика мусора и диапазон кэшированных целых — подробности CPython 3.14. Байт-код не переносится между минорными версиями, и по этой причине файлы `.pyc` помечены версией. PyPy выполняет те же программы с трассирующим JIT-компилятором и другим сборщиком.
- **Вывод `dis` — это взгляд, а не контракт.** Суперкоманды, заимствованные загрузки и специализации появляются и исчезают от выпуска к выпуску; байт-код стоит читать, чтобы понимать стоимость, а не чтобы от него зависеть.
- **Замер JIT-компилятора — это один цикл.** Он показывает, что в 3.14 «JIT» не означает «быстрее», и ничего больше.
- **Сборка без GIL устроена иначе.** Она использует другую схему подсчёта ссылок (смещённый подсчёт ссылок, biased reference counting), специализирует команды потокобезопасным образом и не имеет JIT-компилятора; [заметка о конкурентности](/ru/notes/python/concurrency) её измеряет.

## Что нужно запомнить \{#what-you-should-remember\}

- CPython токенизирует, разбирает в AST и компилирует каждую функцию в байт-код один раз; `tokenize`, `ast` и `dis` показывают каждую стадию.
- Байт-код выполняется на стековой машине: команды снимают операнды со стека значений кадра и кладут на него результаты. Локальные переменные — пронумерованные слоты; глобальные — поиск в словаре.
- Кадр хранит локальные переменные вызова, стек значений и текущую команду и ссылается на кадр вызывающей функции: эта цепочка и есть трассировка.
- Начиная с 3.11, команды специализируются на месте под встреченные типы, за дешёвыми охранными проверками; это показывает `dis(f, adaptive=True)`. Стабильные типы выполняются быстрее.
- Объекты освобождаются, когда их счётчик ссылок доходит до нуля; для циклов нужен циклический сборщик, который в 3.14.7 поколенческий (пороги `(2000, 10, 10)`).
- `None`, `True`, `False` и целые от −5 до 256 бессмертны и кэшированы. Значения сравнивают через `==`; `is` используют для `None`.
- JIT-компилятор в 3.14 экспериментальный и выключен по умолчанию (`PYTHON_JIT=1`); прежде чем ждать от него выигрыша, его нужно измерить.

## Код \{#code\}

Скрипт проводит одну функцию через стадии этой заметки: типы узлов её синтаксического дерева, её байт-код, специализированные команды после вызовов с целыми и затем с числами с плавающей точкой, цепочку кадров, подсчёт ссылок, цикл и сборщик, бессмертные объекты и состояние JIT-компилятора. Ему нужна только стандартная библиотека; запуск — `python -I inside.py`.

```python
"""Follow a function through CPython 3.14: tree, bytecode, specialization, memory."""
import ast
import dis
import gc
import sys
import weakref

source = "def f(price, qty):\n    total = price * qty\n    return total + 1\n"

# 1. Исходный код -> синтаксическое дерево: типы узлов тела функции
tree = ast.parse(source)
print([type(node).__name__ for node in ast.walk(tree.body[0].body[0])])

# 2. Синтаксическое дерево -> объект кода -> байт-код
namespace = {}
exec(compile(tree, "<f>", "exec"), namespace)
f = namespace["f"]
code = f.__code__
print(code.co_varnames, code.co_stacksize)
print([ins.opname for ins in dis.get_instructions(f)])

# 3. Выполняем: специализирующий интерпретатор переписывает команды под встреченные типы
for _ in range(100):
    f(3, 4)
print([ins.opname for ins in dis.get_instructions(f, adaptive=True) if "BINARY" in ins.opname])
for _ in range(100):
    f(2.5, 4.0)
print([ins.opname for ins in dis.get_instructions(f, adaptive=True) if "BINARY" in ins.opname])

# 4. Кадры: у каждого вызова свой, со ссылкой на кадр вызывающей функции
def inner():
    frame = sys._getframe()
    return frame.f_code.co_name, frame.f_back.f_code.co_name

def outer():
    return inner()

print(outer())

# 5. Подсчёт ссылок освобождает объект, как только исчезает последняя ссылка
class Node:
    pass

freed = []
a = Node()
b = a
weakref.finalize(a, freed.append, "a")
print(sys.getrefcount(a))            # a, b и аргумент getrefcount
del a
print(freed)                         # [] : b всё ещё ссылается на него
del b
print(freed)                         # ['a']: освобождён сразу

# 6. Циклу нужен сборщик мусора
gc.collect()
x, y = Node(), Node()
x.other, y.other = y, x
r = weakref.ref(x)
del x, y
print(r() is None, gc.collect(), r() is None)
print(gc.get_threshold())

# 7. Бессмертные объекты и кэш малых целых
print(sys._is_immortal(None), sys._is_immortal(256), sys._is_immortal(10**6))
print(int("256") is int("256"), int("257") is int("257"))

# 8. JIT-компилятор: встроен, но выключен без PYTHON_JIT=1
print(sys._jit.is_available(), sys._jit.is_enabled())

# Вывод на CPython 3.14.7 на macOS (arm64); в других версиях имена команд другие,
# а последняя строка зависит от того, как собран интерпретатор:
# ['Assign', 'Name', 'BinOp', 'Store', 'Name', 'Mult', 'Name', 'Load', 'Load']
# ('price', 'qty', 'total') 2
# ['RESUME', 'LOAD_FAST_BORROW_LOAD_FAST_BORROW', 'BINARY_OP', 'STORE_FAST', 'LOAD_FAST_BORROW', 'LOAD_SMALL_INT', 'BINARY_OP', 'RETURN_VALUE']
# ['BINARY_OP_MULTIPLY_INT', 'BINARY_OP_ADD_INT']
# ['BINARY_OP_MULTIPLY_FLOAT', 'BINARY_OP_EXTEND']
# ('inner', 'outer')
# 3
# []
# ['a']
# False 2 True
# (2000, 10, 10)
# True True False
# True False
# True False
```

`ast.walk` обходит дерево в ширину, поэтому узлы контекста `Store` и `Load` идут после имён. С `PYTHON_JIT=1` и без `-I` последняя строка печатает `True True`.

- [What's New in Python 3.11](https://docs.python.org/3.14/whatsnew/3.11.html) (проект Faster CPython: специализация, ленивые кадры); [What's New in Python 3.14](https://docs.python.org/3.14/whatsnew/3.14.html) (интерпретатор на хвостовых вызовах, заимствованные ссылки, инкрементальный сборщик и его откат в 3.14.5, официальные сборки с JIT-компилятором); [What's New in Python 3.15](https://docs.python.org/3.15/whatsnew/3.15.html).
- M. Shannon. [PEP 659 — Specializing Adaptive Interpreter](https://peps.python.org/pep-0659/). 2021.
- E. Snow, E. Elizondo. [PEP 683 — Immortal Objects, Using a Fixed Refcount](https://peps.python.org/pep-0683/). 2022.
- B. Bucher, S. Ostrowski. [PEP 744 — JIT Compilation](https://peps.python.org/pep-0744/). 2024.
- H. Xu, F. Kjolstad. [Copy-and-patch compilation](https://doi.org/10.1145/3485513). OOPSLA 2021.
- Исходный код CPython: [`Python/bytecodes.c`](https://github.com/python/cpython/blob/3.14/Python/bytecodes.c) и [`Python/ceval.c`](https://github.com/python/cpython/blob/3.14/Python/ceval.c); внутренняя документация CPython, `InternalDocs/`: [интерпретатор](https://github.com/python/cpython/blob/3.14/InternalDocs/interpreter.md), [кадры](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md), [сборщик мусора](https://github.com/python/cpython/blob/3.14/InternalDocs/garbage_collector.md) и [JIT](https://github.com/python/cpython/blob/3.14/InternalDocs/jit.md).
- A. Shaw. *CPython Internals: Your Guide to the Python 3 Interpreter*. Real Python, 2021. Главы о компиляторе, цикле вычисления и управлении памятью (книга написана для 3.9; специализирующий интерпретатор появился позже).
- L. Ramalho. *Fluent Python*, 2nd ed. O'Reilly, 2022. Гл. 6, ссылки на объекты, изменяемость и повторное использование.
