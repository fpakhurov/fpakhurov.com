Почти каждая программа ещё и читает или пишет текст: имена файлов, сообщения, таблицы результатов, а в курсах NLP — сами данные. Текст выглядит простым, но таким не является. Буква может занимать в файле один байт или четыре; две строки, которые выглядят одинаково, могут оказаться не равны; а сборка сообщения склеиванием строк — то, как в программах появляются ошибки внедрения. Эта заметка формулирует, что такое строка Python, как она превращается в байты и обратно, как её резать и чистить и как безопасно вставлять в неё значения — f-строками и шаблонными строками, которые появились в Python 3.14.

**Обозначения.** **Кодовая точка** (code point) — число, которое Юникод сопоставляет символу; записывается как U+ и не меньше четырёх шестнадцатеричных цифр: U+0041 — это `A`, U+20AC — `€`. **Байт** записывается двумя шестнадцатеричными цифрами, например `E2`.

## Отправная точка: текст как байты \{#baseline-text-as-bytes\}

В глубине каждый файл, каждое сетевое сообщение и каждая строка в памяти — последовательность байтов, чисел от 0 до 255. Самое старое соглашение, ASCII, отводит каждому из 128 символов один байт, так что для английского текста верно «один символ — один байт», и строку можно считать массивом байтов ([Биты, целые числа и порядок байтов](/ru/notes/acos/data-representation#characters-ascii-and-utf-8)). Это перестаёт работать на первом же `é`, `€` или `кот`: символов намного больше 256, поэтому большинство из них должны занимать несколько байтов, и в массиве байтов уже нет одного элемента на символ. Подсчёт, индексирование и разворот байтов тогда разрезают символы пополам.

## Строка — последовательность кодовых точек \{#a-string-is-a-sequence-of-code-points\}

<aside class="callout"><strong>Ключевая идея.</strong> `str` в Python — неизменяемая последовательность кодовых точек Юникода. Её длина, индексы и срезы считают кодовые точки, а не байты. Байты существуют только на границе программы, там, где текст читается из файла или сети или записывается туда: там `encode` превращает `str` в `bytes`, а `decode` превращает `bytes` обратно в `str`, и обоим нужно знать **кодировку** (encoding), почти всегда UTF-8.</aside>

```text
>>> s = "naïve €"
>>> len(s)
7
>>> [hex(ord(c)) for c in s]
['0x6e', '0x61', '0xef', '0x76', '0x65', '0x20', '0x20ac']
>>> s[2], ord(s[2]), chr(239)
('ï', 239, 'ï')
>>> b = s.encode("utf-8")
>>> b
b'na\xc3\xafve \xe2\x82\xac'
>>> len(b), type(b)
(10, <class 'bytes'>)
>>> b.decode("utf-8") == s
True
```

Построчно: в строке семь кодовых точек, включая пробел. `ord` даёт кодовую точку односимвольной строки, а `chr` выполняет обратное преобразование; `ï` — кодовая точка 239, U+00EF. `encode("utf-8")` даёт объект `bytes` из десяти байтов. При его отображении печатные байты ASCII показываются символами, а каждый другой байт — как `\x` и две шестнадцатеричные цифры: `ï` превратился в два байта `C3 AF`, а `€` — в три байта `E2 82 AC`. Декодирование байтов той же кодировкой возвращает ту же строку.

<Utf8Bytes />

1. Строка содержит семь символов.
2. Каждый из них — кодовая точка, число.
3. Индексы считают кодовые точки: с 0 от начала и с −1 от конца.
4. UTF-8 хранит каждую кодовую точку в одном–четырёх байтах: один для ASCII, два для большинства латинских букв с диакритикой и для кириллицы, три для большинства других распространённых символов, таких как `€` и китайские иероглифы, четыре для эмодзи.
5. Поэтому две длины различаются: 7 кодовых точек, 10 байт.

**UTF-8 одним правилом.** Первый байт символа говорит, сколько байтов за ним следует, и каждый следующий байт начинается с битов `10`; таблица и разобранный пример есть в [курсе по архитектуре компьютера и ОС](/ru/notes/acos/data-representation#characters-ascii-and-utf-8). На практике важны два следствия. Текст ASCII без изменений является корректным UTF-8. А последовательность байтов, разрезанная посреди символа, — некорректный UTF-8, о чём и говорит самая частая ошибка декодирования:

```text
>>> "€".encode("utf-8")[:2].decode("utf-8")
Traceback (most recent call last):
  ...
UnicodeDecodeError: 'utf-8' codec can't decode bytes in position 0-1: unexpected end of data
```

**`str` и `bytes` не смешиваются.** Это разные типы, и Python отказывается угадывать кодировку между ними:

```text
>>> data = b"abc"
>>> data[0], type(data[0])
(97, <class 'int'>)
>>> "abc"[0]
'a'
>>> "abc" + b"def"
Traceback (most recent call last):
  ...
TypeError: can only concatenate str (not "bytes") to str
```

Элемент `bytes` — это `int` от 0 до 255; элемент `str` — строка длины 1. Отдельного типа для символа в Python нет.

**Ошибка: не та кодировка.** Декодирование не той кодировкой, которой кодировали, либо завершается ошибкой, либо, что хуже, успешно даёт неверный текст. Второй исход порождает знакомую мешанину символов — **кракозябры** (mojibake):

```text
>>> "café".encode("utf-8").decode("latin-1")
'cafÃ©'
>>> "€".encode("latin-1")
Traceback (most recent call last):
  ...
UnicodeEncodeError: 'latin-1' codec can't encode character '\u20ac' in position 0: ordinal not in range(256)
```

Latin-1 сопоставляет каждому байту один символ, поэтому «декодируются» любые байты, и два байта UTF-8 буквы `é` становятся `Ã` и `©`. Кроме того, в Latin-1 всего 256 символов, поэтому `€` в ней вообще нельзя закодировать. Если в выводе видны `Ã©` или `Ð¾`, значит, текст в UTF-8 был декодирован как Latin-1 или как кодовая страница Windows. Правило, которое предотвращает оба исхода: декодировать байты как можно раньше, внутри программы работать с `str`, кодировать как можно позже и каждый раз называть кодировку. Для файлов это делает `open(path, encoding="utf-8")`. Без этого аргумента Python 3.14 использует кодировку локали, которая в большинстве систем macOS и Linux — UTF-8, а в Windows часто нет; Python 3.15, вышедший в октябре 2026 года, делает UTF-8 кодировкой по умолчанию везде ([PEP 686](#references)). К этому вернётся [заметка о файлах](/ru/notes/python/files-and-exceptions).

**Одна видимая буква, две строки.** Юникод может записать `é` одной кодовой точкой, U+00E9, или как `e`, за которой следует комбинируемый знак акута (combining accent) U+0301. Выглядят они одинаково, но это разные строки:

```text
>>> a = "\N{LATIN SMALL LETTER E WITH ACUTE}"
>>> b = "e\N{COMBINING ACUTE ACCENT}"
>>> a, b, a == b, len(a), len(b)
('é', 'é', False, 1, 2)
>>> import unicodedata
>>> unicodedata.normalize("NFC", b) == a
True
```

`\N{...}` внутри строкового литерала вставляет символ по его имени в Юникоде. `unicodedata.normalize("NFC", text)` объединяет такие пары в одиночные кодовые точки, так что одинаково выглядящий текст оказывается равным; [заметка о тексте](/ru/notes/nlp/text-as-data#what-a-string-is) курса NLP перечисляет четыре формы нормализации и когда какая используется. Даже `len` после нормализации — не то, что читатель считает символом: эмодзи семьи из трёх человек — это пять кодовых точек, три человека, соединённых двумя невидимыми соединителями, и 18 байт в UTF-8.

**Как CPython хранит строку.** `str` в памяти — не UTF-8. Начиная с Python 3.3 ([PEP 393](#references)) CPython хранит каждую строку с фиксированной шириной, выбранной по самому широкому символу: 1 байт на кодовую точку, если все они меньше 256, 2 байта, если все меньше 65 536, иначе 4. Тогда любой индекс стоит одинаково, `s[i]` — это одно обращение к массиву, чего UTF-8 обеспечить не мог бы. `sys.getsizeof` для строк из десяти символов показывает три ширины (64-битный CPython 3.14):

```text
>>> import sys
>>> [sys.getsizeof(x * 10) for x in ("a", "é", "€", "😀")]
[51, 67, 78, 100]
```

Строка ASCII занимает 40-байтовый заголовок плюс 10 байт и завершающий нулевой байт. У остальных заголовок больше, 56 байт, плюс 10 кодовых точек и завершающий ноль, каждый по 1, 2 или 4 байта: $56 + 11 = 67$, $56 + 22 = 78$ и $56 + 44 = 100$. Один эмодзи в длинном тексте увеличивает память под всю строку в четыре раза.

## Индексы и срезы \{#indexing-and-slicing\}

**Правило.** `s[i]` — кодовая точка на позиции `i`, считая с 0; отрицательный индекс считается с конца, `s[-1]` — последний элемент. `s[start:stop]` — **срез** (slice) от `start` до `stop`, не включая `stop`; любую границу можно опустить, и тогда она означает начало или конец. `s[start:stop:step]` берёт каждую `step`-ю кодовую точку, в обратную сторону, если `step` отрицателен. Индекс за пределами диапазона — ошибка; срез за пределами диапазона — нет, он просто короче.

```text
>>> word = "Python"
>>> word[0], word[5], word[-1], word[-6]
('P', 'n', 'n', 'P')
>>> word[0:2], word[2:], word[:2] + word[2:]
('Py', 'thon', 'Python')
>>> word[::2], word[::-1], word[1:100], word[10:]
('Pto', 'nohtyP', 'ython', '')
>>> word[6]
Traceback (most recent call last):
  ...
IndexError: string index out of range
```

**Почему полуоткрытые.** Индексы обозначают промежутки между кодовыми точками, а не сами кодовые точки: промежуток 0 перед `P`, промежуток 6 после `n`. `word[a:b]` — всё, что лежит между промежутком `a` и промежутком `b`. Отсюда три полезных факта. Длина `word[a:b]` равна `b - a`. `word[:k] + word[k:]` равно `word` для любого `k`, без перекрытия и без потерь. И `word[:k]` — первые `k` кодовых точек. То же правило действует для списков, кортежей и массивов NumPy, и его же использует `range(a, b)`.

## Строки неизменяемы \{#strings-are-immutable\}

Ни одна операция не меняет строку. Присваивание по индексу — ошибка, а каждый метод, который как будто меняет строку, возвращает новую:

```text
>>> word = "Python"
>>> word[0] = "J"
Traceback (most recent call last):
  ...
TypeError: 'str' object does not support item assignment
>>> "J" + word[1:]
'Jython'
>>> word.replace("P", "J"), word
('Jython', 'Python')
```

Неизменяемость делает строки безопасными для совместного использования: как в заметке [Значения, типы и имена](/ru/notes/python/values-and-names#mutable-and-immutable-objects), строка, связанная с несколькими именами или используемая как ключ словаря, никогда не изменится ни под одним из них. Цена в том, что построение длинной строки повторяющимся `+=` каждый раз создаёт новую строку и копирует всё накопленное, а это в худшем случае стоит времени, растущего как квадрат итоговой длины ([документация Python, common sequence operations](#references), примечание 6). Куски лучше собирать в список и соединять один раз:

```text
>>> parts = []
>>> for word in ["to", "be", "or", "not"]:
...     parts.append(word.upper())
...
>>> " ".join(parts)
'TO BE OR NOT'
```

## Распространённые методы \{#common-methods\}

Несколько методов покрывают большую часть работы с текстом. Каждый возвращает новый объект; ни один не меняет строку.

| Метод | Что возвращает | Пример и результат |
| --- | --- | --- |
| `strip()` | строку без пробельных символов с обоих концов | `"  a b  ".strip()` → `'a b'` |
| `split()` | список кусков между сериями пробельных символов | `"a b  c".split()` → `['a', 'b', 'c']` |
| `split(sep)` | список кусков между каждыми вхождениями `sep` | `"a,b,,c".split(",")` → `['a', 'b', '', 'c']` |
| `sep.join(items)` | элементы, соединённые через `sep` | `"-".join(["2026", "10", "22"])` → `'2026-10-22'` |
| `lower()`, `upper()` | строку в нижнем или верхнем регистре | `"straße".upper()` → `'STRASSE'` |
| `casefold()` | агрессивный нижний регистр для сравнений | `"Straße".casefold()` → `'strasse'` |
| `replace(old, new)` | строку, где каждое `old` заменено на `new` | `"Python".replace("P", "J")` → `'Jython'` |
| `startswith(p)`, `endswith(p)` | начинается ли или заканчивается ли строка на `p` | `"banana".startswith("ban")` → `True` |
| `find(sub)`, `index(sub)` | первую позицию `sub`; если её нет, `find` даёт −1, а `index` возбуждает `ValueError` | `"banana".find("n")` → `2` |
| `count(sub)` | число непересекающихся вхождений | `"banana".count("an")` → `2` |
| `isdigit()`, `isalpha()`, `isspace()` | все ли символы этого вида | `"4.2".isdigit()` → `False` |

`sub in s` проверяет наличие подстроки: `"nan" in "banana"` равно `True`. Стоит обратить внимание на два варианта `split`: без аргумента серии пробельных символов считаются одним разделителем, а пустые куски отбрасываются; с аргументом разделяет каждое вхождение, поэтому две запятые дают пустой кусок. `"Straße".lower()` сохраняет `ß`, поэтому результат не равен `"STRASSE".lower()`; `casefold` предназначен для сравнения без учёта регистра и превращает `ß` в `ss`.

**`repr` против `str`.** REPL показывает строку через `repr`, который добавляет кавычки и записывает специальные символы экранированными последовательностями; `print` выводит сами символы:

```text
>>> s = "tab\there"
>>> print(s)
tab	here
>>> s
'tab\there'
```

`repr` — форма для отладки, поскольку показывает невидимые символы вроде табуляций и пробелов в конце строки. **«Сырая» строка** (raw string), `r"C:\new"`, считает обратную косую черту обычным символом, а это и нужно регулярным выражениям и путям Windows.

## f-строки и спецификации формата \{#f-strings-and-format-specifications\}

**f-строка** (f-string), литерал с префиксом `f`, вычисляет выражения в фигурных скобках при выполнении строки кода и вставляет их значения ([PEP 498](#references)). После выражения необязательный `!r` применяет `repr`, а необязательное двоеточие открывает **спецификацию формата** (format specification) — маленький язык, который говорит, как показать значение ([документация Python, format specification mini-language](#references)):

```text
>>> name, pi, n = "Ada", 3.14159265, 1234567
>>> f"Hello, {name}!"
'Hello, Ada!'
>>> f"{pi:.2f}", f"{pi:10.3f}|", f"{pi:<10.3f}|", f"{n:,}", f"{n:_}"
('3.14', '     3.142|', '3.142     |', '1,234,567', '1_234_567')
>>> f"{0.256:.1%}", f"{255:x}", f"{255:#010b}", f"{42:05d}", f"{1e-7:.2e}"
('25.6%', 'ff', '0b11111111', '00042', '1.00e-07')
>>> f"{name!r}", f"{name:>6}|", f"{name:^7}|", f"{name:*<6}"
("'Ada'", '   Ada|', '  Ada  |', 'Ada***')
>>> f"{n=}", f"{pi * 2 = :.3f}"
('n=1234567', 'pi * 2 = 6.283')
```

Как читать спецификации: `.2f` — число с фиксированной точкой и 2 знаками после неё; `10.3f` дополняет до ширины 10, а `<` выравнивает влево (числа по умолчанию выравниваются вправо, строки — влево); `,` и `_` группируют тысячи; `.1%` умножает на 100 и добавляет знак процента; `x` — шестнадцатеричная запись, `#010b` — двоичная с префиксом `0b`, дополненная нулями до ширины 10; `05d` дополняет целое число нулями; `.2e` — экспоненциальная запись. `^` выравнивает по центру, а символ перед `<`, `>` или `^` — заполнитель. `{n=}` (начиная с 3.8) печатает выражение, знак равенства и значение, что удобно для быстрого отладочного вывода. Начиная с 3.12 ([PEP 701](#references)) выражение может содержать те же кавычки, что и сама f-строка, как в `f"{items["a"]}"`. Спецификация сама может содержать значение в фигурных скобках: `f"{pi:{width}.2f}"`.

Курсы машинного обучения так печатают каждую метрику: `f"{loss:.4f}"` для функции потерь, `f"{acc:.1%}"` для доли правильных ответов, выровненные столбцы для таблицы результатов, как в разделе «Код» ниже.

## Шаблонные строки: значения отдельно \{#template-strings-values-kept-apart\}

f-строка сразу даёт готовую `str`. В этом её сила и, в одной ситуации, её опасность: как только значение вклеено в текст, уже ничто не может сказать, какие части написал программист, а какие пришли извне. Вклеивание комментария пользователя в HTML или имени в SQL-запрос позволяет тексту пользователя действовать как разметка или как код. Это **инъекция** (injection), одна из самых распространённых уязвимостей.

**Правило.** Python 3.14 добавляет **шаблонные строки** (template strings) — литералы с префиксом `t` ([PEP 750](#references)). t-строка пишется как f-строка, но её значение — объект `string.templatelib.Template`, а не `str`. Этот объект хранит литеральные части и подставленные значения отдельно. Его `strings` — литеральные куски, его `interpolations` — объекты `Interpolation`, в каждом из которых есть значение, исходный текст выражения, преобразование (`'r'`, `'s'`, `'a'` или `None`) и спецификация формата; перебор шаблона выдаёт куски по порядку. У шаблона нет собственного текста: превратить его в текст должна какая-то функция, **рендерер** (renderer), и эта функция может обращаться со значениями иначе, чем с литеральными частями.

```text
>>> name = "Ada"
>>> template = t"Hello, {name}!"
>>> type(template)
<class 'string.templatelib.Template'>
>>> template.strings, template.values
(('Hello, ', '!'), ('Ada',))
>>> list(template)
['Hello, ', Interpolation('Ada', 'name', None, ''), '!']
```

**Разобранный пример: безопасный HTML.** Рендерер, который экранирует каждое значение, но не трогает литеральную разметку:

```text
>>> from string.templatelib import Interpolation, convert
>>> import html
>>> def render_html(template):
...     parts = []
...     for item in template:
...         if isinstance(item, Interpolation):
...             value = convert(item.value, item.conversion)
...             parts.append(html.escape(format(value, item.format_spec)))
...         else:
...             parts.append(item)
...     return "".join(parts)
...
>>> comment = "<script>alert('hi')</script>"
>>> price = 3.5
>>> f"<p>{comment}</p>"
"<p><script>alert('hi')</script></p>"
>>> render_html(t"<p>{comment}</p> costs <b>{price:.2f}</b>")
'<p>&lt;script&gt;alert(&#x27;hi&#x27;)&lt;/script&gt;</p> costs <b>3.50</b>'
```

f-строка вклеила скрипт в страницу. Шаблон позволил рендереру увидеть, что `comment` — значение, и `html.escape` превратил его `<` и `'` в сущности HTML, так что браузер покажет текст, а не выполнит его; литеральные `<p>` и `<b>` остались разметкой. Рендерер должен сам применить преобразование и спецификацию формата, через `convert` и `format`; рендерер, который о них забудет, напечатает `3.5` вместо `3.50`.

**Разобранный пример: SQL-запрос с параметрами.** Рендерер может и вовсе отказаться вклеивать значения и передавать их отдельно, как того хотят драйверы баз данных:

```text
>>> def to_sql(template):
...     query, params = [], []
...     for item in template:
...         if isinstance(item, Interpolation):
...             query.append("?")
...             params.append(item.value)
...         else:
...             query.append(item)
...     return "".join(query), params
...
>>> user = "x'; DROP TABLE users; --"
>>> to_sql(t"SELECT * FROM users WHERE name = {user}")
('SELECT * FROM users WHERE name = ?', ["x'; DROP TABLE users; --"])
>>> f"SELECT * FROM users WHERE name = '{user}'"
"SELECT * FROM users WHERE name = 'x'; DROP TABLE users; --'"
```

Версия с f-строкой — запрос, который удаляет таблицу; версия с шаблоном — запрос с заполнителем и параметром, который база данных считает данными, что бы в нём ни было.

**Чем шаблон не является.** Это не строка: `str(template)` даёт его `repr`, а не текст, а `t"a{1}" + "b"` возбуждает `TypeError`; текст делает только рендерер. Шаблоны оправданы там, где со значениями нужно обращаться особо (HTML, SQL, команды оболочки, структурированное логирование); для обычного вывода инструментом остаются f-строки. Стандартная библиотека 3.14 предоставляет типы и `convert`, а рендереры приходят из библиотек, которым они нужны.

## Обработка текста для NLP \{#text-processing-for-nlp\}

Каждый конвейер NLP начинается с операций этой заметки: нормализовать Юникод, изменить регистр, разрезать текст на единицы. Минимальная версия:

```text
>>> import re
>>> text = "Don't panic: the café opens at 9:30!"
>>> text.lower().split()
["don't", 'panic:', 'the', 'café', 'opens', 'at', '9:30!']
>>> re.findall(r"\w+|[^\w\s]", text)
['Don', "'", 't', 'panic', ':', 'the', 'café', 'opens', 'at', '9', ':', '30', '!']
```

`split` оставляет знаки препинания приклеенными к словам. Регулярное выражение `\w+|[^\w\s]` из модуля `re` берёт либо серию символов слова (буквы, цифры и знак подчёркивания, в любой письменности, поскольку `\w` в Python учитывает Юникод), либо один символ, который не является ни символом слова, ни пробельным; оно отделяет знаки препинания и разбивает `Don't` на три токена. Каждый выбор здесь (приведение к нижнему регистру, нормализация, что считать словом) меняет словарь, который видит модель, и курс NLP обсуждает их как решения при моделировании в заметке [Текст как данные](/ru/notes/nlp/text-as-data#segmentation-cutting-the-string-into-units). Современные модели заменяют разбиение на слова токенизаторами подслов, и байтовые, как у GPT-2, начинают ровно с байтов UTF-8 из этой заметки: их базовый словарь — 256 значений байта, поэтому никакой текст никогда не оказывается вне словаря ([Токенизация](/ru/notes/nlp/tokenization#byte-pair-encoding)). Длины, которые считает модель, — это токены, а не кодовые точки и не байты, и все три величины расходятся:

```text
>>> words = ["cat", "кот", "猫", "🐈"]
>>> [(w, len(w), len(w.encode("utf-8"))) for w in words]
[('cat', 3, 3), ('кот', 3, 6), ('猫', 1, 3), ('🐈', 1, 4)]
```

## Что изменилось \{#what-changed\}

| | Текст как байты (отправная точка) | `str` в Python |
| --- | --- | --- |
| Единица | байт | кодовая точка Юникода |
| `len`, индексы, срезы | считают байты; могут разрезать символ пополам | считают кодовые точки |
| Байты | единственное представление | только на границе: `encode` и `decode` с названной кодировкой |
| Изменение текста | на месте | неизменяемы; методы возвращают новые строки; собирать через `join` |
| Вставка значений в текст | конкатенация | f-строки со спецификациями формата; t-строки, когда значениям нужен рендерер |

## Ограничения \{#limitations\}

- **Кодовые точки — не то, что видит читатель.** Комбинируемые знаки, последовательности эмодзи и некоторые письменности складывают один видимый символ из нескольких кодовых точек; чтобы считать такие символы (кластеры графем, grapheme clusters), нужна сторонняя библиотека, а нормализация помогает лишь отчасти.
- **Регулярные выражения только используются.** У модуля `re` собственный язык, описанный в [Regular Expression HOWTO](https://docs.python.org/3.14/howto/regex.html); курс использует короткие шаблоны и объясняет каждый там, где он появляется.
- **Умолчания, зависящие от локали.** В 3.14 и более ранних версиях, где UTF-8 ещё не кодировка по умолчанию, код, который открывает файлы без `encoding=`, ведёт себя в Windows иначе; этот аргумент нужно передавать всегда.
- **Шаблонные строки — новинка.** Рендереры выше иллюстрируют механизм. Рабочий код должен использовать поддерживаемую библиотеку для экранирования HTML и API параметров своего драйвера базы данных.

## Что нужно запомнить \{#what-you-should-remember\}

- `str` — неизменяемая последовательность кодовых точек Юникода; `len`, индексы и срезы считают кодовые точки.
- `bytes` — то, что передают файлы и сети. `encode` и `decode` преобразуют на границе, всегда с названной кодировкой, почти всегда UTF-8, в которой кодовая точка занимает от 1 до 4 байт.
- Кракозябры вроде `Ã©` означают, что байты UTF-8 декодированы не той кодировкой. Текст, который может содержать комбинируемые знаки, перед сравнением нормализуют в NFC.
- Срезы полуоткрыты: в `s[a:b]` ровно `b - a` кодовых точек, и `s[:k] + s[k:] == s`. Отрицательные индексы считаются с конца.
- Строки никогда не меняются; длинный текст собирают через `"".join(parts)`.
- f-строки форматируют значения спецификациями вроде `.3f`, `,`, `.1%`, `>10`; `{x=}` печатает и само выражение.
- t-строка (3.14) — это `Template`, который хранит литеральный текст и значения отдельно, чтобы рендерер мог экранировать значения или передать их как параметры.

## Код \{#code\}

Скрипт выполняет каждую часть заметки: кодовые точки против байтов UTF-8 для слов в четырёх письменностях и эмодзи, нормализацию разложенной буквы, ошибку с неверной кодировкой, срезы, маленький нормализатор и токенизатор вроде тех, с которых начинаются конвейеры NLP, таблицу, отформатированную спецификациями формата, и шаблонную строку, безопасно отрисованную в HTML. Запуск — `python -I text.py`; скрипт использует только стандартную библиотеку. Выравнивание первого блока сбивается для `猫` и `🐈`, потому что форматирование дополняет строку по кодовым точкам, а терминал рисует эти символы шириной в две колонки, — ещё один пример того, что «длина» зависит от того, кто считает.

```python
"""Strings as code points, bytes, slices, formats and templates (Python 3.14)."""
import html
import re
import unicodedata
from string.templatelib import Interpolation, Template, convert

# 1. Кодовые точки против байтов UTF-8
for word in ["cat", "naïve", "кот", "€", "猫", "🐈"]:
    data = word.encode("utf-8")
    print(f"{word!r:8} len={len(word)}  bytes={len(data)}  {data.hex(' ')}")

# 2. Одна видимая буква, две записи; NFC делает их равными
composed, decomposed = "caf\N{LATIN SMALL LETTER E WITH ACUTE}", "cafe\N{COMBINING ACUTE ACCENT}"
print(composed == decomposed, len(composed), len(decomposed),
      unicodedata.normalize("NFC", decomposed) == composed)

# 3. Декодирование не тем кодеком: ошибки нет, текст неверный
print("café".encode("utf-8").decode("latin-1"))
try:
    "café".encode("utf-8")[:4].decode("utf-8")     # разрез внутри двух байтов é
except UnicodeDecodeError as err:
    print("UnicodeDecodeError:", err.reason)

# 4. Индексы и срезы: полуоткрытые диапазоны, отрицательные индексы
s = "Python"
print(s[0], s[-1], s[1:4], s[:2] + s[2:], s[::-1], repr(s[10:]))

# 5. Крошечный нормализатор и токенизатор, с каких начинаются конвейеры NLP
def tokenize(text):
    text = unicodedata.normalize("NFC", text).casefold()
    return re.findall(r"\w+|[^\w\s]", text)

print(tokenize("Don't PANIC: the cafe\N{COMBINING ACUTE ACCENT} opens at 9:30!"))

# 6. f-строки со спецификациями формата
rows = [("loss", 0.034567, 1200), ("accuracy", 0.98213, 1200), ("tokens", 1234567, 3)]
for name, value, n in rows:
    shown = f"{value:,}" if isinstance(value, int) else f"{value:.3f}"
    print(f"{name:<10}|{shown:>10}|{n:>6}|{n / 1200:6.1%}")

# 7. Шаблонные строки: значения остаются отдельными, пока их не обработает рендерер
def render_html(template: Template) -> str:
    out = []
    for item in template:
        if isinstance(item, Interpolation):
            value = convert(item.value, item.conversion)
            out.append(html.escape(format(value, item.format_spec)))
        else:
            out.append(item)
    return "".join(out)

comment, price = "<b>great</b> & cheap", 3.5
page = t"<p>{comment}</p><p>{price:.2f} EUR</p>"
print(page.strings)
print(page.values)
print(render_html(page))

# Вывод в CPython 3.14.7 (одинаковый на любой платформе):
# 'cat'    len=3  bytes=3  63 61 74
# 'naïve'  len=5  bytes=6  6e 61 c3 af 76 65
# 'кот'    len=3  bytes=6  d0 ba d0 be d1 82
# '€'      len=1  bytes=3  e2 82 ac
# '猫'      len=1  bytes=3  e7 8c ab
# '🐈'      len=1  bytes=4  f0 9f 90 88
# False 4 5 True
# cafÃ©
# UnicodeDecodeError: unexpected end of data
# P n yth Python nohtyP ''
# ['don', "'", 't', 'panic', ':', 'the', 'café', 'opens', 'at', '9', ':', '30', '!']
# loss      |     0.035|  1200|100.0%
# accuracy  |     0.982|  1200|100.0%
# tokens    | 1,234,567|     3|  0.2%
# ('<p>', '</p><p>', ' EUR</p>')
# ('<b>great</b> & cheap', 3.5)
# <p>&lt;b&gt;great&lt;/b&gt; &amp; cheap</p><p>3.50 EUR</p>
```

Токенизатор получает `cafe` с отдельным комбинируемым знаком акута, и NFC превращает их в одну кодовую точку `é` до того, как сработает регулярное выражение; без нормализации `\w+` всё равно оставил бы знак вместе с его буквой, но токен не был бы равен `café`, набранному одной кодовой точкой.
