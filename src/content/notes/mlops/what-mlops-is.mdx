An editor changes the contrast calculation used by a preview-quality classifier. The weight file is unchanged, the server returns valid JSON, and the old accuracy report still looks good. Yet different cards now enter the review queue. To explain the change, we need the version of the feature calculation as well as the model.

**MLOps** is the engineering of repeatable model development, release and operation together with the data and evidence those activities depend on. DevOps already supplies version control, tests and deployment automation. A learned component adds changing training data, delayed labels and statistical acceptance criteria.

## A weight file is not a release \{#baseline-a-model-handed-over-in-a-file\}

For our fictional preview service, define a release by four values: input schema, feature transform, scoring artifact and decision threshold. The artifact may be a trained model or a rule used while the product is being tested. A threshold change can alter editor workload even if every score stays identical.

| Release field | Original fixture value | Why it matters |
| --- | --- | --- |
| Schema | `preview-v1` | Units and valid input ranges |
| Features | `contrast-v1` | Meaning of the model input |
| Weights | `fixture-score-v1` | Scoring behaviour |
| Threshold | `0.6` | Action taken from the score |

A canonical JSON serialization of this record has SHA-256 beginning `adf4ab3310e79`. Changing only the feature identifier to `contrast-v2` produces `bd5f3d6ab786`. The hash identifies bytes; it does not prove that a release is correct or that its inputs were legally obtained. Keep the underlying artifacts and their source records as well.

## Follow one decision beyond the model \{#the-model-is-a-small-box\}

An uploaded card is decoded, transformed, scored and routed. A prediction event records the document ID, release ID, decision time and score. Later, an editor supplies a repair label. Joining that label to the earlier prediction supports evaluation; overwriting the prediction with the repaired state destroys the evidence.

The event path is our architectural boundary. Decoding owns file validity. Feature code owns units. The scorer owns a versioned input/output contract. Routing owns the review action. An editor can correct a card without changing the model, and a model can be replaced without changing the stored original. These separations make failures easier to localize.

## Dependencies become future work \{#hidden-technical-debt\}

Sculley and coauthors describe technical debt arising from dependencies around learned components ([2015](#references)). The following preview-service situations are independently specified illustrations of those concepts.

### Coupled features \{#entanglement-changing-anything-changes-everything\}

Suppose contrast is normalized using a population mean. Adding a new scanner population changes that mean and therefore changes old scanners' feature values too. A local data-source change has a wider effect. Version the normalization state and evaluate the affected populations together.

### Hidden callers \{#undeclared-consumers\}

An editor dashboard starts reading the raw score directly to sort its queue, although the documented API promised only a review decision. A new calibrated model preserves the decisions but changes score order. Register this consumer and give it a contract before treating the replacement as compatible.

### Unowned transformations \{#glue-code-and-pipeline-jungles\}

A scheduled script clips values to a valid range; a web handler rejects them instead. Both call the same model, so a shared weight file does not make their behaviour equivalent. Put the transformation behind one tested definition and check that both paths use its declared version.

### Hidden settings \{#configuration-debt\}

An environment variable changes the threshold from 0.6 to 0.7 without producing a release record. The behaviour changed even though the container digest did not. Configuration that changes a decision belongs in provenance and review.

### Feedback changes the data \{#other-debts-in-brief\}

If only flagged cards receive labels, the next training set overrepresents the old model's suspicions. The loop can reinforce its own blind spots. A separately sampled audit of unflagged cards provides information that the decision policy otherwise prevents us from observing.

## Close the evidence loop \{#the-lifecycle-loop\}

Start with a product outcome and a dataset whose collection is permitted. Split data to match the intended evaluation population. Train or configure a candidate, evaluate it against acceptance criteria, package a release, and observe the resulting decisions. New evidence can justify another candidate; an alert need not automatically start training.

For a tiny fictional cohort, eight cards were submitted and only six have labels after the chosen waiting period. Label coverage is $6/8=75\%$. Quality computed on those six describes the labelled subset. It does not establish quality on all eight unless the missing-label mechanism supports that inference. Report coverage, maturity time and exclusions beside the score.

Reproducibility requires enough information to repeat the computation: code revision, input snapshot, transform state, environment and randomness controls. Traceability asks a related question: which computation produced this particular deployed artifact or decision? MLflow connects runs, logged models and registered versions; a registry alias can move, so preserve the resolved version in the record ([MLflow](#references)).

## Automate a specific repeated decision \{#maturity-levels\}

<span id="googles-levels-0-1-and-2"></span>
<span id="microsofts-five-levels"></span>

Google's MLOps framework distinguishes manual work, automated ML pipelines and CI/CD for those pipelines. Microsoft's framework uses five capability levels. Their numbering belongs to different frameworks and is not a universal certification. Both are useful prompts for identifying missing capabilities; consult their definitions before comparing organizations ([Google Cloud; Microsoft](#references)).

For the preview service, ask whether another operator can reproduce a candidate, locate its evaluation, deploy it, and restore the preceding release. Automate the steps that recur and whose acceptance conditions are explicit. Automating a poorly defined label or a biased sample can repeat the mistake more quickly.

## Assign ownership to artifacts and outcomes \{#roles\}

The data owner defines how a repair label is collected and corrected. The model owner investigates candidate behaviour and limits. The platform owner maintains execution, deployment and recovery. The product owner decides how missed defects and review delay affect users. These are responsibilities, not a required organization chart; a small team may combine them while retaining a named decision owner.

## Follow the course by the failure you need to prevent \{#the-plan-of-the-course\}

[System design](/notes/mlops/ml-system-design) connects outcomes to requirements. Data pipelines and feature consistency keep training and inference aligned. Experiments and tests establish candidate evidence. Serving and rollout govern exposure. Monitoring and retraining handle change after release. Responsibility and cost set constraints on the whole process.

## What changed \{#what-changed\}

The unchanged weight file no longer conceals the contrast update: it creates a different release identity. A repair label can be traced back to the decision it evaluates, and missing labels remain visible in the coverage count.

## Limits \{#limitations\}

A hash cannot reveal an undocumented dependency. A repeatable pipeline can reproduce an unsuitable model. A passing offline evaluation can miss a new scanner type. Provenance, statistical evaluation and operational monitoring address different failure modes and need separate evidence.

## What to retain \{#what-you-should-remember\}

Version the complete decision path. Preserve predictions before labels arrive. Track label coverage and sampling. Test feature contracts on both execution paths. Automate explicit decisions and keep an owner for their consequences.
