Adding workers changes two things at once: where the training state lives and which computations must exchange results. A model can fit across three devices yet run slower because every layer waits for communication. Another can finish a step faster while silently changing the loss normalization. We need a memory ledger, a computation contract and a schedule before a device count is meaningful.

This note uses original scalar data, integer vectors and hypothetical byte counts. A standard-library program executes the reductions, matrix identities, dependency schedule and gradient recomputation. It does not run PyTorch, NCCL or a GPU, and its slot counts are not measured accelerator timings.

## Start with the operation that must remain unchanged \{#baseline-one-gpu\}

A training step reads a specified batch, computes a loss and gradients, then updates parameters and optimizer state. Distributing that step should preserve the intended objective unless a deliberate algorithm change is being evaluated. Identical filenames or equal parameter counts do not establish this: data sampling, gradient normalization and update timing matter.

First establish a small reference calculation. Compare distributed outputs and gradients against it on permitted fixed inputs. Then measure device memory, time spent computing, time waiting for collectives and input-pipeline stalls. An out-of-memory failure and low utilization require different interventions. A faster step also does not guarantee less time to the required validation quality if the effective batch or optimizer behaviour changed.

For the following memory exercise, stipulate a model with twelve million trainable scalar parameters. That is a sizing input, not an actual trained network. Separate it from the six scalar records used to check gradient averaging: each small case isolates one mechanism instead of pretending to benchmark a full training system.

## Count every state and its lifetime \{#where-the-memory-goes\}

Assume a particular mixed-precision layout: two bytes per working parameter, four per gradient, four for a master parameter and eight for the two optimizer moments. The last three arrays are explicitly full precision. Thus persistent model-related storage is

$$
M=N(2+4+4+8)=18N\text{ bytes}.
$$

For $N=12000000$, this is 216 MB in decimal units. A different gradient dtype, optimizer, master-copy policy or parameter aliasing changes the ledger. There is no universal bytes-per-parameter constant for mixed precision. Count actual allocations in the implementation being considered.

This ledger excludes activations retained for backward, temporary kernel workspaces, collective buffers, allocator overhead and input batches. Peak memory depends on which objects coexist. Adding the largest independent measurements from different times can overestimate the peak; ignoring a temporarily gathered parameter block can underestimate it. A useful profile records allocation lifetimes around forward, backward and the optimizer step.

Reducing a local microbatch often reduces activations while leaving parameter and optimizer storage unchanged. Sharding optimizer state addresses a different part of the ledger. Activation recomputation trades extra work for fewer retained intermediates. These choices can be combined, but each needs its own measured effect and correctness check.

## Average examples, not arbitrary worker means \{#data-parallelism\}

In synchronous data parallelism, workers hold compatible replicas and process different data. They combine gradients before applying the same update. For a loss defined as the mean over all examples,

$$
g=\frac{\sum_{r=1}^{R}n_rg_r}{\sum_{r=1}^{R}n_r},
$$

where $g_r$ is the local mean gradient and $n_r$ is the number of included examples. Averaging worker means is equivalent only when those counts are equal, or when the intended weighting explicitly gives every worker equal weight.

Consider $f_w(x)=wx$, the loss $\tfrac12(wx-y)^2$, and $w=1$. The individual gradient is $(x-y)x$. Our independently specified records are:

| Worker | Records $(x,y)$ | Gradient sum | Count | Local mean |
| --- | --- | ---: | ---: | ---: |
| 0 | $(1,0)$ | 1 | 1 | 1 |
| 1 | $(2,1),(1,2)$ | 1 | 2 | $1/2$ |
| 2 | $(3,1),(2,0),(1,1)$ | 10 | 3 | $10/3$ |

The six-example mean is $12/6=2$. The unweighted mean of the three worker means is $29/18$, which optimizes a different weighting. With learning rate 0.1, the correct update gives $w=1-0.1\cdot2=0.8$. This difference comes from normalization, before any floating-point or networking effect.

```python
from fractions import Fraction

workers = [[(1, 0)], [(2, 1), (1, 2)], [(3, 1), (2, 0), (1, 1)]]
sums = [sum((x - y) * x for x, y in rows) for rows in workers]
means = [Fraction(total, len(rows)) for total, rows in zip(sums, workers)]
pooled = Fraction(sum(sums), sum(map(len, workers)))
print("pooled:", pooled)
print("mean of worker means:", sum(means) / len(means))
print("updated weight:", 1 - pooled / 10)
```

Executed output:

```text
pooled: 2
mean of worker means: 29/18
updated weight: 4/5
```

PyTorch DDP synchronizes gradient buckets during backward and lets each local optimizer update its replica. Its documentation explains ordering requirements and overlap with computation. The application still owns data partitioning and loss meaning. Check the last partial batch, duplicated sampler records and token masks: equally sized tensors can contain different numbers of eligible loss terms.

Gradient accumulation introduces another boundary. If several microbatches form one update, normalize by the intended combined count and update only after their contributions are complete. Clipping every local gradient before reduction generally differs from clipping the combined gradient. Batch-dependent layers and stochastic operations can also prevent a naive split from matching a single reference computation.

### Account for the collective's payload \{#the-cost-of-all-reduce\}

All-reduce combines corresponding values and makes the result available to every participating rank. Reduce-scatter distributes reduced chunks; all-gather distributes those chunks again. NCCL documents these semantic operations. It does not promise that every call uses the particular ring schedule we study here.

Split a length-12 vector into three chunks of four integers. Worker $r$ starts with coordinate $j$ equal to $3r+j-4$, for $r=0,1,2$ and $j=0,\ldots,11$. The expected sum is $3j-3$, namely `[-3, 0, 3, 6, 9, 12, 15, 18, 21, 24, 27, 30]`.

Our ring sends one chunk to the next worker per round. Two reduction rounds leave complete chunks 1, 2 and 0 on workers 0, 1 and 2 respectively. Two distribution rounds then give every worker the full sum. The source records every round and checks the result against a direct coordinate-wise sum. The rotated ownership is a convention of this small schedule, not NCCL's API layout.

Each worker sends four chunks, or sixteen values. Assuming a four-byte payload representation, that is 64 payload bytes sent per worker. Python integer object sizes are irrelevant to this declared communication model; the program simulates messages, not actual network buffers.

For $R$ workers and a divisible full payload of $S$ bytes, the same ring pattern has two phases of $R-1$ rounds, each carrying $S/R$ bytes:

$$
V_{\mathrm{sent}}=2\frac{R-1}{R}S.
$$

Our twelve-million-parameter ledger has a 48 MB gradient payload. With three workers, each sends 64 MB and also receives 64 MB. Do not double-count receive bytes when reporting sent traffic, or mistake this total for an end-to-end latency prediction. Latency per round, topology, concurrent flows and overlap all matter. Small buckets can expose round overhead; large buckets can postpone communication until much of backward is finished.

## Shard persistent state, then budget temporary gathering \{#sharding-the-model-states-zero-and-fsdp\}

The ZeRO work by Samyam Rajbhandari and coauthors organizes memory savings by distributing optimizer state, then gradients, then parameters. We apply that idea to our independently specified 18-byte layout and three workers. Master parameters and optimizer moments occupy twelve bytes per parameter in this ledger.

| Persistent state placement | Bytes per worker | Decimal MB |
| --- | ---: | ---: |
| All replicated | $18N$ | 216 |
| Master and optimizer state sharded | $(2+4+12/3)N$ | 120 |
| Gradients also sharded | $(2+(4+12)/3)N$ | 88 |
| All listed states sharded | $(18/3)N$ | 72 |

These are arithmetic persistent-state amounts, not GPU peaks or measured ZeRO performance. Full parameter groups may still be needed during computation. Gathering a group creates a temporary full copy; prefetching the next group can overlap communication while making more bytes coexist. Extremely fine groups reduce that live size but require more collective operations.

PyTorch FSDP2 describes parameter-group all-gathers around computation and gradient reduce-scatters after backward. Grouping and resharding choices affect when parameters are available and released. Its execution policy is more detailed than dividing a total by the device count. Inspect the actual chosen groups and their overlapping lifetimes.

Sharding also changes saving and recovery. A checkpoint consisting of one worker's shard is not the complete model. Preserve shard metadata, optimizer state, data position and random-state requirements for the intended restart. Validate restoration before treating distributed memory capacity as reliable training capacity. Failure after some workers update but before others do cannot be resolved by quietly continuing with inconsistent replicas.

## Split a tensor along a mathematically valid boundary \{#tensor-parallelism\}

Tensor parallelism divides the computation of an operation. For our original row vector and matrix,

$$
x=(2,-1,3),\qquad
W=\begin{pmatrix}1&-1\\2&1\\-1&2\end{pmatrix},\qquad
xW=(-3,3).
$$

Splitting output columns gives two independent scalar outputs that can be concatenated. Splitting the input dimension instead gives partial outputs $(0,-3)$ from the first two coordinates and $(-3,6)$ from the last. Their sum reconstructs $(-3,3)$.

The location of the next operation matters. Applying ReLU after reduction gives $(0,3)$. Applying it to each partial output before summation gives $(0,6)$, a different function. An algebraically valid linear partition does not authorize moving a nonlinear operation across a reduction.

The same reasoning guides a larger network: identify which intermediate must be replicated, sharded, concatenated or reduced before its consumer runs. Communication can occur inside each layer rather than once per optimizer step. Hardware placement and matrix sizes therefore affect whether the split helps. Our exact small matrix verifies an identity and a counterexample; it is not a speedup measurement or an implementation of a framework's tensor-parallel API.

## Schedule pipeline stages without changing the update \{#pipeline-parallelism\}

Pipeline parallelism assigns consecutive parts of a model to different workers. Microbatches let one stage work while another processes a preceding microbatch. The GPipe paper by Yanping Huang and coauthors describes synchronous microbatch accumulation; we derive a separate three-stage abstract schedule here rather than reproducing its diagrams or benchmarks.

Assume each stage's forward or backward operation takes one slot and communication is free. Process all forwards, then all backwards, and update only after every microbatch contributes. The first microbatch needs $P$ forward slots across $P$ stages; each additional microbatch extends the forward phase by one. The backward phase has the same length. For $m$ microbatches,

$$
T=2(m+P-1),\qquad U=\frac{2mP}{PT}=\frac{m}{m+P-1}.
$$

Here $U$ is occupied stage-slot fraction for this balanced fill-and-drain schedule, not measured GPU utilization. The fixture explicitly assigns every operation a stage and slot and verifies forward/backward dependency order.

| Stages | Microbatches | Total slots | Occupied stage-slot fraction |
| ---: | ---: | ---: | ---: |
| 3 | 1 | 6 | $1/3$ |
| 3 | 5 | 14 | $5/7$ |
| 3 | 9 | 22 | $9/11$ |

More microbatches amortize filling and draining, but they do not make an imbalanced slow stage disappear. Making each microbatch too small can hurt kernel efficiency; keeping many activations can consume memory. Alternative schedules interleave forward and backward work, changing live activations and communication. Their correctness still depends on which parameter version each operation reads. Do not infer their memory or timing from this particular fill-and-drain table.

## Recompute the same intermediates \{#gradient-checkpointing\}

Activation checkpointing retains selected boundaries and regenerates intermediates during backward. It is distinct from saving a training checkpoint for recovery. The tradeoff is extra computation for less retained activation state, provided replay reproduces the needed function and its state.

Our independent scalar chain has nine affine layers, starting from 2. Its forward values are `2, 3, 5, 7, 5, 11, 12, 11, 22, 25`. For the final loss $\tfrac12z^2$, full storage gives an input gradient of 200. The fixture first stores all nine layer inputs and computes every weight gradient.

It then retains only boundary inputs at layers 0, 3 and 6. During reverse traversal it replays each three-layer segment, uses the local inputs for its gradients and discards that segment. This deliberately simple replay performs nine extra forward operations, retains three persistent boundary inputs instead of nine, and uses a temporary buffer of four scalar values. Those are separate algorithmic storage counts, not a claim of threefold peak-memory reduction. The verification program keeps the reference arrays for comparison; it does not measure allocated memory. All nine weight gradients and the input gradient match the full-storage calculation exactly.

PyTorch's checkpoint documentation highlights replay state, including random-number handling and differences between implementations. Random masks, mutable counters or side effects that change on replay can invalidate the intended derivative. Our chain has no randomness or side effects, and does not invoke a checkpoint API; it verifies only the stated deterministic recomputation.

## Choose a layout around the bottleneck \{#choosing-a-combination\}

Data parallelism replicates a computation over examples, tensor parallelism splits operations, and pipeline parallelism splits sequential stages. State sharding and activation recomputation modify storage. None is a universal first step: identify what prevents the reference run from meeting its objective.

A twelve-worker layout could have two data replicas, three pipeline stages and two tensor partitions per stage. If each data replica accumulates five microbatches of eight examples, the effective update batch is $2\cdot5\cdot8=80$, not twelve times eight. Tensor and pipeline workers collaborate on the same examples. Gradient collectives must connect the corresponding parameter partitions, not arbitrary groups of twelve ranks.

Record that layout with the run. Before scaling further, verify loss weighting, gradients, optimizer timing and restoration on a small case. Then profile a representative step and the validation trajectory. Include checkpoint time, failed work and the input pipeline in elapsed cost. A configuration that reduces persistent state may expose an expensive all-gather; one that hides communication may exceed peak memory through prefetching.

## What changed \{#what-changed\}

The plan now identifies eighteen bytes of specified persistent state per parameter, separates them from temporary allocations, and preserves example weighting across unequal workers. Reduction, tensor partition and pipeline scheduling each have an executable invariant. Recomputation preserves gradients in a deterministic case while making its extra work explicit.

## Limitations \{#limitations\}

All timings are abstract slots and all communication sizes are assumed payload bytes. There is no hardware benchmark, collective library run, network fault, full optimizer implementation or real model. Integer and rational checks avoid floating-point reduction differences; they do not prove bitwise agreement on accelerators. Balanced stages, correct clocks and synchronous updates are assumptions to test in a real system.

## What to retain \{#what-you-should-remember\}

Specify the objective and update boundary before distributing work. Count persistent and temporary allocations separately. Weight gradients by eligible examples. Check the communication layout and nonlinear-operation boundary. Treat pipeline utilization formulae as schedule-dependent. Verify recomputation and recovery with the state they actually require.
