The store and the website both publish sales data. A replay sends the same store event twice. One feed reports a refund as a positive amount and a separate event type. Storing all the files is useful, but adding all their amounts would give the wrong report.

## Give each layer a job

A landing or **staging** layer preserves the received records and enough information to identify their source and batch. It lets us rerun a transformation against the same input. An **integration** layer resolves differences between sources. It assigns common units and business keys, maps statuses and handles repeated delivery. A **serving** layer exposes data in a shape suited to a report or another consumer. These are responsibilities. They can be implemented in separate databases, schemas or collections of tables. ([Ross, 2004](#references))

Suppose the store sends a 700-cent sale twice with the same source event ID. The website sends a 600-cent sale and a 350-cent refund. The integration contract says a source event ID identifies one event within its source. It keeps one instance of the repeated sale and stores refunds with a negative sign. The gross sales amount is 1300 cents. After the refund it is 950 cents. Counting both deliveries while applying the refund sign would give 1650. Keeping the raw deliveries lets us inspect why the totals differ.

## Decide where those layers live

A **data warehouse** (DWH) organizes integrated data for analytical access, commonly exposing managed tables and marts. A **data lake** commonly uses shared file or object storage to retain inputs in several formats. It can preserve exports, logs and other data that a reporting table does not carry. A directory of files can still leave readers to agree on which files form the published table. Separate lake and warehouse copies also introduce a handoff whose freshness and correctness must be managed. ([Armbrust et al., 2021, §§1–2](#references))

A **lakehouse** aims to support warehouse-style tables and other analytical workloads over shared, directly accessible storage formats. A format such as Iceberg tracks schemas and table snapshots above data files. It can make a change to one table visible through a metadata commit. That mechanism does not choose the event key, establish the sign of a refund or prove that two different engines interpret a report identically. The integration and serving contracts remain necessary. ([Armbrust et al., 2021, §3](#references); [Apache Iceberg, Specification](#references))

For this sales example the same staging, integration and serving responsibilities apply to each design. Their implementations differ in who manages files and tables, which engines can read them, and where an extra copy or refresh is needed.
