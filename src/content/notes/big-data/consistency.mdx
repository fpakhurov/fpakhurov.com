A payment write for order 106 has returned success. The next read goes to a different replica and says that the order is unpaid. We need a contract that says whether that history is allowed, before deciding what the replica should do.

## Compare histories at the client

An operation has a call and a response. **Linearizability** requires a history that can be read as a legal sequential execution, with every completed operation taking effect at a point between call and response. In particular, if one operation has finished before another starts, the sequential order must respect that precedence. If writing `paid` finishes before a read starts and no later write intervenes, that read must return `paid`. If the operations overlap, a read of the old value can be consistent with a read that took effect first. ([Herlihy and Wing, §2](#references))

**Read your writes** is narrower. A session sees its own successful writes in subsequent reads, even if another session can still see older data. A service can carry a session's minimum observed version and send reads to a replica that has applied at least that version. It must wait or change the destination when the local replica is behind. **Eventual convergence** asks replicas to agree if writes stop and updates can be delivered and reconciled. By itself it gives no bound on how long a read can stay stale. The original Dynamo design exposes versioned values and can reconcile conflicting updates. ([DeCandia et al., §§4.4–4.6](#references))

## Derive what quorum overlap gives

For a key with $N$ fixed replicas, let $W$ be the number of acknowledgements required by a write and $R$ the number of responses required by a read. The write and read sets must share a replica when $R+W>N$. If the sets were disjoint they would contain $R+W$ different replicas, which cannot fit among $N$.

With $N=3$, $W=2$ and $R=2$, suppose A and B have applied version 1 after a write, and C still has version 0. A read from B and C receives versions 1 and 0. Selecting the newest version gives 1 in this setup. We assumed a fixed replica set, an order of versions from one writer, and no concurrent or partially completed write. With $W=1$ and $R=2$, a write on A can be missed entirely by reading B and C.

Overlap gives a shared witness, while a full protocol must define write ordering, version selection, visibility and failure handling. Replacing missing replicas with different nodes can invalidate the fixed-set argument. Dynamo's original **sloppy quorum** can use alternate reachable nodes with later hinted handoff, so the size inequality alone is insufficient for linearizability. A leader-based protocol also needs to confirm that a node still has authority before it answers a strong read. Raft describes checks against a majority for this purpose. ([DeCandia et al., §§4.5–4.6](#references), [Ongaro and Ousterhout, §8](#references))

## Read during a network partition

Split A from B and C. Messages between the two sides can be lost indefinitely. A reader can still reach A. Consider one history where the majority acknowledged the payment before that read, and another history where there was no payment. A has the same local evidence in both histories. To behave like a single linearizable copy it must answer `paid` in the first and `unpaid` in the second.

A policy can require A to establish contact with enough peers and withhold a successful read while isolated. B and C may elect a leader and continue under the protocol when they can communicate. Another policy can let A serve its local value. In the first history that answer is stale. These are different contracts during the same partition.

In the CAP result, **consistency** is atomic read/write behaviour, **availability** requires operations on non-failing nodes to complete with valid responses, and the model allows a network partition. No algorithm can always give both guarantees in that setting. A refusal or a timeout is useful feedback, but it does not give the successful read required by that availability definition. The result addresses network separation. It does not classify every product or replace the need to specify a particular operation's semantics. ([Gilbert and Lynch, §§2–3](#references))
