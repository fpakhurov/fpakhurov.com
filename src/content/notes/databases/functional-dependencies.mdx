A report can join order lines and catalog items on demand. Suppose we store that result as the authoritative table. The code of item 7 now appears in three rows. Correcting only one copy from `TEA50` to `TEA-50` gives the same product two current codes. The line key still distinguishes all rows. It cannot protect the separate fact about the product.

## An agreement rule between rows

Start with the [order and catalog example](/notes/databases/data-modeling#put-the-rules-into-a-schema) and add the current order state. Write $R(o,n,p,q,c,k,s)$ for the flattened relation. The attributes are order ID, line number, product ID, quantity, agreed unit price, current catalog code and order state. All are present in this model.

| Order $o$ | Line $n$ | Item $p$ | Quantity $q$ | Price $c$ | Code $k$ | State $s$ |
| --- | --- | --- | --- | --- | --- | --- |
| 101 | 1 | 7 | 2 | 350 | TEA50 | open |
| 101 | 2 | 9 | 1 | 600 | COFFEE | open |
| 106 | 1 | 7 | 1 | 350 | TEA50 | paid |
| 106 | 2 | 7 | 1 | 300 | TEA50 | paid |

A **functional dependency** $X\to Y$ says that any two tuples that agree on all attributes of $X$ agree on all attributes of $Y$. It is a rule for every valid state, with $X$ and $Y$ sets of attributes. It is also a test we can apply to one state. We write $on$ for $\{o,n\}$ and use the same shorthand for other sets. ([Armstrong, 1974, §§4, 7 and 10](#references), [Silberschatz et al., ch. 7](#references))

The shop gives each line a unique number within its order, so $on\to pqc$. Every order has one current state, so $o\to s$. The catalog gives each item one current code, so $p\to k$. Each current code names only one item, so $k\to p$. These rules hold across future insertions and corrections if the data remains valid. The prices 350 and 300 for item 7 in order 106 already refute $p\to c$. The two states happen to identify two different orders in this instance. An additional paid order would break $s\to o$ without breaking a shop rule.

Here “current” matters. A catalog code may change from one valid state to the next. A table that keeps several versions at once would need enough attributes to identify the intended version before we could claim that it determines the historical code.

## Why a key can imply more than it names

**Reflexivity** gives $X\to Y$ whenever $Y\subseteq X$. **Augmentation** adds a common set $Z$ to both sides of a dependency, giving $XZ\to YZ$ from $X\to Y$. **Transitivity** gives $X\to Z$ from $X\to Y$ and $Y\to Z$. Each rule follows from the agreement test. If two tuples agree on $XZ$, for example, they agree on $X$ and hence on $Y$, while their agreement on $Z$ is already given. These rules are sound and complete for functional dependencies. ([Armstrong, 1974, §§4, 7 and 10](#references), [Silberschatz et al., ch. 7](#references))

The **attribute closure** $X^+$ is the set of attributes determined by $X$ under the given rules. Begin with $X$. Whenever the attributes collected so far contain a determinant, add its dependent attributes. Stop when another pass adds nothing. This procedure computes $X^+$ and lets us test a proposed superkey. ([Silberschatz et al., ch. 7](#references), [Berkeley CS 186, DB Design](#references))

Starting with $on$, add $p,q,c$ using $on\to pqc$, add $s$ using $o\to s$, and add $k$ using $p\to k$. All seven attributes are present, so $on$ is a superkey. Starting with $o$ adds only $s$. Starting with $n$ adds nothing. Thus $on$ is a candidate key. Neither $o$ nor $n$ appears on a right-hand side of the listed dependencies. Any candidate key must include both, so this one is unique. Starting with $p$ gives $pk$ and leaves line-specific facts outside the closure.

## One catalog fact repeated three times

**Update anomaly.** Renaming item 7 consistently requires changing three copies of its code. If we update just the first line, a query over the resulting non-null codes can detect the broken rule.

```sql
WITH flat_lines(product_id, catalog_code) AS (
    VALUES (7, 'TEA-50'), (9, 'COFFEE'),
           (7, 'TEA50'), (7, 'TEA50')
)
SELECT product_id, COUNT(DISTINCT catalog_code) AS code_count
FROM flat_lines
GROUP BY product_id
HAVING COUNT(DISTINCT catalog_code) > 1
ORDER BY product_id;
```

The result is `(7, 2)`. A primary key on order and line number still accepts these four distinct lines. The bad state violates $p\to k$.

**Insertion anomaly.** The catalog already contains the 100 g pack with code `TEA-100`. It has no sales in the example. A table with one row per order line cannot hold the fact about the pack without inventing a line. The same problem occurs for a draft order with no lines.

**Deletion anomaly.** Order 101 line 2 is the only row carrying item 9's code. Deleting that line would delete the only copy of a still-valid catalog fact.

The duplicated fact is the current code. The two prices of item 7 record distinct agreements and must both be retained. Deciding what can be stored once begins with the dependencies, rather than with repeated values found in a sample. ([Silberschatz et al., ch. 7](#references), [Berkeley CS 186, DB Design](#references))
