The [flattened order table](/notes/databases/functional-dependencies#an-agreement-rule-between-rows) repeats the current state of order 106 and the current code of item 7. Splitting the table gives each fact a home. An arbitrary split can also create a receipt that never existed, or hide a rule that the original table made easy to check.

## Detect which fact repeats

Keep the previous notation $R(o,n,p,q,c,k,s)$. The candidate key is $on$. Let $F$ consist of $on\to pqc$, $o\to s$, $p\to k$ and $k\to p$. Write $F^+$ for all dependencies implied by $F$. The normal forms below are properties of a schema under these rules, rather than of the four example rows.

**First normal form** uses simple values at the chosen grain. A value is treated as a unit in the relation's operations. In this design the line number, product and quantity are ordinary fields. Packing a variable collection of line records into an order field would change the model and prevent the following line attributes from being ordinary columns of that relation. ([Codd, 1970, §1.4](#references))

**Second normal form** additionally requires that no non-prime attribute depend on a proper subset of a candidate key. A **prime attribute** belongs to at least one candidate key. Here $s$ is non-prime and $o\to s$ uses only the order part of $on$. Separate the order state into $O(o,s)$. In the remaining schema $R'(o,n,p,q,c,k)$, neither $o$ nor $n$ determines a non-prime attribute by itself. It passes the second-normal-form test. ([Bernstein, 1976, §2](#references))

The remaining schema still repeats the product code. For **third normal form** (3NF), every nontrivial implied dependency $X\to A$ with one attribute $A$ on the right must have a superkey $X$ or a prime $A$. A dependency is nontrivial when $A\notin X$. **Boyce–Codd normal form** (BCNF) requires a superkey $X$ in every such dependency, including those with a prime right-hand attribute. In $R'$, $p\to k$ has a non-superkey determinant and a non-prime right-hand side, so it fails both tests. ([Silberschatz et al., ch. 7](#references))

Move the code to $P(p,k)$ and keep $L(o,n,p,q,c)$ for the line. Relative to the stated rules, $O$, $P$ and $L$ are all in BCNF. Their nontrivial determinants contain a key. In $O$ the key is $o$, in $P$ either $p$ or $k$, and in $L$ the key is $on$.

## Reconstruct a valid relation

A decomposition is **lossless** under $F$ if naturally joining the projections of every instance satisfying $F$ gives that instance back. For a binary decomposition into schemas $U$ and $V$ with union $R$, under functional dependencies alone this is equivalent to $U\cap V$ determining all of $U$ or all of $V$ in $F^+$. ([Silberschatz et al., ch. 7](#references), [Berkeley CS 186, DB Design](#references))

To see why the condition suffices, take a tuple in the join. It combines a $U$-projection of one original tuple and a $V$-projection of another. The originals agree on $U\cap V$. If that intersection determines $V$, they agree on all of $V$. The joined tuple is therefore the first original tuple. Every original tuple joins its own projections, so there are neither missing nor extra tuples.

Our first split shares $o$, which determines $O$. Our second shares $p$, which determines $P$. Each split is lossless, so the two joins in reverse reconstruct the flattened lines. SQL needs `DISTINCT` in the projections to give each projected tuple one copy.

```sql
WITH flat(order_id, line_no, product_id, quantity, cents, code, state) AS (
    VALUES (101, 1, 7, 2, 350, 'TEA50', 'open'),
           (101, 2, 9, 1, 600, 'COFFEE', 'open'),
           (106, 1, 7, 1, 350, 'TEA50', 'paid'),
           (106, 2, 7, 1, 300, 'TEA50', 'paid')
),
lines AS (
    SELECT DISTINCT order_id, line_no, product_id, quantity, cents FROM flat
),
orders AS (
    SELECT DISTINCT order_id, state FROM flat
),
products AS (
    SELECT DISTINCT product_id, code FROM flat
)
SELECT order_id, line_no, product_id, quantity, cents, code, state
FROM lines
JOIN orders USING (order_id)
JOIN products USING (product_id)
ORDER BY order_id, line_no;
```

The query gives the original four rows. For order 106 it restores line 1 with code `TEA50`, price 350 and state `paid`, and line 2 with the same code and state at price 300. A real decomposed database also stores the draft order 105 and the unsold 100 g pack in the parent tables. The demonstration projects from lines, so those independent facts are absent from its input.

A different split of just the two order-106 lines into $(n,p)$ and $(p,c)$ shares $p$. The first projection contains $(1,7)$ and $(2,7)$. The second contains $(7,350)$ and $(7,300)$. Both line numbers now match both prices, giving four tuples. In particular $(1,7,300)$ was never sold. The split discarded the association of line number with price. The join exposes the loss by inventing combinations.

## Keep the rules enforceable on the parts

For each resulting schema $R_i$, take $F_i$ to be the dependencies from $F^+$ whose attributes all belong to $R_i$. The decomposition **preserves dependencies** if the union of those local dependency sets implies all of $F$. Equivalently, the closure of that union is $F^+$. In the shop split, each of the four stated dependencies is already in one component, so the test passes. This means no join is needed to test these functional rules. References between tables still need foreign keys. ([Silberschatz et al., ch. 7](#references), [Berkeley CS 186, DB Design](#references))

Losslessness and dependency preservation can differ. Suppose $T(o,v,b)$ records which counter $b$ serves order $o$ for service $v$. An order uses at most one counter per service, so $ov\to b$. Each counter handles one service, so $b\to v$. These are the only generating dependencies. Starting with $ov$ or $ob$ determines all three attributes. Starting with $b$ determines $bv$, and $o$ and $v$ alone determine only themselves. The candidate keys are $ov$ and $ob$. Every attribute is prime, so 3NF holds. Since $b$ is no superkey, $b\to v$ violates BCNF.

The split into $(b,v)$ and $(o,b)$ is in BCNF and is lossless because the common $b$ determines the first component. The local dependencies cannot imply $ov\to b$. For example, store $(7,\text{pickup})$ and $(8,\text{pickup})$ in the first component and $(106,7)$ and $(106,8)$ in the second. Each counter has one service and neither component violates its local dependencies. Their join assigns two counters to the same order and service. Losslessness applies to projections of a valid original instance. It gives no guarantee that every independently edited pair of components represents a valid original instance.

A 3NF synthesis can preserve dependencies and give a lossless join. One standard construction starts from an equivalent minimal set of dependencies, builds relations from their determinants and dependents, and adds a relation for an original candidate key if none of the components already contains one. The proof and precise construction are in the references. Here retaining $T$ in 3NF lets the original rule $ov\to b$ be checked in one relation. The design then accepts some repetition of service across orders that use the same counter. ([Bernstein, 1976, §§6–7](#references), [Silberschatz et al., ch. 7](#references))
