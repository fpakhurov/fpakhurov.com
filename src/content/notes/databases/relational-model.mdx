Order 106 has two lines for the same 50 g tea pack. One records a price of 350 cents and the other a price of 300. To print the receipt, the shop needs both line facts and the one catalog fact that supplies the pack's code. A relational query combines these facts while keeping the two lines distinct.

## A schema describes allowed tuples

A **relation schema** names a collection of attributes and assigns a domain to each. A **domain** describes possible values, for example integer quantities or text catalog codes. A **tuple** assigns one value to each attribute. A **relation instance** is a set of tuples over the schema. The schema can stay fixed while its instance changes. There is no inherent order of tuples, and a set contains at most one copy of a tuple. ([Codd, 1970, §1.3](#references), [Pavlo, 2025, §4](#references))

Use the schema from [the order example](/notes/databases/data-modeling#put-the-rules-into-a-schema). Write $L$ for the order-line relation and $P$ for the catalog-item relation. In the algebra below, $o,n,p,q,c$ name order ID, line number, product ID, quantity and agreed unit price in cents. The catalog uses $p$ as well, and $k$ names the catalog code. These are attribute names, so $p$ refers to the product ID even when it appears at a different position in another relation.

| Relation | Attributes used here |
| --- | --- |
| $L$ | $(o,n,p,q,c)$ |
| $P$ | $(p,k)$ |

The two lines of order 106 are $(106,1,7,1,350)$ and $(106,2,7,1,300)$. The catalog maps item 7 to `TEA50` in the initial state. A tuple holds one line fact, even when its product is the same as a different line's product.

## Keys and references constrain instances

A **superkey** is a set of attributes whose values distinguish tuples in every valid instance. A **candidate key** is a superkey that loses this guarantee when we remove any of its attributes. Here $(o,n)$ is a candidate key for $L$. Order 106 has two lines, so $o$ alone repeats. Orders 101 and 106 both have a first line, so $n$ alone repeats. Including the quantity as well would give a superkey that is no longer minimal. In the catalog, $p$ is the chosen primary key, and $k$ is another candidate key under the rule that each current code is distinct and present. ([Pavlo, 2025, §5](#references), [PostgreSQL 18, §§5.5.3–5.5.4](#references))

A **foreign key** constrains references between instances. Every product ID appearing in $L$ must appear as a product ID in $P$. In set notation this is $\pi_p(L)\subseteq\pi_p(P)$, where $\pi$ keeps the listed attributes. It lets several lines reference the same catalog item and lets the catalog contain items without sales. In the SQL setup `product_id` is `NOT NULL`, so the foreign key requires a catalog match for every line. A nullable SQL foreign key can exempt a row from the usual match requirement. ([PostgreSQL 18, §5.5.5](#references))

## Build a receipt from smaller operations

**Selection** $\sigma$ retains tuples satisfying a predicate. $\sigma_{o=106}(L)$ retains the two lines of order 106. **Projection** $\pi$ keeps only named attributes and removes repeated tuples because its result is a set. **Join** $\bowtie$ combines matching tuples. In this example the natural join matches on the only common attribute $p$. We can express the receipt as a composition. ([Codd, 1970, §§2.1.2–2.1.3](#references), [Pavlo, 2025, §6](#references))

$$
\pi_{n,k,c}\bigl(\sigma_{o=106}(L)\bowtie P\bigr).
$$

Each selected line has exactly one catalog match because the reference is required and $p$ is a catalog key. Projecting line number, code and unit price gives the two receipt tuples. The two line numbers keep the tuples distinct.

To run the SQL below, create the order and catalog tables from the [previous example](/notes/databases/data-modeling#put-the-rules-into-a-schema) before the optional code correction. The query names the shared join column explicitly.

```sql
SELECT l.line_no, c.catalog_code, l.unit_price_cents
FROM order_lines AS l
JOIN catalog_items AS c USING (product_id)
WHERE l.order_id = 106
ORDER BY l.line_no;
```

| line_no | catalog_code | unit_price_cents |
| --- | --- | --- |
| 1 | TEA50 | 350 |
| 2 | TEA50 | 300 |

A Cartesian product would pair both selected lines with all three catalog items and give six pairs. The equality on $p$ retains two. In the algebra, selection, projection and join all return relations, so each result can become an input to another operation.

## Where SQL differs from the model

The projection $\pi_p(\sigma_{o=106}(L))$ contains the single tuple $(7)$. A plain `SELECT product_id` over the two lines returns two rows with value 7. SQL preserves those occurrences by default. Add `DISTINCT` to request set-style projection.

```sql
SELECT DISTINCT product_id
FROM order_lines
WHERE order_id = 106;
```

These examples use relations with ordinary values, so a test such as $o=106$ is true or false. SQL adds the `NULL` marker and an unknown result for many comparisons. It also supports explicit result ordering. The algebra here reasons about tuple membership, while SQL examples must state their duplicate and missing-value behaviour. See [types and NULL](/notes/sql/types-and-null) and [duplicates and ordering](/notes/sql/duplicates-and-order). ([PostgreSQL 18, SELECT](#references))
