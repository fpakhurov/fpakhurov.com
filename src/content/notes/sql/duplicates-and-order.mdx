The shop needs a list of products sold. The [six order lines](/notes/sql/tables-and-queries#what-does-one-row-mean) have distinct position identifiers. The product name answers a different question, and tea occurs in three of those positions. The answer depends on whether each output row stands for a sale line or for a product.

## Why a query repeats a value

The first query reads one product name for each order line. The second asks for one row per distinct name.

```sql
SELECT product
FROM order_lines
ORDER BY product;

SELECT DISTINCT product
FROM order_lines
ORDER BY product;
```

| Product | Occurrences with `SELECT` | Occurrences with `SELECT DISTINCT` |
| --- | --- | --- |
| cocoa | 1 | 1 |
| coffee | 2 | 1 |
| tea | 3 | 1 |

The first result has six rows because projecting the `product` column retains one output row per input line. A **multiset**, also called a bag, records how many times each element appears. The multiplicity of `tea` is three because lines 101/1, 102/1 and 103/2 all contribute it. A mathematical set records membership alone. Classical relational algebra works with sets, so projection there produces one tuple for each distinct combination of retained attributes. A plain SQL `SELECT` uses `ALL` by default and preserves the multiplicities. [Pavlo, 2025, §§4, 6](#references) [PostgreSQL 18, SELECT](#references)

`DISTINCT` compares complete output rows. In `SELECT DISTINCT product, quantity`, the two rows `('tea', 1)` collapse into one, and `('tea', 2)` still appears separately. There are five output pairs. Adding `order_id` and `line_no` to the output distinguishes all six positions in this example, so `DISTINCT` over that output removes nothing. Choose the fields that describe one unit of the answer before asking for duplicates to be removed.

## Missing values in a distinct result

Consider two provisional prices missing from a feed, plus a known price of 350 cents. The `VALUES` clause supplies the three input rows without changing the shop's data.

```sql
SELECT DISTINCT price_cents
FROM (VALUES (NULL::integer), (350), (NULL)) AS feed(price_cents)
ORDER BY price_cents NULLS LAST;
```

The output is `350`, then one `NULL`. A comparison such as `price_cents = NULL` still evaluates to unknown. Duplicate elimination uses a different comparison rule. At the same output position, two missing values count as indistinguishable for that operation. The one `NULL` row says that the input contains at least one missing value. It gives no count of the missing inputs. [PostgreSQL 18, Select Lists](#references) [SQLite, §2.6](#references)

## A limit needs an order

The shop also wants the highest-value line. We can compute its value in cents and request a single result.

```sql
SELECT order_id, line_no,
       quantity * unit_price_cents AS line_total_cents
FROM order_lines
ORDER BY line_total_cents DESC
LIMIT 1;
```

Lines 103/1 and 104/1 both cost 1200 cents. Each satisfies the only sort key equally well, so the query can return either one. A result that repeats across several runs still gives no contractual tie-breaker. With no `ORDER BY` at all, even membership in the group priced at 1200 cents is unspecified. Likewise, duplicate elimination by itself gives no order guarantee. [PostgreSQL 18, §§7.5–7.6](#references)

To pick one line, specify what to do on a tie. First compare amounts from high to low. For equal amounts, take the lower order number. If the orders also match, take the lower position number. The pair `(order_id, line_no)` distinguishes every line in the sample.

```sql
SELECT order_id, line_no,
       quantity * unit_price_cents AS line_total_cents
FROM order_lines
ORDER BY line_total_cents DESC, order_id ASC, line_no ASC
LIMIT 1;
```

Line 103/1 comes first since 103 is less than 104. Sort directions apply to the key they follow. Only the amount goes in descending order here. [PostgreSQL 18, §7.5](#references)

If the request is for every line tied for the maximum, keep the amount as the sole sort key and use `FETCH FIRST 1 ROW WITH TIES` in place of `LIMIT 1`. That returns both 1200-cent lines. Ties are judged using the entire sort key, so including the position identifier inside that query would change which rows qualify. [PostgreSQL 18, SELECT](#references)

For a nullable amount, specify where missing values belong. In PostgreSQL, `DESC` puts them first by default, so one missing amount could fill the entire one-row result. With `DESC NULLS LAST`, known amounts come first. If the query may return only known amounts, exclude missing ones in `WHERE` as well. SQLite puts missing values last by default under `DESC`, which is a reason to write the null placement explicitly in queries used with both systems. [PostgreSQL 18, §7.5](#references) [SQLite, §4](#references)

## A stable order over changing data

`OFFSET` skips rows of the ordered result. Over the original six rows, the order with tie-breakers starts 103/1, 104/1, 101/1. `LIMIT 2` gives the first two, and `LIMIT 2 OFFSET 2` starts at 101/1. Suppose an additional line 107/1 worth 1500 cents becomes visible between those requests. The second query now skips 107/1 and 103/1. It starts at 104/1, repeating a line from the first page even though both queries use the same sort keys. [PostgreSQL 18, §§7.6, 13.2.1](#references)

A total order makes positions unambiguous for a given input. Keeping the same input visible across several queries is a separate requirement. The [opening Databases note](/notes/databases/why-databases) introduces the visibility of committed changes between queries.
