The report already knows that tea accounts for four units. The order table stores the code `tea`, while the catalogue says it belongs to `drinks`. The code connects the two facts. The report needs one catalogue category for each order line.

## Match rows by a shared field

Use the six [order lines](/notes/sql/tables-and-queries#a-reproducible-table) and add this catalogue in the same session. Each product has a single catalogue entry.

```sql
CREATE TEMP TABLE catalogue (
    product text PRIMARY KEY,
    category text NOT NULL
);

INSERT INTO catalogue VALUES
    ('tea', 'drinks'),
    ('coffee', 'drinks'),
    ('cocoa', 'pantry'),
    ('mint', 'herbs');
```

The **inner join** emits one result row for each pair of input rows for which the condition in `ON` is true. The query names each table with an alias, `l` or `c`. The expression `l.product = c.product` compares the two fields, and `SELECT` chooses what to show for every matching pair. ([PostgreSQL 18, §7.2.1](#references); [SQLite, §2.1](#references))

```sql
SELECT l.order_id, l.line_no, l.product, c.category
FROM order_lines AS l
JOIN catalogue AS c ON c.product = l.product
ORDER BY l.order_id, l.line_no;
```

| order_id | line_no | product | category |
| ---: | ---: | --- | --- |
| 101 | 1 | tea | drinks |
| 101 | 2 | coffee | drinks |
| 102 | 1 | tea | drinks |
| 103 | 1 | coffee | drinks |
| 103 | 2 | tea | drinks |
| 104 | 1 | cocoa | pantry |

A **cross join** pairs each row with every row on the other side. It would yield 24 pairs here, from 6 order lines and 4 catalogue entries. We can reason about the inner join by testing the equality on each of those pairs and retaining the six that pass. This explains the result. It does not imply that the DBMS has to build all 24 pairs to execute the query. ([PostgreSQL 18, §7.2.1](#references); [DuckDB 1.4, Cross product and conditional joins](#references))

The catalogue's primary key enforces at most one match for each order line. All six order lines happen to have matching codes. If the catalogue omitted cocoa, the corresponding order line would disappear from the result. The unique key limits multiplicity but does not require a match for each line.

## How many pairs can one key create?

Now the report writer uses a list of supplier offers in place of the catalogue. Each supplier may make one offer per product. Two suppliers offer tea. We compare by product again.

```sql
CREATE TEMP TABLE supplier_offers (
    product text,
    supplier text,
    PRIMARY KEY (product, supplier)
);

INSERT INTO supplier_offers VALUES
    ('tea', 'A'),
    ('tea', 'B'),
    ('coffee', 'A'),
    ('cocoa', 'C');

SELECT l.product, COUNT(*) AS pairs,
       SUM(l.quantity) AS summed_units
FROM order_lines AS l
JOIN supplier_offers AS s ON s.product = l.product
GROUP BY l.product
ORDER BY l.product;
```

| product | pairs | summed_units |
| --- | ---: | ---: |
| cocoa | 1 | 3 |
| coffee | 2 | 3 |
| tea | 6 | 8 |

Each of the three tea positions pairs with both offers. The result has six tea rows and counts the same four sold units twice. The grain is now one row per order line and offer pair. Eight describes the sum over those pairs. Actual tea sales remain four units.

<TeaPairs />

For an equality join on a non-null key value $k$, let $n_k$ and $m_k$ be the numbers of input rows with key $k$ on the left and right. Each of the $n_k$ rows matches all $m_k$ right rows with that value. That key contributes $n_k m_k$ result rows. The tea key contributes $3 \cdot 2 = 6$. Coffee and cocoa contribute 2 and 1, so the joined result has nine rows. In an ordinary equality condition, a comparison to `NULL` is unknown. Null keys do not match each other. ([PostgreSQL 18, §7.2.1](#references); [SQLite, §2.1](#references))

## Match at the intended grain

The offer table's primary key is the pair `(product, supplier)`. The query compares only one part of the key, so uniqueness of that pair does not prevent two offers from matching a line. If another input actually identifies a chosen supplier, match both fields. When the input identifies only a product and the report needs one category per product, the original catalogue has the right grain.

Use the same reasoning with repeated display values. Two tea positions each record one unit. `SUM(DISTINCT l.quantity)` would count the distinct quantities 1 and 2 once each, giving 3. The report needs both one-unit positions. Changing the aggregate would replace the meaning of the calculation while leaving the join's row grain unchanged.

Before applying an aggregate, decide which joined row each pair represents. If the query needs one right-hand match per left-hand row, the compared fields must identify a right row uniquely. A missing match is a separate case. When it matters that every order line has a catalogue entry, that relationship must be checked or enforced independently.
