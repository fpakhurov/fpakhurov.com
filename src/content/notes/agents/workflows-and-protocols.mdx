The notes of this section added memory, planning and self-correction to the agent loop. Each of them can be built in two ways. An open-ended agent decides at run time when to retrieve, when to plan and when to check; a fixed **workflow** does the same things at points chosen by the programmer. The [previous note](/notes/agents/reflection-and-self-correction) ended with such a fixed arrangement, a generator and a verifier in a loop. This note collects the recurring arrangements, says when a fixed workflow is the better design, describes in general terms what agent frameworks provide, and then turns to the plumbing underneath all of them: how a model reaches its tools. The [tool-use note](/notes/agents/tool-use-and-function-calling) described a single function call; the Model Context Protocol standardizes how an application discovers and calls tools that live in other programs, and it changed substantially in 2026.

**Notation.** A step succeeds with probability $s$; a chain has $k$ steps. A router sends a request to the right handler with probability $\rho$. Handlers succeed with probability $h$ on requests meant for them and $h'$ on others. A vote of $m$ independent samples is taken over answers that are each correct with probability $p$.

## Baseline: one agent with every tool

The most general design gives one model every tool and every instruction and lets it loop until it stops. It handles anything in principle. In practice it pays for its generality in four ways, all met in earlier notes: every step re-reads a context that includes every tool schema; errors compound over steps that nothing checks; behaviour varies from run to run, so failures are hard to reproduce; and the cost of a task is unbounded without budgets. The [NLP course](/notes/nlp/tools-and-agents#when-an-agent-is-unnecessary) gave the corresponding rule of thumb: start with a pipeline, and move a decision into the model only when fixed logic is measurably the bottleneck. This note makes the rule more precise.

<aside class="callout"><strong>Key idea.</strong> Most systems built on language models are a small number of model calls arranged by ordinary code: chained with checks between them, routed by a classifier, run in parallel and aggregated, delegated by an orchestrator, or looped with an evaluator. Use the simplest arrangement that measurably works, and leave the choice of steps to the model only when the steps cannot be known in advance. Connect models to tools through a protocol, so that tools are written once and every application can use them.</aside>

## The building block and five workflows

The taxonomy of [Anthropic (2024)](#references) starts from one building block, the **augmented LLM**: a model with retrieval, tools and memory, which can write its own queries, choose its tools and decide what to keep. Workflows arrange several such calls along paths written in code; an **agent** lets the model direct its own process.

<WorkflowPatterns />

**Prompt chaining.** The task is split into a fixed sequence of calls, each consuming the previous output: draft an outline, check it against the requirements, write the document from the outline. Between steps sit **gates**, programmatic checks that stop or retry a bad intermediate result. Without gates a chain of $k$ steps succeeds with probability $s^k$; with a gate that catches a fraction $g$ of failures and allows one retry, a step succeeds with probability $s + (1 - s) g s$. For $s = 0.9$, $k = 4$ and $g = 0.8$, that is $0.9^4 = 0.656$ without gates against $0.972^4 = 0.893$ with them. Chaining trades latency for accuracy: each call does an easier job.

**Routing.** A classifier, often a small model, sends each input to a specialized handler: refunds to one prompt and set of tools, technical questions to another, everything else to a person. Routing pays when the classes need different handling and the classifier is reliable. Overall success is $\rho h + (1 - \rho) h'$. With specialists at $h = 0.9$ on their own requests and $h' = 0.3$ on misrouted ones, routing beats a single generalist prompt that succeeds with probability 0.8 only if $0.9\rho + 0.3(1 - \rho) > 0.8$, that is $\rho > 5/6 \approx 0.83$: the router's accuracy is the first thing to measure.

**Parallelization.** Independent calls run at the same time. In **sectioning**, the task is split into independent parts (review a contract's clauses separately, or check a response for safety while another call answers it), and latency is that of the slowest part instead of the sum. In **voting**, the same task runs several times and the answers are aggregated, the self-consistency of [Chain of thought and reasoning](/notes/agents/chain-of-thought#self-consistency-vote-over-reasoning-paths): with three independent votes each correct with probability $p = 0.7$, the majority is correct with probability $p^3 + 3p^2(1 - p) = 0.784$. Votes from one model are correlated, so the real gain is smaller.

**Orchestrator–workers.** A central model breaks the task into subtasks that could not be listed in advance, hands each to a worker call, and combines the results: a code change that touches an unknown number of files, a search over sources that depend on the question. It resembles parallelization, but the subtasks are decided at run time. It is the bridge to [Multi-agent systems](/notes/agents/multi-agent-systems).

**Evaluator–optimizer.** One call generates, another evaluates and returns feedback, and the loop repeats until the evaluator accepts. The previous note gave its ceiling: the loop is as good as the evaluator's false-positive rate. It fits when the criteria are clear and a critique measurably improves the next draft, as in translation with a reviewer or code with tests.

**Autonomous agents.** The model decides the steps, calls tools in a loop, reads the environment's feedback, and stops by itself or at a budget, the loop of [ReAct and the agent loop](/notes/agents/react-and-the-agent-loop). It fits open-ended problems where the number and order of steps cannot be predicted, and it needs the safeguards of the earlier notes: sandboxes, budgets, confirmation before side effects, and tests on many runs.

### When a fixed workflow is the better design

A decision list, from the cheapest design to the most expensive:

1. If one call with good retrieval and examples solves the task, stop there.
2. If the steps are known in advance, write them as a chain, with gates where a check is possible.
3. If inputs fall into classes that need different handling and a router can be made accurate, route.
4. If parts are independent, run them in parallel; if a single answer is unreliable and answers can be compared, vote.
5. If a result can be checked and improved by critique, add an evaluator loop.
6. Only if the steps depend on what earlier steps reveal, and a wrong step can be detected or undone, let a model choose them: an orchestrator for decomposition, an agent for open-ended work.

Each move down the list buys flexibility with tokens, latency and predictability. The [Evaluating agents](/notes/agents/evaluating-agents) note gives the measurements that justify a move. A design that combines patterns is normal: a router in front of several chains, one of which is an agent with an evaluator.

## Frameworks

Agent frameworks package the plumbing these patterns share. Two families matter, and both change quickly; the dates here are those of first public releases.

- **Graph orchestration libraries**, such as LangGraph (first released in January 2024), describe an application as a **state graph**: a typed state (messages plus application fields), nodes that are functions from state to an update, edges that may be conditional on the state, and a **checkpointer** that saves the state after every step under a thread identifier. The [NLP course](/notes/nlp/tools-and-agents#where-the-memory-of-a-conversation-lives) built a conversation memory this way. Chains, routers and evaluator loops map directly onto nodes and edges; an agent is a node that calls the model and an edge that loops back while tool calls remain.
- **Agent SDKs from model providers** package the agent loop itself: a model with instructions and tools, a runner that executes tool calls and feeds results back, hand-offs between agents, guardrails that check inputs and outputs, and tracing. OpenAI's Agents SDK appeared in March 2025, Google's Agent Development Kit in April 2025, and Anthropic's Claude Agent SDK under that name in September 2025, as a rename of the Claude Code SDK.

What to ask of any framework is the same: can every prompt and every model response be seen and logged; is state persisted so that a run can be resumed or replayed; can a person interrupt the loop and approve an action; and does it get out of the way when a step is better written as plain code. Anthropic's advice is to start with direct calls to the model's API and adopt a framework only with an understanding of the code underneath ([Anthropic, 2024](#references)), because an abstraction that hides the prompt also hides the bug.

## The Model Context Protocol

Every application that wants a model to use a tool must describe the tool, call it and return the result. Without a standard, $M$ applications and $N$ tools need up to $M \times N$ integrations; with one, $M + N$. The **Model Context Protocol** (MCP), released by Anthropic in November 2024 and donated in December 2025 to the Agentic AI Foundation under the Linux Foundation, is that standard. It borrows its design from the Language Server Protocol, which did the same for programming languages and editors. The description below follows the specification revision `2026-07-28`, current in October 2026 ([MCP specification](#references)).

**Roles.** A **host** is the application the user runs (a chat application, an IDE, a coding agent); it owns the model, the conversation and the user's consent. The host creates one **client** per connected server, and each client talks to exactly one **server**, a program that exposes capabilities, running locally as a subprocess or remotely behind a URL. A design principle of the specification is that servers do not see the whole conversation or each other: the host decides what each server receives.

**Server features.** Servers offer three kinds of thing:

- **tools**, functions for the model to call, each with a name, a description and a JSON Schema for its input (and optionally its output), discovered with `tools/list` and invoked with `tools/call`;
- **resources**, data addressed by a URI (a file, a database row, an API response) for the application or the model to read, listed with `resources/list` and fetched with `resources/read`;
- **prompts**, templated messages and workflows offered to the user, such as a "review this pull request" command.

On the other side, servers can ask the client for input from the user (**elicitation**). Two older client features, letting a server request a completion from the host's model (sampling) and telling a server which directories it may use (roots), were deprecated in the 2026 revision.

**Messages.** All messages are JSON-RPC 2.0: **requests** with a method, parameters and an `id` that must not be null; **responses** with the same `id` and either a `result` or an `error`; and **notifications**, which have no `id` and get no response. A tool call and its result, shortened from what the Code section prints:

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "get_order", "arguments": {"order_id": "A-1001"},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
{"jsonrpc": "2.0", "id": 3,
 "result": {"resultType": "complete", "isError": false,
            "content": [{"type": "text", "text": "{\"total\": 40.0, \"status\": \"delivered\"}"}],
            "structuredContent": {"total": 40.0, "status": "delivered"}}}
```

Errors come in two kinds, and the distinction matters for agents. A **protocol error**, such as an unknown tool or a malformed request, is a JSON-RPC `error` for the client. A **tool execution error**, such as an argument out of range or a failed API call, is an ordinary result with `isError: true` and a message in `content`, meant for the model, which can read it and retry with corrected arguments, as in [Tool use and function calling](/notes/agents/tool-use-and-function-calling#errors-and-retries): the external feedback of the previous note.

**One exchange, step by step:**

<McpExchange />

1. **Discover.** The client may call `server/discover` to learn the protocol versions, capabilities and instructions of the server.
2. **List.** `tools/list` returns the tools with their schemas, in a deterministic order so that the host can cache them and keep the model's prompt cache warm ([Context and memory](/notes/agents/context-and-memory#prompt-caching-as-economics)).
3. **Present.** The host puts the tool descriptions into the model's context.
4. **Decide.** The model emits a tool call. The host checks it against the user's consent: the specification requires explicit consent before any tool is invoked and says a person should be able to deny each invocation.
5. **Call.** The client sends `tools/call` with the arguments and the per-request metadata; the server validates the arguments against the schema, runs the tool and returns `content`, optionally `structuredContent`, and `isError`.
6. **Observe.** The host appends the result to the model's context as an observation, and the loop continues.

**Transports.** Two are standard. With **stdio**, the client launches the server as a subprocess and they exchange one JSON-RPC message per line over standard input and output; the server may log to standard error. With **Streamable HTTP**, the server is a web service and each request is an HTTP POST whose response is either a JSON body or a stream of server-sent events; HTTP servers use the protocol's OAuth-based authorization. The earlier HTTP-with-SSE transport is deprecated.

**Revisions.** The protocol is dated by revision, and agents meet servers of several revisions at once:

| revision | main changes |
| --- | --- |
| `2024-11-05` | first public version: an `initialize` handshake that negotiates version and capabilities, then a stateful session; tools, resources, prompts, sampling; stdio and HTTP with server-sent events |
| `2025-03-26` | OAuth 2.1 authorization; Streamable HTTP replaces HTTP with SSE; tool annotations such as read-only or destructive |
| `2025-06-18` | structured tool output; elicitation; resource links in tool results; JSON-RPC batching removed |
| `2025-11-25` | experimental tasks for long-running requests; URL-mode elicitation; tool-calling inside sampling |
| `2026-07-28` | stateless: no handshake and no protocol sessions; every request carries its version and client capabilities in `_meta`; `server/discover`; every result has a `resultType`; sampling, roots and logging deprecated; tasks moved to an extension |

The 2026 change is the one to understand. Earlier revisions began every connection with `initialize`, after which the server could keep per-session state. In the stateless revision every request is self-contained, which lets a remote server run behind ordinary load balancers, and state that must span calls (a shopping basket, an open browser) is held by the server under an explicit handle that the model passes back as an ordinary tool argument. Clients that must talk to both kinds of server probe with `server/discover` and fall back to `initialize` if the server does not understand it.

**Security.** A protocol that lets any program offer tools to a model widens the attack surface. Tool descriptions and annotations come from the server and must be treated as untrusted unless the server is: a description can contain instructions aimed at the model. Tool results are data, not instructions. The specification puts consent and authorization on the host, not on the protocol, which cannot enforce them. [Agent security and prompt injection](/notes/agents/agent-security) treats these attacks and their defences.

### Agent2Agent

MCP connects an agent to tools. **Agent2Agent** (A2A), announced by Google in April 2025 and moved to the Linux Foundation in June 2025, connects agents to each other when neither is a tool of the other, for instance agents built by different organizations. An agent publishes an **Agent Card**, a JSON document at a well-known URL that describes its skills, its endpoint and its authentication; another agent sends it a **task** and follows the task through its states to the result. It also uses JSON-RPC over HTTP. As of October 2026 MCP is far more widely deployed; [Multi-agent systems](/notes/agents/multi-agent-systems) returns to agents that talk to agents.

## What changed

| | one agent with every tool | composed workflows over a protocol |
| --- | --- | --- |
| who decides the next step | the model, always | code, except where the steps cannot be known |
| checks between steps | none unless the model asks | gates, routers, evaluators |
| cost and latency | unbounded without budgets | fixed by the design, parallel where possible |
| reproducibility | low | high for the fixed parts |
| how tools are connected | custom code per application | one server per tool, any host can use it |
| tool calls on the wire | an application's private format | JSON-RPC: `tools/list`, `tools/call`, results with `isError` |

## Limitations

- **The taxonomy is a vocabulary, not a theory.** The patterns come from practice; real systems mix them, and choosing among them is an empirical question answered by evaluation on one's own task.
- **Workflows are brittle at their edges.** A router has no route for an input nobody anticipated, and a chain cannot recover from a failure its gates do not detect.
- **Frameworks and protocols move fast.** The SDKs named above changed their interfaces within months of release, and MCP has had five revisions in under two years, the last of which removed its handshake; code written against one revision may not speak to a server of another.
- **A protocol does not make a tool safe.** MCP standardizes how tools are described and called, not whether a description is honest or a call is wise; consent, sandboxing and least privilege remain the host's job.
- **Interoperability between agents is young.** A2A and similar protocols have little deployed evidence behind them as of 2026.

## What you should remember

- The augmented LLM (a model with retrieval, tools and memory) is the building block; workflows arrange calls in code, agents let the model choose.
- Five workflows: prompt chaining with gates, routing, parallelization by sectioning or voting, orchestrator–workers, and evaluator–optimizer. Their arithmetic is simple: chains multiply step success, gates raise it, routing pays only when the router is accurate enough, voting gains less than independence suggests.
- Use the simplest design that measurably works; move a decision into the model only when it depends on what earlier steps reveal.
- Frameworks provide state graphs with checkpointing or a packaged agent loop with tools, hand-offs, guardrails and tracing; choose one whose prompts and state you can see.
- MCP connects hosts to tool servers: one client per server, tools, resources and prompts, JSON-RPC requests and results, protocol errors for the client and tool execution errors for the model, stdio and Streamable HTTP. Since the `2026-07-28` revision it is stateless, with per-request metadata and `server/discover`. A2A connects agents to agents.

## Code

An in-process tool server and client that speak JSON-RPC 2.0 with the method names, metadata and result shapes of the `2026-07-28` revision of MCP, a minimal JSON Schema check for tool arguments, the two kinds of error, and a routing workflow whose refund route is a short chain with a gate and a confirmation step. The classifier and the extraction step are scripted stand-ins (keyword rules and a regular expression); with a real model each would be one call with a structured output, and the server, client, wire format and workflow would stay as they are. A real host would also run the server as a subprocess over stdio or reach it over HTTP instead of calling it in-process. Standard library only; the script runs instantly and has no randomness.

```python
import json, re

VERSION = '2026-07-28'

# 1. a minimal JSON Schema check: the subset that tool schemas usually need
def validate(value, schema, path='arguments'):
    t = schema.get('type')
    kinds = {'object': dict, 'string': str, 'number': (int, float), 'integer': int, 'boolean': bool}
    if t and not isinstance(value, kinds[t]) or (t in ('number', 'integer') and isinstance(value, bool)):
        return f'{path}: expected {t}'
    if t == 'object':
        for k in schema.get('required', []):
            if k not in value: return f'{path}: missing required property "{k}"'
        props = schema.get('properties', {})
        if schema.get('additionalProperties') is False:
            extra = sorted(set(value) - set(props))
            if extra: return f'{path}: unexpected property "{extra[0]}"'
        for k, sub in props.items():
            if k in value:
                err = validate(value[k], sub, f'{path}.{k}')
                if err: return err
    if 'minimum' in schema and value < schema['minimum']: return f'{path}: must be at least {schema["minimum"]}'
    if 'pattern' in schema and not re.fullmatch(schema['pattern'], value): return f'{path}: does not match {schema["pattern"]}'
    return None

# 2. a tool server: JSON-RPC 2.0 over newline-delimited JSON, stateless, with the 2026-07-28 method names
ORDERS = {'A-1001': {'total': 40.0, 'status': 'delivered'}, 'A-1002': {'total': 15.5, 'status': 'in transit'}}
DOCS = {'returns': 'Items can be returned within 30 days of delivery.', 'shipping': 'Standard shipping takes 3 to 5 days.'}
TOOLS = [
    {'name': 'get_order', 'description': 'Look up an order by its id.',
     'inputSchema': {'type': 'object', 'properties': {'order_id': {'type': 'string', 'pattern': r'A-\d{4}'}},
                     'required': ['order_id'], 'additionalProperties': False}},
    {'name': 'refund', 'description': 'Refund part or all of an order. Side effect: moves money.',
     'inputSchema': {'type': 'object', 'properties': {'order_id': {'type': 'string', 'pattern': r'A-\d{4}'},
                                                      'amount': {'type': 'number', 'minimum': 0}},
                     'required': ['order_id', 'amount'], 'additionalProperties': False},
     'annotations': {'destructiveHint': True}},
    {'name': 'search_docs', 'description': 'Search the help pages.',
     'inputSchema': {'type': 'object', 'properties': {'query': {'type': 'string'}}, 'required': ['query']}},
]

class ToolServer:
    def handle_line(self, line):                                 # one request in, one response out
        req = json.loads(line)
        rid, method, params = req.get('id'), req.get('method'), req.get('params', {})
        def error(code, message, data=None):
            e = {'code': code, 'message': message} | ({'data': data} if data else {})
            return json.dumps({'jsonrpc': '2.0', 'id': rid, 'error': e})
        def result(body):
            body = {'resultType': 'complete'} | body | {'_meta': {'io.modelcontextprotocol/serverInfo': {'name': 'shop', 'version': '0.1'}}}
            return json.dumps({'jsonrpc': '2.0', 'id': rid, 'result': body})
        meta = params.get('_meta', {})
        if 'io.modelcontextprotocol/protocolVersion' not in meta or 'io.modelcontextprotocol/clientCapabilities' not in meta:
            return error(-32602, 'Invalid params: missing required _meta fields')
        if meta['io.modelcontextprotocol/protocolVersion'] != VERSION:
            return error(-32022, 'Unsupported protocol version',
                         {'supported': [VERSION], 'requested': meta['io.modelcontextprotocol/protocolVersion']})
        if method == 'server/discover':
            return result({'supportedVersions': [VERSION], 'capabilities': {'tools': {}}})
        if method == 'tools/list':
            return result({'tools': TOOLS})
        if method == 'tools/call':
            tool = next((t for t in TOOLS if t['name'] == params.get('name')), None)
            if tool is None: return error(-32602, f'Unknown tool: {params.get("name")}')
            args = params.get('arguments', {})
            err = validate(args, tool['inputSchema'])
            if err:                                              # a tool execution error: the model can fix its arguments
                return result({'content': [{'type': 'text', 'text': err}], 'isError': True})
            out = self.run(tool['name'], args)
            return result({'content': [{'type': 'text', 'text': json.dumps(out)}], 'structuredContent': out, 'isError': 'error' in out})
        return error(-32601, f'Method not found: {method}')
    def run(self, name, args):
        if name == 'get_order': return ORDERS.get(args['order_id'], {'error': 'no such order'})
        if name == 'refund':
            o = ORDERS.get(args['order_id'])
            if o is None or args['amount'] > o['total']: return {'error': 'refund exceeds the order total'}
            return {'refunded': args['amount'], 'order_id': args['order_id']}
        if name == 'search_docs':
            hits = [v for k, v in DOCS.items() if k[:5] in args['query'].lower()]
            return {'results': hits}

# 3. a client: one per server; it attaches the protocol version and its capabilities to every request
class Client:
    def __init__(self, server, version=VERSION):
        self.server, self.version, self.next_id, self.wire = server, version, 0, []
    def request(self, method, **params):
        self.next_id += 1
        params['_meta'] = {'io.modelcontextprotocol/protocolVersion': self.version,
                           'io.modelcontextprotocol/clientCapabilities': {},
                           'io.modelcontextprotocol/clientInfo': {'name': 'demo-host', 'version': '0.1'}}
        line = json.dumps({'jsonrpc': '2.0', 'id': self.next_id, 'method': method, 'params': params})
        assert '\n' not in line                                  # stdio framing: one message per line
        reply = self.server.handle_line(line)
        self.wire += [line, reply]
        return json.loads(reply)
    def call(self, name, **arguments):
        return self.request('tools/call', name=name, arguments=arguments)['result']

server = ToolServer()
client = Client(server)
print(client.request('server/discover')['result']['supportedVersions'])        # ['2026-07-28']
print([t['name'] for t in client.request('tools/list')['result']['tools']])      # ['get_order', 'refund', 'search_docs']
r = client.call('get_order', order_id='A-1001')
print(client.wire[-2]); print(client.wire[-1])                 # the two lines on the wire
# {"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "get_order", "arguments": {"order_id": "A-1001"}, "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}, "io.modelcontextprotocol/clientInfo": {"name": "demo-host", "version": "0.1"}}}}
# {"jsonrpc": "2.0", "id": 3, "result": {"resultType": "complete", "content": [{"type": "text", "text": "{\"total\": 40.0, \"status\": \"delivered\"}"}], "structuredContent": {"total": 40.0, "status": "delivered"}, "isError": false, "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "shop", "version": "0.1"}}}}
print(client.call('refund', order_id='A-1001', amount=-5)['content'])          # a tool execution error, for the model
# [{'type': 'text', 'text': 'arguments.amount: must be at least 0'}]
print(Client(server, version='2025-11-25').request('tools/list')['error'])     # protocol errors, for the client
# {'code': -32022, 'message': 'Unsupported protocol version', 'data': {'supported': ['2026-07-28'], 'requested': '2025-11-25'}}
print(client.request('tools/call', name='delete_everything', arguments={})['error'])
# {'code': -32602, 'message': 'Unknown tool: delete_everything'}

# 4. a routing workflow: a scripted classifier picks a route; each route is a fixed chain of steps with a gate
def classify(message):                                           # stand-in for one small model call
    m = message.lower()
    if 'refund' in m or 'money back' in m: return 'refund'
    if '?' in m: return 'question'
    return 'other'

def refund_route(message, approve):
    calls = 1                                                    # the classifier
    oid = re.search(r'A-\d{4}', message)
    amount = re.search(r'(\d+(?:\.\d+)?) ?(?:dollars|usd|\$)', message.lower())
    calls += 1                                                   # extraction: one model call with a schema
    if not oid: return 'ask the user for the order id', calls
    order = client.call('get_order', order_id=oid.group())['structuredContent']
    amt = float(amount.group(1)) if amount else order.get('total', 0.0)
    if 'error' in order or amt > order['total']:                 # gate: a programmatic check between steps
        return 'escalate to a person: the request does not match the order', calls
    if not approve(oid.group(), amt):                            # a person confirms every side effect
        return 'refund declined by the reviewer', calls
    out = client.call('refund', order_id=oid.group(), amount=amt)['structuredContent']
    return f'refunded {out["refunded"]} on {out["order_id"]}', calls

def question_route(message):
    hits = client.call('search_docs', query=message)['structuredContent']['results']
    return (hits[0] if hits else 'no answer in the help pages; escalate'), 2   # classifier + answer

def workflow(message, approve=lambda oid, amt: amt <= 50):
    route = classify(message)
    if route == 'refund': return route, *refund_route(message, approve)
    if route == 'question': return route, *question_route(message)
    return route, 'hand over to a person', 1

for msg in ['I want a refund of 12 dollars for A-1001', 'Please refund A-1002, 99 dollars',
            'How long does shipping take?', 'What is your returns policy?', 'You are great']:
    print(workflow(msg))
# ('refund', 'refunded 12.0 on A-1001', 2)
# ('refund', 'escalate to a person: the request does not match the order', 2)
# ('question', 'Standard shipping takes 3 to 5 days.', 2)
# ('question', 'Items can be returned within 30 days of delivery.', 2)
# ('other', 'hand over to a person', 1)
print(len(client.wire) // 2, 'requests on the wire')               # 10 requests on the wire
```

Every route uses at most two model calls and two tool calls, and the refund that exceeds the order total never reaches the refund tool: the gate stops it in code. An agent given the same tools could handle requests that no route anticipates, at the price of an unbounded number of calls and a decision about the refund that only a check like this gate could make safe.
