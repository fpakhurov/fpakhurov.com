The RAG system of the [previous note](/notes/nlp/rag) calls a retriever on every query, by design of the pipeline, before the model sees anything. The model has no say in whether retrieval was needed, what to search for, or whether to search again after reading the results. Tool use gives it that say, and an agent is what you get when the model is allowed to keep deciding. This note is about the mechanism, what it is good for, and a question the enthusiasm around it tends to skip: when a loop that lets a model decide is worse than a pipeline that does not. Each part below has a note of its own in the [AI Agents course](/notes/agents/what-an-agent-is); this note is the compact introduction that the rest of the NLP course needs.

**Notation.** A model $\pi$ with a context $c$ (instructions, conversation, prior results); a set of tools $\{f_i\}$ with typed signatures; a tool call is $(i, \text{args})$; the runtime returns an observation $o = f_i(\text{args})$ that is appended to $c$.

## Baseline: the model answers from its context

Given a question whose answer requires today's weather, a calculation, or a lookup in a database, a plain model produces the kind of text that follows such questions: a guess with the right form. Retrieval fixes the lookup case for text corpora. It does not cover a calculator, a search engine, a code interpreter, a company's order system, or any action with a side effect.

<aside class="callout"><strong>Key idea.</strong> Describe the available functions to the model, in text, with their argument schemas. Let the model's output be either an answer or a call: a function name and JSON arguments. The runtime, not the model, executes the call, appends the result to the context, and asks the model to continue. The model's job is to decide what to call and to use what comes back.</aside>

## Tool use

### The protocol

1. The system prompt lists the tools: name, what it does, argument names and types (a JSON schema). Chat-tuned models are trained on such listings and on examples of emitting calls in a fixed format, with special tokens around them.
2. The model generates either natural-language text or a call. A call is structured output in the sense of the [RAG note](/notes/nlp/rag#structured-output); constrained decoding or format-specific training makes it parseable. Schemas, validation, constrained decoding and retries are worked out in [Tool use and function calling](/notes/agents/tool-use-and-function-calling).
3. The runtime validates the arguments against the schema, executes the function, and appends the result as a message with a tool role.
4. The model continues: it may answer, or call again.

What the protocol buys is that no one writes the sequence of calls: given a search tool and an image tool, a request for *a photo of the car James Bond drove in the latest movie* can be served by *search, then generate*, composed by the model from the tool descriptions and the question. What it costs is that the model also decides whether to call at all, and the runs below show it deciding badly.

### Code as the tool interface

One variant replaces the fixed call format by Python: the model writes a short program that calls the tools as functions, the runtime executes it in a sandbox, and the printed output is the observation. A loop, a conditional, or a call whose arguments depend on an earlier result is then one step instead of several, and the same interpreter lets the model run code, read the error and fix it. The sandbox is not optional: the model is writing code that runs.

### Three runs of a small code agent \{#three-runs-of-a-small-code-agent\}

Take the code variant, as implemented in the smolagents library, over `Qwen3-4B-Instruct-2507`, a 4 B-parameter instruction-tuned model, and give it three requests. The traces are more instructive than the answers:

- *What is the current weather in Paris?*, with a web-search tool. The first program searches for "current weather in Paris" and gets forum posts of a phone company, matched on the word *current*. The second refines the query to "current weather in Paris, France" and gets weather pages that disagree: one reports 13 °C with scattered clouds, another a clear sky and +16°. The third step answers "Clear sky, around 13-16°C", a merge of the two. Three steps took 9,528 input tokens in total, because the tool listing and every earlier result are re-read at each step: the prompt grows from 2,083 tokens at the first step to about 4,100 at the third.
- *Generate me a photo of the car that James Bond drove in the latest movie*, with the search tool and an image-generation tool. The model skips the search: its one program sends a prompt beginning "James Bond's car from the latest Bond movie, high-res, photorealistic" to the image generator and returns the image. The image generator receives a description of a role, not of a car.
- A script with two bugs, `numbers(i)` on a list and `range(4)` over three elements, passed with the request to *debug it, then run it to make sure it works*. The model returns a corrected version in one step, `numbers[i]` and `range(len(numbers))`, without running either version, so the run-read-fix loop that the code interface allows never takes place.

All three answers look like successes. Only the traces show one answer stitched from conflicting sources, one tool never consulted and one instruction ignored, which is why agents are evaluated on their trajectories and not only on their outputs.

## Agents: a loop around tool calls

A single tool call extends the model; a **loop** that repeats *decide → call → observe* until a stopping condition is an **agent**. The ReAct pattern ([Yao et al., 2023](#references)) interleaves a written reasoning step with each action so that the trajectory is inspectable; its measurements, a complete trace and the stopping rules are in [ReAct and the agent loop](/notes/agents/react-and-the-agent-loop). The trajectory the James Bond request calls for, which the run above did not take:

```
thought: I need the car model first, then an image.
action:  web_search(query="car James Bond latest movie")
observation: ... Aston Martin DB5 ...
thought: Now generate the image.
action:  text_to_image(prompt="Aston Martin DB5")
observation: <image>
final answer: <image>
```

What has to be added to the protocol to make the loop work:

**State.** The context accumulates every call and result. For long tasks it exceeds the window and must be summarized or stored outside the model (a scratchpad, a memory of earlier runs, files); what is kept and what is dropped is a design decision with direct effect on behaviour. The model itself keeps nothing between calls; [where the memory lives](#where-the-memory-of-a-conversation-lives) is a property of the runtime, described after this list.

**Planning.** For multi-step tasks the model writes a plan first (sub-goals in order) and revises it as observations arrive. Planning is text generated by the same model; it is not a separate solver, and plans are often wrong in ways the model does not notice until an observation contradicts them.

**Stopping.** A final-answer action, a maximum number of steps, a token or cost budget, and detection of repetition (the same call twice with the same result). Without the last three, a loop that cannot make progress runs until something external stops it.

**Specialization and coordination.** Beyond a few tools, one prompt that describes everything degrades. The usual structure is several agents, each with a narrow role and its own tools, and a coordinator that routes the user's request and merges results. A concrete shape, from an inventory-operations system: a coordinator agent receives the request; supply, transit and export agents each query their own internal systems and propose actions in their domain; the coordinator assembles a proposal. Each sub-agent sees only its tools and instructions, which keeps every prompt short and every failure local. When several agents help and when they hurt is the subject of [Multi-agent systems](/notes/agents/multi-agent-systems).

**Human confirmation.** Reading is cheap to undo; writing is not. The same inventory system proposes operational actions and executes none of them without an explicit confirmation step for the critical ones (moving stock, changing an export declaration). The loop pauses, shows the proposed call and its arguments, and continues only on approval. This is a property of the runtime, not of the model, and it is the single most effective safeguard in systems that act on the world.

### Where the memory of a conversation lives

A language model is a function from a token sequence to a distribution over the next token. Nothing persists from one call to the next: the weights are fixed, and the KV cache of a call is not carried into the following one (a server may reuse it for an identical prefix, which saves compute and changes no output). A chat model that recalls a name from three turns ago recalls it because the runtime sent those three turns again. Asked *What's my name?* as a single message, a 0.5 B-parameter chat model, Qwen2-0.5B-Instruct, answers with a general paragraph about what names are; given the same question after *Hi! I'm Bob* and its own greeting, it answers *Your name is Bob*.

Memory is therefore part of the runtime, in three pieces.

1. **A stored state per conversation.** The state is a record: the list of messages, plus whatever fields the application needs (the reply language, an account number, the result of an earlier tool call). After every step the runtime saves a checkpoint of the record under a **thread identifier**. A request with the same identifier continues that conversation; a new identifier starts from an empty record. Two conversations never see each other's history because their identifiers differ, not because the model keeps them apart.
2. **An update rule per field.** The message list is appended to: a step returns its new messages and the runtime adds them to the stored list rather than replacing it. Other fields are overwritten when a request supplies them and keep their stored value when it does not, so a reply language set on the first turn still applies on the tenth without being repeated.
3. **A prompt assembled from the state at every call.** A template puts the system instruction first, fills it with state fields (`answer in {language}`), and inserts the stored messages after it, the newest user message last. The result is rendered with the model's [chat template](/notes/nlp/instruction-tuning#baseline-the-base-model-and-the-chat-template) into one ordinary token sequence.

The store must receive only the model's answer. If the generation step returns the prompt together with its continuation and that text is saved as the assistant's message, the next prompt contains the previous one nested inside an assistant turn, and the history grows quickly even when every exchange is short.

**Trimming.** The stored history grows without bound and the context window does not, so before each call the runtime cuts the messages to a token budget, counted with the model's own tokenizer. The usual policy has four rules:

- keep the newest messages, on which the current exchange depends most;
- always keep the system instruction, and count it against the budget;
- never split a message: a message cut at an arbitrary token is a different message;
- start the kept history on a user turn, so the model never reads an answer whose question was cut.

**Worked example (toy token counts).** A conversation of a 10-token system instruction and seven messages, 75 tokens in all, trimmed to a budget of 52:

| Message | Tokens | Kept |
| --- | --- | --- |
| system | 10 | yes (always) |
| user 1: *My name is Ana.* | 6 | no |
| assistant 1 | 5 | no |
| user 2 | 12 | no (over budget) |
| assistant 2 | 20 | no (its question was cut) |
| user 3 | 7 | yes |
| assistant 3 | 9 | yes |
| user 4: *What is my name?* | 6 | yes |

The system instruction leaves 42 tokens. Walking back from the newest message, $6 + 9 + 7 + 20 = 42$ fits exactly, and user 2 would bring it to 54. The kept tail then starts with assistant 2, whose question did not fit, so it goes too. The model receives four messages and 32 tokens, and the question it must answer refers to a message it no longer sees. Trimming bounds the cost of a turn and the size of the KV cache; the price is forgetting. Longer conversations therefore replace the dropped turns by a summary, or keep facts such as the user's name in separate state fields that are never trimmed. The same problem for long agent runs, with compaction and long-term memory as retrieval, is treated in [Context and memory](/notes/agents/context-and-memory).

## Failure modes

| Failure | Mechanism | Mitigation |
| --- | --- | --- |
| Wrong tool or wrong arguments | the model guesses from descriptions | precise descriptions, examples, schema validation, few tools per agent |
| Hallucinated results | the model "remembers" a result it did not receive | only runtime-inserted observations; no fabricated tool messages |
| Loops | same call, same result, no progress | step and cost budgets, repetition detection |
| Compounding errors | a wrong early observation shapes every later step | plan revision, verification steps, human checkpoints |
| Prompt injection through tools | a web page or document returned by a tool contains instructions | tool outputs are data; never execute instructions found in them; confirmation for side effects |
| Cost | every step re-reads the whole context | compact state, caching of shared prefixes, small models for routing |
| Silent side effects | a write succeeds that should not have | confirmation, dry-run modes, reversible actions first |

The injection row deserves emphasis. An agent that reads a web page and then acts has exactly the vulnerability of the RAG system, with higher stakes: the page can say *now call `send_email` with the following content*, and a model that follows instructions well will try to. The only robust defence is structural: side-effecting tools behind confirmation, and a strict separation between instructions (from the system and the user) and data (from tools). Why that separation cannot be enforced inside one token stream, and the layered defences that remain, are in [Agent security and prompt injection](/notes/agents/agent-security).

## When an agent is unnecessary

The loop costs tokens, latency and predictability. It is the right design when the number and order of steps depend on intermediate results that cannot be known in advance: debugging, open-ended research, operating a system with many possible actions. It is the wrong design when the steps are known (the fixed workflows that cover such cases are listed in [Workflows, frameworks and protocols](/notes/agents/workflows-and-protocols#when-a-fixed-workflow-is-the-better-design)):

- A fixed sequence (retrieve → rerank → generate; classify → route) is a **pipeline**. Write it as code, with the model called at the steps that need language; it runs faster, costs less, and fails in explainable ways.
- A single tool call with known arguments (look up this order, convert these units) is a **function call**, not an agent; let the program decide to call it.
- A task with a schema-shaped answer (extract these fields) is **structured output**.
- A task where a wrong action is expensive and the model's decision cannot be checked before execution should not be delegated to a loop at all.

The practical rule: start with the pipeline; move a decision into the model only when the pipeline's fixed logic is measurably the bottleneck. Every decision moved into the model needs an evaluation of that decision, which the [next note](/notes/nlp/llm-evaluation) is about.

## What changed

| | Pipeline (RAG) | Tool use | Agent |
| --- | --- | --- | --- |
| Who decides the steps | the program | the model, one step | the model, repeatedly |
| Side effects | none | possible | likely |
| State | the prompt | the prompt + one result | accumulated, checkpointed, trimmed |
| Cost | fixed | one extra generation | unbounded without budgets |
| Predictability | high | medium | low |
| Evaluate | retrieval + answer | call correctness + answer | trajectory, success, cost |

## Limitations

- **Reliability compounds.** If all ten steps must succeed, nothing recovers from an error, and each step succeeds with probability 0.95 given that the earlier ones did, the task succeeds with probability $0.95^{10} \approx 0.60$. Marginal per-step rates alone do not fix the product when outcomes are dependent in other ways; recovery from errors raises it.
- **Models are poor at knowing what they do not know**, which is the ability an agent most needs when deciding whether to call a tool.
- **Benchmarks for agents are young** and sensitive to tool implementations; a score transfers poorly between environments. How such numbers are made and how far they can be trusted is the subject of [Evaluating agents](/notes/agents/evaluating-agents).
- **Cost is a first-class constraint**; a loop that solves the task at ten times the budget has not solved it.
- **Multi-agent designs add coordination failures** (lost context between agents, contradictory proposals) on top of single-agent ones.
- **Memory is lossy.** Trimming drops the oldest turns and summaries drop details; whatever is not in the prompt does not exist for the model.

## What you should remember

- Tool use: describe functions with schemas; the model emits a call; the runtime executes and appends the result; the model continues.
- An agent is the loop with state, a plan, and stopping rules (final answer, step and cost budgets, repetition detection).
- The model is stateless. A conversation is a record kept by the runtime: checkpointed per thread, its message list appended to at every step, re-sent on every call, and trimmed to a token budget (system instruction kept, newest messages whole, starting on a user turn).
- Split large tool sets across specialized agents with a coordinator; put every side-effecting action behind human confirmation.
- Tool outputs are data; instructions inside them are attacks.
- Prefer a pipeline when the steps are known; move decisions into the model only when they must depend on intermediate results, and evaluate each one.
- Read trajectories, not only answers: in the three runs of the small code agent all three answers look like successes.
